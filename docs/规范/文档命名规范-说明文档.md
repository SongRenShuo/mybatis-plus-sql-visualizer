## SQL文件

1. **文档位置**: `docs/SQL文件/` 目录下。
2. **命名规范**: `{日期}-{时分}-{功能名}-sql.sql`
   - 日期格式：YYYYMMDD（例如：20260327）
   - 时分格式：HHMM（例如：1430）
   - 功能名：简短的中文功能描述
   - 示例：`20260327-1430-用户登录-sql.sql`、`20260327-1530-项目查询-sql.sql`
3. **文件格式**: SQL (.sql)
4. **数据库规范**:
   - 符合mysql5.6的规范
   - 所有表为千万级数据量设计
   - 索引设计要充分考虑查询效率
   - 所有表名使用小写，多个单词用下划线连接，避免使用中文
   - 字段名也使用小写，多个单词用下划线连接，避免使用中文。
   - 字段类型使用 InnoDB 存储引擎
   - 字段类型使用 UTF8MB4 字符集
   - 表需要有中文注释
   - 字段需要有中文注释
   - 字段类型使用 INT(11) 作为主键
   - 自增主键
   - 涉及到状态和类型的字段，请使用 TINYINT(4) 类型，并且每个状态和类型都对应一个固定的值且有中文注释，方便查询和维护。
   - 时间字段使用 bigint(20) 类型，单位为秒，存储 Unix 时间戳,时间字段的名的格式为 {功能}_time，例如：create_time、update_time、delete_time,分别表示创建时间、更新时间和删除时间 delete_time默认为0。

## 字典值

1. **文档位置**: `docs/SQL文件/` 目录下，与 SQL 文件一起管理。
2. **命名规范**: 与 SQL 文件一致，`{日期}-{时分}-{功能名}-sql.sql`，字典内容作为该功能 SQL 脚本的一部分。
3. **文件格式**: SQL (.sql)
4. **新增字典值规范**:
   - 新建字典时必须同时包含「字典类型表」和「字典项表」两条 INSERT 语句。
   - 使用 `ON CONFLICT ... DO NOTHING` 保证幂等，脚本可重复执行。
   - 字典 `code` 命名格式：`DIC_{功能/业务大写}`，例如 `DIC_MERCHANT_WALLET_CREDIT_STATUS`、`DIC_ORDER_TYPE`。
   - 字典项 `value` 使用固定数值（从 1 开始递增），`sort` 与 `value` 保持一致，`dic_status` 默认 1（启用）。
   - 每个字典项 `remark` 写明所属字典，格式为：`{字典name}-{字典项label}`。
   - 参考格式：

```sql
-- ============================================================
-- 字典类型表
-- ============================================================
INSERT INTO "public"."sys_dict_type" ("code", "name", "remark") VALUES
('DIC_MERCHANT_WALLET_CREDIT_STATUS', '商户钱包结算余额入账状态', '商户钱包结算余额入账状态')
ON CONFLICT ("code") WHERE deleted = 0 DO NOTHING;

-- ============================================================
-- 字典项表
-- ============================================================
INSERT INTO "public"."sys_dict_item" ("type_id", "label", "value", "sort", "remark", "dic_status")
SELECT t.id, v.label, v.value, v.sort, v.remark, 1
FROM "public"."sys_dict_type" t
CROSS JOIN (VALUES
  ('DIC_MERCHANT_WALLET_CREDIT_STATUS', '待入账', '1', 1, '商户钱包结算-余额入账状态-待入账'),
  ('DIC_MERCHANT_WALLET_CREDIT_STATUS', '已入账', '2', 2, '商户钱包结算-余额入账状态-已入账'),
  ('DIC_MERCHANT_WALLET_CREDIT_STATUS', '入账失败', '3', 3, '商户钱包结算-余额入账状态-入账失败')
) AS v(code, label, value, sort, remark)
WHERE t.code = v.code AND t.deleted = 0
ON CONFLICT ("type_id", "value") WHERE deleted = 0 DO NOTHING;
```

## 图片/设计稿

1. **文档位置**: `docs/images/` 目录下**按用途分子目录**（2026-09-12 起，此前不分层）：
   - `docs/images/` 根目录：**对外素材**——目前只剩 `{用途}-qr.png`（二维码）与 `{名称}.svg`（图标）。
   - `docs/images/design/`：**开发过程设计稿**——方案讨论用的静态示意图、状态对照图、配色稿等，仅被 `docs/` 内部文档引用，不对外发布。
   - **功能演示图不再入库（2026-10-27 起）**：README 与文档站的功能演示动图一律**引用官网稳定 URL**（`https://sql-visualizer.jvtools.cn/demo/{name}.gif`），仓库内不再保存副本。原 `demo-0N-{功能名}.gif` 与 `screenshot-0N-{功能名}.png` 已于 2026-10-27 全部删除（约 12MB），原因有两条：①它们是在**带 `Start Free Trial` 水印**的 IDE 里截的，属对外事故元素，且同一批文件被上传到了 Marketplace Screenshots；②README 早已改用官网 URL，这些副本已成孤儿，留着会被误当成可用素材。
   - **Marketplace Screenshots 的上传源**同样从文档站 `public/demo/` 取（那一批是无水印重录版），不要在仓库内再存一份。
2. **命名规范**: `{任务号}-{说明}.png`
   - 任务号：开发计划文档的任务编号（如 `T-CrudColor`、`T-LogRowNumber`）；无任务号的通用稿用 `{主题}-{说明}.png`
   - 说明：简短英文小写，多词用连字符连接；同一任务多张图用不同说明区分
   - 示例：`T-CrudColor-outline-light-dark.png`、`T-CrudColor-outline-width.png`
3. **文件格式**: PNG（示意图/对照图，建议按 2x 缩放出图以适配 HiDPI）/ SVG（图标类矢量图）
4. **引用规范**: 文档内嵌图一律使用**文件相对路径**（基准=当前文档所在目录），如 `docs/开发计划/x.md` 内写 `../images/design/T-CrudColor-outline-width.png`、仓库根 `README.md` 内写 `docs/images/design/xxx.png`。理由=文件相对路径是**唯一在 Gitee / GitHub / VS Code / IDE 预览 / 本地 md 工具中全部正确**的写法；仓库根相对路径（在子目录文档里写 `docs/images/...`）在子目录文档中会解析失败。
   - **例外（不算引用）**：资源清单类表格里列「路径」时用**仓库根相对**写法（如 `| 图标 | docs/images/cool-request-icon.svg |`），因为它描述的是文件位置而非嵌入，与仓库内其他路径表述保持一致。
5. **嵌入语法**: 正文插图默认用 markdown `![说明](路径)`；**需要控制尺寸/对齐**时用 `<img src="路径" width="720" alt="说明"/>`（README 功能演示动图即此写法）。两者按需选择，不强制统一语法，但同一文档内保持风格一致。
6. **禁止内嵌外链图片**: 文档内不得使用 `https://gitee.com/.../raw/...` 之类**外链图片**——Gitee raw 对 `Referer: plugins.jetbrains.com` 返回 302 防盗链（见 `docs/memory-archive/pitfalls/pitfall-gitee-hotlink-302.md`），Marketplace 侧必然不可见；需外链时统一走 jsDelivr CDN，或改用 Marketplace 自有 Screenshots 区域上传。
7. **为何与对外素材分开**: 对外素材需长期稳定、不可随意改名删除（被 README / 介绍页 / Marketplace 引用）；设计稿随方案演进可能重出或废弃。混放会导致素材清理时误删对外图，或把过程稿误当成品发布。
8. **设计稿内容要求**: 手工渲染的示意图（非真机截图）在文档引用处必须**显式标注「设计稿，非实现截图」**，避免后续被误读为功能已实现。
