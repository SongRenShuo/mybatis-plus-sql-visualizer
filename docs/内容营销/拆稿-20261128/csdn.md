# MyBatis 的 N+1 排查指南：判定口径、面板用法与修复清单

**这篇适合谁**：接口越跑越慢、怀疑列表页有 N+1 但还没在日志里确认过的后端开发；或者已经确认了，想要一套能复验修复结果的判定口径。全文围绕一条可执行的规则展开，不堆工具清单。

## 一、N+1 是怎么产生的

N+1 的经典形态：列表页一条 SQL 查出 50 行，然后为了渲染每一行的关联字段，对每一行再各发一条详情查询。1 + 50，名字就这么来的。

它难缠在单条都不慢。本地开发数据少，列表几行，每条 1 毫秒，无感。到了预发或线上数据量上来，响应时间随行数线性变长，此时再查日志，面对的是几百行混排输出。

另一个高发入口是一对多懒加载。MyBatis 的 `collection` 嵌套、JPA 的 `@OneToMany` 默认懒加载，「访问到才查」，代码里一行循环访问，日志里就是一串重复 SQL。

## 二、日志里为什么难找

在日志里找 N+1 是三个动作：忽略参数记住形状、判断这些形状是否来自同一次请求、数次数。肉眼干这三件事都有障碍：

- 形状判断容易错。MyBatis 把 `Preparing:`（占位符）与 `Parameters:`（参数）分开打印，人要在脑内做参数化归一；
- 并发下交错。多请求的 SQL 按时间混排，同一次请求的几十条不一定相邻；
- 阈值说不清。重复 3 次算不算？没有规则就只能凭感觉。

## 三、判定口径（可执行）

把三个动作写严格，得到一条机器能执行的规则：

> 同一形状的 SQL——把 `?` 占位符和参数抹掉后文本一致——在同一个线程里、短时间内（默认 60 秒）重复出现 5 次以上，判为 N+1 嫌疑。

### 什么算「同形状」

按参数化模板比较，不是逐字符比较。`WHERE id = 1` 与 `WHERE id = 2` 是同一条模板。日志里 `Preparing:` 行本身就是模板，数它即可。

### 为什么要限定同线程

刻意收紧到线程级。并发场景下 10 个用户各查一次同一条 SQL 是正常业务，跨线程累计会把正常流量判成 N+1。按线程分桶之后，「循环里逐条查」这种同线程短窗重复才命中，误报面大幅缩小。

### 阈值与窗口

满 5 条判嫌疑（可调），更低的只给轻提示；时间用滑动窗而非全天累计，避免把一天里零散的同类查询攒成一桩旧案。

这套口径是 **MyBatis SQL Visualizer**（本文作者维护的 IDEA 插件）里 N+1 检测的实现标准：面板按模板聚合计数，≥3 条给琥珀色「×N 同模板」，同线程 60 秒滑窗 ≥5 条升级红色「疑似 N+1」。

## 四、用面板自动化这套判定

应用跑起来、SQL 日志面板开着，N+1 一旦发生：列表里那组同模板条目直接带红徽章；点徽章，列表收成一组，顶部给总数、首末时间、涉及线程（跨线程会明说）；每条条目带真实参数、耗时、影响行数与发起调用的源码位置，点击跳源码。

![N+1 红徽章与聚合视图](https://gitee.com/SongRenShuo/mybatis-plus-sql-visualizer/raw/master/docs/内容营销/img-20261128/nplus1-aggregate.gif)

两个常见疑问：关掉「SQL 去重」不影响检测，去重只管列表折叠，计数与判定解耦；报错语句与 ShardingSphere 改写条目都计入，N+1 经常藏在报错的那一圈。

## 五、修复与复验

- **改 JOIN**：列表页把关联字段一次查出来，SQL 变宽但条数归一；
- **改批量**：循环里逐条 `getById` 收成一次 `IN`（MyBatis-Plus `selectBatchIds`、JPA `@BatchSize`）；
- **改加载策略**：一对多改 `FETCH JOIN`、subselect 等批量加载形态。

改完重跑同一场景，红色徽章不再出现即修复完成——判定做成徽章的附带好处是修复有了可复验的判据。

## 六、不依赖工具的手工判定

只有一份日志时：取 `Preparing:` 行（它本身就是模板），按线程分组计数，同线程同模板 ≥5 即嫌疑。十行 Python 能做完，核心就一个动作：数同形状 SQL 出现了几次。

## 七、检查清单

1. 圈定一次请求的日志窗口；
2. 取 Preparing 行、抹参数、按「模板 + 线程」分组计数；
3. 同线程同模板 ≥5 → N+1 嫌疑，定位发起调用的源码行；
4. 按场景选修法（JOIN / 批量 IN / 加载策略）；
5. 重跑同一场景，确认计数降到阈值以下；
6. 跨线程的正常并发不计入，别把正常流量当 N+1 修。
