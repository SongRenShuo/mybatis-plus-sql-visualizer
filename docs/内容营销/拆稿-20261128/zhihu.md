# MyBatis 的 N+1 怎么找：数一数「同形状的 SQL」出现了几次

### 先说场景

一条列表请求，日志里跟了几十条长得很像的 SQL——这就是 N+1。列表本身一条查询，然后每一行的关联字段各查一次，1 + N，名字就这么来的。

它麻烦在单条都不慢。本地开发数据少，列表就几行，每条查询 1 毫秒，谁也不会注意。等数据量上来发现接口变慢，再去翻日志，面对的已经是几百行混在一起的输出。一对多的懒加载也一样：`collection` 嵌套、JPA 的 `@OneToMany`，代码里一行循环访问，日志里就是一串重复 SQL，写的时候每一行都合理，合在一起就是 N+1。

### 为什么肉眼找不动

在日志里找 N+1，实际是三个动作：忽略参数记住形状、判断这些形状是不是来自同一次请求、数次数。肉眼干这三件事都吃力。

形状判断容易错——MyBatis 把占位符和参数分开打，`Preparing:` 一行、`Parameters:` 一行，人要自己在脑子里做归一，参数一多就开始出错。并发下会交错——几个请求的 SQL 按时间混排，同一次请求的几十条不一定相邻。阈值也说不清——重复 3 次算不算？批量导出一次合理地查 20 个 id 算不算？没有规则就只能凭感觉。

### 判定其实是一条机械规则

把「肉眼在干嘛」写严格，就是这样一句话：

> 同一形状的 SQL（把 `?` 和参数抹掉后文本一致），在同一个线程里、短时间内（比如 60 秒）重复出现 5 次以上，判为 N+1 嫌疑。

每个限定词都有用意。同形状，是按参数化模板比，不是逐字符比。同线程，是刻意收紧的：并发场景下 10 个用户各查一次同一条 SQL 是正常业务，跨线程累计会把正常流量判成 N+1；按线程分桶后，「循环里逐条查」这种同线程短窗重复才命中。短时间用滑动窗而不是全天累计，免得把一天里零散的同类查询攒成一桩旧案。5 次是行动建议的门槛，比它低的只给轻提示，阈值应该可调。

### 让面板替你数

我自己的插件就是这么实现的（**MyBatis SQL Visualizer**，IDEA 里做 SQL 可见性的一个工具）：SQL 日志面板按参数化模板聚合计数，同线程 60 秒滑窗内满 3 条先给「×N 同模板」的琥珀色计数徽章，满 5 条升级成红色「疑似 N+1」。琥珀色是提示，红色是行动建议。

红徽章可以直接点开：列表收成这一组，顶部一行给总数、首末时间、涉及线程（分散在多个线程时会明说），每条还有真实参数、耗时和发起调用的源码位置。改完代码重跑同一场景，徽章不再出现，修复就算验收了。

### 修法与边界

修法没有秘密：改 JOIN、把循环里的逐条查询收成一次 `IN` 批量、一对多改批量加载形态，三选一看场景。难的不是修，是先找到。

边界也如实说：跨线程的正常并发不算，这是设计取舍不是漏报；它只负责发现和定位，不负责优化。就算手边只有一份日志，把参数抹掉、按形状分组、数次数，任何顺手的脚本都能做——N+1 判断的核心从来就是数同形状 SQL 出现了几次。
