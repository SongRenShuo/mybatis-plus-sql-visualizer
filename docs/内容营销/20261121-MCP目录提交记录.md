### 版本号为什么一直显示 v2026.11.24-beta.1（2026-11-27 查清）

**mcprush 自己不存版本号，它跟随 MCP Registry 记录**。后台 Releases 页原话：「one that installs from a repository or an address follows the version of its MCP Registry record the same way, unless a release of yours holds that version back or the label was set by us by hand」。

所以根因是 **Registry 从 11-24 之后就没更新过**——11-25 正式版、11-25-beta.1、11-26-beta.1、11-26-beta.2 四次发行都没同步上去。查 Registry：

```
GET https://registry.modelcontextprotocol.io/v0/servers?search=mybatis-plus-sql-visualizer
→ version: 2026.11.24-beta.1   （修复前）
```

**教训：发行新版后必须同步 Registry**，否则所有跟随 Registry 的目录（mcprush 这类）会一直停在旧版。

**已自动化（`a70cf6075`，2026-11-27 实测通过）**：`build-plugin.yml` 新增独立 job `registry`，`needs: [gate]` 与 `publish` **并行**，不占发行关键路径。要点：

| 项 | 做法 |
| --- | --- |
| 清单 | `dev-support/mcp-registry/server.json`（**不放仓库根**，避免与项目产物混淆） |
| 版本号 | CI 从 `gradle.properties` 读、用 `ConvertFrom-Json` 改写清单再发——清单里的值是占位，不靠人记得改（连漏四版就是因为靠人记） |
| 认证 | `mcp-publisher login github-oidc`，只需 job 级 `id-token: write`，**零 secret**、不碰 token.json |
| 二进制 | 从 `modelcontextprotocol/registry` 的 GitHub Release 取 v1.8.16 的 `linux_amd64` tarball（npm 上同名包是第三方浏览器工具，别用） |
| 失败处理 | `continue-on-error: true`——此时 Release 与插件包已发出，漏同步只是「目录显示旧版」，不该让发行红掉 |
| 校验 | 发完回读 Registry 确认本版被收录，否则 throw |

**首次真实运行读数**（run `45927546245`，release 模式）：

```
registry : 02:32:53 → 02:33:08   (15s)
publish  : 02:32:56 → 02:33:25   (29s)
```

两者同时启动、独立结束，registry 比 publish 早 17 秒完成 → **并行方案确实没拖慢发行**（若串在 publish 后，发行会多花约 15 秒）。job 日志逐行：

Registry 侧回读：`2026.11.27 | isLatest=True | updated=2026-11-27T02:33:03`，与该 job 的 `Successfully published` 时刻精确对上。

实际发布的版本号是 `2026.11.27`（不是 `2026.11.27-beta.1`）——那次发版在跑 CI 前已把 `gradle.properties` 改成正式号，CI 如实读到了。这验证了「清单 version 只是占位、实际以 `gradle.properties` 为准」的设计：以后发内测或正式版都不用手动改清单。

**顺手修掉的模板错误**：`.local/tools/mcp-publisher/tpl/server.json` 里 `repository.source` 写的是 `"git"`，这是记忆里记过的必错值（validate 阶段报 `invalid-repository-url`，必须写 `github`）。已改成 `github`。

**mcprush 后台的 CUT A RELEASE 对我们不生效**：表单（`cutVer` / `cutNote`）能填，Publish 按钮 `type=submit`、未禁用、命中判据全绿，但点击后无任何请求；Releases 页显示「No server of yours has a release yet」。结合上面的跟随机理，仓库安装型收录页不该走 release 通道，版本号只能靠 Registry 同步。

### mcp-publisher 的 device flow 输入框（2026-11-27 踩坑）

GitHub 的 `/login/device` 输入框是 **9 个 `input[id^=user-code-]`，其中 4+1+4——中间那个 `maxLength=-1` 是分隔符占位，其余 8 个都是 `maxLength=1` 的单字符框**。整段 set 值会被 React 受控组件打乱（实测填 `F1873F73` 变成 `AE969673`），必须逐框单字符输入。

另有两个连带坑：
- 先进 `/login/device/select_account`（Verify Session），要点一次 **Continue** 确认已登录账号，才到输入页
- `login github` 进程被 `timeout` 掐掉后设备码立即失效，但不报错；下次重跑会生成新码，**别拿旧码让用户输**（这轮连续给错三次码，都是这个原因）。判据：`grep -i code: /tmp/loginN.txt` 取当前进程的码，同时 `Get-Process mcp-publisher` 数进程数应为 1

**token 有效期**：`~/.config/mcp-publisher/token.json`，11-24 的 token 在 11-27 已过期（401 `token has invalid claims: token is expired`），需重新 `login github`。`mcp-publisher` 预编译二进制需从 `modelcontextprotocol/registry` 的 GitHub Releases 下载（当前 v1.8.16），本机之前装的那份已不存在。
