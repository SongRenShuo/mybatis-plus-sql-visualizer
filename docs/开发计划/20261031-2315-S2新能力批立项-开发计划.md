## §二 NEW-26 编辑器内 Inspection 体系（本批最高性价比）

**目标**：把「只读分析能力」从「用户主动点工具」变成「编辑器里自动标出来」，这是与竞品差距最大的一环（我方此前只有 `BannedApiInspection` 一个 inspection）。

**形态（经核实后的可行范围）**：
- 覆盖面＝**mapper XML 文件**（`<select>/<insert>/<update>/<delete>` 标签内文本）与 **Java/Kotlin 注解 SQL**（`@Select`/`@Update` 等）。预览面板与日志里的临时 SQL **不在覆盖面**（非源文件 PSI）。
- 判定复用：取 PSI 元素的文本 → 喂给既有 `checkSql` / `mapperCheck` → 解析结构化结果 → 报 problem。**不要把判定逻辑重写一遍**。
- 首批规则（按用户可感知度排序）：
  1. `${}` 拼接注入风险（已有 `BannedApiSourceScanTest` 的扫描判据可借）
  2. `#{}` 参数缺失（mapper XML 里有 `#{}` 但对应方法参数不存在）
  3. resultMap 列不存在（`<resultMap>` 声明的列在表定义/实体里找不到）
  4. 方言不兼容写法（借用 `DialectRegistry` 能力矩阵，如 MySQL 反引号写进 Oracle 方言文件）
  5. OGNL `test` 恒真/恒假（`test="true"`、`test="1==1"` 这类）

**QuickFix**：优先做「跳转到对应方法/参数」与「改为 `#{}`」两类；其余只报不改。

**待验证前提**：
- **P-1** 取 PSI 文本喂纯函数时，mapper XML 的文本是否已含 `<include>` 展开？若不含，判定会误报——先取证一个带 `<include>` 的 mapper。
- **P-2** 注解 SQL 的 PSI 文本可能带编译器插入的换行/缩进，判定前是否需归一化。
- **P-3** inspection 在 EDT/daemon 线程运行，`mapperCheck` 内部若触发渲染（含 PSI 读）是否满足平台的 read-action 纪律——参照 `BannedApiInspection` 的「薄壳」做法（只做 PSI 取数，匹配在纯逻辑层）。
- **P-4** 每条规则误报率：本仓 mapper 语料（`docs/需求文档/MPJ用法收集与兼容性测试清单.md` 的 92 个文件）先跑一遍，**误报为 0 才允许默认开**。

**判据**：五条规则各有正例 + 反例定向测试；inspection 注册进 `plugin.xml` 并过 `PluginXmlStructureGuardTest`；误报率在语料上为 0；每条规则配反向验证（摘掉判定必红）。

**优先级**：P1（本批最高）。

## §三 NEW-21 信创兼容性体检

**目标**：同一段 Wrapper/XML 一次渲染多方言，逐条标「保留字冲突 / 分页语法差异 / 函数不存在 / 隐式转换」，让用户在信创迁移前就看到风险。

**现状**：无批量渲染 API（§一）。渲染入口是 `Dialect` 驱动的单方言渲染。

**设计要点**：
- 新增编排层 `MultiDialectRenderPlan`：输入（SQL 或 Wrapper/XML 源 + 方言集合），输出「每方言一份渲染结果 + 差异清单」。
- **不要为它改渲染引擎**：逐方言调用既有渲染入口（`withResolvedDialect` 或等价入口），差异比较在编排层做。
- 差异分类四档（对应审计册原话）：保留字冲突（查 `Dialect.reserved`）、分页语法（查 `Dialect.limitRequiresOrderBy` 一类能力位）、函数不存在（查方言函数表）、隐式转换（需新增判据，可能降级为「不检测」）。
- 落地形态：诊断面板的一个新页签，或 `DiagnosticReportFormatter` 的一个新段（**推荐后者**，复用既有导出链，零新增 UI 面）。

**待验证前提**：
- **P-5** 逐方言渲染是否需要 PSI/工程上下文（若需要，编排层必须在有 project 的上下文里跑，不能放纯函数）。
- **P-6** 「隐式转换」是否可静态判定——若不可，本券只做前三档，并如实标注。

**判据**：给定一段 SQL + 14 方言，输出 14 行结果且差异分类正确；四个分类各配正例；渲染耗时在 200ms 内（14 次渲染，避免阻塞 EDT）。

**优先级**：P2。

## §四 首用即生效

**目标**：把「用户得先知道有这个功能」变成「打开项目就能看到」。

**现状**：`onboarding/OnboardingAnchorTip.kt` 只有锚点提示，无预热、无状态栏常驻入口。

**三项**：
1. **项目打开预热**：`postStartupActivity` 里预热方言映射与关键索引（注意：本仓有 `T-SqlDialectPrewarm` 的 EDT 慢操作前科，预热必须在 BGT，且不能拖慢启动）。
2. **状态栏常驻入口**：状态栏 widget 显示「本工程 SQL 预览可用 / 上次捕获 N 条」，点击开日志面板或预览。
3. **首用引导**：首次打开带 mapper 的工程时一次性提示（复用 NEW-19 版本亮点通知的防打扰三重约束：一次性 / 版本粒度 / headless 静默）。

**待验证前提**：
- **P-7** 预热是否已有等价实现（`T-SqlDialectPrewarm` 的 S1~S5 已落 master，但 R1/R2 运行期读数缺）——**先查，避免重复造**。
- **P-8** 状态栏 widget 在 Community 版是否可用（本仓已有 `ExecuteSqlSupport.isAvailable()` 的探测范式）。

**判据**：启动后状态栏出现 widget；首次打开 mapper 工程有一次性提示；预热不产生 EDT 慢操作断言（runIde 验）。

**优先级**：P2。

## §五 NEW-23 MCP 安全写路径三件套

**目标**：让 agent 能安全地走完「渲染 → 解释 → 回滚计划 → 执行」，且每一步都过既有闸门。

**现状**：三个工具都在（`sqlv_render_sql` / `sqlv_explain` / `sqlv_rollback_plan`），执行面有写安全闸门。

**设计要点**：
- 本券是**接线**不是新建：把三步串成一条可复用的「计划链」，输出一份「执行前清单」（SQL + 计划 + 回滚语句 + 风险等级）。
- **执行环必须走既有闸门**：`UnboundedWriteDetector`（无界写七规则）、只读豁免证明、`ExecutionDialectGate`。**不得新增绕过通道**。
- 新增面：一个 MCP 工具或一个编排入口（推荐前者，保持「11 工具」口径不变的话就做成现有工具的参数组合，**不新增工具数**——本仓红线「不做 MCP 工具数竞赛」）。

**待验证前提**：
- **P-9** 三步之间是否需要共享中间态（渲染结果 → EXPLAIN 输入 → 回滚计划的 before-image）；若需要，中间态放哪（内存/临时文件）且不能泄漏 SQL 明文。

**判据**：一条链跑通 DML 场景；回滚语句与执行目标一致；闸门反向验证（构造无界写 → 必须被拦）；不新增 MCP 工具数。

**优先级**：P2（接线活，成本低）。

## §六 S1-6 首页与描述文案重写

**目标**：对外表述从「能预览 SQL」升级为「14 方言 + 7 家信创 + EXPLAIN 解读 + 回滚计划」——预览已商品化（竞品普遍具备），不能再当第一卖点。

**现状**：`plugin.xml` description 里「预览」仍是高频词；且受 `PluginXmlStructureGuardTest` 四条约束。

**设计要点**：
- 首 40 字符英文摘要必须自成语义（守卫硬约束），建议：「14 database dialects, EXPLAIN insight, and rollback planning inside your IDE.」
- 中文正文按「能力分组」而非「功能罗列」：①方言与信创覆盖（14 方言 / 7 家信创 / 验证等级可查）②执行前解释（EXPLAIN 解读 + 索引建议）③变更安全（回滚计划 + 写安全闸门）④运行期捕获（agent 增强捕获，方言无关）⑤AI 协作（MCP 11 工具）。
- **数字声明必须与代码对账**（守卫会查）：14 方言 ↔ `DialectRegistry.dialects.size`、11 工具 ↔ `McpToolGate.TOOL_NAMES.size`。
- 描述改动走发行时序：只改 `plugin.xml` 不会立刻改线上（`preserveUIEdits=false` 随上传覆盖），需随发行或手动 PATCH。

**判据**：`PluginXmlStructureGuardTest` 四条全绿（含三条变异必红）；中英双语同构且中文在前；描述中「预览」不再作为独立卖点出现（可作为能力之一列在分组内）。

**优先级**：P1（与下一次发行绑定，成本低收益直接）。
