## 一、背景与现状锚点

T-ReleasePerf 系列第五期（T10，20261030，`90f3f95d`）收口后，两份权威读数把剩余空间钉在两处：

2. **全量测试的方差主体 ＝ T10 遗留未闭环的「同参数并发度不稳」**。同样 `maxParallelLimit=2`：B 轮真并发测试窗 670.5s（execSum 1149.2s），A 轮退化串行 1083.5s（execSum 1000.8s）——同码同参差 413s（§经验总结 20261030 §四 坑 1，§五.2 挂账）。A 轮唯一可观察差异：开局 `:sql-visualizer-agent:test` 失败（1 例 flake）。**在权威 releaseGate 里这个异常会致命**：T10 权威轮1 分片退化串行 ~23min > market 789s，分片窗反而成了关键路径（总 50min 的构成主体）。

**本册目标**：①verifyMarketplace 三目标并行化，把 market 段的串行等待窗叠起来；②测试链并发度稳定化——先取证 T10 遗留异常，再做零风险的排序加固，视取证结论落定向修复；③收口文档。

## 三、券详单

### 券01：verifyMarketplace 三目标并行化（market 段 789s → max(单目标)）

- **现状**：`verifyMarketplace` 单 JavaExec，命令行一次带 3 个目标目录，verifier-cli 串行逐目标解析。
- **修法**：拆 3 个单目标任务 `verifyMarketplace243` / `verifyMarketplace253` / `verifyMarketplace262`（helper 函数 `registerMarketTarget` 生成，参数面与现任务逐项对齐：在线、无豁免、代理注入、`-runtime-dir`、报告格式），加聚合任务 `verifyMarketplace`（**名字保留**——releaseGate dependsOn 与 `gradle-gate.ps1` 的命令匹配都认它）：
  - 每目标**独立 verifier home**：`resolveVerifierHome("marketplace-243" / "marketplace-253" / "marketplace-262")`——并发写互不可见，`assertNoForeignVerifier` 按各自子 home 判定不误伤；
  - 各子任务 doFirst/doLast 打带目标名的 START/END 锚点；zip 与 `-runtime-dir` 解析逻辑复用现实现；
  - **baseline verdict 判定整体迁到聚合任务 doLast**：遍历三个报告目录跑同一 `checkMarketplaceVerdicts`（基线文件按目标名匹配的切块逻辑不变）；子任务自身只负责「verifier 退出码非 0 即失败」（JavaExec 天然语义，与现任务一致）；
  - 聚合任务 dependsOn 三子任务、保留 START/END 锚点；releaseGate 编排不用改（认聚合名）。
- **refresh 适配**：`verifyMarketplaceRefresh` 改为对三个子 home **串行循环**各跑一次单目标 check（闲时任务不在关键路径，刻意不并行以免与主门禁争内存）；stamp 写三份或写主目录一份（实施时按 gate 脚本读取逻辑定，取简单者）。
- **磁盘代价**：3 home × ~3.3GB ≈ 10GB（现单 home 3.33GB，增量 ~7GB，落 `F:\gradle-home`）；D-208 决策点（§五）。
- **预期收益**：三目标的低占用等待窗并行重叠。保守按「243 目标（含 jbr，历史最重）≈ 关键路径 400~500s」估，market 段 789s → 450~550s，gate 总墙钟 802s → **~500~600s**。
- **验证**：W2 三子任务并发起跑（START 戳 <5s 簇）+ 六 verdict 与基线 parity + 三 home 各自「下载 0 B」（暖窗）+ 负向＝拔掉一个目标的报告目录，聚合 verdict 检查必须红。

### 券02：测试链并发度稳定化（取证 + 排序加固 + 视证据定向修复）

- **取证（E1/E2，先于任何代码改动）**：
  - E1：空闲机器同树连跑两轮 `testShards`（lane2），逐片采集 START/END 戳 + `laneOthers`（T10 已内置进程扫描版）——判「同参数并发形态是否可稳定复现」；
  - E2：复刻 A 轮形态——第二轮前先让 `:sql-visualizer-agent:test` 产生一次失败（临时在 agent 测试里注入必红用例**不落盘**，用 `-PtestShardConcurrency=2 --continue` 跑），对比并发形态是否随之退化；
  - 结论三分支：①不复现（E1 两轮都真并发）→ 登记为「机器负载依赖形态」，落监控与结论，不动调度；②E2 复现 → 深挖失败任务与 BuildService/调度器的交互（Gradle 9.7 源码级），落定向修复；③E1 就复现串行 → 机器态问题，由 T10 水位闸门与自适应档位兜底，登记结论。
- **零风险加固（无论取证结论如何都落）**：
  - **分片按权重降序注册**：5 片 lane2 = 波次 [1,2]/[3,4]/[5]，最轻的片留最后使末波尾巴最短；现在装箱均衡但注册顺序未定序。改法＝装箱完成后按片权重和降序注册 testShardN（纯排序，类集不变覆盖面不变）；
  - **`laneOthers` 与逐片 START 戳进 testShards 聚合报告**（execSum 台账旁加一列），让「并发形态」从靠人翻日志变成每轮自报。
- **视证据的定向修复（仅当 E2 复现）**：候选＝agent:test 失败后 `--continue` 场景下调度的许可归还路径（若实证 BuildService 租约在失败任务上悬挂，则把失败面的任务从限流面摘出或改自管信号量）；修法落地前先写小实验钉住根因，禁拍脑袋改调度。
- **预期收益**：方差收敛——独跑 testShards 从「670~1083s 双形态」收到稳定 ~500~600s（lane2）/ ~400s（lane3）；权威 gate 里消除「分片窗反超 market 成关键路径」的 50min 形态。
