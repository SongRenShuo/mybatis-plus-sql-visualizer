## 1. 问题

Mybatis-Flex-Helper 因弹窗骚扰被用户打出 1 星并弃用——「平均一小时一次弹窗，不如直接收费」式评论在 2024-10~2025-11 出现三次（第二轮报告 §4.4），是赛道内最完整的反面教材：体验差不止丢功能分，直接丢用户。

本插件当前的主动触点都有门禁（见 §2.1/§2.2），但「零弹窗导流」只是隐含在既有实现里，没有成文约定。插件仍在高频迭代（9 框架族、11 类触发面持续扩张），未来某个功能顺手加一个无门禁的主动弹窗、或加一条评分引导弹窗，就会重蹈 Flex-Helper 覆辙。本任务把红线固化成文档，防的是「顺手」。

## 2. 方案

纯约定任务，无生产代码改动：盘点触点存证、新建红线文档、接入文档检索索引。

### 2.3 红线内容草稿

允许类（默认放行）：

1. 用户操作反馈：点击按钮后的结果、错误、「未找到」类提示（含跳转失败提示）
2. 用户操作确认：破坏性操作（清空历史等）的 YesNo 确认、轻量输入框
3. 含开关的一次性通知：默认关或可永久忽略（现状基准：更新通知模式），同一触点每会话至多一次

禁止类（一律不做）：

1. 无开关的插件主动弹窗、导流弹窗（导流只走设置页与 README）
2. 营销/评分引导弹窗（评分引导只进 README 与更新通知正文链接）
3. 频率超限的任何主动触点（超「每会话一次」即违规）
4. 后台失败转弹窗（维持 M54 结论：主链失败面板内报错或静默降级）

新弹窗准入检查清单（五问，全过才准合入）：是否用户点击直接引发？面板内/通知形态是否确实不够用？是否带开关或一次性？频率上限是多少？是否已在红线文档触点清单登记？

登记义务：新增或移除主动触点须同步红线文档触点清单；文档头注明复核命令（§2.1 的 grep 一行），清单漂移以 grep 复核为准。
