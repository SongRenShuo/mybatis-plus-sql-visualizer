# T-ConsoleBind263：IDE 2026.3 移除 `setMapping(VirtualFile, LocalDataSource)`，换源弹窗退化为单源、点选无反应（2026-11-07）

- 立项：2026-11-07 16:45
- 状态：**已实施**（2026-11-07 17:16，分支 `t-consolebind263`，实现提交 `bd4eff85`；§八 V1 被推翻见 §12.1；定向测试与反向验证读数见 §12.4/§12.5）
- 目标分支：`master`
- 来源：用户在日常 IDEA 2026.3（`IU-263.7307.200`）打开 SQL 预览，报告「原始控制台的数据源切换又失效了：数据源列表点击切换后没反应，上方更多按钮里更是只要当前一个」
- 取证方式：IDEA 2026.3 日志（`%LOCALAPPDATA%\JetBrains\IntelliJIdea2026.3\log\idea*.log`）+ 本机 263 平台 jar 字节码（`javap` 等价的自写 class 解析）+ `master` `d88b6ea4` 源码静态走查。未跑构建与测试。

## 一、结论

**根因是平台 API 移除，不是插件逻辑回退。**

IDE 2026.3 删掉了 `com.intellij.database.dataSource.DataSourcePerFileMappingsImpl.setMapping(VirtualFile, LocalDataSource)`。
`ExecFileBinding.realignExecBind` 的反射写 per-file 关联这一步因此恒抛 `NoSuchMethodException`，于是：

1. 「清 pin」只完成了 `detachConsole`（这一步没坏），**per-file 关联没被清掉**；
2. 平台的 forced 关联仍在 → `DbImplUtil.getForcedDataSourceForExec` 命中 → runner 枚举被短路成**唯一一条**；
3. 于是换源弹窗只列当前源（用户说的「更多里只有当前一个」），点它就是同一源 → 重建出同方言控制台，看起来「没反应」；
4. 更严重的是第二张脸：从工具栏接管下拉里挑 `mpj_demo@localhost` 时，`preferredRunnerName` 在唯一 runner 集合里找不到同名项，链路落到 `single runner, run directly`，**静默用了被钉住的 Oracle 源**——用户以为换成了 MySQL，实际没有。

用户这次看到的是**同一个根因的两张脸**，不是两个缺陷。它和 2026-10-24 那份复盘里「切换数据源只有一个源 / 第一次能切第二次又只剩一个」是同一形态（forced 关联短路枚举），区别只是当年卡在「没有公开清除 API」，而 262 之后是靠 `DataSourcePerFileMappingsImpl.setMapping` 写通的；263 把这个口子收走了，改由 `DataSourcePerFileMappings.setMappingWithWriteAction(VirtualFile, LocalDataSource?, Runnable?)` 承担。

## 三、根因链与平台实证

### 3.1 263 平台 API 实测（本机 2026.3 安装目录 jar，字节码方法表）

| 类（263 所在 jar） | 方法 | 结论 |
|---|---|---|
| `com.intellij.database.dataSource.DataSourcePerFileMappingsImpl`（`intellij.database.core.impl.ex.jar`） | **无** `setMapping(VirtualFile, LocalDataSource)` | **本次回退的直接原因** |
| 同上 | `setMapping(VirtualFile, String)`，两参均 `@Nullable` | 可清（传 null 即移除）/可写（传数据源 id） |
| 同上 | `setMappingWithWriteAction(VirtualFile @NotNull, LocalDataSource @Nullable, Runnable @Nullable)` | **官方替代入口**，接口层同签名 |
| 同上 | `static setDataSourcePerFileMapping(Project, VirtualFile, LocalDataSource)` | 只能写、不能清 |
| 同上 | `static getInstance(Project)` / `static getDataSourcePerFileMapping(Project, VirtualFile)` | 未变，插件探针仍可用 |
| `com.intellij.database.console.DataSourcePerFileMappings`（`intellij.database.core.impl.jar`） | 接口已收窄为 `setMappingWithWriteAction(...)`、`setMappingWithWriteAction$default`、`getAttachedFiles`、`getInstance` | 说明 263 是「接口重做 + 旧重载下架」 |
| `DatabaseRunners` | `getSwitchDataSourceRunners(PsiFile, String, DatabaseSession, Consumer)` | 未变（四参，插件的反射签名仍对） |
| `DbImplUtil` | `getAllDataSourcesForExec(PsiFile)` / `getForcedDataSourceForExec(PsiFile)` | 未变 |
| `JdbcConsoleProvider` | `detachConsole` / `getValidConsole` / `attachConsole` | 未变（日志 `detach=true` 佐证） |
| `DataSourceStorage` | `getStorage(Project)` / `getDataSources()` / `getDataSourceById(String)` | 未变（插件枚举 14 源正常） |
| `LocalDataSource` / `AbstractDataSource` | `getName()` / `getIcon()` / `getUniqueId()` | 未变 |

也就是说：**换源链上只有这一颗螺丝被拧掉**，其余探测面都还在，所以症状才是「列表能出来、选中没效果」而不是整条链报错。

### 3.2 为什么「清不掉 pin」等价于「只有一个源」

代码里这条链是自洽的（`ExecFileBinding` KDoc 已记录 262 实证）：平台 `DbConsoleRootDataSourceProvider`（per-file 关联）排序在前，`getForcedDataSourceForExec` 命中即 `singletonList` 返回，`getSwitchDataSourceRunners` / `getAttachDataSourceRunners` 全部被短路。所以：

- 写关联失败 → `realignExecBind` 返回 false（`detached && remapped`）→ 上层不做 `dropSharedConsole()/clearPrepared()`（这是对的，缓存不能乱作废）；
- 但链路**继续往下走**，拿着被短路的 runner 集合做分派；
- `forceChoosePopup=true` 时得到「只有一项的弹窗」，`preferredRunnerName != null` 时得到「单 runner 直跑」。

### 3.3 为什么测试没抓到

这条链依赖 `com.intellij.database.*` 的真实运行时，单测里全部走 `runCatching` 退化分支（`Class.forName` 拿不到就 NOOP）。CI 的 `verifyIdes` 只验**能装能起**，不点「切换数据源」。所以 263 的 API 移除在有真机点击之前不会有任何红。

## 四、修复设计

### 4.1 主修：`realignExecBind` 改成「多版本适配链」

按「新 → 旧 → 只写」顺序探测，结果一次性缓存（沿用文件里既有的 `ConcurrentHashMap` 反射记忆化范式，避免每次换源都 `getMethod`）：

| 顺序 | 目标 | 语义 | 适用 |
|---|---|---|---|
| S1 | `instance.setMappingWithWriteAction(vf, ds, null)`（`DataSourcePerFileMappingsImpl.getInstance(project)`） | 写/清都在内（`ds=null` 即清，参数 `@Nullable` 已实证） | 263+ |
| S2 | `instance.setMapping(vf, ds)` | 旧重载 | ≤262 |
| S3 | `instance.setMapping(vf, uniqueIdOrNull)`（String 变体） | 直接写 id / 传 null 清除 | 兜底 |
| S4 | `static setDataSourcePerFileMapping(project, vf, ds)` | 仅 REALIGN（不能清） | 最后兜底 |

约束与注意：

1. **必须验证落地**：S1 的方法名带 `WithWriteAction`，实现里很可能自己派发写命令（异步）。调用后立刻用 `getDataSourcePerFileMapping(project, vf)` 回读比对（目标 id 或 null），不符则落到 S3 并用 `WriteCommandAction.runWriteCommandAction` 同步写一次。回读结果进日志（`remap=S1|S3|failed`），供下次排障直接读数。
2. **CLEAR 与 REALIGN 分开报告**：现在只有一个布尔 `remapped`，日志与上层都分不清「清了」和「写了」。改成返回小结果对象（`Strategy + applied`），`realignExecBind` 的日志里带上策略名。
3. 反射失败仍要 `runCatching`，但**不能静默**：至少 `LOG.warn` 带策略枚举，与本次事故的 WARN 对齐；本次就是因为只有 WARN 没有后续分型，用户端表现为「什么都没发生」。

### 4.2 必修伴生缺陷：请求了 B 源却静默跑 A 源

`DataSourceSelectorResults.kt:540` 只在「同名唯一命中」时采纳偏好；未命中就往下掉到 `:647 single runner, run directly`。这次的现场正是「偏好=mpj_demo，runner 集合只有 Oracle」——链路没有任何告警就把会话建在 Oracle 上了。

修法（二选一，建议 A+B 一起）：

- **A（默认）**：`preferredRunnerName != null` 且 runner 集合里没有任何同名项时，视为**换源失败**：`onError`（换源入口）/`onInfo`（预览静默入口）给一句明确文案，`callback(false)`，不建链。宁可让用户重试，也不能悄悄跑错库。
- **B（判据留痕）**：即便放行单 runner，也要在日志里写 `preferred=X, actual=Y, pinned=Z`，并在面板状态行就地提示「已忽略所选数据源：平台文件级绑定未能清除」。

### 4.3 结构性防复发：平台契约探针

新增一个「至少一条策略可用」的契约自检（不需要 DB 连接）：

- 在 `ExecFileBinding` 暴露 `availableMappingStrategy(): String?`；
- 首次换源时把策略名打进日志（一行），IDE 大版本升级后一眼能看出有没有再次被移除；
- 单测侧加一个 `@Test`：在带 Database 插件的测试平台下断言 `availableMappingStrategy() != null`；不满足就直接红，而不是等真机点。

### 4.4 不改什么

- 不改 `detachConsole` 链（实测通过）。
- 不改 263 的工具栏接管枚举（`getChildren: sources=14` 正常）。
- 不动 `DialectPreMapping` 的语言映射反射（另一套 `setMapping(VirtualFile, Any)`，本次日志显示「dialect pre-mapped」成功，不在本单范围）。
- 不按 2026-10-24 复盘的「交还平台、不接管」回退——2026-11-02 已定案接管（只换源不执行），本次是接管链路里的一个 API 失效点，就地修。

### 12.1 §八 待验证前提的结论

| 前提 | 结论 | 证据 |
