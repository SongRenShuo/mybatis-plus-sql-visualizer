## 缺陷事实（262 沙盒 idea.log 实证）

「Tools → Count Banned API Usages」扫描完成后打开报告即报平台 SEVERE：

```
SEVERE - #c.i.u.SlowOperations - Slow operations are prohibited on EDT
	at com.intellij.openapi.vfs.newvfs.persistent.FSRecordsImpl.update(FSRecordsImpl.java:790)
	...
	at com.intellij.openapi.vfs.LocalFileSystem.refreshAndFindFileByIoFile(LocalFileSystem.java:58)
	at cn.song.mybatisplus.visualizer.actions.ScanBannedApiUsagesAction.present(ScanBannedApiUsagesAction.kt:159)
```

用户可见：右下角红色「IDE error occurred」横幅。扫描与报告内容本身正确，唯 present() 里
的 VFS refresh 在 EDT 的 invokeLater（write-intent read action 上下文）里跑。

## 线程模型（修复前）

1. `Task.Backgroundable.run`（后台）：`runReadAction` 内 PSI 全项目扫描；
2. 后台：`BannedApiScanReport.build` 组装 + `writeTempReport` 写临时文件；
3. `invokeLater`（EDT）：`present()` —— 无命中通知；有命中时 `refreshAndFindFileByIoFile`
   解析临时文件 → `FileEditorManager.openFile`。第 3 步的 refresh 是 Slow Operation，UI-001。

## 修法裁决

**选「线程前移」**：refresh 挪到后台线程（writeTempReport 之后、invokeLater 之前），
present() 改收已解析的 `VirtualFile?`。

理由：临时文件刚由 `Files.createTempFile`+`writeText` 写出，VFS 尚未收录，
`findFileByIoFile`（不触发 refresh 的查找）对它必然返回 null——「不触发 refresh 的查找」
实际做不到，还得再配异步 refresh 回调把 present 拆成两段、打开报告变异步，行为反而变了。
refresh 在后台线程调用合法，前移后 present 只剩 UI 操作，线程模型不变（扫描后台、
写盘+refresh 后台、present EDT），行为等价（解析失败仍降级 `LightVirtualFile` 内存编辑器）。
