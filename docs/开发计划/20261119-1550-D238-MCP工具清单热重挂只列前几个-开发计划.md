# D238 MCP 工具清单在热重挂后只列出前几个（开发计划）

- **立项**：2026-11-19 15:50，真机验收 D3（子页热生效）时发现。
- **严重度**：**P1**——用户只要动一次「启用 SQL Visualizer MCP 工具」开关，外部会话看到的 `sqlv_*` 工具就从 11 个掉到 1~3 个（重启不恢复，重装插件才回 11）。表象是「插件坏了」。
- **性质**：已定位到平台侧竞态，插件侧已落绕过补丁，**待真机复验**。

## 一、现象与读数（IDEA 2026.3 真机）

| 时点 | 操作 | 插件 EP 自检 | 平台 `tools/list` |
|---|---|---|---|
| 15:46:55 | 首次注册（重装后冷启动） | `total=48 shells=11` | **11** ✅ |
| 15:48:37 | 关总开关 | — | 0 ✅（D4 通过） |

关键：**插件侧 11 个都在 EP 上**（自检回读 EP 实例列表证实），平台却只展开前 1/3 个。

## 二、已排除的假设（逐项实测）

| 假设 | 证据 | 结论 |
|---|---|---|
| 装了旧包（三钩子缺失） | `javap` 已装 jar 的 `McpToolsetSupport`：`isUserConfigurable`/`displayName`/`displayDescription` 全在 | 排除 |
| 平台按 `isEnabled()` 过滤掉 10 个 | 平台字节码 `getEnabledToolsets = EP.getExtensionList().filter{ isEnabled() }`；我们的 `isEnabled()` 读 `mcpToolsEnabled`+`mcpDisabledTools` | 排除 |
| 设置持久化了禁用清单 | 全局 `options/` 与项目 `.idea/` 全量搜 `mcpDisabledTools`/`sqlv_`：零命中 | 排除 |
| 静态 XML 声明残留冲突 | `plugin.xml` 只有注释；`mcp-optional.xml` 只剩 1 条 postStartupActivity | 排除 |
| EP 名不一致 | 平台常量与插件常量逐字相同 `com.intellij.mcpServer.mcpToolset` | 排除 |
| EP 非 dynamic（运行期注册被吞） | 2026.3 `mcpserver-plugin.jar/META-INF/plugin.xml`：`mcpToolset ... dynamic="true"` | 排除 |

## 三、根因（平台侧）

`com.intellij.mcpserver.impl.McpToolsListProvider`：
- 监听 `McpToolset.EP` 的 `ExtensionPointListener`，每次变更调 `requestUpdate` → `launch` 一个
  「MCP tools list recomputation」协程（`Dispatchers.Default` + `CoroutineName`）；
- 重算体：`Mutex.lock()` → 读 provider 工具 → **`ConcurrentHashMap.putAll`** 进
  `toolsByProvider` 缓存 → `unlock()`。

我们连续 `registerExtension` 11 次 ⇒ 触发 11 个重算协程排队。**靠前的协程在 EP 只注册了前 1~3 个时
就完成重算并 `putAll` 写缓存**，后续协程的重算结果没有把完整集合覆盖回来（时序相关，故首次冷启动
偶发正常、热重挂必坏）。这与「只列出注册顺序前 N 个」的观测完全吻合。

## 四、修法演进（两次实测定案）

### 4.1 第一版（已撤回）：注册后重放逼平台重算 ❌

思路：注册完成后延迟一拍「摘 11 + 重挂 11」，让最后一次重算读到完整 EP。

**实测证伪**（2026-11-19 15:56 包）：加了重放后，连**冷启动**都只列 1 个（15:46 那版无重放时冷启动正常 11）。
原因：平台收到 EP 变更**立即**重算（字节码确认 `requestUpdate` 无 delay，重算体是
`Mutex.lock → 计算 → keySet.retainAll → putAll → unlock`）。重放必然制造一个「EP 半空」的瞬间，
平台恰在那一刻快照并缓存残集；而重放后的最后一次注册虽让 EP 补回 11 个，平台侧已缓存的残集不会再被覆盖。
**结论：任何「先摘后挂」都会污染缓存，重放不是解。**

### 4.2 第二版（当前实现）：关闭总开关不再摘除 toolset，改由 `isEnabled()` 门控 ✅（待真机复验）

- 关闭总开关时**不动 EP**：`McpToolsetSupport.isEnabled()` 读 `McpToolGate.isEnabled(toolName)`
  → `mcpToolsEnabled == false` → 平台 `getEnabledToolsets()`（`EP.getExtensionList().filter{ isEnabled() }`）
  自动滤掉全部工具。**零 EP 变更 ⇒ 零缓存污染窗口。**
- 重开时同样零变更（`registered` 保持 true，`registerOnce` 直接返回）。
- **结构性免疫不变**：会拖垮平台 MCP Server 的是 `mcpToolFilterProvider` 那条，其摘除仍由
  `McpGateFilterEpRegistrar.sync()` 负责（总开关关闭时不挂过滤链）。

这也解释了为何首次冷启动一直正常：注册发生在启动早期，平台尚未进入「变更即重算」的活跃期。

### 4.3 第三版（当前实现）：关闭照常摘 EP + 注册完成后主动请求平台重算 ✅（待真机复验）

第二版（不动 EP、靠 `isEnabled()` 隐藏）实测**关闭无效**：平台只在 **EP 变更**时重算工具列表，
`mcpToolsEnabled` 变化不触发重算 → 关闭后 `tools/list` 仍是 11 个（2026-11-19 16:28 真机）。

两版各踩一头，只能补上「主动重算」这一环：

- **关闭**：照常 `unregisterExtension` × 11（平台自身会算成 0）；
- **打开**：`registerOnce()` 注册完 11 个后，反射
  `Application.getServiceIfCreated(McpServerService)` → `getToolsStateProvider$intellij_mcpserver()`
  → provider 的 private `requestUpdate(String)`，**在 EP 已完整时就位**请求一次重算；
- 反射失败（平台服务未创建 / 签名变动）只记 WARN，退化为平台自身那次重算（可能仍列部分）。

## 六、风险

- 重放会让工具列表在几百毫秒内「消失→重现」，正在建立会话的 MCP 客户端可能收到一次 listChanged；
  按 dynamic EP 的设计这是合法形态，且重放只发生在注册后一拍（非常态）。
- 若平台 2026.4 改动重算机制，本补丁退化为无害的多余通知（`runCatching` 全包，失败只记 WARN）。
