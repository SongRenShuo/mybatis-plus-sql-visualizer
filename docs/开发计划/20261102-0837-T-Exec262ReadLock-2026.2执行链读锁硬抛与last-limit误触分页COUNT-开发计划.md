# T-Exec262ReadLock：2026.2 执行链读锁硬抛（runners 归零）与 `last("limit")` 误触分页 COUNT 修复计划

> 2026-11-02 立项。来源＝用户日常 IDEA 2026.2（IU-262.10968.63）实测反馈两项：①预览窗点「执行 SQL」
> 报「没有与该 SQL 方言（PostgreSQL）匹配的已配置数据源」，而 Database 工具窗口里 `cyzc_db1@121.40.45.91`
> 就是 PostgreSQL（public schema 在列）；②`selectList` 调用点的预览多出一条「分页 COUNT 查询」。
> 在跑的插件＝`%APPDATA%\JetBrains\IntelliJIdea2026.2\plugins\mybatis-plus-sql-visualizer\lib\mybatis-plus-sql-visualizer-2026.10.31.jar`，
> 与 master 工作树（`version=2026.10.31`）源码行号逐帧吻合，本文引用的行号即用户在跑的代码。

## 一、结论（谁坏谁没坏）

| 现象 | 判定 | 依据 |
|---|---|---|
| 执行 SQL 报「方言不匹配」 | **插件缺陷 A（P0）**：2026.2 上预览窗执行链整体失效 | idea.log 08:17:09 `getAttachDataSourceRunners reflection FAILED: InvocationTargetException` → `Caused by: Read access is allowed from inside read-action only`；与数据源方言毫无关系 |
| 红条把用户引向 Dialects 设置 | 归因缺陷 A'（随 A 一并修） | `runners=0` 时一律套 `execute.datasource.dialectMismatch` 文案，平台调用异常没有单独归因分支 |
| `selectList` 预览附带 COUNT | **插件缺陷 B** | `paginationCountSql` 的判据缺「确有分页消费」这一闸，`.last("limit " + limit)` 解析出的 LIMIT 被当成分页 LIMIT |
| 主查询尾部 `LIMIT ?` | 非缺陷 | `last("limit " + limit)` 的 `limit` 是方法形参，静态不可得 → 占位；参数面板里 `#param2` 就是它 |
| `1@121.40.45.91` 图标带红叉 | 非本案 | 该源平台侧连接失败，只影响它自己进不了可选列表；PG 源 `cyzc_db1` 被挡完全是 A 造成的 |

两处缺陷相互独立，B 是全版本都在的逻辑错误，A 只在 262 平台触发。

## 二、根因（代码级）

### A. EDT 裸反射调平台 `DatabaseRunners`，262 不再给 EDT 隐式读锁

完整栈（idea.log 4605 行起，节选关键帧）：

```
SqlPreviewDialog$createActions$1.doAction(SqlPreviewDialog.kt:93)          ← 按钮回调，EDT
SqlPreviewPanelExecutionKt.executeSql(SqlPreviewPanelExecution.kt:975)
SqlExecutor.execute(SqlExecutor.kt:59)
DataSourceSelector.selectAndExecute(DataSourceSelector.kt:671)
DataSourceSelectorResultsKt.chooseAndPrepare(DataSourceSelectorResults.kt:375)   ← 第二次 remapped retry 在 :446
DataSourceSelector.getAttachDataSourceRunners$lambda$0(DataSourceSelector.kt:1486) ← method.invoke
  ↓ 平台
com.intellij.database.console.DatabaseRunners.getAttachDataSourceRunners(DatabaseRunners.java:190)
com.intellij.database.util.DbImplUtil.getForcedDataSourceForExec(DbImplUtil.java:503)
com.intellij.database.dataSource.DataSourcePerFileMappingsImpl.getMapping(DataSourcePerFileMappingsImpl.kt:124)
com.intellij.util.concurrency.ThreadingAssertions.throwThreadAccessException
Caused by: RuntimeExceptionWithAttachments: Read access is allowed from inside read-action only
```

三层叠加：

1. **平台行为变化**：262 起 EDT 不再隐式持有读锁，平台 `DataSourcePerFileMappingsImpl.getMapping` 内部的读访问断言直接硬抛。与 AGENTS.md「EDT 回调读 PSI 在 262 平台触发 read access 硬抛」「`PsiFileFactory.createFileFromText` 在 EDT 直调触发 262 read access 硬抛」同根。2026.1（261）与 2024.3（243）上 EDT 仍有隐式读锁，所以此前沙盒从未复现。
2. **本文件其它路径已适配、唯独这两处漏网**：`DataSourceSelector.kt` 的 `:326`/`:1604` PSI 段已包 `ReadAction`，`:1622` 冷路径 refresh 段已换 `WriteIntentReadAction.compute`（注释自述「262 平台 RefreshSessionImpl.launch 对 EDT-ReadAction…」）；而 `getAttachDataSourceRunners` 的两处反射——`:1479` attach 版、`:1495` switch 版——仍是裸 `method.invoke`。
3. **失败被静默吞成空列表**：`runCatching { … }.onFailure { LOG.warn }.getOrDefault(emptyList())` → `[M36] runners=0` → `[M36] runners empty (execute=true, registered=2)` → 走方言不匹配文案。日志里紧跟 `Suppressed a frequent exception logged for the 5th time: null`，说明用户已重复点击多次、每次同样失败。

方言推断本身是对的：同一现场 `[M36] dialect pre-mapped to PostgreSQL for mpsql-exec.sql (O-136 ds-dialect routing, ds=null)`。所以不是 O-136 路由、不是 UI-046/048/049 那条「runners=0 真门槛是绑定」的旧问题（记忆 `pitfall-runners-zero-means-unbound-not-unconnected`），而是平台调用本身没跑完。

### B. COUNT 包裹的判据只看「语句有 LIMIT」，不看「调用是不是分页」

链路四步，每步都有源码对应：

1. `QueryWrapperParser.kt:196` `"last" -> limit = parseLimit(call)`——`last(...)` 文本被解析进 `SelectStatement.limit`；实参 `"limit " + limit` 不是字面量，走 `parseLimitFragment`（`:634`）→ 占位 `?`。
2. `WrapperLocator.kt:575-578`——`selectList(w)` 无 Page 实参，`parsePageArg`（`:1134`）在实参里找不到 `new Page` 返回 null → `pageLimit = null`；但 `:592` `pageSearchCount = pageArg?.searchCount ?: true` → **true**（`WrapperChain.kt:38` 默认值同为 true）。
3. `SqlPreviewService.kt:1379-1392 paginationCountSql`：

   ```kotlin
   if (settings?.state?.paginationSimEnabled == false) return null   // 默认 true
   if (settings?.state?.paginationCountEnabled == false) return null  // 默认 true
   if (chain.countConsumed || chain.existsConsumed) return null
   if (!chain.pageSearchCount) return null                            // 无 Page 时恒 true
   val select = statement as? SelectStatement ?: return null
   if (select.limit == null) return null                              // last 给的 limit 让它过了
   return PaginationSimulator.wrapCountSql(base)
   ```

   四道前置里没有一道检查 `chain.pageLimit != null`。`applyPageLimit`（`:1538`）在 `pageLimit` 为 null 时原样返回语句，于是 `last` 的 LIMIT 原封不动进到这里，被当作分页 LIMIT 附赠 COUNT。
4. 用户代码 `MerchantWalletRechargeServiceImpl.listProcessingRecharges`（`cyzc-platform/cyzc-modules/.../service/impl/sys/`，:25-33）＝ `baseMapper.selectList(wrapper)` + `.last("limit " + limit)`，精确命中。

测试盲区：`PaginationSimTest.testSelectListWithoutPageArgStaysUnlimited`（`:161`）是唯一的 selectList 负例，但它既不带 `last` 也不断言 `countSql == null`；类头注释声明的边界「`last("LIMIT n")` 与分页并存以分页为准」只覆盖了「两者并存」，没覆盖「只有 last 没有分页」。R12 T-PaginationSim 把 `selectList`/`selectMaps` 补进 `pageConsumerMethodNames`（`WrapperLocator.kt:1419`）时也没想到 `last` 会把 LIMIT 送进来。

## 三、修复方案

### A. 两处反射 `invoke` 包 `WriteIntentReadAction.compute`

`DataSourceSelector.getAttachDataSourceRunners`（`:1469-1509`）attach 版与 switch 版同形改：

```kotlin
val result = WriteIntentReadAction.compute<Any?, Throwable> {
    method.invoke(null, psiFile, sql, sessionConsumer)
}
```

选 WIRA 而不是 `ReadAction` 的理由：平台 runner 枚举是第三方链入口，内部会建会话、attach 控制台（写意图），AGENTS.md 明示「ReadAction 内开 WIRA 硬抛；第三方链入口需读权限且内部会开 WIRA → 直接包 `WriteIntentReadAction.compute`」；本文件 `:1622` 已有同形先例，243 编译目标可用。EDT 上 WIRA 合法，243/261 上属无害包裹。

### A'. runners 为空时按「平台调用有没有抛」分流归因

`getAttachDataSourceRunners` 增加一个 `internal` 观察缝记录最近一次反射异常（不改调用签名），`DataSourceSelectorResults.chooseAndPrepare` 的 runners 为空分支：

- 反射抛了 → 新文案 `execute.datasource.platformCallFailed`：「调用 IDE 数据库接口失败：{异常首行}。请携带 idea.log 反馈。」（保留「复制错误信息」链接，异常首行取 `Caused by` 最内层）；
- 反射没抛、真的零可选 → 维持 `dialectMismatch` 现文案。

bundle 中英两处同步（`MpSqlVisualizerBundle.properties` / `_zh.properties`）。

### B. `paginationCountSql` 加闸

在 `pageSearchCount` 判断之前加一行：

```kotlin
if (chain.pageLimit == null) return null   // COUNT 只跟随确有 Page/IPage 消费的调用；last("limit") 不算分页
```

语义收口为「COUNT 是分页消费的伴生物，不是 LIMIT 子句的伴生物」。`last` 产生的 LIMIT 仍按原样渲染（`LIMIT 100` / `LIMIT ?`），只是不再附赠 COUNT。

不动：`applyPageLimit`（null 分支已正确）、`parseLimit`/`parseLimitFragment`（`last` 解析进 limit 是对的，预览要如实反映 LIMIT）、`pageConsumerMethodNames`。

可选加固 B2（低优先级，**不并入本券**）：`selectList`/`selectMaps` 按「实参数 ≥ 2 且首参可解析为 Page」才算分页消费，目前靠 `parsePageArg` 返回 null 兜住，语义上够用。
