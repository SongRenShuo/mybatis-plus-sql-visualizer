## 一、背景与问题

### 1.1 当前状态

插件支持 **9 种数据库方言**（`sql/Dialect.kt`）：

| 方言 | 分页形态 | 引用符号 | 保留字集合 | UPSERT | 依据 |
|------|----------|----------|------------|--------|------|
| MySQL | `LIMIT [offset,] count` | `` ` `` | MySQL 8.0 官方 | `ON DUPLICATE KEY UPDATE` | 官方文档 |
| PostgreSQL | `LIMIT count OFFSET offset` | `"` | PG 官方 | `ON CONFLICT` | 官方文档 |
| Oracle | `OFFSET..FETCH` | `"` | Oracle 官方 | 无原生（降级） | 官方文档 |
| SQL Server | `OFFSET..FETCH` | `[ ]` | MS 官方 | 无原生（降级） | 官方文档 |
| H2 | `LIMIT count OFFSET offset` | `"` | ≈ PG | `ON CONFLICT` | 官方文档 |
| SQLite | `LIMIT count OFFSET offset` | `"` | SQLite 官方 | `ON CONFLICT` | 官方文档 |
| MariaDB | `LIMIT [offset,] count` | `` ` `` | ≈ MySQL | `ON DUPLICATE KEY UPDATE` | 官方文档 |
| **DM（达梦）** | `LIMIT [offset,] count` | `"` | ≈ Oracle | 无原生（降级） | **社区资料（假设性）** |
| **KingBase（人大金仓）** | `LIMIT count OFFSET offset` | `"` | ≈ PG | `ON CONFLICT` | **假设性标注** |

### 1.2 核心问题

**DM（达梦）和 KingBase（人大金仓）存在"假设性标注"**：

```kotlin
// Dialect.kt L228-241：DM 分页同 MySQL（DM8 官方社区实证支持 4 种写法）
object DmDialect : Dialect {
    override val reservedWords: Set<String> = ORACLE_RESERVED  // ← 近似：达梦兼容 Oracle
}

// Dialect.kt L248-261：KingBase 分页同 PG（假设性标注：人大金仓兼容 PostgreSQL）
object KingBaseDialect : Dialect {
    override val reservedWords: Set<String> = PG_RESERVED  // ← 假设性：金仓兼容 PG
}
```

**风险**：
1. **DM 保留字集合**：达梦官方保留字与 Oracle 有差异（达梦保留字更多，包含 Oracle 没有的）→ 可能漏包导致 SQL 语法错误
2. **KingBase 分页形态**：人大金仓实际支持 `LIMIT/OFFSET`、`FETCH FIRST`、`ROWNUM` 等多种写法 → 当前选择可能非最优
3. **UPSERT 语法**：DM 的 MERGE 语法复杂，KingBase 的 ON CONFLICT 是否完全兼容 PG 未验证
4. **标识符引用**：DM 和 KingBase 的双引号引用行为是否与 PG 完全一致未验证

### 1.3 影响程度分析

| 维度 | 影响 | 等级 |
|------|------|:----:|
| **功能正确性** | SQL 在目标库执行失败 → 用户手动修正 → 信任度下降 | 🔴 高 |
| **兼容性** | 假设性标注的方言可能输出不兼容 SQL | 🔴 高 |
| **用户体验** | 用户选择方言后期望得到可直接执行的 SQL | 🟡 中 |
| **插件信誉** | 标榜"9 种方言"但 2 种未实测 → 宣传风险 | 🟡 中 |
| **国际化** | DM 和 KingBase 是国内用户重要选择 | 🟡 中 |
| **开发成本** | 需搭建多数据库环境（Docker/Testcontainers） | 🟢 低 |

### 2.2 验证 SQL 用例集

每方言执行以下标准 SQL 模板，比对插件输出与实际执行结果：

| 用例 | SQL 模板 | 验证点 |
|------|----------|--------|
| TC-01 | `SELECT * FROM t LIMIT 10` | 基础分页 |
| TC-02 | `SELECT * FROM t LIMIT 10 OFFSET 20` | 带偏移分页 |
| TC-03 | `SELECT \`table\`, \`value\` FROM t` | 保留字引用 |
| TC-04 | `SELECT "table", "value" FROM t` | 双引号引用 |
| TC-05 | `INSERT INTO t (id, name) VALUES (1, 'a') ON DUPLICATE KEY UPDATE name = VALUES(name)` | MySQL UPSERT |
| TC-06 | `INSERT INTO t (id, name) VALUES (1, 'a') ON CONFLICT (id) DO UPDATE SET name = EXCLUDED.name` | PG UPSERT |
| TC-07 | `SELECT * FROM t WHERE id IN (1,2,3)` | IN 子句 |
| TC-08 | `SELECT COUNT(*) FROM t` | 聚合函数 |

### 2.3 实施 Phase

#### Phase 1：H2 嵌入式验证（Tier 1，零依赖）

**目标**：利用已有的 H2 依赖完成第一轮验证。

**新增文件**：
- `test/.../sql/DialectH2VerificationTest.kt`

**步骤**：
1. 创建 H2 内存数据库
2. 执行标准 SQL 用例（TC-01~TC-08）
3. 验证 H2 方言输出与实际执行一致
4. 修正 H2 保留字集合差异

#### Phase 2：Testcontainers 验证（Tier 2）

**目标**：使用 Docker 容器验证主流开源/商业数据库。

**新增文件**：
- `test/.../sql/DialectDockerVerificationTest.kt`
- `test/resources/docker-compose-dialects.yml`（可选）

**新增依赖**（`build.gradle.kts`）：
```kotlin
testImplementation("org.testcontainers:mysql:1.19.3")
testImplementation("org.testcontainers:postgresql:1.19.3")
testImplementation("org.testcontainers:mssqlserver:1.19.3")

testImplementation("org.postgresql:postgresql:42.7.1")

testImplementation("org.xerial:sqlite-jdbc:3.44.1.0")
```

**验证范围**：
- MySQL 8.0、PostgreSQL 16、MariaDB 11
- SQL Server 2022（Developer Edition）
- Oracle 23c Free

#### Phase 3：DM / KingBase 文档验证（Tier 3）

**目标**：对无法搭建真实环境的商业数据库，采用文档+社区验证。

**验证方式**：
1. 达梦官方文档（`dm.com`）确认：
   - 分页语法是否支持 `LIMIT offset, count`
   - 保留字列表是否完全包含 Oracle 保留字
   - 标识符引用是否仅支持双引号
2. 人大金仓官方文档（`kingbase.com.cn`）确认：
   - 是否完全兼容 PG 的 LIMIT/OFFSET 语法
   - 保留字是否与 PG 完全一致
   - ON CONFLICT 语法是否完全兼容
3. 如文档不足，发布社区验证请求（Gitee Issues）

**产出**：验证报告 + 可能的保留字集合修正

#### Phase 4：差异修正与文档

**目标**：根据验证结果修正代码和文档。

**修正范围**：
1. 保留字集合差异 → 补充/精简
2. 分页形态差异 → 选择最优写法
3. UPSERT 形态差异 → 如需要则实现 MERGE 降级
4. 文档更新 → 移除"假设性标注"，标注验证来源

| 风险 | 等级 | 缓解 |

### 问题记录

1. 计划 1.1 表格「H2（已有）」与实际不符：H2 原非项目依赖，已按计划新增测试依赖。
2. 本机无 Docker 且代理失效（Central 不可达）：settings.gradle.kts 增加阿里云镜像源兜底；
   Tier 2 按风险表缓解路径转为「就绪待执行」。
3. H2 `ON CONFLICT` 支持与常见认知不符：2.3.232 仅 PG 模式支持 `DO NOTHING`（无冲突目标、
   无 DO UPDATE），引擎实测为准——原 H2 方言 UPSERT 输出在真实 H2 上是语法错误（本次验证
   最重要的缺陷发现）。
4. 达梦保留字与 Oracle 并非超集关系而是双向差异（Oracle 保留的 number/size/level 在 DM 仅
   关键字，错包后 CASE_SENSITIVE=Y 下双引号大小写敏感反而失配）——近似归组策略整体废弃，
   各方言改用本方言官方全量集合。
5. 真机验证最终走 DBX MCP 通道而非 `-Dmpvs.dialect.*` 直连：外部实例凭据不进测试进程，渲染在
   gradle 侧（`DialectRenderDumpTest` 导出 JSON）、执行在 DBX MCP 侧完成；顺带发现 build.gradle.kts
   原未把 `-Dmpvs.*` 透传进测试 JVM（外部实例入口文档中的系统属性实际到不了测试进程），已补
   `tasks.test` 的 systemProperty 转发。
