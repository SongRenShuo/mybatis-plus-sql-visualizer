## 一、背景与缺口

用户提出「插件需要支持 翰高、海量、人大金仓」。现状核查结论与直觉不同：

1. **人大金仓不是零支持**。`object KingBaseDialect` 自 P-立项-05 起在册，设置页可选中、URL 可推断、EXPLAIN 已登记；DBX 真机（`KingbaseES V009R001C010`，`database_mode=pg`）实测六项核心形态全部正确。金仓要补的是**三处具体缺口**（保留字缺 `enckey`、增强捕获语句面未登记、PG 协议版驱动未登记），不是方言本体。
2. **瀚高与海量是真正的零支持**。全仓无 `Dialect` 对象、无 URL 子协议、无保留字表。
3. **两个新方言的形态都能复用 PG 族**，但有两处必须单独取证、不能族推定：
   - **保留字**：瀚高官方附录 2 的 150 词里，有 **65 词**不在 dev 的 `PG_RESERVED`（86 词）中——正是 `BIGINT`/`INT`/`VARCHAR`/`TIMESTAMP`/`COALESCE`/`TRIM` 这类类型名与函数名；同时 dev 的 `PG_RESERVED` 有 **1 词**（`procedure`）不在瀚高表里。**两个方向都有差集，必须取并集（151 词）**，照抄任一单表都会漏包。
   - **upsert**：Vastbase 官方通用文法同时收 `ON CONFLICT` 与 `ON DUPLICATE KEY UPDATE`，而同内核的 openGauss 5.0.0 真机只认后者（`ON CONFLICT` 语法错误）——文档文法在这个家族里不等于引擎现实。
4. **金仓与海量在增强捕获链上「只有 URL、没有 SQL」**：dev 的 `WeaveSpecs` 语句面/prepare 面已登记 `org.postgresql.jdbc.Pg*`、`dm.jdbc.driver.Dm*` 与**华为 GaussDB/openGauss 三族**，但 `com.kingbase8.jdbc.KbStatement`、`cn.com.vastbase.jdbc.PgStatement`、`com.highgo.jdbc.jdbc.PgStatement` 一个都没有；这三族都是**整体改名、与 PG 类无继承关系**的独立类（三个 jar 的 `org/postgresql` 条目数均为 0）。好处是 dev 已经跑通了「整体改名必须单列 + 真实驱动字节织入 + JVM 链接期校验」这套先例（`com.huawei.gaussdb.jdbc.jdbc.PgStatement` 那几行及其注释），券 07 直接照抄即可。
5. **接入面比上一次加方言时宽了 4 处**：`ExecDialectRouting` 方言链、`ProjectDialectEvidence` 驱动坐标证据、`ReplayScriptExport` 事务黄金表、`PluginXmlStructureGuardTest` 描述对账，都是 T-DialectXcFamily（2026-09-23，只改 13 个文件）之后才有的。T-GaussDbDialect 已经把 GaussDB 逐处走了一遍，本任务按它的落点清单对齐即可。

因此本任务不是「加两个 object」，而是四件事：**新增两方言（复用 PG 形态 + 各自保留字表）→ 补金仓缺口 → 增强捕获驱动登记（与渲染正交）→ 守卫/文档同步**。

## 二、待验证前提（实施前先证伪）

> 上一轮 T-DialectXcFamily 就是靠这一步推翻了两条「族推定」，GaussDB 那轮又推翻了两条既有结论。以下每条都要先证伪再动手。

| 编号 | 前提 | 证伪方式 | 若不成立的影响 |
|---|---|---|---|
| **P-1** | 瀚高的折叠方向是 `LOWER`（PG 族） | **无法真机**（DBX 无瀚高实例）。取官方 V9 词法章原文「非受限名称总是被转换成小写形式」+ `lower_case_table_names` 仅 MySQL 兼容模式；真机到位后按 H2 先例（`97e28c3`）订正 | 若折大写，目录来源的引用形态全部反过来 |
| **P-2** | 瀚高 `ON CONFLICT (k) DO UPDATE SET c = EXCLUDED.c` 可用 | 官方 INSERT 文法 + 逐字示例（`ON CONFLICT (did) DO UPDATE SET dname = EXCLUDED.dname`）；**无真机**。对照：全部已抓文档无 `ON DUPLICATE KEY UPDATE` | 若不可用 → 降级纯 INSERT 或改 MySQL 形态，必须先有真机再定 |
| **P-3** | 瀚高 `DELETE ... LIMIT n` 是否合法 | **已由子代理取证：官方 DELETE 文法完整大纲无 `LIMIT` 尾段，MySQL 兼容文档也没有** → 支持 `supportsDeleteLimit=false` | 已闭环（文档级） |
| **P-4** | 瀚高显式向自增列写值是否需要 identity 包装 | **已取证**：`GENERATED BY DEFAULT AS IDENTITY` 可直接插值、无需包装；`GENERATED ALWAYS` 需 `OVERRIDING SYSTEM VALUE`（语句内子句）；**无** `SET IDENTITY_INSERT` → `renderInsertWrapper` 保持 null | 已闭环（文档级） |
| **P-5** | Vastbase 在 **A（默认）模式**下 `ON CONFLICT` 可解析 | 官方通用文法在册，但同内核 openGauss 5.0.0 真机拒绝；无 Vastbase 真机 | 若不可解析 → 默认取 MySQL 形态 `ON DUPLICATE KEY UPDATE`（openGauss 真机已证 A 模式可用） |
| **P-6** | Vastbase 折叠方向 `LOWER` | 官方《开发规范》只说「对象名不区分大小写」，未说折小写；无真机 | 同 P-1 |
| **P-7** | Vastbase `DELETE ... LIMIT` 的模式归属 | 官方通用 DELETE 文法有 `[ORDER BY][LIMIT]`、B 模式专章重写且不含 → 文档矛盾；无真机 | 保持 `supportsDeleteLimit=false` 并在 KDoc 写清矛盾来源 |
| **P-8** | 金仓 `supportsDeleteLimit=false` 是否有依据 | **已真机取证**：`EXPLAIN DELETE FROM public.ceshi WHERE FALSE LIMIT 1` → `kb: syntax error at or near "LIMIT"` | 已闭环（引擎级），`false` 正确 |
| **P-9** | 金仓 `transactionBegin="BEGIN"` 与 identity 不需包装 | `BEGIN` 官方文法在册但真机不可测（DBX MCP 拒事务语句）；identity：`BY DEFAULT` 接受显式值、「ALWAYS 需 `OVERRIDING SYSTEM VALUE`」真机两次探针 30s 超时未证 | 保持现值（文档级），KDoc 写明「事务真机不可测」 |
| **P-10** | 新增保留字不会打红高亮守卫 | `SqlMapperLanguage.DIALECT_RESERVED` 是 registry 并集（自动吸收）；`SqlMapperKeywordCoverageGuardTest` 的桶表由代码按长度派生 | 若有硬断言，需同步（当前未发现） |
| **P-11** | 平台 262 确无 HighGo / Vastbase / KingBase 方言 | 本机 `IDEA 262.10968.63` 的 `intellij.database.dialects.*.jar` 逐包列举已证：只有 base/bigquery/…/vertica，无此三族 | 若某版本新增，A9 候选链与「可选平台方言注册」（券 08）都要改 |
| **P-12** | 增强捕获织入 `com.kingbase8.jdbc.KbStatement` / `cn.com.vastbase.jdbc.PgStatement` / `com.highgo.jdbc.jdbc.PgStatement` 能过 JVM 链接期校验 | `StatementWeaverVendorCoverageTest` 现有机制（真实 jar 字节织入 + 隔离 loader 定义）可直接跑；三族驱动均在 Maven Central。**已知风险**：金仓 `KbStatement.execute(...)` / `KbConnection.setClientInfo` / `Driver.connect` 的 StackMapTable 含 chop 帧 | 过不了就不能登记（达梦 `DmDriver` 就是在这里 VerifyError 被整类撤出） |
| **P-13** | `DialectDocTableGuardTest` 当前是否为绿 | dev 侧 `docs/架构设计/03` §218 已把这条坑落档：该守卫读磁盘上的兄弟目录、所有工作树共用一份 → 「插件分支 A 有 N 方言、分支 B 有 M 方言」不可能同时绿。上一轮真实发生（文档站先加 GaussDB 行 → master 仍 11 → master 侧 4 例红 → 文档站回退 `59a7ee0`；dev 合入后反向又红） | 实施顺序固定为「**先 dev 落插件 14 → 再改文档站**」；改完后 master 工作树跑该守卫必红，属已知且可接受 |
| **P-14** | 金仓保留字缺 `enckey` 是真缺口 | **已真机取证**：`pg_get_keywords()` 中 `enckey` 的 `catcode=R`；`SELECT enckey FROM public.ceshi LIMIT 0` 报 `kb: syntax error at or near "enckey"`。**但 `SELECT 1 AS enckey` 通过**（别名位可用，与子代理读数相反） | 已闭环：按「宁可多包」补入，代价是这类别名会多一对引号 |
| **P-15** | PG 协议版金仓驱动（`postgresql-for-kingbase`）会被误判成 PostgreSQL | 字节码级：该 jar 的 `META-INF/services` = `org.postgresql.Driver`、子协议 `jdbc:postgresql:`；`ProjectDialectEvidence.DRIVER_MARKERS` 无对应标记，且 `org.postgresql:postgresql` 标记会先命中 | 已闭环：加 marker 时**必须排在该行之前** |

### 券 05 金仓缺口补全（S）

**先摆清「不缺什么」**（主控已真机实测，避免重复劳动）：

- **URL 子协议零缺口**：`kingbase8-8.6.0` / `9.0.1` / `-mysql` / `-sqlserver` 四份驱动的 `Driver.class` 常量池都只有 `jdbc:kingbase8:`，插件已同时登记 `kingbase8` 与 `kingbase`（后者为宽进，无害）。
- **平台方言 id 候选链已在**（`KingBase` / `KingbaseES` / `PostgreSQL`），262 平台无金仓方言，恒落 PG 兜底。
- **`@KeySequence` 方言集已含金仓**（`BatchOperationConverter.KEY_SEQUENCE_DIALECT_NAMES`）。
- **六项核心形态全部正确**（真机）：分页 / 双引号 / LOWER 折叠 493/493 / PG 形态 upsert（`Conflict Resolution: UPDATE`）/ `EXPLAIN (FORMAT JSON)` 单列 JSON / `DELETE … LIMIT` 语法错误印证 `supportsDeleteLimit=false`。

**要补的缺口**：

1. **保留字补 `enckey`**（dev `SqlKeywords.kt:289` 的 `KINGBASE_RESERVED`）——引擎 `pg_get_keywords()` 标 `catcode=R`，`SELECT enckey FROM …` 报 `kb: syntax error at or near "enckey"`；官方 V8/V9 文档表都标「非保留」，按引擎为准。同步 `DialectDocGoldenTest` 的黄金清单与 KDoc。**登记一条已知分歧**：`SELECT 1 AS enckey` 实测通过（别名位可用），补入后该形态会多一对引号，属可接受的多包。
2. **`postgresql-for-kingbase` 驱动标记**（`ProjectDialectEvidence.DRIVER_MARKERS`）——该 Maven 产物驱动类是 `org.postgresql.Driver`、子协议 `jdbc:postgresql:`，用它构建的金仓项目会被推断成 PostgreSQL，金仓保留字表不生效。**marker 必须排在同表的 `"org.postgresql:postgresql"` 之前**（`ProjectDialectEvidence.kt:70-88` 是顺序匹配）。
3. **增强捕获语句面**（并入券 07）——connect 面在册（角标有 URL），语句面/prepare 面完全未登记 → 用户看到库名但**一条 SQL 都采不到**。
4. **KDoc 文案订正**：`transactionBegin` 与 identity 两项保持现值，但 KDoc 要把「推定」改写成「文档级 + 真机不可测（DBX 拒事务语句 / 探针超时）」，不得继续暗示已验证。
5. 已核实无需改：`DataSourceUrlProbe.DBMS_ALIASES` 只在「平台显示名 ≠ 插件名」时才需要条目，金仓与两新方言名字相等即自动命中。

### 券 07 增强捕获驱动登记（M，与渲染正交、可独立分批）

## 六、风险

- **族推定被打脸**（P-1/P-2/P-5/P-6）：按 H2 先例处理——真机订正 + 反向验证 + 契约断言同步。**注意 P-1/P-2/P-5/P-6 是瀚高/海量的结论，两族都没有实例可验**，只能靠用户侧真机反馈收敛。

- **与在途任务撞写集**：`sql/Dialect.kt` 同时是 T-GaussDbDialect（待拍板）的写集。**开工前必须与它串行或合并**，否则 B1/B2/B3/B7/B8 的冻结清单会互相打红（P-13）。

- **`database-optional.xml` 变更**（券 08）会抬高构建校验门槛，若排期紧可单独成批。
- **金仓保留字补词会动黄金清单**：`DialectDocGoldenTest` 的 `KINGBASE_RESERVED` 黄金断言是逐词对齐的，补 `enckey` 必须同步改测试与两处 KDoc，否则「改了代码忘了测试」会立刻红。
