## 一、待验证前提（实施者先证伪再动手）

本轮结论来自 magpie 侧的实测定点，**对本仓现状的对应判断尚未逐条核实**，实施前必须先验证：

1. **P-1**：本项目「展示脱敏」当前对同一原始值的掩码输出**是否已经稳定一致**（同值同假名、跨查询一致）。若已是确定性映射，W2 只需补「known 再识别 + Hint 诊断 + 分级动作」中的缺口，不必重做占位符。核实入口：`settings.display.mask` 相关实现（见 memory：设置搜索 A+B 已补登记该键）与脱敏渲染调用链。
2. **P-2**：本插件设置持久化（`@State`/PersistingStateComponent 的 XML）在文件损坏时当前的回退行为**是否等于「当空配置重新开始」**。若是，W3 成立；若平台已内置代际备份（如 `StateStorage` 的快照），W3 收窄为「损坏告警与存证」。
3. **P-3**：预览降级 `PreviewDegradationReason` 七档与 W4 的错误分类学对照后，**缺的是「同因不同处置」还是「因分得不够细」**。七档是「原因分型」，magpie 的增量在「每型挂不同处置（重试/切换/休息/垫底）」，先对照再决定动不动分型表。
4. **P-4**：`docs/经验总结/` 现有 260+ 篇是按事件归档的，LESSONS 式台账是**新增一层规则账本**而非重构既有归档——两层的分工（台账只收「可执行规则」，经验总结仍是事件叙事）需在 W1 开工前定稿，避免同一教训两处维护。

## 二、产品代码线（动 src/main，逐项独立立项、独立门禁）

### W2（最高优先）：SQL 展示脱敏对齐 magpie redact 四件套

magpie 出处：`redact.go:308-466`、`redact/known.go`、`redact/writer.go`（证据详见调研报告 §四）。

- **W2-a 确定性 HMAC 占位符**：掩码输出 = f(类别+原值) 的确定性哈希截断，同值永远同假名——同一列值在结果集各行、跨多次预览、WHERE 字面量与结果列之间全部一致。若 P-1 证实现状已确定性，此项只补一致性守卫测试（同值多处出现 → 输出必须相同）。
- **W2-b 已见值再识别（known 索引）**：对每个已脱敏值建索引（Java 侧用 `HashSet`/布桶即可，不必上 Bloom），使「无上下文处再次出现的同值」也映射到同一占位符——对应 SQL 场景：用户在结果里看到的假值，回贴到 WHERE 里再预览时仍是同一个假值。
- **W2-c Hint 式诊断**：脱敏引发的阻断/告警提示**只露首字符+长度，绝不回显原值**；审计/日志记录类别与命中规则，不落值本身。
- **W2-d 动作分级 mask/warn/block + Allow 白名单优先**：对照现状分级补缺；白名单优先级压过一切识别规则。
- 验证口径：每项改动配反向探针（摘掉新分支必须变红）；同值一致性用「一处值出现在 WHERE/结果列/参数预览三处」的合成 SQL 三点断言。

### W3：设置持久化的 lastgood 防护

magpie 出处：`internal/lastgood/lastgood.go` 全文（证据详见调研报告 §5.3）。

- 核心：「文件存在但不合法 = 未知，绝不是空」。写前先把现存合法副本存为 `.bak`；读时主文件解析失败 → 回落 `.bak` 并告警（GUI 通知一次，不刷屏）；坏文件本身拷为 `.bad-<时间戳>` 存证再继续写。
- 「文件不存在」**不**触发回落（区分「人为清空」与「损坏」）。
- 落点：插件自身的设置 State 组件（非平台 IDE 全局配置——平台配置归平台管）。
- 验证：手工把状态文件写成全零/半截 JSON → 重启后设置保留上代值且出现「已恢复」通知；反向=删掉 .bak 存证逻辑 → 坏文件被好写覆盖时测试变红。

### W4：预览执行错误分类学对照扩展

magpie 出处：`fallback.go:1036-1306`（证据详见调研报告 §3.2）。

- 先做对照表（P-3）：把 `PreviewDegradationReason` 七档 × magpie 四类归因（错在账号/错在目标/错在请求/错在环境）画成矩阵，产出**缺口清单**而不是直接改码。
- 预期缺口形态：「连接失败」应区分「数据源整体不可达（切源/闸门出口）」与「库表不存在（不该自动切源）」两类处置；「SQL 错误」永不触发自动重试别的数据源。
- 本项实施与否取决于矩阵读数，可能结论是「已覆盖，只补测试」。

### W5（小项，随路搭车）：钩子链失败策略契约化

magpie 出处：`gwmw.go:1-16`（包头契约）+ 注册返回 remove 函数。

- 对增强捕获/渲染链的扩展点，在接口或包 KDoc 里**显式声明 fail-open 还是 fail-closed**（如：脱敏 fail-closed——脱敏引擎异常时宁可拒绝展示也不裸出原值；日志捕获 fail-open——钩子坏了不拦业务）。
- 新增注册式扩展点时统一「注册返回 `() -> Unit`」模板（Kotlin 侧对应现有 Disposer 习惯，仅约束新代码风格，不回头改存量）。

## 三、开发流程线（不动 src/main，零门禁风险）

### W1（最高优先）：建立 `docs/LESSONS.md` 规则账本

magpie 出处：`LESSONS.md` 全文机制（证据详见调研报告 §二、§6.1）。

- 格式照搬四段式：**一句话祈使句规则 → hash 级证据（提交号/文档行号/真机日志）→ 反例/正例 → `Seen N× (日期)`**；同日多次只算一天；**Seen 满 3 个不同日期 → 整条搬进 `docs/code-standards.md`**，原位留指针。
- 开工动作：从 `~/.zcode/AGENTS.md`「IntelliJ 平台通用陷阱」与本项目 `docs/经验总结/` 高频复发条目中**筛种子规则**（判据：已在 2 个以上不同日期复发的），首批约 10~15 条，逐条补 hash 证据。
- 复盘触发点：不搞自动夜间复盘（那是 magpie 基础设施，我们没有），改为**每次收口/门禁复跑后由收口会话顺手记**；AGENTS.md 或 CLAUDE.md 加一行「改代码前先读 docs/LESSONS.md」。
- 与既有体系分工（P-4）：LESSONS 只收「可执行规则」，`docs/经验总结/` 仍是事件叙事与详版；台账条目链接到详版，不复制内容。

### W6：子代理派活与收口流程三处补强

magpie 出处：`code-standards.md` 验收标准与 worktree 条款（证据详见调研报告 §6.3）。

- **W6-a 验收清单化**：派活模板里把「三档测试分层」改写成编号可勾选清单，末尾加硬条款「没跑的检查项必须标 not run，不得省略」（对应 magpie 验收第 5 条 "What wasn't tried with the real thing isn't told to users as working"）。
- **W6-b worktree 所有权事后校验**：子代理提交后必须 `git show --stat HEAD` 确认只含自己的文件，读数贴进报告——比登记表多一道物理检查。
- **W6-c commit body 带验证记录**：授权提交时 body 里写「跑了什么定向、读数多少」（现仅中文提交 + `-F` 文件，格式约定追加一节即可）。

### W7（可选，低优先）：核心域子系统文档试点

magpie 出处：`docs/subsystems/README.md` 维护规约（证据详见调研报告 §6.4）。

- 选 1~2 个最常被并行车道触碰的核心域（候选：预览执行链、增强捕获链）写「职责 | Source of truth（钉到 文件:符号）」表格型文档，约定「改契约同 PR 更新文档、一个事实只写一处、链接指符号不复制实现」。
- 先试点验证维护成本，再决定是否推广——**这条的价值未经本仓实践检验，不预设收益**。
