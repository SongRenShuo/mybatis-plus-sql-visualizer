## 三、券详单

### T-PerfSweep27-01（R27-1）：头部行 headerFragments 条目级缓存

- **现状**：bindHeaderLine 在 getListCellRendererComponent 内执行，即每次可见格重绘都重跑 headerFragments（buildList 分配 + 序号/库角标/行号等小拼接，SqlEntryPresentation.kt:29-62）与 dropByPriority 优先级裁剪排序（:341-362，含 levels 排序与 isTimeText 形态兜底 :287-308）。同文件的多行 SQL 语义片段已有条目级缓存先例（RailCellRendererBase.kt:284-298），头部行未沿用。测量器 HashMap 每格新建但按字重缓存 FontMetrics（:350-359），维持不动。
- **修法**：按条目身份缓存头部片段结果（键=条目实例或条目代，形态对照 :284-298 先例；SINGLE_LINE 与多行模式同一份缓存，模式差异只在绑定侧）。P-1 若证伪出会话级维度，缓存键补该维度再实施。
- **先红后绿判据**：①新用例「同一条目连续 N 次渲染 → 断言 headerFragments 计算次数 =1（借 presentation 层加计数测试缝）」——修复前为 N，即新增守卫；②反向=摘除缓存 → 用例①回红，贴两次读数；③既有 LogEntryRailPerfTest 全绿且单格预算按改造后实测收紧（现 2.0ms，:49/:60/:71），收紧值写入实施记录。
- **风险与交互**：条目被淘汰/替换后缓存须同步失效或键含条目代；头部行内容受「显示格式严格跟随设置」约束（feedback 定例），设置变更路径若触达绑定须清缓存；组件树规模判据（:80/:98）不得回退。

### T-PerfSweep27-02（R27-2）：EntityResolver/JpaEntityResolver 缓存上限化

- **现状**：两处 companion 静态 ConcurrentHashMap 条目数无上限、无淘汰、仅 clearCache 清空（EntityResolver.kt:543-556、JpaEntityResolver.kt:711-729，键为 fileUrl 字符串+类名+配置签名，JPA 侧多 hostAnchorPath 维度）。配置签名变化后旧键永不命中也永不淘汰，长会话缓慢累积。
- **修法**：套用仓内现成范式二选一：HbmXmlEntityResolver 负缓存 4096 上限超限整体清空（HbmXmlEntityResolver.kt:41-54），或 WrapperCache LRU 512（WrapperCache.kt:28-54）。两缓存键轻、增长慢，容量上限 4096~1024 均可，实施时按 P-2 证伪结果定（有学习态语义选弱引用改键方案）。PluginCacheManager.clearAll 现覆盖两处，不动。
- **先红后绿判据**：①新用例「写入超过上限条目 → 断言条目数不超限且清空后可重填」；反向=摘上限 → 用例红；②PluginCacheManager 覆盖面既有守卫维持绿。
- **风险与交互**：上限淘汰不得造成「同配置同实体第二次解析结果不同」的可观测差异（纯解析结果前提下无此面）；clearAll 后行为与现一致。

### T-PerfSweep27-03（R27-3）：补全降噪 + HqlGutter 开关前置（机械批）

- **现状一**：SqlCompletionContributor.kt:80-88/:101 每次 addCompletions 约 10 条急切插值 LOG.debug——debug 默认不输出但字符串拼接照付，autopopup 下每键触发。
- **修法一**：改 `if (LOG.isDebugEnabled)` 门控包裹或直接删除（按仓内既有惯例选一种，全文件统一）；保留有诊断价值的条目可挂计数缝 opt-in，形态对照 XmlSynHiGate V38 缝。
- **现状二**：HqlGutterLineMarkerProvider.kt:48 的 hasStringFirstArgument（含变量引用 resolve 分支 :86）在开关判断 :51-53 之前——关闭 gutter 总闸的用户每趟仍付一次 resolve。
- **修法二**：开关判断前移至 hasStringFirstArgument 之前（与 SqlGutterLineMarkerProvider.kt:47-50 同型），P-3 证伪通过即一行改动。
- **判据**：①补全侧：非 debug 级别下 addCompletions 断言零字符串拼接（计数缝或静检测试）；②gutter 侧：关闸夹具断言 resolve 零调用，开闸夹具断言标记产出不变；反向=还原顺序 → 关闸用例红。
- **风险与交互**：门控后 debug 开启态日志内容逐字不变；HqlGutter 前移后开闸路径判定次序与结果不变。

### T-PerfSweep27-04（R27-4）：AUDIT_CTX 取消路径 finally 兜底（一行级）

- **现状**：McpToolsetSupport.kt:233 的 AUDIT_CTX（token→审计上下文）写入点在挂起前，remove 只挂在成败记账路径（:175/:240）——工具协程被取消且未走记账时 token 键残留。键为 Long 量级轻，残留属缓慢累积非泄漏放大器。
- **修法（P-4 证伪后替换，见前提证伪结论表）**：放弃 try/finally 方案。companion 新增同步清扫函数 `sweepAuditContexts(now)`：①移除 `started` 距今超 `AUDIT_CTX_STALE_MS`（10 分钟，远超 McpDbExecutor queryTimeout 量级）的过期条目；②总量超 `AUDIT_CTX_MAX`（64）时按 started 移除最旧至限内。`audit()` 写入 `AUDIT_CTX[token]` 后顺手调用。持续挂起中的活条目最坏被误删——记账端 `AUDIT_CTX.remove(token) ?: return` 语义下仅丢一条审计行，无崩溃无错账。
- **判据**：①新用例「协程取消形态 → 断言 AUDIT_CTX 为空」；反向=移除 finally → 用例红。
- **风险与交互**：finally remove 不得早于审计上下文在成败记账中的最后一次读取；幂等以 ConcurrentHashMap 语义天然保证。
