# SQL 日志前缀与 SQL 分行兼容开发计划

> 状态：✅ 已实施（`MyBatisLogParser` 分支 2/3「Preparing:/Parameters: 独占一行」兼容 + 多行续行态 T-LPC-07；2026-11-13 代码核对回填）
> 需求来源：用户反馈——部分用户的 MyBatis 日志中，`Preparing:` 前缀独占一行、SQL 在下一行（中间多一个换行符），导致解析器无法识别、SQL 丢失。

## 1. 目标与范围

**核心目标**：`MyBatisLogParser` 兼容「前缀与 SQL 分行」的日志形态，正确配对并还原 SQL。

**需兼容的日志形态**（新增）：

```
# 形态 A：MP 前缀 + 分行
==>  Preparing:
SELECT * FROM user WHERE id = ?
==> Parameters: 1(Long)

# 形态 B：原生 + 分行
Preparing:
SELECT * FROM user WHERE id = ?
Parameters: 1(Long)

# 形态 C：带日志框架前缀 + 分行
2026-08-15 10:00:00 [main] INFO c.s.m.Log : ==>  Preparing:
SELECT * FROM user WHERE id = ?
2026-08-15 10:00:00 [main] INFO c.s.m.Log : ==> Parameters: 1(Long)

# 形态 D：前缀 + 空白行 + SQL
==>  Preparing:

SELECT * FROM user WHERE id = ?
==> Parameters: 1(Long)

# 形态 E：无参语句 + 分行
==>  Preparing:
SELECT COUNT(*) FROM user

# 形态 F：Parameters 也分行（极端）
==>  Preparing:
SELECT * FROM user WHERE id = ?
==> Parameters:
1(Long)
```

**已确认决策**：
- **默认开启、不可配置**：分行是日志框架/MyBatis 配置的客观产物，无需用户开关；解析器应透明兼容。
- **不区分 `mixedPrefix` 模式**：分行兼容对 `mixedPrefix=true`（宽容匹配）和 `mixedPrefix=false`（行首精确）均生效。
- **空白行跳过**：前缀行与 SQL 行之间的空白行自动跳过（容忍日志框架插入空行）。
- **噪声行安全**：仅在「前缀已匹配、等待 SQL」状态下将非关键字行视为 SQL；正常状态下噪声行处理逻辑不变。
- **影响范围**：核心修复仅动 `MyBatisLogParser`；`SqlLogConsoleBridge`（自动捕获）和 `LogToSqlPanel`（日志转 SQL）复用同一解析器，自动生效。

## 2. 现状分析

### 2.1 根因定位

```kotlin
// MyBatisLogParser.feed()（第 37-53 行）
fun feed(line: String) {
    val sql = extractAfterKeyword(line, sqlPrefix)
    if (sql != null) {
        closePending()
        pendingSql = sql.take(maxParseLength)
        pendingParams.clear()
        return
    }
    val paramsText = extractAfterKeyword(line, paramPrefix)
    if (paramsText != null) {
        if (pendingSql == null) return
        pendingParams += parseParams(paramsText)
        closePending()
    }
}

// MyBatisLogParser.extractAfterKeyword()（第 76-86 行）
private fun extractAfterKeyword(line: String, keyword: String): String? {
    if (keyword.isEmpty()) return null
    val idx = if (mixedPrefix) line.indexOf(keyword) else {
        if (line.startsWith(keyword)) 0 else -1
    }
    if (idx < 0) return null
    val text = line.substring(idx + keyword.length).trim()
    return text.ifEmpty { null }   // ← 前缀独占一行时 text="" → 返回 null
}
```

**问题链**：
1. 输入 `==>  Preparing:`（无尾随 SQL）→ `extractAfterKeyword` 返回 `null`
2. `feed()` 不进入任何分支 → 解析器保持 `pendingSql=null`
3. 下一行 `SELECT ...` 输入 → 不匹配任何前缀 → 当作噪声忽略
4. 结果：这条 SQL 永远不会出现在日志面板

### 2.2 调用链路

```
控制台输出 / 粘贴日志文本
    ↓ 逐行喂入
SqlLogConsoleBridge.attachFilter()  ──→ parser.feed(line)
LogToSqlPanel                        ──→ text.lineSequence().forEach { parser.feed(it) }
                                            ↓
                                    MyBatisLogParser.feed()  ← 唯一修复点
                                            ↓
                                    LogSqlEntry → 缓冲区 → 面板
```

修复 `MyBatisLogParser` 即可同时覆盖自动捕获与手动粘贴两条路径。

## 3. 模块设计

### 3.1 状态机扩展

新增状态标志 `prefixMatched`：

| 状态 | 含义 | 转换条件 |
|------|------|----------|
| `prefixMatched=false`（默认） | 正常态，等待前缀 | — |
| `prefixMatched=true` | 前缀已匹配、remainder 为空，等待 SQL 行 | 前缀行 remainder 为空 |

**状态转换**：

```
【prefixMatched=false 时】
  输入行匹配 sqlPrefix：
    - remainder 非空 → pendingSql=remainder, prefixMatched=false（现有逻辑）
    - remainder 为空 → prefixMatched=true, pendingParams.clear(), pendingSql=null（新增）
  输入行匹配 paramPrefix → 忽略（无 pendingSql 上下文，现有逻辑）
  其他行 → 忽略（噪声，现有逻辑）

【prefixMatched=true 时】
  输入行匹配 sqlPrefix：
    - remainder 非空 → closePending()（闭合空 SQL 条目）, pendingSql=remainder, prefixMatched=false
    - remainder 为空 → 保持 prefixMatched=true（连续空前缀行，罕见）
  输入行匹配 paramPrefix → closePending()（闭合无 SQL 的参数条目）, 处理 params, prefixMatched=false
  输入行为空白行 → 保持 prefixMatched=true（跳过空行）
  其他非空行 → pendingSql=line.trim(), prefixMatched=false（将此行作为 SQL）
```

### 3.2 核心代码改动

#### 3.2.1 MyBatisLogParser 新增状态字段

```kotlin
class MyBatisLogParser(
    private val restorer: LogSqlRestorer = LogSqlRestorer(),
    var sqlPrefix: String = DEFAULT_SQL_PREFIX,

    var mixedPrefix: Boolean = true,

    private val entries = mutableListOf<LogSqlEntry>()
    private var pendingSql: String? = null
    private val pendingParams = mutableListOf<LogSqlParam>()
    private var prefixMatched: Boolean = false  // ← 新增：前缀已匹配、等待下一行 SQL
    ...

```

#### 3.2.2 新增「前缀独占一行」检测方法

```kotlin
/** 行仅含前缀关键字（remainder 为空）——分行形态信号。 */
private fun isPrefixOnly(line: String, keyword: String): Boolean {
    if (keyword.isEmpty()) return false
    val idx = if (mixedPrefix) line.indexOf(keyword) else {
        if (line.startsWith(keyword)) 0 else -1
    }
    if (idx < 0) return false
    return line.substring(idx + keyword.length).trim().isEmpty()
}
```

#### 3.2.3 改造 feed() 方法

```kotlin
fun feed(line: String) {
    // 分支 1：前缀匹配（remainder 非空）
    val sql = extractAfterKeyword(line, sqlPrefix)
    if (sql != null) {
        if (prefixMatched) closePending()  // 前一条空 SQL 条目闭合
        pendingSql = sql.take(maxParseLength)
        pendingParams.clear()
        prefixMatched = false
        return
    }

    // 分支 2：前缀独占一行（remainder 为空）→ 进入等待 SQL 态
    if (!prefixMatched && isPrefixOnly(line, sqlPrefix)) {
        prefixMatched = true
        pendingParams.clear()
        return
    }

    // 分支 3：参数行匹配
    val paramsText = extractAfterKeyword(line, paramPrefix)
    if (paramsText != null) {
        if (prefixMatched) {
            // 前缀独占一行后紧跟 Parameters（无 SQL 罕见形态）→ 闭合空条目
            prefixMatched = false
        }
        if (pendingSql == null) return
        pendingParams += parseParams(paramsText)
        closePending()
        return
    }

    // 分支 4：等待 SQL 态下的处理
    if (prefixMatched) {
        if (line.isBlank()) return  // 跳过空行
        // 此行即为 SQL
        pendingSql = line.trim().take(maxParseLength)
        prefixMatched = false
        return
    }

    // 分支 5：噪声行（现有逻辑不变）
}
```

#### 3.2.4 closePending() 无需改动

`closePending()` 不依赖 `prefixMatched` 标志——它只读 `pendingSql`。当 `prefixMatched=true` 但 `pendingSql=null` 时调用 `closePending()` 会返回 `null`（空操作），符合预期。

### 3.3 前缀行 remainder 为空但行内无其他内容的边界场景

```
# 场景：Preparing: 后紧跟空格然后换行（"Preparing: \n"）
extractAfterKeyword → idx 找到 → text = "".trim() = "" → null
isPrefixOnly → idx 找到 → substring → "".trim().isEmpty() = true → true ✓
```

两个方法对 `Preparing:` / `Preparing: `（有无尾随空格）判断一致。

### 3.4 噪声安全保证

`prefixMatched=true` 仅在当前行刚被识别为「仅含前缀」时设置。一旦进入下一行：
- 匹配 `sqlPrefix` 或 `paramPrefix` → 立即按关键字处理，不把关键字行当 SQL
- 空白行 → 跳过
- 其他非空行 → 视为 SQL，同时 `prefixMatched=false`

不存在「把噪声误当 SQL 后无法恢复」的死锁——最多一行误判。

### 5.2 Parameters 分行极端形态的处理策略

用例 7 需要在 `prefixMatched=true` 分支中增加对「Parameters 行也仅含前缀」的支持。处理方式：

- 当 `prefixMatched=true` 且当前行是 `isPrefixOnly(line, paramPrefix)`（Parameters 独占一行）→ 进入 `paramPrefixMatched=true` 状态
- 下一非空行为参数文本 → 解析并闭合

**实现**（追加状态字段）：

```kotlin
private var paramPrefixMatched: Boolean = false  // Parameters 也分行时

// 在 feed() 分支 3（参数行匹配）之前追加：
if (paramPrefixMatched) {
    if (line.isBlank()) return
    if (pendingSql == null) { paramPrefixMatched = false; return }
    pendingParams += parseParams(line.trim())
    closePending()
    paramPrefixMatched = false
    return
}
```

**影响评估**：新增 `paramPrefixMatched` 字段仅在极端形态（Preparing 和 Parameters 都分行）时使用。若用户日志不存在此形态，该标志始终为 false，不影响正常路径。

### 5.3 回归保证

现有 16 个用例全部覆盖 `prefixMatched=false` 的正常路径，逻辑未被改动（仅新增分支）。所有现有用例应继续全绿。

## 6. 风险与注意事项

- **误判风险**：`prefixMatched=true` 后若下一行恰好是正常业务日志（非 SQL），会被误判为 SQL。但实际日志中 `Preparing:` 后紧跟 SQL 是 MyBatis 的固定输出格式，不存在其他内容插入，风险极低。
- **混合模式一致性**：`isPrefixOnly()` 与 `extractAfterKeyword()` 使用相同的 `mixedPrefix` 判断路径，保证两种模式下行为一致。
- **maxParseLength 应用**：分行形态的 SQL 在设置 `pendingSql` 时同样应用 `.take(maxParseLength)`，保持截断保护。
- **closePending() 安全**：`prefixMatched=true` 时 `pendingSql=null`，调用 `closePending()` 返回 `null`（空操作），不产生空条目。
- **线程安全**：解析器按 console 实例隔离，`prefixMatched` 是实例字段，无共享状态问题。
