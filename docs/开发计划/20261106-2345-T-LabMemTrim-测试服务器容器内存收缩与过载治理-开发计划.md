## 二、目标 / 非目标

**目标**：①主机 `available` 回到可用区间（目标 ≥ 3GB）；②单容器失控不再能拖垮主机；③**不降低**测试可用性（方言矩阵的四实例仍要能 PASS）。

**非目标**：不迁库、不换镜像、不动 `114.66.55.245`、不删任何容器/数据卷；不做性能调优（只做内存治理）。

## 三、方案（按收益排序）

### 3.1 加 swap（最高性价比，先做）

主机 0 swap、剩 133G 盘。建 **4GB** swap 文件（`/swapfile`，`vm.swappiness=10`），写进 `/etc/fstab` 持久化。
作用：内存峰值时把冷页换出，避免 OOM-kill 直接把某个数据库打死（这也是「过载」最危险的后果）。

### 3.2 容器内存上限收缩（cap ≈ 1.5~2× 实测，给 DB 留最低运行量）

| 容器 | 现上限 | **建议上限** | 依据 |
|---|---|---|---|
| xc3-oceanbase | 8 GiB | **4 GiB** | 实测 4.39 峰值已贴线，先给 4G 并同步压 OB 内部 `memory_limit`（见 3.3） |
| xc3-oracle-free | 4 GiB | **2.5 GiB** | 实测 2.16 |
| panweidb-ora | 3 GiB | **1.5 GiB** | 实测 1.15（内部配置同步压，见 3.3） |
| panweidb-test | 4 GiB | **1.5 GiB** | 实测 1.08 |
| xc3-mssql | 2 GiB | **1.5 GiB** | 实测 1.02 |
| xc3-vastbase | 4 GiB | **1.5 GiB** | 实测 724M |
| xc3-gaussdb-kernel503 | 4 GiB | **1.5 GiB** | 实测 647M |
| xc3-opengauss | 4 GiB | **1 GiB** | 实测 589M |
| xc3-mysql8 | 1 GiB | **768 MiB** | 实测 371M |
| xc3-vastbase-b | 2 GiB | **512 MiB** | 实测 219M |
| xc3-mariadb | 2 GiB | **512 MiB** | 实测 193M |
| xc3-highgo | 3 GiB | **512 MiB** | 实测 45M |

合计上限 41 GiB → **17.25 GiB**；配合 swap 后，即使全部同时冲顶也不会瞬间打死主机（swap 兜底 4G）。

> 注意：`docker update --memory` 对运行中容器生效；`--memory-swap` 必须 ≥ `--memory`（或设成与 memory 相等表示不额外给 swap）。

### 3.3 同步压数据库内部配置（**不压就会 OOM-kill，不是可选项**）

容器 cap 只是外框，DB 内部参数才是它「想用多少」：

| 引擎 | 要改的项 | 建议 |
|---|---|---|
| OceanBase | `memory_limit`（sys 租户参数） | 8G → **2.5G**（留 1.5G 给 cap 外开销） |
| panweidb-ora / panweidb-test | `shared_buffers`、`bulk_write_ring_size` | 1024MB → **384MB**；2GB → **512MB** |
| openGauss / gaussdb_kernel503 | `shared_buffers` | 若 > 256MB → **256MB** |
| Oracle Free | `sga_target`/`pga_aggregate_target` | 若 > 1G → **768M / 256M** |
| SQL Server | `max server memory` | → **1024MB** |
| MySQL / MariaDB | `innodb_buffer_pool_size` | → **256MB / 128MB** |
| Vastbase / HighGo | `shared_buffers` | → **256MB** |

改法优先「容器内改配置 + 重启容器」；`ALTER SYSTEM` 能在线改的优先在线改（OceanBase / SQL Server / MySQL 可用 SQL；openGauss 族 `shared_buffers` 需重启）。

### 3.4 收尾：把新基线写进文档

`.local/test-databases.md`（或 `database-lab/` 下的清单）补一节「内存基线」：容器上限 + 内部关键参数 + 采集时间，后续再加库时照此给预算。

| P-1 | OceanBase 的 `memory_limit` 能在线降到 2.5G 且不影响租户可用 | 降不动就只压容器 cap 到 4G，OB 内部保持原值（cap 仍能防它吃穿主机） |

### 7.4 待验证前提结论

| 编号 | 结论 |
|---|---|
| P-1 | **部分不成立**。`memory_limit` 不能直接降到 2.5G：下限是 `sum(unit MEMORY_SIZE)+system_memory`；把 test unit 压到 2G 后 `memory_limit` 才降到 5G。`__min_full_resource_pool_memory=2G`（bootstrap 写死、`ALTER SYSTEM` 改不动）使单租户压不到 2G 以下，故 **2.5G 不可达**。改用「内部 5G + cap 5.5GiB」，租户可用未受影响（`xc3@test` 查询正常）。 |
| P-2 | **成立**。panweidb 压参数后仍跑通方言矩阵：`panwei_a` PASS words=109 skip=1(rowid)。另发现 `max_process_memory` 有引擎下限（本轮算得 4670MB），压到 1GB 直接 `FATAL: the values of memory out of limit`，故保持原值。 |
| P-3 | **基本成立**。`docker update --memory` 未触发 Oracle/SQL Server 重启，连接不断；但 SQL Server 改小 `max server memory` 后内存不归还，需重启容器才生效（重启后 anon 991MB→633MB）。 |
| P-4 | **成立**。加 swap 后 `available` 从 775MB 升到 3265MB，未见数据库被换出到卡顿（`Swap used` 仅 19MB）。 |
| P-5 | **成立**。收缩后 `panwei_a` PASS（109 词 + skip=1(rowid)）、`gaussdb_kernel503` PASS（197 词），与基线一致。 |

### 7.5 验收读数

- `free -m` available = 3265MB（≥3GB）；`docker stats` 最高 79.0%（OceanBase），无容器贴 cap 90%。
- 12 个容器全部 `Up`，无 Restarting。
- 每实例连通：panweidb-ora / panweidb-test `select 1` 通过；OceanBase / Oracle / SQL Server / MySQL /
  MariaDB / openGauss / GaussDB / Vastbase / Vastbase-b 均取到查询结果。
  瀚高 `xc3` 账号密码已过期（`Your password has expired`），属既有状态，未闭环。
- 方言矩阵：`panwei_a` PASS words=109 batch=on 30117ms；`gaussdb_kernel503` PASS words=197 batch=on 37466ms。
- 反向验证：`xc3-highgo` cap=64M 时仍 `Up`（21~39MiB，未触发异常，仅 MemPerc 分母变化）；
  cap=16M 时 `docker ps` 显示 `Restarting (137)`、`OOMKilled=true`、`ExitCode=137`、`RestartCount=7`；
  改回 512M 后 15 秒内恢复 `Up`（18.62MiB、7 个 postgres 进程）。

### 7.7 未做项与风险

- OceanBase 仍是最大占用者（4.34GiB / 5.5GiB）；受 `__min_full_resource_pool_memory` 与 unit 下限约束无法再降。
- 瀚高 `xc3` 密码过期未改（账号策略，不属内存治理）；跑瀚高矩阵前需先改密码。
- `docker stats` 的 MemUsage 含 page cache，判读以 anon 与 `available` 为准。
