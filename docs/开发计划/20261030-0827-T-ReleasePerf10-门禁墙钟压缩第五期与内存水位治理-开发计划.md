## 一、背景与现状锚点

两件事同根：**全量测试/releaseGate 的墙钟方差与 OOM 复发都卡在同一面内存墙（Commit 上限 ~67~75GB，机器基线常驻占用 ~62GB 起）**。

结构性事实（记忆与脚本锚点，全部在役）：

1. **测试链限流在役**（`mpv-testing.gradle.kts:28`）：`MpvTestLaneLimiter` 共享服务，缺省 2 / releaseGate 编排内 3 / `-PtestShardConcurrency` 显式覆盖；分片 5 片真并发起跑，限流压「同时执行的片数」，片数/类集/覆盖面不变（T-ReleasePerf9 定案）。
2. **错峰在役**：`testShardStagger` 共享前置（编排内 240s）＋`verifyGate` 编排内 285s，把分片窗嵌进 verifyMarketplace 长杆（T7/T9 A/B 定案）。
3. **releaseGate 结构**：总墙钟 ≈ max(verifyMarketplace, verifyGate, 分片窗, 编译链) + e2e。暖窗地板 **648s**（T9 stagger240 权威轮）；长杆 verifyMarketplace 暖窗本体 ~9m15s（高占用解析 ~285s + 低占用等待窗 ~330s）。
4. **发行日方差主体**：verifyMarketplace 在线解析对「上游依赖插件前进」增量重下载。10-29 发版门禁 **21m02s，market 单步 18m29s（占整链 88%）**；慢代理窗同一笔下载税膨胀到 ~30m（10-08 记录 3.33GB/30m）。T8 已把 verifier home 外迁机器级持久目录（`GRADLE_USER_HOME/mpv-verifier-home/{gate,marketplace}`，跨树跨 clean 复用 130/131），但**保温只靠「恰好最近跑过」**，上游前进一周即可把发行日打回冷税。
5. **OOM 复发形态**（R15~R24 + T9 记录在案）：native commit OOM（hs_err `Chunk::new` / `G1 virtual space` / errno 1455 页面文件太小），诱因全是**别处占位把 Commit 顶到上限**——并行会话测试链、用户 runIde 沙盒、孤儿测试执行器、64 个 headless CDP 浏览器孤儿（20261029 实测占 20.5GB）、多 Kotlin daemon、1.7GB free 时连 daemon 都起不来。缺省限流 2 是按内存保守定的**静态值**：内存宽裕时白白慢（缺省 2 估 8.5~10min vs 限流 5 实测 5m02s），内存紧张时照样 OOM（闸门不感知实时水位）。
6. 全量 testShards 缺省限流 2 的权威读数**至今缺位**（8.5~10min 是 T9 的估值）。

**本册目标**：①测试链并发度从静态档位改为**内存水位自适应**——内存宽裕时自动提速、紧张时自动收缩，同一机制同时压缩墙钟与消灭 OOM；②给 OOM 高危形态加**执行期快速失败闸门**（水位过低秒级红＋诊断，替代 13 分钟后散成片的 native OOM）；③配**内存卫生脚本**处置孤儿占位者；④verifyMarketplace home 闲时保温，削发行日下载税。

## 二、范围与非目标

**不删不减不改语义**：分片数、每片类集、覆盖面、verdict 判定口径、e2e 内容逐一不变；限流只压并发度、错峰只延迟启动（T7/T9 已钉死的等价性口径沿用）。

**已销案勿再立项**（T6/T7/T8/T9 + T-TestPerf2/4/5 记录）：verifyGate 拆目标进程、e2e 重叠、分片再压、verifier/测试堆旋钮、GC 换型、线程面治理、多 fork、verdict 按 commit 缓存（语义阉割红线）、降片换并行（R3 铁律）。

## 三、券详单

### 券01：测试链水位自适应限流（OOM 与提速同一机制）

- **现状**：`mpv-testing.gradle.kts:30` 的 `laneLimitDefault` 是静态 2（编排内 3）。
- **修法**：新增 buildSrc 顶层类 `MemoryWatermark.kt`（`MemoryWatermarkProbe`：PowerShell 采 `Win32_OperatingSystem.FreeVirtualMemory/TotalVirtualMemorySize` ＋ top-N `PagedMemorySize64` 进程清单，输出 ASCII；探针异常返回 null）。限流注册块在 taskNames 命中 `testShards|releaseGate` 时采样并定档：
  - `effectiveFree = freeCommitGb − reserve`（reserve：testShards 0 / releaseGate 6——market 2.8GB＋gate 2.3GB＋余量）；
  - 档位：effectiveFree ≥24→5；≥18→4；≥12→3；否则 2（上限=min(5, testShardCount)；T9 实测限流 5 在 free 4.8GB 属危险区幸存，故 5 档要求 ≥24 余量）；
  - 优先级：`-PtestShardConcurrency` 显式 > 自适应 > 旧静态缺省；`-PtestLaneAdaptive=off` 一词保险丝回落旧缺省；
  - 采样只发生在分片/门禁形态（其他构建零开销）；选档与原始读数打一行 lifecycle 日志（审计可对）。
- **编排内不变式**：自适应只可能让 gate 内档位 ≥2（内存紧张时 2 片慢跑好过 OOM 重跑）；stagger 240s 不动（lane 3→4 仍是两波，分片窗不劣化）。
- **验证**：W3 A/B（§六）＋「选档日志与档位表一致」断言；负向=`-PtestLaneAdaptive=off` 行为与 HEAD 逐字一致。

### 券02：执行期水位快速失败闸门（OOM 秒级显式红）

- **现状**：水位不足时构建照常起跑，13 分钟后分片执行器 native OOM 散成片失败（R24 实测 13m28s 三份 hs_err）。
- **修法**：`testShardStagger` doFirst 最前＋`verifyGate` doFirst 最前（各自 sleep 之前）插同一检查：执行期重采水位，`freeCommitGb < floor`（缺省 6GB，`-PwatermarkFloorGb` 覆盖，`-PwatermarkGate=off` 关闭）即 `GradleException`，报文含 top-8 commit 消费者（进程名/PID/GB）、四类归因提示（按 [[pitfall-windows-cpu-attribution-diagnosis]] 的 CommandLine 归类法）、 hygiene 脚本一行指引。探针失败→降级 warn 放行（fail-open，闸门自身故障不阻断构建）。
- **时序**：testShardStagger 被全部 testShardN dependsOn 且无输出恒执行——闸门在分片 JVM 出生前完成判定；verifyGate 侧在 285s sleep 之前判，不白睡。
- **验证**：负测 `-PwatermarkFloorGb=999` → 秒级红＋诊断在场（反向两次读数：off 时正常跑完定向）；正向=常规轮不误伤。

### 券03：内存卫生脚本 `dev-support/memory-hygiene.ps1`

- **报告模式**（缺省）：按 CommandLine 归类统计 commit（GradleDaemon / test executor（`test-sandbox`）/ gradlew 壳 / 用户 IDE（IntelliJIdea）/ headless CDP（chrome/node remote-debugging）/ KotlinCompileDaemon / 其他），输出各类 GB 合计与疑孤清单（无活父壳的 executor、CDP headless、Kotlin daemon ≥2、大 commit 死进程）。
- **`-Clean` 模式**：只杀三类——①父壳已死的 test executor；②headless CDP 浏览器；③无任何客户端壳的 daemon。逐条打印 PID+命令行；**用户 IDE 与他会话工作树进程一律不碰**（R17/R22 铁律）；杀后复采水位。
- **验证**：报告模式在干净/负载两种状态下读数自洽；-Clean 的 kill 白名单用 `-WhatIf` 预演核对（不真杀用户进程）。

### 券04：verifyMarketplace home 闲时保温（削发行日下载税）

- **现状**：home 机器级持久（T8）但保温靠运气；上游依赖插件前进一周，发行日 market 单步 18m29s（10-29 实测）。
- **修法**：新任务 `verifyMarketplaceRefresh`（`mpv-verification.gradle.kts`）——JavaExec 与 verifyMarketplace 同参数面（在线、无豁免、同 marketplace home、同 assertNoForeignVerifier 锁探测），差异仅三处：报告落 `build/reports/pluginVerifierRefresh`、doLast 不做 baseline verdict 判定（只打锚点日志＋写 `home/.mpv-refresh-stamp` 时间戳）、zip 解析顺序＝`-PrefreshZip` 显式 → `distributions/*.zip` mtime 最新 → 无 zip 则 `StopExecutionException` 跳过（新树首跑不炸）。用**上一版发行 zip** 触发同一套依赖解析下载（plugin.xml 依赖面相邻版本常态不变，P-3）。
- **登记**：闲时任务系统按日登记（机器空闲窗跑一次，单 verifier JVM ~2.8GB commit 无争用）；若闲时机制只支持一次性，则按发行节奏会话内登记＋gate 侧警告兜底。
- **gate 侧警告**：`gradle-gate.ps1` 在 `$Command` 命中 `releaseGate|verifyMarketplace` 时查 stamp，>36h 陈旧打 WARN（建议先跑 `verifyMarketplaceRefresh`），不阻断。
- **验证**：refresh 轮后紧跟 `verifyMarketplace -PverifyOnly=true`（对同一 zip）应近 0 下载、墙钟 ≈ 暖窗本体 ~9m15s；W4 权威轮内观察 market 分解。

## 五、决策点

- **D-1（用户拍板，不阻塞实施）**：Windows 页面文件扩容——Commit 上限 ~67~75GB 是物理顶，扩 pagefile 可直接抬高天花板（errno 1455「页面文件太小」的直接解）。属系统级改动，本轮只落建议不代改。
- **D-2（实施时裁量）**：闲时保温若登记工具只支持一次性任务，采用「发行日前一天会话内登记＋gate WARN 兜底」形态，并把结论写进经验总结。
