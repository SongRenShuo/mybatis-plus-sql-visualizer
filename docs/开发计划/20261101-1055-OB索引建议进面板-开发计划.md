# OB 索引建议进 IDE 面板 — 开发计划（20261101-1055）

## 一、背景与目标

OceanBase（TEXT 档）的执行计划结构化渲染 fail-closed 走原生控制台，OB 的索引建议只在
MCP `sqlv_explain`/诊断报告露出，不进 IDE 的 EXPLAIN 面板。索引建议解析器已支持 OB
（`util/ExplainIndexAdvisor.adviseObPlanText`，32 例测试含路由钉住），缺的是渲染支持面。

目标：OB TEXT 计划解析成功 → 结构化渲染进 `ui/ExplainPlanResultView` 面板（建议条一并
亮起）；**fail-closed 收窄为「解析失败才回退原生」**。不改 `sqlv_explain`/MCP 侧行为，
不改 MySQL/PG 既有渲染（回归面零变化）。

## 二、fail-closed 机制链（侦察结论，已实证到行）

1. `ui/SqlPreviewPanelExecutionExplain.explainSql`（:55）→ `submitExplainOrStructured`（:410）。
2. `:458` `val format = ExplainSupport.formatFor(dialect.name)`——OceanBase 在
   `sql/ExplainSupport.kt:149-157` 登记为 `ExplainOutputFormat.TEXT`（T-OBExplainFormat
   真机实证纠档：OB CE 4.3.5.6 返回单列 `Query Plan` ASCII 计划树，非 MySQL 表格行）。
3. `:466` `ExplainPanelChannel.decide(...)`：`execute/ExplainPanelChannel.kt:29` 的
   `STRUCTURED_FORMATS = {TABLE, JSON}` 白名单**不含 TEXT** → `:87` 判
   `Decision.DirectSilent`（设计内直送，静默）。
4. `:492` → `submitExplainDirect` → `submitExplainDirectConsole` → 原生 Database 控制台。
   结构化 `onPlan`（`:541`）永不执行，`:547-551` 的 `ExplainIndexAdvisor.advise` 消费点
   对 OB 不可达 → 建议条（`ExplainPlanResultView` hints）不出现。

结论：解析器侧（`ExplainIndexAdvisor.advisePlanText` → `adviseObPlanText`）已按 OB 表头
`|ID|OPERATOR|` 取值可用；唯一缺口是通道判定把 TEXT 档整族挡在门外，以及面板需要把
单列 ASCII 树解析成 `RawResult`（headers/rows）供 `ExplainPlanResultView` 的 TABLE 渲染消费。

## 三、实施方案

### 1. 新解析器 `util/ObExplainPlanTextParser.kt`（纯逻辑，无 IDE 类型）

- `fun parse(raw: McpExplainFormatter.RawResult): McpExplainFormatter.RawResult?`——
  扫描 raw 各 cell（OB 实际是单列 `Query Plan` 多行 cell），命中 OB 表头
  `|ID|OPERATOR|…` 后取表头单元格为 headers，其后列数与表头一致的 `|…|` 行为数据行；
  **表头命中但零数据行 → null**（解析失败）；全 cell 不命中 → null。
- 输出 `RawResult(trimmedHeaders, trimmedRows, truncated, notices)`——
  `ExplainPlanResultView` 的 TABLE 分支（:187-199）直接消费，零视图改动。
- **共享原语单源化**：advisor 的 `obRowCells` + `OB_PLAN_HEADER` 移入本 object（internal），
  `ExplainIndexAdvisor` 机械改引用（行为逐字不变，其 32 例测试作回归证）。

### 2. 通道判定扩展 `execute/ExplainPanelChannel.kt`

- `ExplainSupport.Entry` 增字段 `structuredTextPlan: Boolean = false`（单一事实源：
  「TEXT 档但有面板结构化解析面」的显式登记），仅 OceanBase 置 true。
- `decide(...)` 增尾参 `dialectName: String? = null`（既有调用点/测试零改编译）：
  TEXT 档且 `isStructuredTextPlan(dialectName)` → 放行进 Structured；其余 TEXT/XML/未知
  维持 DirectSilent（H2/SQLite/Oracle 不受影响——不硬解析红线只收窄到 OB）。
- 新增 `FallbackReason.TEXT_PLAN_UNPARSEABLE` + `isStructuredTextPlan(dialectName)`。

### 3. 面板接线 `ui/SqlPreviewPanelExecutionExplain.kt`（Structured 分支 onPlan）

- lambda 参数改名 `submitted`；先按**原始行列**算建议
  （`ExplainIndexAdvisor.advise(dialect.name, submitted.raw.headers, submitted.raw.rows)`
  ——OB 单列 ASCII 树是建议器既有输入形态，建议器零改动）；
- 再做 OB 转换：`isStructuredTextPlan(dialect.name)` 时 `parse`，null →
  `notifyExplainStructuredFallback(TEXT_PLAN_UNPARSEABLE)` + `submitExplainDirect`
  （fail-closed 收窄后的唯一回退点）；成功 → `submitted.copy(raw = parsed)` 命名 `outcome`；
- 下游（history/diff/lastStructuredExplain/视图）全部消费 `outcome`——基线、对比条、
  视图拿到的是同一份解析后行列，`ExplainPlanDiff` TABLE 对齐（matchKey `id=N`）对 OB 可用；
  视图 format 传 TABLE（OB）/ 原档（其余方言）。
- `ExplainPanelWiringGuardTest` 既有字面钉全部保持命中（`outcome.raw`/`diff = planDiff`/
  `baselines = historyCompletion.baselines` 等原样存活——变量命名刻意为此设计）。

### 4. 文案（双语同加，BundleParityGuardTest 守卫）

- `panel.explain.structured.reason.textPlanUnparseable`（en/zh 各一条，挂
  `notifyExplainStructuredFallback` 的新理由分支）。
- 索引建议文案键 `explain.hint.TABLE_FULL_SCAN`/`HIGH_ROWS_ESTIMATE` 已在（R45），不新增。

## 真机回修（2026-11-01 晚，S2-15 真机报障）

**症状**：真机 OB CE 4.3.5.6（`103.36.220.245:25881/xc3_test`）`EXPLAIN SELECT * FROM t_order`
面板 toast「计划文本解析不出结构化行列（计划形态不支持）」，`parse` 恒 null。

**根因（上一节「待验证前提 ①」应验）**：真实 OB 的 EXPLAIN 是**单列 × 多行**——计划文本一行一个
cell（`rows = [["|ID|OPERATOR …|"], [""], ["|0 |TABLE FULL SCAN|t_order|3 |3 |"], …]`），
不是「一个 cell 装整段多行文本」。首版 `parse` 按 cell 逐个 `lines()` 扫描 → 表头单独命中、
`drop(headerIdx+1)` 为空 → `dataRows.isEmpty()` → null。单测当时只用合成形态（单 cell 多行），
**假绿**。同一根因也命中 `adviseObPlanText`（逐 cell 传单行 → 表头单独命中、其后行取不到 →
真机 OB 建议零命中），一并修。

**修法**：
1. `ObExplainPlanTextParser` 新增 `planLines(rows)`：全部 cell **按行序展平**为行列表
   （`rows.flatMap { row -> row.flatMap { it.lines() } }`，不拼接行内结构，`|…|` 保持原样）；
   「单 cell 多行」展平后成同一份行序列，两种形态归一，不再有第二套分支。
2. 判定内核抽为纯函数 `parseLines(List<String>): ParsedPlan?`（可注入行列表 headless 直测），
   `parse(raw)` 只做展平 + 包装 truncated/notices。判定仍是「表头门 + 按表头列位取值」，
   **未放宽到猜列位**。
3. `ExplainIndexAdvisor.advisePlanText`：先展平判 OB 表头门，命中即
   `adviseObPlanText(行列表)` 并返回；未命中维持逐 cell 的 PG 文本树口径（PG 行为零变化）。
4. 测试：真机原文照录样本（单列 × 多行，含空行与 `Outputs & filters` 段）进解析器/advisor/
   面板三层；原合成形态保留作兼容用例。
