# T-DynUpdate263：IDEA 2026.3 动态安装入口消失，自更新回退重启（2026-11-06）

- 立项：2026-11-06 10:04
- 状态：**B1/B2 已实施并验证**（能力族解析 + 护栏改口径；定向 update 包 13 类 **111/0/0/0**，`testExternal` **7/0/0/0**，243/253/262/263 四版检查器直跑 RESULT OK 且老版本仍命中旧入口）；B3 真机（2026.3 上真实热替换）待用户执行，B4 发版待用户决定。用户已撤回 Gitee `2026.11.6-beta.1` 推送，`update/update.json` 已回到 `2026.11.4-beta.2`
- 目标分支：`master`
- 来源：用户真机报障——在 IDEA 2026.3 里点「立即更新」后提示需要重启 IDE；此前（2026.2 及更早）同一路径热替换即时生效
- 取证环境：`IU-263.7307.200`（2026-11-05 20:32 启动），日志 `%LOCALAPPDATA%\JetBrains\IntelliJIdea2026.3\log\idea.log`（8.8 MB）

## 一、结论

IDEA 2026.3 删掉了 `DynamicPlugins.allowLoadUnloadWithoutRestart(...)`。`DynamicInstallSupport` 把「五个反射入口齐备」当作动态安装的总开关，缺一个就把整条链降级为重启脚本——于是热替换变成了「请重启 IDE」。**平台侧只删了一个入口，其余四个（`findPlugin` / `loadDescriptorFromArtifact` / `unloadPlugin` / `installAndLoadDynamicPlugin`）在 263 上原样存在。**

## 三、根因

### 3.1 平台侧：旧入口在 263 被移除，新入口在 262 就已并存

用 `DynamicPlugins.class` 直接读三个发行版的 jar（243 = `ideaIU-2024.3.7.1-win/lib/app-client.jar`；262 = `idea-2026.2.4-win/lib/intellij.platform.ide.impl.jar`，`IU-262.11879.100`；263 = 本机安装目录同名 jar）：

| 入口 | 243 (`IU-243.28141.41`) | 262 (`IU-262.11879.100`) | 263 (`IU-263.7307.200`) |
|---|---|---|---|
| `allowLoadUnloadWithoutRestart(descriptor…)` | 有（3 个重载，返回 `boolean`） | 有（3 个重载） | **无** |
| `validateCanUnloadWithoutRestart(PluginMainDescriptor)` | 无 | 有（返回 `String?`，null = 可卸载） | 有 |
| `checkCanUnloadWithoutRestart(descriptor)` | 有，但**返回 `String`**（语义同 validate） | 有（返回 `boolean`） | 有（返回 `boolean`） |
| `unloadPlugin` | `(IdeaPluginDescriptorImpl, UnloadPluginOptions)` | `(PluginMainDescriptor[, UnloadPluginOptions])` | `(PluginMainDescriptor)`，**单参** |
| `installAndLoadDynamicPlugin` | `(Path, JComponent, IdeaPluginDescriptorImpl)` | 同 | 同 |
| `loadDescriptorFromArtifact` | `(Path, BuildNumber)` | 同（返回 `PluginMainDescriptor`） | 同 |
| `findPlugin` | `(PluginId)` | 同 | 同 |

上游源码交叉核实（`intellij-community` `platform/platform-impl/src/com/intellij/ide/plugins/DynamicPlugins.kt`）：`262` 分支三个旧重载与新 API 并存；`master` 分支 `allowLoadUnloadWithoutRestart` 已整段消失，`validateCanUnloadWithoutRestart` 的 KDoc 是「non-null message explaining why unloading is not possible, null otherwise」，`checkCanUnloadWithoutRestart` 内部就是 `validate(...) == null`。

**同名不同返回类型的坑**：243 的 `checkCanUnloadWithoutRestart` 返回 `String`（原因消息），262/263 返回 `boolean`。只按名字 + 首参匹配会绑错语义，必须连返回类型一起判。

### 3.2 插件侧：探测是「全有或全无」

`DynamicInstallSupport.PlatformApis.buildApi()`（`DynamicInstallSupport.kt:353-405`）逐条 `method(...)`，任一条 `?: error(...)` 即整体抛出；`probe()` 捕获后返回 `null`，`doInstall()` 第 3 步直接 `fallbackToRestartScript(zip, "platform dynamic-install APIs unavailable")`（`:70-73`）。

设计意图（类 KDoc）是「未来版本签名漂移 → 整体降级，不劣化旧行为」，这层兜底是对的；错的是**把「旧名字消失」等同于「平台失去动态装卸能力」**——263 只是换了名字。

### 3.3 为什么护栏没拦住

1. `verifyPlugin` 做的是字节码级检查，反射入口对它不可见；263 早已是验证目标（`buildSrc/src/main/kotlin/mpv-verification.gradle.kts:34/40/44` 三处都在列），照样绿。
2. `PlatformSignatureChecker.java:73-75` 第 1 项硬要求 `allowLoadUnloadWithoutRestart`——**它其实会红**，但它只在 `PlatformSignatureCrossVersionTest` 里跑，且需要目标发行版已解包（本机 `F:/gradle-home/caches/9.7.0/transforms/c819746d…/idea-2026.3-win` 已存在）。也就是说：护栏有能力看见这次漂移，只是没被跑到。CI 上没有该发行版解包，同样跑不到。

结论：护栏的「可发现性」依赖本地环境，属于**事后**发现；本券要把它变成**事前**（改判定口径，不再绑死旧名字）。

## 四、影响面

- IDEA 2026.3（含 EAP）上，插件自更新**必然**走重启脚本——不是偶发。
- 2026.2 及更早不受影响（旧入口仍在）。
- 已撤回的 `2026.11.6-beta.1` 若按原样发出，所有 2026.3 用户更新时都会被要求重启；`update.json` 现为 `2026.11.4-beta.2`，`update/preview.update.json` 草稿仍是 `2026.11.6-beta.1`。

## 五、修复方案

### R1 能力族解析（主修，`DynamicInstallSupport.kt`）

把「入口是否存在」换成「能力族是否可解析」，按 `(方法名, 返回类型)` 绑定：

1. **Validate 族**：`validateCanUnloadWithoutRestart(<descriptor>): String`，或 243 形态的 `checkCanUnloadWithoutRestart(<descriptor>): String`（同名、返回 String，语义就是「不可卸载的原因」）。返回值 `null`/空白 = 可卸载。
2. **Check 族**：`checkCanUnloadWithoutRestart(<descriptor>): boolean`（262/263）。
3. **Legacy 族**：`allowLoadUnloadWithoutRestart(<descriptor>): boolean`（243/262）。

优先级 **Legacy > Validate > Check**：老版本必须与改动前走同一条路径（243 的旧入口源码就是
`checkCanUnloadWithoutRestart(...) == null` 的布尔包装；262 的旧入口走 `validateDynamicReconfigurationPossible(newState)`
整组重配置预演，与单插件的 `validateCanUnloadWithoutRestart` 不是同一套判定），行为差异只落在「原本就不工作」的 263。
三族全无才判能力缺失。

### R2 诊断可读性

- 卸载被平台否决时，把 Validate 族的**原因字符串**打进日志（现在只有一句笼统的 `dynamic unload rejected by platform (vetoer/EP/dependency)`）。
- `buildApi()` 改为**收集全部缺失项一次性报**（`missing=[a, b, ...]`），并打印解析到的能力族名——下次再漂移，日志一眼能定位，不用再翻 jar。
- 首次探测成功时打一行 INFO：`dynamic-install api family=validate|check|legacy`，用户日志里可自证能力面。

### R3 卸载语义（263 单参）

263 的 `unloadPlugin(PluginMainDescriptor)` 内部走 `computeNewPluginsState` + `reconfigureImpl`，不再接受 `UnloadPluginOptions(disable = true)`。现有弹性匹配（最少参数优先）在 262 上就已经落到单参重载，263 形态不变，**预计无需改代码**；但「卸载后插件是否仍为启用态」需要真机确认——若装完变成 disabled，补一次 `PluginEnabler.HEADLESS.enable`（P-4）。

### R4 护栏改口径（`src/test/java/PlatformSignatureChecker.java`）

第 1 项从「必须有 `allowLoadUnloadWithoutRestart`」改为「三族任一可解析」，并输出族名；同时补一条自证用例（构造 243 的 String 形态 / 263 的 boolean 形态 / 只有旧名三种假类，证明判定真的在看返回类型）。`PlatformSignatureCrossVersionTest` 增加断言：每个发行版都必须打印出族名，防止「三族全空但 RESULT OK」的空绿。

### R5 EP dynamic 守卫扩到 263（P2，可后置）

`PluginXmlExtensionPointResolutionTest.dynamicFlagsFromClasspath()` 现在只读测试类路径（243）。263 上本插件 57 处 EP 注册是否仍全部落在 `dynamic="true"` 点位，目前无本地判定——把 263 distro 的 EP 声明表喂给同一判定函数即可复用。

### R6 发行

`update/update.json` 按仓库纪律只有用户能改。修复版通过门禁后，由用户决定是重发 `2026.11.6-beta.1` 还是升 `beta.2`。

## 十、风险与回退

- 反射入口全失配时仍回退重启脚本，**现状不劣化**（这次就是兜底生效）。
- 「旧版已卸载、新版装载失败」是既有风险，现有逻辑回退脚本、用户重启即修复，本券不改。
- 若 P-3 被证伪（263 上 EP 合规被打破），处置是 R5 扩守卫 + 视情况把相应能力标成「需重启」，**不在本券硬扛**。

## 十一、不做的事

- 不把编译基准升到 263（基线仍 243，避免牵动全仓工具链）。
- 不用平台的 `reconfigure` / `checkCanReconfigureWithoutRestart` 协程管线（suspend + `ProductMode` + `PluginStateValidator`，反射成本远高于收益）。

### 教训（`docs/LESSONS.md` 在 dev 分支才存在，master 无此文件，暂记于此，合流后并入）

> **平台 API 改名 ≠ 能力消失，能力探测按能力族不按名字。** 反射门面把「某方法存在」当能力开关时，平台一次重命名就会让整条链静默降级；正确形态是「同一能力的多代签名任取其一」，且**返回类型也进判据**（同名不同语义的跨版本陷阱）。证据：263 删 `allowLoadUnloadWithoutRestart` 后 `DynamicInstallSupport` 全链回退重启（`idea.log` L39249/L39297），而 262 起平台已并存 `validate/check` 两族。
