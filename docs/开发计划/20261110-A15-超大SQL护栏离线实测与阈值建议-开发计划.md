## 三、headless 离线实测方法

### 编译与口径

- 工具链：缓存的 `kotlinc` 1.9.23-release-779（IDEA 2024.1 Kotlin 插件自带，
  `F:/gradle-home/caches/.../ideaIU-2024.1/plugins/Kotlin/kotlinc`）+ JDK 17.0.19
  （`JAVA_HOME=C:/Users/USER/.jdks/ms-17.0.19`）+ `kotlin-stdlib.jar`。**未跑 gradle**。
- **被测代码是生产原文件逐字副本**：从 master `HEAD` 取出 13 个纯函数内核
  （`git show HEAD:<path>`），从 `dev` 取出 2 个护栏对象与 `xml/` 解析闭包共 21 个文件
  （`git show dev:<path>`），逐个 `sha256sum` 与 `git show` 输出比对，**全部 MATCH**。
  即下文读数是**真实生产 Kotlin 函数**的耗时，不是 Python 重实现、不是合成等价物。
- 平台依赖用最小 Java 桩替代（仅让编译通过、不参与被测逻辑）：
  `LexerBase`（含 `getTokenText()`）、`IElementType`、`Language.ANY`、`TokenType.WHITE_SPACE`、
  `Logger`（no-op）、`model.LikePosition` 枚举、`PreviewResult` 数据类（只留
  `paramCountOf` 读到的字段）、`MpSqlVisualizerBundle.message`（返回 key）。
  `XmlDirectText.kt` / `XmlInlineSqlDetector.kt`（用 `com.intellij.psi.xml.XmlTag`）不在
  `XmlMapperParser.parse` 闭包内，未纳入编译（已 grep 复核零引用）。
- 计时：`System.nanoTime()`，每例 warmup 3 次、重复 9 次，取 min / median / max（ms）。
- 内存：`com.sun.management.ThreadMXBean.currentThreadAllocatedBytes()`（JVM 侧的
  `tracemalloc` 等价物，实测 `allocSupported=true`），每例前后取差，报**精确线程分配字节**
  的 9 次中位数（KiB）。比 `heapMemoryUsage.used` 更细——后者受 GC 粒度影响只能读到
  MiB 整数倍。首轮曾用它，已弃用；本轮用精确分配字节。
- 造数：纯 ASCII、确定性 `repeat`，写入系统临时目录，不入库。SQL 夹具为带 `?` 占位符的
  多行 SELECT（每行含 JOIN / LIKE / BETWEEN / ORDER BY / LIMIT）；mapper 夹具为
  `<mapper>` + N 条 `<select id="qN">` 语句。

## 五、阈值建议与降级方案

给三档建议，逐条标注证据来源（实测 / 既有读数 / 推断），**不拍板、不改码**。
判据统一用「纯函数内核累计 median 耗时 + 分配」作为**代理刻度**，
真机 EDT 叠加另需 GUI 验收（§六）。

### 档 A：保持 dev 现值（推荐）

| 常量 | 现值 | 建议 | 判据 | 证据 |
|---|---|---|---|---|
| `DECORATION_LIMIT_CHARS` | 204800（200K 字符） | **保持** | 200KB 处 7 链累计 20ms / 17.8 MiB，仍在「一次预览」量级；1MB 处跳到 95ms / 89 MiB，跨过 200KB 后成本单调上升，把线画在 200KB 正好在拐点前 | 实测（§4.2） |
| `RENDER_LIMIT_CHARS` | 1048576（1M 字符） | **保持** | 1MB 是「必须让用户知道为什么没标注」的诚实提示线；实测 1MB 累计 95ms，真机叠加平台开销后是可见卡顿量级，此时挂提示合理；`>1MB` 才提示避免正常大 SQL 被无谓打扰 | 实测（§4.2）+ dev KDoc |
| `MAX_TEXT_BYTES` | 2097152（2MB） | **保持** | 预算内 1MB/4000 完整解析 16ms / 9.6 MiB 可接受；2MB 文本已触发降级且降级成本 7ms / 6 KiB；JDK DOM 代理 13ms / 6.9 MiB 只是下界，叠加语句树只会更高 | 实测（§4.3） |
| `MAX_TOP_LEVEL_NODES` | 5000 | **保持** | 4000 语句在预算内、9000 语句降级；5000 卡在中间，与「代码生成产物常见」的注释口径吻合。多算（CDATA 里 `<select`）的后果只是降级提示，比漏判后卡住安全 | 实测（§4.3）+ dev KDoc |
| `MAX_ID_SCAN` | 200 | **保持** | 实测 1MB 与 2MB 的 id 扫描成本都被钉在 0~1ms / 135 KiB，不随文件大小增长；提示不需要穷举 | 实测（§4.1） |

**总判据**：dev 现值全部有实测支撑，且 `plan()` / `check()` 自身零到几毫秒、不接设置 UI
（调大即失去保护）。本轮没有发现任何「现值明显偏松或偏紧」的读数，**保持是默认结论**。

### 档 B：分级细化（可选增强，需新证据才动）

只在「真机 EDT 叠加实测」表明某档仍卡或明显过早降级时才考虑，本轮**不实施**：

| 候选 | 触发条件（待验证前提） | 证据 |
|---|---|---|
| 在 200KB~1MB 之间加「部分装饰」档（保留 `SqlFormatter`、只关逐行标注/逐值参数） | 需真机证明 `SqlFormatter.format` 在 EDT 上可感但高亮/折叠不可感 | 推断（本轮只有纯函数分项读数，`SqlFormatter` 1MB 40ms / 45 MiB 是单链最大头） |
| `MAX_TOP_LEVEL_NODES` 按「文本字节 + 节点数」双轴加权 | 需真机证明 4000 语句 / 1.2MB 的面板渲染已卡 | 推断（本轮只测到解析链 16ms，面板渲染不可达） |
| 提示线 `RENDER_LIMIT_CHARS` 与装饰线合并 | 需用户反馈「200KB~1MB 之间关了装饰却没提示，不知道为什么」 | 推断（dev 现设计有意让 `SKIP_DECORATION` 静默） |

### 档 C：上调 / 下调（本轮证据不支持，不建议）

| 方向 | 结论 | 理由 |
|---|---|---|
| 上调 `DECORATION_LIMIT_CHARS`（如 512KB） | **不建议** | 实测 1MB 累计 95ms / 89 MiB，且真机还有平台叠加；上调等于把保护往后推到已可见卡顿的区间。dev 注释「调大只会失去保护」与本轮线性度读数一致 |
| 上调 `MAX_TEXT_BYTES` / `MAX_TOP_LEVEL_NODES` | **不建议** | 2MB 的完整生产解析被护栏短路后无法直测，JDK DOM 代理 13ms / 6.9 MiB 只是下界；没有「放行也安全」的真机证据 |
| 下调任一阈值 | **不建议** | 100KB / 200KB 累计仅 17~20ms、8.9~17.8 MiB，200KB 处 `SKIP_DECORATION` 已在拐点前；再往下调会让正常大 SQL 过早失去高亮/折叠，属体验回退 |
| 把阈值接进设置 UI | **不建议** | dev 两处 KDoc 明写「安全护栏，不接设置 UI」；本轮实测 `plan()` 0ms，护栏本身零成本，开放调节只增风险 |

### 降级方案现状核对（dev 已实施，本轮只复核）

- 正文**永不截断**：`plan()` 只返回档位，不改写 `result.sql`；参数面板早退只加汇总标签，
  结果视图只挂横幅。与任务书「截断不丢执行能力」一致（既有读数：F-09 定向全绿）。
- 装饰**整体关**而非半截：`decorationsEnabled` 一个布尔同时门控高亮增强、自动折叠、
  逐行标注；`perValueParamsEnabled` 同时门控参数逐值行。无「只装饰前半段」形态。
- 诚实提示：`NOTICE_ONLY` 档走既有 `degradationBanner`（`RENDER_WARNING`），文案双语均声明
  「原文完整保留，可在导出/执行链使用」；参数面板另有 `paramSizeGuardSummary` 报省掉的参数行数。
- mapper 降级：`degraded = true` + `statements` 空 + `errors` 带原因与 id 清单，
  `XmlPreviewService` 早退避免「mapper 中无语句」误导文案；不抛异常、不建树。

## 六、待验证前提（供后续 GUI / 收口证伪）

1. **真机 EDT 叠加**：本轮 7 链累计 95ms（1MB）是纯函数内核的 median 求和，不含
   `Editor` 文档写入、`RangeHighlighter` 逐 mark、`FoldingModel.runBatchFoldingOperation`、
   每个参数一行 `JBTextField` + `DocumentListener`。真机是否达到「可见卡顿」需 runIde
   沙盒埋点（任务书明令本轮不跑 GUI/沙盒）。**这是「200KB / 1MB 阈值是否恰好」的唯一权威刻度。**
2. **阈值口径是字符数不是字节数**：`SqlSizeGuard` 用 `text.length`（UTF-16 单元），
   `XmlParseBudget` 用 UTF-8 字节。纯 ASCII 夹具下两者一致；含大量中文的 SQL 在
   `SqlSizeGuard` 下会比「KB」直觉更早触发，需真机确认是否要改按字节。
3. **合成夹具形态**：单行 SELECT 夹具使 `SqlAutoFoldPlanner` 产出 0 区；已补折叠活跃夹具
   （8 列分行，1MB 产出 8457 区）覆盖「建区」成本。但真实 SQL 的列数/行数分布不同，
   折叠区数量与成本可能偏离。
4. **`ExecutableSqlFormatter.format` 空参数表读数 0ms** 是因为无 `?` 可替换时直接返回原文；
   它不在护栏关闭清单内（执行链/导出读正文），本轮列它是为了证「正文链不受影响」，
   不代表带真实参数表时的回填成本。
5. **`XmlParseBudget.check` 的 0ms 短路**：2MB/9000 因 `length > 2MB` 第一段即返回，
   未走到节点正则；`TOO_MANY_NODES` 单独触发路径（文本 <2MB 但 >5000 节点）本轮未单测，
   dev `XmlParseBudgetTest.超节点上限走降级模型并给id清单` 已覆盖该形态（既有读数）。
