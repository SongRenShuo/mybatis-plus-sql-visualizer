## 一、现状问题（实测定性，非估算）

两条列表共用同一套两行卡片结构：日志页 `LogEntryListCellRenderer`（`LogEntryRendering.kt:316`）、
历史页 `HistoryCellRenderer`（`HistorySqlLogPanel.kt:1421`）。每个条目 = 左侧 3px 类型色条 +
元信息行（`SimpleColoredComponent`）+ 1~N 行 SQL（`SimpleColoredComponent` 组件池）。

五个结构性缺陷：

1. **元信息平铺无列概念**。片段顺序固定为 `#序号 → 时间戳 → 耗时 → [库] → [MCP] → (影响行数) → 报错 →
   ⨉去重 → 同模板 → [文件:行号]`（`SqlEntryPresentation.kt:19`）。每段宽度随内容浮动，第二段起点取决于
   第一段多宽，无法竖着扫。

2. **超宽只做整段截断**。两列表都强制跟随视口宽度（`LogEntryFiltering.kt:154` 的
   `getScrollableTracksViewportWidth() = true`），横向滚动条被禁（`SqlLogPanel.kt:1546`），溢出统一交给
   `clipForList` 二分测量截断（`SqlEntryPresentation.kt:54`）。截断点由窗口宽度决定，实践中最常见的是把
   `[BizCarStationOccupyInfoServiceImpl.java:1…` 的**行号**切掉。

3. **时间戳逐行重复**。默认格式 `yyyy-MM-dd HH:mm:ss`（`PluginSettings.kt:784`）占 19 字符，同秒内多条
   几乎完全相同却每条重画。

4. **SQL 实际可用宽度被元信息挤压**。元信息越长，`…` 出现越早，「查哪张表」这类首要信息越容易被裁掉。

5. **两个渲染器重复实现**。`LogEntryListCellRenderer` 与 `HistoryCellRenderer` 的
   `getListCellRendererComponent` / `ensureSqlLineCount` / `sqlLineFragmentsFor` 三组方法近乎逐行同构，
   一处改动必须人工同步两遍（本次改造的直接诱因之一）。

另有两处既有不一致，本次顺带对齐：

- 历史页元信息把 `showDuration` 硬编码为 `true`（`HistorySqlLogPanel.kt:1487`），设置页关掉耗时对历史页无效。
- 历史页 `showLogDetails` 默认 false，故不显示影响行数与报错片段，与日志页信息集不一致。

## 二、定稿形态

### 2.1 条目结构

```
[3px色条] [88px 信息轨] [1px竖线] [SQL 区]
            #3 13:03:55      ← 行1：序号 + 时间（HH:mm:ss）
                 28ms        ← 行2：耗时，右对齐，按阈值分档着色
            ▁▁▁▁▁▁▁▁▁       ← 行3：2px 耗时条，按当前列表最大耗时归一
            …alletRecharge   ← 行4：类名（骨架化压缩）
```

- **类型表达**只留左侧 3px 色条，**不加「查/增/改/删」字样**（用户明确否决）。
- 耗时条归一化基准 = 当前列表可见条目的最大耗时，随排序/过滤刷新。
- 分档配色沿用既有阈值：`>= threshold` 红、`>= threshold/2` 橙、其余绿（`LogEntryRendering.kt:208`）。

### 2.2 三种显示模式

| 模式 | 信息轨 | SQL 区 |
|---|---|---|
| `SINGLE_LINE` | 压成 2 行：`#N 时间` / `耗时 + 类名`，无进度条 | 单行固定行高 |
| `KEYWORD_WRAP` | 4 行完整轨 | **三行实内容**：SELECT / FROM / WHERE 三个子句都读到，剩余条数缩成第三行行尾 `… (+N)` |
| `FORMATTED` | 4 行完整轨 + **垂直分布**（时间顶锚点、耗时居中、类名沉底） | **不封顶**，全部子句展开 |

关键字换行的关键变化：现有实现是「超 3 行时取前 2 行 + 整行占位符」（`SqlEntryPresentation.kt:42`），
等于第三行什么都不给看。改为三个子句全渲染，`… (+N)` 只作为第三行行尾标记。

### 2.3 类名压缩规则

原实现取前 11 字符，实测 `BizCarStationOccupyInfoServiceImpl` 与 `BizCarStationOccupyController`
都压成 `BizCarStati…`，完全无法区分。改为**先剥公共后缀再取尾部**：

```
剥除：(ServiceImpl|Controller|Service|Mapper|Repository|Impl)$
仍超 14 字符 → 保留末尾 13 字符，前缀加 …
```

实测效果：`…ionOccupyInfo` / `…alletRecharge` / `BizTaskRecord` 可区分。

## 三、待验证前提（实施者先证伪再动手）

以下四条是本次推断，**未经实测**，动手前必须逐条验证：

- **P1｜轨道的 4 行不会撑破单行模式的固定行高**。单行模式当前靠
  `fixedCellHeight = measureFixedCellHeight()`（`SqlLogPanel.kt:1583`）走 O(1) 快路径，样例是
  `SELECT 1` 渲染一次取首选高。若轨道压成 2 行后仍高于 SQL 行，行高会从 ~27px 涨到 ~30px，
  一屏条数下降。**先量再定**：若涨幅 >3px，考虑把「耗时 + 类名」这一行的字号降到 9px。

- **P2｜`SpeedSearchUtil.applySpeedSearchHighlighting` 能作用到轨道内的多个 `SimpleColoredComponent`**。
  现实现只对 `metaLine` 与各 SQL 行调用。轨道拆成多个组件后，若漏调某一项，该列的搜索高亮会静默失效
  （不会报错，只是不亮）。**验证方式**：`ListSpeedSearch` 输入关键词后逐列断言 `STYLE_SEARCH_MATCH`。

- **P3｜`clipForList` 的可用宽度算式对轨道不适用**。现有算式
  `list.width - cell.insets.left - cell.insets.right - colorBarWidth - list.insets.left - list.insets.right`
  （`SqlEntryPresentation.kt:54`）只扣了色条宽度。轨道 88px 必须在算式里再扣掉，否则 SQL 行会按
  比实际宽 88px 的宽度测量，导致末尾字符被 `…` 吞掉却看不出来。**这是最容易被忽略、症状最隐蔽的一条。**

- **P4｜格式化模式下轨道的 `justify-content: space-between` 等价实现**。Swing 里要让轨道三项
  「顶/中/底」分布，需要用 `BorderLayout(NORTH/CENTER/SOUTH)` 或 `BoxLayout(Y) + verticalGlue`，
  而当前 `linesPanel` 是 `GridLayout(0,1)` 顶对齐。**若轨道用 `BorderLayout`，注意它默认拉伸 CENTER**，
  耗时会被垂直居中到行高一半，这正是需要的效果；但要确认行高由谁撑起（SQL 区还是轨道），
  否则 SQL 只有 1 行时轨道会被压扁。

## 四、实施步骤

### W1｜抽出共用轨道组件

新增 `src/main/kotlin/cn/song/mybatisplus/visualizer/log/LogEntryRail.kt`：

```kotlin
internal class LogEntryRail {
    internal val timeLine = SimpleColoredComponent()      // #N + HH:mm:ss
    internal val durationLine = SimpleColoredComponent()  // 53ms
    internal val track = JPanel()                          // 2px 进度条（自绘）
    internal val sourceLine = SimpleColoredComponent()     // 类名
    fun bind(entry, isSelected, maxDurationMs, fg)
    fun setCompact(compact: Boolean)                       // SINGLE_LINE 两行模式
}
```

`bind` 内完成：序号时间格式化、耗时分档着色、进度条宽度（`ms / maxMs`）、类名骨架化。
不持有条目状态，纯投影，便于单测直接断言。

### W2｜两处渲染器接轨

- `LogEntryListCellRenderer`（`LogEntryRendering.kt:316`）：`linesPanel` 由
  `GridLayout(0,1)` 改为 `BorderLayout(轨道 WEST + SQL 区 CENTER)`；`add(rail, WEST)`。
- `HistoryCellRenderer`（`HistorySqlLogPanel.kt:1421`）：同款改造。
- **顺带消除重复**：把 `ensureSqlLineCount` / `sqlLineFragmentsFor` 提到文件级 internal 函数或共用基类，
  两处调用同一份实现。

### W3｜三种模式分流

- `visibleSqlLines`（`SqlEntryPresentation.kt:42`）：KEYWORD_WRAP 分支改为「全渲染，`… (+N)` 附在末行行尾」；
  FORMATTED 分支保持不封顶（现状已是）。
- 单行模式：`LogEntryRail.setCompact(true)` + 隐藏 track。
- 格式化模式：轨道切 `BorderLayout` 分布；`applyListCellHeight` 仍返回 -1。

### W4｜宽度算式修正（对应 P3）

`clipForList` 增加 `railWidth` 参数，SQL 行与元信息各自按实际可用宽度测量。

### W5｜最大耗时快照

两个面板在 `refreshList` / `applySqlSearch` 时算一次 `maxDurationMs` 传给渲染器，
沿用 `dedupeCounts` / `templateCounts` 的既有快照范式（`LogEntryRendering.kt:317`）。

### 8.2 实施中偏离计划的地方

1. **抽出共用基类**（计划外）。原计划只写「两处渲染器接轨」，实际发现两处仍有约 100 行逐行同构（`getListCellRendererComponent` / `ensureSqlLineCount` / `sqlLineFragmentsFor`）。改版时一并收进 `RailCellRendererBase`，`HistorySqlLogPanel.kt` 净减约 100 行。子类只声明 `templateCountsSnapshot` / `maxDurationMsSnapshot` / `dedupeCountsSnapshot` / `showDuration` 四个差异点。

2. **徽章与角标迁到注脚行**（计划外）。定稿图里没有画 `⨉N` / `同结构 N 条` / `[MySQL]` / `(3 rows)` 这些片段，但它们是既有能力，不能静默丢弃。这些片段宽度不可控（`[MySQL · jpa_demo@localhost:3306]`、影响行数），塞进 88px 轨道会被截成无意义残片，故新增**SQL 区下方通栏注脚行**承载。报错另挂独立错误行（红字）。

3. **顺带修复历史页两处不一致**（计划 §1 已记录，本次落地）：耗时开关从硬编码 `true` 改为跟随设置；报错片段从「不显示」改为「显示」（去重计数仍只属实时通道）。

4. **压测套件新增 31 例**（计划外，用户中途两次追加要求：「几千或几万条压测」→「搜索还有筛选排序，所有功能都需要压力测试」）。见 §8.3。

### 8.3 压测与性能修复

用户中途强调「面板内容多、更新快，不得因渲染卡死」，故把性能从「顺带关注」提升为专项。

**两个压测套件，共 31 例，两档判据**：

| 套件 | 压什么 | 用例 |
|---|---|---|
| `LogEntryRailPerfTest` | 渲染器热路径：单格成本、组件树稳定、缓存失效、宽度算式 | 17 |
| `LogPipelinePerfTest` | 刷新管线：搜索/筛选（类型·慢查询·屏蔽）/排序（七模式）/完整管线/线性度 | 14 |

- 绝对耗时预算：单格 2ms（实测 0.03~0.05ms，约 30 倍余量），只拦数量级退化
- 结构性判据：组件树规模稳定 + `preferredSize` 变更次数为零 + 管线成本随条数线性（不依赖机器快慢）
- 数据规模：200 条 / 2000 条 / **20000 条** 三档

**实测读数**（headless / JDK 21）：

| 场景 | 200 条 | 20000 条 |
|---|---|---|
| 单行模式单格 | 0.0480 ms | 0.0469 ms |
| 关键字换行单格 | 0.0324 ms | 0.0408 ms |
| 格式化单格 | 0.0338 ms | 0.0358 ms |
| 最大耗时扫描 | — | 0.6092 ms/次 |

**结论**：渲染成本与总条数无关（两档持平），一屏 20 格约 1ms，远低于一帧预算。

**管线读数**（20000 条，headless）：搜索在 40ms 预算内、正则 120ms 内、类型筛选 20ms 内、
慢查询 20ms 内、屏蔽 30ms 内；排序七模式 TIME 3.7/4.1ms、DURATION 10.2/9.1ms、
SEQUENCE 0.3ms、STRUCTURE_CLUSTER 16.4ms、DATABASE_GROUP 7.1ms；
**完整刷新管线 22.4ms**。四条常态路径（空查询 / 类型全选 / 慢查询关 / 无屏蔽规则）实测零成本透传。

**刷新频率已有保护**（既有，非本次引入）：内容通知节流 20 条或 200ms 双阈值；搜索输入防抖 200ms。
两万条最坏情况每秒最多 5 次刷新 × 22.4ms ≈ EDT 占 11%，本次改动只新增 0.6ms/次（占 3%）。

**审查中发现并修复的三处热路径隐患**（均为改版初稿引入，压测/审查阶段修掉）：

1. `railHost.preferredSize` 每格新建 `Dimension` → propertyChange → revalidate。改为只在宽度变化时设。
   副产：`LogEntryRail.setRailWidth` 加 `railWidthApplied` 标志——缓存初值等于默认宽度时，
   仅比数值会把首次调用误判为「已设置」，导致窄侧栏降档失效（此 bug 由压测用例抓出）。
2. 注脚片段每格 `buildList` 重建。改为按（条目引用 + 选中态 + 两份快照引用）缓存。
3. `mapNotNull{}.maxOrNull()` 每次刷新分配临时列表。改为单遍零分配 `maxDurationOf()`。
4. 附带：`railTimeFormat` 每格重走字符扫描 → 按配置串缓存（单变量，非 Map）。
