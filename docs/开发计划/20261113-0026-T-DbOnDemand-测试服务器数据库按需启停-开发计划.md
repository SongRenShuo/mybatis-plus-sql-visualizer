## 三、方案设计

核心原则：**无租约记账，以「该端口当前有无 established 连接」为唯一占用判据**。本地、CI、人工三路并存时天然安全——有连接就不停，连接断了空闲满 N 分钟就收。不做「谁起谁管停」的记账，因为多路并发（本地跑着 + CI 在跑 + 用户开着 DBX）会让租约账本变成新的踩坑面。

### 3.1 服务器侧 `dbctl`（唯一权威入口，repo 内 `dev-support/dbctl/`，装机照 svbackup 模式）

- `dbctl-registry.tsv`：key → 容器名 / 宿主端口 / 容器内端口 / 健康探针命令 / 启动预算秒 / 启动覆盖命令 / 预期 RSS / pin 标志。
  覆盖北京全部在役容器（12 个正常 + tidb 单列标记废弃）；已知特殊项：海量 A 停起走 `/opt/xc3-vastbase/start.sh`（skill §0 台账），磐维两实例 `--privileged`。
  pin 默认值（D2 拍板）：**xc3-mysql8 = pinned**，其余全空——pinned 实例不参与 restart=no 转换、不被 reaper 回收。
- `dbctl start <key…>`：幂等（已在跑直接跳过并报 healthy）；**逐个起、按预期 RSS 降序**，每个起之前过内存闸门（`available ≥ 预期RSS + 500MB` 余量，不足则停下并给清晰报告：哪些起了、哪个被闸、建议先停谁）；
  健康等待 = 宿主 TCP 探活 + 容器内探针命令（各引擎 client 路径登记在 registry），到启动预算仍未 healthy 判失败并继续后续 key（与 dialectExternalVerify 的实例级看门狗同口径）。输出各实例启动耗时。
- `dbctl stop <key…>`：pin 豁免。
- `dbctl stop-idle --min <N>`：对每个未 pin 且运行中的容器，探测其端口 **established 连接数**（候选机制：`nsenter -t <容器PID> -n ss -tn state established '( sport = :<容器内端口> )'`，绕开 docker-proxy/DNAT 差异，P2 实测定案；宿主 `ss` 过滤发布端口作兜底），连接数为 0 持续满 N 分钟才 stop。
- `dbctl status`：表格（key / 容器状态 / 健康 / RSS / 当前连接数 / 最近一次启停时间与原因），这是「11-09 那种连红」未来的排障第一站。
- 空闲回收 systemd timer：每 10 分钟跑一次 `dbctl stop-idle --min <D3 阈值，建议 15>`。
- `--dry-run` 与 `--fake-available <MB>` 两个测试钩子（反向验证要用，见 §五）。

### 3.2 重启策略转换（与铁律 3 的冲突处置）

对全部按需实例执行 `docker update --restart=no`（**pin 的 xc3-mysql8 保留 unless-stopped**）。db-env-provisioning 铁律 3（「容器一律 `--restart unless-stopped`」）**同批修订**为按用途二分：常开实例 unless-stopped，按需实例 restart=no、由 dbctl 托管。`scripts/bootstrap-db-env.sh`（§9 从零重放）同步改，否则下次整机重建又回到全自起。

代价：容器崩溃后不再自动拉起。但换来的是故障**可见**（status 一眼看穿谁停了、为什么），且 dialect 腿红会带 dbctl 的失败原因而不是裸 connection refused。备选方案（保留 unless-stopped + 开机即停单元）记录为 D4。

### 3.3 本地包装脚本 `dev-support/dbctl/run-dialect-verify.ps1`

1. 读 `.local/dialect-external-matrix.properties`，按实例 URL 的 host 归组（北京组才有 dbctl 动作）；
2. SSH（dbcictl 密钥账户，M0 配好）→ `dbctl start <北京组 keys>` → 等待 healthy；
3. 原样执行 `./gradlew dialectExternalVerify`（矩阵、任务、参数全不动）；
4. 结束后不显式 stop，交给空闲回收（本地调试中途还会重跑，立刻 stop 反而添乱；急着释放可手动 `dbctl stop-idle --min 0`）。
5. 保留 `--no-dbctl` 逃生口 = 现在的裸 gradle 用法。

### 3.4 CI 集成（nightly-full.yml dialect job）

- 新 step（在 gradle 之前）：从 secret `MPV_DBCTL_SSH_KEY` 落私钥 → `ssh -o StrictHostKeyChecking=accept-new dbcictl@103.36.220.245 -- dbctl start panwei_a gaussdb_kernel503` → 输出健康读数；失败时显式红并写明「实例未起来」，不再让 gradle 端报模糊的 connection refused。
- **不加 stop 步**：reaper 兜底，避免 CI 与本地并行时互踩。
- 预算重算：job timeout 35→40min，步骤 25→28min（启动等待按实测最大值 +5min 余量，落地时按 M1 的实测启动耗时回填算式，注释同步更新）。
- 凭据安全：服务器建受限账户 `dbcictl`，authorized_keys 强制命令白名单（只放行 `dbctl start / status / stop-idle`，CI key 不给 stop）+ `no-port-forwarding,no-pty,no-agent-forwarding`；私钥进 GitHub secret。secret 录入与安全组若需开端口，属对外动作，**等用户授权/亲手操作**（AGENTS.md 规则 9）。
- 114 上的 mysql84 / pg16 两腿不动（见 D1 / D5）。

### 3.5 备份协调（svbackup）

`svbackup-collect.sh` 开头对本次要 dump 的容器清单调 `dbctl start`（幂等，非 pin 也能起），收尾调 `dbctl stop-idle --min 0 --only <本次清单>`——只回收「因备份而起的、现在已无连接」的容器，绝不碰 pin 与有连接的实例。srv-backup-restore skill 与「整机重建」文档同步补这段。反向口径：改前「全停状态跑备份应 FAIL」、改后「同状态应 PASS」，两读数都要留（§五 V4）。

## 七、待验证前提（实施者先证伪再动手）

- P1：panwei/gaussdb/OB 等 stop→start 往返后数据与账号完好（理论上是普通容器生命周期，但磐维 `--privileged` + 引擎内部参数特殊，必须实测一轮再全量转换 restart 策略）。
- P2：established 连接探测机制——nsenter 进容器 netns 用 `ss` 在本机可用且能数到 JDBC/DBX 的连接（docker-proxy 与 DNAT 两种网络模式下宿主 `ss` 的可见性不同，P2 定案后写死机制）。
- P3：各容器内健康探针命令（dm8 / kingbase / vastbase / highgo 的 client 路径各异），逐个实测填 registry，不许写「应该能行」。
- P4：GitHub windows runner 的 OpenSSH 客户端可用、服务器 SSH 端口对 runner 网段可达（确认安全组现状；若需开端口走用户授权）。
- P5：vastbase A 的 `start.sh` 停起语义与 `docker stop/start` 的关系（registry 启动覆盖命令以实测为准）。
- P6：`dialectExternalVerify` 首连失败是否无内建重试（`DialectExternalMatrixVerificationTest` 连接建立处核对）——若确实无重试，健康等待是唯一防线，预算必须留足。

## 八、风险

- **停机后引擎起不来**（OB 冷启慢、某引擎数据卷异常）：每实例启动预算 + 健康探针 + V7 演练兜底；真坏了走 §9 从零重放，这正是 skill 已固化的能力。
- **reaper 误停**：判定只看「有无 established 连接」，JDBC 连接池空挂会拖延回收（可接受，方向是安全侧——宁可晚停）。
- **密钥泄露面**：受限账户 + 强制命令白名单 + CI key 无 stop；密钥轮换口径写进 M6 文档。
- **swap=0 主机 OOM**：本方案本身就是解药——平时只活 2~3 个容器；全矩阵跑时内存闸门强制先腾后起，延续 skill §2.5 口径。
- **整机重建流程漂移**：bootstrap-db-env.sh 与铁律 3 必须 M2 同批改，否则下次重建回到全自起，本方案失效。
