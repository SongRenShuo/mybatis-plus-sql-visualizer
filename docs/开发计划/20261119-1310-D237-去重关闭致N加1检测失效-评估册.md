# D237 去重开关与 N+1 检测的隐藏耦合（立项评估册）

- **立项**：2026-11-19 13:10，用户在真机验收 B2 时发现：**SQL 去重未勾选时，N+1 红徽标完全不出现**。用户要求「立项评估（先测成本再定）」。
- **性质**：评估册，**不动生产代码**；是否实施等用户拍板。
- **编号**：新占 **D237**（D233~D236 已由本日路线图册持有）。

## 一、问题与证据

### 1.1 现象

`SQL 日志` 工具栏的「SQL 去重」未勾选时：
- 红色「疑似 N+1」徽标**永不出现**（D216）；
- 由徽标进入的聚合过滤态（D235）**无从触发**——两个功能一起静默失效；
- 用户侧**没有任何提示**说明这是开关依赖，只能靠翻代码发现。

### 1.2 代码根因（`SqlLogEntryBuffer.kt`）

窗口嫌疑戳只在「去重开启 + 条目可去重」分支登记：

```kotlin
if (dedupeEnabled && canDedupe(added)) {
    dedupeIndex[added.dedupeKey] = added
    dedupeKeyPresence[added.dedupeKey] = ...
    markCountKeyLocked(added.dedupeKey)
    markWindowStampLocked(added)        // ← 唯一登记点
} else {
    countFullRebuildPending.set(true)   // ← 不登记
}
```

`windowSuspectKeys()` 读的是 `windowStamps`（第 904~928 行），空则直接 `return emptySet()`，于是 `NplusOneSuspect.isSuspect()` 恒 false。

### 1.3 为什么会这么写

`markWindowStampLocked` 需要 `structureKey`（结构指纹，参数化+哈希），而 `structureKey` 又经 `dedupeKey`（内容指纹）做缓存键。T-PerfSweep9 专门优化过「去重关闭时不触 `dedupeKey` lazy」——把窗口戳放在去重分支里，等于顺手省掉了这两次指纹计算。

### 1.4 严重度判断

- 去重开关的**默认是开启**（`SqlLogEntryBuffer.dedupeEnabled = true`，UI 复选框初始态直读该字段），所以新用户默认能用 N+1；
- 但「关掉去重」是完全合理的用法（不想把重复行折叠成一行 + ×N 徽章），一旦关掉，诊断能力**无提示地消失**；
- 定位：**P2（中）**——不影响主体功能，但一个已发布能力被无关开关静默关掉，属可预期会被追问的坑。

## 二、成本实测（本册核心：先测再定）

临时基准（`TmpFingerprintCostTest`，已跑完删除，读数如下）：

| 项 | 规模 | 总耗时 | 单条均值 |
|---|---|---|---|
| `structureFingerprint`（结构键：空白归一 + 字面量参数化 + 哈希） | 10,000 条 × 101 字符 | **38 ms** | **3.8 µs** |
| `sqlFingerprint(normalizeSqlWhitespace(...))`（内容键，对照） | 10,000 条 × 101 字符 | 18 ms | 1.8 µs |

**结论：所谓「省成本」在实测量级下不成立。** 典型开发场景每秒几条到几十条 SQL，单条 3.8µs 约等于零；即使每秒 1000 条也只有 3.8ms/秒。而且 `structureKey` 在条目上就是 `by lazy`，同一条目只算一次，后续判定零成本。

## 三、方案对比

| 方案 | 做法 | 成本 | 风险 | 评价 |
|---|---|---|---|---|
| **A（推荐）把窗口戳移出条件分支** | `markWindowStampLocked(added)` 无条件调用（放在原 `if` 之外）；`dedupeEnabled` 只管索引/计数 | +3.8µs/条（实测） | `structureKeyByDedupe` map 会开始累积（见 §四）；`canDedupe` 的 ShardingSphere 排除是否需要保留待定（见 §五） | 改动 3 行，语义最直白：N+1 是诊断，与去重展示偏好无关 |
| B 用轻量哈希替代结构键 | 为窗口判定单独算一个便宜指纹 | 更低 | **改变判定语义**——参数化（字面量 → `?`）正是「同模板」的定义，换成原始文本哈希会让 `id=1`/`id=2` 判成不同模板，N+1 恒不命中 | 不可行 |
| C 加提示不加能力 | 去重关闭时在徽标区给一句「N+1 检测需要开启去重」 | 0 | 仍要求用户改开关才能用诊断；且「为什么诊断依赖去重」无法自圆 | 只作 A 的兜底（若 A 遇阻） |
| D 独立轻量窗口计数 | 不复用 structureKey，按「参数化后的 SQL 前缀 + 长度」粗判 | 低 | 与 D216 既有阈值语义分叉，两套口径（违反 D235 的「口径一致性生命线」） | 不推荐 |

## 四、方案 A 的前置风险（实施前必须核）

1. **`structureKeyByDedupe` 的有界性**：该 map 目前只在 `clear()` 时清空（`SqlLogEntryBuffer.kt:941`），**没有随条目淘汰清理**——去重开启时它本来就在累积，A 只是让去重关闭时也开始累积。实施时要顺带评估：是否按 `entries` 淘汰同步删键（属既有小泄漏，可在同一批修）。
2. **`windowStamps` 的修剪**：读时按 `nowMs - windowMs` 修剪（已有），与去重开关无关，A 不改变这段。
3. **去重关闭时的「不可去重条目」**（`canDedupe == false`，ShardingSphere 来源）：窗口戳该不该登记？建议**登记**（N+1 判定与去重能力无关），但要在计划里明确写死，并补一条 ShardingSphere 来源的 N+1 用例。
