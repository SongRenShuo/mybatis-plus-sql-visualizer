## 一、问题重定义：T7 地板 613s 与发行日实测 31~55min 的裂缝

T7 的 613s 地板是**理想窗读数**（夜间单车道、暖 home、6522 例基线）。但发行日实测连续三轮远超地板：

| 轮次 | 整链 | 关键读数 |
|---|---|---|
| v2026.10.9（10-08） | **31m9s** | 变更记录原文：verifyMarketplace 单步**下载 3.33GB 平台插件耗 30m** 是墙钟大头 |
| v2026.10.13 重发（10-13） | **54m11s** | `--no-configuration-cache` 形态 |
| v2026.10.16 定稿（10-15） | **55m8s** | 临时 detached 发行工作树内跑门禁 |

本日静态取证（主树）：

- `build/verify-home-marketplace/loaded-plugins/`：**131 个 zip 共 3.4GB**，mtime 全部=2026-10-14（最后一次发行轮把整组重下了一遍）——缓存键是 `pluginId_buildNumber.zip`，marketplace 上依赖插件的 compatible 最新 build 变了就整键失效重下；
- `build/verify-home/loaded-plugins/`：0 个——离线门禁零下载， Offline/Online 两道门禁的下载税**只压在 marketplace 一道**；
- verifier home 都在 `build/` 下——**换工作树（发行常规操作）= 全量冷下载**，这正是 55min 轮的形态。

结构判断（T7 S5 分解 + 本节证据）：五环节中 verifyGate(202s)/分片窗(~200s)/testExternal/e2e 全部藏在 marketplace 窗口内，整链 ≈ 头部编译链(~60s) + verifyMarketplace。marketplace = 高 CPU 解析段 ~285s（进程内三目标并发，T6 L1 销案证据链在案）+ **在线等待段 ~300s（暖窗快链路）~30m（慢链路）**。等待段吞吐率随代理状态漂移 6~30 倍——**整链剩余可压缩空间几乎全部集中在这一段**。

全量测试（日常 `testShards` 独跑）侧如实登记：T9 已钉「构建侧地板 ≈2.5min、97% 在分片窗口」，T7~T9 三次否决 6 片、T5/T9 双销 JVM 旋钮、T15 销测试源码收割——日常全量无新杠杆，本轮不动它，releaseGate 内的分片窗本就藏在 marketplace 窗口里。

## 二、目标与非目标

**目标**：把在线等待段的可压缩量做成实测定案并落转正改动；即使全销案，产出同样成立（把「发行日 55min 不可压缩」的证据等级从变更记录孤证升格为进程级取证）。

**非目标（红线，继承 T6/T7 全部）**：

- 五环节零删减、三目标 × 2 道兼容门禁口径不变；
- **在线 freshness 语义不动**：marketplace 判定的本体是「在线解析可选依赖 + 无豁免 + 按 verdict 文本判失败」，verdict 按 commit 缓存 / marketplace 离线化仍属语义阉割，否决勿再提；本轮动的只是**传输层**（走不走代理）与**缓存目录位置**，不触判定语义；
- 不动测试执行语义与分片算术；testHeapSize/GC/线程面旋钮已实测销账不再复跑；
- 不复活 T6/T7 已销案项：verifier 拆目标进程（进程内已并发）、mustRunAfter 收紧式错峰、e2e 重叠、分片 6 片、marketplace verdict 按 commit 缓存；
- **例外复审一项**：T6 L5「verify-home 迁出 build/」的销案理由是「发行日历史全暖窗、预期收益≈0」——该理由被上方三条发行日读数直接证伪（detached 工作树=冷 home=30m 下载税），本轮按新证据复审，是否转正由探针读数定；
- dev 未经允许不合 master（用户明令），本分支不合 dev（合流待批）。

**验收判据（parity 三断言，对齐 T6/T7 口径）**：终轮 releaseGate 全绿读数中，①testShards 计数 ≥ 当前 dev 基线、failures=0、skip=9（docker 离线口径）+ testExternal 40 例 + agent ≥164 例 0 失败；②verifyGate + verifyMarketplace 六判定全 Compatible，问题计数与基线读数逐字一致（0 未登记块）；③e2eFakeIde PASS=26 FAIL=0。

## 四、待验证前提（实施者先证伪再动手）

- **前提 A（N1→N2/N3 的生死线）**：warm marketplace 轮结束后 `loaded-plugins` 有新文件（mtime 推进/新 build 号）或网络字节流量 ≥1GB——「每轮付下载税」实锤。若一轮后文件零变化且流量近零，等待段=元数据往返，N2 改测元数据请求路径、N3 只剩 idb 冷建收益（缩水重估）。
- **前提 B（N2 的生死线）**：直连 marketplace 下载域名在本机可达且吞吐 ≥ 代理路径——用 curl 对同一批大文件 URL 做代理/直连对照取样（各 3 次），直连不稳或反慢即 N2 销案，不进 A/B。
- **前提 C（N3 的生死线）**：连续两轮 marketplace 之间 `loaded-plugins` 的 build 号集合差异显著 <100%（有跨轮复用空间）；若 100% 更换则下载税不可免，N3 只剩 idb/extracted 冷建收益，按缩水后的量级重新裁决是否值得引入共享目录的并发面。
- **前提 D（实验窗资源）**：单车道（parallel_tasks 登记表无冲突 + Commit 底噪 <60GB 才开计时轮）；并窗轮一律弃样。本仓已有活跃任务时，gradle 动作只在工作树跑、不碰主树 build。
- **前提 E（home 位置中性）**：verifier 行为不因 home 目录位置改变——verdict 文本与问题计数逐字 parity 兜底；发现路径假设破裂即回退。
- **前提 F（环境前置在位）**：e2e 硬依赖本机 MySQL 3306 + demo 工程 + docker 离线（skip 9 口径）；轮前复验。
- **前提 G（配置缓存约束）**：新增 gradle 属性读取与 doFirst/doLast 写法照抄 T7 教训——脚本顶层 val 经任务 lambda 引用不可序列化，必须 register 块内局部值。
- **前提 H（L5 复审合法性）**：T6 L5 销案理由「发行日历史全暖窗」与 10-08/10-13/10-15 三读数矛盾——复审以三条发行日读数 + 本日 131 zip 同日 mtime 取证为据，写入台账。

- `mpv-verification.gradle.kts`：`resolveVerifierHome(role)` 三态——缺省 `GRADLE_USER_HOME/mpv-verifier-home/{gate,marketplace}`（机器级持久）；`-PverifierHomeRoot=build` 一词回落既有每工作树形态；给绝对路径则用该根。gate 与 marketplace 保持分家（离线/在线语义不互染，同链并发无共享写点）。verifyPlugin（报告生成器，不在发版链）维持 build/verify-home 不动。
