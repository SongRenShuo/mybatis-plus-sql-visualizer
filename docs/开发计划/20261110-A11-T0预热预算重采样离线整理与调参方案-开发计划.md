### 2.5 `-Dmpvs.*` 与预热预算相关的口径

全仓 `-Dmpvs.*` 属性去重清单（只读 grep 结果）：`-Dmpvs.contract.ide`、`-Dmpvs.dialect.*`（`jdbcUrl` / `name` / `user` / `password` / `multiRowValues`）、`-Dmpvs.dm.url`、`-Dmpvs.docker.enabled`、`-Dmpvs.dump.dir`、`-Dmpvs.external.*`（`instanceTimeout` / `matrix` / `maxConcurrency` / `wordWorkers`）、`-Dmpvs.update.*`（`devMode` / `manifest.url` / `previewManifestUrl`）。

- **结论：不存在 `mpvs.prewarm.*` / 预热预算 / 采样开关类的系统属性**。`PREWARM_WAIT_MS` 是编译期 `const val`（`SqlPreviewPanel.kt:1520`），运行期无覆盖通道。
- 相关但**不在本链**的两处口径：`-Dmpvs.external.instanceTimeout`（实例级预算，优先级「矩阵条目 → 系统属性 → 默认 300s」，见 `docs/开发计划/20261106-1757-T-MatrixInstanceTimeout...:72`、`:236-238`）与 `mpvs.docker.tests.enabled`（Docker 腿显式开关，`-PmpvDockerTests=true` 才启用）。**两者都是 CI/测试腿预算，不要与 `PREWARM_WAIT_MS` 混为一谈**。
- 教训登记：`docs/开发计划/20261106-1757...:236-238` 实证过「`-Dmpvs.*` 透传只挂 `tasks.test`，`dialectExternalVerify` 没接线＝假文档」。**若日后要给 01d 加运行期覆盖通道，必须先证系统属性真的透传进目标 JVM，不能只在计划册写一行**。

### 3.2 哪些证据足以支持改，哪些不足以

**足以支持「改常量」**：

- 上述 1~5 全部满足，且新分布 **P95 明显落在当前 500ms 之外**（例如 P95 > 500ms 且降级率不可接受），同时**抬预算的观感代价**由同批占位/空窗读数证明可接受（采样报告 §六 `:142-170` 已给代价模型：冷启主要项是 EDT 排队、抬预算代价接近零；复开会多出「预热耗时 − 旧预算」的几十到百余毫秒）。
- 或者反过来：新分布 **P95 远低于 500ms**（如 ≤300ms）且尾部不再出现 820/1347/3016ms 类，则足以支持**下调**预算以缩短复开等待期（采样报告 §六 `:160-161` 的代价是可感拉长）。

**足以支持「改自适应窗口」**：

- 分布呈**明显双峰/长尾**（中低负载集中在 100~400ms、首次索引/重负载跳到 1~3s），单一常量无论取哪档都必然在一端失配；且能给出**可判定的前置信号**（如 `DumbService.isDumb`、`UnindexedFilesScanner` 在跑、CPU/索引负载）在**预热起算时**即可取得，不需要等预热完成。
- 并能证明「自适应」不破坏 `PrewarmAwait` 的一次性语义（`:87-101`）、迟到换装恢复出口、`DEGRADED_GRACE_MS` 宽限期，且新窗口有明确上下界与回落默认值。

**不足以支持任何改动**（当前仓内证据全部落在这一档）：

- **3016ms / 1347ms / 820ms**：三次都是单次样例，且都绑定特定重负载/首次索引场景；计划册 `:68`、`:138` 明令禁止据此拍常量。
- **#1 / #2 两组 n=3 冷启分布**：采样报告 §5.3 `:133-135` 自述「最大值 360ms 带偶然性、中位与最大差 50%、尾部未采到，建议再补 3~5 次」；预算抬高后复验（走查记录 §8）也只是 3 个冷启样本。
- **#6 间接夹逼区间与「≥1.0~1.5s」派生结论**：`:123-125` 自述「三样本、负载上界下的估计，不是分布」；且它测的是**旧 60ms 期、无完成打点**的形态，与现行打点口径不可混算。
- **1619ms / 1.7–2.0s / 3116ms 等全链墙钟**：量纲是 `request→console-visible`/`request→dialog`，不是 `prewarm done` 自身耗时；`性能报告:14` 与采样报告 `:150` 都指出其主体是锁等待/EDT 排队，**不能拿来定预热预算**。
- **代码注释里的 3016ms（#17）**：是引用历史读数，不是新实测；性能报告 `:62` 的「双证」措辞只表示两处注释一致，不构成第三个样本。
- **T-ConsoleBind263 的 40 例测试读数（#29）**、widget tick 4.61µs（#25）、9015 用例全量门禁（计划册 `:148`）：分别是绑定面、周期资产、回归门禁，与预热耗时分布零交集。
- 任何「仓内 0 处违规 / 定向测试全绿」类**空绿**：守卫没写命中不等于真实形态被覆盖（全局 AGENTS.md 口径）。

10. **分布**：对「同索引态、同负载档」的 `prewarmMs` 排序，出 **n / min / P50 / P95 / max**；P50/P95 用明确算法（如最近秩或线性插值）并**写明算法**；n < 10 只写「样本不足，未出分布」。
11. **分层**：冷启首开 / 同会话复开 / 首次索引期首开三张表分开；`prewarmMs` 与 `request→console-visible` 两张表分开；60ms 期与 500ms 期历史读数（§二）只作对照列，不并入。
12. **01d 开窗判定**：按 §3.1 五条逐条打勾；任一不满足 ⇒ 维持 A 档（500ms），并把「未取」项与原因回填计划册 §六实施记录。

14. **证据分级**：以 `idea.log` 原始行、逐次 `samples.jsonl`、截图为准；文档自述与派生推算只作旁证。合成样本只能证「规则看得见我造的形态」，证不了真实形态。

### 4.5 失败时该给哪几行日志（交给执行者贴回）

按失败类型给出**最小必要日志集**（均为生产代码现有打点，非臆造）：

- **预热超预算降级**：`[M36] prewarm done in Xms (file=…, psi=…)` ＋ `[M36] in-memory PSI preview document created (len=…)` ＋ `[M36] showSql branch=createEditor: len=…` ＋（若有）`[M36] late prewarm product consumed: editor upgraded to …`。要把三行**时刻**一并贴，用于分离「预热耗时」与「EDT 排队」。
- **预热硬失败**：`[M36] prewarm FAILED in Xms: <原因>` 四选一（project preview file unavailable / VFS refresh null / PsiManager.findFile null / 其它），＋ 该次 `[T-PreviewFast] request→dialog` 与 `request→console-visible`。
- **全链墙钟异常**：`[T-PreviewFast] request→dialog: Nms` ＋ `[T-PreviewFast] request→console-visible: Nms` 两行成对贴；若出现 10151ms 类量级，附 `ConsoleVisibleLogGateTest` 相关结论并判该次口径失真。
- **Slow operations / DumbMode**：`grep -c "Slow operations are prohibited on EDT"` 的**命令与读数**，以及命中时 `Plugin to blame: SQL Visualizer` 的完整栈；索引组附 `UnindexedFilesScanner - Started scanning for indexing of …（N 个文件 / M 线程）` 行与 `IndexNotReadyException` 相关行。
- **轮次/换装异常**：`[M36] prewarm product dropped: stale round=… (current=…)`、`[M36] late prewarm product kept: document edited since last render (len=…)`。
- **口径自检**：同一次打开的 `idea.log` 原始片段（勿只贴整理后的表格），并注明 `idea.log` 是否已按 `AppStarter - JRE:` 切分会话。
