## 二、本轮遇到的问题（记录）

### O1（待定性，可能是缺陷）两条未触发的同 SQL 条目

面板出现 **#2 `[22:42:59] 2ms`** 与 **#3 `[22:45:43] 3ms`**，SQL 与 `#1`（`/user/list`，`22:40:57`）逐字相同，但**我只发过一次 `/user/list`**。

- `#3` 的时刻 `22:45:43` **紧贴 JVM 恢复时刻**（22:45:43 恢复、22:45:44 重建会话）。
- `#2` 的 `22:42:59` 无任何我方动作对应。

**当前假设（未证实）**：`#3` 来自「增强通道掉线窗口内控制台桥恢复解析」——掉线后 `SqlCaptureGate.paused` 开闸（`SqlLogConsoleBridge.kt:774`），桥重新扫到控制台里**早已打印过的**同一条 SQL 行，于是产出一条时间戳为**解析时刻**而非执行时刻的条目。该假设能解释 `#3`（落在开闸窗口 22:43:43–22:45:44 内），**解释不了 `#2`**（当时闸门关闭）。`#2` 也可能来自 agent 事件（应用真的又执行了一次该 SQL，但我没找到触发源）。

### O2（待定性，可能是缺陷）第三次请求未产生面板条目

第三次打 `/user/list`（约 22:52:04，HTTP 200）后面板**没有新增条目**（列表止于 `#5 [22:47:19]`，已放大确认下方为空）。而日志在 **22:52:04,483** 有 `[M37.3] 首条 SQL 自动展开日志工具窗`。

**当前假设（未证实）**：面板「移除重复的 SQL」勾选框处于**勾选**状态，同 SQL 的第三次执行被去重掉了；但 `#2`/`#3` 同样是重复 SQL 却留在列表里，去重语义不一致——与 O1 同源，都指向**「同一条 SQL 多次执行时的条目去重与来源合并语义」**。

### O3（工具链问题，非产品缺陷）验收工具链三处卡点

1. **`kill -STOP` 在 Git Bash 对原生 Windows PID 不可用**（报 `No such process`）；须改用 ntdll `NtSuspendProcess`/`NtResumeProcess`（本轮已写成 `%TEMP%/proc.ps1` 可用）。`docs/规范/测试沙盒验证清单.md` 里「`kill -STOP` 应用进程」这条**照原样跑不通**，需更新配方。
2. **CUA 对沙盒 IDE 的窗口截图时好时坏**（`Screenshot unavailable … hidden or unrendered window`），且坐标点击要求 frame 有效、frame 易过期；本轮实际路线是 **PowerShell 全屏 `CopyFromScreen` 取图 + CUA 键盘**（键盘需先用一次点击把 IDE 置前，否则 `frontmost_pid_mismatch`）。
3. **沙盒 IDE 的 a11y 树只有 7 个窗口级元素**（与既有记录一致），工具窗口菜单项只能靠键盘 `Down×N + Return` 导航（本轮 `SQL Visualizer` 是 Tool Windows 子菜单第 13 项）。

## 三、下一步：先做定性实验，再决定是否改码

**为什么不在本轮直接改**：O1/O2 目前只有观察与假设，没有能区分「产品缺陷」与「预期行为」的实验。按仓内纪律（计划前提先证伪再动手），先补三个实验：

| 实验 | 做法 | 判定 |
|---|---|---|
| E1 同 SQL 多次执行 → 条目数 | **取消勾选**「移除重复的 SQL」，连打同一接口 3 次，数面板新增条目 | 3 次全进 = 去重是 O2 的原因（预期行为，只需文档说明）；少于 3 = 真丢条目 |

| E3 `#2` 的触发源 | 冻结前先清空列表并记录应用控制台输出行数，静置 3 分钟不碰任何东西，看是否自发多出条目 | 自发多出 = 有第三方在跑该 SQL（应用侧定时/IDE 侧探测）；不自发 = `#2` 与 E2 同源 |

**若 E2 成立，修法方向**（待定性后再定稿）：桥在开闸瞬间不应把「闸门关闭期间控制台已存在的历史行」当作新行产出条目——闸门开合时应重置桥的「已见行」游标（`consoleLinesSeen` 一类），只解析开闸之后新增的行。

### 本轮新发现（工具链，已实测）

**O4：强停 `runIde` 会留下孤儿进程，导致下一次启动直接 `BUILD FAILED`。**
- 现象：`TaskStop` 掉 gradle 任务后，沙盒 IDE 的 JBR `java.exe`（pid 30020）与 `fsnotifier.exe` 仍在跑；再次 `runIde` 报

**O5：冻结 JVM 的副作用**：应用恢复后 HikariCP 打 `HikariPool-1 - Thread starvation or clock leap detected (housekeeper delta=1m28s…)`——这是冻结造成的时钟跳跃，**属预期副作用，非插件缺陷**（真机验收时看到它不必当问题）。

### O4 的根因修正（第二轮只定位到一半）

第二轮记的是「强停 runIde 留下 IDE 与 fsnotifier 孤儿」。第三轮复现启动失败时**两个孤儿都已清掉却仍失败**，深挖后拿到确切持有者：

- 报错仍是 `Unable to delete directory '…\transforms\cfd9113040487d86d63d9022472046cb'`，手动删除时报 **`对路径"libasyncProfiler.dll"的访问被拒绝`**——Windows 会锁住已加载的 DLL。
- 用「遍历所有进程的模块名找 `libasyncProfiler.dll`」定位到持有者：**沙盒 IDE 启动的 demo 应用 JVM**（pid 61592）——它加载了 IDE transform 目录里的 async-profiler DLL，从而锁住整个 transform 目录。
- 所以清理清单必须是**三样**：IDE 的 JBR `java.exe` + `fsnotifier.exe` + **IDE 启动的应用 JVM**。只清前两个仍会 BUILD FAILED。
- 定位配方（可复用）：枚举各进程模块找目标 DLL 名 → 拿到 pid → `Stop-Process -Force` → 手动 `Remove-Item -Recurse -Force` 验证是否解锁（成功即解锁）。

**优雅退出的正确交互链**（第二轮失败的真正原因）：关窗后是**两个**确认框，不是一步——① `Confirm Exit`（Are you sure you want to exit?）→ ② **`Process 'X' Is Running`（Do you want to terminate the process?）**，必须点 **Terminate** 才会继续退出；第二轮只点了第①步的 Exit，IDE 就停在第②步等输入，所以「没在预期时间内退出」。若先手动杀掉应用进程，再关窗则只需第①步。

### O1 闭环：消除论证，定性为非缺陷

| 候选解释 | 状态 | 依据 |
|---|---|---|
| 控制台桥在「增强掉线、闸门开」窗口复读历史行 | **已证伪** | E2：冻结 40s → 摘除 → 恢复 → 重建会话，恢复后**无任何新条目**，条目数与冻结前一致 |
| 第三方组件周期性/自发执行同一 SQL | **已证伪** | E3：静置 3 分钟，插件日志 0 行 + 面板仍 0 条 |
| 我方动作引发的**真实执行** | **剩余解释** | `#3`(22:45:43) 紧贴我 `resume` 的 22:45:43；`#2`(22:42:59) 落在我写 `proc.ps1`/探测端口的时段。冻结会把**在途请求**阻塞住，恢复后集中执行——两条条目的耗时是真实值（2ms / 3ms）而非 0，支持「真执行」而非「解析产物」 |

**为什么无论哪种解释都不构成插件缺陷**：
- 若 SQL **真的执行了**，插件如实记录——这正是捕获通道应有的行为（耗时、源码位置、参数都对得上）；
- 若 SQL **没执行**，E3 已证明插件不会凭空产出条目（静置 3 分钟零产出）；
- 两条候选机制（复读、自发）都已被独立实验排除，**没有第三条通向「错误条目」的路径**。

**残留不确定性（如实登记）**：`#2`/`#3` 的确切触发源（哪个在途请求、由谁发起）**未定位**。但它落在「应用侧行为」范畴，且已排除插件的捕获/去重缺陷；继续追需要抓应用侧的网络/请求栈，不在本插件范围内。

**因此 O1 不需要改码**。O2 同理（E1 已用代码定论：去重是「丢弃 + `×N` 徽标」的预期语义）。
