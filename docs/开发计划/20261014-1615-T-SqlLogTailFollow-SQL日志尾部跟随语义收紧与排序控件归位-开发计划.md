## 一、需求结论

用户提出两个调整点，性质不同，需分别定案：

### 1.1 点一：尾部跟随（滚底）语义收紧

用户口径拆成三条：

1. 默认继续自动跟随（新条目到达自动贴底）——**保留**；
2. 用户一旦手动滚动，就**不得**再自动往下滚；
3. 浏览同一批条目期间，只有「滚动到底部」按钮能恢复；**用户后续明确确认：清空列表也可以恢复跟随**，因为它开启一轮新的日志浏览。

关键点在于第 2、3 条比现状更严：现状是「滚离底部超过 48px 才停跟随，且滚回底部附近会自动恢复跟随」。用户要的是「任何手动滚动即停」+「旧条目不因滚回底部自动恢复」，清空是明确许可的例外。

### 1.2 点二：排序控件归位

把当前显示「时间升序」的排序方式按钮从工具栏**右侧控制组**移到**左侧按钮集的最右端**（用户 2026-10-14 追加校正：不是整行最左，而是图标组右侧）。

### 1.3 共同约束

两个点都落在 `SqlLogPanel.kt` 的工具栏与列表区，与 O-146 的 W4（紧凑布局）和 §5.6（工具栏整理）有交集。为避免同文件两处改动互相打架，实施顺序固定为：O-146 先落工具栏分组与列表布局，本计划再落跟随语义与排序归位；若 O-146 尚未实施，本计划可先行，但两者不得并行由不同执行者同时改该文件。

## 二、现状与实证

### 2.1 尾部跟随机制已经存在（T-SqlLogPerf，20261006）

不是「从未做过」，而是「语义比用户预期松」。现有实现：

- 跟随开关：`autoFollowTail`，默认 `true` —— `SqlLogPanel.kt:240`
- 跟随判定松量：`tailFollowSlackPx = 48` —— `SqlLogPanel.kt:243`
- 归因基线：`lastScrollMax` / `lastScrollValue` —— `SqlLogPanel.kt:246-247`

- 动作实现：`ScrollToEndAction`（图标 `AllIcons.General.ArrowDown`，文案键 `log.panel.scrollBottom`）—— `SqlLogPanel.kt:950-960`
- 滚动归因监听 —— `SqlLogPanel.kt:1236-1248`

动作文案键已双语在位：`log.panel.scrollBottom` / `log.panel.scrollBottom.tip`（`MpSqlVisualizerBundle.properties:662-663`，`_zh.properties:642-643`）。

### 2.2 与用户预期的三处差距

**(a) 48px 松量导致小幅上滚不暂停（最可能的真根因）。** 判定式是「视口底沿距列表底沿 ≤ 48px 即视为在底部」（`SqlLogPanel.kt:243`、`:1247`）。48px 约等于一行半：用户用滚轮向上滚一两行时仍落在松量内，`autoFollowTail` 保持 `true`，下一条 SQL 到达就把视口拉回底部——在持续灌入的场景下，观感正是「手动滚了还是被一直往下拽」。

**(b) 滚回底部会自动恢复跟随。** 同一判定式对称使用：距离回到 48px 内即 `autoFollowTail = true`。用户要求浏览当前列表时不能靠滚回底部自动恢复（清空列表另起一轮是用户允许的例外），此自动恢复与之直接冲突。

**(c) 归因依赖启发式，脆弱。** 现用「`maximum` 增长且 `value` 未动」判为程序性追加、提前返回（`SqlLogPanel.kt:1241-1246`）。该启发式把「用户滚动」与「程序追加」的区分建立在滚动条模型的更新时序上：一旦 `maximum` 增长与 `value` 变化落在同一次调整事件里（例如增量追加后紧接贴底、或全量重建期间的 clamp），就会被判成用户滚动或反之，两种误判都会让跟随态与实际意图不一致。

### 2.3 排序控件现状

`sortButton` 是 `JButton`（原生 LaF 扁平按钮 + 右侧下箭头，文案显示当前排序方式）—— `SqlLogPanel.kt:221-226`；弹单选菜单 `showSortPopup()`、文案刷新 `updateSortButtonText()` —— `SqlLogPanel.kt:1453`、`:1474-1490`。

它当前被加入**右侧控制组**：`controls` 含 `slowQueryLabel`、`typeFilterButton`、`sortButton`、`dedupeCheckBox`，挂 `BorderLayout.EAST` —— `SqlLogPanel.kt:659-674`。左侧是 `ActionToolbar` 的动作图标组，挂 `BorderLayout.CENTER` —— `SqlLogPanel.kt:632-647`。

排序方式文案键：`log.sort.label`、`log.sort.time.asc` 等 —— `MySqlVisualizerBundle.properties:866-871`、`_zh.properties:893-895`；测试断言默认文案为「时间升序」—— `SqlLogPanelSortAndSlowQueryTest.kt:116-117`。

### 2.4 测试现状与缺口

- **跟随语义零覆盖**：全仓测试未触及 `autoFollowTail` / `tailFollowSlackPx` / `ScrollToEndAction` 的滚动行为，只有帮助/布局测试读取 `toolbarGroup` 子项（`HelpDialogTest.kt:25`、`HelpUiTest.kt:41,61`）与动作数 ≥5（`SqlLogPanelLayoutTest.kt:54-61`）。这正是「语义偏差长期存在却全绿」的原因。

- `sortButtonForTest` / `sortButtonTextForTest` 测试缝已存在（`SqlLogPanel.kt:338`、`:344`），归位后仍可复用。

## 三、方案

### 3.1 显式两态跟随状态机

把「跟随」从「每次按距离现算的布尔」改为**显式用户意图状态**：

```text
TailFollowMode: FOLLOWING | PAUSED
```

- 初值 `FOLLOWING`（保留用户要求的默认自动跟随）；
- 状态由三个明确来源改变：**用户滚动**（→ `PAUSED`）、**「滚动到底部」动作**或**清空列表**（→ `FOLLOWING`）；
- 追加/刷新等程序行为**永不改变**状态，只按当前状态决定是否贴底。

### 3.2 暂停判据：任何用户滚动离开底部即暂停

- 删除 48px 松量，不用像素距离推断用户意图；
- 接收到滚轮、滚动条鼠标操作或键盘导航输入即进入 `PAUSED`；
- 不再存在「滚回底部附近自动恢复」这一路径。

### 3.3 恢复入口

- 浏览现有条目时，`scrollToEndAction`（「滚动到底部」）把状态置回 `FOLLOWING`，同时跳到底部；
- 清空列表视作新一轮日志浏览，也恢复 `FOLLOWING`（用户追加确认）；
- 仅靠滚回底部不恢复，删除现有对称判定。

### 3.4 直接监听用户输入，不再靠 AdjustmentEvent 猜归因

最终实现比额外维护「程序性滚动中」布尔守卫更简单：只对滚轮、滚动条鼠标操作与列表/滚动条的导航键事件调用 `onUserScroll()`。`JScrollBar` 的 `maximum/value` 变化、`ensureIndexIsVisible`、批量追加与窗口布局变化均不会产生这些用户输入事件，因此程序性滚动天然不会修改跟随状态；不需要跨 EDT 脉冲维持可误伤用户输入的守卫标志。

贴底保留 `ensureIndexIsVisible(last)`，再把 `verticalScrollBar.value` 设为 `maximum`。V181-2 的真机贴底时序仍待复验。

### 3.5 状态可发现性

- 动作 tooltip 需区分两态语义（跟随中 / 已暂停，点击恢复跟随），文案键在现有 `log.panel.scrollBottom.tip` 基础上扩展双语；
- 「暂停态」是否需要额外可见提示（图标态变化或「N 条新记录」徽章）列为 V181-5：**用户未明确要求前不新增控件**，因为右侧控制组有宽度预算锁，新控件会牵动 §2.4 的预算与单行契约。

### 3.6 排序控件归位（点二）

最终落点（2026-10-14 用户三轮校正后定稿）：排序**并入左侧动作组**——作为 `toolbarGroup` 里最后一个直接动作（捕捉 / 清空 / 设置 / 屏蔽管理 / 搜索 / 帮助 / 滚动到底部 / **排序**），**不设自建「更多」弹层**（用户第四轮令：不要这个更多，之前侧边栏不够宽时自动折叠、鼠标放上去能看全部，那个交互更好）。排序实现为 `sortModeAction : AnAction`，图标用平台排序字形 `AllIcons.RunConfigurations.SortbyDuration`（竖杠+下箭头+三条递减横杠，一眼可辨为排序）；窄宽时与其余动作一起折进平台 ActionToolbar 自带的溢出 `»`。当前排序方式进动作 tooltip（`排序：<方式>`）与菜单选中态。右侧控制组仍只留慢查询徽章 / SQL类型 / 去重勾选。

> 形态演进留痕：①排序移入左簇、挂行宿主 `WEST`——用户指出「是否与 SQL类型重叠」，核实为两侧各取理想宽在窄宽度必然压盖；②改挂 `CENTER`（图标组吸收挤压、排序钉在簇右缘）——用户指出「排序没被左侧按钮集归入、过窄应当自动折叠」，确认 `JButton` 不参与 ActionToolbar 溢出；③改为组内动作并自建「更多」弹层收纳设置/屏蔽/帮助——用户指出「不要这个更多、原来的自动折叠+悬停看全部更好」；④定稿：全部动作直达、排序为组内末项并换用排序图标，折叠完全交平台。代价：工具窗工具栏只渲染图标，当前排序方式不再常显为文字。

理由：

1. 保留 `JButton` 形态与「显示当前排序方式」的文案能力（...）；
2. 复用既有 `updateSortButtonText()`、`showSortPopup()`、tooltip 与测试缝，改动面最小；
3. 排序属于「展示方式」而非「过滤条件」，与图标组同簇、紧邻控制组左侧，符合用户指定的阅读顺序。

备选（不推荐，仅在用户要求排序控件夹在图标之间时采用）：把排序包装为 `AnAction` 并入 `toolbarGroup`。代价是窄宽度下文案不可见，且需与图标组溢出行为一起真机确认。

同时：`typeFilterButton`、`slowQueryLabel`、`dedupeCheckBox` 保持在右侧控制组不动（用户只点名排序）。

### 3.7 布局预算重算

排序控件从控制组移出后：

- `SqlLogPanelLayoutTest.kt:228` 的「控制组应含排序按钮」改为「控制组**不应**含排序按钮」；
- **新增**左侧位置断言（排序控件在左簇容器内、且位于动作图标组右侧，仍不在右侧控制组）；
- 控制组最坏宽预算锁（`:188-205`）保留其「防再往控制组加控件」的职责，但常量需按实测重算；
- **新增组合宽度守卫**：侧栏 460px 下「左簇（排序 + 图标组）+ 控制组」必须放得下且仍单行——只调旧常量会留下「左簇膨胀挤掉图标」的盲区。

## 五、验收矩阵

### 5.1 跟随语义

1. 默认 `FOLLOWING`：连续追加条目，视口始终贴底。
2. 用户上滚任意量（含仅一行）→ 立即 `PAUSED`；此后追加条目**不移动视口**。
3. 用户拖动滚动条、滚轮、键盘（PageUp/↑）三种输入都能触发 `PAUSED`。
4. `PAUSED` 状态下滚回底部**不**自动恢复（关键反转点）。
5. 点击「滚动到底部」→ 贴底并回到 `FOLLOWING`；随后追加继续贴底。
6. 清空列表后状态回到 `FOLLOWING`（新会话以「最新」为锚点）。
7. 程序性追加在 `FOLLOWING` 下不被误判为用户滚动（不出现「贴底一次后莫名暂停」）。
8. 全量重建（去重/淘汰/过滤变更触发）后，`FOLLOWING` 仍贴底、`PAUSED` 不跳视口。

### 5.2 排序控件归位

1. 排序动作并入左侧动作组（组内最后一个直接动作），窄宽随组一起折叠；当前方式进 tooltip 与菜单选中态；
2. 右侧控制组不再含排序控件，去重勾选仍在最右；
3. 400 / 460 / 600 / 800px 宽度扫描下工具栏恒单行、不越界、图标组不被挤出；
4. 排序切换后列表重排与刷新行为逐字不变。

## 六、反向验证

1. 把暂停判据改回 48px 松量 → 「上滚一行即暂停」用例必须红。
2. 恢复「滚回底部自动恢复跟随」→ §5.1-4 必须红。
3. 恢复按 `max/value` 调整事件反推跟随状态 → §5.1-4/7 必须红；当前实现只接受真实用户输入事件。
4. 在 `PAUSED` 态仍执行贴底 → §5.1-2 必须红。
5. 删除动作对状态的恢复 → §5.1-5 必须红。
6. 把排序控件放回控制组 → 左侧位置断言必须红。
7. 只调控制组预算常量而不加组合宽度守卫 → 临时把排序控件宽度加大后，单行守卫应能捕获（验证守卫有效性）。

> 反向验证必须在真实滚动路径上做「摘掉修复必红」，不接受只断言内部布尔值的空绿（跟随语义的价值全在滚动与视口的真实交互上）。
