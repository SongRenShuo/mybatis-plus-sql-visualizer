## 一、问题重定义：11m15s 权威轮与「一条命令不可靠」的裂缝

T8 权威轮（2026-10-24，rp8 树）11m15s 全绿：marketplace 长杆 ~10m 占总墙钟 ~90%，verifyGate(202s)/分片窗/e2e 全部藏在其窗口内。**但 10-28 三轮实测（master 与 dev 树）暴露了 T8 权威轮未曾覆盖的形态**：

| 轮次 | 命令 | 结果 |
|---|---|---|
| 10-28 #1 | dev 树 `testShards`（默认参数） | 5 片 START 戳相差 <60ms **真并发起跑** → shard2/3/4 启动期 native OOM（`Chunk::new`），**零读数**，落 5 份 hs_err |
| 10-28 #2 | master 树 `testShards`（默认）×2 | 同形态：测试 JVM 非零退出 + hs_err（`G1 virtual space` / `Chunk::new`） |
| 10-28 #3 | master 树 `testShards --max-workers=2` | **跑完出读数**（先 1 红=既有守卫误报，后全绿） |
| 10-28 #4 | master 树 `releaseGate` 一条命令 | 13m28s 被 OOM 打断（testShard1/3 执行器非零退出 + verifyGate 连带失败） |
| 10-28 #5 | 分阶段人肉跑：`testShards --max-workers=2` → `buildPlugin verifyGate` → e2e | 11m13s 全绿 8324/0/0/8 |

结构性结论：

1. **5 个分片（同 root project）在当前树是并发起跑的**——与 2026-10-20 轮「严格串行（911s）」的读数相反（该轮树 `1870b41d`；其间 e0088d24 并行运行器改动入库）。并发形态在单车道干净内存下能全绿（T8 权威轮即此形态），内存挤时（另一会话测试链/用户 IDE/62GB+ 基线）必然 native OOM。
2. **OOM 重跑才是现实时间大头**：每次 OOM 浪费 10~15min + 判读 + 清 hs_err + 重跑 10min。10-28 当日因此作废至少 3 轮。
3. **兜底手段是人肉的**：`--max-workers=2` 要手工带、releaseGate 要拆三段人肉编排——口径散落在踩坑记忆里，未固化进构建默认。
4. 全量测试独跑（`testShards`）串行基线 911s（e0088d24 提交信息）、并行运行器稳态 499s——日常通道仍缺「一条命令、默认安全、可调并发」的形态。

## 二、目标与非目标

**目标**：把「测试链并发度」做成构建内置的、内存安全的一等参数——`testShards` 与 `releaseGate` 一条命令在常见内存条件（含中等挤压）下可靠出读数，OOM 重跑面归零；在此之上把并发度做成可调旋钮，内存干净时全量测试墙钟显著低于串行基线。

**非目标（红线，继承 T6/T7/T8 全部）**：

- 五环节零删减、三目标 × 2 道兼容门禁口径不变；测试覆盖面零删减（类集、分片算术、testExternal、agent、隔离类补跑全不动）；
- **在线 freshness 语义不动**（marketplace 判定本体、verdict 不缓存、不直连——T8 已销案）；
- 不复活销案项：分片内 `maxParallelForks`（T-TestShardParallel 证伪：共享沙盒写坏）、6 片（T7/T8/T9 三否决）、JVM 堆/GC/线程旋钮（T5/T9 销案）、e2e 重叠（L3）、verifier 拆目标进程（L1）、降片（`-PtestShardCount` 调小禁令）、build cache（T-TestPerf-01）；
- **限流 ≠ 降片**：限流压缩的是「同一时刻几片在跑」，片数、每片类集、覆盖面逐一不变——与 R3 禁降片口径不同维度；
- 错峰机制形态不变（仅延迟启动，不删不减不重排任务语义），只允许重校参数值；
- dev 未经允许不合 master；本分支不合 dev、不回 master（合流待批）。

**验收判据（parity 三断言 + 计时，对齐 T8 口径）**：终轮一条命令 releaseGate 全绿读数中——①testShards 计数 = 当前 master 基线 8324（≥）、failures=0、skip 数与同环境对照轮一致 + testExternal 例数 + agent 例数持平；②verifyGate + verifyMarketplace 六判定全 Compatible、问题计数与基线逐字一致；③e2eFakeIde PASS=26 FAIL=0；④全程无 hs_err/native OOM；⑤墙钟：releaseGate ≤ 11m15s（T8 权威轮）或劣化 ≤5% 且换来一条命令可靠性；testShards 独跑墙钟 < 串行基线 911s。

## 四、待验证前提（实施者先证伪再动手）

- **前提 A（限流挂点）**：IPGP `testIde` 块注册的 `task {}` 内层 Test 任务可用 `usesService` 限流——用 `help` 配置验证 + 单分片定向轮验证 START/END 戳串行化；若挂点失败（外层包装任务才是调度单元），改挂外层 `testShard$i` 任务，再不行落 `--max-workers` 缺省化（gradle.properties `org.gradle.workers.max` 不行——影响编译面；退路是文档化分阶段口径）。
- **前提 B（并发形态现状）**：S1 先实测当前树 `testShards` 默认形态（START 戳）——10-20 串行 vs 10-28 并发的分叉树差异不追根，以当前 master HEAD 实测为准；限流缺省值与「防 OOM / 提并发」定位由该轮读数定。
- **前提 C（内存账）**：并发 N 路 × 分片 JVM Commit ~2GB + daemon 4GB + （releaseGate 内）verifier 2.3~2.8GB + agent 子 JVM——对 Commit 上限 74.7GB 与轮前底噪余量的等式，S1 采样后填数；并发 3 在 releaseGate 编排内（错峰后与 verifier 并存）须单独验内存峰值。
- **前提 D（stagger 与限流组合无害）**：分片 doFirst 的 `Thread.sleep(285s)` 占 worker 槽——限流后分片排队等槽，sleep 只发生在已获槽的分片上，行为正确；须实测确认无「sleep 占槽饿死其它片」的死锁形态（错峰窗内最多 N 片各睡 285s，其余片在槽外排队——正是期望行为）。
- **前提 E（配置缓存兼容）**：新属性读取与 BuildService 注册照抄 T7 教训——脚本顶层 val 经任务 lambda 引用不可序列化；`usesService` 是官方 CC 通道；service 注册用 `registerIfAbsent` 幂等。
- **前提 F（环境前置在位）**：e2e 硬依赖本机 MySQL 3306 + demo 工程；docker 离线（skip 口径）轮前复验 `timeout 10 docker info`；计时轮须等 insight 树 UI 验收任务（02:28~03:28 预期）结束、Commit 底噪 <60GB。
- **前提 G（buildSrc 编译税）**：本任务改动全在 buildSrc——落地后第一跑自带 ~+2min 编译税，计时对照轮必须「改动后首跑弃样」，从第二跑取数。
- **前提 H（agent 侧挂点）**：`:sql-visualizer-agent:test` 是子项目独立脚本，跨项目共享服务需经 root extension 传递 Provider——第一版可不挂（181 例轻量、独立 JVM 恒跑），S4 权威轮内存峰值若贴顶再补挂。
