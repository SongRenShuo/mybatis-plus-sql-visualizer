# T-LogListHeader：撤掉左侧信息轨，元信息回到 SQL 上方

> **创建日期**：2026-10-26 19:20
> **触发**：用户对 `bed58b64` 实测效果反馈三点——①条目间分割不明显、容易混在一起；②方言与其他信息应回到 SQL 上方；③增强捕获的类名（来源）也从左侧栏移到 SQL 上方
> **前序**：`bed58b64`（T-LogListRail，左侧 88px 信息轨）——本次是对该形态的**定向回退**，不是全盘撤销
> **实施分支**：`master`
> **用户最终定案**（2026-10-26，两轮修正后）：
> ①分割 = **留白 + 1px 细线，不画斑马纹**（先定斑马纹，看预览后否决）
> ②头部超宽 = 按优先级丢片段
> ③**耗时进度条不要了**（先定保留缩到右侧，看预览后否决）
> ④**左侧栏不要了**（先定保留三行，看预览后否决）
> ⑤头部信息顺序 = **方案 ④「库前置」**：`#序号 时间 耗时 [库] 类名:行号 (行数) 同结构 N 条`

---

## 一、用户反馈的三个问题（对应实测截图）

截图是「SQL 历史」页，可以清楚看到三处：

1. **条目之间没有视觉分界**。当前只有 1px `JBColor.border()` 底部细线 + 上下各 5px 内边距，而条目内部的行间距也是 1.45 倍行高——**条目内间距与条目间间距接近**，眼睛找不到切分点。用户原话「容易混在一起」。

2. **方言（`[MySQL]`）在 SQL 下方**。它现在挂在注脚行（SQL 区 SOUTH），而用户期望它与时间、耗时一起在 SQL **上方**。截图里 `[MySQL] 同结构 24 条` 出现在 `WHERE` 行下面，读起来像 SQL 的一部分。

3. **来源类名（`User:41` / `User:55`）在左侧栏**。用户明确要求移到 SQL 上方。

## 二、目标形态

### 2.1 版面

```
┌─ 1px 强分隔线（条目边界，见 §2.3）──────────────────────────┐
│ [3px色条] #1 09:42:02  1ms  User:41  [MySQL] 同结构 10 条   ← 头部行（全部元信息）
│           SELECT id,username,password,age,email,role_id ... ← SQL 第 1 行
│           FROM user
│           WHERE deleted = 0 … (+1)                          ← SQL 第 3 行 + 尾巴
└────────────────────────────────────────────────────────────┘
```

**左侧 88px 信息轨、竖线、进度条全部撤除**，色条回到最左、直接贴内容。所有元信息合并为**头部一行**，顺序采用用户选定的**方案 ④「库前置」**：

```
#序号  时间  耗时  [目标库]  [MCP]  来源类名:行号  (影响行数)  ⨉去重  同结构 N 条
```

与 `bed58b64` 之前的既有顺序相比，**唯一变化是把「目标库」从第 4 位提到「来源类名」之前**。
理由（用户与主控共识）：
- 多数据源场景下「这条打的是哪个库」是判定 SQL 是否走对源的第一判据，比「哪个类打的」更前置；
- 库角标是**定长短串**（`[MySQL]` / `[PostgreSQL]`），位置固定，扫视时形成稳定锚点；
- 来源类名长度可变（骨架化后 13 字符 + 行号），放它之后，宽度不足时先裁它不会破坏前面几列的稳定性。

时间仍用完整格式（含日期），宽度不足时按 §2.4 的优先级丢。

### 2.2 保留 `bed58b64` 的三项改进（不回退）

用户只否定了「左侧栏」这个形态，没有否定其余改进，故以下保留：

1. **关键字换行三行实内容**（`visibleSqlLines` 的 `MAX_KEYWORD_WRAP_LINES = 3`）——原实现第三行整行放 `… (+N)`，实际只读到两个子句。
2. **格式化模式不封顶** + 三行以上全部展开。
3. **类名骨架化压缩**（`railSourceName`：先剥 `ServiceImpl`/`Controller`/`Mapper` 等公共后缀再取尾部）——这条在头部行里仍然有价值，因为头部行宽度也有限。

### 2.3 条目分割（问题 1 的处置）

当前分割不足的根因是「条目内行距 ≈ 条目间距」。三层一起改：

| 手段 | 改法 |
|---|---|
| 分隔线 | 底部 1px 用略强于 `JBColor.border()` 的色（`JBColor.namedColor("mpvs.log.rowDivider", 0xC8C8C8, 0x4A4D52)`） |
| 留白拉大 | 条目**上下各 12px** 内边距（当前 5/5）——这是分条的主力手段 |

> **用户最终定案**：**只做「留白 + 细线」，不画斑马纹**。
> 演变：先定「强色线 + 斑马纹」→ 看预览后改为「不要斑马线，拉大间隔」。
> 留白 12px 是可调值（预览里给了 4~24px 滑杆），实施时定为常量 `ROW_VERTICAL_PADDING = 12`，
> 后续若嫌松/紧只改这一个数。

### 2.4 时间格式（顺带的必要调整）

`bed58b64` 把时间改成时段格式 `HH:mm:ss`（因为 88px 轨道放不下 `yyyy-MM-dd HH:mm:ss`）。头部行宽度充裕，但**历史页跨天浏览**时只有时刻会混淆。

处置：头部行时间恢复为**完整格式**（跟随 `logTimestampFormat` 设置），超宽时按**优先级丢片段**（用户定案）。

丢片段顺序（从最先丢到最晚丢）：
1. 时间中的日期段（`yyyy-MM-dd ` → 只留 `HH:mm:ss`）
2. 影响行数 `(N rows)`
3. 目标库角标
4. 同结构徽章（截断为 `…`）
5. 来源行号（`User:41` → `User`）
6. 序号（最后才丢，它是最常用的引用锚点）

> **待验证前提 P2**：现有 `clipForList` / `clipSqlFragments` 是「从右往左截断，超出即停」，无法表达优先级。需新增 `clipFragmentsByPriority(fragments, maxWidth, measure, dropOrder)` 纯函数。这是本次唯一的新算法，需单测覆盖。

### 2.5 行高影响

| 模式 | 当前（信息轨） | 改后（头部行） |
|---|---|---|
| 单行 | 两行：轨道 `#N 时刻` / `耗时+类名`，右侧 SQL 一行 → 视觉两行 | 头部一行 + SQL 一行 = **两行**（不变） |
| 关键字换行 | 轨道 4 行 vs SQL 3 行，取高者 | 头部 1 行 + SQL 3 行 = **4 行** |
| 格式化 | 轨道 4 行 vs SQL N 行 | 头部 1 行 + SQL N 行 |

结论：**行高不会变差，关键字换行还少一行**（原来轨道 4 行撑高）。

> **待验证前提 P3**：`measureFixedCellHeight()` 用样例 `SELECT 1` 渲染取首选高。头部行加入后，单行模式的固定行高会从「轨道两行」变成「头部一行 + SQL 一行」，需要实测两者是否等高——若头部行因包含徽章而高于 SQL 行，固定行高会略增。

### 7.2 实施中发现的三个真 bug（均由测试/探针抓出）

1. **类名片段缺尾随空格**。`sourceNameText` 返回 `User:41`（无尾空格），导致下一个片段粘成 `Order:42⨉3`。
   由 `SqlListV179HeadlessTest` 抓出。修复：补尾随空格，与 `formatDurationFragment` /
   `formatDatabaseFragment` 的片段间距契约一致。

2. **日期剥离规则静默失效（第一次）**。`isDatePrefixed` 只认 `2026-10-26 09:42:02` 形态，
   而真实片段来自 `formatTimestampFragment`、形态是 `[2026-10-26 09:42:02] `（带方括号）。
   单测里手写无括号形态能过，真实渲染永远不剥日期。修复：容忍前导 `[`。

3. **日期剥离规则静默失效（第二次）**。把日期剥离塞进优先级循环里，而时间片段的优先级是
   `NEVER`（时刻不能丢），于是 `levels` 过滤后时间片段根本不在循环里 → 日期永不剥离。
   修复：把「剥日期」提升为独立第一步，与优先级循环解耦。

另有一处**测试覆盖缺口**由反向验证暴露：R1（把留白退回 5px + 换回 `JBColor.border()`）
第一轮**没有变红**——说明「条目分割」这个用户最在意的特性完全没有守卫。补了
`test条目留白_显著大于改造前` 与 `test条目分隔线_强于平台默认边框` 两条，重跑 R1 后精确命中。

### 7.8 修正：时间格式不再按宽度改写（用户 2026-10-26 追加纠正）

原实现（§2.4 与 7.2 记录）在头部行超宽时**剥掉日期段、只留时刻**，理由是 88px 时代放不下
完整时间。用户在实测中提出质疑：**设置页配了 `logTimestampFormat`，显示就该严格遵循它**，
不能按宽度偷偷改格式——同一份配置在宽栏与窄栏显示成两种形态，用户无从察觉。

**处置**：整段删除「剥日期」逻辑。时间片段列为**不可拆分**，宽度不足时按优先级丢其他片段
（影响行数 → 库角标 → 徽章 → 行号 → 序号），全丢完才由 `clipSqlFragments` 顺序截断。
`HeaderFragmentPriority.DATE_PART` 常量、`isDatePrefixed` / `stripDatePrefix` 函数一并删除。

**搜索侧反而更简单**：时间不再有第二种显示形态，「所见即所搜」天然成立。
我曾为此加过一个 `matchesTimestamp`（同时匹配完整格式与时段），实测确认原实现本就够用
（完整串包含时段），已一并回滚——不做多余改动。

**新增守卫**：
- `test头部裁剪_绝不改写时间格式`：窄档下断言完整时间仍在
- `test头部行时间格式不随宽度变化`：900/420/320/280/240/**200**px 六档渲染同一配置，
  断言可见时间片段逐字节一致（200px 档是关键——只有它会把时间压到截断边界）

反向验证：把「剥日期」加回去 → 上述两条**恰好变红**。

### 7.7 遗留

- **真机走查未做**：三种模式 × 日志页/历史页 × 窄宽两档，重点看「条目边界是否一眼可辨」。
- **头部行在极窄（≤200px）下时间会被顺序截断成 `[…]`**：这是「格式不可改写」的必然代价。
  正常侧栏宽度（≥280px）不会触发；若真机上出现，处置是放宽优先级顺序而非改格式。
- **12px 留白是否合适需真机确认**：这是本次最能影响观感的单一参数，常量在
  `RailCellRendererBase.ROW_VERTICAL_PADDING`，改一个数即可。
- **全量 `testShards` 未跑**：只跑 `log` 包 1759 例，全量交收口阶段。
