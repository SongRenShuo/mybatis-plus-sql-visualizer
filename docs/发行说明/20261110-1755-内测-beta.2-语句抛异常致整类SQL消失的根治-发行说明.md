## 修复

**一条语句抛异常之后，同一线程后续的 SQL 会整片消失——已根治。**

根因在增强捕获的语句织入：原实现只在方法体里**显式出现**的返回点前插出口回调。当语句执行抛异常、且异常是从被调方法逃逸出来时（本方法体自身没有 try/catch），字节层只有一条正常返回指令、一个 `athrow` 都没有，出口钩子**无处可插**——嵌套门禁的入口计数了、出口没执行，线程深度永久 +1。此后该线程每条语句都被当成「外层、已由内层报过」而静默抑制。

这解释了那类最难查的现场：**前几条语句正常，之后整类不上屏**，而既有的「门禁抑制」计数恒为 0（被抑制的是最外层自己，不是嵌套外层）。

现在 timed 语句面（`execute` / `executeQuery` / `executeUpdate` / `executeLargeUpdate` / 批处理）的方法体统一包一层 catch-all 出口：异常也走一次出口回调**再原样重抛**，链深度立即归零。附带的行为改善是——**失败的那条语句本身现在会产出一条带错误信息的事件**，不再是「报错了但列表里什么都没有」。

## 新增

- **状态栏「门禁陈旧 N」**：嵌套门禁的链龄超过阈值仍有新帧进入即计数，debug 档另在宿主 stderr 打一次陈旧链摘要与调用栈（只一次、不含 SQL 原文），心跳带出 `nestStale` / `nestMaxDepth`。它把「深度泄漏」从不可见变成可读事实。
- 上一版（`beta.1`）的四段读数（让位丢弃 / 组装失败 / 门禁抑制 / 登记盲区点名）继续保留。

## 测试

- 定向 **45 / 0 / 0 / 0**：新 `StatementWeaverExceptionExitTest` 6 例（行为 / 字节级 / 四种返回形态 / handler 帧）、厂商对齐 17、帧补丁 3、端到端 13、NestGate 6。
- **反向验证**：注掉 handler 插入 → 6 例中 **5 红**（行为例统一报「异常出口必须产一条 error 事件」，字节级报 `expected:<3> but was:<2>`），恢复复绿。
- 字节级逐方法断言：磐维 V1/V2、金仓 `KbStatement`、达梦 `DmdbStatement`、`org.postgresql.jdbc.PgStatement` —— 每个 timed 方法 `enter=1`、`exit=显式返回数+1`、catch-all handler 各加 1 且紧随有效帧。
- **真机（香港磐维 A 模式，`jdbc:panweidb://155.103.159.54:26201/panweidb`）**：两条失败 `DROP` 之后，`SELECT COUNT(*) FROM pg_settings` 照常产出；心跳连续三拍 `nestSuppressed=0 / nestStale=0 / nestMaxDepth=1`。修前同一载荷：两条 DROP 零事件、`nestStale=2 / nestMaxDepth=3`、之后整类消失。全量 observe 载荷（DROP/CREATE/两条 INSERT/SELECT/COUNT/DELETE）→ 10 条事件全出。
- **`-Dsqlvis.agent.nestGate=false` 不再是必需**：关闭门禁与开启门禁现在读数一致。

## 已知边界

- 本轮**没有**改嵌套门禁的判定语义（仍靠「同线程只报最内层」去重）。本次修的是出口配平，不是门禁策略。
- 一条语句在同一线程内**真正嵌套**执行（存储过程里再执行语句）时，外层那条仍不产事件——这是门禁的既有取舍，未变。
- `ADD_BATCH` / `CLEAR_BATCH` / `PREPARE` 三面未包 catch-all：异常时可能少一次登记，但不影响链深度，不会造成整类丢失。
