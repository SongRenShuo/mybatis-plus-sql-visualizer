# 🎉 SQL Visualizer v2026.11.2

> 发行说明留档：对应 Gitee 发行版 **v2026.11.2**（标签 `2026.11.2`），附件 `mybatis-plus-sql-visualizer-2026.11.2.zip`。
> 通道：**Gitee 正式版**（Marketplace 侧由作者单独上传）。
> 范围＝v2026.10.31 发行包之后的全部用户可见增量：三处修复，集中在预览窗的取源链路、分页 COUNT 判定与预览文档落盘。

本版修的是三条被日常使用撞出来的问题，前两条出在预览窗的「执行 SQL」链路上，第三条在预览面板的落盘链路上。

第一条是用户 2026.2 真机报障：数据源配好了、方言也推断对了，预览窗却报「没有与该 SQL 方言匹配的已配置数据源」，点了也执行不了。根因不在配置——2026.2 起平台不再让 EDT 隐式持有读锁，插件反射调用平台取数据源列表时被平台内部抛读锁异常，而这个异常被自己的 `runCatching` 吞成了空列表，于是「零个数据源」被套上「方言不匹配」的文案，把用户引去改一个本来就没问题的设置。第二条范围更大、跨所有版本：`selectList` 之类非分页查询只要带了 `last("limit N")`，预览就会凭空多出一条分页 COUNT。第三条同样跨所有版本、已存在三周：预览面板挂上控制台之后，勾选参数或返回预览会弹 `Access is allowed from write thread only`，同时预览 SQL 一直写不进执行文件。

## 🛠 修复

**IDEA 2026.2 上预览窗「执行 SQL」报方言不匹配且无法执行（T-Exec262ReadLock，用户真机报障）**
- 现象：预览窗顶部红条「没有与该 SQL 方言（PostgreSQL）匹配的已配置数据源」，执行按钮点了没有反应。现场 PostgreSQL 数据源配置齐全、上次使用的源可见、方言推断也正确，改 Dialects 设置怎么改都无效
- 根因：2026.2 起 EDT 不再隐式持有读锁，插件反射调用平台 `DatabaseRunners.getAttachDataSourceRunners` 时，平台内部 `DataSourcePerFileMappingsImpl.getMapping` 直接抛 `Read access is allowed from inside read-action only`；插件侧 `runCatching` 把异常吞成空列表，`runners` 归零后进入「没有匹配数据源」分支。异常与「真的没有数据源」在修复前完全不可区分
- 修复分两层：
  - 取源两处反射调用（attach 与切换数据源）统一包 `WriteIntentReadAction.compute`——平台链内部会 attach 控制台属写意图，按第三方链入口口径用 WIRA 而不是 `ReadAction`
  - `runners` 为空时按「平台调用有没有抛异常」三分归因：真的零个可用数据源才报方言不匹配；平台调用抛异常则报异常最内层首行并提示反馈；其余按空源引导
- 重载选型踩了一个真实的兼容坑，一并记在这里：首版用的是 `compute(ThrowableComputable)`，那个重载只在 243 存在——262 改名为 `computeThrowable`，编译期引用到 262 运行时直接 `NoSuchMethodError`（用户装首版新包后实测）。现改用 243 / 262 两平台方法集的交集 `compute(Computable)`，语义等价（Kotlin lambda 抛受检异常在字节码层合法，`InvocationTargetException` 照常穿透给外层捕获）
- 顺带得到的一个副产物：即便包裹将来再出问题，红条也不会再误导用户去改 Dialects——归因分流会把平台侧的真实异常亮出来

**`selectList` 等非分页查询的预览凭空多出一条「分页 COUNT」（T-Exec262ReadLock）**
- 现象：`queryWrapper.last("limit " + n)` 这类写法，预览里除了原语句还多出一条 `SELECT COUNT(*)`，像是把非分页查询当成分页处理了
- 根因：`last(...)` 被解析进语句 LIMIT（形参静态不可得 → 渲染成 `LIMIT ?`），而 COUNT 包裹的判据只看「语句有没有 LIMIT」，没看「调用是否真的传了 `Page` / `IPage` 实参」——`last` 的 LIMIT 被当成了分页附赠
- 修复：以「确有分页实参解析产物」（`chain.pageLimit != null`）为唯一闸。`last` 里的 LIMIT 照常渲染，但不再附带 COUNT；XML / 注解路径上真正带 `Page` 形参的分页查询不受影响

**预览面板已挂控制台时，勾选参数 / 返回预览弹 `Access is allowed from write thread only`，且预览 SQL 写不进执行文件（T-PreviewDocPersistLock，用户真机报障）**
- 现象：控制台已嵌入预览面板后，勾选参数、切换显示模式、返回预览、刷新都会弹一个 `RuntimeExceptionWithAttachments`，提示只能在写线程访问；SQL 本身显示正常，但勾选按钮文案与「绑定数据源」指示行停在旧态，磁盘上的执行临时文件一直是旧内容
- 根因：渲染回填时 `setText` 放在 `WriteCommandAction` 里，紧跟着的 `saveDocument` 留在块外。写命令返回的一刻写意图就释放了，而 `FileDocumentManager.saveDocument` 首行断言写环境（243 `FileDocumentManagerImpl:323-336` → `TransactionGuardImpl.assertWriteActionAllowed`；262 同形改名），于是在 EDT 上硬抛。异常从 `showSql` 往外抛后，尾部两条刷新、`lastRenderedSql` 更新与自动折叠全被跳过；落盘从引入以来一次都没成功过
- 引入时间与面：写这段的原始意图（T-PS4-12「同临界区落盘」）是对的，落地时把落盘放在了块外，恰好把想消除的「已改未存」窗口变成了永久窗口。2026-10-10 起、243 / 261 / 262 全版本都在，只是先前被上游取源那条 P0 挡在前面，用户走不到这条路径
- 修复：落盘移进同一个 `runWriteCommandAction` 块（与 `DataSourceSelector.writeVfTextViaDocument`、`DataSourceSelectorResults` 既有形态一致），`setText` 与落盘重新真正同临界区
- 这一条为什么一直测不出来：`BasePlatformTestCase` 的整个测试体被框架包在一条 `WriteIntentReadAction` 里，写意图全程持有，`saveDocument` 的断言永远通过。本轮先按「EDT 无写意图帧」写用例，实测两条前提都不成立（嵌套 `writeIntent=false` 剥不掉外层意图；改判 `isWriteAccessAllowed` 在未修复代码下仍恒真），最终改用「保存调用栈里必须出现写命令帧」这条可判别的不变式——未修复时红、修复后绿，两次读数都在实施记录里

## 兼容性

- 支持 IntelliJ IDEA **2024.3+**（Ultimate / Community；EXPLAIN、执行 SQL、表右键入口与 Database 原生图需 Ultimate；MCP 能力需平台 MCP Server）
- 插件 ID 与升级链路不变，v2026.10.31 用户可直接覆盖升级
- 读锁包裹对 2024.3 / 2025.3 / 2026.1 无害：不存在该异常时包裹是纯透传；`compute(Computable)` 在三个目标平台都存在
- 行为变化一处：`last("limit N")` 的非分页查询不再附带 COUNT（这是修复，不是可选项）
- 设置项数量不变，无需重新配置

## ⚠️ 已知边界

- **262 运行时实效尚未取到沙盒真机读数**：本轮验证止于编译、双平台 `javap` 方法集对照与定向单测；`WriteIntentReadAction` 包裹在 2026.2 上的实际取源效果、以及「切换数据源」入口，需装本版包在 2026.2 真机上确认。首版（`compute(ThrowableComputable)`）已被用户真机否掉，本版是据此重选重载后的修复，**不写「262 已真机验证」**
- 平台调用异常的分流文案依赖平台抛出可读异常；若平台以其它形态失败（返回空而非抛错），仍会落到「方言不匹配」文案——该形态本轮未复现
