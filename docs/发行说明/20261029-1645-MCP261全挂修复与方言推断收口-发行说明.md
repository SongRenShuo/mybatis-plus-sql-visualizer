# 🎉 SQL Visualizer v2026.10.29

> 发行说明留档：对应 Gitee 发行版 **v2026.10.29**（标签 `2026.10.29`），附件 `mybatis-plus-sql-visualizer-2026.10.29.zip`。
> 范围＝自 v2026.10.28 正式版发行包之后的全部用户可见增量。

自 v2026.10.28 后的正式版。本版有一个必须先说的 P0：**IDEA 2026.1.x 上启用 MCP Server 会让平台内置 MCP 服务对所有客户端不可用**（HTTP 500，卸载插件才恢复），已修。其余是四处采集与交互可读性修复（定时任务线程的调用栈看不到项目代码、日志列表暂停后被顶动、智能方言推断被非 SQL 数据源带偏）、一处推断增强（按模块与激活 profile 取方言证据），以及编辑期 daemon 负担与长会话内存的三处收口。

## ✨ 新增

**方言推断的配置证据按模块收窄（T-DialectInferSmart）**
- 多模块项目各自连不同库、或测试资源另用一套库时，原来的项目级全量共识会退化成「无共识」、整条推断落回 IDE 方言设置。现在配置证据按来源模块收窄：模块内拿不到结论才回落项目级，结论按模块单独缓存
- 扫描排除测试资源目录（`ProjectFileIndex.isInTestSourceContent`）——主库 PostgreSQL + 测试 H2 不再互相挤成无共识
- 优先采用激活 profile：解析 `spring.profiles.active` / `include`（扁平键、properties、YAML 缩进块、逗号与方括号与列表项都认），`${ENV:default}` 取默认值，`${ENV}` 与 `@maven@` 视为未知；激活 profile 的 `application-<profile>.*` 覆盖基础文件、其它环境文件不参与投票；拿不到激活 profile 才回到全量共识

## 🛠 修复

**IDEA 2026.1.x 下插件让内置 MCP Server 对所有客户端不可用（T-Mcp261FilterContract，用户报障 P0）**
- 现象：261 上启用 MCP Server 后任何客户端 `initialize` 都拿到 HTTP 500（`/stream` 每次失败、`/sse` 建不起会话），`idea.log` 是同一句 `NullPointerException: Parameter specified as non-null is null ... CollectionsKt.addAll`
- 影响面：不止本插件的 11 个工具——**平台 MCP Server 整体不可用**，其他插件注册的工具一并消失，关掉插件里的 MCP 总开关也没用，只能卸载插件
- 根因：平台的工具过滤器接口在 261 上是另一套契约（`getFilters` 返回过滤器清单 + `modify` / `apply` 改写工具集合），而插件的全反射代理是按 2026.2 的 `applyFilters` 写的。261 调 `getFilters` 时落到兜底返回 null，平台紧接着把 null 当迭代器传给 `addAll`
- 修复：改为「先探测契约再注册」——`applyFilters` 形态（2026.2 / 2026.3）与 `getFilters` 形态（261.24374 起）各走对应实现，认不出的形态一律不注册；同时给代理的所有未知方法加按返回类型的空值兜底（集合 / Map / Flow / 原始类型绝不返回 null），实现体全程异常降级。即使下一条版本线再改契约，最坏结果是「门控不生效」，不会再让平台的 MCP 服务整体挂掉
- 取证：把 Marketplace 下载的 `mcpserver` jar 装进严格 child-first 子加载器对真实字节码跑形态探测（261.17801 无此类 / 261.22158 UNKNOWN / 261.24374 与 261.25134 `getFilters` 形态）；并按报障原文复现出与用户 `idea.log` 逐字一致的 NPE，换现行桥后不抛、返回空清单

**定时任务等非 Web 线程的调用栈看不到项目代码（T-StackBizFrame）**
- 现象：`@Scheduled` 一类调度线程产出的 SQL，日志列表的位置列能正常指到业务文件（如 `MerchantWalletRechargeServiceImpl.java:32`），但同一行的栈摘要与调用栈弹层里一个项目类都没有，看上去像「这条 SQL 不在我的调用链上」
- 根因：栈底锚点只认插件自有基础设施的包白名单，不含 `org.springframework.scheduling.*` 与 `io.micrometer.*`。非 Web 线程穿透时锚点在栈底第一帧就停住、锚点等于栈底，业务帧全被挤出 8 帧窗口；摘要与源码定位又是两条独立判定，中间没有一致性约束，于是出现「位置列对、摘要全是内部帧」
- 修复分三层：栈底锚点改为业务来源（复用 `StackLocator` 判据，不另造名单）→ 框架前缀穿透 → 字面兜底；源码定位帧成为摘要必含项（落在窗口外时单列一段，省略计数同步扣减），两条判定不再各说各话
- 展示面同步三处：折叠名单补入 JDBC 驱动族与 MyBatis `logging` / `binding` / `reflection` / `type` 等内部包（这些包在每条 SQL 的栈顶恒在场，旧名单不收时弹层可见行反而是驱动帧）；日志列表 meta 行的栈摘要先取景（头部全内部帧时跳到首个项目帧）再按原 120 字符契约截断；调用栈弹层标题附线程名，`scheduling-1` / `pool-2-thread-1` 与请求线程一眼可辨
- 真机对拍（真实 Spring 应用：`ThreadPoolTaskScheduler` + 两层 `TransactionTemplate` + MyBatis + H2，线程 `sched-1`）：旧包摘要零项目帧（栈底被 `ScheduledMethodRunnable` / `OutcomeTrackingRunnable` / `DelegatingErrorHandlingRunnable` 占满），本版同一事件剩五个项目帧、锚点落在 `@Scheduled` 方法本身；两版源码定位诊断逐字相同，差异只在摘要侧
- 无设置项变化：折叠名单是内置常量

**智能方言推断被非 SQL 数据源与日志还原链规避（T-DialectInferFix）**
- Redis 一类非 SQL 数据源被当成方言候选、产出「未知」后，按引擎「未知候选不得宣称共识」的规则整项目回落到 MySQL
- 日志 / 历史双击预览不携带本次执行方言，渲染与 PSI 映射一并落到 MySQL——PostgreSQL 的合法列名 `signal` 被 MySQL 保留字表判成语法错
- 现候选只取 SQL 数据源（按平台 query language → DBMS 显示名 → URL 子协议精确比对）；日志 / 历史预览携带本次执行方言（旧条目按 `db:` 角标回填）；兜底不再硬编码 MySQL，新增 `PreviewDialectResolver` 统一渲染与 PSI 映射口径，PSI 预映射改为继承平台项目 / 全局 SQL 方言并清理历史 MySQL 映射；无 IDE 数据源时改按「配置 JDBC URL → 构建驱动坐标 → SQL 方言特征」的唯一共识再退一级到项目 / 全局设置，状态行显式标注来源

**日志列表暂停态被新 SQL 顶动、关键字换行退化成单行**
- 手动滚动暂停后，新 SQL 到达仍把正在看的内容往上顶：JList 没有滚动锚定，缓冲满载（默认 200）时每条新 SQL 淘汰头部一条、整屏上移一行
- 显示模式为「关键字换行」时多数只剩单行：摘要取 160 字，长列清单在预算内到不了 `FROM`，一个换行点都找不到，恒退化成单行 + 行尾省略号
- 修复：头部淘汰按被删行高上移视口，全量重建按条目身份复原且条目落在后续批次时逐拍重试；换行模式改为取完整还原 SQL 并按 4096 字符预算在空白边界截断（单行摘要仍取 160 字）；滚底判据抽成纯函数，程序性滚动与「位置变小」都不算用户手势，只有用户主动往底部滚动且到位才恢复跟随

## 🔧 改进

**Mapper 双向跳转的图标判定（T-PerfSweep28-01）**
- 此前对每个打开 Java 文件的每个方法声明在 daemon 慢趟都调一次语句定位：没有「文件是不是 Mapper 接口」的前置判定、不缓存负结果、命中后还为统计同名扫完所有 mapper 文件；文件清单 5 秒 TTL 过期后的全项目 XML 索引重扫也落在 daemon 线程里
- 现加接口前置（O(1)）、定位结果级记忆（正负都缓存，与文件清单同代失效）、两个 Provider 接入总闸与 `mapperXml` 组闸
- 行为面不变：非接口类本来也解析不到目标、不显示图标

**字符串 SQL 方法 gutter 的检查开销（T-PerfSweep28-04）**
- 原在每个候选方法名叶子做一次方法体全子树遍历，只有 200K 方法体护栏兜底
- 字符串 SQL 必为字符串字面量，改为先扫方法体文本是否含引号：零分配单次扫描替代子树遍历，精度 100%

**长会话内存的两处无上限累积（T-PerfSweep28-03）**
- Hibernate 命名探测缓存：键含项目基路径与模块资源目录，多项目长会话缓慢累积且项目关闭不摘除；现加 512 上限（写入单一守卫，超限整体清空再写）
- 预览弹窗登记表：以 `Project` 强引用为键、项目关闭不摘除，改弱键映射后项目存活期不误回收、关闭后随 GC 摘除

**栈摘要的业务帧判定（T-StackBizFrame P-5）**
- 原走相对路径计算、每帧拼一次 `pkg/File.java` 字符串，改为直接判文件名。压测 35 / 41 / 13 帧三形态对拍：Web 形态省约 1.6µs/SQL，调度形态与浅栈约 0，最坏形态约 1µs/SQL

## 兼容性

- 支持 IntelliJ IDEA **2024.3+**（Ultimate / Community；EXPLAIN、执行 SQL、表右键入口与 Database 原生图需 Ultimate；MCP 能力需平台 MCP Server）
- 插件 ID 与升级链路不变，v2026.10.28 用户可直接覆盖升级
- 本轮改动面：MCP 工具过滤器注册契约（261 / 2026.2 双形态）、方言推断的证据来源与兜底链、调用栈摘要与展示、日志列表视口与换行取源、编辑期 gutter 判定路径与内部缓存；设置项数量与默认值未变
- IDEA 2026.1.x 用户升级后 MCP Server 恢复可用，无需再卸载插件；此前在 261 上关过插件 MCP 总开关的，恢复后按原开关状态生效
