# 🎉 SQL Visualizer v2026.11.4

> 发行说明留档：对应 Gitee 发行版 **v2026.11.4**（标签 `2026.11.4`），附件 `mybatis-plus-sql-visualizer-2026.11.4.zip`。
> 通道：**Gitee 正式版**（Marketplace 侧由作者单独上传）。
> 范围＝v2026.11.3 发行包之后的全部用户可见增量。

这一版有两件大事：增强捕获在 Oracle 上终于能把业务 SQL 采全，以及预览执行链上三处「在界面线程干重活」的老毛病被清掉。

Oracle 那条是用户报的：应用跑起来只看见 `select 1 from dual` 这类连接校验语句，MyBatis 的业务 SQL 一条都不出。根因在驱动层——Oracle thin 对外返回的是包装器（`OraclePreparedStatementWrapper` 等），插件把 SQL 登记在包装器上，而 `executeQuery()` 的织入点落在包内的物理语句（`T4CPreparedStatement`），登记对象与执行对象错位，查表永远落空。同一条链上还有两处去重门的缺陷，导致一条失败语句被重复上报三次。两处一起修了，真机上三种 Oracle 驱动、premain 与 attach 两条路径、连接池环境都验过。

线程那三条是这一轮验收里从 IDE 日志里翻出来的：控制台数据源下拉每次刷新都在界面线程读 PSI、执行 SQL 时在界面线程做目录查找、执行与方言映射的写派发不是写安全的。三处都会让 IDE 刷 SEVERE 告警，前两处还直接拖慢预览。

## 🛠 修复

**Oracle 应用的增强捕获只剩连接校验 SQL，业务 SQL 一条不出**
- 现象：Oracle 应用只采到 `select 1 from dual` 这类连接校验语句，MyBatis 业务 SQL 完全不可见
- 根因：Oracle thin 驱动对外返回包装器，prepare 面把 SQL 登记在包装器上，而 `executeQuery()` 的织入点在包内物理语句——登记对象与执行对象错位，事件按「盲区」丢弃；plain `Statement` 走「SQL 取首参」不依赖登记表，所以只有连接校验 SQL 能看见
- 修复：prepare 面登记时按字段类型反射解一层包装，把内层物理语句一并登记（绑定参数与批串随之接回内层）
- 顺带修掉同链路两处去重门缺陷：嵌套门把「进入过」当「产出过」，内层盲区会连外层能出的 SQL 一起吞掉；同一帧「try 内 ATHROW + 处理器重抛」两条出口钩子会让嵌套深度多减一次，一条失败语句重复上报三条
- 真机复验：Oracle Free 23（ojdbc11 23.3 / ojdbc8 19.3 / ojdbc8 12.2，premain 与 attach 双路径，HikariCP 池）业务 SQL 全部可见且带绑定参数，失败语句只报一条

**打开预览就弹「选择数据源」列表，多源工程每次预览都要先选一次**
- 现象：工程里配了多个数据源又没有上次使用记录时，打开预览必弹选源列表，面板右上同时还显示「未绑定数据源」
- 根因：预览默认准备与显式执行走同一个分支，弹窗那一段不区分两者，与该函数自己声明的「预览默认准备静默」意图矛盾
- 修复：预览准备阶段不再弹窗、不建链、不报错，面板保持未绑定灰字，等点「执行 SQL」时再弹；单飞门按 owner 正常结算，下一次执行不会排队到 60 秒超时。显式执行与「切换数据源」两个入口的弹窗行为不变

**改了 IDEA 方言并刷新预览后，底部方言红条仍按旧方言报冲突**
- 现象：顶部写「方言: MySQL（已绑定数据源）」、SQL 也按 MySQL 渲染，底部却报「当前 SQL 按 PostgreSQL 渲染」
- 根因：三条叠在一起——闸门请求无条件优先取预览生成时固化的方言快照，而顶部决策会随绑定与刷新升级；XML 载体不能无损重渲染，AUTO 被降级成「重渲染不可用」，红字两边方言都取自陈旧值；「刷新」按钮只重渲染文本，不重算决策
- 修复：方言无关载体（XML 原文 / 纯文本）的闸门渲染方言取最新决策，与顶部同源；模型 / 批量 / 分页载体仍取渲染事实；点「刷新」按预览生成时的同一份证据重算决策，匹配就清掉红条

**控制台数据源下拉每次刷新都在界面线程读 PSI**
- 根因：接管组覆写了 `update()` 与 `displayTextInToolbar()`，平台据此判定它不是默认 update，线程落回 EDT；而它逐字委托的原生动作自己返回后台线程
- 修复：声明后台线程更新，与原生动作一致，update 体仍只读写 Presentation

**执行 SQL 时在界面线程做 PSI/VFS 目录查找**
- 根因：准备链第一次取控制台脚本模型会实例化临时文件的 PSI，平台内部走目录查找与索引刷新，EDT 上调用即记慢操作；靠缓存也不行——方言映射会触发重解析把 PSI 作废
- 修复：attach 之后先到后台线程用读锁预热 PSI，再以写安全模态回 EDT 续接准备；续接异常统一收口，单飞门不会悬挂

**执行入口与方言映射的写派发不是写安全的**
- 根因：一处用 `ModalityState.any()` 投递（恒为 write-unsafe），一处从后台线程用省略模态派发模型写，链内改文档与改模型的动作因此没有写资格
- 修复：两处统一改 `ModalityState.nonModal()`，投递顺序、回调内容与异常路径都没变；方言映射仍保留原有有界等待与超时降级

## ⚡ 改进

**没有匹配方言的数据源时，提示改成能照着做的「下一步」**
- 原来是一条红色「执行失败：没有与该 SQL 方言（MySQL）匹配的已配置数据源……」，后面跟着项目里全部数据源的名字：看不出该改哪一个，措辞还让人以为插件坏了——其实只是数据源还没就绪
- 现在按 JDBC URL 推断哪些源看起来就是目标方言：唯一命中直接把源名写进标题（「下一步：给「mp_demo@localhost」启用 MySQL 方言」），多个则点名前 5 个、其余折叠，推断不出就只说「给一个数据源启用」
- 状态行从红色降级为橙色，右侧给「打开数据源属性」与「切换数据源」两个可点入口，前者直接打开数据源对话框并选中推断出的源
- 悬停能看到推断依据与可执行的下一步：右键目标数据源 → Properties，用「Test Connection」确认能连上（平台在连接成功后才把该源识别为该方言）
- Runner 的筛选逻辑与既有归因未动，只在「方言不匹配」这一态接入新提示

## ⚠️ 已知边界

- 线程修复的证据层级到「源码形态守卫 + 定向测试 + 一次真机日志确认（三类 SEVERE 归零）」；未做长期运行的稳定性观察
- 方言不匹配提示的推断只认 JDBC URL 子协议。URL 用了非标准写法或自定义驱动接入时推断不出，此时退化为「给一个数据源启用…」，仍可点开数据源属性自己确认
- 「打开数据源属性」走平台 Data Sources and Drivers 对话框（与右键数据源选 Properties 同一入口）；Community 版没有该插件时不出现这个入口，只保留文字提示
- Oracle 修复覆盖 thin 驱动的一层包装；更深的包装层级或多层代理池尚未验证
