# 🎉 SQL Visualizer v2026.10.26

> 发行说明留档：对应 Gitee 发行版 **v2026.10.26**（标签 `2026.10.26`），附件 `mybatis-plus-sql-visualizer-2026.10.26.zip`。
> 范围＝自 v2026.10.23 正式版发行包之后的全部用户可见增量（本轮为单项修复版）。

自 v2026.10.23 后的正式版。本版修一个外部用户真机报障：**实体打包进 JAR 后，`@Embedded` 嵌入列的前缀丢失**，并顺带为嵌入列解析加了一组诊断日志（报障排查用）。

## 🐛 修复

**JAR/lib 模块实体的嵌入列命名宿主级联（T-EmbeddedHostCascade）**

- 现象（外部用户报障）：「JAR 里的实体 @Embedded 无法正常识别，源码正常」——预览的嵌入列名丢 component-path 前缀（`base_qty`），而真库列名带前缀（`qty_base_qty`），一执行就对不上
- 取证：既有读数存档 + 重建真实模型 JAR 的全链端到端探针证明，HEAD 对二进制实体的注解读取 / 展平 / 映射本就正确；真正成立的缺口形态是——**实体在 lib/JAR 模块且该模块有自己的 resources 但没有命名配置**时，嵌入列命名探测按「实体所在模块」收范围会判不出，而命名策略实际配置在宿主 App 模块（持久化单元）
- 修复＝宿主级联：实体所在模块探测 miss 后，改查查询宿主模块再判（HQL / JPQL 链自动生效）；两档都判不出仍**不回退工程级扫描**——多模块聚合根打开时兄弟模块配置外溢的既有防护不变
- CRUD / Specification / Criteria 等单参调用维持原行为；同症状出现时按同款模式扩展
- 验证：级联定向 4/0/0/0（反向摘掉级联恰 1 红）+ 真实 JAR 全链 2/0/0/0（真表名与三列前缀逐项断言）+ 嵌入簇回归 9 类 59/0/0/0

**嵌入列解析诊断日志（T-EmbeddedIdentify W1）**

- 报障排查用：`idea.log` 里按 `[T-EmbeddedIdentify]` 前缀即可看到命名档判定来源（显式配置 / 探测命中 / 回落默认）、嵌入列展平清单、以及「嵌入类型不可解析」降级的 WARN 签名
- INFO 级、无新配置开关、不改任何判定语义；仅日志本身 runCatching 包裹
