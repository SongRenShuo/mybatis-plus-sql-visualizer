## 这一版有什么

### 大工程里 MBG Example 预览一直停在占位符（D1，`85e09cab9`）

真机读数（demo/cust-big-demo，用户工程同构）：

```
[m2] trace …CustAddressMapper#selectByExample methods=1 noCallSite -> criteria=0
[open-perf] total=166ms parse+ctx=50 profile=1 m2=101 model=14
```

同一刻在 IDE 里对同一方法 `Find Usages` 得 **253 处引用**、`ProjectIndexableFilesFilterHealthCheck` 也没有报错——索引是好的，是 `ReferencesSearch.search(...).findFirst()` 在这条链上恒返回 null。M5 把「收全量再取第一个」换成 `findFirst` 时只在 Heavy 测试里跑过，而那条路本来就 `refs=0`（引用索引未建），等于从未被真机证过。

修法：改 `forEach { hit = it; false }` 取首个命中（语义等价、同样提前终止，不把 253 条收成 List）。同时补齐 `[m2]` 诊断：命中/失效/未解析三态、`scope=`、`and/or` 各类拒绝计数，避免下次再出现「已修好」与「从未生效」在日志里长得一样。

### 同一方法里两次 Example 查询，条件被并进同一条 WHERE（D4，`b12ccf8cc`）

MBG 生成的服务实现常见写法是一个方法里先后查两次：

```java
example06A.createCriteria().andTenantIdEqualTo(t).andCustNameLike(n).andStatusEqualTo(s);
result.addAll(mapper.selectByExample(example06A));
example06B.createCriteria().andTenantIdEqualTo(t).andCreateTimeBetween(a, b);
result.addAll(mapper.selectByExample(example06B));
```

旧判定 `rootedAtExample` 的兜底是「变量**类型名**以 Example / Criteria 结尾」，于是检索 06A 时把 06B 的两条也收了进来（真机 `[example06A:5]`，5 条里 2 条属于 06B），产物变成 `tenant_id` 出现两次、永不成立的谓词。

修法：只认同一个对象——根引用名等于实参变量名，或根变量是局部别名且其**初始化表达式**追溯回同一个 example 变量（`Criteria c = example.createCriteria(); c.andX()` 这种分步写法仍然收）；类型名兜底整条删除。真机随后读数 `(and/or=7 notRooted=5) [batch1203:2] -> criteria=2`。

### 混 kind 时区间条件少一个占位符（D5，`875c942f8`）

用户复验产物：`WHERE (create_time BETWEEN '11' AND tenant_id = ?)`。模型层三路对照（同一模板 + 手工注入 mock）：

| 注入 | 产物 | 占位数 |
| --- | --- | --- |
| 只有 `create_time between` | `create_time between ? and ?` | 2 |
| `tenant_id =` + `between` | `tenant_id = ? and create_time between ?` | 2（应 3） |
| `between` + `tenant_id =` | `create_time between ? and tenant_id = ?` | 2（应 3） |

根因是默认勾选档把整组 `<choose>` 强制成单一分支（多数票选 `singleValue`），而 `renderSql` 又把没勾的 id 全部覆盖成 false——区间条件因此走等值模板，`and #{criterion.secondValue}` 整段丢失。修法：M2 注入了元素级 kind 时，那四个 kind 分支不再接受开关强制，交给表达式按每条条件自己的标志求值；其它形态的 `<choose>` 语义不变。

### mapper 语句里选中文字后按快捷键误报未找到（D2，`85e09cab9`）

`Ctrl+F` 命中会顺手选中语句 id，此时按 `Alt+Shift+Q`，选择区里没有任何语句起始标签 → 直接提示「未在光标处找到可预览的 SQL 源」。现在 0 候选时回落到光标所在语句，多候选分发不变。

### 接口方法仍卡在占位符：命中的引用不等于可用调用点（D6，`bdc1f89ab`）

用户在日常 IDE 装本地包后复测 `mybatis-plus-demo` 的 `CtCustmanagerRelMapper#selectByExample`，仍是占位符：

```
[m2] trace …CtCustmanagerRelMapper#selectByExample scope=mybatis-plus-demo methods=1 noCallSite -> criteria=0
```

项目里明明有两个真实调用点（`CustmanagerRelQueryRepro.querySingle / queryOr`），而且**没有** `findCallSite empty` 那行诊断——说明引用是取到了，是「取到的引用上溯不到方法调用节点」之后被直接放弃。

根因：`ReferencesSearch` 对接口方法会把**实现的声明处 / 方法引用**一并返回，这类 ref 的 element 上溯没有 `PsiMethodCallExpression`；旧逻辑只取第一个 ref，撞上这种就整条失败。改为跳过不能当调用点的 ref 继续找下一个（仍是提前终止：找到第一个可用调用点就停），失败诊断补 `refsSeen=`，把「一条引用都没有」与「引用都不是调用」分开。

这条与 D1 是两个不同的失败面：D1 是 `Query.findFirst()` 恒返回空，D6 是第一个命中不可用。

### `example.or()` 的条件被拍成 AND（D7）

`CustmanagerRelQueryRepro.queryOr()` 是本轮最典型的复现：

```java
example.createCriteria().andCustIdEqualTo(42L);
example.or().andStaffLoginLike("song%");
mapper.selectByExample(example);
```

MBG 里 `createCriteria()` 与 `or()` 开的是**不同 Criteria**，`Example_Where_Clause` 用 `separator="or"` 连接，真引擎产物是 `WHERE ( cust_id = ? ) or ( staff_login like ? )`。此前 M2 把所有条件拍平成一条 Criteria，产物是 `cust_id = ? AND staff_login like ?`——占位符数量对了，语义错了（结果集从「或」变「与」）。

三处一起修：

1. 按 Criteria 分组：`createCriteria()` / `or()` 调用节点（或分步别名变量的初始化表达式）当分组键，`oredCriteria` 注入 N 条 Criteria；
2. 内层 `criteria.criteria` 不再绑成全局集合（原来外层每条 Criteria 都会把**全部**条件再渲染一遍，出现 `( a and b ) or ( a and b )`）；
3. 单词分隔符后补空格：`or` 与下一段的 `(` 曾粘成 `or(`。

用例 `M2两条Criteria_按or连接而不是and` 钉住；两次中间态读数（`( a and b ) or ( a and b )`、`or(`）就是这次修复的反向证据。

### 2026.3 打开数据源列表刷一条插件错误（D8）

用户日常 IDE 的日志：

```
java.lang.Throwable: Do not call `getChildren(null)`. Do not expand action groups manually.
  at DefaultActionGroup.reportGetChildrenForNullEvent
  at cn.song.mybatisplus.visualizer.execute.NewDataSourceEntry.buildNativeDriverActions(NewDataSourceEntry.kt:150)
  at NewDataSourceEntry.isAvailable$...
  at ChooseDataSourceTakeoverGroup.getChildren(ChooseDataSourceTakeover.kt:178)
```

`isAvailable` 挂在**菜单更新路径**上，却在那里用 `getChildren(null)` 展开原生驱动组；2026.3 把这种手写展开记为插件错误。现在可用性判定只做类可达判断（不在高频路径展开组），真正点击时才用带真实事件的重载取子项。

### 首次打开不再干等那次冷检索（M10 / M11，`2ef581793` / `34488db41` / `773421955`）

真机首次打开 `[open-perf] total=1689~2115ms`，其中 M2 冷检索独占 1628~2042ms；第二次起只有 30ms 装配。先把检索范围收到「mapper 所在模块 + 依赖它的模块」（语义不丢命中），实测**没有变快**——说明这 1.6~2s 是冷索引/冷 JIT 的固定成本，换作用域不解决。

于是把成本挪到用户还在读文件的时候：gutter 渲染时对 `select` 且 `parameterType` 以 Example 结尾的语句后台预取一次；带「失败记忆」（解析不到就本会话不再试）与「单条在途」两道护栏——首版没有护栏时，`countByExample` / `deleteByExample` 这类没有调用点的语句在 6 秒内被反复预取 4 轮，白烧检索还刷屏，该缺陷在本版内一并修掉。

实测（M11 带护栏）：

```
14:14:39 首次  [open-perf] total=104ms m2=1  → 弹窗 1346ms
14:14:43 再点  [open-perf] total=30ms  m2=0  → 弹窗 188ms
```
