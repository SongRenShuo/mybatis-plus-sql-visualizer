# 🎉 SQL Visualizer v2026.11.4-beta.1（内测版）

> 内测版留档：Gitee 抢先体验通道发行版，标签 `2026.11.4-beta.1`，附件 `mybatis-plus-sql-visualizer-2026.11.4-beta.1.zip`。
> 通道：**Gitee 内测**（Marketplace 侧按纯数字版本另行上传）。
> 基线为正式版 v2026.11.3，本内测版承载其后的全部增量；对外更新清单只保留最新一个 beta 版。
> 范围＝v2026.11.3 发行包之后的全部用户可见增量：Oracle 增强捕获的业务 SQL 断链修复，以及从 dev 回 port 到 master 的五项预览、方言与线程修复。

这一版两个主体。一个是用户真机报的 Oracle 问题：业务 SQL 一条都采不到，日志里只有 `select 1 from dual` 这类连接校验语句。根因在驱动句柄——Oracle thin 对外给的是包装器，而织入点在包内的物理语句，登记对象与执行对象从头到尾不是一个，查表自然永远落空。同一链路上还压着两处去重门缺陷，一条执行失败的语句会重复上报三次。

另一个是回 port。dev 分支上已经修掉、master 用户却还在踩的五项：打开预览就弹数据源选择器、改了方言并刷新后底部红条还报旧方言、以及三类线程违规——控制台数据源下拉在界面线程读 PSI、执行链在界面线程做目录查找、执行入口的写派发没有写资格。前两项是看得见的交互问题，后三类表现为 IDE 日志里一次「预览 + 执行」刷出二十来条点名本插件的 SEVERE，以及随之而来的界面卡顿。

## 🛠 修复

**Oracle 应用的增强捕获只剩连接校验 SQL，MyBatis 业务 SQL 一条不出（T-OracleWrapperRegistry，用户真机报障）**
- 现象：Oracle 工程里只打印 `select 1 from dual` 这类连接校验 SQL，Mapper 里的业务 SQL 一条不出；宿主 stderr 打「无登记 PS 执行被跳过 psClass=oracle.jdbc.driver.T4CPreparedStatement」
- 根因：Oracle thin 驱动对外返回的是包装器（`OraclePreparedStatementWrapper` / `OracleCallableStatementWrapper` / `OracleStatementWrapper`），prepare 面把 SQL 登记在包装器上，而 `executeQuery()` 的织入点在包内物理语句（`T4CPreparedStatement`）——登记对象与执行对象错位，查表永远落空。plain `Statement` 因为直接取首参、不依赖登记表，才「侥幸」可见，这也正好解释了现象形态
- 同一链路另有两处去重门缺陷：嵌套门把「进入过」当成「产出过」，内层盲区会把外层本来能出的 SQL 一起吞掉；同一帧「try 内 ATHROW + 处理器重抛」两条出口钩子让嵌套深度多减一次，一条失败语句重复上报 3 条
- 修复：prepare 面登记时按字段类型反射解一层包装，把内层物理语句一并登记，绑定参数与批串随之接回内层；嵌套门改为「真产出后才置位」；新增同帧重复出口去重
- 真机复验（Oracle Free 23）：ojdbc11 23.3 / ojdbc8 19.3 / ojdbc8 12.2 三驱动 7/7 全出且带参数；HikariCP 连接池 5/5；attach 挂载后新建的 PreparedStatement 连续 11 轮全出；失败 DDL 由 3 条降为 1 条

**打开预览就弹「选择数据源」列表，多源工程每次预览都要先选一次（T-PreviewPreparePick，用户真机报障）**
- 现象：配了 7 个数据源的工程，每次打开 XML 预览都自动弹一次数据源列表，右上角同时还写着「未绑定数据源」
- 根因：预览默认准备与显式执行走同一个 `chooseAndPrepare` 分支，弹窗分支不区分两者；多源又没有 last-used 记忆时必弹。这与该函数自己声明的「预览默认准备静默」意图正好相反
- 修复：预览准备阶段不再弹窗、不建链、不报错，面板保持未绑定灰字，等用户点「执行 SQL」时再选源；单飞门按 owner 正常结算，下一次执行不会排队到 60 秒超时。显式执行与「切换数据源」两个入口的弹窗行为不变
- 取舍：多源且无记忆时，预览控制台会保持未绑定、不预热。这是有意的，与 dev 侧同款语义

**改了 IDEA 方言并刷新预览后，底部方言红条仍按旧方言报冲突（T-DialectGateRenderDialect，用户真机报障）**
- 现象：面板顶部写「方言: MySQL（已绑定数据源）」，SQL 文本已按 MySQL 渲染，数据源也是 MySQL，底部红字却报「当前 SQL 按 PostgreSQL 渲染，所选数据源是 MySQL」
- 根因三条：闸门请求无条件优先取生成时固化的方言快照，而顶部决策会随绑定与刷新升级，两份方言事实分裂；XML 载体不能无损重渲染，被降级成「无法重渲染」，红字两边方言都取自陈旧值；「刷新」按钮只重渲染文本，既不重算决策也不更新渲染方言
- 修复：方言无关载体（XML 原文 / 纯文本，排除分页 LIMIT 行）的闸门渲染方言改取最新决策，与顶部状态行同源；模型 / 批量 / 分页载体仍按渲染事实判定，不做字符串替换冒充重渲染；点「刷新」按预览生成时的同一份证据重算决策，一致就清掉红条，仍不一致则报真实的两边方言。只在结果区没有执行结果时动作，不会覆盖执行结果与真实报错
- 方言冲突放行不拦执行的既有定案保持不变

**控制台数据源下拉每次刷新都在界面线程读 PSI（T-ThreadFix A）**
- 现象：一次「预览 + 执行」里，IDE 日志出现 1 条「'psi.File' is requested on EDT by ChooseDataSourceTakeoverGroup#presentation」与 8 条慢操作告警，界面同时有可感知的卡顿
- 根因：接管组覆写了 `update()` 与 `displayTextInToolbar()`，平台据此判定它不是默认 update，线程落回 EDT；而它逐字委托的原生动作自己返回后台线程，PSI 走平台预缓存
- 修复：声明后台线程更新，与原生动作一致；update 体仍只读写 Presentation，不新增任何 PSI / Swing 调用

**执行 SQL 时在界面线程做 PSI/VFS 目录查找（T-ThreadFix B）**
- 现象：每次执行 SQL，日志都刷出慢操作告警，栈里是 `findDirectory → isUnderIgnored → ensureIsUpToDate`，一次执行 9 条
- 根因：准备链第一次取控制台脚本模型会实例化临时文件的 PSI，平台内部要做目录查找；而方言映射会触发重解析把 PSI 作废，靠缓存躲不过
- 修复：挂控制台之后先到后台线程用读锁预热 PSI，再以写安全模态回界面线程续接准备；非界面线程调用方保持原同步语义；续接异常统一收口，准备门不会悬挂 60 秒。预热失败只是退回「取模型时自己建 PSI」的旧行为

**执行入口与方言映射的写派发不是写安全的（T-ThreadFix C）**
- 现象：执行 SQL 时日志出现 3 条 Write-unsafe 告警，指向控制台文档写入与方言映射重解析；写有被平台拒绝的风险
- 根因：执行入口用「任意模态」投递，方言映射从后台线程用省略模态派发——两者都不带写资格，而链内确实在改文档、改模型
- 修复：两处派发统一改为写安全的非模态投递，投递顺序、回调内容与异常路径都没动；方言映射仍保留原有有界等待与超时降级（模态弹窗存续期映射延后，预算内没落地就回落通用方言，执行照常）

- 插件 ID 与升级链路不变，v2026.11.3 用户可直接覆盖升级
- 设置项数量不变，无需重新配置
- 本版为内测版，版本号带 `-beta.1` 后缀；上架 Marketplace 时使用去掉后缀的纯数字版本

## ⚠️ 已知边界

- 三类线程修复的证据层级＝源码形态守卫 + 定向测试。发行包上「同样操作序列后 IDE 日志中三类 SEVERE 归零」还需真机复验
- 预览在多数据源且无记忆时保持未绑定、不预热，点「执行 SQL」时才选源。这是本次的刻意取舍
- 方言闸门只对 XML 原文 / 纯文本这类方言无关载体改取最新决策；模型、批量、分页载体仍按渲染事实判定，既有「不做字符串替换冒充重渲染」的结论不变
- 执行入口改非模态投递后，密码框 / 文件缓存冲突弹窗存续期间触发的执行，方言映射会延后；预算内没落地则回落通用方言，由平台自愈，SQL 渲染与执行本身不受影响
- Oracle 修复覆盖 thin 驱动的一层包装器；插件挂载前就已经存在的 PreparedStatement 仍按既有的一期限制记盲区
