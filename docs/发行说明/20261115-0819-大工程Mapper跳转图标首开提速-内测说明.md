# v2026.11.15-beta.1 内测说明（大工程 Mapper 跳转图标首开提速与自定义索引）

- 版本：`2026.11.15-beta.1`（内测，Gitee 抢先体验通道；Marketplace 不收内测包）
- 发布日期：2026-11-15
- 提交范围：`2026.11.14` 正式版之后到本版发行提交，T-GutterFirstOpenDelay 五刀与配套文档/测试共 23 笔提交
- 兼容 IDE：2024.3（243）/ 2025.3（253）/ 2026.2（262）/ 2026.3（263）

## 这一版有什么

- 冷打开 mapper XML 时，语句行上的跳转图标不再闪没、几秒后又回来
- Java 接口方法行的「跳到 XML 语句」图标在大工程刚打开头几秒不再长期缺席
- 根工程 scope 下（数千 mapper XML）Java→XML 图标不再被慢趟饿死
- mapper namespace 注册成自定义文件索引，索引期摊平成键，运行时一次查询毫秒级出答案
- 首次渲染图标时的三件后台预热延后到工程就绪之后，不再和索引重建抢资源
- Registry `sqlvis.gutter.warmDelayMs` 可调延迟，置 0 回到旧行为

## 按能力面展开

### 冷打开时 XML→Java 图标不再闪没（T-GutterFirstOpenDelay F1，`d3eb65079`）

用户 2026.11.14 正式版大工程实测的现象是：冷打开 XML 文件后预览图标晚约 5 秒才出现，图标出现后我方跳转图标消失、约 3 秒后再回来；IDE 重启等初始化完成后打开则没有这个现象。静态归因把「消失再重现」定在慢趟 `MapperXmlToJavaLineMarkerProvider.createMarker`：`resolveInterfaceMethod` 走 `JavaPsiFacade.findClass(namespace, allScope)` + `findMethodsByName`，图标是否显示原本只取决于「接口方法此刻能不能解析到」。索引未就绪或重建中的那一次解析会瞬时返回 null，而慢趟 pass 按整趟结果换装，就把先前已渲染的图标摘掉了；几秒后索引就绪，下一趟解析成功，图标又回来。

修法把判定改成四段：解析成功就产出并记入会话级正缓存（键 `namespace#id`，`ConcurrentHashMap.newKeySet`，无失效，取舍写进类头注释）；解析失败但正缓存命中仍照常产出（导航 handler 本就 null-safe 会再解析一次）；解析失败且落在 dumb 窗（F1-b，走 `isDumbProvider` 测试缝）乐观产出且不入缓存；其余失败不产出。不 catch `ProcessCanceledException`，不变式是「图标只在确认真没有时缺席，不在还没查到时缺席」——真没有对应方法的语句依旧不显示图标。`resolveInterfaceMethod` 本体未动。

定向读数 17 例全绿：`MapperNavigationLineMarkerProvidersTest` 15 例（含 F1 判定矩阵 4 例：成功入缓存 / 失败+命中仍产出 / 失败+未命中不产出且不污染缓存 / dumb 乐观产出不入缓存），`MapperXmlSlowResolveFailGuardTest` 接线守卫 2 例（源码扫描钉住「判定在 createMarker 解析失败分支上」，含修复前、先缓存后解析、无解析调用三种漂移自证）。反向验证摘掉「失败但缓存命中仍产出」分支复跑，17 例 2 红——缓存命中用例 `NoSuchElementException`（`.single()` 空即图标被摘形态，缺陷本体复现）＋接线守卫 `AssertionError`（wiring=false）；Edit 恢复分支后复跑 17 例 0 红、BUILD SUCCESSFUL。实施期还订正了一处夹具事实：`BasePlatformTestCase` 夹具方法体跑在读操作内，`waitForSmartMode` 会断言「Don't invoke waitForSmartMode from inside read action in dumb mode」，矩阵用例因此不能依赖夹具真实 dumb 态，改走 `isDumbProvider` 测试缝。

边界：预览图标晚到那 5 秒（S1）是冷打开 dumb/扫描窗加平台快趟 pass 多波次排程，provider 本体 O(1)，不修；F2 落地后冷窗 CPU 竞争下降，S1 有望自然缩短。消失重现的显形窗在沙盒里没有自然复现过，行为由单测矩阵、接线守卫与反向验证兜底。

### Java→XML 图标不再长期缺席（T-GutterFirstOpenDelay F1'，`6bc12e9c8`）

F1 上线后用户报 `CustChannelMapper.java` 跳转图标不显示。沙盒复现实锤是全局而非文件特异：`CustChannelMapper.java` 和 `CustAddressMapper.java` 全部方法行都没有图标，daemon 重跑（敲空格再撤销）立刻回来。机制与 XML 侧同源——大工程刚打开头几秒，慢趟首跑 `MapperXmlLocator.locate` 时 XML 文件清单还没就绪，这次「暂时的失败」被当成结果记住，而 daemon 不会自动重算慢趟，图标就一直缺席到文件改动触发重分析。XML 侧有 F1-b 的 dumb 乐观产出兜住，Java 侧没有这层兜底。

修法与 F1 同构，改 `MapperJavaToXmlLineMarkerProvider.createMarker` 的四段判定；成功入的是**共享正缓存** `resolvedStatementKeys`，XML 侧确认过的语句双向受益；`isDumbProvider` 测试缝移入 companion 双侧共用。定向 31/31 绿（矩阵 19＝原 15＋Java 侧 4；接线守卫 4＝原 2＋Java 侧 2，提取器泛化到第 N 个 `createMarker`、Java 侧锚 `MapperXmlLocator.locate(`；元守卫登记 `javaFailureBranchWiring`）；反向摘分支恰红 3（矩阵 2＋守卫 1）后恢复复绿。沙盒目视复验：修复包暖开 `CustChannelMapper.java` 全方法行图标在位，首截图 10 秒未显是首次全项目 XML 清单构建成本，属既有缓存链，不在本刀范围。

### 根工程 scope 下图标不再饿死（T-GutterFirstOpenDelay F1''，`81884a539` / `588d64604`）

真机实证（用户沙盒 demo 根工程）：scope 约 4841 个 XML（含 2042 个 `target/classes` 拷贝），`CustChannelMapper.java` 图标长期缺席；单工程约 2100 个 XML 尚可自愈，根工程翻倍即失守；daemon 重跑即回，实锤「结果固化」形态。根因是 `MapperXmlLocator` 的清单首扫——4841 个 XML 逐个 PSI 解析 rootTag——在慢趟 ReadAction 内被 JPS 写盘反复以 `ProcessCanceledException` 取消，慢趟饿死，图标永不落地。

`81884a539` 把清单构建移出慢趟关键路径：无可用槽时只踢后台异步构建（nonBlocking 可取消 `expireWith` + `coalesceBy`）并立即返回 null，不写 MISS（「还没查到」不固化为「真没有」）；构建落地后一次性 restart daemon 重跑；TTL 过期改为 serve stale 加后台刷新（stale-while-revalidate，图标不因刷新缺席）；单测缝 `asyncListBuildForTest` / `restartAnalyzerForTest` 保住单测模式同步的旧语义。它与 F1' 互补：F1' 管「失败分支不缺席」，这一刀管「清单本身别压死慢趟」。

用户接着反馈根工程下图标出现速度仍慢，`588d64604` 做续刀：清单扫描从「4841 个 XML 全量 PSI 解析 rootTag」改为「VFS 原始头扫 16KB 提取 `<mapper>` 的 namespace」，慢趟定位只对 namespace 命中的 1~2 个候选付 PSI，头扫 4841×16KB≈2~3s 且全在后台；TTL 5s→30s（serve stale 下新增文件至多滞后 30s）；异步构建加 `inSmartMode` 防 dumb 期空清单落地。覆盖面没有收窄：头扫窗内没看到 `<mapper` 但文件名含 `Mapper` / `sqlmap` 的，回退一次 PSI 取根标签 namespace，覆盖根标签前超长注释这类头扫盲区，iBatis sqlMap 与旧口径一致不收入（独立链负责）。顺带修了测试隔离——`MapperXmlLocatorTest` 加 setUp/tearDown 强制清静态槽与旗标，治的是「单跑绿、全套件红」（`test命中` 被前序用例的静态槽状态毒化）的跨用例污染。

读数：前刀定向 56/56 绿（locator 13/13，新增异步 2 例钉住「无槽 null＋MISS 不污染＋落地 restart 恰一次」「过期槽服务旧值＋刷新恰一次」；导航 19、守卫 4、元守卫 8、BannedApi 12）；续刀定向 60/60 绿（locator 17 ＋ 导航 19 ＋ 守卫 4 ＋ 元守卫 8 ＋ BannedApi 12，新增头扫内核纯单测 2 例＋盲区兜底＋iBatis 边界共 4 例）。

### 改用自定义文件索引替换清单状态机（T-GutterFirstOpenDelay F1'''，`7dc6c1c73`）

前三刀都在补同一个坑：数据源不是索引，运行期全扫清单、TTL 单槽、pending→restart 状态机本质都是自建缓存的补丁。子智能体反编译调研 `docs/调研报告/20261115-0202-MPJ跳转实现反编译调研-调研报告.md` 给出 Top1 可借鉴点：MyBatisCodeHelper-Pro 3.6.8+2321 把 mapper XML 的 namespace 在**索引期**摊平成键（自定义 `ScalarIndexExtension`，索引 ID `MybatisCodeHelperIndexer6`，version 7，注册在 `fileBasedIndex`），运行时一次 `FileBasedIndex.getContainingFiles` 就是答案，失效全交平台增量管理，零 TTL、零自建监听器。

采纳前先核屏障风险：平台 `product.jar/META-INF/plugin.xml` 实证 `<extensionPoint name="fileBasedIndex" dynamic="true"/>`，不是动态卸载屏障，插件热更新（免重启装）不受影响——这一条推翻了既有记忆里的屏障清单，以平台声明为唯一权威。后续 `042cf6572` 补跑 verifyPlugin（243/253/263）BUILD SUCCESSFUL，验证器输出「Dynamic Plugin Eligibility: Plugin can probably be enabled or disabled without IDE restart」，实证在册。

实施：新建 `log/MapperNamespaceIndex`（`ScalarIndexExtension`，键＝根标签 namespace，输入过滤器＝XML，`dependsOnFileContent`，version=1，提取内核＝原头扫正则喂 `FileContent.contentAsText` 全文本）；plugin.xml 注册 `<fileBasedIndex implementation="cn.song.mybatisplus.visualizer.log.MapperNamespaceIndex"/>`；`MapperXmlLocator` 瘦身重写为「索引查询＋PSI 校验」，单槽 TTL、头扫异步、missedWhilePending、restart 整套状态机退役（该文件删 266 行、加 37 行，净减 229 行）；provider 层 F1' / F1-b 的失败分支兜底保留，索引未就绪窗口由它们接住。正确性闸门仍在 PSI 侧——根 namespace＋id 精确匹配。既有 TTL / 缓存 / 异步机制测试随机制退役，行为面保留。

读数：定向 84/84 绿（locator 9 ＋ 导航 19 ＋ Gate 11 ＋ 守卫 4 ＋ Ibatis ＋ 元守卫 8 ＋ BannedApi 12 等），新增索引内核纯单测 2 例。调研报告 §五的收益预估是 4800 XML 下 Java→XML 首跳从「秒级全扫（头扫 2~3s）」降到毫秒级，冷启动图标随索引就绪自然出现。边界：索引 version 升级触发一次全量重索引；`dependsOnFileContent=true` 让每次 XML 编辑多付一次该文件的单文件 PSI 解析；dumb 期查询仍会等索引，F1-b 乐观产出语义原样保留。

### 首渲染预热延后，不再和索引重建抢资源（T-GutterFirstOpenDelay F2，`7ad1d1a5d`）

首次渲染图标时会顺带在后台踢三件预热：`MbgExampleCallResolver.prefetch` 调用点预取、`warmCompletionContextOnce` 补全上下文、`PreviewAssemblyWarm.warmOnce` 预览装配。立项沙盒（2026-11-14 21:40 会话）实测的首开 BGT 重活清单：反查索引一次建成 `tables=1012 耗时=3337ms`，跨 ORM 回补完成 `tables=8688 耗时=15017ms`，`assembly warm done in 17095ms`，`resolve=1736ms`，dumb 双窗（扫描 72287 文件触发二次 dumb）。CHANGELOG 的口径即「实测首开后台扫描累计 3.3s + 15s」——冷打开时它们和索引重建挤在一起，既拖慢图标落地，也让上面那个闪没更容易发生。

修法：新增 `ui/gutter/GutterWarmScheduler`，把 `getLineMarkerInfo` 原三处直踢收拢为 `GutterWarmScheduler.onGutterFirstRender(tag)` 一个调度点；判定内核抽纯函数 `shouldKickNow(dumb, msSinceProjectSmart, delayMs)`（dumb ⇒ 不踢；delay≤0 ⇒ 立即踢；到点 ⇒ 立即踢；未到 ⇒ 延迟派发），延迟派发走 `AppExecutorUtil.getAppScheduledExecutorService().schedule`（243 API 实证：同仓 `MbgExampleCallResolver.kt:554` 在用＋IU-243 sources jar 反查 `getAppScheduledExecutorService(): ScheduledExecutorService`；整数 Registry 读数 `Registry.intValue(key, default)`，util-8.jar javap 实证）。延迟锚点是本会话内最近一次观察到工程 smart 的时刻（per project，渲染遇 dumb 即清锚点重起算，实际延迟 ≥ 配置值，方向保守）；到点复查「工程未关、已 smart、文件仍在」，仍 dumb 就放弃本轮等下次渲染。每文件一次的调度去重按 VirtualFile.url，踢出或放弃即撤销，三链自身每文件去重不动。Registry `sqlvis.gutter.warmDelayMs` 默认 5000，0＝旧行为首渲染立即踢（回退通道，且不做 dumb 预检，三链自带 dumb 检查保持原语义）；plugin.xml `<registryKey>` 以纯英文 description 登记，BundleParityGuard 对 registryKey 族整元素豁免。

读数：定向 `GutterWarmSchedulerTest` 7/7 绿（纯函数矩阵 4 例＋接线守卫 3 例）、`PreviewAssemblyWarmTest` 7/7 绿（零改动，其接线守卫断言 `PreviewAssemblyWarm.warmOnce(` 在 provider 源码内，`kickFileWarmers` 保住了这一点）。反向验证红/绿两读数：红（临时把 `getLineMarkerInfo` 改回直踢绕过调度器）`GutterWarmSchedulerTest > 首渲染预热必须经调度器 FAILED — java.lang.AssertionError: getLineMarkerInfo 必须经 GutterWarmScheduler.onGutterFirstRender 调度（F2：三链合并为一个调度点）`（`GutterWarmSchedulerTest.kt:90`）；绿（还原后 `git diff` 为空再跑）7/7 ＋ 7/7、BUILD SUCCESSFUL。

主控真机验收（`6d9cf5bd2`，runIde IU-2024.3.7.1 cust-big-demo，合并态包 `0dd0aef52`）四轮：F1 图标不闪没——冷开 41 帧逐秒两轮均「预览图标先落、MP 图标后落、双图标全程稳定」，无「双图标→单图标」回退；S1 形态——预览图标首渲染即落、MP 图标 +2~3s，暖重开 <1s 双图标齐（日志 159/393ms）；F2 延迟生效——对照轮（5000）kick≈smart+8~9s，决策轮（`ide.general.xml` 置 30000）kick≈smart+34s，前三轮 8~9s 形态消失，回补／装配链全部落在延迟踢出窗内，暖重开立即踢（159/393ms），延迟／立即两分支真机均证；噪音 0 ERROR / 0 SlowOperations；回退通道 Registry UI 显示键＋默认 5000＋自定义描述渲染正常，`0=旧行为` 由单测钉住。验收期还记下一条平台事实：给沙盒预设 Registry 值，手写 `config/options/registry.xml` 243 一律不读，该版本 Registry 持久化在 `ide.general.xml` 的 `Registry` 组件（`<entry key value source>` 形态），UI 改值后强杀进程也不落盘；另有一处夹具污染（冷窗口期打字落进 `CustAddressMapper.xml`）已 undo 加 `git checkout --` 恢复并复核干净。
