## 这一版有什么

### 预览终于能说清「这句话为什么是 UPDATE」（T-PreviewStmtTypeScope M1/D-3，`1b3af3ec5`）

现象：用户拿一段 `LambdaQueryWrapper` 查询链点预览，出来的是 `UPDATE`；而同一段代码在 `selectOne(wrapper)` 处点又变成 `SELECT`。

根因：判型只看「这个 wrapper 变量上出现过哪些消费方法名」，且扫描范围是**该变量的全部引用**——同一个变量先在别处交给 `update(entity, w)`、重新赋值后再交给 `delete(w)`（真实工程常见复用写法）时，判型与用户正在看的语句脱钩，面板又不说明依据。

修法：meta 行直接写出依据（「类型依据: `remove()` 消费（第 235 行）」），悬停列出该 wrapper 上的全部消费调用；同一 wrapper 出现两种以上用法时，工具栏出现「语句: UPDATE」入口，弹层列出全部档位（带方法名与行号）按需切换，切换即按强制档位重算。

### 判型作用域收紧：跟着光标所在语句走（D-2，同版）

消费证据按「方法名 + 行号 + 语句区间」记录，再从锚点位置选一条：优先锚点所在语句内的消费，其次锚点之后最近的一次；「声明与消费分离」（`w = new …; service.remove(w);`）照旧判 `DELETE`。

### 在重新赋值那一行点预览，条件与消费不再全丢（D-B1/D-B2，`3731e2eed`）

现象：`w = new LambdaQueryWrapper<>();` 这一行（重新赋值）点预览，得到无 WHERE 的 `SELECT`。

根因：赋值表达式右侧的 `new` 不在任何变量祖先里，定位器落到「内联 new」路径，而那条路径只收赋值表达式内部的链——后续另起语句的 `w.eq(...)` 与 `delete(w)` 全被丢掉。

修法：赋值锚点按**目标变量**走变量路径；同时重新赋值即分段，锚点在哪一段就只收那一段的条件（赋值前是声明段的 `user_id / status`，赋值后是 `order_no / user_id`），DELETE 不再串进上一段的 `status`。

### 实体更新的 SET 参数可以逐列填（D-C，`90e494b33`）

现象：`update(entity, wrapper)` 的预览里，SET 六列被同一个输入框一次性填成同一个数（`order_no = '1', user_id = 1, …`）。

根因：SET 各列占位符共用一个来源 `?`，面板按来源去重后只剩一行 `#?`，填一个值命中全部。

修法：每列各有来源（`patch.order_no` …），一行一列，填哪个改哪个；取不到实体实参文本时回落「实体.列名」。

### 名字叫 remove/delete 的普通集合调用不再误判删除（M3，同版）

`list.remove(wrapper)` 这类 JDK 容器上的同名调用此前按方法名就改判 `DELETE`。现在叠加接收者负门：接收者类型（含父链）落在 JDK 容器/常见非 DB 类型集合内即不算 SQL 消费。

### 方言实在推断不出来时会主动说一声（T-NotifyTune 券 A）

智能推断既没有数据源、项目配置、依赖坐标也没有语法特征可依时，预览一直在按 MySQL 兜底渲染，但用户不开预览就看不到。现在打开含 SQL 的文件时后台算一次方言决策，仅在「确实没有方言可依」时弹一次提示，动作「去设置方言」定位到插件方言行、「本项目不再提示」按项目永久抑制。

### 「已捕获到第一条 SQL」的引导改成每台机器一次（T-NotifyTune 券 B）

原来那条提示只是「每个 IDE 进程一次」，重启 IDE 或反复拉沙盒就会再出现。现在持久化记忆，且三个场景直接跳过：日志窗本来就开着、这次捕获是自动展开、引导窗口已可见。

### 预览的 INSERT 列名提示让位 IDEA 原生（T-PreviewInlayNativeYield，`5f054e4c8`）

IDEA Ultimate 自带的「SQL 列名」inlay（`INSERT … VALUES` 一项默认开启）与本插件预览面板的 INSERT 目标列提示逐字重叠，每个值前出现两枚列名。现在检测到原生在显示时本插件让位，原生关掉或不可用时我方照常生效。

### 两处全局动作接管不再刷平台 Keymap 告警（T-CommentShortcutKeymap，`3ce4b7c54` + `e00e779b5`）

现象：真机日志里每关一次预览面板刷一条 `ShortcutSet of global AnActions should not be changed outside of KeymapManager`。

根因：预览编辑器接管行注释（`Ctrl+/` 插 `--`）与控制台「选择数据源」动作组都是 `ActionManager.replaceAction`，而平台每次注册动作都会回填 `ProxyShortcutSet`，`AnAction.setShortcutSet` 于是判定「全局动作在 KeymapManager 之外被改快捷键」。

修法：换入/换回前先把目标动作的快捷键集合置为 `CustomShortcutSet.EMPTY`（平台唯一豁免条件）再换；键位仍由平台按 keymap 惰性解析，`Ctrl+/` 行为不变。首版只修了一处，按真机日志的调用点归因发现第二处后一并修掉，并把源码守卫升级为**全树扫描**（`src/main` 只允许共享助手出现 `replaceAction(`）。

## 验证与边界

- 定向：`PreviewStmtTypeScopeTest` 15、`EditorCommentShortcutsTest` 17、`ConsumerMethodsCoverageTest` 33、`WrapperLocatorTest` 31 等，合并态 159/0/0；反向探针五个（判型负门、分段、SET 来源、单文件守卫、全树守卫）各自恰红。
- 真机：沙盒实测同一 wrapper 的三处锚点分别得到 `UPDATE` / `DELETE` / `SELECT`；SET 逐列填值；关面板后平台 Keymap 告警归零。
- 已知边界：判型依据的默认落点仍是启发式（锚点在两条消费之间时取最近一条），要换档用「语句」下拉；实体 SET 仍是「非主键全列」近似（运行时才知道哪些字段非空）。
- 全量门禁走 CI（push-test 分片 + 发行轮 gate），本地只跑定向。
