# 开发流程：夜间复盘协议

> 来源：T-MagpieGems 后续（2026-10-24 立制），机制取自 magpie `LESSONS.md` 的夜间复盘
> （其头部声明 "Each night the day's commits are reviewed for what had to be fixed again,
> what shouldn't have merged and what was verified too thinly"），按本仓单机单代理环境降级适配。
> 配套资产：[`LESSONS.md`](LESSONS.md)（账本本体）、[`code-standards.md`](code-standards.md)（升级去向）、
> [`开发流程-派活与验收清单.md`](开发流程-派活与验收清单.md)（白天链路）。

## 一、目的与产出

每天对当日的提交与验证记录做一次无人值守复盘，产出三样东西：

1. **当日量化日志**（写在 LESSONS.md 顶部日期段）：几个 commit、跑没跑门禁、几处返工、错在哪类；
2. **新教训**（按 LESSONS 四段式入账：规则一句话 → hash 级证据 → 正反例 → `Seen N×(日期)`）；
3. **水位线推进**（`reviewed-through` 注释指向复盘过的最新 commit）。

复盘**不产出**：代码改动（零写集）、issue 批量立项（发现候选只登记不立项，候选池规则见竞品轮报告 §编号承接）、对既有教训的重写（只追加 Seen 与日期）。

## 二、运行环境与节奏

| 阶段 | 触发 | 说明 |
|---|---|---|
| 试运行（前两周） | 每日收口后**手动**跑一次本协议 §四提示词 | 验证量化日志与教训格式真的有用，防止建了机制没人看 |
| 常态 | ZCode 定时自动化（CronCreate）每日 23:30，或闲时任务（OffPeakCreate） | 提示词全文复制进定时任务，不用改写 |
| 人工审 | 次日早上 5 分钟，清单见 §五 | 复盘产出是**草稿**，人过目后才算入账 |

多车道日（多个工作树/多会话并行）：复盘范围=主仓 + 各登记在册工作树的当日提交（`git worktree list` 遍历）；工作树未登记的改动不审（登记表纪律见 docs/MEMORY.md 协作节）。

## 三、水位线机制

- 位置：`docs/LESSONS.md` 第 2 行 HTML 注释：`<!-- reviewed-through: <sha> (<yyyy-MM-dd HH:mm> +0800) -->`；
- 语义：**该 sha 及之前的提交已审**；复盘从 `git log <sha>..HEAD` 开始消费；
- 推进：每轮复盘结束时更新为当前 HEAD（多仓时取各仓各自 HEAD，主仓水位线为准、工作树在日志段点名）；
- 回退保护：若复盘中途失败（见 §六），水位线**不推进**，次日晚重跑同一区间。

## 四、复盘提示词（定时任务/手动复制即用）

```
你是本仓的夜间复盘代理（协议：docs/开发流程-夜间复盘协议.md）。只读复盘，
零写集——唯一允许写入的文件是 docs/LESSONS.md（追加内容），不改任何代码。

【输入】
1. 水位线：读 docs/LESSONS.md 第 2 行 <!-- reviewed-through: ... --> 注释取 sha；
2. 提交流：git log <sha>..HEAD --format=fuller（含 body 的验证记录），
   多工作树时对 git worktree list 逐树取当日提交；
3. 既有教训：docs/LESSONS.md 全文（判断复发=追加 Seen，新教训=新增条目）；
4. 当日门禁读数：各 commit body 里登记的定向/testFast/反向读数（commit body 是
   验证记录的权威载体，见 code-standards S8；body 没写验证记录的提交要点名批评）。

【步骤】
1. 消费提交流，按四类分桶：
   a) 返工——同一问题被二次以上修复（fix 的 fix；diff 里修同一函数/同一守卫）；
   b) 验证过薄——body 无验证记录 / 只报退出码不报用例数 / 反向探针缺失的守卫类改动 /
      声称「全量绿」但当日无全量门禁读数；
   c) 不该合的——越过写集的提交 / 编译不过就提交（LESSONS L11）/ 门禁读数与产物不符；
   d) 教训复发——提交形态命中 LESSONS 既有条目（追加该条 Seen，同日多次只算一天）。
2. 写当日量化日志（LESSONS.md 顶部新建日期段）：
   - 第一行数据：X 个 commit / Y 个工作树 / 门禁跑了什么（定向/testFast/全量，各几处）/
     返工 Z 处 / 点名批评的提交（短 sha + 一句话）；
   - 之后每类一段：现象 → 证据（短 sha）→ 判定。
   - 当日无提交：只写一行「当日零提交，水位线推进至 <sha>」，不硬凑教训。
3. 新教训入账（只在 a/b/c 类里有可提炼规则时）：四段式——粗体祈使句规则 /
   hash 级证据（提交号或 文件:行）/ 正例与反例 / Seen 1× (今日日期)。
   规则必须可执行可复核；复述既有条目不算新教训（去追加 Seen）。
4. 升级检查：任何条目 Seen 达 3 个不同日期 → 整条搬进 docs/code-standards.md 对应节，
   LESSONS 原位置换成指针（升级区）。S 条目编号顺延。
5. 推进水位线为当前 HEAD，写时间戳。

【硬条款】
- 只写 docs/LESSONS.md（+升级时的 docs/code-standards.md）；碰 src/ 立即停机报告；
- 教训无 hash 级证据不入账；推测性结论（"可能/大概"）不入账，写入日志的「待核实」段；
- 当日没有问题就是没有问题——零教训日是正常日，禁止为产出而产出；
- 文档里承认的缺陷（如某计划写「目前没有 X」）→ 在日志里点名并标注「待开 issue」，
  不得自行开 issue 或改计划；
- git 命令只读（log/show/diff），禁 checkout/reset/commit；
- 卡住（合并冲突态、工作树脏、水位线 sha 不存在）→ 停机，输出失败原因，不推进水位线。

【输出】
复盘摘要（给早上人审用）：当日数据一行 / 新教训 N 条（各一句话）/ Seen 追加 M 条 /
升级 K 条 / 待人裁决事项（含「待开 issue」清单）。
```

## 五、早上人审清单（5 分钟）

| # | 看 | 动作 |
|---|---|---|
| 1 | 复盘摘要的数据行与点名批评 | 认同 → 留；不认同 → 当天改回（复盘代理可能误判） |
| 2 | 每条新教训 | 入账前人工过目：规则是否可执行、证据是否成立；弱条删除 |
| 3 | Seen 追加 | 抽查 1 条复发判定是否真是同型 |
| 4 | 「待开 issue」清单 | 人来开 issue / 拍板进候选池 |
| 5 | 升级条目 | 确认搬到 code-standards 的措辞（S 条目是硬标准，措辞要求最高） |

## 六、停机条件与告警

复盘代理在以下情况立即停机并输出失败原因（不推进水位线）：工作树有未提交脏改动且无登记在册说明、水位线 sha 在当前分支不存在（rebase/强推过）、git 命令连续失败、LESSONS.md 出现合并冲突标记。

告警通道（二期）：复盘结束推送 webhook（企微/钉钉）一条「完成摘要 + 停机原因」；一期先靠次日早上的摘要文件本身。

## 七、与既有体系分工

| 载体 | 收什么 | 不收什么 |
|---|---|---|
| `LESSONS.md` | 可执行规则（四段式）+ 每日量化日志 | 事件叙事、排查过程 |
| `docs/经验总结/` | 事件叙事与完整排查（按事件一篇） | 规则条目 |
| `docs/code-standards.md` | Seen≥3 升级的硬标准 + 机制导入 | 新教训（先进 LESSONS） |
| 项目 memory | 任务终态与跨会话状态 | 规则本体（链接到 LESSONS） |

一个事实只活在一处，其余链接（magpie 子系统文档三原则的同款纪律）。
