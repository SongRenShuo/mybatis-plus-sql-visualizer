2026-09-22 同一个排查任务里，用户先发「限制生成开发计划文件」，紧接着又发「先生成开发计划文件」。两次口径合起来的实际规则是：**不要自动、无必要地为每条发现新开 `docs/开发计划/*.md`；但用户点名要计划文件时，先出计划文件、等确认再动手实施**。前一条别读成「禁止」——我第一轮就是这么读的，随后被下一条推翻。

**Why:** 用户没有展开理由。可观察的事实是 `docs/开发计划/` 单日多份、每份都要按模板写全章节，成本高；同时用户认「先计划后实施」这道闸门本身（所以会主动点名要计划文件）。

**How to apply:**
- 默认不新建计划文件：发现与读数写进**既有**文件——`docs/验收文档/20260920-待分析问题清单.md`（P 编号条目）、对应的实测/验收报告（正文 + 变更记录）、`docs/变更记录.md`；要动代码就直接改码 + 补测试。
- 用户说「立项」「生成开发计划文件」时：命名 `docs/开发计划/{日期}-{时分}-{功能名}-开发计划.md`，章节照最近的同类计划（背景与依据 / 目标与非目标 / 方案 / 验收标准 / 风险 / 实施顺序 / **待验证前提** / 实施记录），写完**停下来等确认**，不要顺手开始改码。
- **同句预授权例外（20261005 T-MergeMasterToDev 定例）**：用户同一条指令里写「先生成一份开发计划文件**再实施**」时，计划写完落库后**直接按计划实施，不停等确认**——授权已含在同句里；「写完停等」只适用于只点名要计划、未同句授权实施的情况。自主运行模式下更应如此（停等=阻塞无人应答）。
- 「待验证前提」是硬要求：把推断的机制、平台行为、落点显式列出，实施者先证伪再动手（见 [[project-doc-conventions]] 与全局 AGENTS.md）。
- 只对用户点名的任务出计划文件，不借机给在册的其他问题批量补计划（见 [[project-pending-plans]]）。
- **落库范围可以比点名的那一件宽（20261010 T-RepoLayout 实证）**：用户点名一件事（「`gitee-token.json` 这类放 `.local/`，记得同步记忆和文档」）时，把**此前同会话里已经做过的那一轮分析结论一并写进同一份计划**是用户认可的——他随后明确要求「前面的项目目录结构分析相关调整也记得更新到开发计划中，开发计划名字可以适当调整」，我据此把计划从单点「本地凭据迁移」重写为更宽的「仓库目录结构优化」，并把发现按 **A 本次实施 / B 本次顺带 / C 单独立项 / D 维持现状** 四档归档（避免把大改动夹带进本次范围）。**推论**：计划文档的范围由「用户点名的落点 + 本会话已产出的相关分析」共同决定，命名跟着范围走；发现项宁可分档登记，也不要么夹带实施、要么丢在会话里。
- **计划落地另一条被点名的动作（同轮）**：用户看完计划后说「现在立项或者更新之前的开发计划」——C 档发现项要**真的变成计划文件**（新立项，占号前先 grep 实测 O/R/D/V 四系最高号）或**追加进既有计划**（同轮把「巨型文件拆分」作为第二轮 T-M53-II 追加进 `20260826-…-开发计划.md`，并更新其状态头），而不是留在待办清单里。同时**实测推翻的条目要销案并写依据**（同轮 C⑤「Java 残留 3 文件」经读三文件头注释证伪为「有意保留 Java」，销案而非立项）。
- **给拆分/重构类计划加红线（20261010 用户令）**：用户会要求把验收口径写死为「不允许出现回归、不允许影响既有功能」——落成**一票否决**式红线 + 「拆前拆后读数三者一致（用例数/通过数/失败数），不是只看拆后绿」，并配 §验收清单条目。见 `docs/开发计划/20260826-巨型文件拆分降低token消耗-开发计划.md` §红线。
