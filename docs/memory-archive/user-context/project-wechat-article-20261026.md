原文：「最近 7 个版本里『修』108 条、『新增』85 条。修比加多，而且多半是『这条 SQL 我算错了』：达梦的自增列包装漏了、openGauss 的 upsert 按 PG 族推定推错了、执行计划取源在多模块工程里串到兄弟模块的库上」。**数字本身准确**（CHANGELOG 逐版计数 Fixed 108 / Added 85），但三个转化视角的问题：

1. 数字没有参照物——读者不知道 108 条对两个月/16 版算多算少，容易往「问题很多」想；
2. **「修比加多」是危险信号**——对已用用户是「维护积极」，对还没装的读者是「这工具还不稳」，正落在转化漏斗最不该给的位置；
3. 三个 bug 太术语化（自增列包装/PG 族推定/取源串库），没踩过的人无感，踩过的人也不会因此去装。

重写方向：保留「16 个版本」，把「修 N 条」换成具体反馈，bug 一律改写成**现象描述**（「识别不了前缀的列名」而非「自增列包装漏了」），并补一句修复过程的不体面细节（先复现三个版本确认不是新改坏的，才挖到根因）。落点从「我们很努力」换成「你报的问题会被认真对待」。详见 [[feedback-marketing-copy-style]]。

## 写稿时核过的事实（可直接复用）

版本口径：**用户本人把正文改成「发了 17 个版本，还在迭代」并明示「按照 17，这是我改的」**——不要按实测数把它改回去。实测对照：Marketplace API `/updates` 当前返回 **16 个已上架版本**（最新 2026.10.28），git tag 33 个（含 beta 与未上架）。IDEA 2024.3+（`since-build 243` 无上限）；11 方言；11 个 MCP 工具**全部声明 `readOnlyHint = TRUE`**（grep 计数 11）；21 条性能规则；调用栈 12~64 默认 24、栈底固定保 8 帧业务侧；慢查询阈值默认 1000ms；同结构徽章阈值 `TEMPLATE_BADGE_MIN_COUNT = 3`（演示图是 5 条因采到 5 条）；CHANGELOG 最近 7 版「修」108 /「新增」85 /「变更」24 条。

EXPLAIN 验证程度分级别拔高：MySQL/MariaDB/PostgreSQL/KingBase/DM/openGauss/Oracle 真机通过，H2/SQLite 引擎级单测，OceanBase 官方文档级（真机留账），SQL Server 官方文法落地**真机未验证**。
