## 现行口径（20261028 用户令，此后一律按此执行）

用户原话：「**我希望完全不阻塞 后台执行完成后通知主控即可**」「**不阻塞的话可以一边等一边继续做其他事情**」。

标准作业三步，不做第四步：

1. **长命令（>30s：gradle、全量测试、mvn、runIde、依赖下载）一律 `Bash(run_in_background=true)` 发起**，输出交给工具自建日志（不要自己再套 `> file 2>&1` 把进度藏掉）。
2. **发起后同一回合立刻做不依赖该读数的事**：写开发计划/验收记录/CHANGELOG/发行说明/changeNotes/索引行、核产物 zip 与 sha256、准备提交信息文件、读 demo 仓配置、复核对齐性。实在没有可做的，直接结束回合。
3. **读数只在 `<task-notification>` 到达后取一次**（`tail` 日志一次或直接读 `build/test-results/**/TEST-*.xml`）。

禁止的第四步（三种等价违规，均被用户多次点名）：

- `sleep N; grep/tail 日志` —— 哪怕主观上只是「等一个合适的读日志时机」也算；
- `TaskOutput block=true` —— 与 sleep 同级；需要结果就等通知，不要挂起主控；
- 给前台命令设长 `timeout` 来「等」。

**Why**：阻塞等待 = 主控假死、用户看到会话卡住；等待期间本可推进的独立工作全部停摆（20261028 实测：一轮里反复 sleep/TaskOutput 把一小时的活拖成几小时，而当时该写的计划与发行文档都还没动）。

**How to apply 补充**：进度脚本类需求让它在用户自己的前台终端跑，代理后台命令不要再重定向一层；被 `TaskStop` 的后台命令不等于子进程真退出（gradle wrapper/daemon 仍持锁），处置时先确认进程消失再重发。

**How to apply**：
- 后台任务发起后直接继续：做不依赖该结果的其它工作（文档/记忆/独立验证），或直接结束回合——任务完成时系统会自动通知，届时再处理结果。

- 前台只保留秒级快命令（git status/grep）；任何 >30s 的命令一律 run_in_background。

- 需要看长任务日志时，让后台命令把输出**重定向到固定文件**（如 `> /tmp/xxx.log 2>&1`），完成通知后一次读取，而不是中途反复 grep。
