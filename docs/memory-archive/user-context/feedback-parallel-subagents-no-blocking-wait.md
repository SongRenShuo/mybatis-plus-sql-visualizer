2026-10-05 用户在 T-JpaDeleteWhereGuard 实施轮的两点明示：

1. **派完子代理不许阻塞等待**：用 `TaskOutput block=true` 轮询等子代理完成被用户点名纠正（「你应该等A车道完成后主动通知你 而不是一直阻塞等待」）——子代理完成会自动通知唤醒主控，主控应结束回合让出轮次，期间去做不重叠的并行工作（写文档等）或直接收尾。
2. **「使用多个子智能体并行实施 提升开发效率」**：实施类任务尽量拆车道并行。

**Why**：阻塞等待既占轮次又零产出（与 AGENTS.md「不许空等、并行车道固定为写文档」同源，但该轮我把禁令窄化成了「长命令不 sleep」，对 agent 等待用了 TaskOutput 阻塞变体，被纠正）。

**How to apply**：①派活后立即结束回合或转做其他车道，靠完成通知继续；②拆车道时按文件交集分——紧耦合 src/main 主控先落（子代理测试跑在同工作树，半成品会互相污染），零交集的测试/文档派子代理并行，各子代理明令「达标即提交＋只 add 自己的文件＋parallel_tasks 独立沙盒登记」；依赖主控在途改动的测试用例，把行为契约写进派活词即可并行（红绿以收口门禁为准）。与 [[pitfall-parallel-session-batch-staging]]、[[parallel-build-resource-rules]]（并发上限 2 路）合读。

**2026-10-15 再次明确（JDK8/Redis 启动崩溃调查）**：用户原话「你拍子智能体的时候不要阻塞主任务 等子智能体后台通知即可」。不仅禁 `TaskOutput block=true` 和轮询，**派发 Agent 时就应使用 `run_in_background: true`**；主任务继续调查、写计划等独立工作，靠完成通知接结果。本轮此前用同步 Agent 调用导致主任务随调查子代理阻塞，正是用户这次纠正的形态。

**Why:** 同步派发虽没有显式调用 TaskOutput，主任务仍会等待代理结束，违背并行目的。

**How to apply:** 派 Agent 明确设置 `run_in_background: true`；派出后推进不依赖其结果的工作，收到完成通知后再整合结论，绝不通过阻塞工具等待。
