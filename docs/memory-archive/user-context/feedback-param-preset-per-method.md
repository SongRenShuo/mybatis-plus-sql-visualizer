用户第二次验收（20261006）对参数预设提的语义要求：**每个方法一套预设、互相隔离**——「现在所有的方法都是一套预设，这是不正确的」。同轮还有一处措辞偏好：数据源指示行「关联（上次使用）：X」→「**数据源（上次使用）：X**」（英文 `Associated (last used)` → `DataSource (last used)`）。

被判定不对的形态（修复前）：`ParamHistoryCache` 的 `schemes` 是「预设名 → (SQL键 → 参数快照)」——**快照已按方法/SQL 分桶，但预设名是全局的**：`schemeNames()` 不带键参数、面板下拉与「管理预设…」对话框直接消费全量名单，激活指针 `activeScheme` 也是全局单值。

## 已实施形态（`9810df8`，dev）——按这四条对齐，别退回全局语义

1. **名单按键过滤**：`schemeNamesFor(key)`——UI 只列「在本条语句下确有条目」的预设。
2. **激活指针按键存储**：`activeSchemeFor(key)` / `switchScheme(name, key)`；每条语句各自记住自己上次选的预设。持久化新增按键指针（`paramActiveSchemeByKey`），旧全局指针**降级为「未记录键的回落值」**且仅当该名字在当前键下确有条目时生效（迁移安全、老数据零迁移；存储格式未动，因为快照本就按键分桶）。
3. **另存为按键查重**：同名预设可在不同方法各自存在、各存各值（这是隔离语义的**必然推论**，不是可选业务规则——维持全局唯一则隔离根本达不成）。
4. **重命名/删除维持名字级**（用户认可推荐案）：改一次，同名预设的全部语句一起变；对话框文案已注明。

配套细节：面板异步写回（`flushHistoryToCache`）取方案名必须**按键取**（取回落值视图会写错桶）；对话框条目摘要改「本语句 N 条快照」；数据模型层留了两个 `internal` 兼容缝（回落值视图 `activeSchemeName()`、单参 `switchScheme`）——生产侧一律按键，禁在新代码里用它们。

## ⚠️ 第四轮（20261021）：「按方法隔离」至此时仍不成立

第 1 条的「按键过滤/按键指针」里的**键仍是 `表名+SQL 指纹`**，没有方法维度。同文 HQL 的两个方法（demo `WmsInventoryJarQueryService` 拼接版 vs StringBuffer 版）键相同 ⇒ 预设、激活态、值全共享。根因与修法见 [[project-preset-method-scope-key]]。读本条第 1 条时不要把「按键」当成「按方法」。

**⚠️ 隔离范围是按 SQL 而非按方法（20261021 用户追问后补充）**：用户随后问「预设永久绑定方法、改 SQL 也不丢」，说明他要的是**归属**而不是**快照**——同一条预设跨 SQL 编辑仍应在。若照此实施：回落只恢复参数值 + FieldFill，**勾选态（`__chk__`/`__fnull__`/`__fev__`）不得跨 SQL 回落**（Wrapper 条件 id 是解析序自增 `c0/c1/…`，改 SQL 会让旧 id 张冠李戴到别的条件上，比失效更糟）。

**20261021 已按此实施完毕**（两阶段：隔离 + 绑定，已合 master `5b49dfd2`，未 push）。用户对该方案的措辞是「采纳，按照你的推荐实施」——即 B 路线（精确键优先 + 同 scope 最近键回落）+ 结构态不回落，这两条已成为定案语义，不要再回到「按 SQL 隔离」或「整份快照原样回落」。落地细节、读数与反向探针见 [[project-preset-method-scope-key]]。

## 第二轮走查结论（`00e23f1`，dev）——命名预设＝快照语义（**已推翻上稿的「自动保存按激活预设归桶」**，别再退回）

用户实测报错流程：**输入 zhangsan →「另存为 zhangsan」→ 改参数为 lisi →「另存为 lisi」→ 切回 zhangsan → 仍显示 lisi**（而默认预设反倒留着 zhangsan）。

根因：自动保存（参数击键 500ms 防抖 → `flushHistoryToCache`）按**当前激活预设**归桶——「另存为」后激活指针指向该预设，**后续编辑的自动保存即就地覆写该预设的该键快照**；默认预设没被改只因为它在那之前已落库。⇒ 命名预设会被日常编辑悄悄改写，用户零提示。

修复后语义（三条，改预设/保存相关代码前先读）：
1. **自动保存恒写默认（工作区）桶**（`saveForScheme(DEFAULT_SCHEME, …)`）——编辑只更新工作区；防串桶目标（异步写回不落到别的桶）由「恒默认」天然满足，不再需要按键捕获方案名。
2. **命名预设只经「另存为 / 管理预设」显式写入**＝快照语义。
3. 切预设＝按目标预设快照召回；编辑后切走再切回会看到该预设自己的值（这正是用户要的）。

已知未做（用户未点名，别自作主张加）：没有「更新此预设」按钮——若用户将来要求「把当前编辑写回该预设」，那是新增的显式动作，不是恢复自动写回。

## 第三轮走查追加（`9596095`，dev）

- **参数区「清除」按钮在 XML 预览下无反应**：原实现只遍历 `previewModel.conditionViews` 的属性来源，而 **XML 预览的条件行没有值输入框**（值都在「参数 / foreach」分区）⇒ 该路径在 XML/注解预览下无可清对象。修法＝「清除」语义定为**清空本预览全部参数输入**（模型预览条件值来源 + 普通参数 + foreach 权威值）；边界：批量列归批量分区自己的清除、勾选态归「全不选」，别把这三种职责合并。回归用例形态＝XML 预览填 foreach 值 → 点清除 → 字段空（旧实现下必红 `expected:[] but was:[1,2]`，本轮红读数实测）。
- **数据源指示行文案**已按用户偏好改为「数据源（上次使用）：X」（见本档开头），位置在顶栏「更多」按钮下方右对齐（第一轮走查定的）。
- **另一例（同族，取自同批实测）**：日志/历史条目预览对 **DDL**（`CREATE TABLE` / `ALTER` / `DROP` / `TRUNCATE`）**不做字面量参数恢复**——DDL 里的单引号是列注释/默认值，不是可编辑参数；恢复命中还会把预览/执行的 SQL 换成占位符形态（`COMMENT ?`）致语法不合法。门禁白名单＝`SqlTypeClassifier` 判 `QUERY`/`DML`（DDL/UNKNOWN fail-closed）。已实施＝`aba39b6`（S1 门禁+S2 DDL 排版+S3 零变化轻提示，dev），详情见 [[project-pending-plans]] T-DdlLogPreview 条与 [[pitfall-fake-green-test-assertions]]。

**Why:** 上稿把「防串桶」理解成「按激活预设归桶」，方向上恰好反了——那正是就地覆写缺陷本身；用户的原话「这是为什么」要的是机制解释，不是随机现象，写结论时须给出可复现的步骤链（哪一步把哪份快照改了）。这类「编辑是否算修改预设」的语义分歧，用户界面上只有靠实测流程才能暴露，改完必须把该流程做成回归用例。
**How to apply:** 动预设链时：①任何自动/隐式写回一律进默认桶；②验证用例的标准形态除「两方法同名各自存值」外，再加一条**用户流程用例**（另存 zhangsan → 改 lisi → 另存 lisi → 切回 zhangsan 必须显示 zhangsan）；③反向验证＝把写回改回按激活预设归桶，该流程用例必须红（本轮红读数＝2/2 红）。相关：[[project-pending-plans]]、[[feedback-ui-match-existing]]。
