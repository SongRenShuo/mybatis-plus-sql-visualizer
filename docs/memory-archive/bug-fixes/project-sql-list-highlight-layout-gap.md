## 根因（三条独立，别只当成「配色不好看」）

1. **两套插件自管配色并存**：日志/历史/单击预览走固定 One Dark 的 `SqlHighlightColors`（`MP_SQL.*`，关键字强制粗体）；SQL 预览的**自建回退编辑器**走平台语义槽 `DefaultLanguageHighlighterColors`（私有 `MP_SQL_*`）⇒ 同一条 SQL 三处变色（Ultimate 下预览还可能被平台 Database 控制台替换，那是第三套、平台托管）。
2. **多层颜色同时发声**：八类 token 色 + 耗时快慢色 + 数据库/MCP/错误/同结构徽章色 + CRUD 左侧色条 + 选中背景 + Speed Search。
3. **「乱」＝概览列表在做编辑器的事**：默认 `KEYWORD_WRAP` 拆多行 ⇒ 行高不一、关键字反复顶格、元信息与 SQL 都横向超宽触发水平滚动；而正文早已被 `summary` 截成首行或 160 字。

## 已落地形态

- **复用配色语义，不复用 Editor 组件**（硬边界：旧版仅 `JLabel + HTML` 就 16 秒 EDT Freeze；完整 Editor 需显式 `releaseEditor`，JList renderer 无稳定的一行一对象生命周期）。列表继续 `SimpleColoredComponent` 片段渲染。
- 唯一 token→key 表落在既有 `SqlHighlightColors` 作 canonical（`MP_SQL.*`，用户既有 scheme 覆写不失效），fallback 链 = `MP_SQL.*` → `MP_SQL_*` 旧覆写 → 平台语义色；删掉固定 RGB 与强制粗体。
- 多行缓存改**语义缓存**（存 `text + tokenType`，不存 `SimpleTextAttributes`）——否则换 scheme 后旧条目残留旧色；订阅 `EditorColorsManager.TOPIC` 只失效属性缓存 + repaint（`LafManagerListener` 覆盖不了「同主题换 Editor Color Scheme」）。
- 抽共享 `SqlEntryPresentation` 收敛两页 meta 顺序（行号→时间→耗时→库→MCP→来源→同结构）；日志独有的 update/error/dedupe 走显示级 extra slot（保留在日志的元信息里，历史不伪造占位）。
- **🔴 默认显示经用户校正回到 `KEYWORD_WRAP`**：我曾按计划把新配置默认改成 `SINGLE_LINE` 紧凑单行，用户明确「默认列表显示最好能和之前一样，关键字换行，方便看 sql 的大概情况」⇒ 改回 `KEYWORD_WRAP`（非法值回退也改回），另加「子句概览最多 3 行 + 溢出显示剩余行数」。**已保存的显示模式一律不迁移**（现无「旧默认 vs 用户主动选」标志）。教训＝**改默认值属于产品取向，别只照计划的字面执行**。
- 宽度省略：`getScrollableTracksViewportWidth()=true` + `HORIZONTAL_SCROLLBAR_NEVER`（**只藏滚动条不够**，不 track viewport 宽度则 renderer 拿不到窄宽度、省略不会发生）；裁切按 code point（避免切坏 emoji）；模型/复制/预览仍用完整 `restoredSql`。
- **不做**：不做八个十六进制色设置页、不动 Mapper XML 14 键配色页、不覆盖 Ultimate Database 控制台 highlighter。

## 20261026 第二轮：用户再问「SQL 列表内容乱」，只出方案未动代码

**触发**：用户贴 SQL 日志页截图（约 590px 宽侧栏，KEYWORD_WRAP，#3/#4/#6 挂「同构 4 条」徽章），问「查看不方便，分析当前布局并提供几套优化方案」。**要求包含 SQL 日志与 SQL 历史两个列表**。本轮全程只读代码，未改一行。

**当前结构的事实（供下次直接续做）**：两个列表共用同款渲染器——`LogEntryListCellRenderer`（`LogEntryRendering.kt:316`）与 `HistoryCellRenderer`（`HistorySqlLogPanel.kt:1421`），结构都是「左 3px 色条 + GridLayout 纵向堆叠：元信息行 + 1~3 行 SQL」。元信息是**一串无列概念的片段**，固定顺序：`#序号 → 时间戳 → 耗时 → [库] → [MCP] → (影响行数) → 报错 → ⨉去重 → 同结构 N 条 → [文件:行号]`（`SqlEntryPresentation.kt:19`）。宽度策略＝列表恒跟随视口（`LogEntryFiltering.kt:154`）+ 横向滚动条直接禁掉（`SqlLogPanel.kt:1546`），所有超宽内容走 `clipForList` 二分测量裁切加省略号（`SqlEntryPresentation.kt:54`）⇒ **截断点随窗口宽度漂移，可能截在行号中间**。行高＝单行模式按 `SELECT 1` 样例测一次固定（`SqlLogPanel.kt:1583`），关键字换行/格式化模式可变且最多 3 行（第 3 行起折成 `… (+N)`，`SqlEntryPresentation.kt:42`）；默认 `KEYWORD_WRAP`（`PluginSettings.kt:409`，默认值不得擅自改，见上节用户校正）。同时生效的颜色有六套：耗时五档、库青、MCP 紫、同结构琥珀、类型色条、SQL 语法高亮（`LogEntryRendering.kt:105` 起）。同结构徽章阈值 3（`LogSqlModels.kt:352`），按 `structureKey` 计数。

**诊出的六个病灶**：①每行开头 60~90 字符是重复前导（时间戳默认 `yyyy-MM-dd HH:mm:ss`，用户截图带 `,SSS` 更宽）；②元信息无列对齐，眼睛无法竖扫；③裁切吃掉最有用的部分（来源截在行号中间、SQL 只剩 SELECT 列表丢了 FROM/WHERE）；④同一事实重复展示（三行都挂同结构徽章却仍是平铺独立行，无分组头）；⑤颜色无主次；⑥纵向利用率低（2~4 行一条+上下 5px 留白，一屏 6~8 条）。

**顺带查出的两处不一致（真缺陷，后续要修）**：历史页元信息把 `showDuration` **硬编码 true**（`HistorySqlLogPanel.kt:1487`），设置里关掉日志页耗时对历史页无效；历史页 `showLogDetails` 默认 false，不显示报错与影响行数，两页信息集不一致。

**三套方案（已完整交付给用户，内容与取舍）**：
- **A 列对齐**（推荐先做）：保留两行卡片，元信息拆成固定宽度列——`#N` 窄槽、`HH:mm:ss.SSS`、耗时右对齐、单字类型徽标（查/增/改/删，替代 3px 色条）、库名缩写、来源尾部省略但**保留行号**；按宽度断点降级（≥560 全显示 / 460~560 去日期 / <460 去库名 / <400 只留时间+耗时+类型+SQL）。改动＝两个渲染器 + `SqlEntryPresentation`，**9 个测试文件引用 `metaLine`/`metaTextForTest` 需同步改**，必须沿用 `setBorderIfChanged`/`setBackgroundIfChanged` 同一性守卫（`LogEntryRendering.kt:146` 起）。约 1 天。
- **B 按模板折叠**：行单位从「一次执行」改为「一个 `structureKey` 组」，组行显示 ×N、耗时区间、代表 SQL，展开才是逐次执行；复用 `structureKey`/`dedupeKey`。交互语义需先定义（展开态记忆、复制全部还是代表、跳转选帧），且与「SQL 去重」语义重叠要合并口径。178 条典型可压到 20~30 组，但改变心智模型，按迭代估。
- **C 主从分离**：列表压成 22~24px 单行表 + 列头（`JList` 无表头，需在滚动面板上方加固定 `JPanel`，列宽与渲染器共用列模型，点击列头排序可顺带把排序从工具栏图标组里挪走）+ 常驻详情。**基础设施已存在**：`SqlListPreviewHost`/`SqlDockedPreview` 已有可拖分栏与比例持久化（`OnePixelSplitter` 0.65），只需把「点开才出现」改成「选中即更新、默认展开」。1~2 天。
- 另有四件零结构改动的减噪小事：时间默认改短、同结构徽章只在与「同结构聚类」排序下显示、来源中间省略保行号、类型字母/单字徽标。

**最终建议（已给出）**：不要把 A/B/C 当互斥三选一，做成设置里「列表视图」的三个取值——卡片（A 改造后）/ 紧凑表格（C）/ 按模板分组（B）；**顺序 A → C → B**，因为 A 产出的列模型正是 C 的基础，B 改动最大且动默认视图风险最高。B 暂不做默认视图。

**版本对账提醒**：截图里的徽章文案是「同构 4 条」，而 master/dev/k2j 三棵树的 bundle 都是「同结构 {0} 条」——用户装的插件构建与这三棵树都不同，拿截图与代码对账时先确认版本，别据此判代码缺失。

**字段顺序六方案**（交付 `sql-list-head-order.html`，同一形态只换顺序，含宽度滑杆）：
1. **现状顺序** `#序号 时间 耗时 [库] (行数) 徽章 类名:行号` —— 改造前口径，零适应成本；**缺陷＝来源排最末，宽度不足时最先被裁，而它恰是定位时最需要的**
2. **定位优先** `#序号 类名:行号 时间 耗时 [库] 徽章` —— **我推荐的方案**；理由是列表主用途是「找到可疑的那条」，线索通常来自代码位置（谁打的）而非时间；时间用于排序/看密度、序号用于引用，类名紧跟其后正好在视线下移路径上
3. **三段分组** `#序号 时间 耗时 │ 类名:行号 [库] (行数) │ 徽章` —— 竖线分隔有节奏感，但两根竖线约吃 20px，窄侧栏会挤掉徽章
4. **库前置** `#序号 时间 耗时 [库] 类名:行号 …` —— 多数据源场景先看环境；用户当前单库，收益暂体现不出
5. **双行头部** 第一行时序、第二行归属+诊断 —— 不裁剪但每条多一行，一屏少看约一条
6. **来源右对齐** 左段时序+诊断、来源推到最右 —— 两条信息带固定，但与 SQL 正文左缘不对齐，滚动易跟丢

**待用户拍板**：选哪个顺序；以及头部时间用完整日期还是只留时刻（540px 下完整日期已接近占满整行）。

**方法论**：字段顺序这类「同一形态内的排列决策」，用「同一版面只换顺序」的轮播对照 + 每个方案配一句取舍说明，比文字罗列顺序有效得多——用户能直接看出哪一项先被裁、眼睛往哪落。

**用户连问三件**：①之前能搜行号和时间的搜索功能有没有回归；②窄侧栏显示 `[06:13:20]`、宽侧栏显示完整时间，这样是否合适；③**设置里有时间格式，应该遵循设置吧**。

**①②实测结论：搜索没有回归。** 四种情况全正常——完整格式 / 时段 / 自定义格式（`MM/dd HH:mm:ss`、`HHmmss`）都能命中；行号 `#42` 与 `42` 精确命中、`43` 不命中；时间戳开关关闭时时间不参与匹配。我曾误判为缺陷并加了「同时匹配完整格式与时段」的 `matchesTimestamp` 补丁，实测发现原实现本来就够用（完整串天然包含时段），已回滚。

**③我确实做错了**：按宽度剥日期＝用智能覆盖用户配置，同一份配置在宽窄栏显示两种形态、用户无从察觉。详见 [[feedback-display-format-follows-settings]]。

**处置**：整段删除剥日期逻辑，时间片段列为**不可拆分**。宽度不够时按优先级丢其他片段，全丢完才顺序截断。

**新增两条守卫**：`test头部裁剪_绝不改写时间格式`（窄档断言完整时间仍在）、`test头部行时间格式不随宽度变化`（900/420/320/280/240/**200**px 六档断言可见时间片段逐字节一致）。**200px 档是关键**——只有它会把时间压到截断边界，前五档旧实现与正确实现输出相同，测不出差异。

**遗留边界**：≤200px 时时间会被顺序截断成 `[…]`，这是「格式不可改写」的必然代价；正常侧栏（≥280px）不触发。真机若遇到，正确处置是调整丢弃顺序，不是改格式。

**最终读数**：`log` 包 **1764/0/0**（第九轮 1759 + 本轮 5 条新守卫）。

**仍待真机走查**：三种模式 × 两页 × 窄宽两档，重点看 12px 留白下的条目边界是否一眼可辨（这是唯一仍需人眼判的参数）。

## 20261026 第十一轮：丢序两轮调换 + 第 4 个真 bug（`79e232be` + `4ba423d3`，最终 1768/0/0）

### 一次概念混淆（被我自己的命名带偏）

用户先说「**行号不能先丢** 方言和类位置可以先丢」，随即澄清「**我说的是序号 不是类后面的代码行**」。
根因是我在设计与注释里把 **捕获序号 `#42`** 与 **源码行号 `:183`** 都叫「行号」，才凭空造出
「序号不能先丢」与「行号不能先丢」的表面冲突。两者是两个不同字段，代码与注释现已分开表述。

### 最终丢序（两轮调换后定稿）

```
影响行数(1) → 库角标(2) → 源码行号(3) → 来源类名(4) → 同结构徽章(5) → 捕获序号(6)
```

- 第一轮（`79e232be`）：类位置（类名+行号）整体靠前、**捕获序号最后**——序号是团队里指认某条的锚点。
- 第二轮（`4ba423d3`）：用户要求**类位置内部把行号提前**——`:183` 脱离类名毫无意义（哪个类的第 183 行？），
  而 `…ionOccupyInfo` 单独出现仍能定位到文件，先丢行号信息损失更小。

**实测退化梯度**（540px 侧栏、时间格式跟随设置）：
480~320px 全保留 → **300px 丢行号** → 280px 丢类名 → 240px 起只剩 `#42 时间 5ms` → 200px 序号才兜底截断。

### 第 4 个真 bug：`isTimeText` 把源码行号误判成时间

`isTimeText` 用「含冒号 + 含数字」判定时间片段 ⇒ **`:183` 完全命中** ⇒ 被强行升为 `NEVER`、窄宽度下**永不丢弃**。
用户视角的症状是「该丢行号时反而丢了序号」（260px 实测留下 `:183`、`#42` 消失）。
修复：要求 `colon > 1`（冒号左侧必须还有内容），排除以冒号开头的行号形态。

### 结构性收敛：优先级改成显式字段，不再按文本形态猜

三次翻车（方括号形态不匹配、时间=NEVER 让日期永不剥离、`:183` 被判成时间）**同一根因**：
> 凡是「按文本形态猜测片段语义」的判定都会翻车。

最终把优先级做成 **`SqlTextFragment.dropPriority: Int = Int.MAX_VALUE`** 显式字段——
**生成片段的地方本就知道它是什么，由它自己标注；读取处只取值**。`isTimeText` 降级为
「时间绝不可整段丢」的兜底保留。这是本轮唯一值得复用的设计结论。

**排查手法**：怀疑「丢弃顺序不对」时，直接打印 `headerFragments` 的 `text + dropPriority`，
再在 `dropByPriority` 循环里打一行 `drop=[…] prio=… total=… max=…` ——比读代码推断快得多，
本轮正是靠这行日志一眼看出「`:183` 从未出现在丢弃列表里」。

### 反向验证

把序号优先级提到最前 → **恰 2 红**；换回「类名先丢」→ **恰 1 红**。
