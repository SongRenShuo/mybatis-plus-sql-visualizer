# SQL 日志尾部跟随 + 排序（T-SqlLogTailFollow，O-148）——已实施

20261014 用户原话：「目前是 sql 日志默认一直滚动到底部，这个可以保留，但是我希望当用户手动滚动后就不能自动往下滚了，除非点了滚动到底部按钮才会继续触发自动滚动，并把这个时间升序移动到左侧的按钮集」。计划册 `docs/开发计划/20261014-1615-T-SqlLogTailFollow-*`。占号 **O-148 / R98 / D158 / V181**（R97/D157 已被 O-147 占用）。

**实施与分支**：独立工作树 `mpsv-sql-list-native-tail`（分支 `t-sql-list-native-tail`，自 `master@803ef689` 新建），O-146 与 O-148 两计划在同一树上串行落地（先 O-146 后 O-148）。**未合并、未 push**（动 master/tag/发版面须用户明示，见 [[feedback-dev-merge-needs-approval]]）。

## 头条：不是新功能，是语义修正

跟随与「滚动到底部」**早已存在**（T-SqlLogPerf 2026-10-06）。真问题三处：①48px 松量让小幅上滚不暂停（最可能的真根因）；②滚回底部会自动恢复（与「只有点按钮才恢复」冲突）；③归因靠 `maximum` 增长＋`value` 未动 的启发式（押在滚动条模型更新时序上）。**全仓测试原本零覆盖跟随语义**——这才是偏差长期存在却全绿的原因。

## 已落地形态（四轮收敛，以最后一轮为准）

- **显式两态** `TailFollowState: FOLLOWING | PAUSED`。暂停由**真实用户输入事件**驱动（滚轮 `mouseWheelListener`、滚动条 `mousePressed`、列表/滚动条的导航键），不再用像素距离反推意图——程序性滚动天生不产生这些事件，故不需要跨 EDT 脉冲维护「程序性滚动中」守卫标志（比原计划更简单：删掉 48px 松量与 adjustment 监听）。
- **恢复入口**：滚底动作 + **清空列表**（用户 2026-10-14 明确追加确认「清空列表后恢复跟随可以的」——曾按字面「只有按钮」临时删掉 `onClear()`，收到确认后立刻恢复）。滚回底部自身**不**恢复。
- **排序控件四轮演进（留痕，避免下次再走弯路）**：①移入左簇、挂行宿主 `WEST` → 用户问「是否与 SQL类型重叠」，核实＝两侧各取理想宽在窄宽度**必然**互相压盖；②改挂 `CENTER`（图标组吸收挤压、排序钉在簇右缘）→ 用户指出「排序没被左侧按钮集归入、过窄应该自动折叠」，确认 `JButton` **不参与 ActionToolbar 溢出机制**，因此「固定宽按钮」这条路本身是错的；③改为组内 `AnAction` + 自建「更多」弹层收纳设置/屏蔽/帮助 → 用户指出「**不要这个更多**，之前是侧边栏不够宽时自动折叠、鼠标放上去能看全部，那个交互更好」；④**定稿**＝全部八个动作直达、无自建「更多」，窄宽折叠交平台自带溢出 `»`；排序为组内末位操作动作。
- **最终工具栏顺序（用户选定「方案 A」）**：`捕捉 → 清空 → 设置 → 屏蔽管理 → 搜索 → 滚动到底部 → 排序 → 帮助`——操作在前、工具在后、**帮助收尾**（`?` 属纯信息性动作、平台惯例在末尾；平台溢出从右端折叠，故帮助最先让位）。
- **排序图标**：`AllIcons.RunConfigurations.SortbyDuration`（竖杠+下箭头+三条递减横杠＝「梯子」形，一眼可辨）。原用 `General.ArrowDown` 与「滚动到底部」撞脸。平台里可用的排序类图标极少（全部分支扫下来只有 `SortBySeverity`/`SortByType`/`Sorted`/`SortedByUsage`/`VisibilitySort`/`SortbyDuration` 这几个）。
- **代价（须向用户交代）**：排序变成图标后**当前排序方式不再常显文字**，只进 tooltip（`排序：<方式>`）与菜单选中态。用户若要文字，可放回右侧控制组当文字按钮。

## 排序方式与慢查询筛选（用户追加「值得补的补上去，注意性能」）

- 排序菜单补两项：**同结构聚类**（按 `structureKey` 分组、组内保持时间升序 ⇒ 排查 N+1 时同形状相邻）、**按目标库分组**（库名升序、未知沉底、组内保时间升序）。
- 「只列慢查询再按耗时排」的**排序半边已被既有「耗时降序」覆盖**（同一语义：按耗时降序、无耗时沉底），故只补**筛选半边**＝类型过滤弹窗内新增「只看慢查询」勾选（阈值取 `slowQueryThresholdMs`，判定走 `durationOf`，与慢查询徽章同口径；**耗时未知不算慢查询**）。
- **性能核算（用户点名）**：两个新排序都是对「当前可见条目」一次 `sortedWith`（O(n log n)，n ≤ 缓冲上限 200），`structureKey` 是条目级 lazy 指纹、库名只做字符串比较；筛选一次 O(n)。三者都在**刷新管线**内、不在渲染热路径，不新增 per-cell 开销，不触碰 T-LogListFreeze 的固定行高与片段缓存。
