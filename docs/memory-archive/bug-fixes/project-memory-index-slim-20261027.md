# 索引瘦身（2026-10-27）

两个「主索引」都偏大，但病根不同，处置也不同。

## docs/MEMORY.md：结构性问题（两代索引叠加）

**症状**：216KB / 850 行，出现**两个** `# docs 文档检索索引` 一级标题（第 13 行、第 501 行）。第 495 行起是完整第二份文件（含自己的 frontmatter）。

**定量事实**（改前实测）：
- 两段交集 268 行完全重复；第一段 423 行非空、第二段 304 行
- 第一段自身还有重复节：验收文档 ×2、内容营销 ×2、mcp ×2、经验总结 ×3
- 299 条链接行里 68 个目标重复（「全量测试墙钟压缩」系列各 2 次），29 行超 400 字符（最长 1148）
- 开发计划计数自相矛盾：第一段「530 篇」、第二段「548 篇」，实际目录 607 篇

**处置**：删第二份整段 → 系列文档（竞品 29/性能 24/审计 20）由逐篇登记改「最新一期 + 系列范围」→ 开发计划节只留指针（完整清单在 `docs/索引/开发计划.md`）→ 修 5 条断链。结果 37KB / 253 行、一级标题 1 个、断链 0。

## agent MEMORY.md：规范执行问题

**症状**：100KB / 208 行 / 178 条，但 111 条超 200 字符、44 条超 400、最长 3160。规范早就写了「一行速览、200 字符以内」，问题是没执行。

**处置**：按**真实状态**三分——进行中（有未完成动作）/ 长期参考（约定·入口·口径·领域语义）/ 已完成（留跳转待归档）。结果 27.5KB / 236 行 / 188 条、最长 199 字符、零断链、零未索引。

## 两个可复用的判据

**一、归档判定必须 git 实测，不能读条目文字。** 条目自己写着「已实施 `xxx`」不等于在 master 里。逐个跑 `git merge-base --is-ancestor <sha> HEAD`：本次实测出 6 个「声称已实施但实际未入 master」的，全部分布在未合并分支上——`5c28943d`/`bcb99506` 在 `t-sql-insight`、`713416bb` 在 `t-magpie-gems`、`d763c7bb` 在 `feature/kotlin-to-java`。这些必须留在「进行中」并标注分支名，否则会被当成已完成而漏掉合流债。另有一个 `2175a632` 在任何分支上都不存在（内容相同的 `6b6b56e3` 才是实际落地提交）。

**二、「重复」要先分辨是冗余还是双职责。** docs 索引里 68 处重复目标全是冗余（同一文档登记两次），删。agent 索引里 `project-kotlin-to-java-port-sync.md` 出现两次却该保留——一处是「机制说明」（长期参考）、一处是「当前分支状态」（进行中），职责不同。同样，`runide-demo-verify-workflow.md` 原本被索引 4 次（3 条在踩坑节写不同侧面 + 1 条在归档节），合并成 1 条并在描述里注明合并了哪三方面。

## 踩到的两个坑

- **私有材料目录是独立 git 仓库**（有自己的 `.git`），不随主仓发布。旧索引里有 4 条把它写成普通子目录，是断链的真因（不是文件丢了）。修索引时的正确做法：**公开仓的索引不登记私有目录的内容与路径**，只留一句中性说明；需要指向私有材料时写进本地记忆，不写进随仓发布的文档。
- **Bash 内 python 写文件不落盘**（本仓既有定例）：`io.open(...,'w')` 在同进程回读正常，跨调用丢失。跨调用改文件一律用 Write/Edit 工具；Bash 内 python 只做只读分析。本次先试 `/tmp` 落盘即失败，改 Write 才成。
