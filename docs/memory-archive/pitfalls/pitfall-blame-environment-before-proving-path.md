**「本环境取不到这个读数」这个结论，必须先证明路径走过一次，再写。**

**实例（2026-09-23，同一件事上连错两次）**：O-49 的定位按钮真机读数一直取不到，我先后写下两次环境性结论——
先说「该失败走不到富通道、本环境造不出来」，再补一句「除非造一条真走异常链的失败」。**两次都错**：

1. **真因一：口令对话框吃掉了监听窗口**。数据源口令没保存时，执行会弹登录框；用户填完再执行，
   而插件的结果监听窗口（40 拍 ≈16 秒）**早已超时停止**——所以「SQL 报错」这件事发生时插件根本没在看。
   现象与「环境不支持」一模一样（面板留着超时提示、控制台有错误）。把口令存成 Forever 后，同一场景一次就复现。
2. **真因二：第三个投递点漏转发**。错误提取日志（`extracted console error` / `early console error detected`）
   都在打，说明错误拿到了；但富通道回调一次都没被调用——因为 `prepareInConsole` 在
   `executeAfterPrepare` 分支调下游时**漏传** `onErrorRich`（签名里一直有该参数），
   而这条正是「点执行 SQL」的主路径。

**判别手法（成本极低、结论确定）**：在**判定点**（这里＝`errorLocateAction()` 的三个 return 之前）
加一条临时 `Logger.info`，跑一次真实场景后 grep 日志：
- 日志**打了** → 路径走到了，问题在判定条件里（继续往里看）；
- 日志**一行没打** → 路径根本没进 → 是**接线断**，不是环境不给。**这一条是「环境受限」结论的反证**。

**Why**：把接线漏判成环境受限，代价是**永久性地把缺口写进验收文档当既成事实**——下一个接手的人
（或下一轮的我）会照着「环境受限」不再尝试，而缺陷在用户那里一直存在。而且这类误判**全绿**：
单测直接调函数、必然传参，门禁照过。

**同族第二形态（2026-10-13：「用户假设的机制」也要先证伪再采信）**：用户报障时**自己给了归因**
——「这个 var 可能是在 class 中，疑似依赖或者 jar 中的信息」（怀疑要跨 jar 解析 DAO 实现才能识别）。
读代码后该假设**直接证伪**：识别链走的是「qualifier 变量名后缀 + 方法名关键字 + 首参内容启发」，
`PreviewReceiverResolver.classify` **名字命中即返回、不触发 `qualifier.type` 的 resolve**，
根本不看 DAO 实现体 ⇒ 实现体在哪个 jar 与能否识别无关。真因在另一处（提取层 `when` 无
`PsiMethodCallExpression` 分支，见 [[project-hql-buffer-concat-gap]]）。
**关键**：用户给的归因**很有说服力但可能是错的**，而它错得很自然——因为它解释得通「为什么只有这条
调用不认」，且用户比谁都熟悉自己的代码库。照它去查（去找 jar 里的 DAO 类、试跨模块解析）会**白跑**，
且大概率顺手写下一个「跨 jar 解析受限」的错误结论留在文档里。**用户提供的机制假设＝待证伪的线索，
不是结论**；先把它落到「哪几行代码会因此改变行为」上，读一遍就知真假。

**How to apply**：写「环境受限未验证」之前，至少做一件事——在决策点加临时日志或计数探针跑一次，
证明路径被走到；做不到就如实写「未能证明路径可达」，而不是「环境不支持」。
同一场景连错两次时，先怀疑自己的实验装置（对话框/超时窗口/默认参数），再怀疑环境。
**用户自带归因时同理**：先定位「若该归因成立，哪段代码是判定点」，读那段代码决定采信或推翻，
再往下查；归因正确时它省一大圈，归因错误时它是最贵的一条错路。
