2026-09-19 T-TailSweep2 T-FS-06 实证（独立验证者用「对提交版已编译类的反射实测」抓到，**初判不通过**）：

**坑一：掩码器漏 Kotlin 字符串模板 `${…}` 内嵌字符串，导致守卫覆盖静默收窄。**
`BannedApiSourceScanTest.maskStringLiteral` 遇首个未转义 `"` 即结束外层字符串 → `"a${b("c")}d"` 里
模板内的 `"c"` 被误判为字符串结束，**in-string 状态翻转**：字符串正文被当代码暴露、模板内真代码被涂白。
后果（353 个 main 源文件反射实测）：`execute/DataSourceSelector.kt:1009` 的实参区被正文里的 `)` 提前
配平到 0（截断到 9414 字符，真实 13999）→ 不再含 `ModalityState.any()`；`:2684` 配平返回 −1 被整条丢弃
→ **两个真实 `any()` 站点从「旧规则扫」变成「两条规则都不扫」**（`any() TARGET LOST=2 / GAINED=0`）。
修法：掩码器加模板状态——`${` 开模板、模板内 `{`/`}` 计数配对、模板内 `"` 递归按字符串处理，整段字符串
（含模板）涂白且**严格保长保行**。

**坑二：自证样本没有判别力，等于没钉住。**
修完先加的样本是单行形态 `"a${b("c")}d"` + 其后一个 `invokeLater` 站点——**它钉不住修复**：掩码输出虽然
修复前后不同，但误判在同一行内自行重新同步、括号得失对称，两版判定结果一致（都是 any=1/default=0）。
能区分的形态是**模板跨行 + 其后正文里带一个 `)`**（复刻真实受损形态）。当时提交报文还写了「修复前该样本
必红」，与实测不符，被复测打回后另开提交更正。

**坑三：掩码口径跟语言走，Java 树上嵌套注释配平会整段涂白（20260919 T-SyncK2JMaster92 实证）。**
`maskNonCode` 的嵌套注释配平（为 Kotlin 而设）遇到「注释内不成对收尾符」的 Java 文件，会把该注释**之后整个文件涂白**：
仓内 2 文件命中（多涂白 145/327 行），5 处真实 catch 站点静默脱离扫描面（595→590）。修法=**按扩展名选掩码口径**
（Java 用非嵌套配平）。连带教训：**新增源码扫描守卫时必须先验「命中数非零」**——`AcpTransportScopeSourceScanTest`
已加扫描集非空自检（空集绿灯在守卫写法本身为 0 命中时毫无意义）。

**Why:** 这两个坑的共同点=**「看起来绿的守卫」在静默失去判别力**，正是守卫自身最该防的失败模式；而它们
都无法被「跑一遍测试看绿不绿」发现（0 offender 时两条规则用例修复前后都绿）。这也印证了
[[project-test-conventions]] 的守卫两轮原则，并新增一条：**守卫类改动必须做「去掉修复分支看是否变红」的
反向验证**，且样本要按真实受损形态构造。

**How to apply:**
- 改源码扫描类守卫（掩码/配平/正则提取）后，除常规先红后绿外，**必须做一次「移除本次修复分支 → 样本是否
  变红」的反向验证**；样本不变红就说明钉不住，换形态（优先复刻真实受损站点的形状）。
- 掩码/涂白类工具**必须处理 Kotlin 字符串模板 `${…}`**（模板内可有嵌套字符串、`{`/`}`、换行），并保持
  **严格等长 + 保行**（行号要能回喂豁免标注识别）；未闭合字面量的收手行为也要显式测。
- 验证此类改动的最强手段是**对已编译类做反射实测**（不需要跑 gradle）：直接调 `maskNonCode`/
  `invokeLaterSites` 等内部函数，对全仓源文件做新旧实现的**目标集对比**（DROPPED / TARGET LOST / GAINED），
  比读代码推演可靠得多——本次正是这样抓到「绿着的收窄」。
