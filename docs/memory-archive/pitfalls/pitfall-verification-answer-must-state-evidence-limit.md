2026-09-21 用户连续三次以「这个是干什么的 / 会不会卡顿 / 数据从哪来」提问式走查。当轮把回答拆成**已实测事实 / 代码可判 / 代码定不下来（标注并建议真机点一次）**三层，用户全部接受、未追问修正。

**Why**：本仓很多行为在代码层不可判（不传 UI 宿主 → 结果落在哪里由平台决定；平台侧只能证伪「它自己不开编辑器」，不能断言平台别处不会）。含糊作答或直接给「应该没问题」的结论，会把风险留给下一次真机门禁——与本仓既有教训一致（判「有无用户受影响」看产物不看文档自述，见 [[pitfall-verification-blindspots-and-wrapup]]）。同时用户是产品提问而非要求改码：本轮只做排查、未改任何代码，是正确处置。

**How to apply**：用户问「这个功能是干什么的 / 会不会有问题」时——(1) 先给结论再给证据，证据带 `文件:行`；(2) 任何「我推断但没验证」的机制/落点，**在回答里显式标为未证实并给出最小验证动作**（如「真机点一次即可定」），不要写成事实、也不要因未证实就不说；(3) 不要顺手改代码——描述问题/提问时交付物是判断，改动等用户明说；(4) 结论要能直接支撑产品决策（「该不该留这个键位/入口」），而不是只描述实现。
