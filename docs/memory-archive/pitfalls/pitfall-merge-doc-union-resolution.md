20261005 T-MergeMasterToDev（master 33 笔并入 dev，合并 `fb60c3d`）实测的可复用合并解法：

1. **冲突预演即全量**：`git merge-tree --write-tree --name-only <ours> <theirs>` 先于真实 merge 列出冲突文件与两侧改动面（含自动合并交集文件清单），本轮预演 5 冲突文件与真实 merge **完全一致**。冲突形态归类裁决：①两侧各自新增条目（CHANGELOG hunk）=union 双保留；②同键改值+异行加键（bundle properties）=union 且同键取新值；③同文件 add/add（计划文档）=用 `git ls-files -u` 取 stage2/3 blob，`comm` 对比「仅在一侧存在的行」再裁决（本轮 master 侧仅多一行占位符→取 dev 实施完成版）。
2. **巨型单行 Markdown 表格行（变更记录.md 每行数千字）不要整段重打**：需要按「最新在上」把一侧行插到另一侧行之上时，`git checkout --ours -- <file>` 取干净侧，再用 Edit 以另一侧首行的**短锚点前缀**（~60 字符，唯一）做一次插入——移动的一侧选**行数少/字数少的一侧**（master 4 行 ≈5K 字 vs dev 4 行 ≈10K），只需转录一次小侧内容。
3. **转录保真必须机械校验**：插入的行与源侧原文 `grep 同前缀行 | diff` 逐字比对（本轮 TRANSCRIPTION-EXACT-MATCH）；肉眼转录 5K 中文字符必错，Edit 匹配失败是安全失败可重试，但 new_string 打错字会静默入库。
4. **裁决后双向在场校验**：每文件对两侧改动各 grep 锚点（CHANGELOG 八锚/变更记录两侧行/bundle 三改动），零冲突标记残留 grep 收尾——[[pitfall-merge-take-one-side-loses-half]] 的合并场景操作化。
5. **Git Bash 调 `python C:\Users\...` 反斜杠路径被 MSYS 吃掉**（`C:\UsersUSER...`）：一律写正斜杠 `python C:/Users/USER/.zcode/cli/parallel_tasks.py`。

6. **`checkout --theirs` 会让该文件从 `git status` 里"消失"，但不是已解决（20261008 实测）**：对证据类文件（`dev-support/e2e-fake-ide/evidence/app.log` 这类）用 `git checkout --theirs <f>` 取对侧后，`git diff --name-only --diff-filter=U` **仍列出该文件**（索引里还是 UU），只是 diff 里不再有冲突标记。**「文件里没有 `<<<<<<<` 了」≠「已解决」**——判据一律回到 `--diff-filter=U` 是否为空，逐个 `git add` 后才真解；收尾再用 `git diff --cached --check`（顺带抓尾随空格）与全仓 `grep -rnE "^(<<<<<<<|>>>>>>>)"` 扫残留。
7. **同内容行两侧一致时 merge-tree 可能不报冲突、直接归并（20261008 实测）**：`docs/变更记录.md` 里 master 侧的 `v2026.10.7 发行八处同步` 行与 dev-bak 侧**逐字相同**（1066 vs 1064 字节，char 级 diff 只见 2 个字符差，实为 `\r\n` 与 `\n` 的行尾差异），git 自动合并后该处无事，因此「表里出现两行同名行」是**真重复**而不是冲突残留。**正确形态＝取对侧整表 + 短锚点插回本侧独有行**（本轮插回 `2026-10-07 T-ReleasePerf7` 与 `2026-10-06 T-ReleasePerf6` 两行到 `2026-10-05` 那行之前，与既有"最新在上"序一致）；校验用「日期列非递增即停」＋关键行 `grep -c` 恰为 1（判重、判丢一步到位），比逐字比对整表可靠。
8. **冲突文件里的"两侧各写了一版同一功能"要走语义合成，不是二选一（20261008 实例）**：`SqlLogPanel.kt` 的历史 tab 常驻（dev 侧 R19 / master 侧 T-HistoryTabAlways）冲突面里，注释合并两侧事实、方法体却必须取 master 那份——因为 master 已把调用点（设置变更监听）一并删除，dev 侧保留的幂等版 `updateHistoryTabVisibility()` 在合并态是**死代码**。**判法**：冲突块取谁不按"谁的更完整"，按"合并后的调用图里谁可达"；同步用 `grep -rn` 确认被丢弃的方法在生产代码里零调用点。见 [[pitfall-merge-take-one-side-loses-half]]。
9. **两分支各自 +1 的「计数守卫」合并定例（20261009 四分支合回实测）**：两分支各自向同一设置页加一个复选框、又各自把 `PluginSettingsPersistenceTest` 的复选框总数守卫 41→42——合并后真值=**43**（+2），解法三件：①zh/en 两侧各自**不完整的 assertTrue**（共享一个收尾 `)` 的形态）合并时补全各自括号双保留；②计数注释行双保留并推进到 43；③`assertEquals("复选框总数应为 42", 42, …)` 改 43。**合并后必跑该测试类验证手工解**；其首轮 17 红全是数据类（PluginSettings.State）双字段新增后的陈旧测试二进制（回归假失败清单第 0 条），`compileTestKotlin --rerun-tasks` 清零即证合并解无语义错。CHANGELOG 同批冲突（HEAD 侧 `### Added` vs 分支侧 `### Changed`）=两节双保留即可。

10. **「两侧各写了同一个新功能的一半」合并也要 union，不是二选一（20261009 第二次实测，收口通用形态）**：同一批次的多个功能分支各自给设置页加一个控件、各自给同一测试类加断言时，冲突块里**两侧都是新增、都要留**——判法=看「冲突块两侧是否都是本批新增行」（是→union），不要因为「它们改的是同一个方法/同一个 assertTrue 链」就以为要选边。本轮实例：`PluginSettingsPersistenceTest` 里两分支各插一条 `assertTrue`（zh 侧文案断言 + en 侧文案断言）+ 各自把复选框总数注释与 `assertEquals(…, 43, …)` 推进一格 ⇒ 解法=断言双保留 + 注释行双保留 + 计数推进到 **+2 后的真值**（41→42→43）；`CHANGELOG.md` 冲突=HEAD 侧 `### Added` 段 vs 分支侧 `### Changed` 段 ⇒ **两节双保留**（不是取一侧整段）。
11. **合并后「手工解的那一处」必须单独验证，且先排除陈旧二进制假红（20261009 实测）**：解完 union 后跑被改的那个测试类，首轮 **17 红全是 `NoSuchMethodError: PluginSettings$State.<init>(…新参…)`**——即 [[pitfall-regression-false-failure-flakes]] 第 0 条（数据类加字段后旧测试二进制未重编译），`compileTestKotlin --rerun-tasks` 后全绿，**证明手工合并无语义错**。判据=**红的信息里若出现构造器/方法**签名**不匹配（而非断言失败），先重编译再判合并对错**；只有断言类失败才是真的合并写错了。

12. **「编译过」的合并仍可能藏着语义缝，两类高发形态要专门取证（20261010 T-MergeMasterToDev2 十冲突文件实测，两处都是真缝）**：①**回调接线被单侧删除，另一侧还在依赖它**——`SqlLogPanel` 的日志页搜索框，master 的 `T-SearchToggleNativeLook`（`2f992b2`）迁平台原生 `SearchTextArea` 时**丢了 `DocumentListener` 接线**：`onSearchTextChanged()`/`searchDebounceTimer` 成了**零调用孤儿**、两个 `javax.swing.event` 导入变成未用、`hideSearch()` 还写着「非空时触发 DocumentListener 清过滤」的注释——**编译全绿、测试全绿**（测试钩子 `applySearchTextForTest` 直调内部入口，覆盖不到真实键入分派，同 [[pitfall-fake-green-test-assertions]] ⑬）。dev 侧原接线在 `buildSearchField` 里，合并弃该函数后接线一并消失 ⇒ 补 `init` 块接线（提交 `87c1141`）。**判据**：合并/重构后 grep「零调用的回调注册点」（`addXxxListener` 的配套回调、`onXxx` 命名函数无调用者）＋「未用导入」＋「注释描述的行为实现里没有」三件套，作为编译门之外的独立取证；尤其当一侧替换了另一侧的 UI 装配函数时。②**枚举/常量重命名只推进一半**——`SqlPreviewPanel` 的 `embedConsole(..., previewMode = true)` 撞上 `1501ebf` 把入参归口为 `embedMode: ConsoleEmbedMode` 的重构（该笔**漏迁 R42 DML 影响面预演 probe 调用点**，`95c5bd5` 引入）。**这条还暴露一个更值钱的形态：dev 自身 tip 就编译不过**——漏迁那笔晚于 dev 最后一次门禁（`27009aa`），此后 dev 从未编译过一次。**判据**：合并前对**每个两侧分支的 tip 单独跑一次编译门**（不只是合并树）——「目标分支自己就是红的」会把它后面的所有读数都污染。③配套：源码计数守卫会随改动同步（`PrepareSingleFlightGateTest` 断言 `embedConsole(consoleMessage, embedMode = EXECUTE)` 恰 5 处，合并后真值 6，须连注释一起改为 6 并说明新增那处为何是 EXECUTE 而非 PREVIEW）；**改计数型守卫前先读它的期望值来源**，别只改断言数字。

13. **巨型索引文件「只改我这一行」的隔离法在这里基本不需要——正解是取并集，且用户要的可能是全表改一处（20261015 T-MergeSqlLogToMaster 实测）**：23 笔特性分支并入已前进 8 笔的 master，唯一文本冲突是 `docs/索引/开发计划.md`（两侧各加行 + 同一份计划两行状态文案分歧）。**判据＝先量「两侧相对 base 各自新增/替换了哪些行」**（`git show :1:/:2:/:3:<path>` 取三阶段 blob 逐行 diff），确认冲突片两侧**都是新增** ⇒ union：两侧行一条不丢、分歧行的**状态文案统一成一版但保留各自独有注记**（本例保留 master 侧的 V179/V181 待走查字样，只把「未并 master」改成「已并 master」）。前一版记忆里的「零上下文补丁被模糊定位到文件末尾」是「只想提交一行」时的隔离问题，**合并场景下不要往那个方向想**。
    - **用户随后追加口径（本条真正的产品教训）：索引里的相对链接前缀要对（本例 538 条同型改一处）**——该文件在 `docs/索引/` 下，链接写作 `./开发计划/<file>` 少一个点，**正确形态是 `../开发计划/<file>`**（与文件内 `../MEMORY.md` 一致），改前全表 `grep -c "](./"` 与改后 `grep -c "](../开发计划/"` 双向核数。**若 `./` 与 `../` 两种前缀在需改行里都不在，才用「全表 replace_all」**——本例 538 条需改、1 条原本就对，故用两个带链接上下文锚点的 Edit，绝不用「`./`→`../`」裸替换字符串。改完**逐条 `os.path.isfile`（相对该文件所在目录）实测 0 断链**，别只数行数。出题方是用户（他看渲染出来的文档时发现点不进去），我原先只按「冲突解掉」交差、没验链接可达性——**文档合并的收尾判据不是「无冲突标记」，是「表里的每条链接都点得开」**。
14. **两处自动合并文件必须逐行核「有没有取一侧丢一半」（20261015 实测形态）**：`CHANGELOG.md` 与 `docs/变更记录.md` 由 git 自动合并，`git status` 里显示为普通 `M`、无冲突标记，**看着像没事**——实际要拿两侧 blob 与工作树结果做**双向子集检查**（已核验结论：master 全部行 ⊂ 合并结果 且 分支全部行 ⊂ 合并结果，即真并集）。做法＝`git show HEAD:<f>` / `git show MERGE_HEAD:<f>` 导出后 `tr -d '\r'`（本仓 CRLF 会让 diff 整片假差异）再 diff。**判据一句话：`diff 侧边 结果 | grep '^<'` 为空 = 该侧没有丢行**。
15. **合并提交前先量「代码侧是否真有交叉改动」，无交叉就能给出「不存在自动合并的语义缝」这句结论（20261015）**：`comm -12 <(git diff --name-only master...branch | sort) <(git diff --name-only branch...master | sort)` 求两侧改动文件交集——本例 35 vs 23 个文件，交集只有 `CHANGELOG.md` 与 `docs/变更记录.md`，`src/main` 零同文件 ⇒ 自动合并区不含生产代码。**有这句实测打底，才敢说「合并语法干净」不等于「代码语义没事」，也才知道该不该复跑全量门禁**（本例仍跑了，因为带 `src/main` 的 23 笔是首次落到 master 这个新 base 上）。
16. **合并后仍要跑一次权威全量，且要按并行登记表避让别人（20261015 实测）**：`python C:/Users/USER/.zcode/cli/parallel_tasks.py check` 报出他会话 `T-M19-SqlContext` 在 dev 工作树跑定向测试 ⇒ 先 `register --name <本任务> --sandbox <独立名>` 再跑；跑前 `timeout 10 docker info` 验 daemon。判据＝`Get-CimInstance Win32_Process` 过滤 `gradlew|<task>` 时**看命令行里的树路径**（另树的 gradle 不算撞车，本树有自己的 daemon）。

17. **索引表里「一侧的行是过时状态」不是 union，要取另一侧（20261024 t-sql-insight 并 master 实测）**：`docs/索引/开发计划.md` 里 master 侧的 T-SqlInsight 行仍写「实施组织已定案，功能未开工」，而分支侧早已是「已实施、六轮门禁通过」。**冲突块两侧都是「同一条目的两个状态版本」时，union 会保留两条自相矛盾的记录**——正解＝按事实取较新一侧整行覆盖，同时把 master 侧新增的 26 行计划条目一条不丢。判据：先看冲突片两侧是「不同条目各加一行」（union）还是「同一条目不同状态」（取新），二者在同一文件里会混着出现。
18. **worktree 的 `.git` 是文件不是目录——提交信息不能写进去（20261024 实测）**：在 `mpsv-sql-insight` 工作树里 `Write F:\...\mpsv-sql-insight\.git\merge-msg-insight.txt` 直接报 `EEXIST: file already exists, mkdir '...\.git'`（linked worktree 的 `.git` 是指向真实 gitdir 的文本指针）。**提交信息一律写 `C:/Users/USER/AppData/Local/Temp/*.txt` 再 `git commit -F`**，别往 `.git/` 里放。
19. **「合并完成」的判据是 `--is-ancestor`，而且它立刻会过期（20261024 实测）**：合完 67 笔后 `git rev-list --left-right --count master...t-sql-insight` 变成 `2 178`——**并行会话在合并进行中又往 master 落了 2 笔**，于是要再合一轮（零冲突）。所以交差口径不是「合过了」，而是「`git merge-base --is-ancestor master <branch>` 为真」；回流/交接前必须重跑这一条，别拿几十分钟前的读数当现况。也正因为上游会动，本轮只跑定向不跑全量是合理的（全量读数同样会过期）。

20. **merge-tree 预演的基点在「先合一支再合另一支」后会失效（20261031 fr45→dev→magpie 实测）**：对 `dev` 预演 `t-magpie-gems` 报**零冲突**，于是先合 `t-fr45-integration`（3 处文档冲突解完）再合 magpie —— **实际撞出 3 处冲突**（双语 `MpSqlVisualizerBundle*.properties`、`convention/BannedApiSourceScanTest.kt` 白名单）。原因＝预演用的是旧 dev 基点，fr45 合入后两侧同时改过这些文件（fr45 加 bannedApi 键与 `BannedApiConfigurable.kt` 白名单，magpie 加 landing 键与 `UpdateSection.kt` 白名单）。**判据：串行合并多支时，每合完一支就要对下一支重跑一次 `merge-tree` 预演**，别拿第一轮的预演结论当全链结论。
21. **Git 会把对侧相邻两行拼成一行（巨长表格行特有形态，20261031 实测）**：`docs/变更记录.md` 冲突块里，对侧（fr45）本应是两条独立条目（FR-0045 裁决条目 + 2026-10-30 beta.2 条目），合并后 beta.2 的正文被**拼接到 FR-0045 条目行尾**，形成 `…（§8.1~§8.4 分券台账） |：范围＝… id 1256540 |` 这种一行两条的怪形态。**判别法**：拿对侧原始文件 `git show <branch>:<file>` 逐行比对，确认该段在对侧本就不在同一行 ⇒ 是合并拼接而非原文。**修法**＝按 `|：` 这个粘连点截断该行（保留本侧条目 + ` |` 收尾），并在报告里写明删了多少字符（本轮 738 字符）；直接删标记行不够，肉眼扫「无 `<<<<<<<`」也发现不了。
22. **索引类文件的 union 不能写成「HEAD 第一行 + 对侧全部」（20261031 实测丢 3 行）**：解 `docs/索引/开发计划.md` 时用「`head[0]` + `theirs` 全部」合并，结果丢掉 master 侧另外 3 行（r34 册、RecordSkillConsolidate、XmlBraceNested）。**正解＝先量两侧相对 base 各自新增了哪些行**（`git show :1:/:2:/:3:<path>` 或直接对 master 版 grep 关键册名），再逐行 union；「同一条目不同状态」仍按第 17 条取较新一侧。解完必须跑一次索引缺口对账（锚 vs 目录 md 数 + 孤儿清单），本轮据此发现并补回。

23. **一侧做过「文件拆分」时，另一侧打在拆分前大文件上的改动全部变成 move-vs-modify 冲突（20261103 master→dev 实测，13 文件 22 块）**：dev 把 `DataSourceSelector.kt`/`DataSourceSelectorResults.kt`/`SqlPreviewService.kt` 按 D202 拆出 `DataSourceSelectorConsoleText.kt`、`SqlPreviewServiceStatementOps.kt` 等，master 的 v2026.11.2/11.3 修复正好改在被搬走的函数上 ⇒ 冲突块呈现为「`<<<<<<< HEAD` 下一行就是 `=======`」（HEAD 侧为空 = 本侧已删除该区域），master 侧是一大段函数体。**裁决原则＝保拆分形态、把 master 的语义增量搬进新落点**，绝不能用 `checkout --theirs` 整文件取对侧（会整块回退拆分）。操作顺序：①`sed -i 'A,Bd'` 删掉 master 整块（先 `sed -n 'Ap;Bp'` 确认首尾正是 `=======`/`>>>>>>>`）；②把该块里 master 新增的**语义增量**（如 `chain.pageLimit` 闸、`clearConsoleHistory` 三参 + `WriteCommandAction`）单独补进新文件；③**跨调用回读**确认 sed 落盘（本环境 Bash 内写文件有「同进程回读成功、跨调用丢失」的先例，见 [[pitfall-tool-echo-vs-disk-state]]）；④删块前逐名 grep 一遍新文件，确认被删的函数在新文件里一个不少（本轮 20 个符号全在，才敢整块删）。另：**不要用 `git patch-id` 判「这笔是不是已经合过了」**——cherry-pick 到不同 base 上 patch 内容不同、patch-id 必不同；两侧还常有同 subject 不同 hash 的提交（`2aa4f080` vs `43891d81`）。判重只能看内容 diff。

24. **文档里的「计数」两侧会各报一个过时值，合并后必须按合并树重算，不能挑一侧（20261103 实测）**：架构 03 的测试三档（827 vs 809）、守卫族（51+6 vs 48+5）、服务数（16 vs 15）、经验总结篇数（38 vs 39）、调研报告篇数（103 vs 100）两侧全都不同且**都不等于合并后的真值**。做法＝解完冲突立即用一条命令量真值再回填：`find src/test -name '*Test.kt' | wc -l` + 按 `:\s*(Base|Heavy)PlatformTestCase` 分类、`find src/test -name '*Guard*Test.kt' | wc -l`、`grep -rl '@Service(Service.Level.APP)' src/main/kotlin | wc -l`、`ls docs/经验总结 | wc -l`。**另一条同族坑**：同一功能两侧各写了一版守卫且命名相反（dev 的 `ExplainStructuredDefaultOnGuardTest` vs master 的 `…DefaultOffGuardTest`），真值以仓里实际存在的那个文件为准，别按「较新一侧」猜。索引表（`docs/索引/开发计划.md`）的 union 仍按第 17/22 条：按文件名去重、同条目取较新状态，缺的条目一条不丢。
