新仓库（`songsrv-backup/v2`，快照 `f3f9fd64`）首轮 **dump→restore 闭环实测**：9 引擎全部打通（临时库已清）。

## 一、为什么先修采集器

恢复演练的前提是「有内容丰富的当日 dump」。首轮采集（17:08）暴露采集器四个 bug，dbs 目录只剩 1 个文件：

1. **MySQL 族枚举拿 dump 工具当客户端**——`mysqldump` 没有 `-e` 选项，`SHOW DATABASES` 恒空 → mariadb/mysql8 无 dump。改用 `mysql -N -e 'SHOW DATABASES'`。
2. **gs_dump/gsql 不认 PGPASSWORD**（skill 老坑）→ openGauss/Vastbase 枚举空、dump 卡 `Password:`；而 **pg_dump 的 `-W` 是无参 flag**（强制提示），连写 `-W'口令'` 会把口令字符逐个当短选项解析（`invalid option -- 'X'`）——HighGo 加 `-W` 反而坏。修法按工具分：`gs_dump/gsql/vsql` 显式 `-W'<口令>'`，`pg_dump/psql` 只用 PGPASSWORD。
3. **TiDB/OceanBase 容器内没有 mysql/mysqldump** → 增加回退路径：借 `xc3-mysql8` 的客户端走宿主网关（`172.17.0.1` + `docker port` 取宿主端口），且 **mysqldump 8.x 默认开 `--column-statistics`**（查 `information_schema.column_statistics`，TiDB/OB 无此表）必须 `--column-statistics=0`。
4. **`dbuser_for` 里 mariadb 与 mysql8 共用 `MDB_USER`**——mysql8 容器里没有 `xc3` 用户（只有 `root@%`），枚举恒空。拆分 `MYSQL8_USER=root` 并落进 `/etc/svbackup/db.env`。

三轮修复迭代还踩了两个 shell 坑，一并记入：**`timeout` 是外部命令调不动 shell 函数**（函数体内自带 timeout）；函数版 dump 重写时**丢了 `> "$out"` 重定向**（dump 输出全进脚本 stdout，产物文件恒空却报 FAIL）。另：dump 失败不再 `rm -f "$out"`（保留同日上一轮成功产物，避免重跑失败把好备份删了）。

五轮采集（17:08→17:32）从 FAIL=6 到 **FAIL=0**：12 个 dump 覆盖 8 引擎（vastbase A/B 各 2 库、opengauss 2 库、gaussdb、highgo、mariadb、mysql8、tidb、oceanbase）。MSSQL 无业务库（`database_id > 4` 空集）不产出 bak 属正常；磐维/Oracle 落「未知族」SKIP（已知边界）。

## 二、恢复演练：9 引擎逐坑实录

`restic restore f3f9fd64 --target /tmp/verify` → 按引擎灌 `restore_verify` 临时库 → 比对 → 清理：

| 引擎 | 结果 | 关键坑 |
|---|---|---|
| MariaDB | ✓ schema 比对（源库空） | **dump 首行 `/*M!999999\- enable the sandbox mode */` 会让 mariadb 客户端忽略后续全部语句**——导入前 `sed '1d'` 删掉再改库名 |
| MySQL8 | ✓ **6 表精确行数全等**（user 3 / user_2026 3 / user_address 4 / area 3 / station_info 3 / car_device_info 4） | sed 改库名直接导 |
| TiDB | ✓（`t_probe` 还原） | 借网关导入（dump 与导入同通道） |
| OceanBase | ✓ schema 比对（源库空） | **临时库先用 `root@test` 建并授权 xc3**（xc3 无建库权）；**导入用 OB 容器内 obclient**——借 mysql 8 客户端连 OB 执行 DDL 报 `Character set '45' is not a compiled character set`（OB 的 charset 编号体系与 MySQL 8 客户端不兼容） |
| Vastbase A/B | ✓ gs_restore 完成 | **业务用户 xc3 无 CREATEDB**——超级用户是 `omm`（env `INITUSER=omm`/`INITPASSWORD`），建临时库用 omm、gs_restore 用 xc3 |
| openGauss | ✓ 超管 restore | xc3 **无权 set `session_replication_role`** → gs_restore 用超管 `opengauss`；gsql `-c` 两条语句分号串联会静默漏跑第二条，DROP/CREATE 分条 |
| GaussDB | ✓ gs_restore 完成 | omm 建库（容器内无 GAUSS_PASSWORD env，从宿主 db.env 经 `docker exec -e` 传）+ gsql 直连要 `LD_LIBRARY_PATH=/opt/gaussdb/app/lib` |
| HighGo | ✓ schema 比对（源库空） | **psql `-c` 多语句包单事务**（`DROP DATABASE cannot run inside a transaction block`）分条执行；pg_restore 的 `-U xc3` 口令是 `HG_XC3_PASS`（业务用户）不是超管 `HG_PASS` |
| MSSQL | — 无业务库 | 采集端本就不产出 bak，跳过属正常 |

补一句：源库 xc3_test 里各探针表在验证后已清（schema-only dump），所以「空库比对」的引擎以「restore_verify 建库成功 + 表清单与源一致（空）」判定；MySQL8 是唯一有业务数据的库，做的是逐表精确 COUNT 比对。
