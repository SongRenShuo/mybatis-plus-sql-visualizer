# 预览面板原生控制台嵌入：五层真因与三轮误判复盘

> 2026-11-03。T-PreviewConsoleOwnership。症状从「点执行后预览窗口毫无变化」一路查到五层独立缺陷，
> 前两轮判断都被真机日志推翻。这里记结论、记方法、记判据，避免下次再从现象猜。

## 一、用户侧症状（四条，逐轮暴露）

1. 点「执行 SQL」后预览面板没变化，结果只出现在 IDEA 的 Database 控制台；
2. 面板里连原生控制台工具栏（▶ / Tx / 数据源下拉）都不出现；
3. 控制台能显示之后，又发现「还没执行就先出现结果栏」「换一条 SQL 预览，结果栏还是上一条的」；
4. 结果栏折叠后又自己长回来，占掉下半屏；工具栏最右侧数据源只剩图标、名称只在 tooltip。

四条全部修复，真机逐条验证通过。

## 二、五层真因（每一层单独修都不够）

### 1. `editorHolder` 是单槽位，被预览编辑器装配抢占

`SqlPreviewPanel.editorHolder` 是「预览编辑器」与「原生控制台 consoleHost」**共用且唯一**的显示槽。
冷启首开预热超预算（实测 820ms > 500ms）时，降级装配（`onFallback`）与迟到换装
（`tryUpgradeToLateProduct`）**都落在 `embedConsole` 之后**，各自 `removeAll()` 再挂自己的编辑器，
于是 `consoleHost` 整块被挤出显示链。

两个判据同时失效，所以谁都不会修回来：

- `consoleAttachedToMe()` 只查 `consoleHost.isAncestorOf(console)`——宿主被摘下仍为 true；
- `embedConsole` 同实例早退只查 `console.parent === consoleHost`——同上。

真机签名（`idea.log` 09:42）：

```
09:42:24.509  embedConsole identity: id=941301681 ... embedMode=PREVIEW
09:42:24.811  in-memory PSI preview document created (len=204)
09:42:25.107  late prewarm product consumed: editor upgraded
09:42:30.848  showSql branch=nativeDoc: ... attachedToMe=true     ← 判断说还挂着，其实没有
```

修法：新增 `mountEditorHolderContent` 作为 `editorHolder` 的唯一装配口；控制台在位时保留
`consoleHost`，预览编辑器只作文档/状态载体；归属判据补 `editorHolder.isAncestorOf(consoleHost)`。

### 2. DBN 对同一 exec 文件复用同一个结果面板，新建控制台路径没有清场

两次预览的 `resultComponent` 是**同一个实例**（真机 id 均为 839493854），首次取到就带
`889x248` 的已布局尺寸。旧的 `Result 1` 页签原样留着 → `resultAreaHasContent` 恒 true →
折叠判据失效 →「未执行先出现结果栏」「换 SQL 结果不隔离」。

复用路径（`reuseSharedConsole`）本来就有清场，**新建控制台路径（`prepareAfterEditorResolved`）
一直缺**。修法：预览路径（`!executeNow`）补 `clearResultContents` + `clearConsoleHistory`。

### 3. 接管组没覆写 `displayTextInToolbar()`，工具栏退化成纯图标

平台在 `AnAction.createTemplatePresentation()` 里按 `displayTextInToolbar()` 决定写不写
`SHOW_TEXT_IN_TOOLBAR`，`ActionToolbarImpl.createToolbarButton()` 再据此选
`ActionButtonWithText` 还是 `ActionButton`（243 `app-client.jar` 字节码实证）。
原生 `ChooseDataSourceAction.displayTextInToolbar()` 返回 **true**，接管组继承 `AnAction` 的 false。

**`isPopup=false` 不是开关**：非 popup 组在工具栏里会把子项摊平成一行按钮，实测把整条 header
工具栏挤没（`31d6db38` 已回退过）。`setPerformGroup` 也不是这条链的开关。

### 4. 折叠被结果区的 160px 最小高度钳制

`JSplitPane.setDividerLocation(1.0)` 会被子组件 `minimumSize` 钳住。结果区为了「执行后不被压回
preferred 84px」设了 `(w,160)` 兜底（M36.5.64），于是推 1.0 只推到 `height-163`——真机
`bottom≈165px`、divider≈0.67。

修法：`applyConsoleBottomCollapse(sp, collapse, tag)`，折叠时同时清零最小高度并推 divider。

### 5. 折叠成功后仍会被两处复位

- **回收守卫**：DBN 抢走结果组件后 `reclaimResultBottom` 挂回时**无条件**写回 `minimumSize=(…,160)`，
  折叠 2.5 秒后被弹回 ~0.67。真机铁证：

  ```
  11:23:57,417  [Collapse] embed-firstResize collapse=true h=511 divider=304→508 bottomMin=…160→0x0
  11:23:57,998  result reclaim guard: bottom re-mounted (id=945302547, n=1, collapsed=true)
  ```

- **split 放大**：divider 停在旧的**绝对**位置，新增高度全分给结果区（h 150→490 最明显）。

修法：守卫读 `BOTTOM_COLLAPSED_MARK`；折叠态挂常驻 resize 监听重新贴底；`prepare/reuse` 两处折叠
加 `height > 0` 守卫（h=0 上算出的 `divider=0` 会让底部吃掉全部新增高度）；`buildConsoleSplitPane`
里那个「无条件 0.6」的一次性监听也要读标记跳过。

## 三、三轮误判为什么发生

| 轮次 | 当时的判断 | 被什么推翻 |
|---|---|---|
| 第一轮 | 「结果区组件被 DBN 抽走、补挂没触发」 | 补挂每次都在跑（`persistent console bottom swapped`），它补的是一块**不在显示链上**的 SplitPane |
| 第二轮 | 「`consoleComponent` 不是 JSplitPane，所以 `is` 判定为 false」 | 日志早写了 `embed component=...buildConsoleSplitPane$1[...VERTICAL_SPLIT]`，前提没先证伪 |
| 第三轮 | 「折叠判据没生效」 | 加带标签的日志后看到 `collapse=true divider=304→508` 成功，2.5 秒后被回收守卫打回 |

可复用的方法：

1. **判据要带"谁、在什么时候、改成了什么"**。只打 `collapse=true` 看不出被谁复位；
   打成 `[Collapse] <tag> collapse=<bool> h=<高> divider=<前>→<后> bottomMin=<前>→<后>`
   才一眼看出"折叠成功 → 之后又被改了"。
2. **真机日志的因果顺序比截图可靠**。`collapse=true` 与 `result reclaim guard` 相邻两行就是全部答案。
3. **无头测试要按真实时序造**：小高度先折一次 → 再放大。只测"折一次对不对"测不出"折叠被放大弹开"。
   headless 里 `setSize` 不给未显示组件派发 `COMPONENT_RESIZED`，要手动 `dispatchEvent`。
4. **平台行为以字节码为准**。`displayTextInToolbar` / `ActionButtonWithText` 这条链是
   `javap` 出来的，不是猜出来的。
5. **先证伪自己的前提**。第二轮如果先 `grep "embed component="` 就能省掉一轮。

## 四、坑清单（带判据，可直接抄）

- `JSplitPane.setDividerLocation` 被子组件 `minimumSize` 钳制——折叠必须连最小高度一起管；
- 同一 split 上多个一次性 `componentResized` 监听按**注册顺序**通知，后注册的赢；
- 单槽位容器（`editorHolder`）只能有一个装配口，所有权判据必须包含"宿主是否仍在显示链上"；
- 平台 `AnAction.displayTextInToolbar()` 决定工具栏渲染文案；`isPopup=false` 会把子项摊平；
- DBN 对同一 exec 文件复用同一个 `RunnerLayoutUi` 内容面板，新建控制台不会自动清旧页签；
- 262 文档写断言：`setText` 必须在 `WriteCommandAction` 内；反射 `invoke` 抛的
  `InvocationTargetException` 会把真因裹成方法签名（日志里只剩
  `com.intellij...DocumentImpl.setText(java.lang.String)`），排查时要打 `cause`；
- 预览态判「有没有结果区」看 `bottomComponent` + `resultAreaHasContent`，不是看 divider
  （折叠后 bottom 仍在 split 里，只是 0 高）。

## 五、验证口径

无头用例（全部可在秒级跑完）：

- `PreviewEditorAssemblyKeepsConsoleTest`：控制台在位时，降级装配/迟到换装/准备中占位都不得
  把它挤出显示链；宿主被摘下后同实例 `embedConsole` 必须重挂（修复前 4 红）；
- `PreviewResultIsolationTest`：清场只摘结果页签保留 Output、预览链清场接线、
  折叠连最小高度一起放开、折叠后放大不弹开、回收守卫折叠感知、工具栏文案开关。

真机锚点（每次预览/执行都可用）：

## 六、遗留

- `ensureResultBottomMounted`（第一轮的产物）仍在代码里，作为「split 下半区为 null」的幂等兜底；
  与最终根因无关，但保留无害。
- `Suppressed a frequent exception ... createEditor path / releaseEditor path` 是
  `T-RefreshDbSteal` 的栈探针被平台日志节流，属既有噪音，不影响功能。

## 附：下次遇到同类症状的排查顺序（先做这五步再动手）

1. **先看组件树，不看截图**。面板里显示的到底是谁？在 `embedConsole` 与 `editorHolder` 的装配点各打一行
   `class= / parent= / isAncestorOf`，确认「控制台组件 → consoleHost → editorHolder → 面板」这条链有没有断。
   截图只能看出"没有工具栏"，看不出断在哪一层。
2. **先证伪前提，再改代码**。想加"补挂"之前，先 `grep` 日志确认那个东西**是不是真的没挂**——
   第一轮就是没做这步，给一块不在显示链上的 SplitPane 加了三层补挂。
3. **判据要带前后值**。凡是"设了没生效"的怀疑，日志必须打 `<前>→<后>`（divider、minimumSize、父容器），
   只打布尔值等于没打；有多个写入点时还要带调用点标签（`embed-firstResize` / `reclaim-guard` / …）。
4. **按真实时序复现**。折叠类问题必须在无头用例里造「小高度先折一次 → 再放大」，只测一次静态折叠
   测不出"被放大弹开"；`JSplitPane` 的 `minimumSize` 钳制也要用真实 `setSize` 才能暴露。
5. **平台行为查字节码**。`displayTextInToolbar` / `ActionButtonWithText` / `ActionPopupButton` 这类
   "为什么只画图标"的问题，`javap` 一次就有答案，别靠试参数（`isPopup=false` 试过，反而把工具栏搞没）。

排查时优先收集这五行真机日志，基本能定位到层：

```

[M36][Collapse] <tag> collapse=… h=… divider=<前>→<后> bottomMin=<前>→<后>
[M36] result reclaim guard: bottom re-mounted (id=…, n=…, collapsed=…)
[M36] result contents cleared (preview switch, removed=N)
[M36] editor assembly kept native console mounted (console=…)
```
