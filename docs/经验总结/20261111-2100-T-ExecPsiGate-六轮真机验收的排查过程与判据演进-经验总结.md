# T-ExecPsiGate 六轮真机验收：排查过程与判据演进（2026-11-11）

> 账本规则见 `docs/LESSONS.md`（L38/L39/L40 是本轮沉淀的可执行规则）。本文只记**过程与判据怎么变的**，
> 用于下次遇到"功能明明改了但用户那边不生效"时对照。

## 一句话结论

用户从 beta.1 到 beta.9（同版本号 beta.2 的重建）报了六次"还是有问题"，真正的缺口有三个、彼此独立：
**判据取错层级**（文件 vs 父目录）、**元数据走共享可变状态**（被清/被覆盖/被读方清空）、
**回调接线只接了一半**（5 个执行调用点只接了 2 个）。前五个修正都只解决前两个，最后一个缺口
让整条修复在**直接点执行**上从未生效。

## 被证伪的假设（都花了实验成本）

- **并发外部写**导致 vf 失效（R2）：344 次并发写 + refresh 零 null，否证。
- **坏映射反复 `findFile` 会缓存 null**（R3）：连续 5 次恒抛同一 CCE，无"缓存成 null"。
- **某个方言建不出 PSI**（R4）：把 38 个方言全试一遍，除测试用的无 parser 语言外都可建。
- **reparse 竞态**（R5）：探针下未复现。
- **继承方言（项目根映射 / 全局默认）是毒源**：SQL Dialects 截图显示 Global/Project 都是 `<None>`，否证。
- **落点自动改写**（F6）：技术可行、用户否掉——产品口径优先于"技术上更省事"。

## 最终根因链（三条，各自独立）

1. **判据层级**：263 的 `AbstractFileViewProvider.shouldCreatePsi()` 第一层判文件名忽略模式、第二层判
   `findDirectory(vFile.getParent())`。我们的归因面全取在**文件**上，于是"文件在内容根里、目录被记为
   ignored"这一形态表现为"四项全绿却建不出 PSI"，归因落 UNKNOWN。→ L38。
2. **元数据传递**：失败成因存在 object 字段里，靠"谁清谁写"传递。四轮里被三种机制各打掉一次
   （预热链入口清空 / 并发覆盖 / 同一次失败的第二次渲染时读方清空）。最终改成编码进文案。→ L40。
3. **接线**：`onError` 有五个调用点，其中四个直连 `resultPanel.showError`。第 1、2 条修好之后，
   占位逻辑仍然只在那两个已接线的入口上跑。→ L39。

## 为什么花了六轮

- **交付靠嘴**：四个同版本号的包只在消息里说"重建了"，没给 sha256、没让核对安装目录时间戳。
  用户实际装的停在 F6b，F7 从未被验。
- **先猜后取证**：前三轮都在"报错信息为什么丢"上打补丁，没有先问"这条信息有没有人读"。
- **只改复现路径**：接线类修复只覆盖了当时复现走的那条链，其余调用点没审计。

## 下次遇到"改了但用户那边不生效"的检查单

1. 先做**产物取证**：用户装的是不是含修复的包（扫安装目录 jar 的类/字节），不信版本号（L35）。
2. 先问**有没有人读**：这条逻辑挂在哪几个回调/事件上，逐一 `grep` 调用点（L39）。
3. 再问**数据丢没丢**：一次性元数据是否走了共享可变状态；有没有读后清空的约定（L40）。
4. 再问**判据层级对不对**：解释平台拒绝时，读字节码确认它问的是文件、目录还是内容根（L38）。
5. 现象"时有时无 / 某入口恒无"时，先 diff 两个入口的接线，别先怀疑竞态。
6. 一次真机反馈只改一个可判定的点，并在回复里给出**用户可自查的凭据**（sha256、日志行、
   面板上应出现的具体字段），让下一轮能定性而不是再猜。
7. 产品口径要单独确认：能修≠该修（落点自动改写就是例子）。
