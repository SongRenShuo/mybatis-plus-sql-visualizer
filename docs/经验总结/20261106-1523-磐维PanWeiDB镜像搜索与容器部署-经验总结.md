# 磐维 PanWeiDB 镜像搜索与容器部署（2026-11-06）

> 任务：查明国产数据库「磐维 PanWeiDB」（中国移动，openGauss 系）有没有可用的 Docker 镜像；
> 找到就部署到测试服务器，找不到就如实报告（禁止拿 openGauss/GaussDB 镜像改名充数）。
>
> 结果：**没有官方镜像**；在阿里云个人命名空间找到第三方重打包镜像并部署出 **B（MySQL 兼容）与
> A（Oracle 兼容）两个实例**，均通过**外部客户端**实测；过程中解掉三处硬阻塞。
> 完整搜索轨迹与结论见 `docs/调研报告/20261106-1435-磐维PanWeiDB容器镜像搜索与真机部署-调研报告.md`。

## 一、结论先行

| 问题 | 答案 |

| 有官方镜像吗 | **没有**。Docker Hub / quay / ghcr / 三家国内公有云 registry 全无；`panwei.tech`、`open.10086.cn` 下载中心只有白皮书与手册 |

## 二、镜像搜索轨迹（逐源留痕）

先说一条**判读法**，它决定了后面所有「0 命中」能不能当结论：

> **先跑对照查询证明接口本身正常，再判本产品的 0 是真 0。**
> 本轮 `query=opengauss` 回 111 条（接口正常 + 搜索确实能用），此时 `query=panweidb` 回 0 才是硬结论；
> 反过来 ghcr.io 的对照组（公开仓库 `homebrew/core/hello`）也没取到 200 ⇒ 该源本轮探测不可信，
> 结论只能写「未取到」，**不能写「没有」**。

  10136 行，**全文没有 `docker` 与「镜像」**。文档不提容器本身就是「无官方镜像」的一条旁证，比纯搜索结果硬。

## 三、命中镜像的取证与定级

**先钉死三样东西再动手**：digest、包内产品版本、底座形态。

| 项 | 值 |
|---|---|
| index digest | `sha256:18ecce711e55467a130150d1333fcd24f9c8b6fa5a5b180df4802d1269b6df6d`（OCI image index，amd64+arm64） |
| amd64 manifest | `sha256:0a7df528c7e753b036820a1c1f3b2df118b0d0fbeea7ebbb50c1ec8e7973360b` |
| 体积 | 压缩层合计 1792.9 MB（10 层），`docker images` 本地 2.9 GB |
| 构建时间 | 2026-05-29 |
| 包内产品 | `PanWeiDB_V3.0-S3.4.0_B01`（`/root/PanWeiDB_db.tar.gz`，884 MB） |
| 底座 | openEuler rootfs + systemd（`ENTRYPOINT /usr/sbin/init`） |
| 启动逻辑 | `init-db.service` → `/root/run.sh`：解包 → ansible → `gs_install` → 改 `pwadmin` 密码 → `tail -f /dev/null` |

**怎么判断「真厂商产物被重打包」而不是「改名冒牌」**——看包内有没有该产品的专属指纹：

- 磐维指纹：`script/gs_install`、`script/gs_om`、`/root/PanWeiDB_db.tar.gz`、
  `PanWeiDB_V3.0-S3.4.0_B01-Linux-64bit.tar.bz2`、角色 `pwadmin`/`pwaudit`/`pwsso`（`pwsso` 是磐维自有）、
  `gs_initdb --dbcompatibility`。⇒ 内容是真的。
- 但**分发链无人背书**：版本来源、是否被改、有无夹带，都不可证。⇒ 定级为「第三方重打包，非厂商官方分发」，
  **只作内部验证**，对外结论/文档逐处标来源（仓库全名 + digest + 构建时间）。

这条正好是本任务红线的落点：**找不到官方镜像时，把「真厂商产物被第三方重打包」和「拿 openGauss 改名充数」
分开写清**，而不是笼统说「找到了镜像」。

## 四、三处硬阻塞的定位过程

镜像起得来不等于装得上。本轮第一个容器 `docker run` 之后，装到一半就退出，**每次修完一处又冒出下一处**，
一共三处。定位手法都是**读厂商自己的代码**（脚本就在 `/database/panweidb/soft/script/`），不是猜。

### 1. CPU 预检：`avx` + `rdtscp` 是门槛，不是依赖

现象：`gs_preinstall` 抛 `Warning: This cluster is missing the rdtscp or avx instruction` 后退出。

定位：读 `script/local/PreInstallUtility.py`：

```python
def check_cpu_instructions(self):
    if "x86_64" not in platform.machine():
        return
    cmd = "lscpu | grep rdtscp && lscpu | grep avx"
    (status, output) = subprocess.getstatusoutput(cmd)
    if status != 0 or not output:
        raise Exception("%s. Command is %s\nOutput is %s" % (cpu_mission, cmd, output))
```

注意是 `&&`：**两个都要有**。本宿主是 QEMU vCPU，实测 `avx / avx2 / rdtscp / sse4_1 / sse4_2 / popcnt`
**全部没有**（只有 `cx16`），见下表：

```
model name : QEMU Virtual CPU version 2.5+
avx: NO   avx2: NO   rdtscp: NO   sse4_1: NO   sse4_2: NO   popcnt: NO   cx16: YES
```

处置：把该函数末尾的 `raise Exception(cpu_mission)` 改成 `pass`（先 `cp` 留 `.orig`）。

**关键取证是「绕过之后到底行不行」**：改完重跑，`gs_preinstall` 打
`Successfully checked cpu instructions.`，一路到 initdb 成功（数据目录出现 `PG_VERSION`、`PW_COMPATIBILITY`）、
`gs_ctl start` 打 `server started`、`gs_checkos` 通过。⇒ **是预检过严，不是引擎真需要这些指令**。
这一条必须落到结论里，否则读者会以为「在无 avx 机器上跑磐维不安全」。

顺带一个反面参照（本仓台账在册）：`enmotech/opengauss:5.0.0` 在同一宿主是 initdb 阶段
`Illegal instruction` —— 那种**绕过预检也救不了**，因为二进制真用了。两者形态不同，别互相套用。

### 2. 一个 `checkDockerEnv()==False` 连带 9 处「容器内可容忍」分支失效

第二处现象：`gs_checkos` 失败，包着两层错误。外层是笼统的
`[GAUSS-51400] : Failed to execute the command: .../gs_checkos ...`，**真正的内层**在
`gs_local.log` 里：

```
[GAUSS-51400] : Failed to execute the command: find /etc/sysconfig/network-scripts -iname 'ifcfg-*-lo' -print.
```

读 `gspylib/common/Common.py` 的 `getNetWorkConfFile()`，发现它其实**已经写了容器容忍**：

```python
(status, output) = subprocess.getstatusoutput(cmd)
if (status != 0 and DefaultValue.checkDockerEnv()):
    return output.strip()          # 容器里找不到就容忍
if (status != 0):
    raise Exception(...)           # 非容器才报错
```

于是问题是 `checkDockerEnv()` 为什么是 False：

```python
def checkDockerEnv():
    cmd = "egrep  '^1:.+(docker|lxc|kubepods)' /proc/1/cgroup"
    (status, output) = subprocess.getstatusoutput(cmd)
    return True if output else False
```

它认的是 **cgroup v1** 形态（`1:...:/docker/...`）。本宿主是 **cgroup v2**，`/proc/1/cgroup` 只有
`0::/init.scope` ⇒ 恒 False ⇒ **所有「容器内可容忍」分支全部走不到**。

`grep -rn "checkDockerEnv()"` 数了一下：**9 处**（`LocalCheckOS.py` ×2、`LocalCheck.py`、`Common.py`、
`inspection/items/network/CheckMultiQueue.py`、`inspection/items/os/CheckHyperThread.py`、
`inspection/common/SharedFuncs.py` ×3）。也就是说这一个函数修好，9 个坑一起消失——所以**修探测函数比逐个
patch 检查点干净**。

处置（`gspylib/common/Common.py`）：

```python
def checkDockerEnv():
    # patched-by-agent: cgroup v2 hosts (/proc/1/cgroup = "0::/...") are not matched
    # by the cgroup v1 grep below, so fall back to the container marker files.
    if os.path.exists("/.dockerenv") or os.path.exists("/run/.containerenv"):
        return True
    cmd = "egrep  '^1:.+(docker|lxc|kubepods)' /proc/1/cgroup"
```

改完这一处，**下一个原本等着报错的** `/sbin/ethtool -g eth0`（GAUSS-50612 `Operation not supported`，
虚拟网卡不支持 ring 参数）也自动被容忍了（同一函数在 `getNetWorkTXRXValue()` 里把关）。

顺手做的第二件事：`mkdir -p /etc/sysconfig/network-scripts`。因为 `find` 在**目录不存在**时返回非 0，
而在**目录存在但无匹配**时返回 0，配合上面的容忍分支就够了（这条也让「不修探测函数、只补目录」成为
一条独立的降级选项）。

### 3. `listen_addresses` 绑死安装期容器 IP，重启换 IP 就起不来

第三处**不是安装期**发现的，而是我 `docker restart` 之后：容器 Up，但库里连不上，
`gs_ctl start` 手打报：

```
LOG:  <netstat>:tcp6 ... ::1:17700 ... LISTEN 361/panweidb
FATAL:  could not create listen socket for "172.17.0.12:17700"
```

读 `run.sh` 就明白了——安装时它做过一次 IP 改写：

```bash
ip=$(ifconfig |grep inet |awk '{print $2}' |egrep -v '127.0.0.1|::1' |head -1)
sed -i "s/localhost/$ip/g"  /database/panweidb/soft/cluster_config.xml
```

于是 `postgresql.conf` 里落成 `listen_addresses = 'localhost,172.17.0.12'`；容器重建/重启后拿到
`172.17.0.13`，绑不上。处置是在 `run.sh` 的启动分支（`gs_ctl start` 之前）按当前 IP 重写：

```bash
ip=$(hostname -I | awk '{print $1}')
sed -i "/^listen_addresses/c\\listen_addresses = 'localhost,${ip}'" /database/panweidb/data/postgresql.conf
```

两个试错值得记：

- `gs_guc set -c "listen_addresses=*"` → `ERROR: The parameter(*) exists illegal character:*`
- `gs_guc set -c "listen_addresses=0.0.0.0,localhost"` → `The value "0.0.0.0,localhost" ... is incorrect`

⇒ **`gs_guc` 不收 `*`、也不收逗号值，只能改文件**。

改完做了**真实重启验证**（`docker restart panweidb-test`）：容器自愈起库，且重启前的探针数据仍在
（`select name from pw_probe` → `磐维`）。这一步不能省——只写「应该自愈」不算数。

另有一处**非阻塞**噪音：`hostnamectl set-hostname pdb` 在容器内报 `Device or resource busy`，
但主机名实际已生效（`hostname` 回 `pdb`），`run.sh` 的 `set -e` 被注释掉所以没中断。

## 五、内存怎么腾（这一步差点让第二个实例起不来）

宿主 16 GB，**已有 11 个容器**。起第一个磐维实例后 `available` 掉到 1.6 GB 左右，装第二个时
我先把第一个 `docker stop` 腾出内存，装完再回来调两边参数。

调参时踩了引擎自己的下限（这条比数字更有用）：

```
FATAL: the values of memory out of limit, the database failed to be started,
max_process_memory (2048MB) must greater than 2GB + cstore_buffers(512MB) +
(udf_memory_limit(200MB) - UDF_DEFAULT_MEMORY(200MB)) + shared_buffers(256MB) +
preserved memory(2241MB) = 5057MB
```

⇒ **`max_process_memory` 压不到 2GB，实用下限约 5GB**；它是**记账上限不是预占**（设 8GB 时实测常驻
RSS 只有 1.4GB）。真正影响常驻的是 `shared_buffers`：默认 1GB → 改 256MB 后单实例 RSS
**1.42 GB → 0.897 GB**。

最终：两实例各 `--memory=4g/3g`、库内 `max_process_memory=8GB` + `shared_buffers=256MB`，
宿主 `available` 稳定在 **约 960 MB** —— 这个数要写进结论，它意味着**再上新库前必须先腾内存**。

## 六、部署后怎么验（三档都取了，别只到容器 Running）

1. **容器内自连**：`docker exec -u omm <容器> gsql -d postgres -t -c "select version();"`
   —— 只能证明库起了。
2. **外部客户端经宿主发布端口**（这才是「部署完成」的读数）：用另一个容器当客户端
   （`docker exec xc3-opengauss gsql -h 103.36.220.245 -p 2610x ...`）。
   第一次连会 `Invalid username/password,login denied` ——那是因为 `run.sh` 尾部的
   `alter user pwadmin` 我重跑 playbook 时没走到，改密后即通。
3. **数据正确性用 HEX 钉死**（避免中文被双编码后「看起来正常」）：
   `insert ... chr(30928)||chr(32500)` → `select name, hex(name)` → `磐维` / `E7A390E7BBB4`。

最终读数（两实例）：

```
PostgreSQL 9.2.4 on x86_64-pc-linux-gnu, compiled by g++ (GCC) 7.3.0, 64-bit
26100 (B): panweidb B   + pw_probe 中文 hex E7A390E7BBB4
26101 (A): panweidb A   + select dummy from dual → X
gs_om -t status --detail → cluster_state : Normal / DN 6001 /database/panweidb/data P Primary Normal
```

`version()` 沿用 PG 9.2.4 的字符串（openGauss 系惯例）——**不能据此判断内核版本**，真实版本以安装包名
`PanWeiDB_V3.0-S3.4.0_B01` 为准。这一条必须写进结论，否则后人会拿 9.2.4 去对标 PG 特性。

| 文件 | 改动 | 是否随卷持久 |
|---|---|---|
| `/database/panweidb/soft/script/local/PreInstallUtility.py` | `check_cpu_instructions` 的 raise → pass | 是（在 `/database` 卷里） |
| `/database/panweidb/soft/script/gspylib/common/Common.py` | `checkDockerEnv()` 加 `/.dockerenv` 判定 | 是（在 `/database` 卷里） |

> 「起容器 + 轮询等脚本解包出来就打」的方式补上的，可行但脆（时间窗几十秒到几分钟）。

## 八、没做 / 不能做

- **~~没验证~~ 后续已补齐（2026-11-06 15:0x~15:2x，主控侧）**：
  - V1 驱动（`panweidb-jdbc-1.0.0.jar`）连 A 实例 26101：`version()` / `select dummy from dual` → X / `t_order` 4 行全通；demo 用 `-Dpanweidb.version=1.0.0` 重编后假 IDE 四窗口 **12/0 ALL-PASS 43.5s**。
  - 方言渲染套件 `dialectExternalVerify`：`panwei_b`（MySQL，262 词）与 `gaussdb_kernel503`（197 词）通过；`panwei_a`（Oracle，109 词）首轮撞 `rowid`（磐维 A 内核把它做成系统列），按用户拍板在矩阵加**按实例 `skipWords` + 必填 `skipReason`** 后复跑 **PASS words=109 skip=1(rowid) 66.4s**，产品保留字表未动。
  - 结论升级：磐维 3.4.0 A/B 两档现在都有**引擎级**读数（渲染套件真执行），不再只是「实例可用 + 客户端实测通」。
- **不能做**：单实例内切兼容档（`\h create database` 无 `DBCOMPATIBILITY`；`\l` 显示连 `template*` 都是同一档）。
- **风险**：镜像来自个人命名空间。对外材料引用时必须带「第三方重打包」定语。
- **仍缺**（本条目的原意保留）：三处补丁不可重放（重建容器即丢）、两实例未进 `.local/db-env-instances.tsv` 灾难重建清单。

## 九、三条可复用的判别法

1. **0 命中要配对照查询**：证明接口能用（`query=opengauss` → 111）之后的 0 才是结论；对照组也坏掉的源
   （ghcr 本轮）只能写「未取到」。
2. **厂商预检报错先读代码，再判定「门槛 vs 依赖」**：读函数体看它到底检查什么，然后**用「绕过之后能不能跑」
   取证**——能跑就是门槛（磐维 avx），跑不了才是依赖（enmotech openGauss 的 Illegal instruction）。
3. **一个环境的探测函数失效，往往会连带一片**：本轮 `checkDockerEnv()` 一个 False 打掉 9 处容忍分支；
   `grep -rn` 数清影响面再决定「修函数还是逐个补」，别见一个修一个。
