# 测试服务器整机重建与备份体系入仓（2026-11-12）

「不大-北京-16G」（103.36.220.245）被重装系统，用户要求把之前的测试环境全部恢复，数据库账户密码不变。本文记录这次真跑一遍拿到的结论；操作口径已固化进两个 skill：`srv-backup-restore` 与 `db-env-provisioning`。

## 一、重装后的机器是什么状态

实测（不是推断）：Ubuntu 22.04、开机 16 分钟、Docker **29.9.3**（旧 28）、16C/15G/200G、CPU 仍是 QEMU vCPU（无 avx/rdtscp/sse4_2/popcnt）。`docker ps -a` / `docker images` / `docker volume ls` 全空，`/www/xc3`、`/opt/xc3-vastbase*`、`/etc/svbackup/`、`/usr/local/bin/svbackup-*`、systemd 单元、restic 二进制**全部蒸发**。这是标准的「整机重建」，不是「容器停了拉起来」。

SSH 主机密钥也变了。DBX 有两份 `known_hosts`，都要处理：

- `C:\Users\USER\.ssh\known_hosts`
- `C:\Users\USER\AppData\Roaming\com.dbx.app\plugin-data\io.dbx.ssh\known_hosts`

只删第一份会报 `Host key ... changed`（系统那份）；两份都删掉后 DBX 报 `Unknown server key`——它不会自动信任新密钥。正确做法：先 `ssh-keygen -R 103.36.220.245 -f <各文件>`，再 `ssh-keyscan -T 20 -p 22 103.36.220.245` 取新密钥**追加**进去。新旧指纹不同属重装预期，不是中间人攻击。

恢复依据全部在本地资产，与备份仓库无关：

|---|---|---|

| 凭据台账（唯一口令来源） | `.local/test-databases.md` | 回答「账号口令是什么」，**一律沿用旧值不改** |
| 重放引擎 | `dev-support/svbackup/` 之外的 `.agents/skills/db-env-provisioning/scripts/bootstrap-db-env.sh` | 幂等重建，已存在的跳过、镜像缺失才拉 |
| 种子 | `dev-support/test-demo/db/mpj_demo.sql`（首行 `SET NAMES utf8mb4;`）、demo 工作树 `schema-gaussdb.sql` | 首次 initdb 自动灌入 |
| 磐维补丁 | `dev-support/db-lab/patch-panweidb-image.sh` | 解包后、checkos 前的三处补丁 |
| 七牛 AK/SK | `.local/qiniu-keys.env` | restic 仓库访问（口令另说） |

12 个实例按引擎族/内存分三组并行部署（A 轻量标准 5 个 / B PG 族与 OceanBase 4 个 / C 磐维与 Oracle 3 个），每组一个后台子代理，符合「子代理并发 ≤3」与「慢操作走后台任务」两条纪律。镜像源实测 `docker.1ms.run`（824ms）与 `docker.m.daocloud.io`（833ms）最快，`hub.rat.dev` 可用；SQL Server 走 mcr 直连。

**踩到一个新的并发坑**：三组各自拉镜像时全部卡死十几分钟、零落盘，dockerd 却活着（`docker info` 秒回、CPU 11%）。逐条证据拼出的真因是——① Docker 从 28 升到 **29.9.3** 后默认用 containerd image store，层落在 `/var/lib/containerd/io.containerd.content.v1.content`（**不受 `data-root: /www/server/docker` 管辖**），所以「data-root 只有 236K、`docker images` 空」是假象，实际 content store 已有 2.3G 层；② 多个 `docker pull` 并发抢**同一个跨镜像共享基础层**（digest `2d473b07cdd5` 同时出现在 highgo 与 vastbase 层列表），全部停在 futex_wait；③ 主控单路实测 `hub.rat.dev/library/mariadb:10.11.11` 层陆续 `Download complete`，几分钟提交成功，证明确实是并发争抢而非镜像源坏。
⇒ 重建纪律改为：**全局任意时刻只允许 1 个 docker pull**，按组错峰（A→B→C，2.9GB 磐维最后），每拉完一个 `docker images` 确认提交再拉下一个；「各组自己串行」不够，组间也会互抢。另：`docker.m.daocloud.io` 有白名单，个人命名空间镜像（`xuxuclassmate/*`、`apecloud/*`、`gvenzl/*`）会被拒，须走 `hub.rat.dev` / `docker.1ms.run`，官方 library 镜像才用 daocloud。

**再往下挖一层**：清空所有 pull + 重启 dockerd 后单路 `docker pull` 仍全部退出、零镜像提交（hub.rat.dev / daocloud / gmssh 三源同现象），但 curl 取 manifest 秒回 http=200、containerd content store 已 2.3G。结论是 **`docker pull` 的「层落盘 → 镜像提交」在这台 Docker 29 + containerd image store 上不可用**，不是源不可达。最终走 skill §1 的兜底：registry v2 匿名 token → OCI index 选 amd64 → 子 manifest → 逐层 curl 下 blob（**带 token、串行**）→ sha256 校验 → 组 tar → `docker load` → `docker image inspect` 验提交。两个配套坑：① **blob 必须用 curl，不能用 python urllib**（后者跟 302 后拿 403）；② 带 token 的 blob 是通的（实测 116B 层 sha 匹配），慢在连接建立而非零字节，别把「慢」误判成「不通」。这些已写进 `db-env-provisioning` skill §1 第 5 条。

**选源是逐层兜底里最值钱的一步**（B 组实测，同一 76MB 共享层 12s curl）：`docker.m.daocloud.io` **0.46MB/s**、`docker.gmssh.com` 28KB/s、`docker.1ms.run` 17KB/s、`hub.rat.dev` 401（blob CDN 不认 token）。差 28 倍，按 0.46MB/s 一个 105MB 镜像约 4 分钟，按 17KB/s 要一小时以上。反直觉的是：**daocloud 的白名单只挡 `docker pull` 与 manifest 阶段，而且按 repo 放行**——`apecloud/vastbase`、`library/mariadb`、`library/mysql:8.0-debian` 全 200（digest 与部署原文逐字一致），但 **`xuxuclassmate/highgo` 与 `opengauss/opengauss` 的 manifest 403**。最终定论（A 组三轮实证：发现 → 反证 → 定论）：**daocloud 放行的其实是「它本地已缓存的 blob」，未缓存的回源一律 403，与 repo 路径 / token scope 是否一致都无关**。共享基础层 `2d473b07…` 已缓存 ⇒ 用什么路径都 200、0.46MB/s；highgo 独有层（config/L1/L9）未缓存 ⇒ 换成 `library/mariadb` 路径配同 scope token 逐一 HEAD 仍 403。中间两次口径（「blob 端点不校验 scope」「改 library 路径就通」）都被反证推翻，别再写进文档。
可行路径：manifest 从 1ms.run 取小 JSON，未缓存的 blob 只能回 1ms.run / gmssh 慢通道（实测 L9 109MB 约 28KB/s、412MB 全量约 4 小时），配 7200s + `-C -` 续传；已缓存的共享层用 `find_cached()` 从别组工作目录复用。⇒ 排期上**把能走快通道的镜像先落地、未缓存的镜像放最后慢慢下**，别让它阻塞整组交付。别从「apecloud 通」推出「所有 repo 都通」。

**轩辕合规通道的两种失败形态（别一概而论）**：highgo 首次 `net/http: timeout awaiting response headers`（大层响应超时）后 5 个大层仍留在 content store、重试 §3.3 即成功；但 gaussdb 公共域 5 层全 `Pull complete` 后**末段一个额外 blob 超时触发 dockerd 回滚**，把 5 层从 content store 清理了（82→76 blob，B 组 15:14 实证）⇒ 「pull 失败也保留层」不是普遍成立。判别口径：失败后立刻 `du -sh` content store 并按 digest 查在不在，在就复用、不在就按 §3.3 换专属域/公共域重试，不盲目换官方源。

**最值钱的一条其实是「复用 containerd content store 里已落盘的层」**（B 组 14:54 发现，决定性提速）：
`docker pull` 虽然提交不了镜像，但**层早就下载并落进**
`/var/lib/containerd/io.containerd.content.v1.content/blobs/sha256/<64hex>`（文件名即 digest、大小即原 blob 大小）。
主控独立枚举实证 **68 个 blob / 2.4G**，含 926MB、429MB、374MB、259MB、181MB、82MB、70MB、55MB、29MB 等大层，
覆盖 vastbase / highgo / opengauss / oracle / panweidb 的绝大多数层。B 组把 vastbase 13 层按 digest
`test -f` 命中后 `ln -f` 硬链接补进 workdir，逐层 sha 校验通过直接凑齐，秒级、不占带宽。
⇒ **重建第一步就该枚举 content store**，拿 manifest 每层 digest 去命中，只缺极少数才走网络；
本次若一开始就查这里，能省掉两三个小时的逐层 curl 与 4 小时慢通道。
别只看 `docker images` 空、`data-root` 只有 236K 就以为层没落盘——Docker 29 的 content store 在
`/var/lib/containerd/`（与 `data-root` 分离），`du -sh` 它才是真相。这条已写进两个 skill。

**ACR 是另一条完全独立的快通道**（C 组实测）：磐维 `registry.cn-shenzhen.aliyuncs.com/shine_fei/panweidb:3.4.0` 的 401 challenge → `dockerauth.cn-hangzhou.aliyuncs.com/auth` 匿名 token → OCI index（4 条目，amd64 digest `sha256:0a7df528…` 与本地调研报告逐字一致）→ amd64 manifest（10 层、压缩 1.79GB）→ blob `GET` 307 到 CDN（**必须 `curl -L`**），实测 **8.98MB/s**、82MB 层 9.2 秒。与 Docker Hub mirror 的故障无关，可与其它组并行跑，不必排队。三条通道（ACR / daocloud blob / Docker Hub mirror）速度差两个数量级，是这次重建耗时的主要变量。

**发现一个漏登**：重装前是 **12 个**在役容器（11-06/07 的 `docker stats` 实名表三处互证），但 TSV 只有 11 行——`xc3-oracle-free`（21521→1521，`gvenzl/oracle-free:23-slim`，service `FREEPDB1`，账号 `probe`）从没登进台账。根因是 TSV 自述「从 test-databases.md 全量抄录」，而该实例的凭据只写在 demo 工作树的 `application.yml` 里，抄录时整体漏掉。本次已补登 TSV 一行，并把「新增实例就地登记 + 交叉核对 docker stats 实名表」写进 skill §9。这个缺口在整机重建场景下等价于「该实例不存在」，正是清单纪律的价值。

## 三、备份仓库：口令丢了，数据就没了

七牛私有空间 `songsrv-backup` 仍在，AK/SK 有效（raw S3 匿名列举回 `NotSupportAnonymous`，说明桶存在且私有）。但 `restic snapshots` 报 `an empty password is not allowed`，加 `--insecure-no-password` 后报 **`wrong password or no key found`**——**restic 仓库口令 `/etc/svbackup/pass` 随重装丢失**。

查证范围：本地全工作区（三个工作树 + 同级仓）、三台存活机（香港/百度云/华为云）都没有 `pass` 副本；openget 的凭据台账明确写「值只在服务器 `/etc/svbackup/` 与本地密码管理器」，本地镜像只取过 AK/SK，没取口令。文档里出现过的一串 `test-only` 口令是调研脚本的示例，不是真实值。用户拍板「口令不要了」，旧快照数据不再追回。

教训写进 skill 第四条铁律：**仓库口令必须离线双份**（密码管理器 + 另一台设备）。AK/SK 丢了还能新建一对，仓库口令丢了没有任何恢复路径——对象还在，但解密不了。

## 四、脚本从「只活服务器上」改为仓库资产

旧脚本 `svbackup-{collect,run,notify}.sh` 与三个 systemd 单元只在服务器的 `/usr/local/bin` 和 `/etc/systemd/system` 里，重装后无法逐字复刻。本次按架构文档与旧行为重写，落在 **`dev-support/svbackup/`**：

- 三个脚本 + 三个 systemd 单元模板 + `install-svbackup.sh`（幂等部署）+ `README.md`
- 脚本里**没有任何真实凭据**，运行时读 `/etc/svbackup/`（700/600）
- 缺口令时 `svbackup-run.sh` 明确 `fail` 并告警，不静默写成一个读不出来的仓库
- 未知引擎族默认 `SKIP_FILE_LEVEL_TAR=1` 只告警、不做整卷 tar（复刻 11-08 PanWeiDB 两天打爆 10GB 额度的教训），另有 500MB 体积哨兵
- `install-svbackup.sh` 已部署到服务器：脚本 700、timer `enabled`+`active`、下次触发 UTC 19:00

restic 二进制装法也订正了：全新系统**没有 `bunzip2`**，`.bz2` 是 10MB（在 SFTP 16MB 上限内），解出的二进制 30MB 超限——所以必须传压缩包、在服务器上用 `python3 -c "import bz2,shutil; ..."` 解包，不能跳过压缩直传。

## 五、三组并行部署的协调口径

12 个实例按「引擎族 + 内存 + 部署复杂度」分三组，各派一个后台子代理（符合全局「子代理并发 ≤3」）：

| 组 | 实例 | 特点 |
|---|---|---|
| A | highgo / mariadb / mysql8 / mssql / opengauss（5） | 标准 entrypoint、一行 env 起库型 |
| B | vastbase A/B / gaussdb-kernel503 / oceanbase（4） | 初始化复杂、内存大 |
| C | 磐维 A/B / oracle-free（3） | 首装约 10 分钟 + 三处补丁时序 |

有效的协调做法：主控把「恢复作业基准」写成服务器上的 `/root/db-restore/restore-manifest.md`，三组读同一份；
凭据只在服务器 `/etc/svbackup/db.env`（600），基准文件里只写变量名不写口令。
**遇到组间冲突由主控统一处置、不叫子代理自己 kill**：本次三组并发 `docker pull` 互抢共享层、
后来逐层 curl 又互抢出口带宽，都是主控读 `ps` 证据后统一清孤儿进程、定错峰顺序
（A→B→C，但发现 ACR 是独立通道后立刻让 C 组并行，不排队）。
子代理的取证质量很高（hex 逐字节核库名、正反探针、digest 与部署原文逐字比对、
900s 超时预判、`.bashrc` 注入根因链），主控只做决策与交叉复核，不重复它们的搜索。

一个反例也要记：主控写进基准文件的字面值被环境的占位符机制替换显示（库名、容器名、变量名都变成随机串），
三组一度以为库名不一致。最后靠 A 组 `hex` 逐字节实证（真实字节 `78 63 33 5f 74 65 73 74`）钉死
「所有脚本写进磁盘的是同一个真值」，虚惊一场。⇒ 判据要落在**写进磁盘的字节与实连通不通**，
不要落在终端显示的替换串上。

## 六、磐维兼容档的确定性坑（本次新发现，已写进 skill）

C 组在验收时发现标称 **B/MySQL 档**的 26100 实例实际装成了 **A 档**：`pg_database` 四个库全是 A、
`show sql_compatibility`→A、数据目录 `PW_COMPATIBILITY` 文件 = A。根因链用三层证据钉死：
`init-db.service` 是 systemd 服务，**不继承 `docker run -e` 的容器环境**——
`systemctl show -p Environment` 为空、PID1 `/proc/1/environ` 有 `dbcompatibility=B` 但
run.sh 进程 `/proc/44/environ` 没有 → `ansible-playbook -e dbcompatibility=""` →
模板渲染出 `gs_initdb ... --dbcompatibility=` 空值（`gs_local-*.log` 第 511 行实证）→ 引擎默认落 A。
即「`-e dbcompatibility=B|A` 是安装期参数」这条口径本身没错，但**这台全新机器上经 systemd 启动时 env 传不进去**，
原 2026-11-06 部署记录没暴露这一层。

修法无时序竞态：run.sh 第 2 行 `source /root/.bashrc`，`.bashrc` 在镜像层、容器启动前可改——
`docker create`（不 start）→ `docker cp` 注入 `export dbcompatibility=B|A` → `docker start`，
三处补丁仍由编排器在解包窗口打。装完必须验 `show sql_compatibility` / `pg_database` 真的落对档，
**不能只看 `select 1` 通就当装好了**。这条与「三处补丁」并列，都是磐维重建的必检项。

## 七、镜像拉取口径：以轩辕官方 Agent 文档为准

用户在本轮中途提供 `https://xuanyuan.cloud/agents.md` 与专业版凭据，要求「先阅读并遵守，未读文档前不要生成 pull 命令或排错方案」。该文档 §0.2 把 `daemon.json` 的 `registry-mirrors` 列为「禁止作为 Agent 默认」的第 5 优先级，§2.2 MUST 优先生成 **`docker pull docker.xuanyuan.run/<原始路径>`**（显式域名，不是靠 mirror 自动回退）。执行顺序：按 §1.2 查 `~/.docker/config.json` 的 `auths` → 未登录按 §1.3 用 `--password-stdin` 一次性 login（凭据在个人中心「镜像仓库信息」，网站登录密码即镜像密码）→ §2.2 默认域 pull → 失败按 §3.2 分类错误跳 FAQ、§3.3 重试轩辕路径，**MUST NOT 默认换官方源或删轩辕前缀**。

两个实测坑：① 首次 login 用错了用户消息里的占位符 id（写成另一个 `{{PHONE_*}}`）导致「用户名或密码验证失败」，按系统规则**原样使用用户给的占位符**后 `Login Succeeded`——占位符只能逐字照抄，不能凭记忆改写；② 匿名请求 `docker.xuanyuan.run/v2/...` 全 401 是正常的「需登录」信号（§1.3），不是域名不可达；③ 专业版登录成功后 highgo 小层 `Already exists`/`Pull complete`，但 69MB 大层报 `net/http: timeout awaiting response headers`（§3.2 归 i/o timeout），按 §3.3 第 4 步**重试即成功**（1.51GB / 约 3 分钟 / ~8MB/s，比 daocloud 逐层快两个数量级）。

用户随后补了**专属域名 `6rzy4mgbhtco8j6ztc.xuanyuan.run`**（§1.5 docker.io 主专属域、免 login、MUST NOT login），使 §2.2 备选方案成立；非 docker.io 按 `{前缀}-{slug}.xuanyuan.run` 拼。B 组 gaussdb 在公共登录域 5 层全 `Pull complete` 后末段 blob 超时触发回滚，按 §3.3 换**专属域重试即成功**（1.46GB、约 5 分钟 382MB，比 daocloud 逐层快一个数量级），没有换官方源。
