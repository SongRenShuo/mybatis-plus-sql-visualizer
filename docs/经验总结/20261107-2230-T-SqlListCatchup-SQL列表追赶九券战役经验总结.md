# T-SqlListCatchup：SQL 列表追赶九券战役经验总结（2026-11-07）

> 计划册：`docs/开发计划/20261107-1140-T-SqlListCatchup-SQL列表追赶延迟与风暴期刷新成本优化-开发计划.md`（§九含每券完整证据链，本文只沉淀可复用的方法论与机制结论）。
> 战役范围：七轮真机压测（join-demo 沙盒，累计 ~60 万请求）、九张券（A 刷新时间窗 / B+B2 计数增量化与悬挂冲洗 / C 桥机制证伪 / D 追赶徽章与探针 / E 渲染器缓存与淘汰增量 / F1 跨通道越窗对账 / F2 丢弃可见化与队列聚合 / G1 池代理白名单 / G2 重放守卫陈旧水位 / G3 停摆定界 / H 排水读超时税）。合 master `80512ec7`。

## 一、四个真缺陷（全是「绿灯看不出」的家族）

1. **渲染器行高全扫**（券 E）：风暴期 `refreshList` 单拍 102~232ms 的真凶不是计数（增量计数仅 0.6~1.4ms），是**贴底滚动触发 `BasicListUI` 变高布局 O(N) 逐格重算 preferred size**——模型变更后首 bounds 27~31ms、温态 0.05ms，每拍必付。修法＝条目级 preferred size 缓存（身份键控 + 代戳作废）。
2. **重放守卫陈旧水位**（券 G2，真丢数据）：平台控制台 clear 是同一文档实例原地删除，偏移从头重计而守卫水位停在旧长度——**清屏后的流式新行被持续误判 Replay 丢弃，直到新文档追平旧水位**（真机一次风暴丢 138,243 行、产出 0 条）。修法＝decide 先核文档总长度、缩小即核销水位。`replayGuard.reset()` 全仓无调用点是关键旁证。
3. **跨通道折叠窗被墙钟清除**（券 F1）：去重开启下同一次执行出现两行，定因是**超窗而非指纹分叉**（crossKey 原材料两侧同源，六族分叉被 18 例证据排除）——5s 窗 + 墙钟惰性清除把 agent 键提前摘掉。修法＝索引取消时间清除 + 越窗 60s 兜底对账。
4. **排水读超时税**（券 H，投递天花板）：排水循环每轮最多 64 条，随后一次带 1s 超时的阻塞入站读——agent→IDE 方向平时无入站流量，**每排 64 条干等 1 秒**，投递钉死 ~64 条/秒（真机 74 条/s 实测吻合）。修法＝burst 达上限先 `available()` 探测、无数据零等待继续排（512 条 726ms→31ms，≈23 倍）。

## 二、被证伪的四个前提（立项时的机制假设全要过真机）

| 前提 | 证伪证据 | 结果 |
|---|---|---|
| 尾巴延迟在桥逐拍解析积压（券 C 字面设计） | 桥是 filter 逐行制，解析在控制台输出线程同步完成；`scanAll` 全历史无文本路径 | 券 C 取消，证伪结案 |
| 每拍全量回退计数是大头（券 E 主攻假设） | 拆拍账单：counts 段仅 0.6~1.4ms；真凶在渲染器布局 | 主攻转向，账单驱动 |
| 桥逐行 filter 占 EDT（券 G3 立项假设，主控两次归因错误） | `handleConsoleLine` 在控制台输出线程不在 EDT；实测 0.02~0.36% 单核 | 薄交付，停摆定界为平台 ConsoleViewImpl 文档管线自身上限（55 万行量级），插件不可修 |
| 遥测读数＝用户体验 | 慢拍 EDT 占用 0.9% 用户仍报控制台停摆；慢拍 0+徽章 0 用户仍报没跟上 | **真机定位的最后一环永远是用户肉眼**，探针只负责把嫌疑收敛到正确的一段 |

## 三、方法论沉淀（本次跑通、下次直接用）

1. **探针先行、账单驱动**：性能券先落拆拍探针拿账单再动刀（券 E 的 `LogPerfProbe` 分布采样 + 拆四段），禁止按假设直接优化。判读自动化：`mybatis-plus-sql-visualizer-demo/stress-test/verify_capture.py`（沙盒 idea.log → 慢拍分布/徽章事件/插件异常三行判读）。
2. **反证自动化**：`dev-support/reverse_probe.py` 双模式——`--commit` 整提交反打仅适用「改既有行为」；**新增能力型提交（机制与测试缝同批落地）整打必编译不可判**，走 `--patch` 手术式补丁（禁机制保缝，补丁库 `dev-support/reverse-probes/`）。锚定用例取机制最小面禁带回归面。
3. **每轮压测一个变量**：七轮读数构成「旧版 → +A/B2/E → +F/G → +H」的差分链，同形态（去重开/关）分别对比，避免多变量混判。
4. **状态栏可见化先于优化**：丢弃数（F2a）、追赶落后数（D）、慢拍分布（E）三类读数先可见，肉眼验收才有抓手。
5. **真机判定分级**：遥测收敛嫌疑段 → 用户肉眼定案；两次「遥测说好、用户说没好」都把瓶颈推到了下一段（EDT→控制台管线→agent 投递），没有肉眼否决就会停在错误的「已修复」。

## 四、已知边界（记档不再追）

- 控制台停摆：平台 ConsoleViewImpl 文档管线在数十万行量级的自身吞吐上限，插件侧逐行成本已实测不显著（0.02~0.36% 单核）；让位升级（agent 健康期注销 filter）过三关评估后不做（clearMessageFilters 连坐 EP/计数冻结/水位冻结）。
- 去重关闭 + buffer 恒满异键风暴：每拍 200 行全异键的模型换血成本仍在（慢拍 2 拍 ≈0.1% EDT），视觉本就是整屏翻滚形态；再压需 diff 增量换血，未立项。
- 接管沿 grace 截断形态：buffer 无法区分「迟到副本」与「attach 后新执行」，与 P3 可见性互斥，明确不修。
- F2b 面板级 ⨉N 计入聚合余量：需 buffer API 扩展，未做（事件帧内聚合计数已保数据面）。
