# 执行计划取源/换源十二轮拉锯：平台关联副作用与排障纪律（2026-10-24）

> 背景：用户报「执行计划」相关的一连串问题——不弹原生密码框、选错数据源、切换数据源只有一个源、
> 点切换没反应、点了报错、第一次能切第二次又只剩一个、执行 SQL 卡死。前后开了 5 个任务
> （T-PreviewChainNoise / T-ExplainPwdPrompt / T-DialectInferPollution / T-ExplainFailUx /
> T-ExplainSwitchNative），在同一个功能上修了 12 轮（W1~W12），其中 W11 整段落空被撤回。
>
> 这份文档只记**可复用的判断**，不记流水账。凡是下次可能再踩的，都在下面。

---

## 一、最贵的一条：平台「选中即关联」是隐式状态，且没有公开清除 API

这是整个十二轮里唯一真正卡死方向的问题，也是把「修一个 bug」变成「修十二轮」的根源。

**机制**（243 反编译 + 字节码偏移实证）：

1. 用户在 IDE 原生工具栏给某个 `.sql` 文件选了数据源，平台会把「这个文件 → 这个源」的关联
   通过 `VirtualFileDataSourceProvider`（EP）**持久化下来**。
2. `DbImplUtil.getForcedDataSourceForExec(psiFile)` 读到关联后**直接返回
   `Collections.singletonList(该源)`**（字节码偏移 34/63 是两条短路口），不再枚举其它源。
3. 于是插件侧任何「列全部数据源」的尝试（走 `getAttachDataSourceRunners` /
   `getSwitchDataSourceRunners`）在关联存在时**恒得 1 个**。
4. **平台没有公开的清除 API**：`ChooseDataSourceAction.actionPerformed` 依赖内部类
   `RunQueryInConsoleIntentionAction$Manager.chooseAndRunRunners`，插件调不进去。

**症状对号**（同一个原因的四张脸，当时被当成四个 bug）：

| 用户话 | 真实原因 |
|---|---|
| 「为什么点击切换数据源只有一个数据源？当前可是配置了很多」 | forced 关联短路枚举 |
| 「第一次点击切换数据源时候是列表了，但是我第二次点击又变成一个了」 | 第一次切换**成功**写入了新关联，第二次起又被短路 |
| 「执行时还是用的原生工具栏上的数据源」 | 平台执行链本来就认 forced 关联，插件自选源改不了它 |
| 「第一次切换成功后还是没有其他的数据源了，而原始工具栏却是正常的」 | 原生工具栏走的是「Detach + 全部源」菜单，它知道自己该忽略关联 |

**结论（已落地 W12）**：插件侧**不要自建换源 UI**。自建的任何入口都做不到与原生一致——
原生工具栏自带 `Data Sources` 菜单（Detach Data Source + 全部源），它才是这个关联的唯一
正确出路口。插件该做的是**指路**，不是重写。

**排障纪律**：遇到「列表只剩一个」这类问题，**必须拿连续多次操作的日志**。单次快照看不出
「第一次/第二次行为不同」——那正是关联被写入的时刻。本轮就是靠第二次点击的日志把
「runner 唯一时仍直选」和「forced 短路」两个不同层的原因分开的。

## 二、反射改接入点，必须先 javap 核**完整签名**

**事故**：W8 把 `getSwitchDataSourceRunners` 按**三参**反射调用。真实签名是**四参**：

```
(PsiFile, String, DatabaseSession, Consumer)
```

`getMethod(...)` 找不到 → `NoSuchMethodException` → 被 `runCatching` 吞掉 → 返回空列表 →
`runners=0` → UI 弹出「没有与该 SQL 方言匹配的已配置数据源」红条。

用户看到的是「点击切换数据源就报错了」，一句红字完全指向方言配置，**与真实原因（参数个数）
毫无关系**。这就是最坏的一类故障：错误信息把人往反方向带。

**纪律**：

- 反射调用平台 API 前，一定 `javap -s` 看**方法描述符**，不靠方法名猜参数表。
- 同类 API 常同族不同参（attach 三参 / switch 四参），**不能互相类推**。
- 反射失败必须**响亮**。本轮修法是「任何失败都回退 attach 版，绝不返回空」——
  `switched.ifEmpty { attach() }`，让能力降级而不让功能消失。

## 三、`runCatching` 会把「实现失败」伪装成「业务空结果」

上面那条事故的放大器。`runCatching{...}.getOrDefault(emptyList())` 让
「反射签名写错了」与「平台确实没有可选源」在返回值上**完全不可区分**。

**判据**：只要下游会把这个返回值呈现给用户（「没有可用的 X」），就**不能**用
`getOrDefault(空)` 收口。至少要让失败走日志 + 走降级分支，而不是混进空集合。

本轮另一处同族：`showExplainErrorDialog(msg) { ... }` 尾随 lambda 撞上 `openConsole: Boolean`
参数，编译期没报错（Kotlin 把它当 trailing lambda 传给了最后一个函数参数），但语义跑偏。
**改具名参数**（`onOpenConsole = { ... }`）是这类 API 的唯一安全写法。

## 四、平台 API 的「三步无解链」要一次证伪到底，别逐个试

本轮花了三轮才发现这条链是封闭的：

1. 想「列出全部源」→ `getForcedDataSourceForExec` 短路（第一节）。
2. 想「清掉关联再列」→ 无公开清除 API。
3. 想「照抄原生菜单」→ `ChooseDataSourceAction` 依赖内部类。

**结论**：三条路各自探一次就够判定无解，**不要**在这一层反复做新尝试。一旦确认封闭，
正确动作是**改变产品形态**（把入口交还平台），不是继续找第四条路。

反面教材是 W11：为了绕过 1，改用 `createDataSourceConsolesRunner` 合并全部在籍源，
用户实测报 `argument type mismatch`，且列表项是「New Query Console / Default Query Console」
——**这个 API 产出的是「新建控制台」Runner，不是「选源」Runner**（见第七条），整段撤回。

## 五、自研 UI 违背平台语义，必然被反复否决

用户在本轮**三次**否决自研换源形态：

1. 自研下拉 → 「我希望选的优先是 idea 原生的」
2. 面板链接按钮 → 「点击下方这个切换数据源依然有问题，点击没有反应」
3. 直接执行（借执行链换源）→ 「点击切换数据源却重试执行了」

三次的共性：**自研入口在别人负责的状态空间里做增量操作**。数据源的「当前选择」是平台状态，
插件改得动显示、改不动语义。

**纪律**：判断要不要自研，只看一条——**这个状态的所有权在不在插件**。不在，就只做指路
（打开原生 UI / 给出明确下一步），不做替代实现。

## 六、反向探针必须**真删符号**，注释和死代码骗不过源码形守卫

本轮两次假绿，代价是差点把「守卫无效」当成「修复有效」：

- `// REVERSE-PROBE` 注释式探针 → 守卫读的是源码文本，注释里出现关键词照样命中，**红不了**。
- `false && 目标调用` → 文本仍在，守卫照样命中，**红不了**。

**纪律**：源码形守卫的反向验证，唯一合法做法是**把符号真删掉**（删函数 / 删调用行 /
改常量值到相反分支），跑测试看到红，再恢复。合成样本只能证明「规则看得见我造的形态」。

## 七、提交后必须复核 `git status` + 提交态编译

**事故**：`f2050329` 提交了 `cachedOwnerIndexes` 的调用方，但漏 `git add` 定义所在的
`DatabaseSchemaResolver.kt` → **提交态编译不过**（本地工作树是好的，所以本地编译骗过自己）。
补提交 `540125bb`。

**纪律**：`git commit` 之后，`git status --short` 必须为空（或只剩预期外的无关改动）；
大改动后跑一次**提交态**编译，而不是只信工作树。这和「工作树绿 ≠ 提交绿」是同一件事。

## 八、源码形守卫指向哪个文件，必须先 `grep` 确认

本轮三次把断言写到错误的文件上（守卫读的是源码文本，文件名写错就恒真或恒假）：

- 「防重复弹选择器」的 Timer 在 `DataSourceSelectorResults.kt`，不在 `SqlPreviewPanelExecution.kt`
- `cachedOwnerIndexes` 在 `DataSourceSelector.kt`，不在 Execution
- `switchDataSourceViaNativeChooser` 撤掉后，旧守卫还在断言它存在（W12 后已改）

**纪律**：写守卫前先 `grep -n <符号> src/main/kotlin`，用真实文件路径；W12 之后还要回头
**改旧守卫**，否则「代码删了、守卫还在要求它存在」会一直红。

## 九、沙盒 GUI 合成输入对 `JTextField` 不可靠 —— 用日志增量做门禁自证

本轮最后一次沙盒自验，`#id` 输入框试了三种合成输入**全部失效**：

- 精确坐标点击后 `pyautogui.typewrite`
- `Tab` 切焦后输入
- 剪贴板粘贴

本机只装 zh-CN 无英文布局（同 `code-completion.gif` 那次的坑），合成键入还会被 IME 吞掉。

**结论**：GUI 闭环不是每次都能跑通。**门禁证据要落在日志增量上**——
`[M37.2] explainSql: dialect=..., len=...` 这类打点只要出现，就证明点击命中了真实执行链，
不必依赖「输入框里确实出现了字」。本轮就是靠 16:51~16:52 的 runner 枚举条数（6~10 个，
不再恒 1 个）判定 W12 达标。

## 十、同族 API 的语义差一等：`createDataSourceConsolesRunner` ≠ 选源 Runner

W11 的方向性错误。`createDataSourceConsolesRunner(dbSource, consumer)` 的消费者拿到的是
**新建出来的 VirtualFile（控制台文件）**，所以列表项显示为「New Query Console / Default
Query Console」——它是「给这个源开一个新控制台」，不是「把这个文件挂到那个源」。

用户实测的两个症状（`argument type mismatch` + 列表全是 New Console）其实是同一句
「API 用错了」的两种表现。

**纪律**：反射用平台 API 前，把**消费者回调的参数类型**一起核清楚（javap 看 `Consumer<X>`
里的 X）。方法名里带 `create` 的，多半不是「选择」语义。

## 十一、失败呈现的共同原则：先分型，再决定用哪种打扰方式

十二轮里被反复修的一块 UI 行为，最后收敛成一条可复用的判定：

| 失败类型 | 呈现 | 理由 |
|---|---|---|
| 认证失败（AUTH） | 轻通知，**不弹模态** | 平台凭据链已经弹过原生对话框（失败与「换凭据/终止」两个出口都在那里），再弹红字是二次打断 |
| 选错源（WRONG_TARGET） | 结果区**就地横幅** + 换源动作 | 模态会先遮住预览，用户还得先关窗再找入口 |
| 用户取消（CANCELLED） | 轻通知 | 用户自己按的终止，不需要被告知 |
| 其它（OTHER） | 回退直送通道 + 说明 | 复用既有能力，不新增第二套执行链 |

**关键点**：分型表必须在**结构化通道和直送通道两处同源**（共用
`classifyExplainFailure`），否则两条链路的行为会漂移——本轮就是结构化侧改了、直送侧没改，
同一个错误在两条路径下表现不同。

## 十二、`askPassword` 这类平台开关必须**按通道表态**，且编译期强制

`DatabaseConnectionManager$Builder` 的 `askPassword` 默认 `true`（javap `iconst_1` 实证），
但旧实现无条件 `setAskPassword(false)`（MCP 通道的「零弹窗」红线连坐到了 UI 通道），
导致 UI 侧该弹原生密码框时不弹。

**修法**：把 `askPassword` 做成**必填参数**（无默认值），每个调用点必须在编译期回答
「我这个通道要不要弹」。

| 通道 | 取值 |
|---|---|
| 面板结构化执行计划 / 旁路查询 | `true`（走平台凭据链） |
| MCP 工具 | `false`（MCP 零弹窗红线） |

**纪律**：凡是「一个开关的默认值对某个通道是错的」，都用**必填参数 + 无默认值**来逼表态，
不要靠注释提醒。

## 十三、执行链里的「卡死」优先怀疑意图未结算，不是数据库慢

用户报「点击执行 SQL 卡住」。根因是单飞闸门的**排队意图没有自己的结算出口**：排队方
在等闸门 owner，owner 那侧若走了不回调的分支，排队方永远等。

**修法**（`PrepareSingleFlightGate.expirePendingExecute`）：让**排队意图**有独立的有界
超时（15s）自己结算成 BLOCKED，**不动门、不动 owner**。这样「等待方」的出口与「持有者」
的生命周期解耦。

**判据**：任何 `QUEUE` 型等待，都必须有「等待方自愈」路径，不能只依赖持有者释放。

## 一条总纲

这十二轮里凡是「修对了」的，都是**把判断权交回给负责该状态的平台组件**；凡是「修错了」
（W11、自研下拉、自研链接、借执行链换源），都是**插件在别人负责的状态上做增量**。

排障顺序也固定成三步，别跳：

1. **拿连续多次操作的日志**（单次快照会漏掉「第一次 vs 第二次」的差异）；
2. **反射签名 `javap` 核**（猜参数表必翻车）；
3. **确认平台是否已有正确入口**（有就指路，没有才考虑自研，且要先证明「无解链」封闭）。
