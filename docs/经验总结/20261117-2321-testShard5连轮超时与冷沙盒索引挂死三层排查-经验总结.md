## 一、现象与最初误判

`push-test` 的 `test (5)` 腿连五轮失败，日志里**没有任何测试失败行**，只有：

```
##[error]The action '分片 5' has timed out after 30 minutes.
```

当时的收官记录把它写成「test(5) 历轮稳定绿、末轮收尾中」——这是第一个误判：**红读数只剩 timeout 时，
「历轮绿」既不可信也不可查证**（超时杀进程会把该片所有用例的失败信息一并吞掉）。基线绿轮
`42904843372`（2026-11-10）的 test(5) 是 7m24s，说明问题是本轮引入的，只是没人看到过它的真实形态。

## 二、第一层：先证明「是挂死，不是慢」

同轮 `test(1~4)` 只需 6~9 分钟；从 run `44082606101` 的 test(4) 日志里量出 `:testShard4` 任务本身只跑
**92 秒**（160 类/~1900 用例，与本地一致）。而 test(5) 的日志在 `> Task :testShard5` 之后 25 分钟零输出。
两个读数夹在一起 ⇒ 不是「CI 机器慢」，是**确定性挂死**。

这一层的价值：把「再推一轮 CI 试试」这类盲操作直接排除——挂死不会因为重跑消失。

## 三、第二层：离线复算分片，把「看不见的失败」捞出来

CI 冷树没有 `build/test-results` 历史样本 ⇒ 分片权重只吃入库画像 `dev-support/test-shard-weights.tsv`
（缺类取已知权重中位数），无 S3 头部巨类拆分、无 auto-handicap ⇒ **分片分配是确定性的**。
按 `buildSrc/src/main/kotlin/mpv-testing.gradle.kts` 的贪心装箱算法离线复算（`dev-support/test-shard-replay.py`），
打印的 `loads=` 行与 CI 日志**逐字一致**（当轮 `shard1=175.9s/158classes … shard5=175.9s/160classes`；
基线轮 `171.9s/143,152,144,145,144` 亦一致）——这个自校验是工具可信的前提。

拿到 shard5 的 160 类清单后本地整片跑
（`-PtestShardIgnoreLocalWeights=true -PtestSplitHeavy=false` 复现 CI 冷树口径）：
**1900 用例 15 红、5 个类**，全部可单独复现（非顺序依赖），全是 Kotlin→Java 漏移植
（lexer 缺 iBATIS 单字符定界符四态 / `XmlPreviewService` 缺多文本静态常量入口 / `<pages>` 误接全扫探针 /
设置面板漏 `localDirField` 的 `isModified` / 一个测试漏 `setUp` 隔离）。修复提交见文首。

这一层的方法论：**失败信息被环境吞掉时，先重建「本该跑什么」的清单，再到本地把真实失败集跑出来**；
比在 CI 上盲推重跑便宜得多。注意本地整片跑要对齐 CI 的权重口径（`-PtestShardIgnoreLocalWeights=true`），
否则分到的类集不同，复现不了同一片。

## 四、第三层：修完 15 红后仍超时 ⇒ 冷树复现 + jstack + 沙盒日志

修完 15 红后 test(5) **依旧** 31m20s 超时 ⇒ 超时另有独立成因。三个动作把根因钉死：

1. **冷树复现**：另起干净 worktree（无 `build/`）跑同一分片——**7.5 分钟 0 个结果 XML**，
   与 CI 的 `completedClasses=0` 一致（热沙盒跑 2 分钟就出结果）。⇒ 挂死需要「冷」这个条件。
2. **`jcmd <testWorkerPid> Thread.print`**：`Test worker` 在 `EdtTestUtil.runInEdtAndWait` 等 EDT；
   `AWT-EventQueue-0` 在 `PlatformTestUtil.waitWithEventsDispatching ← IndexingTestUtil.waitNow ←
   IndexingTestUtil.waitAfterWriteAction` 里 sleep 自旋——**EDT 在等索引收尾，而没有任何索引线程在工作**。
3. **沙盒 `idea.log`**：`UnindexedFilesScannerExecutor` 报
   `VfsRootAccessNotAllowedError: File accessed outside allowed roots:
   <build>/test-sandbox/<分片>/plugins_<任务>/mybatis-plus-sql-visualizer/lib/<插件>.jar`，
   随后 `Task interrupted` + `Requesting heavy scanning on project open` ⇒ 扫描任务反复中断，
   **dumb mode 永不退出**，`waitNow` 的条件永远不满足。

链路复原：`plugin.xml` 的 `<standardResource>`（iBATIS DTD 离线映射，T-Ibatis2Support 券 E）让平台把
「承载该资源的 jar」＝**插件自身 jar** 算进索引根（`ExternalResourcesRootsProvider` →
`IndexableSetContributorDescriptor` → `VirtualFileManagerImpl.findFileByUrl`）；测试 JVM 里该 jar 在
`build/test-sandbox/…`，不在 `VfsRootAccess` 放行集合（temp / `build/classes` / IDE 安装目录 / 家目录 /
config）内 ⇒ 冷沙盒首次建索引必炸。**热沙盒不触发**：持久化索引里已有该根，`findInPersistence` 不走
文件系统、守卫不介入——这正是「本地反复复跑一直绿、CI 天生冷树必挂」的原因。

## 五、修法的选择与两次试错

- **试错 1**：测试 `setUp()` 里 `VfsRootAccess.allowRootAccess(getTestRootDisposable(), PathManager.getPluginsPath())`
  → 无效。检查发生在 `HeavyPlatformTestCase.super.setUp()` 建项目/起扫描**期间**，早于测试自己的 `setUp`；
  `allowedRoots()` 虽然每次现算（无缓存），但扫描已经先发起。
- **平台反编译**：`VfsRootAccess.<clinit>` 里 `SHOULD_PERFORM_ACCESS_CHECK` 由 env/系统属性
  **`NO_FS_ROOTS_ACCESS_CHECK`** 决定（置位即整个检查关闭，异常文案里也写着这条提示）；
  另一条路 `vfs.additional-allowed-roots` 按 `":"` 分割，Windows 盘符路径无法表达，弃用。
- **落点**：`buildSrc` 的 `tasks.withType<Test>().configureEach` 统一
  `environment("NO_FS_ROOTS_ACCESS_CHECK", "1")`——一处配置覆盖全部测试任务，时序问题不复存在。
  代价：测试期不再断言「越界访问真实文件系统」；本仓测试不依赖该断言，且不关掉就无法在冷沙盒建索引（硬阻断）。

**验证口径**：把 `build/test-sandbox/shard5/system_testShard5` 挪走强制冷索引，复跑 `:testShard5`
→ 160 类全落盘、BUILD SUCCESSFUL 6m11s（修复前同条件永不收敛）。CI 两轮全绿 + gate 全绿（读数见文首）。

## 六、沉淀为可复用手段

1. **「任务超时」≠「无失败」**：红读数只剩 timeout 时，按 L80 的顺序走——离线复算类清单 → 本地整片跑
   → 按失败集修；不要重推 CI。
2. **「分片绿」必须冷沙盒复跑**：挪走 `build/test-sandbox/<片>/system_<任务>` 强制重建索引再跑；
   热沙盒的绿只证明「索引已建好之后」的行为，不证明首次建索引路径。
3. **插件新增「资源型 EP」时必须想到测试 JVM 的 VFS 放行面**：`standardResource` 之类把插件 jar 变成
   平台索引根的登记，会让冷沙盒建索引撞 `VfsRootAccess`——测试任务统一关 `NO_FS_ROOTS_ACCESS_CHECK`（L81）。
4. **CI 加 `if: always()` 进度诊断步骤**成本低收益高：超时杀进程后仍能打印已完成测试类清单与完成时刻，
   `completedClasses=0` 一个读数就区分了「跑不完」与「跑完了不退出」两种挂死形态。
5. **平台测试挂死的两把钥匙**：`jcmd <pid> Thread.print`（看 EDT 卡在哪个测试框架等待点）+
   沙盒 `idea.log`（`build/test-sandbox/<片>/log_<任务>/idea.log`，索引/dumb mode 的全过程都在里面）。
