# 测试服务器容器内存第二轮压缩（2026-11-13）

「不大-北京-16G」整机重建（2026-11-12）加 TiDB 后共 13 容器，`available` 只剩 3144MB。本轮按 `.agents/skills/db-env-provisioning/SKILL.md` §2.5 的治理口径再做一轮压缩，**available 提到 4149MB（+1005MB）**，13/13 数据面实连通、零 OOM。

## 一、根因：重建流程缺了「治理收尾轮」

上一轮整机重建时只给磐维两实例压了 DB 内部参数（那是 C 组部署脚本自带的步骤），**其余 11 个容器全部按台账旧 cap 起、内部参数全是镜像默认值**。采集实测暴露四处欠压：

| 实例 | 参数 | 改前 | 改后 | RSS 变化 |
|---|---|---|---|---|
| Oracle Free | `sga_max_size` / `sga_target` / `pga_aggregate_target` | 1536 / 1536 / 512M | 512 / 512 / 256M（scope=spfile + 重启） | 1216→1017MiB |
| MSSQL | `max server memory (MB)` | **2147483647（默认无限）** | 512 | 768→591MiB |
| openGauss | `shared_buffers` | 1024MB | 256MB（改 conf + 重启） | 522→~470MiB |
| Vastbase A / B | `shared_buffers` | 各 1024MB | 256MB | 各降 ~130MB |

cap 收缩 11 个（`docker update` 在线、无重启）：总 cap **40.7G → 19.3G**——oceanbase 8→5.5G、panweidb-test 4→1.5G、vastbase 4→1.5G、gaussdb 4→1.5G、panweidb-ora 3→1.5G、opengauss 4→1G、mssql 2→1.5G、vastbase-b 2→1G、mysql8 1→768M、highgo 3→512M、mariadb 2→512M（oracle 2.5G / tidb 1.5G 已达标不动）。cap 本身不降 RSS，作用是防单实例失控吃满宿主；真正把 available 抬上去的是上面四处内部参数压缩。

结论已固化：**「整机重建」的收尾步骤必须包含内存治理轮**（cap 全部按 §2.5 目标 + 内部参数压缩清单逐实例核），不是「有空再做」——否则重建出来的环境就是欠压状态。已写进 skill §9 重建顺序与 LESSONS L57。

## 二、本轮新踩的四个坑

1. **MSSQL `max server memory` 是 advanced option**：直接 `sp_configure 'max server memory', 512` 报 `Msg 15123 ... may be an advanced option`。两步法：先 `sp_configure 'show advanced options', 1; RECONFIGURE`，再改目标项。第一遍直改失败被我误当成已执行（输出被 grep 吃掉），复核 `value_in_use` 还是 2147483647 才暴露——**改完必须回读 `value_in_use` 确认**。
2. **重建脚本里的 cap 是第二处事实源**：幂等重建脚本写死旧 cap——`/www/xc3/oceanbase/start.sh`（`--memory=8g` + `OB_MEMORY_LIMIT=6G`）、`/www/xc3/gaussdb/init.sh`（4g）、`/opt/xc3-vastbase[/b]/start.sh`（4g/2g）、`a-deploy.sh`（3g/2g）。只 `docker update` 运行时 cap 而不改脚本，下次整机重放全部回退。本轮已逐个 sed 同步；磐维编排脚本 `c-orchestrate-panweidb-v2.sh` 本就参数化（cap 是第 4 参），在脚本头注明「重建传 1536m」。**cap 有两处事实源（运行时 + 重建脚本），治理必须两处都改**。
3. **Vastbase vsql 实连的口令变量**：start.sh 是宿主上的幂等重建脚本（`docker rm -f` + 完整 `docker run`，数据在宿主卷跳过初始化），容器 env 是 KubeBlocks 风格的 `GS_USERPASSWORD`——`docker exec` 里拿宿主 db.env 的 `$VB_PASS` 是空的，报 `Invalid username/password` 虚惊一场。vsql 不读 PGPASSWORD，容器内用 `-W "$GS_USERPASSWORD"`。
4. **Oracle `v$parameter` 查询的引号**：SQL 里的单引号经 `sh -c` 双引号嵌套被吃（`\047` 转义也翻车），改用管道法 `echo "select ... where name in ('sga_max_size',...);" | docker exec -i <c> sqlplus -s "/ as sysdba"` 一次通过。

## 三、反向验证

highgo cap 压到 16m（远低于 RSS 30MiB 反而活着——空闲占比过低不触发回收，续压到 16m 仍 Up 一轮后才触发）：`OOMKilled=true、ExitCode=137、RestartCount=3`，证明 cap 真生效；恢复 512m 后 Up + `select 1` 通。两次读数齐全。

## 四、一个虚惊：别用 `docker ps` 相对时间判重启循环

治理中途看到部分容器 `Up 2 hours` / `Up About an hour`，而「记忆里」它们是昨天起的——差点判成隐藏重启循环。`docker inspect` 证实 `restarts=0 / OOMKilled=false`，StartedAt 与创建时刻一致：**我把 UTC 和北京日期搞混了**（部署实际发生在当天 UTC 下午）。判重启循环用 `docker inspect` 的确定性字段（`RestartCount` / `State.OOMKilled` / `State.StartedAt`），不要拿 `docker ps` 的相对时间加时区心算。
