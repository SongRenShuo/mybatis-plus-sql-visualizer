# 夜间 dialect 腿连红四轮的根因分层与真机实例对外可达排查法（T-NightlyLocalMysql 续）

- 日期：2026-11-13
- 关联：`docs/开发计划/` 下 T-NightlyLocalMysql；`.agents/skills/db-env-provisioning/SKILL.md` §4.5；`docs/LESSONS.md` L44
- 目标实例：`103.36.220.245`（不大-北京-16G），`114.66.55.245`（对照，一直绿）

## 一、现象与排除过程

夜间全量从 11-09 起 `dialect` 腿连红。矩阵四实例的读数一直是「通过 2 / 失败 2」：

```
PASS  mysql84            262 词   (114.66.55.245:20084)
PASS  pg16                86 词   (114.66.55.245:20033)
FAIL  panwei_a            (103.36.220.245:26101)
FAIL  gaussdb_kernel503   (103.36.220.245:25882)
```

两个失败实例都在同一台机、两个通过的都在另一台机 ⇒ 先怀疑 103.36.220.245 的服务状态，而不是矩阵或插件。
11-12 晚该机整机重启过，容器因 `--restart unless-stopped` 自动拉起（`docker ps` 显示 Up），但端口从外部
不可用。报错文案随时间变化，正是分层排查的入口：

| 时间点 | 报错 | 指向 |
|---|---|---|
| 11-12 夜间 / 11-13 凌晨 | `gaussdb: Connection refused`；`panwei_a: The connection attempt failed.` | TCP 层（refused）与握手层（failed）**混在一起**，两种都有 |
| 修完 `listen_addresses` 后 | 两个都变成 `The connection attempt failed.` | 全部落到握手层 ⇒ 网络无关，是认证 |

## 二、四层排查法（本轮的实质产出）

`refused` 落在 ①②③，超时落在 ②，**握手期断连落在 ④**：

1. **宿主机端口**：`ss -tlnp | grep <port>` —— 看 `docker-proxy` 有没有在听。
2. **DNAT 目标**：`nft list chain ip nat DOCKER | grep <port>`，与
   `docker inspect <容器> --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'` 逐个对。
   目标指向已消失的容器 IP 时 SYN 石沉大海，表现为**超时**而不是 refused。
3. **容器内监听地址**：`docker exec <容器> ss -tln | grep <引擎端口>`。只听 `127.0.0.1:x` 时外部经 DNAT 进来
   直接 refused。
4. **pg_hba 放行范围**：`grep -Ev '^\s*#' pg_hba.conf`。只放行容器网段（`127.0.0.1/32`、`::1/128`、
   `172.17.0.0/16`）时，DNAT 进来的外部连接源 IP 是**真实公网地址**，一条都匹配不到 ⇒ 握手期被踢，
   **不是 refused**。

本轮实测数据（每层都对过一次）：

| 层 | 读数 | 结论 |
|---|---|---|
| ① | `ss -tlnp` 有 `docker-proxy` 监听 26101 / 25882 | 正常 |
| ② | DNAT：25882→172.17.0.8、26101→172.17.0.4，与容器实际 IP 一致 | 正常 |
| ③ | gaussdb 容器内只听 `127.0.0.1:5432`；panwei 已是 `172.17.0.4:17700` | **gaussdb 坏** |
| ④ | gaussdb hba 只有 `127.0.0.1/32`、`::1/128`、`172.17.0.0/16`；panwei 同构 | **两个都坏（真凶）** |

## 三、改动

三处，全部只改配置、都有备份 `*.bak-20261113`：

```bash
# ① 容器内监听地址（gaussdb 原来听 loopback）
listen_addresses = '*'

# ② pg_hba 追加外部源放行（三实例同款；口令认证，不放 trust）
host    all             all             0.0.0.0/0               sha256
host    all             all             ::/0                    sha256

# ③ 生效方式：改 hba 用 reload，不 restart（restart 会打断在跑的真机矩阵）
docker exec -u omm <容器> bash -lc \
  'export LD_LIBRARY_PATH=/opt/gaussdb/app/lib:$LD_LIBRARY_PATH; gs_ctl reload -D <datadir>'
```

顺带把磐维两档的 hba 从钉死 `172.17.0.4/32` 放宽成 `172.17.0.0/16`（`omm` 那条 trust 行保持钉死不动，
不扩大免密面），并把 `listen_addresses` 一起改成 `'*'`——从此不再依赖容器 IP 稳定，整机重启/容器重建后
只要库进程起来就能被外部连上。

## 四、验证（三档递进，缺一档就是假绿）

1. 容器内走容器 IP + 矩阵凭据：`gsql … -c 'select 1'` → `ok=1`
2. **外部视角**（本机走公网，等同 CI 路径）：DBX 直连 gaussdb `select version()` 539ms、panwei A `select 1`
   984ms —— 这一步是本轮的关键，第 1 档在 hba 未修时也是绿的（源 IP 落 172.17.0.0/16）
3. 夜间 dispatch 由 `DialectExternalMatrixVerificationTest` 出引擎级读数

第 3 档的转绿读数（run `43337831586`，2026-11-13，**11-09 以来第一轮 17/17 全绿**）：

```
通过 4 / 跳过 0 / 超时 0 / 失败 0
PASS  mysql84              262 词  batch=on wordWorkers=4  73766ms
PASS  pg16                  86 词  batch=on wordWorkers=4  25788ms
PASS  panwei_a             109 词  skip=1(rowid)  batch=on wordWorkers=4  75586ms
PASS  gaussdb_kernel503    197 词  batch=on wordWorkers=4  87287ms
```

注意 gaussdb 这次跑的是 **197 词**（此前失败轮没有产出词数），panwei_a 109 词与历史读数一致；
`skip=1(rowid)` 属既有词表例外，不是本轮新增。

**「端口 OPEN」不等于库活着**：`docker-proxy` 会自己完成 TCP 握手，所以只做 TCP 探活会给假绿。

## 五、踩过的两个操作坑

- **引号被 shell 吃掉**：跨层拼命令（本地 → bash → `docker exec` → `sh`）里 `'*'` 落成了无引号的
  `listen_addresses = *`，openGauss 直接 `could not start server`。改完必须 `grep '^listen_addresses'` 回读。
- **`gs_ctl`/`gsql` 缺 `LD_LIBRARY_PATH`** 会报 `libpq.so.5.5` / `libcjson.so.1` 缺失——是环境问题，
  不是库装坏了。gaussdb 容器还没有 entrypoint（`Cmd` 只有 `tail -f /dev/null`），整机重启后库进程不会自启，
  必须人工 `gs_ctl start`。
