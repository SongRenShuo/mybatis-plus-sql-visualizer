# SQL 方言映射在 EDT 上的慢操作断言：定位、修法与两条通用教训

**证据边界**：本轮的根因链在 243 发行版字节码上逐跳核实；**262 上只有上报栈**（本机无 262 发行版可反编译），运行期「0 条」读数尚未取得，文中不宣称两版语义一致。

## 一、现象与真正的责任人

用户上报：

```
java.lang.Throwable: Slow operations are prohibited on EDT.
	at FSRecordsImpl.update(FSRecordsImpl.java:711)
	at PersistentFSImpl.findChildInfo(PersistentFSImpl.java:615)
	at VirtualFileManagerImpl.findFileByUrl(...)
	at PerFileMappingsBase.ensureStateLoaded(PerFileMappingsBase.java:315)
	at SqlDialectMappings.getMapping(...)
	at SqlLanguageSubstitutor.getSqlLanguageDialect(...)
	at SqlSyntaxHighlighterFactory.getSyntaxHighlighter(...)
	at LogToSqlPanel.createResultEditor(LogToSqlPanel.kt:647)
	at SqlLogToolWindowFactory.createToolWindowContent(SqlLogToolWindowFactory.java:50)
```

读起来像「我们的编辑器建得慢」，实际是**平台的一处延迟加载被我们提前拉到了 EDT 上做**：

1. `PerFileMappingsBase.loadState` 只解析持久化 XML，把「文件 → 方言」条目存进
   `myDeferredMappings`（列表为空时置 `null`，见下节「空绿陷阱」）；
2. `ensureStateLoaded` 在**首次任何映射查询**时才消费该列表，逐条 `VirtualFileManager.findFileByUrl`
   把路径解析成 `VirtualFile`（`"PROJECT"` 条目跳过）；
3. `findChildInfo` 内部走 `FSRecordsImpl.update`，平台把它归为慢操作，EDT 上无许可即
   `Logger.error`（`SlowOperations.assertSlowOperationsAreAllowed`：只认 EDT、按栈签名去重、写动作内默认放行）。

结论一句话：**插件只是触发者，成本在平台；把首查挪出 EDT 即可，不需要也不允许动平台的断言开关。**

## 二、教训一：只修「第一个调用点」等于给错误换落点

第一处修法很自然——把 `LogToSqlPanel` 里那次显式取高亮器改成自研高亮器。但同一构造链
（`SqlLogPanel.kt:141` → `:143`）紧接着构造 `SqlToJavaPanel`，其输入区按 **SQL FileType**
建编辑器；243 `EditorHighlighterFactoryImpl` 字节码显示：按 FileType 建编辑器时会走
`SyntaxHighlighterFactory.getSyntaxHighlighter(FileType, Project, VirtualFile)` —— 同一条首查。

所以正确的范围判断是**先画「谁会让平台做这件事」的清单**，再决定修哪里：

| 入口 | 是否受控 | 处置 |
|---|---|---|
| `LogToSqlPanel` 显式取高亮器 | 我们自己的多余调用 | 删掉，换自研高亮器 |
| `SqlInputEditor`（SQL→Java 输入区） | 必须保留 SQL FileType（补全按 `language="SQL"` 注册） | 无法消除 → 预热 |
| 预览面板编辑器 | 先按 SQL FileType 建、随后才换自研高亮器 | 预热覆盖 |

可操作判据：**凡是「隐式」触发（不写在我们代码里的）都不可能靠改调用点消除，只能靠时机**。
这类位置要按「什么线程、第一次是什么时候」来排，而不是按「我们哪一行代码看起来可疑」来排。

## 三、教训二：一次性延迟加载 + 空数据 = 空绿

`PerFileMappingsBase.loadState` 只有在解析出的列表**非空**时才设置 `myDeferredMappings`；
列表为空直接置 `null`，`ensureStateLoaded` 随即空转返回——**项目里没有任何 per-file 方言映射时，
这个断言根本不会出现**。

后果：拿一个干净项目去「验证修复」，前后都是 0 条，读数看起来完美，实际什么都没测。
本册因此把「复现前置」写进验收红线：项目必须有 `.idea/sqldialects.xml` 里的 `file` 条目，
且先红与后绿各起一个新 IDE 会话（`SlowOperations` 按栈签名去重，同一会话跑两次只有第一条会记）。

推广口径：**平台「懒加载 + 数据驱动的短路」是空绿的高发区**。验收前先问一句「这条路径在什么数据
条件下才真的执行」，把那个条件造出来再取读数。

## 四、修法（三笔，可分别回滚）

- **S1**：结果编辑器改挂自研 `SqlSyntaxHighlighter`（与预览面板、日志预览同源）。顺带修掉
  「未装 Database 插件时结果区整片无高亮」——`plugin.xml` 里 `com.intellij.database` 是 optional，
  `getStdFileType("SQL")` 拿不到时旧代码直接不设高亮器。
- **S2**：`SqlDialectMappingPrewarm`——`prewarmNow`（BGT 同步首查，`ReadAction.compute` +
  `EmptyProgressIndicator`）、`prewarm`（fire-and-forget）、`prewarmAndAwait`（EDT 有界 300ms）。
  失败只 WARN、成功才记「已预热」（可重试）、弱键集合不持有 Project。
- **S3**：工具窗工厂在 `new SqlLogPanel` **之前** `prewarmAndAwait`；预览预热任务在 BGT 首行
  `prewarmNow`（该任务随后才产出临时文件、EDT 才装配编辑器，顺序天然继承）。

明确否掉的三条「假修」：`allowSlowOperations` 逃生舱（仓内 243+262 双证伪）、把调用包进写动作
（平台默认在写动作内放行慢操作，但那是用豁免盖住问题，还把 VFS 解析塞进全局写锁）、
关 `Registry ide.slow.operations.assertion`（改用户环境不是修缺陷）。

## 五、实施中顺带踩到的两处

1. **`executeOnPooledThread` 在 Kotlin 里有两个重载（`Runnable` / `Callable<T>`）**，lambda 返回值
   参与推断时会歧义，二次推断能让整段表达式退化成 `Any!`。显式写 `Callable { }` / `Runnable { }`。
2. **`FileTypeManager.getStdFileType` 在 Kotlin 侧是非空平台类型**：写
   `val x: FileType = getStdFileType("SQL") ?: run { … }` 会触发「elvis 恒取左值」警告——
   不要先声明非空类型，让推断从 elvis 走。
