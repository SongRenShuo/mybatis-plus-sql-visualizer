# 全景盘点全量实施批的五个教训

> 2026-10-31。本批把盘点 26 项里的 18 项实施完（合流三棒中的两棒、巨文件五件拆分、设置收敛、文档结构、方言矩阵页、两图重录），过程中踩到的问题比交付本身更值得留档——其中三个是**工具行为与人的直觉相反**，两个是**文字记录与产物脱节**。

## 一、`git add -A` 会把未解冲突标记一起提交

合并 `t-magpie-gems` 时，冲突解完我用了 `git add -A` 收口。git 接受了——因为**它只检查索引状态，不检查文件内容**。于是 `plugin.xml` 里那三行 `<<<<<<< HEAD` / `=======` / `>>>>>>>` 进了提交，下一轮构建 `patchPluginXml` 直接 `JDOMParseException: Error on line 387: 元素内容必须由格式正确的字符数据或标记组成`，整条链断掉。

判据要从「我以为解完了」改成机检：合并提交前必须

```
git grep -n "^<<<<<<< \|^>>>>>>> " -- .
```

清零再提交。另外两条同样有效：合并收口**逐个 `git add <冲突文件>`** 而不是 `-A`；提交后立刻跑 `patchPluginXml`（它是最早暴露 XML 破坏的环节，比编译还早）。

这个坑在本仓有前科——同一批里 `git add -A` 还把 insight 工作树里 82 个本地录制探针脚本卷进合并提交。两次都指向同一个结论：**在有并行会话与大量未跟踪文件的仓里，`-A` 不是省事，是把不确定的东西塞进历史**。

## 二、Kotlin 增量编译不跟踪 data class 构造器签名

`PluginSettings.State` 加了字段之后跑定向测试，一批用例报 `NoSuchMethodError: PluginSettings$State.<init>(boolean, String, …, int, boolean…`——字节码里还是旧签名。

根因是测试 class 的增量产物没失效：测试代码里 `State(...)` 的调用点在旧 class 里已编译成旧签名，Kotlin 增量编译没把它识别为需要重编。

处置：`rm -rf build/classes/kotlin/test` 后重编。全量 `testShards` 不受影响（它会全量重编），但**定向测试会给出假红**，而假红最容易被误判成真回归。

判据：改 `State` 这类 data class 的字段后，定向测试若报 `NoSuchMethodError`（尤其是构造器/属性访问器），先怀疑增量编译，删测试 class 重编再复跑。

## 三、`Class.forName` 探测在 headless 恒 false，把功能误置灰

G5 的 Community 执行入口预判置灰用 `Class.forName(database 标记类)` 判断 DataGrip/Database 插件是否在。测试 classpath 里没有那个类，真实探测恒 false，于是**所有执行类动作在 headless 下被判定为「Community 版」并置灰**，`SqlPreviewPanelDisplayEditorTest`（验「选中表名 → Explain 应启用」）首轮全量报 1 红。

修法是给判定加测试缝（`availabilityOverrideForTest`，生产恒 null）：

```
fun isAvailable(): Boolean = availabilityOverrideForTest ?: runCatching {
    Class.forName(DATABASE_MARKER_CLASS); true
}.getOrDefault(false)
```

值得记的是另一面：**这种探测在真实环境里也分不清「探测失败」与「功能不存在」**。一旦某个用户的 classpath 异常，Ultimate 功能会静默置灰且无从诊断。凡是用「类在不在」当能力判据的地方，都要留一条可观测的降级路径。

## 四、合流会推翻刚定下的行数预算

G3 把五件巨文件拆到线下（最紧的两件 1989 / 1987，预算 2000），收口后复测发现 `DataSourceSelector.kt` 变成 **2023**——因为 G5 的换源重播放在同一文件里加了 34 行。预算守卫（`GiantFileBudgetTest`）当场变红。

两个连带结论：①**预算收紧与功能增量不能在不同分支上并行做**，谁后合谁承担超线；②超线后的正解是继续拆（把 G5 新增的广播机制搬到 `DataSourceSelectorLastUsedEvents.kt`），不是提预算——预算表注释里那句「A size budget raised whenever a change reaches it bounds nothing」是上游踩过的坑，这次没重犯。

顺带一条：`PluginSettingsPanel.kt` 也超了（1887 > 1830），那个选择了「拆方法体 + 按实测校准预算到 1840 并注明两笔合法增量来源」——因为两笔增量（FR-0045 设置子页、NEW-18 体检入口）都是用户可见功能，拆无可拆。**判据是「能不能拆」，不是「一律不许提」**。

## 五、文字记录会与产物脱节，唯一的判据是复核产物

重录两张演示动图前，我给代理的缺陷描述是「`code-completion.gif` 里是 IME 候选框冒充补全弹窗、`log-community.gif` 二维码未加载完」——来自 2026-10-24 的验收记录。代理抽帧复核后发现**仓内当前那版两个问题都不存在**：补全列表是真的（4 行表名+注释）、二维码也已加载；真正的问题是补全**没有收窄过程**、加载态占比过大且完整定格太短。

那份 10-24 的记录描述的是**更早一版**，中间重录过一次（10-23 收口时「24 张动图全部在位」），记录没跟上。

结论对两类文档都成立：验收表（帧数/体积/接缝）看不出「录错内容」，文字记录同样会脱节。**引用任何历史结论前，先对当前产物做一次最小复核**——动图抽三帧、报告抽两个数、代码抽一个符号。成本是分钟级，收益是避免整轮返工。

## 附：一条流程观察

本批 6 路子代理并行（合流、四路实施、两路文档），冲突面比预期小——因为写集切得干净（配置 / 拆分 / 文档 / 新功能各占一块）。真正相撞的是**跨路共用的文件**：`plugin.xml`（合流修复 + G2 注释债 + G5 活动注册）、`docs/索引/开发计划.md`（r34 + 两处补登）、`架构设计/03`（文档核对 + R45 守卫改名）、`DataSourceSelector.kt`（拆分 + G5 增量）。

派活时把「共用文件归谁」写死比划大块边界更管用。这四处的冲突都是我在收口时手工裁决的（取并集或按新事实），没有一处需要业务判断——说明只要写集清单是真的，冲突是可预期的。
