## 二、根因

三条叠加，单独修任何一条都不够：

1. **cap 按大机器给，不看实测**。41 GiB 上限对 16GB 物理机没有约束意义，但任一容器的失控（例如 OceanBase
   一次灌数据冲到 8G）就够把主机吃穿。
2. **0 swap**。没有兜底，内存压力直接走 OOM-kill，第一个死的是占用最大的数据库进程。
3. **DB 内部参数照大机器配**：磐维 `max_connections=3000`、`bulk_write_ring_size=2GB`、`cstore_buffers=512MB`；
   Oracle `sga_max_size=1.5G`；SQL Server `max server memory` 无上限；openGauss 族 `shared_buffers=1GB`。
   这些是「它想用多少」的声明，容器 cap 只是外框——**只压 cap 不压参数，容器会被自己的 DB 撑爆**。

## 三、处置步骤（顺序有讲究）

### 1. 先加 swap（收益最高、风险最低）

`fallocate -l 4G /swapfile` → `chmod 600` → `mkswap` → `swapon` → `/etc/fstab` 持久化；
`/etc/sysctl.d/99-mpvs-swap.conf` 写 `vm.swappiness = 10`。

放在第一步的原因：后面每个容器改参数都要重启，重启窗口里内存峰值最不可控，有 swap 兜底才不会在治理过程中
先把某个库打死。

### 2. 压 DB 内部参数

先压「想用多少」，再改「最多能用多少」。若反过来（先按 1.5GiB 设 cap 再改参数），中间那个窗口里引擎仍按
旧的大参数启动，会直接被新 cap 卡死。

| 容器 | 参数 | 旧值 | 新值 |
|---|---|---|---|
| panweidb-ora | `cstore_buffers` | 512MB | 128MB |
| panweidb-ora | `bulk_write_ring_size` | 2GB | 512MB |
| panweidb-ora | `max_connections` | 3000 | 200 |
| panweidb-ora | `shared_buffers` | 256MB（有效值） | 256MB（不动） |
| panweidb-test | `shared_buffers` | 1024MB | 384MB |
| panweidb-test | `cstore_buffers` | 512MB | 128MB |

| xc3-oracle-free | `pga_aggregate_target` | 512M | 256M |

| xc3-highgo | `shared_buffers` | 128MB | 128MB（已低于目标，不动） |

### 3. 逐容器收缩 cap

`docker update --memory <新值> --memory-swap <新值> <容器>`，一次一个，改完立刻 `docker inspect` + `docker ps` 复核。
cap 按实测的 1.5~2× 定，但**必须高于 anon 常驻**——`docker stats` 的 MemUsage 含 page cache，不可回收的 anon
才是硬地板。

## 四、坑

### 4.1 磐维容器的 `max_connections` 有两条，靠后的那条才生效

`postgresql.conf` 里第 82 行是 `max_connections = 200`，第 955 行又被改成 `3000`。PostgreSQL 语义「后出现的
覆盖前面的」，所以有效值是 3000。计划册只看了第 82 行，按 200 估的内存；实际改到 200 后，常驻直接从
950MiB 掉到 500MiB——**这是本轮单项收益第二大的改动**。同理 `shared_buffers` 在 ora 容器里第 978 行写着
256MB，覆盖了第 161 行的 1024MB，所以计划册写的「1024MB」对 ora 并不成立（test 才是 1024MB）。
**读配置必须 grep 全部出现位置并取最后一条，或直接查 `pg_settings`**。

### 4.2 `max_process_memory` 有引擎下限，压过头起不来

磐维启动校验：`max_process_memory` 必须大于
`2GB + cstore_buffers + (udf_memory_limit - UDF_DEFAULT_MEMORY) + shared_buffers + preserved memory`。
本轮把 `max_process_memory` 设成 1GB 时直接
`FATAL: the values of memory out of limit ... = 4670MB`。它是记账上限不是预占，**保持原值（8G/12G）即可**，
真正省内存靠 `shared_buffers` / `cstore_buffers` / `max_connections`。

### 4.3 磐维重启后的两处启动陷阱

- 残留**空 `postmaster.pid`** → `gs_ctl start` 报 `invalid data in PID file`。删掉再启即可。
- `docker exec -u omm <c> gs_ctl start` 会因缺 `GAUSSHOME` 报 `Get environment of GAUSSHOME failed`，
  **必须走 `docker exec <c> su - omm -c 'gs_ctl start'`**（`su -` 会加载 omm 的 profile）。

### 4.4 OceanBase 的 `memory_limit` 不能直接砍到目标值

三处限制：

- `ALTER SYSTEM SET memory_limit='2.5G'` 报 `ERROR 4147 Invalid config`——下限是
  `sum(unit MEMORY_SIZE) + system_memory`（本轮 2G+3G+1G = 6G），**必须先压租户 unit**。
- `ALTER RESOURCE UNIT <unit> MEMORY_SIZE='1.5G'` 报 `Parse error`——**不接受小数**，写 `1536M`。
- 压到 1536M 时被拒：`The memory of memstore needs to be less than 90% of the new memory ... shrink is not supported`；
  先看 `GV$OB_MEMSTORE` 的 `memstore_used`（本轮 test 租户 0.449G）再定，2G 可以过。
- 还有 `__min_full_resource_pool_memory` 下限（本机 bootstrap 写死 2G，`ALTER SYSTEM` 改不动），
  所以**单租户压不到 2G 以下**，OceanBase 的理论地板就是 4G unit + 1G system = 5G。

关键读数：把 `memory_limit` 从 6G 改到 5G 后，**observer 的 anon 纹丝不动（4.21GiB）**——它不会立即归还。
所以定 cap 要照 anon 而不是照 memory_limit：计划册给的 4GiB 会当场 OOM，本轮实际给 5.5GiB。

### 4.5 特权容器会改宿主 sysctl

宿主 `vm.swappiness` 设成 10 后过一阵又变回 0。真凶是磐维容器（`--privileged=true`）：它内部
`/etc/sysctl.conf` 写着 `vm.swappiness = 0`，容器重启时 systemd-sysctl 直接写进宿主内核。
修法：把容器内那份也改成 10（`/etc/sysctl.conf` 备份为 `.bak-memtrim-20261106`）。
**排查方向**：宿主 `grep -rn swappiness /etc/sysctl.d/ /etc/sysctl.conf` 只看到自己的 10 时，去看特权容器内部。

### 4.6 openGauss 族客户端连接姿势

- `xc3-opengauss` / `xc3-gaussdb-kernel503` 的 `gsql` 缺 `LD_LIBRARY_PATH`，直接跑报
  `libcjson.so.1: cannot open shared object file`；显式给 `-e LD_LIBRARY_PATH=<...>/lib`。
- 这两家 **`PGPASSWORD` 不生效**（仍弹 `Password for user ...` 并判 `Invalid username/password`），
  必须用 `-W '<密码>'`。
- 瀚高（HighGo）本轮 `xc3` 账号密码**已过期**（`Your password has expired, please alter password first`），
  属既有状态、与本次改动无关，已在报告里登记为未闭环项。

### 4.7 SQL Server 改小 `max server memory` 不会立即归还

把 `max server memory` 从无上限改到 768MB、再改到 512MB，`sp_configure ... RECONFIGURE` 都报成功，
但 cgroup 里的 anon 一直停在 **991MB** 纹丝不动；`DBCC DROPCLEANBUFFERS` + `DBCC FREEPROCCACHE` 也没用
（它只清缓存，不还内存给内核）。**重启容器**后 anon 才降到 633MB。所以 SQL Server 的内存改动要按
「改配置 + 重启容器」两步做，别指望在线改就立刻看到 available 回升。

### 4.8 反向验证的 cap 要低于实际常驻，否则验证不了任何东西

计划册设想「把 highgo cap 压到 64M 它就该起不来」。实测：64M 下容器照常 `Up`，占用 21~39MiB
（HighGo 空闲常驻就很小，`docker stats` 的分母确实变成了 64MiB、MemPerc 重算为 61%，说明 cap 生效了，
但它就是不缺内存）。继续压到 **16M** 才触发真 OOM：`OOMKilled=true`、`ExitCode=137`、
`docker ps` 显示 `Restarting (137)`、`RestartCount=7`；改回 512M 后 15 秒内恢复 `Up`。
**教训**：反向验证要挑「cap 明显低于该容器真实常驻」的量级，否则你验证的只是「docker 接受了这个参数」。

## 五、判据与反向验证

- `free -m` 的 `available` 从 **775MB → 3265MB**（三次采样 3265/3271/3278，≥3GB 达标）。
- `docker stats`：最高 79.0%（OceanBase），无容器贴 cap 90%。
- 12 个容器全部 `Up`，无 Restarting。
- 每实例连通一次成功：panweidb 两实例 `select 1` + `select version()`；OceanBase / Oracle / SQL Server /
  MySQL / MariaDB / openGauss / GaussDB / Vastbase 均取到查询结果（瀚高见「未做项」）。
- 方言矩阵子集：`panwei_a` PASS（words=109、skip=1(rowid)、batch=on、30117ms）、
  `gaussdb_kernel503` PASS（words=197、batch=on、37466ms），与基线一致。
- 反向验证两次读数：cap=64M 时容器仍 `Up`（21~39MiB，**未**触发异常）；cap=16M 时
  `docker ps` 显示 `Restarting (137)`、`OOMKilled=true`、`ExitCode=137`、`RestartCount=7`；
  改回 512M 后 `Up`、18.62MiB、7 个 `postgres` 进程。

## 七、未做项与风险

- **OceanBase 仍是最大占用者**（4.34GiB / 5.5GiB）。受 `__min_full_resource_pool_memory=2G` 与
  「unit 不可小于 2G」限制，做不到计划册设想的 2.5G；压到 4GiB cap 会立刻 OOM（anon 硬地板 4.21GiB）。
  要再降只能重建集群（改 bootstrap 参数），本轮不做。
- **瀚高 `xc3` 密码已过期**，未改（属账号策略，不在内存治理范围）；跑瀚高矩阵前需先改密码。
- `docker stats` 的 MemUsage 含 page cache，所以「改完立刻测」的数字偏乐观；判定时以 `drop_caches` 后的
  `available` 和 anon 为准。
- 本轮只治理容器内存，没动磁盘、镜像、数据卷，也没做性能调优。
