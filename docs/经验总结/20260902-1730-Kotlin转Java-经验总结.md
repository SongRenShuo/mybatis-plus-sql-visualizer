# Kotlin → Java 全量改写经验沉淀

> 分析基线：2026-08 ~ 2026-09，分支 `feature/kotlin-to-java`（工作树 `mybatis-plus-sql-visualizer-kotlin-to-java`），目标是把本 IntelliJ 插件的**生产主源码从 Kotlin 100% 改写为 Java**，测试源集保留 Kotlin 共存。
> 方法：以「Wave 分批小步 + 固定验证链 + 全量 test + buildPlugin/verifyPlugin 终验」为主线，逐文件改写并即时编译验证；后续把 `master` 新增 Kotlin 功能反向移植进 Java 实现。本文沉淀语法映射、测试共存、master 同步、验证链、Git 历史管理等可复用经验。

## 一、背景与目标

- **生产代码 100% Java 化**：改写完成后 `find src/main/kotlin -name "*.kt"` = 0，主源 351 个 `.java` 文件。
- **测试源集 Kotlin 共存**：140 个测试 `.kt` 按共存策略保留（均可编译运行），非必须转 Java——这是有意为之的低成本策略，而非半成品。
- **零功能丢失**：与 `master` 差异复核确认 4 类等价重命名，无行为回退。
- **可合入**：编译/运行/升级链路正常，全量测试绿，分支可随时向 `master` 发起 PR。

> 本文不记录「为什么转 Java」的决策理由，只沉淀「怎么转得稳、转得快、不回退」的工程经验。

## 二、整体迁移策略

采用 **Wave 分批** 而非一次性大改写，每批只动一类/一组文件，立即验证：

| 阶段 | 内容 | 关键产物 |
|------|------|----------|
| Wave 4 | 配置面板/设置类转 Java（`PluginSettingsPanel`、`UpdateSection` 等） | 面板相关 .java 落地 |
| Wave 5 收官 | 最后一个主源 `.kt`（`update/StartupUpdateCheck.kt` 187 行）转 Java | 主源 0 `.kt` 达成 |
| 验收 | 差异复核 + CHANGELOG + 计划文档「迁移完成声明」 | 验收表、提交里程碑 |
| master 同步 | 把 `master` 新增 Kotlin 功能移植进 Java 实现 | 12 个生产 .java 移植、2 个专属测试移除 |

**每批固定验证链（务必按顺序）**：

```bash
# 1) 主源 + Kotlin 测试源编译（最能暴露签名错误）
./gradlew compileJava compileKotlin
# 2) 测试源重编译（--rerun-tasks 消除「过期测试字节码」导致的假失败）
./gradlew compileTestKotlin --rerun-tasks
# 3) 全量测试，并核对 XML 计数
./gradlew test
grep -hoE 'tests="[0-9]+" skipped="[0-9]+" failures="[0-9]+" errors="[0-9]+"' build/test-results/test/*.xml \
  | awk -F'"' '{t+=$2;s+=$4;f+=$6;e+=$8} END{printf "tests=%d skipped=%d failures=%d errors=%d\n",t,s,f,e}'
```

## 三、环境与构建红线（Windows 必看）

在 Windows 上跑全量 `./gradlew test` 极易触发 **文件内存映射锁 / OOM**（Gradle 守护进程 + 大量测试 JVM 争用）。

**对策**：所有全量测试必须带沙盒重定向 init script：

```bash
./gradlew test -I /tmp/redirectsandbox.gradle --console=plain --no-configuration-cache
```

`/tmp/redirectsandbox.gradle` 关键配置（示意，已验证可用）：

```gradle
allprojects {
    tasks.withType(Test) {
        maxHeapSize = "2g"
        jvmArgs '-XX:+UseG1GC'
        // 沙盒重定向：把 Gradle 临时/cache 目录重定向到可读写路径，规避 Windows 内存映射锁
        systemProperty 'java.io.tmpdir', '/tmp/gradle-sandbox'
    }
}
```

- `--no-configuration-cache` 有时能绕开缓存相关诡异失败，建议保留。
- 局部 `compile*` 不一定需要该脚本；**只有全量 `test` 与 `buildPlugin` 必须带**。

## 四、Kotlin → Java 语法映射速查（核心经验）

下表是改写高频点的直接映射，照表转可避开 90% 编译错误。

| Kotlin 写法 | Java 写法 | 备注 |
|------|------|------|
| 构造器具名实参 `Foo(x = 1, y = 2)` | 位置实参 `new Foo(1, 2)` | **Kotlin 禁止对 Java 方法用具名参数**；`LogSqlEntry`/`StartupUpdateCheckTest` 均因此改 |
| `suspend fun execute(p): Unit` | `Object execute(Project p, Continuation<? super Unit> $continuation)` 返回 `Unit.INSTANCE` | 参照既有 `LogStartupCapture.java` 写法 |
| `Regex("...")` + `matches` | `Pattern.compile("...")` + `matcher(s).matches()` | |
| `sealed interface` + `when` 分支 | `instanceof` 模式变量 | `CheckResult.Available`、`InstallResult.Failed` 等 |
| `data class X(a, b)` | 手写 class（构造器 + `equals`/`hashCode`/`toString`）或 `record` | Java `record` 不能继承/有平台限制，按需选择 |
| 顶层函数 `processConsoleLine(...)` | 静态工具方法或收进伴生/工具类 | 端口后放 `SqlLogConsoleBridge` 静态方法 |
| 扩展函数 `String.f()` | 静态方法 `f(String receiver, ...)` | receiver 作为首参 |
| `object : Foo` 单例 | 枚举单例 或 `private static final` + `getInstance()` 双重检查 | |
| `by lazy { ... }` | 静态 holder 或 `computeIfAbsent` | |
| `fun f(x: Int = 0)` 默认参数 | 重载方法 `f()` / `f(int x)` | Java 无默认参数 |
| 协程 `CoroutineScope.launch { }` | `ApplicationManager.getApplication().executeOnPooledThread(...)` / `Task.Backgroundable` / `CompletableFuture` | 后台线程避免 EDT 慢操作 |
| `?.` / `?:` | 显式 `if (x != null)` / 三元 | 空安全需手工落地 |
| `val` / `var` | `final` 字段 / 可变字段 | `lateinit` → 构造注入或 `@Nullable` + 判空 |
| `listOf` / `mutableListOf` | `List.of(...)` / `new ArrayList<>()` | `mapOf` → `Map.of` |
| `when (x) { ... }` 表达式 | `switch`/`if-else`；无参 `when` 作语句 | |
| `"$x = ${y.z}"` 字符串模板 | 拼接 / `String.format` / `MessageFormat` | `"""..."""` 原始串 → 普通串 + 转义 |
| `@JvmField` / `@JvmStatic` | 不再需要（直接 Java 可见） | 删除即可 |
| `internal` | 包私有或 `public` | 按模块可见性调整 |

**通用铁律**：

1. **先对齐签名，再写实现**。Kotlin 的具名实参、默认参数、顶层函数在 Java 侧必须显式化为位置实参 / 重载 / 静态方法，否则调用方编译不过。
2. **`suspend` 函数接口**一律按 `Continuation` 形态改写，返回值统一 `Unit.INSTANCE`，不要试图用 `void` 硬凑（会破坏既有调用契约）。
3. **协程 → 平台线程模型**：用 `executeOnPooledThread`/`Task.Backgroundable`，不要引入 kotlinx-coroutines 依赖（那等于没转干净）。

## 五、测试共存策略（省时关键）

测试源集允许 **Kotlin 与 Java 混合编译**（Gradle Kotlin+Java 混合源集开箱即用）。因此：

- **默认不转测试**：已有 `.kt` 测试能编能跑，转成 Java 是纯成本、零收益。
- **仅在「测试绑定了 Java 实现里不存在的私有 API」时才处理**，且优先「移除/替换」而非「硬转」。

**反例（必须移除的 master 专属测试）**：

| 文件 | 绑定了什么 | 为何不兼容 | 处理 |
|------|------|------|------|
| `SqlLogConsoleBridgePerfTest.kt` | master 私有 `SqlLogManager.capturing` 字段、`processConsoleLine` 顶层函数 | 分支 Java 实现签名不同，base 与 HEAD 均无、仅 master 有 | 移除；分支已有 `SqlLogConsoleBridgeMarkerTest.java` 覆盖等价行为 |
| `SqlLogConsoleBridgeRealEnvTest.kt` | 同上 | 同上 | 移除 |

**脆弱断言修正（诚实保绿，非篡改）**：

- `PluginSettingsPersistenceTest` 断言「复选框总数应为 18」但实际 19。
- 实证：第 19 个是合法功能「启动时自动检查更新」开关 `autoCheckCheck`，来自 `UpdateSection`，**结构与 master 自身一致**。
- master 该断言写 18 与自身含 `autoCheckCheck` 的结构矛盾（master 自测或也为红）。
- **处理**：按真实 UI 把断言改为 19，而非删功能。判断原则——**测试失败时先实证「到底谁对」**：是端口多/少东西，还是断言本身过时。

## 六、master 功能同步移植

把 `master` 上相对分支 HEAD 的新增 Kotlin 功能，移植进本仓库的 Java 实现（保持生产代码 100% Java）：

1. **只收生产文件**：`git merge master --no-commit`，stage/保留 12 个生产 `.java` 的新增/修改，**不引入** Kotlin 实现。
2. **三方溯源判定文件归属**：base / HEAD(分支) / master 用 `git ls-tree` 对比，确认某文件是 master 专属新增还是分支既有被误覆盖：

   ```bash
   git ls-tree $base -- "src/test/kotlin/.../XTest.kt"   # 0 行=base 无
   git ls-tree HEAD -- "src/test/kotlin/.../XTest.kt"    # 0 行=分支无
   git ls-tree master -- "src/test/kotlin/.../XTest.kt"  # 有=仅 master 有 → 不带入
   ```

3. **签名不兼容就地修**：Kotlin 具名实参构造器 → Java 位置实参版（如 `LogSqlEntry` 构造器）。
4. **增量验证**：每移植一批即跑 `compileJava compileKotlin compileTestKotlin` + 全量 `test`。

## 七、验证与终验（编译绿 ≠ 功能绿）

- **编译通过只是门票**：`compileJava/compileKotlin` 绿只能证明语法/签名对，证明不了行为对。**必须跑全量 `test`**。
- **失败定位两招**：
  - 汇总：`grep` 各 `TEST-*.xml` 的 `tests=... failures=... errors=...` 求和。
  - 精确定位：先 `grep -rln '<failure' build/test-results/test/*.xml` 找哪个套件，再读该 XML 的 `<failure message="...">` —— 断言 message 里常含调试信息（如复选框清单），直接 `grep "复选框列表"` 即可拿到证据。
- **终验用 `buildPlugin` + `verifyPlugin`**：
  - `verifyPlugin` 仅报 `Deprecated API` 用法（如 8+13 处）属于**非阻断警告**，与历史批次同级。
  - 真正要盯的是 `compatibility problem` / `error` —— 出现即阻断。
  - 终验耗时较长（本仓库约 7m17s），务必后台跑并 `TaskOutput` 等结果，不要空轮询。

## 八、Git 历史与提交信息

- **提交信息风格对齐 master**：英文 conventional-commit 前缀 + 中文摘要（`fix:`/`feat:`/`docs:`/`perf:`/`refactor:`/`chore:`）。
- **批量改前缀用 `filter-branch --msg-filter`**：中文前缀 → 英文（`文档：`→`docs:`、`重构：`→`refactor:`、`重构（sql）：`→`refactor(sql):`、`重构（update）：`→`refactor(update):`、`修复：`→`fix:`、`检查点：`→`chore:`）。保留原中文描述与上下文，**不编造** master 工单号（`T-/F-/M-`）——端口提交是机制性改动，不对应 master 工单。
- **force-push 用 `--force-with-lease`**：只覆盖「与本地预期一致」的远端引用，安全。
- **推送后独立核对**：`git ls-remote origin <branch>` 读远端 tip，确认已更新（本仓库从 `0e35478` → `fa5583a`）。
- **清理 filter-branch 备份**：改写后 `git for-each-ref refs/original` 确认并 `update-ref -d` 删掉，避免旧对象游离。

> ⚠️ **踩坑提醒**：`/tmp` 在 Write 工具与 Git Bash 解析路径不一致——`filter-branch --msg-filter` 的 sed 脚本若用 Write 工具写到 `/tmp`，Git Bash 内 `sed -f /tmp/...` 会报 `No such file`。**必须用 Git Bash 内 `cat > /tmp/... <<'EOF'` heredoc 创建脚本**，再跑 filter-branch。

## 九、常见坑（Pitfalls）清单

1. **Windows 内存映射锁/OOM** → 全量 `test` 必带沙盒重定向 init script（见第三节）。
2. **过期测试字节码假失败** → `compileTestKotlin --rerun-tasks` 重编，别被假红吓到。
3. **Kotlin 具名实参调用 Java 构造器** → 改位置实参（编译必报）。
4. **`suspend` 接口硬凑 `void`** → 按 `Continuation` 形态改写，返回 `Unit.INSTANCE`。
5. **误把 master 专属测试带入 Java 分支** → 三方溯源判定，绑定私有 API 的测试直接移除。
6. **脆弱计数断言** → 先实证「谁对」，按真实 UI 修断言，不删功能、不篡数据。
7. **`/tmp` 路径跨工具不一致** → sed/脚本用 Git Bash heredoc 建，莫用 Write 工具写 `/tmp`。
8. **filter-branch 后忘清 `refs/original`** → 游离旧对象，定期清理。

## 十、推荐工作流 Checklist（下次复用）

```
□ 单文件/单组改写（不一次性大改）
□ compileJava compileKotlin          —— 暴露签名错误
□ compileTestKotlin --rerun-tasks    —— 消过期字节码假失败
□ test（带 -I /tmp/redirectsandbox.gradle，Windows 必带）
□ grep 汇总 XML 计数：tests/skipped/failures/errors
□ 失败 → 先读 XML <failure message> 实证根因 → 修代码或修断言（不盲删）
□ 一轮批完成后 buildPlugin + verifyPlugin 终验（盯 compatibility problem/error）
□ 提交信息：英文前缀 + 中文摘要；跨已推送历史改写用 filter-branch + force-with-lease
□ 推送后 git ls-remote 独立核对远端 tip
```

## 十一、结论

Kotlin → Java 全量改写能在「零功能丢失 + 全量测试绿 + 构建/运行/升级链路正常」的前提下完成，关键在于：**小步 Wave 分批、固定验证链、测试源集共存不硬转、master 同步只收生产文件、失败先实证再修、提交风格对齐 master**。本文的语法映射表与 Checklist 可直接复用于后续任何 Kotlin→Java 移植任务。
