# 插件免重启更新（动态热替换）与跨版本签名核验经验沉淀

> 分析基线：2026-09-11 交付 T-DynUpdate（master `34055dd` → merge `771b5f2` → 验证与护栏 `50748d1`/`11407b7`/`7e1d3e0`/`1a1faac`/`7531cfb`/`9c2788f`/`9f8821d`），真机 Gitee 通道实测免重启生效。
> 适用范围：IntelliJ 平台动态插件（243/253/262 三版本实证）。本文沉淀「平台机制、实现范式、跨版本反射的验证盲区、踩坑清单」，不重复开发计划里的逐行实现细节（见 `docs/开发计划/20260911-0614-T-DynUpdate-自更新免重启动态安装改造-开发计划.md`）。

## 一、背景：一个被误判定论锁死半年的能力

- **T-M23.10（2026-08 早期）**：实测更新后必重启，当时归因「环境 Performance Testing 插件否决动态卸载」→ 定论「覆盖更新必重启，不做动态加载」，M28 更新器据此固化为 `StartupActionScriptManager`（调度下次启动删旧解新）+ 重启提示。
- **2026-09-11 推翻**：反编译该 vetoer（`PlaybackRunnerExtended$PlaybackRunnerExtendedPluginUnloadVetoer`）——它只否决 performanceTesting **插件自身**的卸载、且仅在其命令回放执行期间（`activeExecutionCount > 0`），从不否决第三方插件。**教训：vetoer 这类扩展点必须反编译读实现，不能按「存在即否决」推全局结论。**
- 同时排除项（262 逐条实证）：插件 9/9 扩展点 `dynamic="true"`、无 `<components>`、根标签无 `require-restart`、免费插件（付费插件平台强制重启）、无其他插件反向依赖、自定义语言/FileType 已于 2026-08-20 移除——**插件描述文件侧完全合规，问题只在更新器代码绕过了平台动态链路**。

## 二、平台机制速览（243 javap + 262 反编译双端实证）

**更新判定链**（Settings→Plugins / Install from Disk 同源）：

```
PluginInstallOperation.prepareToInstall
  ├─ DynamicPlugins.allowLoadUnloadWithoutRestart(descriptor)  ──否决──▶ downloader.install() 启动脚本，重启生效
  ▼ 通过
PendingDynamicPluginInstall → installAndLoadDynamicPlugin(file, parent, descriptor)
  ├─ installWithoutRestart：unpackPlugin(zip → <plugins>/<zip顶层目录名>)（descriptor 参数仅进度标题/日志/fireState 用！）
  ├─ PluginDescriptorLoader.loadDescriptor(解包产物)
  └─ DynamicPlugins.loadPlugin(新描述)                      ──任一步失败──▶ installAfterRestart 启动脚本
```

**五入口反射签名**（本插件自更新实际使用的最小集）：

| 入口 | 用途 | 跨版本注意 |
| --- | --- | --- |
| `PluginDescriptorLoader.loadDescriptorFromArtifact(Path, BuildNumber)` | 从发行 zip 读新描述 | 两版本一致 |
| `PluginManagerCore.findPlugin(PluginId)` | 取当前已装描述 | 两版本一致 |
| `DynamicPlugins.allowLoadUnloadWithoutRestart(descriptor)` | 卸载预检（EP dynamic 属性/vetoer/依赖图） | 两版本一致 |
| `DynamicPlugins.unloadPlugin(descriptor)` | 运行期卸载旧版 | **262 首参漂移为子类 PluginMainDescriptor**（见 §四.1） |
| `PluginInstaller.installAndLoadDynamicPlugin(Path, JComponent?, descriptor)` | 解压 + 动态装载新版 | 两版本一致 |

**否决者（vetoer）**：`ide.dynamicPluginVetoer` 扩展点（平台 `FallbackPluginVetoer` 走 app+project messageBus 二次查询、`XDebuggerPluginVetoer`、performanceTesting 自保 vetoer）。卸载预检不通过 → 回退脚本路径，不硬试。

**卸载后观察与「未完全卸载」警告**：动态重配置完成后平台用 `GCWatcher` 观察旧类加载器，默认仅等 5 秒（registry `ide.plugins.unload.timeout=5000`），超时仍被强引用即弹「插件未完全卸载，这可能会导致功能问题」（建议重启/保存内存快照）。**hprof 实证（2026-09-11）：旧加载器（24.89MB）引用全是结构性互联**——兄弟/子加载器 parent/children 链、`Module`、`ProtectionDomain`、`classDataConsumer`、旧描述对象、弱引用；本插件仅有两处 static 小引用（`RunConfigurationProcessListener.platformClassLoader`、`SqlLogConsoleBridge` 的 LOG，合计 2-3KB）。**定性=GC 时机问题非泄漏**：新版实例完整接管（扩展点/服务平台已清理重建），旧加载器一次性内存驻留（重启即清、不增长）。缓解=Registry 调大 timeout 至 30000 或点重启；不要硬屏蔽平台诊断通道。

**付费插件例外**：第三方付费插件平台强制重启，动态更新仅对免费插件可行。

## 三、实现范式（可直接复用）

**自更新两条铁律**：

1. **动态安装代码跑在旧版插件的进程与类加载器里**——旧版卸载后调用栈仍在孤儿 classloader 上执行，善后动作只允许触达平台 API 与通知（通知组 id 是平台侧注册字符串），不得再调自身服务单例。
2. **热替换能力自「包含新代码的正式版」发布后才对真实用户生效**——Gitee 通道现发的 2026.9.10 不含动态代码，其下次更新仍走 M28 脚本路径。

**编排序列**（`DynamicInstallSupport`）：

```
zip 前置校验（纯函数：id 匹配 + version 提取，兼容 IPGP 嵌套布局与直属布局）
→ 开发态守卫（isDevInstallation 黑名单防误删 build 产物）
→ 反射五入口探测（一次缓存；任一缺失 = 签名漂移/裁剪发行版 → 整体回退）
→ findPlugin(自身 id) 取当前描述
→ allowLoadUnload 预检（防 vetoer/依赖图否决）
→ EDT invokeAndWait：unloadPlugin(旧) → installAndLoadDynamicPlugin(zip, null, 新描述)
→ 任一环节失败回退 installRestartScript（原 M28 脚本路径降级兜底，无中间死态）
```

**失败出口全覆盖**：卸载失败 → 插件继续运行原版 + 脚本兜底；卸载成功装载失败 → 脚本兜底重启修复；反射缺失 → 脚本兜底。任何路径都不劣化 M28 原行为。

**UX 分叉**：`InstallResult` 三分支 `InstalledDynamic`（通知「已更新并立即生效」）/ `InstalledRestartRequired`（保留重启提示）/ `Failed`；设置页 `UpdateSection` 增 `InstalledLive` 状态。

**路线教训**：`installFromDisk`（平台 Install from Disk 实现）**不能用于热更新**——243 包私有 + `File` 参数 6 参、262 public + `Path` 7 参（跨版本签名漂移），且两条平台流程都不卸载已加载旧版，对覆盖更新场景热替换必失败。

## 四、踩坑清单（每条都已实证）

1. **262 `unloadPlugin` 首参漂移**：243 首参 `IdeaPluginDescriptorImpl`，262 漂移为其子类 `PluginMainDescriptor`。反射探测器按 243 签名精确匹配在 262 扑空 → 回退重启，只有真实用户暴露。修复=首参弹性匹配（方法名 + 首参与描述类互为可赋值、参数最少优先；双参形态自动构造 `UnloadPluginOptions` 无参实例）。
2. **跨版本反射是三重验证盲区**：反射调用绕过编译期检查、`verifyPlugin` 只验编译期引用、单测只跑构建平台 243——签名漂移三层门全穿透。**制度化解法：`PlatformSignatureCrossVersionTest`**——自动发现本机已解压目标平台发行版（gradle transforms 里 verifyPlugin 下载的 243/253/262 + 已安装 IDE 兜底），用各发行版自带 JBR 跑纯 Java 检查器按生产同款弹性逻辑核验全部反射入口，漂移即本地测试失败；发行版缺失按 Assume 跳过。**新增强化：新增跨版本反射入口必须同步在该测试登记核验。**
3. **签名核验必须逐方法 javap 实际签名**：反编译元数据（d2 数组）不体现重载参数类型漂移，本次 262 验证缺口正源于此。
4. **vetoer 语义**：见 §一，按名字/存在性推全局结论是本次事故起点。
5. **`.run` 运行配置对开着 IDE 的用户不可靠**：IDE 以内存运行配置为准，且会把内存旧副本与磁盘新配置**同时写回 `.run` 文件形成同名双配置**——改文件分发行为无效。重要行为必须落在 gradle 任务本身（本次把服务自动起停挂到全局 `runIde` + `runIdeHotSwap` 双任务，点到哪个都通）。
6. **Gradle 配置缓存冻结配置期读取**：任务配置期 `System.getProperty(...)` 被缓存，后续带 `-D` 的运行不再生效（manifest URL 转发实测踩雷）。动态值必须走执行期求值（`jvmArgumentProviders` 每次 run 求值）。
7. **Kotlin DSL 三坑**：脚本内 `java` 被项目扩展访问器占位（`java.net.Socket` 须文件顶部 import）；任务动作引用脚本级 val/函数 = 配置缓存报「script object references」（路径配置期 `.get().asFile` 解析、逻辑内联 doFirst）；testing-DSL `register` 块只认 `sandboxDirectory` 等少数属性（autoReload/classpath 必须进 `task {}` 子块）。
8. **KDoc 嵌套注释**：注释里写 `` `lib/*.jar` ``，`/*` 会开启 Kotlin 嵌套块注释吃掉外层 `*/`，报出「Unclosed comment」级联语法错误且行号错乱。注释措辞禁用 `路径/*` 形态。
9. **陈旧编译产物劫持**（本仓库第四次）：增量编译后 `build/classes` 残留旧类遮蔽新类（本次 internal 函数名混淆 NoSuchMethodError）。症状=编译过但运行期 Unresolved/NoSuchMethod，清 `build/classes` + `build/kotlin` 即复绿。
10. **自研 hprof 解析器不划算**：IDEA「保存内存快照」产物是**私有格式变体**（顶层记录 tag 后带 u4 skip + u4 len；堆段子记录标准 HPROF 但根记录尺寸易错位），自写解析器调试数轮。**定例：堆分析一律用 IDEA 自带能力**——弹窗「保存内存快照」→ hprof 直接用 IDEA 打开看「传入引用/支配树」。
11. **`.run` 本地验证口子**：清单 URL 系统属性 `mpvs.update.manifest.url` 覆盖（`dev-support/hotswap-local-server.py` 自动选最新构建包生成 update.json 起本地服务）；「Install from Disk / 从磁盘安装」测不出免重启（平台该流程不卸载已加载旧版，必提示重启）。

## 五、验证体系（四层）

| 层 | 手段 | 拦截什么 |
| --- | --- | --- |
| 单测 | `PluginUpdateRunnerTest`/`DynamicInstallSupportTest`（seam 注入不触平台） | 编排分支、zip 前置校验、弹性匹配纯函数 |
| 跨版本签名护栏 | `PlatformSignatureCrossVersionTest`（243/253/262 真实平台 jar） | 反射入口签名漂移 |
| runIde 沙盒 | `runIdeHotSwap` 专用任务 + `hotswap-local-server.py`（服务随任务自动起停） | 端到端下载→校验→热替换全链 |
| 真机通道 | Gitee 通道低版本装机 → 通道更新 | 真实用户路径（自更新代码跑在旧版的约束） |

runIde 沙盒的限制：沙盒插件是 jar-copy 安装（非 dev classes 直载，dev 守卫放行），但**纯 runIde 无法测自更新**——更新动作本身要在 UI 里驱动，且 `runIdeHotSwap` 共享默认沙盒时 prepareSandbox 每次覆盖插件目录会重置状态。真机通道演练仍是最终验收。

## 六、本地热替换测试三步（不依赖 Gitee/市场）

```bash
./gradlew buildPlugin -Pversion=2026.9.12-beta.1   # ① 构建比 gradle.properties 更高的版本
python dev-support/hotswap-local-server.py          # ② 起本地服务（自动选最新包生成 update.json，端口 8919）
# ③ 点 Run IDE (Local Manifest) → 沙盒设置 → 更新分区 → 检查更新 → 下载并安装
```

判定：通知「已更新并立即生效」；沙盒 idea.log `dynamic install succeeded — plugin hot-reloaded`；设置页版本即时变化。失败看 `dynamic install not applicable — falling back to restart script:` 后的原因字段。服务随任务生命周期自动起停（doFirst 拉起 / finalizedBy 停止，端口被占则复用）。

## 七、遗留与边界

- `ide.plugins.unload.timeout` 调大由用户按需执行（Registry），插件不代改全局设置。
- 8-20 计划的静态缓存项（EntityResolver companion cache 等）定性为内存卫生、非卸载屏障，暂不实施。
- Gitee 通道接入平台 custom release repository（走平台原生更新 UI）另行评估。
