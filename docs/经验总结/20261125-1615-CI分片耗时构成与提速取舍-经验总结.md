# CI 分片耗时构成与提速取舍（2026-11-25）

- 触发：用户看 test (4) 16m21s，问「拆成两个分片或其它方式会不会更快」
- 结论：**拆片不会更快**；该轮多出的 7 分钟全部来自重试阶梯的误判。已实施 P0（重试分类重写）。
  稳态 9~10 分钟是每 job 固定成本主导，安全可压缩空间不足 1.5 分钟。

---

## 二、失控轮的构成（test(4)，16m21s）

| 尝试 | 用时 | 结果 |
|---|---|---|
| 1 | 1m02 | 配置期 `ClosedFileSystemException`（zip-FS 竞态，约 4/25 片） |
| 2（停 daemon + 清 transforms） | 49s | 同错（该级 2026-11-05 已被实测证伪） |
| 3（清项目侧 IPGP 缓存） | 7m04 | 竞态已恢复，**真跑完 1117 例 / 1 红**：`SqlStandalonePreviewPanelDialogTest`（已知 flaky，L90） |
| 4（`git clean -xdf` 干净树） | 5m44 | 通过 |

第 3 次是测试红而非竞态，但旧脚本把多次尝试 append 进同一日志、对整份文件匹配
`ClosedFileSystemException` → 命中第 1 次留下的签名 → 判「竞态第三级未恢复」→ 全量重跑。
**多烧 5m44，且把一次真红掩盖成绿**。

## 三、为什么拆片不划算

- 每片固定成本 ≈ 4~5 分钟（配置 + buildSrc + 两次 Kotlin 编译 + 沙盒 + 1 分钟级缓存恢复），
  测试本体只 ≈2 分钟；
- 拆两半：每片 ≈4.5 分钟固定 + 1 分钟测试 ≈ 6 分钟，但多一个 job 的固定成本与缓存恢复，
  总 runner 分钟 +≈9，墙上时间由最慢 job 决定 → **不变**；
- 且 job 数从 5→7 会把 zip-FS 竞态的命中面扩大（现约 4/25）。

## 四、逐项被否的提速手段（都有实证）

| 方案 | 为何不做 |
|---|---|
| Gradle build cache（跨 job 复用编译产物） | `gradle.properties` 明写 T-TestPerf-01（2026-09-14）关闭：三次实证复用陈旧 `compileTestKotlin` 产物 → 成片 `NoSuchMethodError` 假失败，只能 `rm -rf build` 全量重跑。本轮又遇到同族的 State 字段 ABI 陈旧（L21），同源风险。 |
| `maxParallelForks>1` 提升单片测试并发 | `mpv-testing.gradle.kts:124` 明确保持 1：多 fork 共享默认 test 沙盒，PersistentFS 互踩成片异常（2026-09-14 实测 4 fork 成片 `PersistentFSConnector` 异常）。 |
| 传 `build/classes` + 项目 `.gradle/` 工件给分片 | workflow 注释 2026-11-05 实测：会触发本文正在修的 zip-FS 竞态（已撤回）。没有执行历史时 Gradle 仍会全量重编，收益本来也不成立。 |
| 恢复项目 `.gradle/configuration-cache` 省配置期 ~1m45 | 同属「传项目 `.gradle`」的高风险面；且平台/插件依赖变化会让缓存失效或串味。收益 1m45，风险不对等，未做。 |
| 5 片并成 1~2 个 job（多任务并发） | 编译只做一次可省 runner 分钟，但墙上时间仍 ≈ 编译 3 分 + 测试 3~4 分 ≈ 8~9 分，仅省 0.5~1 分；代价是失败隔离变差、4 vCPU/16GB 上 3~5 个平台测试 JVM 并发有抖动风险。未做。 |

## 五、本轮实施（P0，T-CiRetryClassify）

`dev-support/ci/run-gradle-retry.ps1` 重写：

- 每次尝试独立日志 `gradle-run-N.log`，判定只读本次；
- 三类分流：竞态 → 停 daemon + 清项目侧 IPGP 缓存与 IDE 解包 + `--max-workers=1`（仍命中才退干净工作树）；
  测试红 → 只重跑失败类一次（编译 UP-TO-DATE，约 1 分钟），通过则 warning 点名放行；其它失败立即红；
- `-SelfTest`（7 项断言）钉住分类逻辑，含「测试红不得判为竞态」这一旧缺陷形态；
- 本机 fake-wrapper 四场景验证：纯编译错 1 次即退 / 竞态两次升干净树 / 竞态后成功 / 测试红只重跑失败类。

预期收益：同类 flaky 或竞态轮次 16m21s → 约 10 分钟；且不再把真红掩盖成绿。

## 六、还能再压，但需要接受风险（未做）

1. 配置缓存工件化（≈1m45/job）：只传 `.gradle/configuration-cache`，先在一个受控 run 里验证不触发 zip-FS 竞态。
2. 单 job 五片并发（`-PtestShardConcurrency=3` + `-PtestShardMaxLane=5`）：本地有 lane 限流与内存水位闸门，
   CI 侧未验；需先测 4 vCPU/16GB 下 3 lane 是否产生负载敏感红。
3. 减少 runner 侧固定成本（缓存只留 distro+modules、去掉定期未命中的 transforms 分包）：恢复 3.5GB 用 44s，
   收益上限 20~30s。
