# T-ReleasePerf9 测试链限流内置化与错峰共享前置 经验总结

> 2026-10-29。分支 `t-releaseperf9`（工作树 rp9，基于 master 69d37526）。计划 `docs/开发计划/20261029-0245-T-ReleasePerf9-发版门禁与全量测试墙钟压缩第四期-开发计划.md`。
> 接续 T6/T7/T8（发版门禁墙钟压缩一~三期）。用户令逐字同题第四轮。

## 一、问题定性与本期定位

T8 权威轮 11m15s 已把 releaseGate 的结构性空间收干（marketplace 长杆 ~10m 占总墙钟 ~90%，在线语义红线不动）。但 2026-10-28 三轮实测暴露了权威轮未覆盖的运行形态：

1. **5 个分片（同 root project）真并发起跑**（START 戳相差 <60ms）——2026-10-20 轮「严格串行 911s」是旧树读数已过时；
2. 内存挤时（另一会话测试链 / 用户 IDE / 62GB+ 基线）5 测试 JVM + verifier 同时在场直冲 **native OOM**（hs_err `Chunk::new` / `G1 virtual space`），当日三轮作废；
3. 兜底手段（`--max-workers=2`、releaseGate 人肉分阶段 11m13s）散落踩坑记忆，未固化进构建默认——**OOM 重跑 + 人肉编排才是现实时间大头**。

本期把「测试链并发度」做成构建内置一等参数（限流内置化），错峰实现同步重构为限流兼容形态。

## 二、机制（三项落地，e47fc3a9）

### 1. 共享构建服务限流

`MpvTestLaneLimiter.kt`（无状态服务类）+ mpv-testing.gradle.kts 注册块：

- `gradle.sharedServices.registerIfAbsent("mpvTestLaneLimiter", ...)`，并发上限设在 **`BuildServiceSpec.getMaxParallelUsages()`**（Gradle 9.7 javap 实证——注册块 configuration action 的 receiver 是 spec，服务实例上无 maxParallelLimit 属性，首版误写即编译错）；
- 挂接面：`tasks.withType<Test>().configureEach` 块内 `usesService(...)`——**IPGP 2.18.1 的 `TestIdeTask` 直接继承 `org.gradle.api.tasks.testing.Test`**（javap 实证），分片任务本身就是测试 JVM 的调度单元，一处挂接覆盖 testShard1..N / testExternal / test / testFast；
- DB 集成桶豁免（`isDbIntegration` 判断已有现成变量）——保 T-TestPerf14 的 testDb* 七路并行语义；
- 缺省值：独跑 2（= 10-28 实测 `--max-workers=2` 干净读数的精准化），releaseGate 编排内 3（`invokedTaskNames` 判定，与 stagger 同款机制），`-PtestShardConcurrency=N` 显式覆盖；
- **限流 ≠ 降片**：片数、每片类集、覆盖面逐一不变，压的是「同一时刻几片在跑」——与 R3 禁降片口径不同维度；
- 配置缓存兼容：`registerIfAbsent` + `usesService` 是官方通道，实测 `Configuration cache entry reused`。

### 2. 错峰迁移到共享前置（限流兼容的必然改动）

原 T7 形态：每片 doFirst 内 `Thread.sleep(285s)`。限流下这是结构性缺陷：**sleep 发生在限流槽内**——releaseGate 编排内限流 3 时，首波三片各睡 285s 占槽（正常），第二波分片排队拿到槽后会**再白睡整段 285s**（总墙钟 +5min 量级）。

重构：新增共享前置任务 `testShardStagger`（所有分片 `dependsOn` 它），错峰 sleep 只发生一次、睡满释放，分片们随后抢槽。**分片真实起点不变（≥ t0+285s），时间线与逐片 sleep 逐字等价**，仍守 T7「仅延迟启动，不删不减不重排测试语义」红线。

### 3. 交互面核查（零改动结论）

- **CI（build-plugin.yml）**：分步骤跑（各 gradle 命令独立 step），不触发 releaseGate 编排内缺省 3 分支 → 走缺省 2；CI runner 上「分片 JVM 偶发挂起」大概率即内存挤兑，限流 2 属改善方向；
- **test-shards-parallel.ps1**：lane 是独立 Gradle 进程且单 lane 单任务，限流不产生排队——无交互；
- **verifyGate 的 gateStaggerMs**：verifyGate 是 JavaExec 不在 Test 面，与限流无交互，不动。

## 三、实施坑

1. **maxParallelLimit 不存在**：Gradle 9.7 的注册期并发上限 API 是 `BuildServiceSpec.getMaxParallelUsages()`，首版按记忆写 `maxParallelLimit` 编译错——API 以 javap 为唯一权威（本项目一贯纪律）。
2. **.ps1 中文注释静默漂移**：等待脚本带中文注释（UTF-8 无 BOM），PS 5.1 按 ANSI(GBK) 误读后 `$target` 赋值行被坏字节破坏，while 比较恒 False、等待立即跳过（**不报错**，两次后台任务都 ~1 分钟内 "reached"）。改纯 ASCII + 打印 target 自证后正常。给 PS 5.1 的 .ps1 要么纯 ASCII、要么 UTF-8 带 BOM；含中文的静默失败面包括条件比较这类无异常的行。
3. **-P 属性不进任务 inputs**：`-PtestShardConcurrency` 只改限流服务配置，分片 Test 任务 inputs 不变 → 同码轮 UP-TO-DATE 跳过、START 戳读数消失——形态验证轮前须删 `build/test-results/testShard1..5` 强制真跑（并行运行器同款手法）。
