## 一、核心结论（TL;DR）

全量测试/releaseGate 的墙钟方差与 OOM 复发是**同一根因的两面：内存墙（Commit 上限 ~67.6GB，基线常驻 ~50GB 起）**。本轮不再分别打补丁，用一套水位机制两头收：

1. **测试链档位从静态改自适应**（券01）：内存宽裕自动提档提速，紧张自动收缩防 native OOM。同机同码 A/B 实测待回填（§三.3）。
2. **执行期水位快速失败闸门**（券02）：free commit 低于 floor（缺省 6GB）时秒级显式红＋Commit 占用 top-8 诊断＋处置指引，替代「13 分钟后分片执行器散成片 native OOM」（R24 形态）。负测 2s 红见 §三.1。
3. **内存卫生脚本**（券03）：孤儿占位者报告/清理——20261029 实测 64 个 headless CDP 孤儿占 20.5GB 的那类问题从此有一键处置入口。
4. **verifyMarketplace home 闲时保温**（券04）：发行日下载税（10-29 实测 market 单步 18m29s 占整链 88%）常态化解——对最近发行包提前回填依赖缓存，正式门禁语义零变化（T7 verdict 缓存红线未触碰）。

## 二、机制与落点

### 券01 水位自适应限流

- 探针：`buildSrc/src/main/kotlin/MemoryWatermark.kt`（`MemoryWatermarkProbe`）。Commit 口径＝`Win32_OperatingSystem` 的 `TotalVirtualMemorySize/FreeVirtualMemory`（与 R1「判构建慢先采 Commit」同源）；PowerShell 调用样式照抄 `VerifierHomeGuard`（base64 `-EncodedCommand` UTF-16LE 零转义歧义＋CLIXML 清洗＋超时 fail-open）。
- 档位表（`pickLane`）：`effective = freeCommit − reserve`（releaseGate 编排内 reserve=6GB，预留 market 2.8GB＋gate 2.3GB 两 verifier JVM）→ ≥24→5；≥18→4；≥12→3；否则 2。5 档要求 ≥24 的依据：T9 实测限流 5 在 free 4.8GB 属危险区幸存（execSum +27% 争用膨胀），每 lane 测试 JVM ~1.5~2GB commit。
- 优先级：`-PtestShardConcurrency` 显式 > 自适应 > 静态缺省（2 / 编排内 3）；`-PtestLaneAdaptive=off` 一词保险丝回落 T9 静态行为。
- 采样时机：只在 taskNames 命中 `testShards|releaseGate` 的配置期采样（其他构建零开销）；选档与原始读数打 lifecycle 日志（`mpv-test-lane adaptive (...)`），审计可对。

### 券02 执行期快速失败闸门

- 挂点：`testShardStagger` doFirst 最前（testShardN 全体 dependsOn 它且它无输出恒执行 → 分片测试 JVM 出生前必经）＋`verifyGate` doFirst 最前（285s 错峰 sleep **之前**判定，不白睡）。
- 语义：`freeCommit < floor`（缺省 6GB；`-PwatermarkFloorGb` 覆盖；`-PwatermarkGate=off` 关闭）→ `GradleException`，报文含 top-8 commit 消费者＋四步处置指引。
- fail-open：探针失败（PS 不在/超时 30s/解析失败）降级 warn 放行——闸门自身故障不阻断构建；探针命中真低水位才硬失败。

### 券03 内存卫生脚本 `dev-support/memory-hygiene.ps1`

- 报告模式（缺省）：java/chrome/node 按 CommandLine 归类（gradle-daemon/test-executor/gradlew-shell/kotlin-daemon/verifier/sandbox-ide/user-ide/cdp-headless/cdp-other/java-other）输出各类 commit 合计＋疑孤清单（无活父壳 executor、CDP headless、WS<50MB 僵尸 Kotlin daemon、Kotlin daemon ≥2 提示）。
- `-Clean`：只杀 ORPHAN-EXECUTOR（父壳已死）/CDP-HEADLESS/CLIENTLESS-DAEMON（**仅当 0 个 gradlew 壳存活**——daemon↔client 无映射，有活壳即全保）/ZOMBIE-KOTLIN-DAEMON；用户 IDE、verifier、他会话进程永不碰。输出全 ASCII（PS5.1 BOM-less UTF-8 按 ANSI 误读坑，T9 在案）。
- 已知边界：CDP 子进程不带 `--headless`/`remote-debugging-port` 旗标 → 归 cdp-other；杀父进程后子进程随之退出（chrome 进程树语义），不做逐子猎杀。

### 券04 verifyMarketplace home 闲时保温

- 新任务 `verifyMarketplaceRefresh`（`buildSrc/src/main/kotlin/mpv-verification.gradle.kts`）：与 verifyMarketplace 同参数面（在线、无豁免、同 marketplace home、`assertNoForeignVerifier` 锁探测同款），差异仅三处——报告落 `build/reports/pluginVerifierRefresh`／doLast 不做 baseline 判定（只打锚点＋写 `home/.mpv-refresh-stamp`）／zip 解析 `-PrefreshZip` 显式 → `distributions/*.zip` 最新 mtime → 无 zip `StopExecutionException` 跳过。
- 语义红线：正式门禁仍在线、无豁免、按 verdict 判失败；本任务只是把「下载」段搬运出关键路径，**不做任何 verdict 缓存**（T7 语义阉割红线未触碰）。
- 登记形态（D-2 裁量）：OffPeak 机制为一次性任务（OffPeakList 实测 16 条历史均一次性）、CronCreate 才支持周期——**不做常驻自动化**（用户未委托）；落地＝发行日前手动 `./gradlew verifyMarketplaceRefresh` ＋ `gradle-gate.ps1` 在 `releaseGate|verifyMarketplace` 命中时查 stamp、>36h 打 WARN（只警告不阻断）。

### 3.3 A/B 档位对照（同工作树，B=lane2 基线 / A=自适应）

**B 轮（`-PtestLaneAdaptive=off`，实为 lane=2）**：总墙钟 **16m08s**（BUILD FAILED 于 shard2 的 4 例已知红，见 §3.5）；测试窗 670.5s（首片 START 1793321366915 → 末片 END 1793322037397）；execSum 1149.2s；构建段 ≈298s（**新工作树冷构建**：compileKotlin+jar+composedJar+5×prepareSandbox）。水位闸门读数 `free 11.24GB ≥ floor 6.0GB`，未误伤。

**A 轮（自适应，同工作树第二轮）**：总墙钟 **22m18s**（BUILD FAILED 于 4 例已知红 + agent 1 例 flake）；测试窗 1083.5s；execSum **1000.8s**（比 B 轮 1149.2s 少 148s）；分片四元组 **8429 / 4 / 0 / 8**，与 B 轮**逐字 parity**。

两个必须分开说的结论：

1. **权重自愈生效**：B 轮是冷树首跑（零历史 XML → 等权装箱 → shard1 扛 417.9s），A 轮吃到 B 轮产出的时长样本后重排，shard1 降到 224.4s、临界片失衡从 **+82% 收敛到 +13%**。这是 T-TestPerf12 定例的又一次复现：**新树冷轮读数不能当性能判据**。
2. **A 轮实际是 1 片同时跑（并发度 1），不是 lane=2**：START/END 戳严格首尾相接（shard1 END 1793322701219 → shard2 START 1793322701255，差 36ms；shard2 END → shard3 START 差 26ms），测试窗 1083.5s ≈ execSum 1000.8s × 1.08。B 轮同参数（lane=2）却是真并发（shard2 在 shard1 结束前 366s 就起跑，测试窗 670.5s ≈ execSum/1.7）。⇒ **限流服务的「2 个许可」在两轮里的实际并发度不同**，这是本轮最值得追的异常，见 §四 坑 1。

**档位与墙钟的关系（本轮实测锚点）**：测试窗 ≈ execSum ÷ 实际并发度。execSum 稳定在 1000~1150s，因此 **并发度是唯一可动的杠杆**：并发 1 → ~1080s；并发 2 → ~670s；并发 4~5 → 250~350s（T9 实测 5 片全并发 5m02s）。

## 四、新坑与定例（本轮新增）

### 坑 1：`maxParallelUsages` 是许可上限，不等于执行期并发度——同参数两轮走出两种形态

同一工作树、同一 `maxParallelLimit=2`，B 轮 2 片真并发（测试窗 670.5s ≈ execSum/1.7），A 轮严格串行（测试窗 1083.5s ≈ execSum/1.08）。戳面证据：A 轮 shard1 END 与 shard2 START 相差 36ms、shard2 END 与 shard3 START 相差 26ms（首尾相接）；B 轮 shard2 在 shard1 结束前 366s 就起跑。

两轮可观察到的唯一差异：A 轮开局 `:sql-visualizer-agent:test` **失败**（190 例 1 红 flake），B 轮该任务通过；且 A 轮的 `testExternal` 在 shard1 起跑前 44ms 结束（B 轮是并行重叠 72s）。

**处置（已落代码）**：分片 doFirst 增打 `laneActive=N`（`MpvLaneMeter`，进程内原子计数）——以后判「档位到底有没有变成并发」只看这一个读数，不再从 START/END 戳反推。**未闭环**：根因（失败任务是否导致许可未释放 / 调度降级）需在空闲窗复跑取证，已列 §五 移交。

**教训**：判并发度不能只看「档位配置值」或「START 戳是否重叠」（后者在限流排队下会被延迟启动掩盖）；要一个执行期自报的活跃计数。

### 坑 2：配置缓存复用会让配置期水位采样变旧（P-1 的实测答案）

实测：`./gradlew testShards --dry-run` 连续两次，第二次打印 `Reusing configuration cache` 但**采样行仍然重新出现**——因为 dry-run 与真实轮之间 `build/test-results` 未变，CC 复用了；真实测试轮写完结果 XML 后 CC 必然失效，故**真实轮每次都会重采样**。

结论：配置期采样在真实轮是新鲜的；但「同一份结果目录连跑两次」的形态（例如改完参数只跑 dry-run）会吃到旧读数。因此**券02 的闸门刻意放在执行期（doFirst）**，与 CC 完全解耦——负测里 `entry reused` 而闸门照常判定，即此设计价值的直接证据。

### 坑 3：冷工作树的墙钟读数会把「构建段」和「分片失衡」算进来

新工作树首跑：构建段 ≈298s（compileKotlin + jar + composedJar + 5×prepareSandbox），分片失衡 +82%（零历史权重 → 等权装箱）。两者合计让首轮 16m08s 里只有 670s 是真测试窗。**给用户报「全量测试要多久」时必须说明是冷树还是暖树、第几轮**——这也是本轮 A/B 两轮不可直接比墙钟的原因。

### 坑 4：配置期用 `ProcessBuilder` 起子进程会被 Gradle 9 判失败（CC problems）

券01 最初在配置期用 `ProcessBuilder` 起 PowerShell 采水位。前几轮 dry-run 都"看起来正常"（日志有 `Configuration cache entry stored`），但**权威 gate 轮直接以第三条失败收场**：

```
Configuration cache problems found in this build.
1 problem was found storing the configuration cache.
- Plugin 'mpv-testing': external process started 'powershell -NoProfile -NonInteractive -EncodedCommand ...'
```

Gradle 9 把 CC problems 当失败处理（不是警告）。**修法**：配置期改用 CC 官方通道 `providers.exec { commandLine(...) }.standardOutput.asText.get()`（结果作为构建输入被记录），执行期（doFirst）继续用 `ProcessBuilder`——执行期起进程不受此限制。改后 `BUILD SUCCESSFUL` 且无 problems。

**教训**：这类缺陷**只在真实构建里现形**——dry-run 与单任务调用都能"存下 CC 而不报"，必须跑一次完整多任务构建才算验证过。

### 坑 5：并发度计数器会被失败任务污染

第一版 `laneActive` 用进程内 `AtomicInteger`（doFirst 自增、doLast 递减）。失败分片不执行 doLast → 计数只增不减，此后每轮读数都带着上一轮的残值（gate 轮实测 `laneActive=2` 实为 shard2 失败的残留，真实并发是 1）。

**修法**：改成**进程扫描**（`ProcessHandle.allProcesses()` 数命令行含本树 `test-sandbox/` 的执行器），读数与任务成败无关；并改名为 `laneOthers`（本片起跑瞬间**其他**在跑分片数），语义不含歧义。

**教训**：可观测点自身也会撒谎。凡"自报状态"的埋点，先问一句"失败路径上它还准吗"。


### 定例：水位机制的验证要能脱离「此刻机器有多少空闲」

档位表用 `-PwatermarkOverrideFreeGb` 钉住输入做六点矩阵（5/8.2/9.8/11.4/13/20 → 2/2/3/3/3/3（默认 cap=3）），闸门用 `-PwatermarkFloorGb=999` 做反向红测——两条都不依赖真机水位。真机水位轮（free 3.73/9.66/13.09GB）只用来证明「探针读得到、档位对得上」。
