# Token 消耗治理调研与分级落地方案

**日期**：2026-10-31
**触发**：用户提问「插件开发过程中 token 消耗较高，如何在保质保量不受影响的情况下节省 token」，并点名调研 GitHub 项目 rtk。
**基线**：master `afd3d091`；本文只做调研与方案，未改生产代码。
**取数**：ZCode 本地用量库 `~/.zcode/cli/db/db.sqlite`（只读）、`mcp__zcode-token-usage-statusbar__token_usage`、仓库实测文件体量、`zcode.cjs` 发行包反查。

## 一、核心结论

1. **成本不是输出造成的**：近 30 天 prompt 42.23B、output 77.79M，输出只占 0.18%。所有「让模型少说话」的手段对本仓无效。
2. **缓存已到顶**：cache read 占 prompt 的 95.2%，继续优化缓存没有空间。问题在绝对量——每次请求都背着几十万 token 的历史。
3. **消耗高度集中**：951 个会话里，平均上下文 >400K 的 35 个（3.7%）吃掉 61.8% 的 prompt；≥200K 的 106 个（11%）吃掉 85.6%。单 turn ≥50 次模型请求占 77% token，≥100 次占 51.5%。
4. **省 token 的主杠杆是会话粒度，不是提示词**：总消耗 ≈ Σ(每次请求的上下文大小)。一条工具输出进入上下文后，会在后续每次请求里重发。所以「早收口」的收益是乘法级的，「少写几个字」是加法级的。
5. **rtk 不适用**：它对 Gradle 测试日志的 99.8% 压缩，压掉的几乎全是任务行噪音；构建模式保留的 94KB 全是它明确不压的 `w:` Kotlin 警告，而编译错误的 `symbol:`/`location:` 续行它明确丢弃。且它只拦 Bash 工具，`Read`/`Grep` 不过 hook。

## 三、成本模型

单次请求的成本 ≈ 该时刻的上下文大小。上下文由三部分组成：常驻开销（≈20K）+ 会话历史（工具输出、助手回复、用户消息）+ 本轮新内容。

关键性质是**放大效应**：第 k 次请求产生的一条 5K token 工具输出，会在此后每一次请求里重发；若会话还有 100 次请求，它实际消耗 500K。因此：

- 在会话前段省 1K，等于后段省 N×1K；
- 一个 100 次请求的 turn，成本随请求数近似二次增长；
- 把长会话切成多个新会话，等于把二次曲线拉直。

这也是为什么「会话粒度」的收益远大于「输出压缩」和「指令瘦身」：后两者只减少每次请求的增量，前者直接改变 N。

## 四、分级方案

### P0 会话粒度（预估 -50% 量级，成本 0）

- 上下文到 12–15 万就收口：写交接文档 → 开新会话。
- 一个可提交单元一个会话；不在单会话里连做几天。
- 探索性工作交给 Explore 子代理（实测单请求均值 7.7 万，主 agent 40.4 万），主上下文只收 ≤1.5K 的结论。
- 查看当前上下文：`token_usage` 的 `current` 口径会显示「上下文容量 ≈ X tokens（最近一次请求输入）」。
- 对照现状：压缩发生在 ~90 万（由「压缩后回落到 30–40 万」的轨迹反推，属推断非读数），触发点太晚。

**与「丢记忆」的关系**（用户关心点）：新会话丢的是会话内工作上下文（读过的文件内容、工具输出、未落盘的推理），不丢 `AGENTS.md`、项目记忆目录、仓库文档与 git 历史。补偿手段是交接文档，字段固定为：当前分支与 tip、已完成、未完成、证据读数、下一步、踩过的坑。仓库现有的「计划文件 + 实施记录回填」就是这套机制，P0 只是把它的触发条件从「任务结束」提前到「上下文到线」。

### P1 工具输出闸门（预估 -10~20%，成本 0.5 天）

- 测试收口只跑 `dev-support/test-shard-aggregate.py`（8 行），不读 `build/*.log` 全文。
- 禁止整读 >100KB 的文件：先 `grep -n` 或 IDE 符号定位，再 `Read(offset, limit)`。
- 长输出一律 `> file 2>&1` 后 grep；`gradlew` 加 `-q --console=plain --warning-mode=none`。
- `BASH_MAX_OUTPUT_LENGTH` 由默认 30000 降到 12000：平台会把超长输出落盘，并在结果里给出 `Full output saved to: <path>`，全文不丢。

### P2 常驻开销（预估 -3~6%，成本 0.5 天）

- 重建 `MEMORY.md`：36KB → <20KB，恢复六节可见；「进行中」里自述已完成的条目移档。
- `AGENTS.md` 两条一次性事故（ACP 认证 973B、沙盒许可 1,426B）正文已在 `~/.zcode/cli/memories/global/pitfall-*.md`，压成指针。
- 清掉三个工作树重复注册的 8 条技能。
- 关闭 `autoresearch` 插件（2026-10-31 单日记录 1,048 次 hook 失败，单次 339–3,156ms）。

### P3 可选增强（1–2 天）

- 开 IntelliJ MCP Server（`config.json` 里 `idea` server 已配置，端口 64342 未监听），用 `search_symbol` / `find_usages` 定位后只读行区间。它是唯一能正确解析 IntelliJ SDK + Kotlin + Gradle 多模块的检索后端。
- serena 免费 Kotlin 后端为 pre-alpha（Gradle classpath 不自动注入），不建议；向量检索类方案对本仓「符号级跳转」需求不如 IDE 索引精准。
- 模型路由无空间：主力已是 deepseek-v4.1-flash / GLM-5.3-Flash。

## 五、rtk 裁决

| 项 | 结论 |
|---|---|
| 仓库 | `rtk-ai/rtk`，85,117 star，Rust，v1.1.0（2026-10-25），Windows 原生支持 |
| 机制 | PreToolUse hook 改写命令 + 规则过滤输出；**只拦 Bash**，`Read`/`Grep` 不过 hook |
| 测试日志实测 | 155KB → 292B（-99.8%），但原日志 1,675 行里 `> Task` 仅 42 行，压掉的是噪音 |
| 构建日志实测 | 556KB → 94.7KB（-83%），保留的 94KB 全是 397 条 `w:` Kotlin 警告 |
| 信息损失 | `Caused by:` 细节被丢；`org.opentest4j` 断言行被当噪音；编译错误 `symbol:`/`location:` 续行无匹配规则被丢 |
| 接入成本 | 每条改写命令弹权限确认（它只读 Claude/Codex/Cursor 的 allow 规则） |
| 结论 | 不装。同等工作用 P1 即可，且不引入中间层 |

## 六、保质保量的红线

1. 会话收口必须配交接文档，否则新会话等于失忆。
2. 截断只截「通过时的噪音」；失败必须走 `build/test-results/**/*.xml` 的 `<failure>` 聚合，不能盲截栈。
3. `AGENTS.md` 的「验证与收口纪律」不动——省 694 token 换不回一次漏门禁。
4. 常驻开销瘦身只做「指针化」与「去重」，不删规则内容。

## 附：取数方法（可复现）

```sql
-- 会话分桶（近 30 天）
select session_id, sum(model_request_count) n, sum(input_tokens) inp
from turn_usage where started_at >= :cut group by session_id;

-- turn 分桶
select model_request_count, input_tokens from turn_usage where started_at >= :cut;

-- 工具输出
select tool_name, count(*), sum(output_bytes), max(output_bytes),
       sum(case when output_bytes > 50000 then 1 else 0 end)
from tool_usage where started_at >= :cut group by tool_name order by 3 desc;
```

静态体量：`wc -c/-l` + 分节正则切分；token 估算口径为中文 1 token/1.3 字符、英文 1 token/4 字符，误差 ±25%。
