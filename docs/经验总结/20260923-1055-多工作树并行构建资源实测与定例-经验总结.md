# 多工作树并行构建资源实测与定例 — 经验总结

- 来源：2026-09-22~23 会话。用户报「同时运行测试或构建时效率很低、并发受限」，诉求「多工作树、多智能体并发完成任务，不受构建工具影响」。立项 T-BuildConcurrency（**O-65**，计划 `docs/开发计划/20260922-2038-T-BuildConcurrency-多工作树并行构建并发治理-开发计划.md`），两轮实测（P-2 并发档位对照 + 降片对照与快通道验证）把原推断推翻两次后定例。
- 结论：**瓶颈是内存不是 CPU；构建并发上限 2 路；日常验证走 testFast、全量 3 片只单路收口；降片换并行度证伪**。机器规格 6C12T / 32GB / Commit 上限 74.7GB。

## 一、实测读数（3 秒粒度采样，同提交双工作树对照）

| 配置 | 每路墙钟 | CPU 均值 | Commit 均值/峰值 | 可用物理内存最低 |
|---|---|---|---|---|
| 单路 3 片 | 227s | 49.8% | 61.6 / 63.0 GB | — |
| 双路各 3 片 | 298s | 71.6% | 63.6 / 66.9 GB | 2.8 GB |
| 双路各 2 片 | 598s / 503s | 79.4% | 55.7 / 62.0 GB | **0.3 GB** |
| 双路 testFast | 94s / 155s | 80.1% | 56.6 / 57.5 GB | 2.0 GB |

采样方法：PowerShell 循环采 `Win32_Processor.LoadPercentage` + `Commit`（`TotalVirtualMemorySize - FreeVirtualMemory`），每 3 秒一条落 CSV；用「CPU 均值 + free 最低值」两个数即可区分 CPU 瓶颈与内存瓶颈。

## 二、三个被实测推翻的推断

1. **「单路 3 片吃满 6 核，并行无吞吐收益」→ 错。** 单路 CPU 均值仅 49.8%（53% 采样点低于 50%）；双路每路退化 1.31 倍，但两个任务总完成时间从串行 454s 降到 298s，**加速比 1.52**。
2. **「降片（3→2）省内存换更多并行路」→ 错。** 双路 2 片比 3 片慢一倍：片数减一使每片测试类从约 512 涨到约 770（时长均衡分区按片数重新贪心分配），单个测试 JVM 生命周期拉长、累积占用更大；Commit 只省 4.9 GB 而 free 从 2.8 GB 跌到 0.3 GB（换页风暴）。理论上也不通：每路时间 ∝ 片数，吞吐 ∝ 路数×片数÷时间 = 路数——**降片本身不产生吞吐，只能靠省内存换路数，而实测连这个都没兑现**。
3. **「`~/.gradle` 迁盘会让缓存因绝对路径失效」→ 错。** 目录联接（junction）保持逻辑路径 `C:\Users\USER\.gradle` 不变，迁后首个构建 10 个任务 9 个 `up-to-date`，缓存完全有效。40.003 GB（140114 文件）零失败搬移，C 盘可用 2.7→43.0 GB。

## 三、定例（此后按此执行）

| # | 规则 | 依据 |
|---|---|---|
| R1 | **构建并发上限 2 路** | 三组双路配置 free 均 ≤2.8 GB；Commit 上限余量仅 7.8 GB |
| R2 | **日常验证 `testFast`（可双路）；全量 `testShards` 3 片只在单路收口跑** | testFast 双路 94~155s、Commit 峰值低 9.4 GB、验证吞吐约 2 倍 |
| R3 | **禁止用降片（`-PtestShardCount` 调小）换并行度或图提速** | 双路 2 片实测慢一倍 + free 0.3 GB |
| R4 | **预检仅 Docker 测试腿需要**：`timeout 10 docker info` 只在显式跑 Docker 测试腿（`-PmpvDockerTests=true`）前执行；Docker 腿默认关且在 testFast 桶、不进五片分片——日常全量/门禁**无需**验 daemon 活性（20261107 T-DockerGateOffload 改窄，取代旧「跑全量前必验」口径） | 引擎「半活」态会让该类无限挂起且不产失败读数（三态详版见项目记忆 `pitfall-docker-guard-hangs-indefinitely`）；开关前置（`mpvs.docker.tests.enabled`）后默认门禁连 daemon 都不探测 |
| R5 | **`~/.gradle` 实体在 `F:\gradle-home`，`C:\Users\USER\.gradle` 是 junction**；拆联接只用 cmd `rmdir` 或 PowerShell `Remove-Item`，**禁用 Git Bash `rm -rf`**（会跟随联接删真实内容） | 2026-09-23 迁移定案 |
| R6 | **判断构建慢先看 Commit 提交量，不是 CPU** | Commit 61~67 GB vs 物理 32 GB，超售即换页、全体变慢 |
| R7 | **提并行度只有两条路：加内存（CPU 常年有 20~28% 余量）或加快验证通道** | 其余手段（降片、限 daemon 参数）实测均无效或负收益 |

与既有「测试三档分层」（20260922-2310 经验总结）的关系：R2 是其在资源维度的补充——分层解决「跑什么、谁来跑」，本定例解决「同时能跑几路、用什么通道」。

## 四、方法与坑（复用价值）

1. **同提交双工作树对照法**：实验对照的首要条件是两树代码状态一致（本轮选 `01c6a99` 的两棵树，测试类数 2015/2026）；树不一致则测试集不同、墙钟不可比。
2. **实验树先清陈旧产物**：`build/classes` 落后主源码 15 小时 → 首跑 663 个 `NoSuchMethodError`（本仓在册形态）；`rm -rf build/classes build/kotlin` 后重编译即绿。**跑实验前看产物 mtime 是否新于 `src/main` 最新改动。**
3. **跨树并行无需改 `sandboxContainer`**：testShards 的分片沙盒在各自工作树 `build/test-sandbox/shardN`，天然隔离；改 build 脚本反而引入「用后忘还原」风险（在册前科两轮）。
4. **Git Bash 调 Windows 工具的 `/X` 参数会被 MSYS 转成路径**：`robocopy ... /E` 的 `/E` 被转成 `E:/`，报「无效参数 #3」直接退出（幸好零改动零损坏）。**带 `/X` 形式参数的 Windows 命令一律写 PowerShell 脚本执行**。`robocopy` 退出码 0~7 均为成功，8+ 才是失败，脚本判断禁用 `&&`。
5. **实验树可能被并行治理会话摘除注册**：本轮两棵实验树在实验后被 BranchHygiene3 批次摘了 worktree 注册（`.git` 指针删除、`git worktree list` 不再列出）——目录文件完好、不影响已提取的读数，但依赖这些树的后续动作要先 `git worktree list` 确认。
6. **实验后必须还原并验证**：本轮还原清单——临时移走的 `DialectDockerVerificationTest.kt` ×2、`~/.testcontainers.properties`（Testcontainers 探测成功时会**自行写回**该文件，手工改的绕过配置会被覆盖，绕过须用「明确指定快速失败策略 + 无效 DOCKER_HOST」）、并行登记注销、采样进程 kill、日志清理；以 `git status` 与进程清单双重验证。
