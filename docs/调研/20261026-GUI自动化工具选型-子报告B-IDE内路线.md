## 0. 一句话结论

**外部像素方案的根本缺陷只有一处：它不知道「组件是谁」。** 这条信息在 IDE 进程里本来就有，而且现成的 robot-server 已经把通道开出来了——只是我们一直只用它的 `/xpath/components`，没用它的 `/js/execute`。

**推荐路线：把「动作」搬进 IDE 进程，把「录像」也搬进 IDE 进程（或者至少换成 `gdigrab title=`），Python 只保留编排与后处理。** 不需要改插件、不需要重编译、不需要重启 IDE 换构建，且能一次性消掉四类失败模式里的三类半。

## 2. 路线 1：IntelliJ Platform 内部 API 直接驱动

### 2.1 先说一个被忽略的事实：robot-server 早就有执行通道

我把 `record/robot-plugins/robot-server-plugin/lib/instrumented-robot-server-plugin-0.11.23.jar` 反编译，`RobotServerImpl$startServer$2$2.class` 里的路由表是（反编译，字符串常量）：

```

/xpath/{id}/component  /xpath/{id}/components  /{id}/component ...
/hierarchy  /highlight  /recorder  /execute  /js/execute  /js/retrieveAny

```

我们只用了 `/xpath/components` 和 `/screenshot`。**`/js/execute` 和 `/js/retrieveAny` 一直躺在那里。**

### 2.2 `/js/execute` 是什么（反编译）

- 处理类 `RobotServerImpl$startServer$2$2$24$1.class` → 调 `IdeRobot.doAction(String, boolean)`，第二参数是 `runInEdt`
- 底层 `robot-server-core-0.11.23.jar` 的 `services/js/RhinoJavaScriptExecutor.class`：用 Mozilla Rhino 编译并执行脚本
- 关键实现细节（`RhinoJavaScriptExecutor` 字节码里的字符串常量）：
  ```
  importPackage(java.awt); importPackage(java.util); importPackage(java.lang);
  importPackage(org.assertj.swing.core); importPackage(org.assertj.swing.fixture);
  ```
- ClassLoader 构造（`executeWithContext` 反编译）：
  ```java
  PluginId.getId("com.jetbrains.performancePlugin") → getPluginClassLoader()
  new MultipleParentClassLoader(Arrays.asList(appClassLoader, perfPluginCl))
  context.setApplicationClassLoader(cl);
  ```
  即：**脚本能看见 IDE 的完整 classpath，外加 performancePlugin 的类**。
- 请求体（`data/js/ExecuteScriptRequest.class` 反编译）只有两个字段：`script: String`、`runInEdt: boolean`
- 加密默认关闭：`EncryptorFactory.getInstance` 只在 `-Drobot.encryption.enabled=true` 时才用 AES，否则 `TurnedOffEncryptor`（反编译）

### 2.4 平台自带的三个「非 robot」官方通道

这三条都是**官方**能力，不是野路子，但性质不同：

#### (a) `com.jetbrains.performancePlugin` 的 Playback 脚本引擎 —— 可用，且已在沙盒里启用

- 沙盒实测 `PluginManagerCore.isPluginInstalled('com.jetbrains.performancePlugin') = true`（默认随 IDE 发行）
- 入口属性（反编译 `ProjectLoaded` 静态初始化）：`-Dtestscript.filename=<脚本路径>`
- 执行链：`ProjectLoaded`（`ApplicationInitializedListener`）→ `PlaybackRunnerService.runScript(project, script)` → `LocalPlaybackRunner` → `PlaybackRunnerExtended.runBlocking`
- 命令注册：`CommandProvider.EP_NAME`，实测 `getAllCommandNames().size() = 226`
- 命令前缀实测（`javap -constants`）：
  - `%action <id>` —— 直接触发 action（**这条就是替代坐标点击的核心**）
  - `%toggle on|off`
  - `%sleep`
  - `%takeScreenshot` —— 走 `TakeScreenshotCommandKt.takeScreenshotOfAllWindows(...)`，**截所有窗口**（不只是主窗），落到 `<log>/screenshots/`；并且同类里还有现成的 `captureComponent(Component, File)`（组件级 paint 截图）和 `takeFullScreenshot(String)` —— 也就是说我在 §2.3 里手写的 `contentPane.paint(g)` 那套，平台已经有封装
  - `%executeEditorAction`、`%expandMainMenu`、`%goto`、`%openFile`、`%searchEverywhere`、`%closeAllTabs`、`%runClassInPlugin`
- 平台侧基础命令（`intellij.platform.ide.impl.jar` 的 `com/intellij/openapi/ui/playback/commands/`）：`%delay`、`%call`、`%[<shortcut>]`、`%pushStage/%popStage`、`%print`
- 构造参数已查清（反编译 `PlaybackRunner` 构造器 + `PlaybackRunnerExtended` 构造器）：
  - 第 3 个 boolean = `useDirectActionCall`，performancePlugin 传的是 `Registry.is("performance.plugin.playback.runner.useDirectActionCall", false)` → **默认 false，走真实点击模拟**（录 GIF 想看到光标动，这个默认正合适）
  - 第 4 个 boolean = `stopOnAppDeactivation`，performancePlugin 传 **`false`** → **IDE 失去激活不会中止脚本**
  - 第 5 个 boolean = `useTypingTargets`，传 `true`
- 也就是说：**我原本担心的「录屏时被抢焦点就中止」并不成立**，官方这条链已经把它关掉了。这条路线比我初判的更可行

#### (b) `intellij.driver`（JMX）—— JetBrains 新一代 UI 测试驱动，能力最强但工程最重

- 位置：`plugins/performanceTesting/lib/intellij.driver.{client,model,impl}.jar`（发行版自带）
- 机制（反编译 `com.intellij.driver.impl.Invoker` / `InvokerMBean`）：注册 JMX MBean **`com.intellij.driver:type=Invoker`**，方法 `invoke(RemoteCall)` / `newSession()` / `takeScreenshot(String)` / `exit()` / `putAdhocReference(Object)`
- 端口属性（反编译 `jmxDriver/InvokerService`）：`rdct.tests.backendJmxPort`、`rdct.tests.backendJmxHost`
- 客户端 API（`com.intellij.driver.client.Driver`）：`service(KClass)`、`utility(KClass)`、`new(KClass, args)`、`cast(...)`、`withContext(OnDispatcher, LockSemantics)`、`withReadAction`、`withWriteAction`、**`takeScreenshot(String)`**、`exitApplication()`
- 官方文档明确写了这套 DSL（`https://plugins.jetbrains.com/docs/intellij/integration-tests-ui.html`，原文）：
  > `invokeAction()` triggers a registered action directly by its action ID, without simulating a click or keyboard shortcut.
  >
  > `ideFrame { invokeAction("SearchEverywhere"); searchEverywherePopup { actionButtonByXpath(xQuery { byAccessibleName("Preview") }).click() } }`
  >
  > Similar to web testing frameworks like Selenium, XPath is used to locate components.
  - 组件树是**真正层级化**的（Top-level containers / Nested containers / Individual components），并且有 `http://localhost:63343/api/remote-driver/` 的 HTML 视图可查结构。
- 配套 `Starter`（`ide-starter`）负责**起一个全新 IDE 实例**并接管：`Starter.newContext(...).runIdeWithDriver().useDriverAndCloseIde { ... }`
- **代价**：这条路的定位是「CI 里跑集成测试」，要走 `intellijPlatformTesting { testIdeUi { ... } }` 与 `Starter` 起新实例，不是在现有录制沙盒上接管。用它录演示 GIF 属于「用叉车搬鸡蛋」。**但它证明了一件事：官方也认为「按 action ID 触发 + 按组件层级定位」才是正解，而不是像素。**

### 2.5 `testFramework` / `fixtures` 到底能干什么（结论：**不能驱动真实 UI，与录制无关**）

jar 实证（`com.jetbrains.intellij.platform:test-framework:262.10968.63` 与 `test-framework-common`）：

| 类 | 能做什么 | 不能做什么 |
|---|---|---|
| `BasePlatformTestCase` | 起一个 **light project**（内存 PSI），`myFixture` 造文件/编辑器 | javap 字段表只有 `CodeInsightTestFixture myFixture`；无窗口、无 ToolWindow、无 Action 菜单 |
| `CodeInsightTestFixture` | 编辑器级代码洞察测试（补全、高亮、重构） | 无 UI 交互 |
| `LightPlatformTestCase` | 静态 `ourProject` / `ourModule`，纯内存 | 同上 |
| `HeavyPlatformTestCase` | 真 project 结构 + 临时目录 | 仍是无窗口的 headless 应用 |
| `PlatformTestUtil` | `waitForPromise` / `waitForAlarm` / `assertTiming` / `dispatchAction` 相关断言 | **无截图、无鼠标、无窗口** |

`intellij-ui-test-robot`（我们现用的 robot-server 所属项目）在 GitHub 上 **131 star，2026-09-24 仍在更新，未归档**（API 实测）。它仍是外部客户端 + 进程内服务端的组合，只是我们已经用上了。

## 3. 路线 2：IDE 内置宏 / 脚本能力

### 3.1 Macro（Edit → Macros）—— 粒度太粗，但**可编程构造**

jar：`intellij.platform.ide.impl.jar` → `com/intellij/ide/actionMacro/`

- `ActionMacroManager`（反编译方法表）：`startRecording(Project, String)` / `stopRecording` / `playbackLastMacro()` / `playMacro(ActionMacro)` / `getAllMacros()` / `addMacro(...)` / `removeAllMacros()`
- `ActionMacro` 的三种 descriptor（反编译内部类）：
  - `ActionMacro$ActionDescriptor` —— **按 action ID**
  - `ActionMacro$TypedDescriptor` —— 按字符 + 键码（打字）
  - `ActionMacro$ShortcutActionDescription` —— 按快捷键
- 实测（沙盒内）：
  ```
  mgr=true | macros=0 | recording=false | builtActions=1 | actionId=Macro.probeMacro
  ```
  即：**能在内存里程序化构造一个宏**（`new ActionMacro('x'); m.appendAction('ActivateProjectToolWindow')`），ID 形如 `Macro.<name>`，也可以 `playMacro()` 回放。

**粒度问题（这是它的死穴）**：宏的录制单位是「action ID / 字符 / 快捷键」，**没有等待、没有断言、没有条件**。对录制演示动图来说，缺的恰恰是「等这个面板出来再点」。而且它回放依赖 DataContext 的当前焦点，焦点丢了照样点空（F4 不解决）。

结论：**宏只能当「动作序列的极简载体」**，做法与 `%action` 重复但更弱。**不推荐**。

### 3.2 Kotlin/Groovy Scripting（Settings → Languages & Frameworks）

- 发行版里 `plugins/groovy-scripting/lib/intellij.libraries.groovy.jar` 含 2630 个 `org/codehaus/groovy` 条目，**Groovy JSR-223 引擎随包发**（`META-INF/services/javax.script.ScriptEngineFactory`）
- 但沙盒实测 `isPluginInstalled('org.jetbrains.plugins.groovy') = false`（`groovy-scripting` 模块在但语言插件未启）
- `plugins/Kotlin/kotlinc/lib/` 有完整 `kotlin-scripting-*.jar`
- **硬伤**：IDE 的 script console 是**交互式 UI**，没有「跑一个文件、拿返回值、被外部程序驱动」的接口。要自动化就得自己找 `ScriptEngineManager` 去 `eval`，等于在写插件——绕了一大圈。**不推荐作为主路线。**

### 3.3 LivePlugin —— 路线 2 里唯一真正对口的

GitHub API 实测（`dkandalov/live-plugin`）：

- **951 star，未归档，最后 push 2026-10-21**
- 最新 release **v0.12.0 / 2026-10-21**
- `plugin.xml` 原文：`<idea-version since-build="2026.1"/>` → **与我们 2026.2.1 兼容**
- change-notes 原文：**"Added MCP tools for AI agents to run/find IDE actions, read IDE log and list/clear IDE errors"**

README 原文（`How does LivePlugin work?`）：
> - create a new classloader with dependencies on other plugins and jars (on a background thread)
> - compile code if necessary and load classes in the classloader (on a background thread)
> - run the plugin code (on EDT)
>
> **This means that plugin code can use any internal IDE API and observe/change IDE state.**

官方 wiki「Scripting a macros」（原文）：
> ```groovy
> def action = actionById("ActivateProjectToolWindow")
> action.actionPerformed(anActionEvent())
> ```

也就是说：LivePlugin = **在运行中的 IDE 里，热加载一段 Kotlin/Groovy，直接调任意 IDE API，不用重启、不用重编译、不用改本项目插件**。

**它与 `/js/execute` 的关系**：能力高度重叠（都是「进程内跑代码」），差别在
- `/js/execute`：Rhino（ES5 语法），零安装，已有通道，能调 `Packages.xxx`
- LivePlugin：Kotlin/Groovy（强类型、能 `import`、有 IDE 补全），需要装一个插件 + 重启一次 IDE，但**代码写起来舒服得多，且能注册 listener / 后台服务长驻**

**它比 `/js/execute` 少的一件事**：LivePlugin 没有 HTTP 入口，外部 Python 无法直接驱动它。要么靠它自己的 MCP 工具（`run_live_plugin`），要么让它自己做编排（即把整段录制逻辑写成 live plugin，Python 只负责收尾）。

### 3.4 路线 2 能力矩阵

| 方案 | 触发 action | 条件等待 | 截图 | 外部可驱动 | 改一行要重启 | 评级 |
|---|---|---|---|---|---|---|
| Macro | 可（ID 级） | **无** | 无 | 可（`playMacro`） | 否 | **受限**（粒度不足） |
| Kotlin/Groovy Scripting | 可 | 可 | 可 | **无接口** | — | **受限** |
| LivePlugin 0.12.0 | 可 | 可 | 可 | 半（MCP） | 否 | **可行** |
| `%action` playback 脚本（performancePlugin） | 可 | 仅 `%sleep` | 可（`%takeScreenshot`） | 可（`-Dtestscript.filename`） | **是** | **可行但有摩擦** |

## 4. 路线 3：录制层优化

### 4.1 三种抓取方式的实测对拍

同一台机、同一时段、800x600 区域、3~5 秒：

| 方式 | 命令要点 | 实测帧数 | 结论 |
|---|---|---|---|
| `mss`（现状） | Python 循环 grab + 管道 | 15fps 目标，`wait_stable` 依赖它 | 受 Python GIL/调度影响，且**画面不含弹窗之外的桌面元素** |
| `gdigrab` 区域 | `-f gdigrab -framerate 30 -offset_x -offset_y -video_size -i desktop` | 5s→149 帧 / 3s→89 帧 | 达标，CPU 抓 |
| `gdigrab` 窗口 | `-f gdigrab -i title="<精确标题>"` | 2s 抓到，`1354x976` | **按客户区抓，且不受遮挡**（见 4.2） |
| `ddagrab` | `-filter_complex "ddagrab=framerate=30:video_size=800x600:offset_x=300:offset_y=100,hwdownload,format=bgra"` | 5s→149 帧 | 达标，GPU 侧，能效更好 |

`ddagrab` 官方文档（`https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/filters.texi` 第 30557 行起，原文）：
> The filter exclusively returns D3D11 Hardware Frames, for on-gpu encoding or processing. So an explicit `hwdownload` is needed for any kind of software processing.
>
> `video_size` — Specify the size of the captured video. ... **Cropped from the bottom/right if smaller than screen size.**
>
> `dup_frames` — When set to true (the default), the filter will duplicate frames when the desktop has not been updated in order to maintain approximately constant target framerate. **When set to false, the filter will wait for the desktop to be updated (inter-frame intervals may vary significantly in this case).**

这条 `dup_frames` 很重要：`dup_frames=true` 会**制造大量重复帧**，正好和 `assemble.py` 的静态段裁剪对撞（白抓一堆再扔掉）。实测 `dup_frames=false` 3 秒仍出 90 帧（30fps），说明面板在动时它并不掉帧。

### 4.2 一项被低估的实测结论：`gdigrab title=` 不受遮挡影响

我做了对照实验：
1. 用 `EnumWindows` 找到 Chrome 窗口，`ShowWindow(SW_RESTORE)` + `SetForegroundWindow`，确认 `GetForegroundWindow() == Chrome`（实测 `True`）
2. 此时 IDE 被 Chrome 遮挡
3. `ffmpeg -f gdigrab -i title="mybatis-plus-sql-visualizer-demo – schema.sql [mpj_demo@localhost]"` 抓 1 秒
4. 出帧 1354x976，肉眼核对：**IDE 完整内容，没有任何 Chrome 的残影**

**意义**：`gdigrab title=` 走的是**目标窗口的 DC（`WM_PRINT`/bitblt from window DC）**，不是屏幕像素合成，所以**「别的窗口抢前台」不再污染画面**。这直接解决 F4 的「画面」那一半（点击仍会受前台影响，但至少录出来是干净的）。

注意两点：
- 标题必须**完全精确**（含 `– schema.sql [mpj_demo@localhost]` 这种动态后缀）。现成做法是从 `EnumWindows` 动态取标题，别写死。
- 未验证：`title=` 在 DWM 关闭 / RDP 会话下是否仍然成立。

### 4.3 现有中间格式要不要换

**不用换。** 实测 `record/perf/a13_execute_sql.mp4` 是 `h264 / High 4:4:4 Predictive / yuv444p`、`-qp 0`——**已经无损**，第 0 节已说。真正可优化的是：

- **只在需要时才录**：现在 `Recorder` 是全程连续录（`gifkit.py:357-382`），而 `wait_stable` 的等待时段全是死帧，录完再靠 `assemble.py` 剪。改成「稳定期暂停、动作期录」能把中间产物缩到 1/3 以下
- **抓区域而非整屏**：现状已经是区域（`Recorder(region)`），这条已做对
- **`ddagrab + dup_frames=false`**：省掉重复帧，`assemble.py` 的 `thr` 判定也会更干净

### 4.4 「录完自动去静止段 + 出 GIF」的成熟工具链

| 工具 | 定位 | 实测/核实 |
|---|---|---|
| `ffmpeg mpdecimate` | 单命令去近重复帧 | 本机 `ffmpeg 8.1.1` 可用；单遍 `fps=10,scale,mpdecimate,split/palettegen/paletteuse` 实测出 172KB/4.2s（对比现有 `assemble.py` 346KB/3.87s，**更小但时长控制不如现有精细**） |
| `ffmpeg freezedetect` | 只检测不删除，输出时间戳 | 本机可用（`-filters` 实测列出） |
| `gifski` | 基于 libimagequant 的高质量 GIF 编码器 | GitHub 实测 **5678 star，1.34.0 / 2025-07-13，仓库 2026-06 仍在更新**；但本机**未安装**（`which gifski` 空） |
| OBS + obs-websocket | 专业录制，WebSocket 遥控 | OBS **33.0.0 / 2026-10-23**；`obs-websocket` 4380 star；OBS 启动参数官方文档（`https://obsproject.com/kb/launch-parameters`）原文含 `--startrecording`，但**没有 `--stoprecording`** —— 停止必须走 WebSocket 或 UI |

**关键判断**：这三类工具解决的都是「已经录好的视频怎么变小」，**不解决「录的过程点不准」**。而我们的失败根因在后者。所以路线 3 只能当**降本增效**，不能当**方案**。

一个具体的可落地点：`gifski` 替代 `palettegen/paletteuse` 双通道，能在同等体积下明显提质（尤其渐变色/抗锯齿文字）。但它是新增外部依赖，需评估 CI/他人复现成本。

## 5. 三条路线的失败模式覆盖对照

| 失败模式 | 路线 1（进程内 API） | 路线 2（宏/脚本） | 路线 3（录制层） |
|---|---|---|---|
| **F1 坐标写死** | **彻底消除** —— 按 action ID 触发（实测 #12），不产生坐标 | **消除** —— `%action` / `actionById` 同效 | 完全无改善 |
| **F2 像素扫描** | **彻底消除** —— XPath 按 `accessiblename`/`class` 定位；弹窗也能取（实测 #15） | 消除（同左） | 完全无改善 |
| **F3 动画漂移** | **大幅改善** —— 进程内可先 `invokeAction` 再等真状态：ToolWindow 用 `isVisible`（实测 26ms 落定）、弹窗用 `JBList.getModel().getSize()`（实测 #20），**用状态而非时间判就绪** | 部分改善（能等状态，但要自己写） | 无改善（甚至因 `dup_frames` 更差） |
| **F4 焦点丢失** | **画面侧解决**（进程内 `paint` 截图不需要前台，实测 #6）；**点击侧需注意**：真鼠标轨迹（实测 #14）仍受前台影响 | 同左 | **画面侧彻底解决**（`gdigrab title=` 实测在 Chrome 前台时仍抓到完整 IDE） |

读法：**路线 1 与路线 2 是互补的「同一件事的两种载体」；路线 3 是正交的「另一层」**。真正的最优解是 1（或 2）+ 3 组合，不是三选一。

## 7. 明确推荐

### 7.1 主推：**路线 1 为主体 + 路线 3 的 `gdigrab title=` 替换 `mss`**

具体形态：

```
Python 编排（保留现有 scene_*.py 骨架）
  ├─ 动作：POST /js/execute   → ActionUtil.invokeAction("XxxAction", ...)   ← 消 F1
  ├─ 定位：POST /xpath/components（现有）→ 盲区用 /js/retrieveAny 遍历组件  ← 消 F2
  ├─ 就绪：POST /js/retrieveAny { script: "String(tw.isVisible())" }        ← 消 F3
  │        （ToolWindow 用 isVisible，弹窗用 JBList 行数，别用 isShowing）
  ├─ 录像：ffmpeg gdigrab title=<动态取到的窗口标题>                        ← 消 F4（画面）
  └─ 后处理：assemble.py 原样保留（已经调好）
```

**不做的三件事**（并给出理由）：
1. **不改本项目的插件源码** —— 所有能力都在 platform + robot-server 里，加代码只会增加维护面
2. **不换 `BasePlatformTestCase`** —— 它是 headless 的 PSI 测试，产不出动图（第 2.5 节，jar 实证）
3. **不上 `intellij.driver`/`Starter`** —— 它是给 CI 起新实例的，接管现有沙盒是逆着设计用；但**它的存在反证了我们的方向是对的**（官方文档原话：`invokeAction()` triggers a registered action directly by its action ID, without simulating a click or keyboard shortcut）

### 7.2 什么情况下改投路线 2

如果出现以下任一情况，把编排逻辑整体搬进 LivePlugin 更划算：

- Rhino 的 ES5 语法成为主要摩擦（想写复杂状态等待、循环、异常处理）
- 需要长驻监听（例如「等某个 toolwindow 出现就开录」）
- 希望这套录制引擎能被团队其他人复用，而不是私有 Python 脚本

**注意**：LivePlugin 是第三方（个人维护，951 star），引入它等于给录制链加一个外部依赖。用它做**开发期工具**可以，**不要**成为发行物的一部分。

### 7.3 明确说「不值得」的

- **`Macro`**：粒度是 action/字符/快捷键，**没有等待、没有断言、没有条件**；回放依赖当前 DataContext 焦点，F4 不解决。**不如直接 `/js/execute` 调 action。**
- **`%action` 那套 playback 脚本（不在 LivePlugin 里用时）**：这条本来我判它「不值得」，反编译后**改判为「备选可行」**——`PlaybackRunnerExtended` 显式传 `stopOnAppDeactivation=false`，IDE 失焦不会中止脚本。但它仍有三个实际摩擦：① 脚本要靠 `-Dtestscript.filename` 在**启动时**注入，改一行就得重启 IDE（`/js/execute` 是即时生效）；② 226 条命令里没有「等自定义条件」的通用原语，`%action` 后的同步只能靠 `%sleep`；③ `%takeScreenshot` 的落盘节奏不可控。**结论：可以用，但只在「启动即跑完整脚本、不需要中途改」的场景下才比 `/js/execute` 省事。**
- **OBS 全链路**：`--startrecording` 有官方文档，但**没有 `--stoprecording`**，停止要走 WebSocket。为了「录一个 IDE 窗口」引入 OBS + obs-websocket，工程复杂度远超收益。`gdigrab title=` 已经解决遮挡问题。
- **整屏录后裁剪**：现状已是区域录（`Recorder(region)`），这条早就不是问题，别再往回退。

## 8. 与「继续用外部脚本 + robot-server」的关系

任务要求我明确表态。我的答案是：**不是「不如继续用」，而是「继续用，但把 robot-server 用全」。**

- 架构不变：仍是「外部 Python 编排 + IDE 内服务端」
- 变的是**用哪个端点**：从只用 `/xpath/components`（只解决「找到」），变成 `/xpath/components` + `/js/execute`（同时解决「找到」与「做到」）
- 因此 `record/robot.py` 不需要推翻，只需**并列**加一个 `idejs.py`；现有 XPath 定位逻辑继续服务「断言组件在场」这类需求

一句话：**弃的是「用坐标点击」这个动作原语，不是「外部脚本 + robot-server」这个架构。**

## 9. 待验证前提（实施前先证伪）

这些是我在调研中推断出来、但没有实测的部分，实施第一步就该验证：

1. **`/js/execute` 单次脚本时长上限**：ktor 协程处理，实测 3 秒后台线程任务无问题；但**没测** 60 秒以上是否会超时或阻塞其他请求
2. **`ActionUtil.invokeAction` 的异步性**（已部分证实）：实测触发后 `isVisible` 26ms、`getComponent().isShowing()` 52ms 才转 true，且 `active` 更是滞后。**写场景时必须配 `wait_until`，不能"调完就截图"**；但不同 action 的完成时机差异未系统测
3. **`retrieveAny` 的返回值序列化范围**：实测字符串 OK、`java.awt.Point` OK；`Boolean` 走对象分支（见 #18）→ 说明**只要不是 `String` 就得自己实现 Java 反序列化**。**未测** List / Map / 自定义对象的拆包方案
4. **`gdigrab title=` 在 RDP / DWM 关闭场景**：仅本机物理桌面验证。若要跑在远程桌面主机上，需复测
5. **`gdigrab title=` 与 IDE 标题动态变化**：标题含当前文件名（`– schema.sql [mpj_demo@localhost]`），**切标签页标题就变**。必须在每段录制前重新取标题，或用 `-f gdigrab -offset_x/-offset_y` 走区域路线
6. **`/js/execute` 在 `runInEdt=true` 下调用 `invokeAction` 是否可能死锁**：`invokeAction` 内部可能需要 EDT 队列空闲。实测 #12/#17 成功（IDE 基本空闲）。若场景脚本里连续密集调用，需观察
7. **LivePlugin `MCP` 工具的实际粒度**：README 说有 `run_live_plugin` / `find IDE actions`，**未实测**其协议与稳定性
8. ~~**`PlaybackRunner` 第 5 个构造参数（`stopOnAppDeactivation`）的默认值**~~ —— **已查清**：第 4 个 boolean 是 `stopOnAppDeactivation`，`PlaybackRunnerExtended` 传 `false`；第 3 个是 `useDirectActionCall`（`Registry` 键 `performance.plugin.playback.runner.useDirectActionCall`，默认 false）；第 5 个是 `useTypingTargets`（传 true）
9. ~~**弹窗内的「等就绪」判据**~~ —— **已实测可行**（#20）：遍历 `HeavyWeightWindow` 组件树可拿到 `JBList` 的 `getModel().getSize()` 与 `getCellBounds(...)`。**但仍需逐场景确认**「哪一层状态才算真的渲染完」（`rows>0` 早于文字渲染完是可能的）
10. **`ToolWindow.isActive()` 的语义**：实测触发后 `isVisible=true` 但 `isActive=false`，二者不一致的原因未查清。判就绪建议只用 `isVisible` / `getComponent().isShowing()`

## 附录 A：可直接复用的最小验证脚本

```python
# record/idejs.py —— /js/execute 与 /js/retrieveAny 的最小客户端
import json, urllib.request

BASE = "http://127.0.0.1:8580"

def _post(path, script, run_in_edt=True, timeout=60):
    body = json.dumps({"script": script, "runInEdt": run_in_edt}).encode("utf-8")
    req = urllib.request.Request(BASE + path, data=body,
                                 headers={"Content-Type": "application/json"})
    return json.loads(urllib.request.urlopen(req, timeout=timeout).read())

def execute(script, run_in_edt=True, timeout=60):
    """只执行，不要返回值。"""
    r = _post("/js/execute", script, run_in_edt, timeout)
    if r.get("status") != "SUCCESS":
        raise RuntimeError("js/execute failed: %s | %s" % (r.get("status"), r.get("log")))
    return r

def retrieve(script, run_in_edt=True, timeout=60):
    """执行并取回一个可序列化值。

    返回体是 Java 对象序列化流。字符串的字节布局实测为：
        AC ED 00 05 | 74 | LenHi LenLo | UTF-8 数据
        4 字节魔数   标签  2 字节长度
    即数据从偏移 7 开始（2026-10-26 实测：'ABC' -> ac ed 00 05 74 00 03 41 42 43）。
    """
    r = _post("/js/retrieveAny", script, run_in_edt, timeout)
    if r.get("status") != "SUCCESS":
        raise RuntimeError("js/retrieveAny failed: %s | %s" % (r.get("status"), r.get("log")))
    raw = bytes((b & 0xFF) for b in r.get("bytes", []))
    if len(raw) >= 7 and raw[:4] == b"\xac\xed\x00\x05" and raw[4] == 0x74:
        n = (raw[5] << 8) | raw[6]
        return raw[7:7 + n].decode("utf-8", "replace")
    return raw

def invoke_action(action_id, timeout=60):
    execute("""
      var App = Packages.com.intellij.openapi.application.ApplicationManager.getApplication();
      var AM  = Packages.com.intellij.openapi.actionSystem.ActionManager.getInstance();
      var AU  = Packages.com.intellij.openapi.actionSystem.ex.ActionUtil;
      var act = AM.getAction('%s');
      if (act === null) throw 'no such action: %s';
      var W = Packages.java.awt.Window.getWindows(), frame = null;
      for (var i = 0; i < W.length; i++)
        if (W[i].getClass().getName().indexOf('IdeFrameImpl') >= 0) frame = W[i];
      AU.invokeAction(act, frame.getContentPane(), 'recorder', null, null);
    """ % (action_id, action_id), timeout=timeout)

def wait_until(js_condition, timeout_s=5.0, interval=0.1):
    """轮询一个 JS 条件直到为 true。

    两条实测出来的硬约束，写脚本时必须遵守：

    1) 条件必须包一层 String()。裸 Boolean(...) 返回的是已序列化的 java.lang.Boolean
       对象（流标签 0x73 TC_OBJECT），不是 UTF-8 串，拆包会拿到乱码，条件永远不成立。
    2) ToolWindow **没有** isShowing()。对 ToolWindow 调 isShowing() 返回的是空值
       （Rhino 侧表现为空串/undefined），不报错也不为 true —— 这是一个静默的死锁，
       会让 wait_until 白等满超时。判就绪请用 ToolWindow.isVisible() 或
       ToolWindow.getComponent().isShowing()。

    实测（hide → invokeAction('ActivateProjectToolWindow')）：
        hide 后 isVisible=false、getComponent().isShowing()=false
        触发 action 后 26~52ms 内两者均转 true

    例：wait_until("%s.isVisible()" % tw_expr)
    """
    import time
    t0 = time.time()
    while time.time() - t0 < timeout_s:
        if retrieve("String(%s)" % js_condition) == "true":
            return True
        time.sleep(interval)
    return False
