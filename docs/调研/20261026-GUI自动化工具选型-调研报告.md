# 演示动图录制效率优化调研报告

> 2026-10-26。起因：连续多轮录制反复因 UI 操作不当返工（dialect-gate 2 轮、replay-script-export 3 轮、sql-snippets 5 轮、mcp-agent 4 轮）。
> 目标：找出能减少操作时间、提高准确性与效率的最终方案，只留一种。
>
> 本报告由 3 个子代理并行调研 + 主控实测汇总：子报告 A（GUI 框架横向对比）、B（IDE 内路线）、C（ZCode 技能实测）。
> 所有读数分三类标注：**【实测】本机跑出来的**、**【反编译】jar/二进制证据**、**【文档】官方 URL**。未验证的推断明确写「未验证」。

---

## 一、结论先行

**最终选型：`/js/execute` 进程内驱动（新） + robot-server XPath 定位（保留） + `gdigrab title=` 抓帧（替换 mss）。**

一句话理由：**过去所有失败的根因不是「工具不够好」，而是「所有操作都在 IDE 进程外面」**——只能看像素、只能点坐标、只能靠 sleep 等。而 robot-server 里一直躺着一个从未被用过的 `/js/execute` 通道，能在 IDE 进程内直接触发 Action、读组件状态、抓帧、操作弹窗。接通它，四类失败模式里三类半直接消失。

**不建议换任何第三方 GUI 框架**（pywinauto / FlaUI / WinAppDriver / Airtest / SikuliX / Squish 全部实测或反编译证伪，见子报告 A）。
**不建议用 ZCode 的 computer-use 或视觉模型**（对 IDE 无障碍树只剩 2 个节点，视觉定位小图标 0/4，见子报告 C）。

## 二、现状定量基线（主控实测）

这组数据是选型的客观依据，先立在这里。

### 2.1 失败模式分布：坑表 52 条的分类

对 `~/.zcode/skills/ide-demo-gif/SKILL.md` 的坑表全文做关键词归类（一条可命中多类）：

| 失败模式 | 命中条数 | 占比 |
|---|---|---|
| **定位 / 坐标** | **26** | **50%（最大项）** |
| 布局漂移 | 22 | 42% |
| 环境配置 | 21 | 40% |
| 焦点 / 遮挡 | 14 | 27% |
| 输入法 / 键盘 | 14 | 27% |
| 产物质量 | 9 | 17% |
| 时序 / 动画 | 8 | 15% |

**关键观察**：52 条里 **21 条**（40%）是 2026-10-25/26 这两天新增的——不是「老问题反复」，而是**每录一张新图就踩一批新坑**。这说明成本不在「某个工具不好」，在于**每张图都要从零标定坐标**。

### 2.2 定位方式与硬编码坐标的强相关（82 个 scene 脚本全量统计）

| 定位方式 | 脚本数 | 硬编码坐标 |
|---|---|---|
| 纯 robot XPath | **30** | **0** |
| robot + 少量坐标 | 9 | 4~8 个 |
| **纯坐标（无 robot）** | **43** | 1~9 个，另有 5 个脚本叠像素扫描 |

全仓累计 **234 处硬编码 `(x, y)` 常量**。

本轮 4 张图的定位方式，正好解释了返工次数：

| 动图 | robot | 硬编码坐标 | 像素扫描 | 返工轮次 |
|---|---|---|---|---|
| n05 replay-script-export | ✅ | 3 | ✗ | 3 |
| n08 dialect-gate | ✅ | 4 | ✗ | 2 |
| **a15 sql-snippets** | **✗** | 3 | **✅** | **5** |
| **r10 mcp-agent** | **✗** | 6 | **✅** | **4** |

**结论：返工轮次与「是否用 robot 定位」强负相关。** 不用 robot 的两张正是最难的两张。

### 2.3 各定位方式耗时（本机 5 次均值）

| 方式 | 耗时 |
|---|---|
| robot XPath 定位 | 107 ms |
| 整屏抓帧 + 像素扫描 | 40 ms |
| 小区域抓帧 | 15 ms |
| pyautogui 全屏截图 | 41 ms |

**注意：robot 比像素扫描慢 2.7 倍，但准确率差距远大于这个代价。** 一次点空 = 重录一整条（几十秒到几分钟），而 robot 多的 67ms 完全可忽略。**优化目标是准确率，不是单步延迟。**

### 2.4 此前「robot 覆盖不全」的假设被推翻（主控实测）

过去认为「AI 面板、右键菜单 robot 查不到，只能用坐标」。实测推翻：

```
//div[@accessiblename]             -> 114 个
//div[@class]                      -> 225 个
仅靠 className 可定位（无 accessiblename） -> 111 个（占 49%）
```

**近一半组件没有可访问名，只有 className。** 之前查不到是因为 XPath 只写 `@accessiblename`。实测按 className 精确命中：

| 目标 | XPath | 结果 |
|---|---|---|
| AI 面板输入框 | `//div[contains(@class,'AIAssistantInputEditorTextField')]` | **1 个（332x56）** |
| 输入框编辑器本体 | `//div[contains(@class,'EditorComponentImpl')]` | 2 个（含编辑区） |
| 输入区容器 | `//div[contains(@class,'AIAssistantNewToolbarInput')]` | 1 个（348x108） |
| **右键菜单项（20 项）** | `//div[contains(@class,'ActionMenuItem')]` | **20 个，几何精确** |

右键菜单实测返回（屏幕坐标）：

```
(869,177) 461x26    (869,203) ...  (869,1012) 461x26   ← 20 项，等间距 26px
```

**这直接推翻了「a15 必须像素扫描找末项」的前提**——菜单项由 IDE 组件树直接给出，项数变化也不影响「取最后一项」。

## 三、三条路线评估

### 3.1 路线 A：第三方 GUI 自动化框架（子报告 A 结论：全部不优于现状）

调研 17 个候选，实测/反编译要点：

| 候选 | 结论 | 证据 |
|---|---|---|
| pywinauto / FlaUI / WinAppDriver / TestStack.White / uiautomation | **不可行** | 全部只支持 Win32/UIA；本机实测 UIA 对 IDE 只看到 `SunAwtFrame`、`children=0`（同探针在 Explorer 上 173 个后代）。**协议层的墙** |
| Airtest | **重复实现** | 读其源码 `airtest/core/win/win.py`：就是 pywinauto + mss + aircv（OpenCV），与现有 `anchor.py` 同构 |
| Poco | **不支持 Windows** | 官方平台表标「Not yet」 |
| SikuliX | **重复实现** | 纯图像匹配（OpenCV），与 `anchor.py` 等价；仓库已迁 `oculix-org/SikuliX1` |
| Squish（商业） | **冲突** | 支持 Swing，但要 `-javaagent:squishagent.jar` 挂钩 JVM，与本仓 qwdn 许可 agent 链路冲突 |
| AssertJ Swing / SwingLibrary / Marathon | **要求同 JVM** | 必须与 IDE 同进程或同 classpath |

**顺带修掉一个既有隐患（子报告 A 实测）**：`anchor.py` 的模板匹配在屏幕缩放偏离 1.0 时，不缩放模板直接掉到 **0.68~0.78**（低于 0.85 阈值）——表现就是「明明在屏幕上却找不到」。实测数据：

| 屏幕缩放 | 0.90 | 0.95 | 1.05 | 1.10 | **1.20** | 1.25 | 1.50 | 2.00 |
|---|---|---|---|---|---|---|---|---|
| 原尺寸模板得分 | 0.737 | 0.776 | 0.768 | 0.717 | **0.683** | 0.694 | 0.706 | 0.703 |
| 同尺度缩放模板 | 1.000 | 0.967 | 0.968 | 1.000 | **1.000** | 0.971 | 1.000 | 1.000 |

**处置**：本仓录制构图固定（IDE 缩放恒 120%），所以模板按 120% 标定、把 1.0 当基准，多尺度只吸收 ±3% 的字体渲染差异即可，不要让多尺度去吸收 ideScale。现有 5% 步长网格存在盲区（真实缩放落格点正中时最高只 0.83~0.87）。

### 3.2 路线 B：IDE 进程内驱动（子报告 B 结论：最优，且通道已就绪）

**核心发现：robot-server 早就有 `/js/execute` 通道，一直被忽略。**

反编译 `robot-server-plugin-0.11.23.jar` 的路由表：

```
/hello /screenshot /component /components /xpath/components
/hierarchy /highlight /recorder /execute /js/execute /js/retrieveAny
/retrieveAny /{id}/execute /{id}/js/retrieveAny /{id}/retrieveText ...
```

底层 `RhinoJavaScriptExecutor` 用 Mozilla Rhino 执行脚本，classpath 是 `appClassLoader + performancePlugin classloader`——**脚本能看见 IDE 的完整 API**。

沙盒实测 20 项全部通过，摘录关键读数：

| 能力 | 实测结果 |
|---|---|
| 枚举全量 action | `ActionManager.getActionIdList('')` → **4857 个** |
| 编辑器/文档可读 | `editors=26, text.len=639` |
| **进程内截图** | `contentPane.paint(g)` → 1354x936 PNG，肉眼核对为完整 IDE |
| **进程内截图速度** | 纯 paint **44 fps**；裁剪 700x500 + 内存 JPEG **32.7 fps**；后台线程连跑 3s **≈30fps 无异常** |
| **触发 Action 真实生效** | `ActionUtil.invokeAction(ActivateProjectToolWindow, ...)` → toolwindow `isVisible` 26ms 内转 true |
| **合成鼠标事件改真实选中态** | JTree 派发 `MOUSE_PRESSED/RELEASED/CLICKED` → `selectedRows=1` |
| **重弹窗可达（XPath 盲区）** | `Window.getWindows()` 里出现 `Popup$HeavyWeightWindow`，可遍历其 `JBList` 拿 `rows` |
| **等状态而非等时间** | 弹窗就绪判据 `JBList.getModel().getSize()` 实测可读 → **26ms/52ms 落定** |
| 跨调用状态 | JS global 每次新建；用 `System.setProperty` 可跨调用 |

**已知限制**（全部实测）：Rhino 是 ES5（无箭头函数/let/模板串）；变量不跨调用；返回值须可序列化；长脚本会阻塞 ktor 协程；取布尔必须 `String(...)`（裸 `Boolean(...)` 拆不出）；`ToolWindow` **没有** `isShowing()`（误用会静默等到超时）。

**明确不值得的**：Macro（粒度不足、无等待/断言）、Kotlin/Groovy Scripting（无外部驱动接口）、OBS（只有 `--startrecording` 没 `--stoprecording`，停止要走 WebSocket）、`testFramework`/`fixtures`（headless PSI 测试，产不出动图，jar 实证）。

### 3.3 路线 C：ZCode 内置技能（子报告 C 结论：不可用）

| 项 | 实测读数 |
|---|---|
| computer-use 无障碍树 | Raw/Control/Content 三视图各 **2 节点**，`Descendants` 仅 1；同机对照组 magpie 1787 / chrome 134 / weixin 36（探针有效） |
| MSAA | `S_OK` 但 `accChildCount=1`，展开 7 节点 name 全空 |
| JAB（Java Access Bridge） | 加载了 dll 但桥未启用；且 computer-use 是 UIA-only，启用也救不了 |
| **同一刻 robot-server** | **297 组件** —— 同一棵树，三种读法：**1 / 0 / 297** |
| 视觉 grounding 盲测 9 目标 | 整体 5/9；**文本大字 5/5 全中，小图标 0/4 全败**（最差裁出来是行号 `57`） |
| deepseek-eyes | 当前不可用：默认 VL 模型无 provider，ModelScope 账号未实名 |

**额外发现**：`agent.computerUse` 在子代理内直接拒绝（`Computer Use is not available in subagent`）——**无法塞进批处理管线**，这条单独就足以否掉。

**视觉方案的唯一可用落点**：一次性标定（产出候选框后用 robot/模板交叉确认）、失败取证与状态描述。**不适合每步驱动**（小图标不可靠 + 秒级耗时 + 不可脚本化）。

## 四、最终选型与架构

```
Python 编排（保留 scene_*.py 骨架与 assemble.py 后处理）
  ├─ 动作：POST /js/execute → ActionUtil.invokeAction("XxxAction")     ← 消除坐标依赖
  ├─ 定位：POST /xpath/components → class 与 accessiblename 双通道     ← 消除像素扫描
  │        弹窗/盲区 → /js/retrieveAny 遍历组件树
  ├─ 就绪：/js/retrieveAny {"String(tw.isVisible())"} 等状态           ← 消除 sleep 猜时间
  ├─ 抓帧：ffmpeg gdigrab title=<动态取到的窗口标题>                   ← 消除焦点/遮挡
  └─ 后处理：assemble.py 原样保留（已调好）
```

四类失败模式的覆盖：

| 失败模式 | 现状 | 新方案 | 依据 |
|---|---|---|---|
| **F1 坐标写死** | 234 处硬编码 | **消除**：按 action ID 触发，不产生坐标 | 实测 #12 |
| **F2 像素扫描** | 5 个脚本 | **消除**：class/name 双通道 + 弹窗遍历 | 主控实测 ActionMenuItem 20 项 |
| **F3 动画漂移** | 靠 sleep 猜 | **大幅改善**：等真实状态（26ms 落定） | 实测 #17 #20 |
| **F4 焦点丢失** | 常被浏览器抢 | **消除**：进程内 paint 截图不需前台；`gdigrab title=` 也不受遮挡 | 实测 #6 #11，B 报告 4.2 |

### 4.1 落地成本

| 项 | 工作量 |
|---|---|
| `record/idejs.py`（封装 /js/execute 与序列化解码） | ~150 行 |
| `record/ideactions.py`（invoke_action / wait_until / find_component / popup 等原语） | ~200 行 |
| 抓帧改 `gdigrab title=` | ~40 行 |
| 每个 scene 脚本改造 | 10~20 行 |
| 改插件 / 重编译 / 重启 IDE | **都不需要** |

### 4.2 立即已落地（本报告写作期间完成）

`record/robot.py` 新增三个函数，已实测通过：

| 函数 | 作用 | 实测 |
|---|---|---|
| `menu_items()` | 列出当前弹出菜单全部项（屏幕坐标，按 y 排序） | 20 项，首项 (869,177)、末项 (869,1012) |
| `click_menu_item(index)` | 点第 N 项（负索引从末尾数，`-1` = 末项） | 闭合检测正常 |
| `has_menu()` | 快速判断有无弹出菜单 | True/False 正确 |

**这已经把 a15 那套「像素扫描找末项 + 两段式量测子菜单」（为此返工五轮、约 100 行像素逻辑）替换为一行 `click_menu_item(-1)`。** 旧逻辑保留为 robot 不可用时的兜底。

## 五、分阶段执行建议

**第一期（立刻做，半天）**
1. `record/robot.py` 的菜单原语已落地 ✅
2. 把本轮 4 张图（n05/n08/a15/r10）里剩余的硬编码坐标逐处改成 XPath——这是最高性价比的改造，因为「纯 robot 的 30 个脚本零硬编码」
3. `anchor.py` 尺度细化窗口从 ±0.02 改 ±0.025，`scales` 默认改成 120% 基准窄带 `[1.15, 1.20, 1.25]`

**第二期（下一轮录制前，1~2 天）**
4. 新增 `record/idejs.py` 打通 `/js/execute`，先只用于「等状态」（替换所有 `time.sleep(3.6)` 这类猜时间）
5. 抓帧从 mss 换 `gdigrab title=`（顺带消除遮挡问题）

**第三期（可选）**
6. `ideactions.py` 把高频动作改成 `invokeAction`（彻底摆脱坐标）
7. 若要长期复用这套引擎，再评估 LivePlugin（第三方依赖，只在开发期工具用，不进发行物）

**不做**：换 GUI 框架、用 computer-use、用视觉模型驱动、上 OBS、改插件源码。
