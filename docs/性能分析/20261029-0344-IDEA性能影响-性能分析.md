# IDEA 性能影响深度分析（2026-10-29 复查）

> 分析基线：2026-10-29，master `69d37526`（v2026.10.28 发版后）。距上一份《20261027-0821-IDEA性能影响-性能分析》（基线 058cb33c）推进 23 笔生产码提交，增量主体为 T-PerfSweep27 修复批四券、Mapper 双向跳转（GitHub 外部贡献合入）、T-SqlDialectPrewarm（自研结果区高亮器＋方言映射预热）、T-ConsoleBind（执行控制台绑定对齐，含新文件 ExecFileBinding）与 T-ConnCastSafety 配套（agent 参数采集搬进语句织入通道，8c960343）。
> 方法：三路并行只读走查（启动注册面＋agent 通道、编辑器热路径、缓存内存与生命周期），主控对全部高风险断言逐行亲验（MapperNavigationLineMarkerProviders.kt、MapperXmlLocator.kt、GutterGroups.kt 全文在读）。全程未跑 gradle，量级词为代码级推算加既有压测判据，非 profiler 实测；涉及运行期读数的结论均注明证据边界。

## 一、总体结论

上轮「默认配置对 IDEA 无体感影响、零常驻线程/定时器/监听」的主体结论维持，且 2026-10-27 版遗留的 4 个可修点已随 T-PerfSweep27 全部销账（证据见 §三）。本轮唯一需要正视的是**新合入的 Mapper 双向跳转里 Java→XML 方向的 daemon 热路径缺陷**：它对每个打开 Java 文件的每个方法声明收取 O(mapper XML 文件数) 的 PSI 遍历，无接口判定前置、无负结果缓存、命中后也不早退，且文件清单缓存 5 秒过期后的全项目 XML 索引重扫发生在 daemon 慢趟线程内。形态与 2026-09-10 版定 P1 的 CustomDaoHql/CriteriaQuery gutter resolve 同族，本轮定级高（缓解因素与机制详见 §四）。这是本系列四期以来第一个非微项新发现，来源是外部贡献功能合入时未走「锚点→开关→重逻辑」定例的把关。

其余新增面全部健康：T-SqlDialectPrewarm 与自研高亮器是净改善（把 EDT 慢操作首查挪进后台一次性预热，词法成本变便宜）；agent 通道织入面实际缩小（达梦 connect 面摘除，拆掉了 VerifyError 炸宿主启动的雷）；ExecFileBinding 零状态零驻留。缓存/监听/线程三张清单与上轮对照：新增线程 0、新增监听 0、新增常驻 0，头部行新缓存经逐行核验无累积无泄漏。

风险分级一览：

| 级别 | 组件 | 现象 | 触发条件 |
|------|------|------|----------|
| 高 | MapperJavaToXmlLineMarkerProvider | 每方法声明一次 `MapperXmlLocator.locate`：无接口判定、无负 memo、命中不早退恒 O(mapper 文件数)；5s TTL 过期后全项目 XML 索引重扫＋逐文件 PSI 解析落在 daemon 线程 | 打开的 Java 文件 daemon 慢趟，活跃编辑期约每 5 秒一次全扫 |
| 中 | 两个 Mapper 导航 Provider | 完全未接设置开关（GutterGroups 未登记、文件内零开关引用），偏离「锚点→开关→重逻辑」定例，用户无逃生口 | 常驻判定链 |
| 中 | XML→Java 方向 resolve | `resolveInterfaceMethod` 用 `allScope`（含库）findClass 且无 DumbService 守卫（同文件 resolveClass :161 有），口径不一致 | mapper XML 语句标签行每慢趟一次 |
| 低 | 技术性无上限缓存 3 处 | SqlLogFileReader.countCache／HibernateNamingConfigProbe.cache／SqlPreviewService.activePreviewDialogs（键强持 Project）——均基线前既有、非本轮回归 | 长会话跨多项目/多模块 |

| 微 | F103 Kotlin 占位注册／AUDIT_CTX 清扫触发时机／Resolver 整体清空策略 | 维持登记 | 各条自明 |
| 无 | 启动/常驻/内存主线 | 启动五点类零改动；默认零常驻；T-PerfSweep27 三券修复形态干净 | — |

## 三、上轮遗留销账复核（T-PerfSweep27，四券全落）

- **R27-1 头部行每帧重算**（ea2b6f71）：静态段/来源段缓存为挂条目自身的三个可空字段（LogSqlModels.kt:237/240/246），非旁路 map——条目被缓冲区淘汰（默认 200 上限）时缓存片段同生共死，两万条流式灌入下机制上不可能累积；缓存键为纯设置值六元组（SqlEntryPresentation.kt:15-22），设置变更天然走重算；徽章段（去重/同结构计数）输入为面板级快照 map，正确地保持现算（:103-115）。单格预算 2.0ms 收紧到 1.0ms，改造后实测约 0.08ms/格（JUnit XML，2000 次渲染 0.197s 含预热均摊）。
- **R27-2 Resolver 族无上限**（002f0e37）：两处 4096 上限、写入前守卫超限整体清空（EntityResolver.kt:86,:566、JpaEntityResolver.kt:89,:735），键仍为字符串四元组不持 PsiFile 强引用；PluginCacheManager.clearAll 覆盖完整。
- **R27-3 补全日志＋HqlGutter 开关前置**（718233bf）：addCompletions 全部急切插值收进 isDebugEnabled 块（SqlCompletionContributor.kt:81-94）；HqlGutter 开关判定已移到 hasStringFirstArgument（含 resolve 分支）之前。
- **R27-4 AUDIT_CTX 取消残留**（3df4ebd8）：写入点顺带同步清扫——10 分钟过期窗＋64 上限按 started 移除最旧（McpToolsetSupport.kt:247-268）。「要累积残留就必须继续调用、而每次调用都触发清扫」互锁，绝对上界成立；误删在途条目代价为丢一条审计行，KDoc 如实登记。
- 全量门禁三轮终态收口（首轮 shard1 红出 PerfSweep27StaticGuardTest 未登记 GUARD_CLASSES 的真实缺口并补登，后两轮 4 红均为环境性假失败：C 盘被 O147HistoryUpgradeTest 临时目录泄漏吃满、排序比值判据毫秒以下基数噪声）。两条移交项见 §七。

## 四、新增面详评

### 4.1 Mapper 双向跳转（本轮唯一高风险，主控亲验）

注册面：plugin.xml:234-237，XML 语言挂 MapperXmlToJavaLineMarkerProvider、JAVA 语言挂 MapperJavaToXmlLineMarkerProvider（MapperNavigationLineMarkerProviders.kt）。两者 getLineMarkerInfo 恒 null（:19、:56），全部工作走 collectSlowLineMarkers（BGT 慢趟，可取消、不直接冻结 EDT，但吃 daemon CPU 拖慢绿检）。

**XML→Java 方向形态良好**：判定链 O(1) 语法锚点先行（XML_NAME token→语句标签名→起始名元素→mapper 根直接子级，:29-35），重活 resolveInterfaceMethod 只对真语句标签付出，一个 50 语句的 mapper 文件每趟约 50 次索引 findClass。两个瑕疵：`allScope` 而非 `projectScope`（namespace 是全限定名，库扫描纯浪费，MybatisXmlTargets.kt:180-182）；无 DumbService 守卫（同文件 resolveClass :161 有，dumb 态结果不完整，风险微）。

**Java→XML 方向是本轮唯一的高风险**（MapperNavigationLineMarkerProviders.kt:65-70，主控逐行核实）：

1. 判定链只有三层 O(1)（PsiIdentifier→parent PsiMethod→nameIdentifier），第四步即 `MapperXmlLocator.locate(project, "$namespace.${method.name}")`——**没有任何「这是不是 Mapper 接口」的判定**。service/util/main 等普通类的每个方法声明每趟照付全程。
2. `locate` 内 ReadAction 包裹后 `locateUnderRead` 遍历项目内全部 mapper XML 文件逐个比对根标签 namespace 属性（MapperXmlLocator.kt:58-74、:160-166）——且**命中第一个也不早退**（要扫完统计多模块同名用于 LOG.info，:60-66），单次 locate 恒为 O(N_mapper)。
3. 文件清单单槽缓存 TTL 5 秒（:101），过期后 `mapperXmlVirtualFiles` 做全项目 XML FileTypeIndex 枚举＋逐文件 PsiManager 解析根标签（:132-154）——**这次全扫发生在 daemon 慢趟线程内**。文件自身 KDoc 自述「数千 XML 项目首跳百毫秒级」；活跃编辑期该成本约每 5 秒重付一次。
4. 无负结果 memo：非 Mapper 方法必然落空但每趟重付。同族先例齐全——MybatisXmlTargets 有 namespace→文件单槽 memo（F96，MybatisXmlTargets.kt:94-122），CriteriaQueryGutter 有文件级特征门控（CriteriaQueryGutterLineMarkerProvider.kt:42-45，治愈样板）。
5. 无任何设置开关：GutterGroups.PROVIDER_GROUP 未登记两个类（GutterGroups.kt:23-40），Provider 文件内零开关引用——组开关体系对它们完全失效，同时失去了靠关闸省掉重逻辑的逃生口。

量级推算（代码级）：N_mapper=100、打开文件 30 个方法时，单文件单趟约 3000 次根标签属性读（未加载 PSI 访问含重解析风险）；数千 XML 的项目上每 5 秒一次百毫秒级索引全扫。定级高的依据：与 20260910 版 P1-1（CustomDaoHql/CriteriaQuery daemon resolve 无门控）同形态，且本项目的既有定例（锚点→开关→重逻辑＋门控＋memo）三条全缺。缓解因素：慢趟可取消、只作用于打开文件、TTL 封顶全扫频率、小项目无感。

### 4.2 T-SqlDialectPrewarm 与自研结果区高亮器（净改善）

- 预热助手非 EP 非启动活动，两个调用点都在编辑器装配链之前（SqlPreviewPanelEditorLifecycle.kt:82 预热线程、SqlLogToolWindowFactory.java:54 工具窗装配）。prewarmNow 在 BGT ReadAction 内触发一次 `SyntaxHighlighterFactory.getSyntaxHighlighter(SQL)`，把平台 PerFileMappingsBase 延迟加载（原会落在 EDT 的慢操作断言源）提前到后台；一次性由弱键 warmed 集合保证（SqlDialectMappingPrewarm.kt:49-50），失败不误标、致命错误透传（:87-92）；EDT 入口 prewarmAndAwait 有界等待 300ms 超时照常装配（:103-127）。
- 自研 `SqlSyntaxHighlighter`（231 行手写线性单遍词法）替换平台 Database 插件高亮器链后，结果区编辑器创建成本变便宜，且绕开了方言映射首查——预热要驯服的正是那条链。挂 LexerEditorHighlighter 的 7 处均为编辑器实例创建一次性路径，非每键/每帧。
- f062e833 守卫三件套锁住成果：SqlDialectEdtSourceScanTest（src/main 内 getSyntaxHighlighter 只允许预热助手一处，等值断言防失效豁免）、LogToSqlPanelUiTest（结果区首 token 必须是 MP_SQL_KEYWORD）、SqlDialectMappingPrewarmTest（短路契约）。
- 证据边界：运行期读数 R1/R2（262 沙盒 Slow operations 计数）未做，T-SqlDialectPrewarm 实施册已如实登记「断言已消失的结论目前没有运行期读数支撑」；结果区配色变化（P-5/P-8）待用户并排截图拍板。

### 4.3 agent 通道（织入面缩小）

- 参数采集搬进语句织入通道（8c960343）：织入类名单零扩大（WeaveSpecs.java:50-52、:88-89 只在既有形态数组追加 PARAM），每次类加载仍是 HashSet 名单先拦（SqlHookTransformer.java:72-83）未登记类零 ASM 开销；PARAM 织入为方法头 5~6 条直线指令插桩，无新局部、不动 maxLocals、不碰 StackMapTable（StatementWeaver.java:300-309）。
- 运行期每 setXxx 多一次 invokestatic，volatile 停采/代理门禁短路先行（SqlHookCallbacks.java:216-225）→ 16 桶弱键表 get＋TreeMap put（StatementRegistry.java:163-171），参数槽随 Ctx 弱键回收。
- 对宿主启动影响面净缩小：连接代理出厂关闭（SqlHookCallbacks.java:51-57 默认 false）；DriverRegistry 把达梦 DmDriver 从 connect 面摘除（DriverRegistry.java:40-47）——该面织入在 premain 路径会因 chop_frame VerifyError 炸宿主启动，是本轮实拆的一颗雷。

### 4.4 ExecFileBinding 与 DataSourceSelectorResults（零驻留面）

ExecFileBinding.kt（+249 行）为 internal object 纯判定函数＋反射探测，无任何集合字段/监听器/线程/Disposer 挂靠，反射 Method 现场查找不缓存（仅执行链触发），全部 runCatching fail-closed。DataSourceSelectorResults 的 65 行增量是复用判定升级，新增对象全部方法内瞬态，两处 dropSharedConsole 反而是主动回收。

## 五、缓存、监听、线程全量对照（与上轮差异）

**缓存**：有上限 19 处（新增 EntityResolver 4096、JpaEntityResolver 4096、AUDIT_CTX 64+10min 三处入册，其余与上轮清单一致）；弱键 4 处（新增 SqlDialectMappingPrewarm.warmed——WeakHashMap 键控 Project，项目销毁自动摘除）；设计有界 6 处。技术性无上限清单从「两处 Resolver」换为基线前既有的三处微项：SqlLogFileReader.countCache（键=历史文件路径，SqlLogFileReader.kt:153）、HibernateNamingConfigProbe.cache（键=projectBase|资源目录，:113）、SqlPreviewService.activePreviewDialogs（值弱但键强持 Project，SqlPreviewService.kt:2006）——键空间小、单条目轻，定级低。

**线程**：默认零常驻维持；开启捕捉后常驻面与上轮一致（桥 EDT Timer 互斥对 500ms 起步指数退避、面板诊断 Timer 2s、每 agent 会话读线程＋5s 巡检）；自建 daemon 5 处停机路径逐一在位；Swing Timer 全部单发/自停；基线以来新增线程创建点 0。无 java.util.Timer。

## 六、启动与常驻足迹

启动五点全部秒返或默认关，类文件自基线零改动：StartupUpdateCheck（默认关）、LogStartupCapture（默认关）、OnboardingAnchorTip（默认开一次性）、McpGateFilterRegistrar 与 AcpTransportRegistrar（探测式条件加载）。无新增 postStartupActivity、无索引/stub 注册、不参与索引构建。17 处 lineMarkerProvider 中 15 处维持「O(1) 锚点＋开关前置」定例，2 处新登记的不符合（见 §四.1）。agent premain 对宿主 JVM 的影响面较上轮缩小（§四.3）。MCP 无自建线程池，工具跑平台协程。

## 七、移交与在途

**上批移交（非本轮回归）**：① O147HistoryUpgradeTest 每跑一轮泄漏 130M 临时目录不清（曾累计 1292 个≈35G 吃满 C 盘，放大成全量门禁磁盘假失败）；② LogPipelinePerfTest 排序比值判据基数过小（2 千条 0.067ms，毫秒以下噪声主导，跨轮漂移 60.6→43.1）；③ 券01 真机项：头部行缓存对 EDT 占用的 JFR/Performance Watcher 对照读数未做。

**T-SqlDialectPrewarm 未闭环**：运行期 R1/R2 读数（262 沙盒 Slow operations 计数与先红栈）未做；BannedApiSourceScanTest 在 master 现行红——`setMapping` 裸子串守卫误命中 ExecFileBinding.kt 的 DataSourcePerFileMappingsImpl 反射（T-ConsoleBind 引入，目标类并非 SqlDialectMappings，守卫粒度太粗）；结果区配色观感待用户拍板（零观感方案=单独 revert e3ab9335 走 D3）。

**在途分支前瞻（未纳入本轮基线）**：t-sql-insight 领先 master 81 文件 +6797 行（方言改绑/内嵌控制台/DML 试算链），t-magpie-gems 28 文件 +1402 行，feature/kotlin-to-java 端口分支 60+ 笔未推。三者合流后须再走一轮增量走查，重点为 insight 的绑定态链路是否新增 daemon/EDT 面。

## 八、优化建议（按收益排序）

1. **MapperJavaToXml 门控与缓存（P1）**：`containingClass.isInterface` O(1) 前置→文件级特征门控（CriteriaQueryGutter :42-45 样板）→locate 结果按 (namespace,id) memo（与文件清单同代失效，F96 范式，正负结果都缓存）→接 GutterGroups 组闸。多模块同名 LOG.info 契约在 memo 后退化为「每窗口一次」可接受，或拆参数只在右键路径保留全扫统计。大项目模拟夹具（数百 mapper XML）下断言每趟 locate 调用次数。
2. **XML→Java 方向卫生批（P2）**：allScope→projectScope＋DumbService 守卫对齐，各一行级。
3. **三处技术性无上限缓存收口（P2）**：activePreviewDialogs 键换弱键或挂项目关闭钩子（值已是弱引用，一行级）；countCache 与 HibernateNamingConfigProbe 套 HbmXml 4096 整体清空范式。
4. **StringSqlMethodGutter 文件级门控（微，随批）**：同 CriteriaQueryGutter 样板，F 系遗留终账。
5. **守卫与测试卫生批（P2）**：BannedApi setMapping 子串守卫收窄（消除 master 现行红）；O147 临时目录 tearDown 清理；LogPipelinePerfTest 比值判据设最小基数下限（分母 <1ms 跳过比值只留绝对预算）。
6. 其余微项（F103、AUDIT_CTX 触发时机、Resolver 清空策略）维持登记，随下轮自然消化。

## 九、验证方法

延续既有方法：沙盒 attach JFR/VisualVM 观察 EDT 事件队列；IDEA 自带 Performance Watcher（idea.log 的 UI freeze 与 Slow operations 报告）量化。本版针对性场景：①大项目（≥500 mapper XML 夹具）打开含数十方法的非 Mapper Java 文件，改造前后对比 daemon CPU 占用与单趟慢趟墙钟（对应建议 1）；②活跃编辑期观察 mapper 文件列表重扫频率（TTL 窗口内应零重扫，memo 命中判据可加 indexScanCount 测试缝断言）；③262 沙盒跑 T-SqlDialectPrewarm R1/R2 补运行期读数。例行回归红线维持：两百条 SQL 流式灌入不掉帧、50KB 动态 SQL 逐键 <50ms、IDE Freezes 报告无本插件新增记录。
