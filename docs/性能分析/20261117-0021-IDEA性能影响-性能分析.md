## 一、总体结论

「默认配置对 IDEA 无体感影响」的主体结论第五次维持，且本周期出现了本系列首次**由性能问题驱动、以平台索引收口**的正向重构：F1'''（T-GutterFirstOpenDelay 精华采纳刀）与 T-IbatisGutterPerf 把 MyBatis 与 iBatis 两套「全项目 XML 清单」链路整体替换为自定义标量索引——旧链（FileTypeIndex 全扫 + 逐文件建 PSI + 5s TTL 单槽，demo 根工程 2493 → 303 文件每 5s 重扫一遍）在新形态下是「索引期一次摊平 + 运行时一次 getContainingFiles」，失效全交平台增量。这一刀同时收掉了上期 DumbMode 清单第 1 条（MapperXmlLocator 空表入 5s TTL 单槽——该状态机整体退役）。新增 20 处 lineMarkerProvider、3 个 gotoDeclarationHandler、1 个 gotoRelatedProvider 的热路径逐个抽查，锚点先行、O(1) 判定的声明与代码一致；启动活动 7 点（主 5 + optional 2）全轻；master 侧「新增常驻 0」不变式维持（无新周期任务，GutterWarmScheduler 是一次性延迟派发不是轮询）。

但本期有一项口径变化与一项新发现必须置顶：

第一，**master 与 dev 已形成「各自修了一半」的分裂态**。dev 已把第七期移交的 T-PerfSweep30 全套落地（预览首开五项账本券01a/01b/01c、DumbMode 五处、缓存上限化、红线面）；master 一笔都没有——但 master 自己用索引化收掉了 dumb 清单里 MapperXmlLocator 一条（dev 是用 dumb 早退修的同一条）。两支的收口余额互不覆盖，合流（T-BranchAlignMerge）后必须按 §三矩阵逐条验证「继承到位」，而不是默认合并即修复。

## 四、新增面详评（master 口径）

### 4.1 两个自定义标量索引：本周期最大的性能正贡献（合规，登记三条）

两个索引形态对称（`ScalarIndexExtension<String>`、XmlFileType 专属 filter、`dependsOnFileContent=true`、键域有界、Void 值、纯函数提取内核、正确性闸门全部在 PSI 侧——索引键偏差只「少收」不「错跳」）：

- **MapperNamespaceIndex**（v2）：头 16KB 提 namespace + 根元素判定，另摊平 `#mapper`/`#config` 两类文件级标记键给补全清单服务（§4.4）。消费方三个：MapperXmlLocator（跳转/日志定位）、MybatisXmlTargets.findMapperFileByNamespace（XML 属性 reference 热路径）、XmlSymbolNameIndexCache。
- **SqlMapNamespaceIndex**（v1）：`all`/`ns:`/`stmt:` 三类键，语句 id 全文扫描。消费方 IbatisXmlStatementTargets（跳转/GTD/预览目标解析），旧链「FileTypeIndex 全项目 XML + 逐个 PSI + 5s TTL 单槽 + 多工程互踢」整套状态机退役（ui/nav/IbatisXmlStatementTargets.kt:26-32 KDoc 自证）。

登记三条成本边界（都不是问题，防后续误判）：

1. **版本 bump＝升级用户一次性重索引**。MapperNamespaceIndex 1→2 触发平台对全项目 XML 重跑该索引（纯文本扫描、无 PSI 建树，demo 口径 2493 文件 / 16.6MB 的正则扫描为秒级以下量级，BGT 完成）；SqlMapNamespaceIndex v1 为新增，装载即全量建（同口径）。用户可感知的是升级后首启索引条目数增加，不构成 freeze 面。
2. **索引期全文正则**。SqlMapNamespaceIndex 对每个 XML 文件全文跑根锚正则（非 sqlMap 文件一次扫描即出空集）；MapperNamespaceIndex 的 namespace/根元素限头 16KB，唯 `#config` 分支对 `<configuration>` 根文件全文 containsMatchIn 两遍（mybatis-config 文件通常 KB 级）。量级相对平台 XML PSI 解析可忽略；若日后要抠，`#config` 判定可收进头窗（本系列不立项，登记即可）。
3. **索引代戳语义坑已文档化**。`getIndexModificationStamp` 只随索引产出变化、不随内容编辑变化（类头实测记录），消费方 XmlSymbolNameIndexCache 已按「索引代戳 ⊕ 逐文件 modificationStamp」双戳合成，边界（未保存编辑不进清单）如实登记。

### 4.2 iBatis 波次三对 provider 与导航入口（合规，静态缓存族登记）

- **快路径**：IbatisXmlGutterLineMarkerProvider（预览图标）`getLineMarkerInfo` 严格 O(1)（token 类型 + 标签名表 + 父标签名，零 resolve 零索引查询，方法头单次取 state）；IbatisJavaToXmlLineMarkerProvider 同形。
- **慢趟**：IbatisXmlToJavaLineMarkerProvider / IbatisJavaToXmlLineMarkerProvider 全走 `collectSlowLineMarkers`，锚点四道门全部语法级；「箭头是否要求调用点存在」的词索引查询（T-IbatisXmlArrowCallerGate）带**正负缓存**（命中入缓存、确认缺失收回，P2.1 教训在位），dumb 窗乐观产出不入缓存，Registry 回退通道在位。
- **导航入口**：MapperNavigationGotoDeclarationHandler / MapperNavigationGotoRelatedProvider / IbatisDaoStatementGotoDeclarationHandler / IbatisXmlStatementGotoDeclarationHandler——接口形态判定 + dumb 闸都在索引查询之前（MapperNavigationTargets.kt:38-57），非命中位置零开销，Ctrl+B/Ctrl+Click 用户动作频度。
- **预览装配链**：IbatisStatementPreview → IbatisXmlPreviewService（池线程 ReadAction 内，KDoc 明示调用方持读锁）；`parameterClass` 属性类型解析（T-IbatisParamClassQuote）走 IbatisParameterClassResolver → **IbatisTypeAliasResolver（P2，见 4.3）**。
- **静态缓存族登记**：resolvedIbatisKeys（IbatisJavaToXml:103）/ resolvedIbatisCallKeys（IbatisXmlToJava:91）/ optimisticLoggedKeys（:113）/ perfLoggedKeys（IbatisXmlStatementTargets:276）均为应用级 ConcurrentHashMap.newKeySet()，会话生命周期、无项目关闭清理、键为 `namespace|id` 不含项目身份——两个工程同 namespace 同 id 时正缓存语义会跨项目串（A 工程确认过调用点，B 工程直接信）。量级：小字符串集合，按项目语句数封顶；跨项目撞键是正确性小瑕疵非性能问题。与既有「static 容器逐个登记」口径一致，处置建议见 T-PerfSweep31 券04。

### 4.3 IbatisTypeAliasResolver：模块级 VFS 全走查（P2 本期主菜）

形态（ui/IbatisTypeAliasResolver.kt:46-77 亲读）：`fqnOf` 按模块名 `computeIfAbsent`，未命中时 `scan()` 对**模块全部内容根** `VfsUtilCore.iterateChildrenRecursively`（filter：目录或 .xml），对**每个 XML 文件** `PsiManager.findFile` 建 PSI 后筛根标签 `sqlMapConfig`、提取 `<typeAlias>`。缓存会话级（config 改动要重启会话才生效，v1 取舍自证）。

调用链与线程（亲读）：iBatis 预览点击 → `IbatisStatementPreview.previewTag` → IbatisXmlPreviewService.preview:117 → IbatisParameterClassResolver.resolve → findClass（先 FQN 直查，未命中**先查别名表再落短名索引**）→ fqnOf。IbatisStatementPreview KDoc 明示「gutter 点击在 previewAsync 的 ReadAction.compute 内」——即整模块走查跑在**池线程持读锁**内：

- **代价账**：大模块（数千 XML）首次点击 = 全模块 VFS 递归 + 逐文件 PSI 建树。PSI 建树是不可控的内存分配（且全部留在平台 PSI 缓存里），走查过程不可取消、无预算；持读锁期间平台写动作排队——与 T-StartupReadLockFreeze 的「BGT 持读 + EDT 写」互等形态同类（那次是两根现场栈实锤，本条为代码级推算，未取现场栈，证据边界如实注明）。
- **触发面**：每模块每会话一次（缓存后零成本）；只有 iBatis 预览链会走到；`findClass` 把别名表查询放在短名索引**之前**（注释自证「大工程里短名索引本身就可能慢」——动机是省查询，代价是把全模块扫描前置）。
- **修法方向**（详见 T-PerfSweep31 券01）：首选照 F1''' 同款思路把 `sqlMapConfig` 的 `<typeAlias>` 摊平进标量索引（新增第三索引或并入 SqlMapNamespaceIndex 键族），运行时零扫描；次选走查改 `ReadAction.nonBlocking + inSmartMode + expireWith` 并加预算/进度；兜底把扫描范围收窄到惯例配置目录（src/main/resources）。禁在 EDT 路径上保留现在的同步 computeIfAbsent。

### 4.4 预热三链与统一延迟调度（合规）

- **GutterWarmScheduler**（T-GutterFirstOpenDelay F2）：三条预热链（MBG Example 预取 / 补全上下文 / 装配预热）的踢出时刻统一后移到「工程 smart 后 N ms」（默认 5000，Registry 可调 0=旧行为）。每文件一次调度去重、到点复查（未关/已 smart/文件在）、一次性 `schedule`（非周期）、失败退化立即踢；派发体整体包 read-action（T-GutterWarmReadAction：AppScheduledExecutorService 池线程不持读动作，真机 3 条 SEVERE 实证后修）。
