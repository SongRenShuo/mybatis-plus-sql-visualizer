## 一、总体结论

「默认配置对 IDEA 无体感影响、零常驻线程/定时器/监听」的主体结论第三次维持，且本系列首次实现高级别发现清零：第五期唯一高风险（Mapper 双向跳转 daemon 热路径）的修复逐行核实在位、并被门控/memo/组闸三层测试钉死（§三）；第五期登记的 3 处技术性无上限缓存全部消解（§五）。对 53 笔增量的新增面逐项走查：新增线程 0、新增监听注册 0、新增 Timer 0、新增常驻 0，新增缓存 3 处全部有界（locate memo、方言证据双槽、竞品探测单布尔）。唯一值得修的新发现是一个 P3 渲染路径项（R29-1，§4.2）：脱敏开启＋多行显示模式下，条目级片段缓存命中路径仍每帧重算展示 SQL 取源（含全量词法打码）后丢弃，修法一行级，量级与五期实测单格预算同阶，不构成体感风险。

回答本期问题「当前插件是否会带来 IDEA 性能问题」：默认配置下不会。本轮重点核过的四个新机制——竞品探测（懒缓存每会话一次）、让位门（O(1) 布尔且三道闸全前置）、方言配置证据链（EDT 只读缓存＋30s TTL＋文件数上限三重限频）、栈摘要框架帧扩展（复用既有前缀表、JDBC 执行线程内、压测 +1µs/SQL）——无一触碰 EDT 慢操作与索引红线；MCP 过滤器注册从「按 262 签名分发」改为「契约形态判定」后仍是启动期一次性、失败有界不自旋。

## 四、新增面详评

### 4.1 T-MapperNavCoexistYield 让位门（形态正确，主控亲验）

- 探测走全反射（PluginManagerCore.getPlugins → PluginDescriptor.getPluginId → getIdString → isEnabled，MyBatisCompetitorGate.kt:98-123），无平台 API 静态引用（KDoc :19-23 说明 243/262 形态漂移规避）；探测结论 `@Volatile cachedActive` 懒缓存＋双检锁（:43-44/:62-72），命中路径一次 volatile 读；反射失败降级「不在位」且 WARN 只打一次（:46-48/:125-129）。探测成本每会话一次 O(已装插件数)，非每 marker 趟。
- 门位置正确：两 Provider 在批级方法头单次取 state，判定链为「总闸 → 组闸 → 让位门 → 锚点/重逻辑」（MapperNavigationLineMarkerProviders.kt:28-42/:81-93），让位门是 O(1) 布尔短路（shouldYield 纯函数，MyBatisCompetitorGate.kt:78-79），设置项 mapperNavYieldToCodeHelper（PluginSettings.kt:123，默认 true）每趟读一次。让位门排在锚点解析（XmlToken/语句标签判定）之前，竞品在位时连 O(1) 锚点税都不付。
- 已知取舍（KDoc 自述）：「对方在位 ≠ 对方真画了」的区间级推断只适用于注入面，gutter 图标按「在位即让位」判据取插件启停；插件启停需重启 IDE，故缓存不做时效失效——运行期动态启停（若平台支持）下缓存偏保守，性能上无害。
- 折叠名单增量（IDE 侧）：StackDigestFrames 补驱动族/ibatis 族折叠（:146-153），纯展示面字符串前缀匹配。

### 4.2 T-LogListAnchor 锚定与换行取源（含本轮唯一 P3）

- 视口锚定：AdjustmentListener 挂竖向滚动条（SqlLogPanel.kt:1656-1669），每事件成本＝valueIsAdjusting 早退＋isUserScrollToBottom 纯函数 O(1)（TailFollowState.kt:39 起，程序性滚动/位置变小/非贴底三判据零分配）；程序性滚动用深度计数器包住（SqlLogPanel.kt:312/:318-322），锚点捕获/复原只在模型变更拍发生（暂停态每条新 SQL 至多一次），复原线性扫模型 O(n≤缓冲 200)。挂靠为 scrollBar lambda，生命周期随 UI 宿主回收，无泄漏路径（未走 Disposable 显式摘除，口径备注）。
- 换行取源：KEYWORD_WRAP 分支改取完整 SQL＋4096 字符预算（T-LogListAnchor 券01 定案），词法分词有条目级缓存（键=模式+脱敏态，LogSqlModels.kt:239-248），命中时绘制期只做 scheme 投影——五期实测 0.08ms/格的分片缓存结构未破坏。
- **R29-1（P3，本轮唯一新发现，主控亲验）**：RailCellRendererBase.kt:292-307 的 `sqlLineFragmentsFor` 在缓存检查之前无条件执行 `withTerminator(displaySqlForList(entry, mode, maskOn))`（:295）。多行模式缓存命中时该值不被使用，但脱敏开启时 displaySqlForList 内部走 `DisplayMasker.maskDisplay(entry.restoredSql, masked)`（SqlListFragmentRenderer.kt:63）——全量词法级打码 transform，O(SQL 长)。即脱敏开＋KEYWORD_WRAP/FORMATTED 模式下，每次重绘（滚动/选中/repaint）× 每个可见格（约 10~30）付一次全量打码后丢弃。量级推算与五期单格预算（0.08ms/格）同阶或略高，只在「用户显式开脱敏＋多行模式」组合出现；脱敏关时 maskDisplay 原样返回成本趋零。SINGLE_LINE 模式不受影响（直渲染本就要用该值）。修法一行级：把取源收进 SINGLE_LINE 分支与多行缓存未命中分支（缓存键已含 maskOn，脱敏切换天然重算）。

### 4.3 T-DialectInferFix/Smart 方言证据链（EDT 只读缓存，三重限频）

- 线程面：EDT 上只读缓存绝不触发扫描（Dialect.kt:1103 对 isDispatchThread 走 cachedOrNull，KDoc 明示平台慢操作断言规避）；后台重算入口走 executeOnPooledThread。
- 触发频率：仅当决策 dialectName 为 null 且非 CONFLICT 时才问证据；配置/驱动证据 TTL 30s（ProjectDialectEvidence.kt:139，:192 判过期），项目槽 WeakReference 单槽＋模块槽 WeakHashMap。
- 扫描面：FilenameIndex 按名（3 名）＋按扩展（yml/yaml/properties 3 扩展）索引查询而非 VFS 全项目枚举，上限 MAX_CONFIG_FILES=24/MAX_BUILD_FILES=12/单文件 256KB（ProjectDialectEvidence.kt:50-52）；测试资源用 fileIndex.isInTestSourceContent O(1) 排除；激活 profile 判定纯函数。
- R29-2（登记不动）：按扩展名枚举是「先取全项目匹配再过滤截前 24」，数千 yml/properties 的大项目索引查询本身 O(匹配文件数)，另加逐文件 findModuleForFile；但被「仅决策为空才问＋30s TTL＋非 EDT」三重限频，且收窄枚举反而伤首次推断精度，判定可接受。

### 4.4 T-Mcp261FilterContract（启动一次性、失败有界）
