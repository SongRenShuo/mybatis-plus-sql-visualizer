## 一、总体结论

主体结论维持：默认配置下对 IDEA 无体感影响，零常驻线程、零常驻定时器、零常驻监听。比这更重要的变化是，9 月版点名的全部 P1/P2 风险在当前 HEAD 已逐一销账（逐项证据见 §2），第二十六轮挂账的 16 条 F 系发现也随 T-PerfSweep26 批次销掉 10 条，余 7 条均为微项维持。本轮三路走查未发现新的高级或中级风险，这是本系列开始以来首次连续两轮零中高级发现。

新增面唯一值得单独说明的是 T-LogListHeader 头部行：`clipFragmentsByPriority` 在每次可见格重绘时重跑片段构建与优先级裁剪，没有条目级缓存。它是当前列表渲染链上唯一的每帧重复计算，但不含正则、测量器有 FontMetrics 缓存，且有单格 2ms 的压测预算钉住，定级为低而非缺陷。

风险分级一览：

| 级别 | 组件 | 现象 | 触发条件 |
|------|------|------|----------|
| 低 | 头部行渲染 | headerFragments + clipFragmentsByPriority 每次重绘逐格重算，无条目级缓存 | 两万条流式灌入期可见区反复 repaint / 滚动 |
| 低 | EntityResolver / JpaEntityResolver | 静态 ConcurrentHashMap 条目数无上限、无淘汰，仅 clearCache 手动清空 | 长会话跨多项目大量实体且配置签名多次变化 |
| 低 | 控制台桥逐行 | 每行 1 次反射 invoke 取修改戳 + synchronized(context) | 数千行/秒的高频控制台输出 |
| 微 | HqlGutterLineMarkerProvider | 开关判断在 hasStringFirstArgument 之后，关闭总闸仍付一次 resolve | 文件含 createQuery(变量) 且用户关闭 gutter |
| 微 | StringSqlMethodGutter | 每方法名叶子全方法体结构扫描，无文件级门控，仅 200K 字符护栏 | daemon 每趟 × 大文件多方法 |
| 微 | SqlCompletionContributor | 每次补全约 10 条急切插值 LOG.debug + 全文 detectClause | autopopup 下每键 |
| 微 | 第二十六轮遗留 F100/F103/F106~F110 | 全局文档监听常驻、Kotlin 注册零产出、agent 暂停期 Gson 全解析等 | 各条自明 |
| 无 | 启动/常驻/内存主线 | 默认零常驻；PSI 缓存有界；写盘走专用线程批量 flush | — |

## 四、当前遗留风险

头部行渲染是本轮唯一的新增成本面。bindHeaderLine 在 getListCellRendererComponent 内重跑 headerFragments（SqlEntryPresentation.kt:29-62，buildList 分配加序号库角标等小拼接）与 dropByPriority 优先级裁剪（:341-362），即每次可见格重绘都重算，而同文件的多行 SQL 语义片段已有条目级缓存先例（RailCellRendererBase.kt:284-298）。SINGLE_LINE 模式 fixedCellHeight 固定（SqlLogPanel.kt:1583-1597），多行模式逐条测量但有片段缓存兜底。压测读数见 §7，单格 2ms 与组件树稳定判据均过，风险定级低的依据是预算钉住而非不存在。

EntityResolver 与 JpaEntityResolver 是当前内存面仅剩的两处无上限静态缓存：键已是 fileUrl 字符串不持 PsiFile（EntityResolver.kt:543-556、JpaEntityResolver.kt:711-729），泄漏面从「死 PSI 对象」缩到「字符串到解析结果的映射」，但配置签名变化会让旧键永不命中也永不淘汰，长会话缓慢累积。同族的 HbmXmlEntityResolver 负缓存 4096 上限加项目级 userData 戳换代是现成的收窄范式。

其余微项：HqlGutter 的 hasStringFirstArgument（含 resolve 分支）在开关判断之前（HqlGutterLineMarkerProvider.kt:48 先于 :51-53，:86）；StringSqlMethodGutter 每方法名叶子全方法体扫描无文件级门控（:92-105，200K 护栏 :123）；补全热路径约 10 条急切插值 LOG.debug（SqlCompletionContributor.kt:80-88,:101）——debug 级别默认不输出，但字符串拼接本身照付；桥逐行 docStampReader 反射 invoke 每行一次，Method 查找已缓存（F57），invoke 本身是 decide 语义必需，属设计内成本；McpToolsetSupport.AUDIT_CTX 工具协程被取消且未走记账路径时可能残留 token 键（:233），键为 Long 量级轻，未见 finally 兜底。

## 五、内存驻留

有界缓存运转正常：WrapperCache LRU 512；metaCache 弱键 WeakHashMap 随数据源回收（DatabaseSchemaResolver.kt:294）；cachedOwnerIndexes 只读该缓存做表归属路由不新增驻留；dedupeCounts 4096 FIFO；LogThreadRouter 64 桶空闲淘汰；RollbackSnapshotStore LRU 100；SqlPerfAnalyzer LRU 128；LogTimeCorrelator 512 键加 30s 窗；ParamHistoryCache LRU 50 加存储代际；JoinFkRegistry 图关闭换图时 clear；HbmXmlEntityResolver 负缓存 4096 加 PSI 戳换代。

生命周期面干净：全部 messageBus.connect 挂 Disposable，唯一裸连 PluginSettingsPanel.kt:699 是有意为之（Configurable 不在 Disposer 树，挂树反报泄漏），由 disposeResources 显式断开；PreviewSchemaHighlighter Session 入 Disposer 树的修复保持完好（:87-113）；全项目零 EditorMouseListener/CaretListener/PsiTreeChangeListener 注册（两处 KDoc 禁引注除外）。

唯一例外即 §4 所述 EntityResolver/JpaEntityResolver 两处无上限，键轻、增长慢、有手动清空入口，定级低。

## 六、启动与常驻足迹

启动五点全部秒返或默认关：StartupUpdateCheck 网络在 Task.Backgroundable（StartupUpdateCheck.kt:43-59）且开关默认关；LogStartupCapture 开关默认关，开启时池线程 3 次重试封顶；OnboardingAnchorTip 默认开但一次性，弹过即断开订阅；McpGateFilterRegistrar 与 AcpTransportRegistrar 均为探测式条件加载，第二项目起零成本。lineMarkerProvider 共 15 处（主文件 14 加 kotlin-optional 1）全部 O(1) 语法判定加开关前置；无 Annotator、无 stub 或索引注册，不参与索引构建；externalAnnotator 限 SQL 语言但首行文件名紧致判据秒拒用户自己的 .sql。

默认配置零常驻线程。开启捕捉后的常驻开销收敛为：桥轮询 EDT Timer 一个（500ms 起步指数退避封顶 2s，检测到主控制台切 2s 常规，与常规 poll Timer 互斥）、面板诊断 Timer 一个（2s 只读内存态，捕捉期常跑）、每控制台两个 Filter（EP 加桥代理，EP 生效后桥解析短路）、每 agent 会话一条读线程加 5s 巡检。自建 daemon 调度线程 5 处（exec 文档自动保存、日志历史写盘、agent 执行器与监控、反馈调度、agent 事件发送）全部有 shutdown 或 Disposer 停机路径，无 java.util.Timer，Swing Timer 清单全部单发或超时自停。agent premain 三项收口保持：全域 catch(Throwable) 双入口（AgentMain.java:73-81）、30s 窗未认领降级（AgentManager.kt:120,:688-700）、暂停恢复 join 40s 预算加代际让位（:100,:1525,:1585-1589）。MCP 无自建线程池，工具跑平台协程，阻塞调用有 withDbBlockingContext 兜底（McpDbExecutor.kt:62-72）。

## 七、压测与量化证据

本仓库已把性能判据固化进测试，全部为两万条规模加双档判据（绝对预算拦数量级退化加结构性判据验组件树与线性度），是本次「无体感影响」结论最硬的证据：

- LogPipelinePerfTest（LARGE=20000）：搜索 80ms、正则 120ms、类型/慢查询筛选 20ms、屏蔽 30ms、七种排序各有预算、完整管线 200ms、空态 120ms；结构性判据为空查询透传小于 0.05ms、搜索成本随条数线性、排序近似线性。
- LogEntryRailPerfTest：单格渲染 2.0ms 预算、三种显示模式均过预算、200 次渲染组件树规模稳定、两万条数据下单格成本与总条数无关、滚动 30 帧 × 20 格预算、maxDurationOf 零临时分配。
- SqlLogConsoleBridgePerfTest：退避曲线、descriptor 缓存短路、反射负缓存与容量失效、token 下传等结构性断言。
- SortModeLabelBenchmarkTest：sortModeLabelKey 由每次新建 7 个 SortOption 加 7 次 bundle 取值改为纯 when 查表，20 万次基准 191µs 降到 29µs（6.6x），另有「不得再引用 sortOptions」的结构反向探针（739bfd8a）。

维护性议题非性能缺陷，登记备查：SqlLogPanel 2264 行、SqlPreviewPanelExecution 2166 行、SqlPreviewService 2072 行，巨文件预算已再失守。

## 八、优化建议（按收益排序）

1. 头部行条目级缓存：headerFragments 的输入是条目不可变字段，可按条目身份或条目代缓存，对照同文件多行片段缓存先例（RailCellRendererBase.kt:284-298），改动局部；两万条流式灌入与滚动场景直接受益，并可把 LogEntryRailPerfTest 单格预算同步收紧作验收。
2. EntityResolver/JpaEntityResolver 加上限：套用 HbmXml 负缓存 4096 加戳换代范式，或键改弱引用，消除仅剩的两处无上限静态缓存。
3. 补全热路径日志降噪：10 条急切插值 LOG.debug 改条件输出或删除；顺带 HqlGutter 开关前置一行改动。
4. AUDIT_CTX 取消路径 finally 兜底：一行级，与 F100 的非 exec 宿主早退前移可合并为一批微项收口。
5. 其余 F 系微项（F103/F106~F110）维持登记，随下次性能轮自然消化，不建议单独立项。

## 九、验证方法

延续既有方法并补充本版针对性场景：沙盒 attach JFR 或 VisualVM 观察 EDT 事件队列；IDEA 自带 Performance Watcher（idea.log 的 UI freeze 与 Slow operations 报告）直接量化。本版新增场景：两万条流式灌入期快速滚动日志列表，对比头部行条目级缓存改造前后单格耗时与 EDT 占用（LogEntryRailPerfTest 预算同步收紧）；长会话反复切换配置签名后 dump EntityResolver 静态缓存条目数验证上限改造。既有验收红线（两百条 SQL 流式灌入不掉帧、50KB 动态 SQL 逐键小于 50ms、IDE Freezes 报告无本插件新增记录）继续作为例行回归项。
