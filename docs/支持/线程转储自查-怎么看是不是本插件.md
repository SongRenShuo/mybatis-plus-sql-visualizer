# 线程转储自查：怎么看「卡住」是不是本插件

> 用途：用户报「IDE 卡死/未响应/点了没反应」并附一份 thread dump 时，按下面三步在两分钟内判定我方是否有责。
> 背景结论（2026-11-19 用户报障实证）：绝大多数这类冻结是**别人的长读锁**把 EDT 写动作挡住，本插件通常只是在场。

## 一 三步判定

### 第 1 步：我方线程在干什么

```bash
grep -n 'cn.song.mybatisplus.visualizer' <dump>
```

我方线程只有四类，且**正常情况下都应该停在 socket 上**：

| 线程 | 正常形态 |
|---|---|
| `mps-agent-premain-*` | `ServerSocket.accept`（等应用连过来） |
| `mps-agent-session-*` | `DataInputStream.readInt`（等 agent 发数据） |
| `mps-agent-manager` / `mps-agent-monitor` | condition wait |

若它们停在这里，说明我方**没在跑活、也没持锁**，可以继续第 2 步。
若出现我方的计算栈（索引扫描、PSI 解析、`ReadAction`），才需要往「我方长读锁」方向查。

### 第 2 步：卡住的那个线程里有我方帧吗

先找 `"AWT-EventQueue-0"` 段（界面线程），再找所有 `"JobScheduler FJ pool` 段：

```bash
awk '/^"(AWT-EventQueue-0|JobScheduler)/{p=1} /^$/{p=0} p' <dump> | grep -n 'cn.song.mybatisplus.visualizer'
```

- 一条都没有 → 本插件不在卡死链上，转第 3 步找真凶。
- 有 → 记下函数名与行号，按行号回仓核对（那是真问题，要立项）。

### 第 3 步：谁在拖时间

界面上所有卡顿最终都是「某个线程持着锁不放」。看那段栈的**栈顶包名**：

| 栈顶形态 | 结论 |
|---|---|
| `prepareWriteFromWriteIntentBlocking` / `RunSuspend.await` 且调用方是 `SwingUtilities.invokeAndWait` | 有线程在等 EDT，而 EDT 在等读锁 → 继续往下看谁在读 |
| `com.jetbrains.clones.` + `InputVariables` / `bulkProcessElementsWithWord` | IDE 自带「重复代码片段」检查在做全工程词条搜索（最常见，本仓 2026-11-19 报障即此类） |
| `com.intellij.util.indexing.` / `FileBasedIndexImpl` | 索引重建或索引查询 |
| 某第三方插件包名 | 记下包名，转给对方 |

## 二 我方自己的纪律（为什么通常查不到我方）

- 后台线程等 EDT 一律有界：`util.EdtDispatch.invokeLaterAndWaitBounded`，超时记一条 WARN 就继续，不把第三方的长读锁时长传导成功能不可用。
- 写文档前先比内容，一致就不开写命令（不开写命令就不必抢写锁）。
- 形态由 `convention/EdtBoundedWaitGuardTest` 守卫：`ui/execute/log/mcp/psi` 包内不得出现裸 `invokeAndWait`。

## 三 回复用户时的取证口径

判定为「与我方无关」时，回执里给三条可核对的事实，别只说结论：

1. 我方线程清单与它们停在哪（第 1 步输出）；
2. 冻结线程栈里没有我方帧（第 2 步输出为空）；
3. 真正的持锁方及其栈顶包名（第 3 步），并给出可操作的规避开关（例如关掉「重复代码片段」检查、收窄 Inspections Scope、排除 `node_modules`/构建产物目录）。

要求用户下次复现时补三样：新 dump、复现前的操作序列、上述开关状态。
