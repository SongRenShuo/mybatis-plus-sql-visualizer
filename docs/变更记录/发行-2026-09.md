## [2026.9.23] - 2026-09-23

> 正式版，承载 `v2026.9.18-beta.1` ~ `beta.4` 内测系列全部内容及其后至发行日的增量；`2026.9.18` 编号未随任何发行使用，按「版本号即发行当日日期」规则跳过。

### Added

- **可回放 INSERT 的 identity 包装（T-IdentityInsertWrap，O-52）**：回滚链与 CRUD 链此前生成 INSERT 时**零方言、零自增列感知**——把带 identity 列的整行 INSERT 直接提交会报错（SQL Server 须 `SET IDENTITY_INSERT <表> ON`）。现 `Dialect.renderInsertWrapper(tableName, sql, caseSource)` 默认返回 null（不包装、逐字节不变），`SqlServerDialect` 覆写为 `SET IDENTITY_INSERT … ON/OFF` 包裹整段；判定落点定在 `BatchModel.renderSql`（`BatchColumn` 增 `autoGenerated`，生成器只负责接线），回滚快照扩 `dialect` + `identityColumns` 两个可选字段（**字段缺失 = 不包装**，向后兼容，老快照照常生成）。用例 +13（CRUD 4 / 回滚 6 / 往返 1 / 面板 2）；SQL Server 端到端**环境受限未验证**（本机在册数据源无 `sqlserver` 类型）
- **列名数据源校正开关（T-DbColumnCalibration，O-58）**：实体字段名与数据库真实列名不一致时（库 `order_id` / 实体 `orderID` 这类非标准命名），预览 SQL 此前按命名策略盲猜列名、猜错即产出不可执行的 SQL。现按「精确命中 → 归一化唯一命中 → 否则原样保留」的保守口径，用**数据源的真实列集合**校正实体列名，覆盖列清单、逻辑删除列/乐观锁版本列/复合主键列，以及 JOIN ON 用的**外键列名**；全局与项目级各有开关（项目级 null = 跟随全局），默认开启。**无可用数据源（社区版 / 未配置 / 未连接 / 表看不见）时逐字段等价于改造前**；热路径只读缓存、未命中仅投递后台预热，不新增任何 schema 遍历。附带修掉一处既有缺口：`@Column` 写在 getter 上时此前完全读不到、静默回落盲猜——该离线读取不查数据源、不受开关约束
- **foreach 集合快捷别名（T-ForeachCollectionAlias，N-32）**：mapper 方法只收一个集合参数、又没写 `@Param` 时，`<foreach collection="list">` / `"collection"` / `"array"` 这类快捷名此前解析不到集合、该段静默少展开。现按 MyBatis 自身的参数命名语义补齐别名——`List` → `collection` + `list`，`Set`/`Queue` 等非 List 集合 → 仅 `collection`，数组 → 仅 `array`（键集以真引擎实测钉住，不靠推断）；补全面板的 `collection` 属性候选一并列出这三个快捷名，`test` 属性候选不受影响（别名不进 test 候选，`test` 写法与既有语义零变化）；三条别名场景进真引擎对照集（一致面 25 → 28 条）
- **空白符可视化开关（T-PreviewWhitespaceToggle，O-44a）**：设置页「界面与操作」新增「显示空白符」开关——开启后插件自建的全部 9 处编辑器（预览面板 SQL 区、日志转 SQL 面板输入区与结果区、日志点击预览、SQL 输入编辑器、回滚 SQL 弹窗、JSON 参数导入、SQL→Java 结果区、Java 只读预览）用 `·`/`→`/`↵` 标出空格、Tab 与行尾，排查动态拼接 SQL 里的多余空格/Tab 时一眼可见。默认关＝**不设置**该属性（沿用 IDE 全局的「显示空白符」偏好，不改动用户设置），开关只作用于插件自己的编辑器；纯显示层，SQL 文本与渲染结果逐字节不变。内嵌控制台是平台 Database 组件，不受本开关影响（已知边界）
- **预览 INSERT 语句目标列 inlay 提示（T-InsertColumnInlay，O-44b）**：多列动态 INSERT 的「列-值错位」一眼可见——预览面板的 INSERT 语句在每个 VALUES 表达式 / SELECT 投影旁标出目标列名。投影已自带同名列别名（显式或隐式）时丢弃该条提示不重复，点名不算别名；静态不可判（无列清单、列清单非纯列名、元组元素数与列数不等、投影数不等、星号投影）一律不提示。只挂插件自己的预览编辑器（预览文件名与语句类型载体双锚点合取），用户自己的 `.sql` 文件零提示；预览降级到裸文档时不渲染
- **错误上报分级脱敏（T-ErrorReportRedact）**：默认只预填异常类名 + 栈帧摘要 + cause 链 + 指纹，异常消息全文与完整堆栈降为**可勾选附加**（默认不勾；勾选后与改前逐字节一致）
- **参数契约补缺（T-ParamContract2）**：`BigInteger` 归数值档、`UUID` 归文本档（带引号）；含 UNKNOWN 类型参数时在**执行/EXPLAIN 前提示一次**（预览放行不阻断）
- **DELIMITER 感知（T-DelimiterAware）**：`SqlStatementSplitter` 支持 `DELIMITER $$` 等自定义界符——指令行整行丢弃、界符生效期内顶层 `;` 不切分（此前 `DELIMITER $$` 脚本被切成 4 段且残留 `$$`）
- **XML 内联 DTD 膨胀防护（T-XmlDtdHardening）**：新增实体声明数 / 引用路径深度 / 单实体展开字符数三道闸门与特征降级告警；官方 DTD 与合法内部实体照常放行
- **方言智能推断并入主线（T-DialectAutoInfer 合流）**：按「智能推断」模式自动判定渲染方言——优先级 agent 连接 URL > IDE 数据源 URL > 回退，设置页全局与项目级各加「智能推断」哨兵项与推断结果状态行（含依据说明）；老配置缺省即进入推断模式（升级语义变化已在 CHANGELOG 明示）
- **项目级设置页字段进入设置搜索索引**：搜「表前缀」等关键词现在同时命中全局页与项目页条目（此前只命中全局）
- **项目级设置页新增「重置为跟随全局」（T-ProjectSettingsScope P2）**：9 项可覆盖字段一键归零/归 null（方言模式哨兵项一并跟随全局），「使用项目设置」总开关保持不动。此前关掉总开关并不清值，残值只存在于 `.idea/mp-sql-visualizer-project.xml` 里、界面上无从清除
- **设置搜索收录项目级设置页 10 项（T-ProjectSettingsScope P3）**：搜「表前缀」这类关键词时，同一关键词下同时列出全局页与项目页两个作用域的条目、次行标明所属页面。开工前的对照实验确认项目上下文的设置树里能找到项目级 configurable（`ConfigurableVisitor.findByType` 命中；`project=null` 的 Welcome 屏设置不命中——那里本就没有项目页）
- **项目级设置页（T-SettingsTruth P4）**：`plugin.xml` 注册 `projectConfigurable`（tools 顶层防套娃，双语 displayName「SQL Visualizer（当前项目）」）；面板扩容为 10 控件（增强捕获开关 + 方言 + 3 项 tri-state 勾选 + 逻辑删除值 + 表前缀/后缀 + 推断策略下拉 + 忽略字段，apply/isModified 逐项比对 + trim）；`ProjectPluginSettings` 7 个零调用 `effective*` 转正，预览服务全部参数替换/逻辑删除/表配置直读点改走 `effective*`，`EntityResolver` / `JpaEntityResolver` 表配置读取经 `effectiveTableSetting` 项目级覆盖（无项目上下文或异常时降级回退全局），缓存签名走项目维
- **SQL 历史全量化与保留上限（T-SqlHistoryFull / T-HistoryFileRetention）**：历史条目全量落盘（不再达上限后丢弃后续条目）并消除历史打开卡顿；新增历史文件保留上限配置项，按插件命名模板文件族自动裁剪防磁盘膨胀（60 秒节流），自定义目录下用户自有的 .sql 文件永不计数、永不删除
- **汇聚入口跳源码上溯（T-SourceJumpFunnel）**：agent `StackLocator` 判定收敛（候选增厚四列 8 条 / 缓存仅 L1 命中写入 / 上顶路径收敛 / 动态前缀热下发）+ IDE 统一跳转解析器 `EntryJumpResolver`（实时/历史两面板共用，历史面板补候选回退）+ cands/sd 双端协议列尾追加（新旧双向兼容）+ 栈快照详情展示 + 设置页帧过滤前缀
- **增强捕获启动即捕获（premain 通道，T-M56Phase2-Premain）**：此前增强捕获靠 attach 热挂载——用户点 Run 后要等进程出现、再静默 3 秒才挂载，应用启动阶段（框架初始化、数据源探活、Flyway/Liquibase 迁移）发出的 SQL 全落在挂载完成之前，只能靠控制台桥补；JDK 21+ 下动态挂载还会在目标进程控制台打 JEP 451 告警。现在开启增强捕获并同意注入后，插件在 Java 运行配置启动前把 `-javaagent` 写进 VM 参数，agent 在目标 JVM 的 `premain` 阶段就完成 SQL 织入：启动期 SQL 直接进增强通道，且启动加载是 JVM 认定的预期路径，不再产生动态挂载告警。未开启增强捕获、或尚未同意注入时零注入（首次运行的注入确认弹窗语义不变）；jar 落盘/端口协商/注入任一步失败都只回落既有 attach 与桥捕获，绝不影响运行配置本身。attach 链原样保留
- **跨命名空间 include 解析（T-IncludeCrossNs，O-30 / zMyBatis 精华 Z-8）**：mapper 里 `refid="其它命名空间.片段id"` 这种全限定 include 此前只报「not found」并把 include 摘掉，预览少一段 SQL。现在预览按最后一个点切出目标 namespace 与片段 id，在项目内找根 `<mapper namespace>` 匹配的文件取其 `<sql id>` 片段内容合并展开——跨文件片段同样走 property 静态替换与环检测，片段里的 `<if>`/`<foreach>` 等动态标签照常渲染，`${}` 动态 refid 也支持。失败仍走原有降级链（预览不中断），警示改为给出具体原因：目标 namespace 无 mapper 文件 / 该 namespace 下无此片段 / 同名片段在多个文件中重复声明（歧义，MyBatis 运行时为后注册覆盖，差异如实标注）。裸 id 仍只在本文件查（与 MyBatis 运行时一致）；无 IDE 项目上下文的纯文本链（含 MCP 片段直渲、注解 `<script>`）行为逐字节不变
- **XML 动态条件支持面预检标注（T-ExprAstPrecheck）**：XML 预览面板的动态条件行此前对超出受限 OGNL 支持面的 test 表达式毫无表示——用户看到的是「条件展开了」，看不出这个条件其实没算出来（三元、静态方法、`new` 这类写法解析即失败；未知方法链、静态字段引用这类写法求值时静默返回 null）。现在条件行会带一条淡色标注：语法超出受限子集（三元运算、赋值、lambda、静态方法、`new` 等）标「不支持的表达式形态」，语法可解析但含运行期降级形态标「含运行期降级调用」，悬停给出具体理由（解析器原文 / 方法名 / `@类@字段`）。判定在 xml 层纯 AST 遍历完成，零 PSI、零新语义——支持面清单直接从求值器既有事实投影（方法白名单的载体实现表与白名单共用一份，不会漂移），故 `list.size()`、`list.isEmpty()`、`_parameter.getTitle()` 这类常见写法不标注，`map.length()`（`length` 只对字符串有实现）、`list.remove(0)`、`@常量类@字段` 这类会标注。标注只是提示，条件展开行为与勾选开关语义零变化
- **预览 `${}` 注入确认闸门（T-InjectionGate）**：含 `${}` 直替的 XML/注解预览在「执行 SQL」与「EXPLAIN」前弹确认框（说明 raw 段当前以模拟值填充、执行前请确认值真实性），选否即中止（不登记回滚快照、不执行），确认一次后同一面板不再重复弹——不新增弹窗形态，只在既有执行流程加一道门。判定信号取自解析期 `${` token 事实而非最终文本 regex（`${}` 成功替换为模拟值后产物文本里已无痕迹，regex 会漏掉全部成功场景）；纯 `#{}` 预览与 Wrapper/JPA/日志还原链零影响（该链本无 `${}` 概念），无 `${}` 语句的执行路径逐字节不变。复制可执行 SQL 不做弹窗（复制不是执行），改在产物头部加一行 `-- contains ${} raw segments (mock values)` 注释让风险随产物走
- **参数面板类型契约升级（T-ParamTypeContract，N-26 / Z-3+Z-4+Z-13）**：XML mapper 参数从「猜」升级为「按签名」——`XmlParamTypeResolver` 输出由布尔引号映射扩为类型类别契约（`ParamKind`：TEXT/NUMBER/TEMPORAL/COLLECTION/OBJECT/UNKNOWN + nullable 标记，枚举落 xml 层保持该类零 PSI 依赖；布尔引号通道降级为派生视图，`quoteFor` 行为逐值不变）。参数输入行按类别给占位提示（数字 `42` / 日期 `2026-01-01 12:00:00` / 集合 `[1, 2, 3]` / 对象 `{"id": 1}`；无类型信息走参数命名启发式——`s` 结尾或含 ids·list，排除 status/address 等单数词），NUMBER 输入非数字、TEMPORAL 非可解析日期时行尾给淡色警示标（提示不是闸门，值照原样进 SQL，渲染链零改动）。mock 占位值按类别分派（NUMBER→`1`、TEMPORAL→`'2026-01-01 00:00:00'`、COLLECTION→可迭代 mock、OBJECT→属性对象；无类型信息维持 `"1"`）。设置页「SQL 预览」组新增「空参数填充策略」单选（NULL 字面量 / 空字符串，默认 NULL）——带签名信息的参数行留空时按策略出 `NULL`/`''`，无类型信息路径保留 `?` 占位（行为与升级前一致）。映射不到一律 UNKNOWN（宁缺勿错）；`byte[]` 按 BLOB 落 UNKNOWN，日期无特判的引号行为显式定案（TEMPORAL 走引号档）
- **平台 MCP Server 十个确定性只读工具 + 设置页门控（MCP 能力线，T-McpToolset / T-McpToolset2）**：面向外部 agent（Claude Code / Cursor / AI Assistant / Junie 经平台 MCP Server）暴露十工具——`sqlv_render_sql`（文件+行号或 mapper XML 片段 → 渲染链真实可执行 SQL，参数回填+降级说明）、`sqlv_schema_context`（表名白名单 → 数据源真实表列注释紧凑上下文）、`sqlv_explain`（单条 SELECT → 七方言 EXPLAIN 计划文本，headless 同步建连；可选 `maxRows` 默认 200、硬上限 1000，越界静默钳制）、`sqlv_render_logs`（MyBatis / Hibernate / JdbcTemplate 日志还原可执行 SQL）、`sqlv_check_sql`（静态写风险与类型核查）、`sqlv_rollback_plan`（回滚预案，只产出不执行）、`sqlv_perf_advice`（性能建议，超限按严重级别裁剪保高危）、`sqlv_crud_sql`（实体类生成 CRUD 四件套）、`sqlv_reverse_sql`（SQL 转 MyBatis-Plus 代码）、`sqlv_mapper_check`（mapper 契约核查 + 渲染产物分析）。全部只读三 hint 显式声明、SELECT 白名单 fail closed（JSqlParser 结构判定+关键字粗扫双保险）、零弹窗（拒绝走 `McpExpectedError`），每次调用 `[MCP-AUDIT]` 审计；执行结果落进既有 SQL 历史（带 `[MCP]` 徽标，重启后仍在），审计行记真实入参摘要。设置页「MCP 工具」子页：总开关 + 十工具逐项启用/禁用 + 全部切换按钮，下一次工具列表/调用即时生效。MCP 能力需 IDEA 2025.2+（内置 MCP Server）；未装 MCP Server 插件的环境整份 optional 文件不加载零影响
- **执行确认升级为无界写发现清单（T-UnboundedWriteGuard，O-9）**：执行 UPDATE/DELETE 前的二次确认对话框在静态检查命中无界写特征时列出发现（无 WHERE 全表 / 恒真条件如 `1=1` / OR 分支恒真 / `LIKE '%'` 纯通配 / WHERE 仅常量 / 子查询提示 / 无法解析请人工确认）——同一对话框形态零新弹窗，无发现时文案逐字节不变（高频确认不添乱）；规则集对齐 DBX `sql_risk.rs`，JSqlParser AST 权威、解析失败 fail closed。预览执行、日志转 SQL 执行、回滚执行三处确认流共用；回滚视图对恒真/纯通配 WHERE 追加「快照将覆盖全表」警示
- **预览 `${}` 直接替换提示横幅（T-DollarInjectMark，O-11）**：XML 动态 SQL 预览含 `${}` 直替时，预览面板显示非模态单行提示「预览含 N 处 ${} 直接替换——替换文本未转义，注意 SQL 注入面」——引擎忠实计数（转义 `\${` 不计，字符串字面量内同样直替同样计数，MyBatis 同语义）；信息级可 ✕ 关闭，关闭后本 IDE 会话不再弹；纯 `#{}` 预览零打扰；渲染文本零变化（只加元数据）
- **DDL/事务提交后元数据缓存失效（T-DdlCacheInvalidate，O-12）**：内嵌控制台执行 DDL 或 COMMIT/ROLLBACK 等语句提交前，自动失效插件自持的表/列注释缓存（补全与 JOIN 富化的 metaCache）——ALTER TABLE 后立刻预览/补全不再命中旧结构；「失败也要失效」语义继承 DBX（Oracle 系 DDL 隐式提交），失效动作失败只记日志绝不影响执行结果；盘点确认插件其余缓存均不持 schema 信息（架构定案留档）
- **批量等值删除的 IN 合并参考行（T-BatchInMerge，O-14）**：foreach 批删日志还原后执行多语句时，确认浮层显示单行参考「检测到 N 条同表等值删除，可合并为：DELETE FROM t WHERE id IN (…）」——仅预览参考，执行仍逐条原样（等价性不由插件背书）；500 行 + 8KB 双约束截断计数，异构语句在场按「N/M 条」诚实披露，含引号字面量原样显示

### Fixed

- **DM8 需要 identity 包装（真机实测发现的新缺陷）**：达梦 DM8 对「显式给自增列赋值」的拒绝与 SQL Server 同形（`仅当指定列列表，且SET IDENTITY_INSERT为ON时，才能对自增列赋值`），而此前只有 SQL Server 会产出 `SET IDENTITY_INSERT` 包装 ——于是 DM 上凡把自增列勾回生成的 INSERT（含回滚链回填）都必然失败。现 DM 与 SQL Server 共用同一包装形态（真机实测两库语法逐字相同）。**DM 产物形态属用户可见变化**：勾回自增列的 INSERT 自此带成对包装
- **右键菜单「SQL 快捷模板」显示原始键（真机走查发现）**：`plugin.xml` 的 `<group>` 文案不走 bundle 解析（补 `bundle=` 亦无效，实测确认），导致编辑器右键菜单里该分组显示 `action.cn.song.mybatisplus.visualizer.SqlTemplateGroup.text` 原始键。现改为由 `SqlTemplateGroup`（`DefaultActionGroup` 子类）在 presentation 里取 bundle 文案，菜单正常显示「SQL Quick Templates / SQL 快捷模板」
- **回滚回填在「取不到自增列」时不再静默**：SQL Server / 达梦上，若回填 INSERT 需要 `SET IDENTITY_INSERT` 包装但插件没能从表结构里取到自增列（例如该表尚未在 Database 工具窗内省），此前会**静默**产出无包装的 INSERT（执行即 544）；现在弹窗会明确告警并给出处置路径
- **带引用符的表名解析不到（真机走查发现）**：`[user]` / `"user"` / `` `user` `` 这类带引用符的表名**原样**送进 schema 解析器，与 DAS 里的裸名对不上 ⇒ 表结构取不到——表现为回滚链的回填 INSERT 缺 `SET IDENTITY_INSERT` 包装（SQL Server 上仍报 544），同时影响列补全与 JOIN 富化的表结构来源。现解析入口先剥成对引用符
- **SQL Server 方括号引用导致「回滚 SQL」整体不可用（真机走查发现）**：`DELETE FROM [user] …` 这类带 `[...]` 的语句在回滚弹窗里直接报 `无法解析 DELETE: ParseException: Encountered unexpected token: "["`——两条解析链都不带 JSqlParser feature，而 `[...]` 正是本插件为 SQL Server 产出的引用形态。现统一走带 `allowSquareBracketQuotation` 的解析入口
- **数据库表右键「生成 CRUD SQL」按全局默认方言渲染（真机走查发现）**：`DbTableSpecAdapter.toSpec` 取方言时 `currentDialect()` 不传 project，`DialectRegistry.effective(null)` 落到默认 MySQL——真 SQL Server 数据源上产物是 MySQL 反引号形态 ``INSERT INTO `user` ``，同容器 `sqlcmd` 直接报语法错，且方言不是 `SqlServerDialect` ⇒ identity 包装（O-52）在 CRUD 侧的真机判据随之不成立。现改传表节点所属项目；新增源码接线守卫防回潮（`currentDialect()` 未传项目即红）
- **H2 标识符折叠方向归属订正（独立复核 minor㉘）**：H2 2.3.232 实测裸写标识符折为**大写**（与 Oracle 同族），此前登记为「不折叠」——于是 H2 上目录来源的含小写表名/列名不加引号，命中不了带引号创建的对象。现 H2 归入 `UPPER` 族（引号规则随之生效），判别力由真实 H2 引擎对照实验提供（引号创建两个名字后裸写访问：裸写小写名失败、裸写大写名命中）。**H2 产物形态属用户可见变化**：目录来源含小写的名字自此加双引号，实体来源逐字节不变
- **Oracle 驱动自身形态的报错位置识别（独立复核 minor㉕）**：ojdbc 的 `toString()` 拼接模板是 `Error : … , Position : N`（冒号前有空格），此前无任何 marker 覆盖该形态 → 这类报错拿不到位置。现补该形态的 marker（取值 +1 与服务端 `error occur at position` 同源；两形态并存时归并为同一读数、读数不一致则放弃归属），并**把此前只写不读的 `lineInSql` 接到提示文案**：只有行号（如 MySQL 语法错误）的报错不再落到「语句起始位置」兜底文案，而是显示驱动报的行号
- **Oracle 匿名块与 PL/SQL 语句切分（T-SqlSplitterPlsql，O-47）**：`SqlStatementSplitter` 此前对 Oracle 匿名块是「单次武装 + 全文单一深度计数」，`DECLARE … BEGIN … END;` 的声明段被切碎、而碎句还会被逐条提交执行。现新增 `declareSection` + `bodyBeginExpected` 两态（语句首 `DECLARE` 且前视存在配对 `END` 即进入声明段，段内顶层 `;` 不切分，声明段边界后的 `BEGIN` 即块主体起始），并对 `CASE … END` / `END CASE` 做计数隔离（`caseDepth` 在语句边界重置，`END CASE` 按双词终结形态识别，不误吞后续语句）。改前 61 例 8 失败 → 改后 64 例 0 失败；既有 BEGIN/END 用例 6 例全绿零影响。多匿名块串接的期望段数以改前实测钉住（2 条）
- **标识符折叠方向族与引号策略分组（T-IdentifierFoldingFamily，O-51）**：O-42 已落地「按名字来源分流」（CATALOG/ENTITY），但**无方言族概念**、`quoteIfNeeded` 在 DM 等方言未覆写 → 目录来源的含大写名在 PG 族下仍裸写。现新增 `enum class IdentifierFolding { UPPER, LOWER, NONE }` 与 `Dialect.identifierFolding`（接口默认 `NONE`；Oracle=UPPER、PostgreSQL=LOWER、KingBase=LOWER，其余 6 方言 MySQL/SQL Server/H2/SQLite/MariaDB/DM 继承默认 `NONE`），`quoteIfNeeded` 的按来源分流提升为基类默认实现，并补 PG 族用例（含大写 `Issue_New` 加引号、全小写 `id` 仍裸写）。**引号行为变化，属用户可见**；实体来源与其余方言产物逐字节不变

- **动态热更新触发平台 `Write-unsafe context!` 断言（T-DynUpdateWriteSafe）**：自更新走到动态热替换那一步时，插件用 `ModalityState.any()` 从后台下载任务把「卸载旧版 → 装载新版」派发到 EDT；而平台动态卸载会压入一个 ad-hoc 模态（`Unloading of <plugin>`），它的写安全资格取**派发时刻**的快照——`any()` 排出的活动恒为写不安全，于是卸载窗口内平台自身的文档 commit、落盘、组件 dispose 全部触发 `Write-unsafe context!`（真机日志模态串为 `[设置对话框, Unloading of SQL Visualizer]`，每次自更新一条 SEVERE 并进 FUS 错误上报）。现改为派发前在 EDT 上读当前模态：写安全则用它（设置页点安装时正是「模态存续期立即执行」的场景），取不到或非写安全则退 `ModalityState.nonModal()`（延迟到模态结束，平台契约语义）；同时新增派发日志行 `dispatch modality=… writeSafe=…` 供真机取证，并加「update 包禁 `ModalityState.any()`」源码守卫与决策单测防回潮
- **错误定位按钮「可见但点了没反应」（T-ErrorLocateUsability T-ELU-01，O-49）**：结果面板错误态的「定位到出错语句」按钮，其显隐判据是「宿主是否注入了跳转动作」（`locate != null`），而宿主（预览面板）**恒传非 null lambda**——锚点解析发生在**点击时**，解析不出就静默 return。于是无项目上下文 / 本会话尚未登记预览源锚点（gutter 面等未登记入口）/ 源文件已失效这三种情形下，按钮照常出现、点了什么都不发生，而 KDoc 写的「null = 锚点不可解析、按钮不出现」与实现不符。现改为**先解析锚点、再决定给不给按钮**（解析不出传 null，按钮不出现），并把「源文件已失效」也算作不可解析——跳不动的按钮不给，比给了点不动诚实。UI 侧零改动（`SqlResultPanel` 的 null 判定与显隐分支原样沿用），改动只在预览面板；对齐同仓日志面板早已做对的形态（先解析、后显隐）
- **Oracle 位置形态误标且恒差一位（T-ErrorLocateUsability T-ELU-02，O-49）**：错误位置提取器只认 PG `Position: N` / MySQL `at line N` / `Line: N` 三种形态，而 Oracle 报错走的是另一形态（真库实测：`ORA-00942: … does not exist` 换行后跟 ` error occur at position: 23`）。PG 的正则恰好顺带命中这段文本里的 `position: N`，于是 Oracle 位置**一直被提取，却挂着 `pg-position` 的标签、还按 1-based 直接报出**——而 Oracle 的值是**出错记号起点减一**（三例实测：记号在首位 → 0、`SELECT FROM` 的 `FROM` 在第 8 位 → 7、表名在第 15 位 → 14），恒差一位；位置为 0 时报出的值不合法，整条位置反被丢弃。现补 Oracle 专属 marker 并归一到 1-based（N+1）；修法是**先扫 Oracle 段并从文本里遮蔽为等长空格**再扫其余 marker——直接加 marker 会让两个 marker 并存、被「多信号放弃归属」的单一性门控判成不可信而**丢掉位置**（这正是本轮反向验证实测到的红形态）。PG 正则逐字未动，不含 Oracle 形态的消息行为零变化
- **错误位置越界钳制在生产路径失效（T-ErrorLocateUsability T-ELU-03，O-49）**：位置提取器的越界钳制（把驱动报的位置钳到被执行 SQL 长度）早已实现，但四处投递点（执行链三处 catch + MCP 的 `sqlv_explain`）**全都不传长度**——钳制分支只在单测生效。现四处全部接上：执行链传提交文本长度，MCP 传**被提交的 EXPLAIN 包装句**长度（驱动报的位置指向它，不是原始 selectSql）。另把「被执行 SQL 长度」结构化进富错误信息（非 null 即接线到位的证据），并加源码扫描守卫——生产链每个位置提取调用的实参都必须含长度表达式，漏传即红
- **「定位到出错语句」按钮在主执行路径永不出现——富通道投递链两处断点（真机走查发现）**：① 错误收口 `deliverError` 在一次 master 并入（9068fad）中丢失——master 侧从来没有这个函数，端态退回「onErrorRich 之后无条件再投 onError」，而 `showError` 会清掉定位按钮 ⇒ 按钮永不出现（真机实证：一条锚点可解析的失败语句只出红字 + 复制按钮）。现恢复 `deliverError`（富通道优先、两通道互斥、富通道抛异常回退旧通道），提交链三处 + 控制台历史三处全部改走它；连带把错误位置守卫的扫描面从「提取调用」扩到「投递调用」（收口后提取直调只剩 1 处，只认提取会退化成空绿）。② 主路径漏转发：`prepareInConsole` 在 `executeAfterPrepare` 分支调 `executeOnConsole` 时漏传 `onErrorRich`（签名里一直有该参数，只是没往下传）——这正是预览面板点「执行 SQL」的主路径，富通道在此断链。现补上转发，并把「每个 `executeOnConsole(` 调用都必须带 onErrorRich」写成守卫断言；反向验证摘掉转发即点名报「富通道在此断链，定位按钮永不出现」
- **PG 索引建议实际永不触发（T-ExplainChainHardening T-ECH-03，O-48）**：`sqlv_explain` 的 index hints 里 PostgreSQL / KingBase 一类从未出现过——建议器按 `Seq Scan on 表名` 的**文本树**正则解析计划，而 PG 方言渲染的是 `EXPLAIN (FORMAT JSON, VERBOSE)`，真库返回的是**单列 JSON 文本**（实测 PG 16.14：列名 `QUERY PLAN`，值形如 `[{"Plan":{"Node Type":"Seq Scan",…,"Relation Name":"bench_items",…,"Plan Rows":10000,…}}]`），两种形态根本不匹配，于是大表顺序扫描永远不提示。现按 `ExplainSupport` 表里的**输出格式**分派解析器（不再按方言名猜），JSON 档按节点树取 `"Node Type"` / `"Relation Name"` / `"Plan Rows"`（含 `"Plans"` 嵌套子计划），并留三段容错：整段 JSON 解析失败（长计划会被 2000 字符单元格预算截断）时按节点分片扫描、零命中再回落文本树规则。既有测试喂的是文本树形态（所以从未暴露），现补真库实测形态的用例
- **EXPLAIN 支持面与输出格式收敛为显式表（T-ExplainChainHardening T-ECH-02，O-48）**：支持面此前散在 7 处逐方言覆写里、靠默认 `null` 表达不支持——「没写」与「故意不接」在代码上同形，新增方言时也无从判定该不该有 EXPLAIN；输出格式更是压根没有概念（硬编码在各方言字面量里，消费方只能按方言名猜，这正是上面那条 PG 缺陷的成因）。现新增 `ExplainSupport` 表作为单一事实源（方言 → 包装模板 + 输出格式枚举 TABLE/TEXT/JSON/XML + 形态依据出处），Oracle / SQL Server 的「不接入」显式在册；各方言不再逐处覆写，渲染产物**逐字节不变**（守卫用例断言表与实现一致、表覆盖注册表全量、格式取值与模板自洽）
- **注入拦截器的框架帧跳过表补齐（T-AgentResiduals R1b）**：`SQLVIS-SOURCE` 标记行由**注入到用户工程**的 `SqlSourceInterceptor` 打印，而那份模板的跳过表只有 15 项（JDK / 平台 / 本插件 / MyBatis 系）——驱动族、连接池、AOP、数据层插件族（`dm.jdbc.` / `com.alibaba.druid.` / `org.apache.commons.dbcp2.` / `net.sf.cglib.` / `com.github.pagehelper.` / `org.apache.` / `io.netty.` …）四十余项都不在内，于是标记行可能指到框架帧、点跳转落进第三方库；而同一次执行的 agent 通道给的是正确位置（两侧不一致）。现该模板补齐到与 agent 侧同集。R1 当时同步的是**参考副本**（IDE 侧 `CallerSourceLocator`，`src/main` 内无调用点）与文档示例，**漏了这份真正生效的**——守卫已扩到**全部 4 份副本**（agent `StackLocator` / IDE `CallerSourceLocator` / 注入模板 / 文档示例），任一份增删前缀未同步即红；副本清单与各自消费者写进守卫 KDoc，防下次再「同步了不生效的那份」。**迁移前提（务必知悉）**：模板只在注入那一刻写入工程，存量工程里**当前形态**的注入文件被幂等跳过、**不会自动更新**——本改动只对**新注入**与**旧形态副本的内容升级**生效；存量工程需删除注入的 `SqlSourceInterceptor.java` 后重新注入，或按模板注释手工补前缀
- **停采期间 prepare 的语句恢复后不再哑（T-AgentResiduals R5）**：agent 的连接代理此前在 `invoke` 顶层判「停采」就整体直通，于是停采期间 `prepareStatement` 返回**原语句**（不包装）——「停采期间 prepare、恢复后才执行」的语句永远不产出事件。MyBatis 默认 `SimpleExecutor` 每条查询现 prepare、执行后关闭，故实际不可达；但 `ReuseExecutor` 一类复用语句的执行器、以及应用自持语句的场景会命中。现本仓统一为**只在执行级短路**：连接与语句包装一律在位，唯一闸门是语句代理的逐调用停采短路（它排在参数捕获之前，故停采期间既不产出事件也不累积参数，恢复后不会错配）。顺带修一处告警名额：包装失败的「一次性告警」此前会被停采期间的失败消耗掉，导致恢复采集后真失败一声不响——现停采态只计数不打印、不占名额。反向验证：把顶层短路加回 → 新用例红（语句未被包装，实测包装者是驱动自己的 `FakeStatementHandler`）
- **CONFIG 回执超时的告警不再把「连接已断」说成「应用侧未生效」（T-AgentResiduals R4）**：此前 `sendConfig` 后 5 秒内没收到 `CMD_CONFIG_ACK` 只会打一句「CONFIG 未获确认——应用侧可能未生效」，而三种成因（控制通道已断开 / 应用侧在跑却不回执 / 应用侧真静默）对用户的处置完全不同——半死 socket 被判成「应用侧未生效」是**错叙事**（连接都不在了，与应用侧应用与否无关），用户会去查应用侧配置而真正该做的是重连。现按「到点那一刻的会话健康」分三态叙述：`alive=false` → 「控制通道已断开」；下发后仍收到入站帧 → 「应用侧仍在跑（典型是旧版 agent 无回执能力）」，并提示此时的双通道属混合版本正常形态；两者皆非 → 才用「应用侧可能未生效」。三态共用同一个超时计数器，只有文案分叉（文案由纯函数产出，全分支可单测）。另把「旧版 agent（无回执）混合版本下桥永久放行、两条通道同时产出」这条边界写进 KDoc 与 CHANGELOG（**行为不变**，靠列表去重窗口折叠，不回到「按 socket 在线封桥」那条已证有害的老路）。**已知边界**：`INTAKE_DROP_WARN_STEP`（50）与 `CONFIG_ACK_TIMEOUT_MS`（5s）的取值本身现已由用例钉住——断言经**反射读编译产物**而非直接引用常量（`const val` 会被编译期内联，增量编译下直接引用会读到旧值：实测改常量后未重编译测试类时**假绿**，改回后未重编译时**假红**）
- **两侧「框架帧跳过前缀」不再分叉（T-AgentResiduals R1）**：IDE 侧 `CallerSourceLocator` 的跳过表原只收 JDK / 平台 / 本插件 / MyBatis 系 15 项，而 agent 侧 `StackLocator` 另收驱动族（`dm.jdbc.`/`oracle.jdbc.`/`com.mysql.`…）、连接池（`com.alibaba.druid.`/`com.mchange.`/`org.apache.commons.dbcp2.`/`org.apache.tomcat.`）、AOP/字节码（`net.sf.cglib.`/`org.aspectj.`/`org.objectweb.asm.`/`org.jboss.`）与数据层插件族（`com.github.pagehelper.`/`org.mybatis.`/`com.alibaba.`/`org.apache.`/`com.google.`…）共四十余项——同一次执行两侧可能给出**不同位置**（标记行指到框架帧）。现按 agent 侧逐项补齐到**同集**（纯数据同步，IDE 侧仍不依赖 agent 代码——它是 agent 缺席时的降级主路径），示例模板 `docs/instrumentation/SqlSourceInterceptor.kt` 同步补齐；两侧唯一刻意差异只剩各自的自身包前缀。跨侧漂移由 `LocatorSkipPrefixSyncTest` 继续以源码扫描 + 差异登记锁定（`AGENT_ONLY` 现为空集，另加按族点名的补齐锚点用例防「两侧同时回退」）。**未做**：面板位置 vs 标记行的真机前后对照需 runIde 沙盒，留主调度/用户取
- **预览首开降级后无法就地恢复（T-PrewarmLateRecover）**：冷启首开（首次索引 / 重负载）时预热耗时可达 3s，远超 500ms 等待预算，面板落内存 PSI 降级并挂横幅；而预热其实成功了，产物只落在字段上、此后无人消费（`createEditor` 只在没有编辑器时进入），横幅在整个对话框生命周期内常驻，用户只能关掉重开。现在补两条恢复出口：预热产物**迟到到达**时，若面板仍显示那份降级文档且用户没动过，自动原地换装成「项目内文件背书」的编辑器并清除横幅（文本逐字不变，光标与焦点复位）；预热**硬失败**（无产物可等）时横幅多一个「重试」动作，点一下重新预热、就绪后同样原地换装。等待预算仍为 500ms 不抬高，产物按预热轮次令牌归属（旧轮的迟到产物不会覆盖新一轮）
- **服务端 SQL 报错不进预览面板错误条（T-ConsoleErrorCoverage，P15）**：面板下方的错误行与「复制错误信息」按钮只认控制台文本里的一小撮短语（`unknown column`、`doesn't exist`、`syntax error` 等 14 条），而 MySQL 语法错写的是 `You have an error in your SQL syntax`（不含 `syntax error`）、SQLSTATE 又是 `[42000][1064]` 这种数字形态，于是一条都不命中——错误只在控制台 Output 页可见，面板全程无红字、无复制按钮，16 秒后还落回「SQL 已提交执行，但等待结果超时……请检查密码输入框/测试连接」这类把语法错归因成密码/驱动的提示。现判据升级为「结构性判据 + 短语族」：直接认 DBN 给服务端错误加的 `[SQLSTATE][错误码]` 前缀（跨方言同形，Oracle `ORA-00933`/`ORA-00942` 一并认），并补 MySQL 语法错、`Duplicate entry`、`foreign key constraint`、`ORA-00933` 等厂商报文；另加一条兜底——判据认不出但控制台确有新增输出时，把「新增文本去掉本次 SQL 回显」后的内容如实呈现（前缀标注「未能识别为已知错误形态」），不再把失败笼统归因成凭据问题。错误文本同时剥掉逐行的 `[时间戳]` 与库提示符前缀、摘录由 4 行放宽到 8 行，一键复制到的是干净原文。**口径**：属既有覆盖面缺口而非本轮回归——历史真机验证过的报错恰好全是 `Unknown column` 系（该系命中），故缺口长期未现
- **增强捕获会话建立后 30 秒必掉线（T-AgentHeartbeat，T-01/T-02）**：agent 侧心跳此前用「假定每轮 200ms」累加计时，而每轮真实耗时≈1.2s（入站 CONFIG 读超时 1s + 轮询睡眠 200ms），于是「静默 10s 发心跳」实际要 50 轮≈60s；而 T-RA-01（2026-09-18）落地的心跳窗口是 30s，首条心跳永远赶不上窗口，增强捕获会话建立后 30 秒必被摘除——沙盒四轮运行全部命中（HELLO +17ms、首条 HEARTBEAT +60633ms），用户侧表现是「一条 SQL 都捕不到」。现改按最近一次出站帧的墙钟差判定（每轮都判，事件突发期间也按节奏发），连接建立写完 HELLO 后立即补发一条心跳；`ONLINE_WINDOW_MS` 改由 `HEARTBEAT_INTERVAL_MS` 推导（3 倍余量，值仍 30s），两侧常量由源码扫描的跨侧不变量（`window >= 3 × interval`）锁定，原先那条只断言「源码里存在 `10_000L` 字面量」的空绿断言已删除。修复后实测：连上即心跳、此后稳定约 10.7s 一发
- **增强捕获掉线后无法恢复（T-AgentHeartbeat，T-03）**：premain 通道与 attach 链此前都只 `accept()` 一次就关掉监听 socket，而重新挂载的唯一触发点是「进程启动」事件——应用已在运行时不会再触发，于是任何一次会话摘除对该次运行都是终局（现场：应用 JVM 又存活 7 分半，增强通道全程零产出，agent 侧按 1s→5s 退避重连却撞在已关闭的端口上）。现 premain 通道改循环 accept，通道寿命绑定到本次运行（控制台移除即关），另设长 TTL 与重连次数上限兜底，accept 线程与 socket 一并挂进 disposable 树
- **增强捕获状态行不再断言它不知道的原因（T-AgentHeartbeat，T-05）**：会话因心跳窗口过期被摘除时，状态行一律报「应用侧心跳中断（进程可能已卡死）」——而现场进程完全健康、只是首条心跳还没到，这句因果断言把用户往「去看应用进程」的错方向引。现补一个存活帧事实位（HELLO 不计入，它只证明 socket 建立），把「连接刚建立、首条心跳未到」与「曾有心跳后停摆」分成两态分别叙述：等待中为「连接已建立，尚未收到应用侧心跳（等待首条心跳）」，停摆为「已 {0} 秒未收到应用侧心跳，已回落控制台捕获」（秒数取在线窗口值，改窗口文案跟着变），「进程可能已卡死」删除；多会话同时摘除时以停摆为准，不把真停摆降级成等待中
- **子类加载器下 SQL 织入静默失效（T-AgentHeartbeat，T-06）**：驱动由子加载器加载时（Spring Boot fat jar 的 `LaunchedURLClassLoader`、devtools 的 `RestartClassLoader`）代理定义会抛 `interface ... is not visible from class loader`（代理类定义在 agent 侧加载器里，而 `com.mysql.cj.jdbc.JdbcConnection` 等接口属于驱动加载器），该异常被静默吞掉并返回原连接——零事件、零日志。现代理定义改为在候选加载器里选第一个「能看见全部接口」的（逐个 `Class.forName(name, false, loader)` 实测校验，被包装对象自身加载器优先），失败走统一出口计数并给一次性 WARN（不刷屏）；语句包装失败也不再向宿主的 `prepareStatement` 调用点抛异常，改为返回原语句。测试夹具此前只实现 bootstrap 的 `java.sql.Connection`，恰好绕开了唯一失败分支，现补驱动自定义接口并新增子加载器用例。真驱动前后对照：`events=0`（零诊断）→ `events=2`；premain + 系统加载器 / agentmain + retransform / HikariCP 连接池三种既有形态无回退
- **SQL 日志面板空态诊断行被右边界截断（T-AgentHeartbeat，T-04）**：诊断行由「两条通道状态 + 下一步提示」拼成、以 `\n` 分隔，而 `JBList.emptyText` 是 `com.intellij.util.ui.StatusText`（**不是 `JLabel`**）——`StatusText` 及其底层 `SimpleColoredComponent` 在绘制路径上完全不处理 `\n`，也没有任何折行逻辑（`drawWithClipping` 只裁不折），于是各段被无声拼接、超宽部分被右边界裁掉，恰好把「请确认应用已开启 SQL 日志输出（mapper 包日志级别为 debug），或启用增强捕获」这句唯一可执行的提示截掉。现改走平台唯一的多行手段 `StatusText.appendLine`（每行一个 Fragment，逐 Fragment 绘制），并在写入前按字体度量自行折行（宽度取列表可用宽度、clamp 下限、首帧兜底，`ComponentListener` 在缩放时重排）；换行点按语义给：增强通道状态 / 控制台通道与丢弃计数 / 提示语各占一行。**注意 HTML 路线在本平台不可行**：`StatusText` 无 HTML 处理，照 HTML 实现会把标签字面量原样显示给用户（比修复前更糟）
- **设置页双击跳转不再卡顿（N5）**：设置页（Tools → SQL Visualizer）双击搜索/列表条目跳转时，此前按「目标类」在设置树里查找，平台实现会把树里每个设置页都实例化一遍（含其它插件的页面），其中一个页面在构造期做文件名索引扫描，于是在 EDT 上触发 `Slow operations are prohibited on EDT`（大工程或刚打开工程时界面卡顿 + 日志报错）。现改为按设置页 id 查找，只创建目标页；跳转与高亮行为不变
- **占位符拼接串感知化（T-PlaceholderSpliceGate，N-33）**：面板回填与「复制可执行 SQL」此前按朴素逐字符替换 `?`，字符串字面量与注释里的 `?`（如 `WHERE name = 'a?b'`）会被当成占位符换掉、产物错位。现两处改用与日志还原链**同一份**串感知位点实现（上提到 `sql` 包跨包共用，位点实现唯一性有源码断言守卫），引号与注释内的 `?` 不再被替换；正常路径（字面量内无 `?`）产物逐字节不变。位点数与参数条数不等时也不再静默——复制产物头部加一行注释如实标注、执行与 EXPLAIN 前记一条日志（只认「占位符多于参数」这一种，避免已回填的常态误报，不阻断执行）
- **Oracle 目录来源标识符按大小写来源引用（T-OracleQuoteCaseSource，O-42）**：从数据库目录（自省拿到的字典真实名字）生成 CRUD SQL 时，此前一律裸写标识符——Oracle 的裸标识符会被折叠成大写，于是以引号创建的小写对象（如 `"issue_new"`）引用必然报 `ORA-00942`（真库实测，不是静默改语义）。现按名字来源分流：目录来源的名字只要含小写字母就加双引号、全大写才裸写（保留字命中即包的既有行为完整保留）；实体来源的名字逐字不变——实体名派生的小写名正是以裸写创建的名字，加引号反而必然失败（真库反向对照实证：裸写 `user_tables` 命中、加引号 `ORA-00942`）。其余 8 个方言与未接线点产物逐字节不变

- **MySQL 命令行习惯的 `\G` 后缀不再报语法错（T-MysqlGStrip，O-32）**：从 mysql 客户端复制过来的 `SELECT 1\G`（垂直输出后缀）粘进预览面板/控制台执行时，文本原样发给服务端报语法错。现提交前剥掉最后一语句行尾的 `\G`/`\g`（允许尾随空白，允许分号在 `\G` 之前或之后），并把剥后文本同步回编辑器（所见即所执行）；注释行与字符串字面量里的 `\G` 不碰（`SELECT '\G'` 原样透传）；历史记录仍保留你粘进来的原文；非 MySQL 数据源不剥离。规则对齐 DataGrip 同项处理
- **共享会话复用与数据源记忆不再「猜」（T-SessionIdentityGuard）**：预览执行链上有四处静默猜测，现全部收成 fail-closed。①共享控制台复用：判定接上三分量身份探测（复用 attach 路径既有探测），身份不可信即弃会话，数据源已从 facade 消失时同时清掉数据源记忆（旧实现只丢会话不清记忆，下一轮仍按显示名静默命中同名数据源）；②last-used 数据源记忆升级为「UUID 为主 + 显示名回退」双字段（旧显示名键保留读写，兼容一个版本，下个内测版后废弃），命中顺序=UUID 精确命中（数据源改名也认）→ 显示名唯一命中 → 否则弃记忆走弹窗，**同名多条数据源不再静默取首条**；③URL 未指定库的数据源不再静默跳过库上下文对齐——诊断与错误上下文行如实标注「未能确定默认库，当前=X」；④`setSearchPath` 强设后读回校验，与目标库不一致时记警告日志并附实际库（只告警不阻断，避免只读场景被对齐失败拦死）

- **帧过滤前缀输入框被 GridBag 压扁不可见修复（T-FramePrefixVisibility）**：设置页「帧过滤前缀」多行输入框在真机上几乎不可见（真机截图定谳 H4）。修复=`JBTextArea` preferredSize 高度保底 ≥60px + lineWrap，并补平台标准文本框边框（`UIUtil.getTextFieldBorder`）与编辑区背景（`getTextFieldBackground`）+ 内部留白 + 长词换行，深色主题下框体辨识度提升；新增组件树守卫测试 `FrameSkipPrefixesFieldVisibilityTest`
- **定时回归任务不再弹出真机浏览器（T-BrowserLeak2）**：用户真机 Edge 每隔一段时间自动打开 `sql-visualizer.jvtools.cn/about/feedback` 与 `example.invalid/never-opened` 两页。根因是 2026-09-11 帮助页弹浏览器第一轮修复的残余——测试 `SafeBrowserTest` 为验证「测试环境不弹浏览器」而直调这两个真实 URL，但 `SafeBrowser` 守卫写成「有 Application 且 isUnitTestMode 才短路」，纯 JUnit 无平台 Application 的测试进程反而被放行，`BrowserUtil.browse` 降级 `Desktop.browse` 直接 ShellExecute 拉起默认浏览器，定时任务每天跑全量测试即周期性弹窗。修复=守卫语义反转为 fail-safe 默认拦（`app == null || isUnitTestMode` 一律短路，真机 IDE 宿主行为零变化）；测试断言改为直接验证判定函数 `isTestEnvironment()`（不再依赖「没弹」这种不可观测副作用）；守卫测试补位——`BrowserUtil.browse` 禁用扫描扩展到 src/test、SafeBrowser fail-safe 守卫形态加锚点防回退
- **HQL 继承/抽象类实体「列信息未解析」降级修复（T-HqlInhCols）**：HQL 预览出现 `列信息未解析，降级为 x.*`，实体类继承父类（含抽象类）时更易触发。根因链：实体解析返回「表信息在但列清单为空」时被直接当作成功短路，跳过了 hbm 映射兜底与实体别名反查；且 HQL `FROM 别名` 里的 JPA `@Entity(name=...)` 实体名全链无读取点，别名形态的实体名不被替换成表名。修复=①实体解析空列不再短路（先试更优候选，找不到才保留原结果，表名替换不丢）；②新增 `@Entity(name=...)` 实体名反查（类名快路径未命中时兜底，带 PSI 修改计数缓存）；③SELECT 展开降级注释分两档——「实体不可解析」与「实体可解析但列空（提示检查继承链父类映射）」，诊断方向可区分；④`@Inheritance(JOINED/TABLE_PER_CLASS)` 预览附边界说明注释（父类字段实际存于父表/子类独立表，列清单按单表口径合并）；⑤补三级抽象父类链、隔代 `@Transient` 排除、实体别名读取等守卫测试
- **注入确认不再反复打扰（T-PS4-01）**：增强捕获默认开启后，每个进程启动都可能弹一次「是否注入」模态框——拒绝不被记忆、HTTP 请求/测试/profiler 等非主配置进程同样触发，拒绝注入的用户日常开发被反复打断。现拒绝记忆 24 小时冷却（设置页关闭再开启增强捕获即重置）、未确认时非主配置进程静默跳过，弹窗上新增第三个按钮**「关闭增强捕获并不再询问」**一键持久化关闭（设置页可随时重新开启）
- **历史保留上限裁剪不再误删用户文件（T-PS4-10）**：自定义保存目录下与插件历史命名无关的 .sql 文件（用户自有脚本）曾被按「最旧组」一并静默删除；现只认本插件命名模板渲染出的文件族，其余文件永不计数、永不删除（宁漏删不误删）
- **预览格式化回填即时落盘（T-PS4-12）**：预览回填格式化文本后执行文件滞留「已修改未保存」窗口——同临界区落盘收口，不留文件缓冲区冲突暴露面
- **JOIN 图连线丢失修复（T-EmbedFkOrder）**：同样两条 SQL，一条的 JOIN 图有连线、另一条没有。根因=渲染路径分流 + 清理顺序——两张表都能在数据源中定位时走 Database 原生图，其连线来自**虚拟外键注册表**（由 ON 条件登记、框架建边时回查）；而预览面板里是「先建新图、后清旧图」，旧图释放时把注册表整表清空，**连新图刚登记的 ON 条件一并抹掉** → 原生图只剩节点没连线。含子查询的模型因「表未全部定位」回落另一条渲染路径（连线取自模型本身）故不受影响——这正是「一张有、一张没有」的来源。修复=清理旧图前移到建新图之前；组件释放不再顺带清注册表（改由「整图卸载」显式回收，避免误伤当前图）
- **预览/控制台写入上下文 write-unsafe 报错根治（T-WriteSafeCtx）**：真机日志出现 `Write-unsafe context! Model changes are allowed from write-safe contexts only ... current modality=ModalityState.NON_MODAL`，栈底为预览「挂载后回填」的文档写。根因=写模型的合法性不取决于是否包了写命令，而取决于这次 EDT 活动有没有 write-safe 资格——`invokeLater(..., ModalityState.any())` 排出的活动**恒 write-unsafe**（平台文档原文：nonModal 恒安全、any 恒不安全），其中的文档写必触发该断言（生产记严重日志 + 插件错误上报，测试环境直接抛）。修复=新增写入上下文闸门 `DocWriteContext`：`renderSql` 入口自愈（不可写则重投递到 write-safe 模态的下一拍）、5 处写入类 `any()` 回调改 `nonModal`、纯 UI/只读回调统一标注豁免；并新增源码守卫（`any()` 回调内出现文档写即测试失败）与闸门行为测试防复发
- **预览参数区背景丢失修复（T-PreviewBgFit）**：深色主题下左侧参数面板只有标题行是灰的、下方一片黑。根因=界面原生化那一轮把预览左右分栏从自绘分栏换成平台 `OnePixelSplitter` 时，漏掉了原分栏显式设置的「面板背景」——而参数区整条链（滚动区/视口/顶部对齐容器）自古刻意透明以与父容器融合，于是空区直接透出分栏自身背景（深色主题近黑）。修复=恢复分栏面板背景，并让参数滚动区自身成不透明面板灰（今后再换容器也不复发）
- **JOIN 图默认自适应居中（T-PreviewBgFit）**：打开 JOIN 图默认不居中、要手点【调整内容】才对。根因=平台「布局后自适应」是图设置项（工具栏那个开关的实现）＋【调整内容】动作（`fitContent`），二者只在独立图编辑器标签页路径被平台触发；我们手工构造编辑器并嵌进预览面板，开关从未置位、也没有布局完成钩子。修复=嵌入时置「布局后自适应」与「尺寸变化后保持自适应」，并在首次显示且组件有尺寸后按【调整内容】同参补一次 `fitContent`（**第二轮修正**：首次布局是异步触发的，开关必须置于其**之前**才生效——否则同一会话里会出现「第一张图不居中、第二张正常」的竞态，已按此把置位前移到两条建图路径的布局触发点之前）
- **预览会话库上下文对齐与诊断（T-ConsoleDbContext）**：同一条 SQL 在预览窗口执行报 `Unknown column 'u.username'`、在原生控制台正常（数据核对无误）。根因=**库上下文错位**而非 SQL 有错——DBN 的「文件→数据源」映射把执行文件钉在另一个库上（本机实测 `mpj_demo.user` 没有 `username` 列，与报错逐字吻合），而会话连的是 SQL 所属数据源。修复=①预览控制台就绪即把当前库对齐到「数据源 URL 里的库」（用户定案语义；已一致则不动，不覆盖用户后来的手选）；②执行失败提示追加「当前库 / 数据源 / 数据源默认库」上下文，裸 MySQL 报文从此可一眼归因
- **预览控制台显示回归格式化（T-PreviewConsoleFmt）**：预览后内嵌控制台的 SQL 区只显示裸单行、格式化失效。根因=控制台挂载在 exec 文件本体上（其文档即该文件文档），而预览链的预热把「预览原文」写进该文件（裸单行），面板渲染的格式化文本只落在面板自建编辑器里，挂载后既无重渲染、面板编辑器又被释放 → 用户看到裸 SQL。修复=控制台嵌入完成即按当前渲染文本回填一次；预热在控制台已挂载时不再改写该文件内容

- **数据源字段补全恢复 + 库列进补全候选（T-DbSchemaCompletion）**：SQL 预览页只有实体类字段补全、数据库字段补全不生效。两个缺口叠加——①数据源 schema 读取链**从未成功执行过一次**：`DatabaseSchemaResolver` 用 `Class.enumConstants` 取 `ObjectKind.COLUMN`，而 DBN 的 `ObjectKind` 是手写 type-safe enum（非 `java.lang.Enum`，`enumConstants` 恒为 null），每次调用都在该行静默早退，且早退无日志，上层只打印误导性的 "not found in N data sources"（真机 23 次调用成功分支日志 0 次，而同名表其实存在于 information_schema）——M35 的"数据源注释优先"与 JOIN 图列类型富化一直是空转；②补全候选本就只有实体列，数据源列仅用于覆盖同名列注释。修复：ObjectKind 改按静态字段取（取不到即把该类实际常量名写进日志），三处早退路径全部改成必留日志并区分「查不了」与「确认无此表」，查不了的数据源不再写负缓存（数据源晚连接时曾把涉及表钉住 30s）；列候选改为「实体列 ∪ 数据源列」（实体列在前、同名列注释与类型取数据源、tailText 追加 DB 类型串标注来源），预热在预览打开与控制台就绪时后台进行，补全热路径零遍历；顺带修 `refreshCompletionContext` 未同步原生控制台编辑器上下文（控制台是实际输入面，不刷则预热完成也读旧上下文）。**同批伴随修复 JOIN 图字段注释缺失**：JOIN 图列注释只有实体与数据源两路来源，实体没写注释（如 demo 的 `UserDO`）时全靠数据源，此前富化随 ObjectKind 一起静默失效，JOIN 图整片字段注释为空（原生「显示图」直接读库所以有）——修好取法后按列名回填 DB COMMENT 与类型串即恢复；另补「首次富化空手时、数据源建连后补刷一次」的窗口（预览打开常早于建连，此前不重试）

- **Hibernate/JPA 链路并发配对同步修复（T-HibConc）**：与上一版同一缺陷的第三条链路——`HibernateLogParser` 也是单槽状态机，并发下另一线程的语句行会提前闭合本线程的 SQL 块、绑定行被追加进共享参数列表（**A 的 SQL 配 B 的值**）。本轮补齐按线程分桶；难点在 Hibernate 独有的「双副本合并」（`show-sql: true` 的 `Hibernate: ` stdout 副本 + `org.hibernate.SQL` logger 副本）：多行 SQL 正文与 stdout 标志行**都不带日志前缀、提取不到线程 token**，朴素分桶会让正文落回退桶、绑定行落线程桶，合并与参数归属双双失效。故给分桶路由加了一条 Hibernate 专用策略——无 token 行跟随**最近一次出现线程 token 的桶**（MRU），并把零参影子隔离槽**按桶隔离**（并发下不同线程的影子不再互相顶掉，同一 SQL 被两线程执行时各产出独立条目）。仅 stdout 副本（全程无 token）仍回退共享桶，与既有语义一致零劣化
- **并发下 SQL 日志条目严重不正确修复（T-LogParseConc）**：用户实测「并发时日志不对」并附控制台原文（12 个 Tomcat 线程交错、MP 分页 `selectPage` + `selectPage_mpCount` 成对）。三个根因：① `MyBatisLogParser` 是**单槽状态机、不分线程**——另一线程的语句行会提前闭合本线程尚未收到参数的语句，本线程随后到达的参数行因无上下文被静默丢弃（参数全丢、`?` 未还原），而 `JdbcTemplateLogParser` 早在 T-JdbcThreadBucket 就按线程分桶修过同类问题、MyBatis 从未跟进；② 空 `Parameters:` 行（MP 的 COUNT 语句会打印）触发的「等下一行作为参数文本」兼容态**跨语句残留**，把下一行整行吞成参数值——包括另一线程完整的 `Parameters:` 行，面板于是出现 `LIMIT 2026-09-16 14:35:00.413 DEBUG …` 这类文字；③ 多行 SQL 条目（JdbcTemplate `Executing prepared SQL statement [ … ]` 跨行）**取不到日志时间**（收集路径不记首行）→ 回落插件捕获时刻，控制台行多时与日志行拉开（实测 209ms）。修复：线程分桶下沉为三解析器共享的 `LogThreadRouter`（token 提取 + 分桶 + 空闲桶淘汰，MyBatis 全状态按桶隔离）；空参判别式（下一行若带日志行特征 → 判为无参语句并闭合，且**不吞该行**；裸文本行维持旧兼容语义）；多行 SQL 的日志时间统一取**语句首行**；MyBatis 支持多行 SQL 续行（mapper 里格式化的 SQL 不再只留首行，日志行/异构语句行/空行即终止）；解析期静默失效改为计数并在轮询周期上报（参数无上下文丢弃 / 空参行拦下 / 残行闭合 / 参数含日志特征被拒）。未做：Hibernate 链路分桶（其 `Hibernate: ` stdout 副本无日志前缀，与 logger 副本可能分落两桶而破坏 T-HibDualCapture 的影子合并——无复现场景前不冒险，见计划交付记录）
- **增强捕获条目时间与控制台日志行对不上修复（T-AgentLogTime）**：增强条目的「日志时间」是靠控制台日志行暂存、再按指纹取回派生的，而键原先用「还原后的 SQL」——两侧还原器各自独立（布尔参数引号、注释内 `?` 计数、参数个数不等三处口径分叉），静默失配后回落显示 agent 采集时刻；该时刻原先又取在 execute **结束**，于是比控制台日志行（打印于执行前）整整晚一个 SQL 耗时——快查看不出，慢查与首次查询即肉眼可见的偏差。三处同修：① 采集时刻前移到 execute 开始；② 关联键改用占位符版 SQL 指纹（两侧同源的原文，不再依赖参数还原口径），参数值序列降为次级判别，同键改排队不再互相顶掉，并加 30s 陈旧项时间窗；③ 日志时间采集不再受「时间显示开关 / 时间来源」这类渲染偏好控制（关掉显示只影响渲染）。另补跨通道端到端守卫用例（真实控制台解析链 + 真实 agent 适配器，覆盖布尔/时间/null 参数、字面量与注释内 `?`、参数个数不等、同 SQL 多次执行等形态），未命中时前 3 条打印键与 SQL 片段留痕。多行 SQL 的日志时间已随 T-LogParseConc 的续行落地转为命中
- **SQL 历史页元信息顺序与日志页统一**：历史页原为「行号 → 耗时 → 时间」，日志页为「行号 → 时间 → 耗时」，同一条目在两页读法不一致。历史页改用日志页同一套片段与顺序（时间 → 耗时 → 目标库 → 来源），耗时不再自拼 `[xms]` 灰字而是复用日志页片段（按慢查询阈值着色、缺失占位「—」）
- **agent fat jar 构建工具源从未纳入版本控制（构建缺口）**：`src/reloc` 源集的 `RelocateAsmMain.java` 包名路径含 `build` 段，被 `.gitignore` 通用规则 `build/` 整目录忽略——旧工作区因文件残留本地磁盘而构建看似正常，干净检出/其他工作区必然报 `ClassNotFoundException`。照既有风格补 `!**/src/reloc/**/build/` 例外并纳入源文件

- **耗时排序按钮在增强捕获下不显示且排序失效修复**：按钮可见性与排序取值原先只看「日志文本里解析出的耗时」（p6spy/druid 行），而增强捕获的耗时是结构化字段、文本内没有——按钮恒隐藏、排序取值全空。改为结构化耗时优先、文本解析兜底，按钮与排序两处统一口径
- **增强捕获源码位置误选第三方插件帧（T-AgentSourceJump）**：源码位置定位原靠硬编码「框架前缀黑名单」，漏收 PageHelper 等数据层插件——插件帧被误判为用户帧选中，列表显示 `PageInterceptor.java` 且跳转报「源码文件未找到」。改为**按帧来源判定**：开发态用户业务类来自目录（`target/classes`）、第三方依赖恒来自 JAR，据此跳过 JAR 帧（与类名无关，根治黑名单遗漏）；补齐常见数据层家族前缀；并新增候选帧透传 + IDE 侧解析回退双保险。保留安全网：来源不可判或无候选时回退既有行为，杜绝「过滤到空、跳转能力消失」劣化
- **增强捕获事件零到达根治（agent 事件 JSON 非法）**：agent 事件写出器给首个字段也补了前导逗号，产出 `{,"sql":…}` 非法 JSON——SQL、参数、耗时其实已全部采集到位，却在 IDE 侧解析全量失败被静默丢弃（表现为「增强开着但列表空」）。重写为统一首字段分隔并补格式守卫测试（最小事件/全字段/全空字段/转义四例），堵住跨进程协议两端各自测试绿、合流即断的往返缺口

### Fixed

- **SQL 日志面板四项缺陷终局修复（F-44-2）**（开发计划 `20260831-1730-...`）：
  - **列表 SQL 词法高亮恢复**：M46 重构为性能移除 HTML 通道，本次回滚——SQL 摘要走 `SqlListHtmlRenderer`（关键字/表名/字符串/数字/注释分色），时间戳与耗时走灰色 `#9E9E9E` 视觉分层不抢 SQL 颜色
  - **耗时字段接入控制台链路（root fix）**：`ExecutionTimeParser` 已有完整 p6spy/MP TimeCount/自定义前缀实现，但 bridge `FilterProxyHandler` 从未调用——`LogSqlEntry.executionTimeMs` 始终为 null。`SqlLogConsoleBridge` 每次喂行前从 `PluginSettings.state.logTimePrefix` 读自定义前缀，调用 `ExecutionTimeParser.parse(line, prefix)` 并 `entry.copy(executionTimeMs = ...)`。耗时面板与历史面板均自动显示 `ms`，阈值色（<100ms 灰 / ≥100ms 橙 / ≥`slowQueryThresholdMs` 红）
  - **「移除重复的sql」已存在条目同步去重**：用户勾选后面板新增 `SqlLogEntryBuffer.dedupeExisting()` 立即按窗口裁剪（窗口内同 SQL 留首条去后续），丢弃数累加到 `dedupeCounts`，徽章与列表内容同生命周期。panel 调用方 `SqlLogPanel.dedupeCheckBox.actionListener` 升级为 on/off 双分支
  - **去重计数即时刷新**：原 `addEntry` 去重丢弃分支 `return false` 而不通知，徽章数据变了 UI 不知——本轮在去重分支也调用 `notifyChanged()`，`⨉N` 徽章与去重动作一帧同步（修改了两条既有测试 `去重窗口内相同 SQL 丢弃且不通知` → `... 且通知徽章`、`去重丢弃不触发监听器` → `去重丢弃触发监听器`）

- **SQL 历史面板两项修复（F-44-2）**：
  - **历史列表 SQL 高亮 + 耗时显示**：`HistorySqlLogPanel.HistoryCellRenderer` 改 HTML，SQL 段走 `SqlListHtmlRenderer`、耗时/时间戳/源码走灰色 `[...]` 包裹；耗时取自 `LogSqlEntry.executionTimeMs`（现已是真实解析值，非 `—`）
  - **历史文件 SQL 注释恢复标准 `--` 注释**：F-44 一度写为 `--- source: ... ---`（三个 `-`），回归为标准 SQL 单行注释 `-- source: ... --`（两个 `-`）；更严格 SQL 方言对 3 个 `-` 整行注释兼容性差，且与 F-43 旧版注释格式一致便于人眼识读
  - **历史文件读取端向后兼容**：`SqlLogFileReader.NEW_HEADER_REGEX` 升级为 `^--+ source: ...` / `... --+$`，可同时读 2/3 个 `-` 起结的文件（旧 3 `-` 文件仍可读，无需迁移）；`parseContent` 行首识别由 `startsWith("--- source:")` 升级为「含 source: 与 time: 关键字即视为新版」

- **SQL 历史面板两级导航（F-44-3）——默认文件列表 → 双击进文件 SQL 列表 → 双击 SQL 预览**：
  - **一级（默认视图）**：文件列表，每行 = 文件名（加粗）+ 文件大小（B/KB/MB）+ SQL 条数；空目录显示「暂无历史 SQL 文件」；搜索框按文件名过滤（emptyText「搜索文件名...」）
  - **二级（文件内容）**：双击文件进入，展示该文件逐条 SQL（沿用 F-44-2 的 SQL 高亮 + 耗时 + 时间戳 + 源码 renderer）；双击 SQL → 预览面板；右键 → 复制 SQL / 跳转源码（仅二级可用）；顶部「← 返回」回一级；搜索框按 SQL 内容/源文件过滤
  - **刷新语义**：`refresh()` 重新扫描目录生成文件摘要；正在浏览某文件且文件仍存在时保持二级视图（重载内容），否则回一级——`SqlLogPanel` tab 切换监听调 `refresh()` 不打断浏览
  - **性能**：新增 `SqlLogFileReader.countInFile(file)` 轻量条数统计（只数头部行不构建 `LogSqlEntry`，`useLines` 惰性 IO），文件列表加载避免大文件全量解析；计数与 `readFromFile` 完整解析结果一致（新增 3 个一致性断言测试）
  - **文案**：新增 `log.history.back / back.tip / files.empty / entries.empty / sqlCount / search.files` 六个中英文案

- **实时日志跳转不可靠（F-44-6 根因）**：旧 `SqlLogConsoleBridge.extractSourceLocation` 在 **IDE 控制台线程**取调用栈，栈帧只有 JDK / IntelliJ / 插件帧，永远取不到应用调用点 → `sourceFile/sourceLine` 恒为 null/0 → `jumpToSource` 退化为 `WrapperSearchService` 表名猜实体（不可靠、常落空）。改为在应用线程用 `InnerInterceptor` 捕获（见 F-44-6 Changed），实时日志现在能精确跳到触发 SQL 的 Service / Controller 行
