# 预览面板缺陷的无 GUI 复现与验证手段——调研报告

> 2026-11-03。动因＝T-PreviewConsoleOwnership 修复期间，每验证一轮都要用户关 IDE → 换 jar → 重启 →
> 手点预览/执行，四轮下来反馈周期约 40 分钟且每次都要打断用户。本文回答「能不能不靠 GUI 复现和验证」，
> 结论来自 243 平台字节码反编译 + 本仓现有测试基建盘点。

## 一、先划清边界：为什么之前的单测抓不到

`BasePlatformTestCase` 跑的是无头平台，**没有 Database 工具窗、没有 Services 视图**。
而本轮几个缺陷的触发源恰恰在那边：

- 结果组件被重挂回 `ServiceViewComponentWrapper`；
- 结果页签跨预览残留（DBN 复用同一个 `RunnerLayoutUi` 内容面板）；
- 折叠被回收守卫写回 160px。

前两条都是**平台侧异步行为**，测试里没人触发它，所以单测"绿"与真机"红"可以同时成立。
不是单测没用，而是**缺一个能触发平台行为的入口**。

## 二、反编译结论：重挂的确切触发点（243 `DatabaseTools/lib/database-plugin.jar` + `lib/app-client.jar`）

### 2.1 谁把组件挂进 `ServiceViewComponentWrapper`

`com.intellij.database.console.DatabaseServiceViewContributor$BaseViewDescriptor.getContentComponent()`：

```java
public JComponent getContentComponent() {
    if (!isValid()) return null;
    if (myContentComponent == null) {
        LogView<?> view = getView();
        if (ServiceViewUIUtils.isNewServicesUIEnabled()) {
            view.getUi().getOptions().setTopLeftToolbar(getToolbarActions(), "ServicesToolbar");
        }
        myContentComponent = new ServiceViewComponentWrapper(view.getContent().getComponent());
    }
    return myContentComponent;
}
```

### 2.2 包装即抢占

`com.intellij.execution.services.ServiceViewComponentWrapper` 的构造器只有一句：

```java
public ServiceViewComponentWrapper(JComponent component) {
    super(new BorderLayout());
    add(component, "Center");     // ← AWT 立即把 component 从旧父（我方 JSplitPane）摘除
}
```

`JSplitPane.remove()` 会把 `rightComponent` 置 null —— 这就是「面板下半区突然空白」的全部机制。

### 2.3 结论：这不是随机事件，是可精确触发的

- `myContentComponent` **按 descriptor 实例缓存**，所以「重挂」发生在**每新建一个 descriptor** 时；
- descriptor 由 Services 视图重建产生：`refreshView(project)`、session 事件、`selectNode(...)` 等；
- 也就是说：**只要能让平台再建一次 descriptor，就能在测试里 100% 复现重挂**，不需要 GUI。

### 2.4 旁证：还有一个「把节点从服务视图摘掉」的 API

`DatabaseServiceViewContributor.extractNode(project, client)` → `ServiceViewManager.extract(client, 本贡献者)`
——语义是把节点**抽出成独立工具窗**，不是"静默移除"。目前不采用（会把控制台弹到另一个窗口），
但说明「让服务视图不再持有该节点」在平台侧是有路径的，将来若要彻底消除抢组件可以沿这条线再挖。

## 三、三种无 GUI 手段（可行性 / 覆盖 / 成本）

| 手段 | 跑在哪 | 覆盖什么 | 单次成本 | 现状 |
|---|---|---|---|---|
| **A. 平台级真实触发** | `testDatabase` 通道（真实 DBN + 真实 MySQL + 真实 `attachConsole`） | 平台重挂、结果页签复用、执行链时序 | ~2 分钟/类 | **实测不可达**：descriptor 的 `isValid()` 在 headless 恒 false，`getContentComponent()` 直接返回 null（见第四节证据） |
| **B. Swing 级组件树不变式** | 普通 `test`（无头，秒级） | 归属判据、折叠/最小高度、回收守卫、装配口 | 秒级 | 已落地 10 例（`PreviewEditorAssemblyKeepsConsoleTest` / `PreviewResultIsolationTest` / `ConsoleStealRemountTest`），**抢走夹具已改用平台真实类** |
| **C. runIde + 自动化 GUI** | 真 IDE 沙盒 | 像素级视觉 + 依赖"可见会话"的时序 | 分钟级 + 许可/焦点约束 | 仓库已有 skill：`ide-ui-acceptance`（robot-server + 图像锚点），助手可自跑、不需用户 |

**修正后的组合**：B 管不变式（每次改都跑，秒级）→ C 管时序与视觉（助手自己跑 runIde）→ 用户只在收尾看一次。
A 方案在本仓不具备可行性（`isValid()` 门），不要在这条路上继续投入。

## 四、A 方案实测：headless 下走不通（已证伪，记录证据）

按第四节的设计在 `DbConsoleIntegrationTest` 里加了一条原型用例（`prepareConsole` 后反射取
`DatabaseServiceViewContributor.getServices(project)` → `getServiceDescriptor(...)` → `getContentComponent()`）。
**实跑结果：`content=null`**——

```
[DB-IT] 平台重挂探针: content=null, splitBottom=com.intellij.ui.content.impl.ContentManagerImpl$MyNonOpaquePanel
```

原因在反编译里写得很清楚：`getContentComponent()` 的**第一行**就是 `if (!isValid()) return null;`。
headless 没有 Database 工具窗、会话不算"可见"，descriptor 恒 invalid，于是：

- 包装器不会被创建 → **平台重挂路径在 headless 下根本不可达**；
- 这也解释了为什么前几轮单测怎么改都复现不出"真机红"。

副作用（同样重要）：这条原型用例挂在 `DbConsoleIntegrationTest` 的共享夹具上跑，会把后面 5 条
UI016 用例连坐成 `JdbcConsole has already been disposed`（一次运行 10 例 6 红，基线是 9 例 1 红）。
**结论：不要在共享 DB 夹具里加这种会重建控制台的用例**；真要做，必须独立成类并登记进
`buildSrc/src/main/kotlin/mpv-testing.gradle.kts` 的 `dbIntegrationTaskSpecs` + `dbIntegrationClasses`
两处清单，同时自己做隔离。

原型已撤回（文件回到提交态），本节留作证据与警示。

## 五、修正后的推荐

| 层 | 手段 | 覆盖 | 谁来跑 |
|---|---|---|---|
| 不变式 | B：真实 `ServiceViewComponentWrapper` + 真实组件（本仓已落地） | 归属判据、折叠/最小高度、回收守卫、装配口 | 每次改动，秒级，CI 可跑 |
| 平台时序 / 视觉 | C：`runIde` 沙盒 + `ide-ui-acceptance` skill（robot-server 图像锚点） | 真 IDE 里的工具栏文案、布局比例、执行后面板 | 助手自己跑，**不需要用户** |
| 最终验收 | 用户看一眼 | 主观可用性 | 收尾一次 |

**关键更正**：原以为"A 方案（testDatabase + 平台真实触发）能覆盖时序"，实测证伪——
descriptor 的 `isValid()` 门把 headless 路径挡死了。所以时序类问题只能靠 C（自动化 runIde），
好在 C 也不需要用户操作，只是比 B 慢一个数量级。

## 六、本轮已经落地的升级

`ConsoleStealRemountTest` 的"抢走"夹具从 `JPanel` 换成**平台真实类** `ServiceViewComponentWrapper`
（构造即 `add(component, "Center")`），与 DBN 服务视图的抢占路径逐字一致——不再依赖"我自己造一个
父容器"的近似模拟。

## 七、结论

1. **可以不靠 GUI 复现**：平台重挂的机制已被反编译锁定（descriptor → wrapper → add）；
2. **但 headless 只能到"组件树不变式"这一层**：`isValid()` 门使真实重挂路径在测试里不可达，
   时序类问题必须用自动化 runIde（C）；
3. **用户从"每轮都要重启复现"降为"收尾看一次"**：B 覆盖逻辑、C 覆盖时序与视觉；
4. 下次同类问题的第一步仍是**反编译找出"平台在哪一行改动了我的组件树"**，再决定用 B 还是 C 复现——
   比反复重启 IDE 快一个数量级。
