**券 C 的登记工作阻塞**：`StatementWeaverVendorCoverageTest` 的字节层校验必须直读真实类字节，

## 二、已证实的事实

### 2.1 驱动类名 `org.panweidb.Driver`（四个独立来源，含用户栈）

| 来源 | 原文 |
|---|---|
| 用户报障栈（计划 §一 来源） | `org.panweidb.Driver`、`org.panweidb.util.PSQLException` |
| bboss（Apache-2.0，`bboss-persistent`）`DBFactory.java:61,134` | 注释 `org.panweidb.Driver`；`adapters.put("org.panweidb.Driver", DBPanwei.class)` |
| bboss `DBPanwei.java` | `public class DBPanwei extends DBPostgres {}`（空实现，直接复用 PostgreSQL 适配器） |
| qhsword/nacos-plugins `nacosplugin-datasource/installation.MD:231-243` | `db.pool.config.driverClassName=org.panweidb.Driver` |
| DBeaver / Smartbi 接入文档（web 检索命中） | 驱动类 `org.panweidb.Driver`，默认端口 17700、默认库 `postgres` |

`DBPanwei extends DBPostgres` 这条是第二重的谱系证据——bboss 认为磐维的做法与 PostgreSQL 完全一致。

### 2.2 URL 子协议是 `jdbc:panweidb:`（P-2 只要确认键名，已确认）

nacos-plugins 原文（可复现的最小证据）：

```properties
db.url.0=jdbc:panweidb://localhost:15432/dbname?currentSchema=nacos&reWriteBatchedInserts=true
db.pool.config.driverClassName=org.panweidb.Driver
```

`currentSchema` 与 `reWriteBatchedInserts` 都是 pgjdbc 的参数名，端口 15432 是 openGauss 默认口；
cnblogs 实机示例是 `jdbc:panweidb://192.168.3.26:17700/testdb`，DBeaver/Smartbi 文档写默认 17700。
**端口不唯一，但子协议唯一**——券 F 两个键 `panwei` / `panweidb` 都登记仍是对的（保守），主键按
`panweidb` 走。

### 2.3 谱系：openGauss 系商业发行版，驱动是整包重定位

官方文档（中国移动开放平台，PDF 下载可通）《磐维数据库 V2.0-S3.0.0_Beta 应用程序开发指南》第 4 章：

- §4.1.1：「PanWeiDB V2.0-S3.0.0_Beta JDBC **基于 openGauss-connector-jdbc**」，jar 名
  `panweidb_jdbc_$version<v|p>_$buildtime.jar`（§4.3.1 的 CLASSPATH 示例是
  `/usr/local/panweidb/java/panweidb-2.0_2021072214.jar`）
- §4.2 接口名沿用 PG：`org.postgresql.PGConnection` / `org.postgresql.PGStatement`
- §4.4.2 明写两套驱动类并存：`"cn.com.panweidb.Driver"` 与 `"org.postgresql.Driver"`

另一独立来源（Zhh9126/backup-platform `core/engines/panwei.py` 文件头注释）：「磐维（PanWeiDB，
中国移动 × 华为，**openGauss 系商业发行版**）……gs_dump / gs_restore / gsql 与 openGauss 同名同用法」。

合起来看，磐维驱动存在**至少两代、三种驱动类名**：

| 代号 | jar 名 | 驱动类（文档口径） |
|---|---|---|
| V1（用户环境） | `panweidb-jdbc-1.0.0.jar` / `panweidb-jdbc-2.0.0.jar` | `org.panweidb.Driver`（DBeaver/Smartbi/bboss/nacos 一致） |
| V2 分发包 | `panweidb_jdbc_<v\|p>_<buildtime>.jar`、`panwei-client-2.0.0.jar` | `cn.com.panweidb.Driver`（官方 PDF §4.4.2） |
| V2 文档示例 | 同 V2 | `org.postgresql.Driver`（§4.2/§4.4.3，疑为照抄 openGauss 文档） |

用户栈是 `org.panweidb.Driver` + `org.panweidb.util.PSQLException`——`util.PSQLException` 这个类名在
pgjdbc 是 `org.postgresql.util.PSQLException`、在社区 openGauss 2.x/3.x 是
`org.opengauss.util.PSQLException`。名同位置同、只换包——**这是整包重定位（rename）的指纹**，
不是「加个 Driver 别名」的形态。这条判断直接决定落地范围，见 §三。

## 三、为什么现在不能登记（禁猜类名的具体缺口）

`StatementWeaverVendorCoverageTest` 的字节层用例读的是 **classpath 里的真实驱动类字节**
（`resourceBytes(...)` → `StatementWeaver.weaveSpec` → 隔离子 loader 定义 + 初始化过 JVM 校验），
本项目 12 家厂商的 jar 全部由 agent 子项目 `testImplementation` 从 Maven 仓库解析
（`sub-projects/sql-visualizer-agent/build.gradle.kts:115-145`）。磐维不在任何仓库，没有字节可读。

缺口的准确位置是两个互斥形态的判别，猜错会让修复「看着登记了、实际一条不出」：

| 形态 | jar 内条目特征 | 需要的改动 |
|---|---|---|
| A. 整包重命名（用户证据支持） | `org/panweidb/jdbc/*` 有类、`org/postgresql/*` 为 0 | connect 面 + 语句面（`org.panweidb.jdbc.Pg*`）+ prepare 面（`org.panweidb.jdbc.PgConnection`） |
| B. 保留 PG 包、只加 Driver 别名 | `org/panweidb/*` 只有 Driver、`org/postgresql/jdbc/Pg*` 齐全 | 只加 connect 面 `org.panweidb.Driver`（语句面/prepare 面已被现有 `org.postgresql.*` 覆盖） |

判别只需一条读数：`unzip -l <jar> | grep -c 'org/postgresql/jdbc'` 与
`unzip -l <jar> | grep -c 'org/panweidb/jdbc'`。**没有这条读数就不该写代码。**

## 五、拿到 jar 之后的落地清单（已对齐现有代码锚点）

1. **先出两条读数**（决定走 A 还是 B 形态）：
   `unzip -l panweidb-jdbc-*.jar | grep -c 'org/panweidb/jdbc'`、
   `... | grep -c 'org/postgresql/jdbc'`、
   `javap -p -classpath <jar> org.panweidb.jdbc.PgPreparedStatement`（execute 族 + setXxx 族描述符）。
2. `DriverRegistry.java` 静态块加 connect 面：`s.add("org.panweidb.Driver")`；V2 若确认另有
   `cn.com.panweidb.Driver` 一并加。厂商前缀 `org.panweidb.` 取两段即可，**不需要**进
   `THREE_SEGMENT_VENDORS`（次段 `panweidb` 已唯一标识厂商，与 `org.postgresql.` / `org.opengauss.`
   不互相包含）。
3. `WeaveSpecs.java`：A 形态则在 `statementFace` 组尾加 `org.panweidb.jdbc.PgStatement` /
   `PgPreparedStatement`（Callable 视 javap 继承链决定是否单列，openGauss 3.0.0 的
   `PgCallableStatement` 是本族同名类，pgjdbc 系一律继承 `PgPreparedStatement` 故通常不单列）；
   `prepareFace` 组加 `org.panweidb.jdbc.PgConnection`。
4. `StatementWeaverVendorCoverageTest.java`：`STATEMENT_FACE_CLASSES` / `PREPARE_FACE_CLASSES`
   同步加组（`名单漂移_SPECS每个类都必须进测试数组或显式排除` 会强制），并把该组加入
   `JAR_OPTIONAL_BYTE_LAYER` + 一个专项用例：jar 不在位时 `Assume.assumeTrue(...)` 显式 skip 并打印原因。
5. **jar 的注入方式与现有机制不同**：测试的字节层读的是 **test classpath 资源**，不是系统属性。
   两种做法：
   - 推荐（与 12 家厂商一致）：把 jar 装进本地 Maven 仓或用 `files(...)` 引入
     `testImplementation`，走 `testImplementation(files(...))` 需连 jar 路径一起入库，违背「jar 不入库」；
   - 本券指定的做法：新增 `-Dpanwei.jar=<path>`，用例内 `JarFile` 直读条目字节后交给
     `StatementWeaver.weaveSpec`，jar 缺失即 skip。这条要新写一小段读 jar 的工具方法（现有
     `resourceBytes` 只认 classpath）。**jar 到位后按此实现，不要把它挪进 classpath**。
6. 定向测试：
   `./gradlew :sql-visualizer-agent:test --tests "*StatementWeaverVendorCoverageTest*" -Pkotlin.compiler.execution.strategy=in-process`
   （跑前过并行登记表；jar 路径经 `-Dpanwei.jar=` 传入需在 build 里透传 `systemProperty`）。

## 七、未完成项与风险

- **未完成**：券 C 全部登记代码（`DriverRegistry` / `WeaveSpecs` / 测试组）——无 jar 不写。这是计划
  §九「券 C 无 jar 不能开工」的既定路径，不是欠账。
- **风险 1（形态误判）**：若不做 §三 的条目计数就读文档照抄（把手册里的 `org.postgresql.Driver` 当成
  实际驱动类），会得出「已覆盖」的错误结论，而用户真机上 `org.panweidb.*` 一处没织上。用户栈里的
  `org.panweidb.util.PSQLException` 就是反证。
- **风险 2（版本分裂）**：V1 与 V2 的 jar 名、驱动类名、可能还有包名都不同。登记前要问清用户应用里
  的 jar 是哪一个（`WEB-INF/lib` 下的文件名足够），否则登记了 V1 的形态，用户在 V2 上依旧零产出。
- **未取证**：语句面类的具体 `execute` / `setXxx` 描述符、`PgCallableStatement` 的继承链、
  `PgConnection.getURL()` 是否 public（影响 `UrlResolver` 反射兜底）。这些都要 jar 才能出读数。

## 八、需要用户提供（两条通道，任选）

1. **首选**：应用 `WEB-INF/lib/` 下的磐维驱动 jar 本体（文件名以 `panweidb-jdbc-` / `panwei-client-` /
   `panweidb_jdbc_` 开头）。放到本机任意目录即可，测试用 `-Dpanwei.jar=<path>` 读，不入库。
2. 备选（拿不到 jar 但进程在跑）：在应用 JVM 上执行
   `jcmd <pid> VM.class_hierarchy | grep -i -E "panwei|panweidb"`，把输出贴回。
   `VM.class_hierarchy` 能直接列出 `org.panweidb.jdbc.*` 的真实类名与继承链——够用来登记，
   只是拿不到方法描述符的字节层校验，需在报告里标「未做字节层」。
