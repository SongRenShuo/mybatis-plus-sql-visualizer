# 宿主能力 EP 化与上游版本监听（F-11 方案文档）

- 日期：2026-11-06
- 分支：`t-idle-f3b`（基点 `f9743c4a`）
- 范围：宿主能力 EP 化只出方案与盘点，不改代码；上游版本监听落最小件（见 §五）
- 依据：`docs/开发计划/20261105-2350-闲时任务待办清单-开发计划.md` §一之二 F-11

## 一、问题陈述

宿主能力（IDE 平台、Database 插件、Kotlin/Diagram/MCP 等其他插件）在不在位、能不能用，目前是在业务代码里用 `Class.forName` 现探现判。这套做法能跑，但有三个持续成本：

1. **口径分散**：同一个「Database 插件在不在」的判断，`execute/`、`ui/`、`config/` 各有各的写法，判定细节（探哪个类、探不到怎么降级）逐处自定，改动面不可见；
2. **不可替换**：想换一种探测方式（例如改探 EP、改读插件描述），得改所有调用点；
3. **测试只能靠类加载器造环境**：没有统一注入缝，测「无 Database 插件」只能靠 headless 环境天然缺类。

EP 化的目标是：**把「宿主能力是否可用」收敛成一个可注册、可替换、可注入的查询入口**，而不是把 71 处反射调用一次性重写。

### C. 平台 API 形态漂移兜底（**不建议** EP 化）

`update/DynamicInstallSupport.kt:355-359`、`update/PluginVersion.kt`、`ui/gutter/MyBatisCompetitorGate.kt` 的反射是**版本适配**——2025.3~2026.2 之间平台类形态与 Kotlin 可见性反复漂移，反射是刻意的防御层。把它包进 EP 只是把漂移挪个位置，不解决问题。

### D. 已经在 EP 面的部分

`plugin.xml` 的 optional depends + config-file 已经是平台自己的 EP 模型：

```
<depends optional="true" config-file="database-optional.xml">com.intellij.database</depends>
<depends optional="true" config-file="diagram-optional.xml">com.intellij.diagram</depends>
<depends optional="true" config-file="mcp-optional.xml">com.intellij.mcpServer</depends>
<depends optional="true" config-file="acp-transport-optional.xml">com.intellij.ml.llm</depends>
```

也就是说：**「加载哪份配置」已经 EP 化了，缺的是「插件自己对外暴露一个统一的能力查询口径」**。这决定了 EP 化的落点不在 plugin.xml 的 depends，而在插件自定义 EP + 业务侧单一入口。

## 三、EP 设计草案

### 3.1 自定义 EP

```
<!-- 主 jar 的 plugin.xml（迁移期新增，需评审：plugin.xml 属冻结面） -->
<extensionPoint name="hostCapability"
                interface="cn.song.mybatisplus.visualizer.host.HostCapabilityProvider"/>
```

```kotlin
// 主 jar：接口与枚举，零宿主类型引用
enum class HostCapability { DATABASE, DIAGRAM, MCP_SERVER, ACP_TRANSPORT, KOTLIN }

interface HostCapabilityProvider {
    val capability: HostCapability
    fun isAvailable(): Boolean
}
```

```
<!-- database-optional.xml：只有 com.intellij.database 在位时才加载本文件 -->
<hostCapability implementation="cn.song.mybatisplus.visualizer.host.DatabaseCapabilityProvider"/>
```

```kotlin
// 业务侧唯一查询入口（内部 EP 遍历 + 结果缓存）
object HostCapabilities {
    fun isAvailable(capability: HostCapability): Boolean
    fun invalidate()   // 动态卸载/插件启用状态变化时清缓存
}
```

关键约束：**provider 实现类只能放在 optional config-file 里**。接口不暴露任何 `com.intellij.database.*` 类型，主 jar 编译期依赖图不变（这是本仓既有的「反射隔离红线」，`execute/DataSourceSettings.kt:12` 的注释即此约定）。

### 3.2 保留反射的场景（不 EP 化）

- C 类（平台 API 形态漂移兜底）：版本适配问题，EP 化无收益；
- `AcpTransportRegistrar` / `McpGateFilterEpBridge` / `McpToolsetDynamicRegistrar`：这些是在**动态注册别人的 EP**（`ExtensionPointName.create<Any>` + 擦除泛型），属于「往宿主 EP 里塞扩展」，与「查询宿主能力」不是一件事，不并入本方案。

### 3.3 分阶段迁移

| 阶段 | 内容 | 判据 |
|---|---|---|
| P0 | 只加 `HostCapabilities` 入口 + Database provider，`ExecuteSqlSupport.isAvailable` 改为「EP 优先、探不到回退 `Class.forName`」 | 状态栏 tooltip / 设置页「执行需 Ultimate」文案零变化；双判不一致时打点 |
| P1 | `execute/` 的 database 面 36 处收敛到入口 | 每处迁移带对照测试（EP 有/无 provider × 类在/不在 四格） |
| P2 | `sql/` 面 14 处（`IdeaSqlContextBridge` 等）收敛 | 同上；注意 `sql/` 属还原链邻域，改动需走定向回归 |

P0 之前不动任何调用点——这是本方案与「一次大重构」的分界。

## 四、迁移风险

1. **EP 可用时机**：`ExtensionPointName.getPoint(null)` 在插件加载完成前不可用，早期调用点（应用级静态初始化、headless 测试）会拿到空列表。必须 fail-open（不可用视为「能力未知」，回退现有探测），不能把空列表当「能力不存在」。
2. **optional config-file 的加载条件与反射探测可能分叉**：插件在位但类被裁剪（Ultimate 的精简发行、插件禁用但目录残留）时，EP 判「在」而反射判「不在」。迁移期保留双判 + 不一致打点，读数稳定后再拆。
3. **反射隔离红线**：provider 接口一旦泄漏宿主类型，主 jar 就需要编译期依赖，Community 版直接加载失败。这条是硬约束，评审时必须看接口签名。
4. **测试面**：现有测试大量依赖「类加载器里没有这个类」来造降级路径；收敛到入口后必须保留注入缝（`HostCapabilities` 可替换实现），否则测试只能整类重写。
5. **动态卸载/启用**：provider 随插件卸载消失，缓存必须失效。本仓已因 `DynamicPlugins` 相关问题踩过坑（`update/DynamicInstallSupport.kt`），缓存失效要挂在插件状态变化事件上，不能只靠进程生命周期。
6. **收益边界**：EP 化解决的是「能力发现」的口径与可替换性，不解决「能力调用」的 API 漂移。别指望一次迁移减少反射总量——C 类（形态漂移兜底）占比不小且应当保留。

## 五、本件落地：上游 MyBatis 版本监听（最小件）

代码：`src/main/kotlin/cn/song/mybatisplus/visualizer/update/UpstreamVersionMonitor.kt`

| 面 | 实现 |
|---|---|
| 读版本 | `META-INF/maven/<group>/<artifact>/pom.properties` 的 `version`；缺失时回落到锚点类所在 jar 的 `Implementation-Version`（Manifest 折行按规范拼接）。探 `mybatis-plus-core` / `mybatis-plus-extension` / `org.mybatis:mybatis` |
| 比对 | 项目级 `PropertiesComponent`（键 `mybatis.upstreamVersion.snapshot`）存上次快照；`artifact=version` 按 artifact 排序拼接，同集合逐字可比 |
| 提示时机 | **变化才提示**；首次探测（无记录）静默登记；本次探不到（环境抖动）静默且不覆盖记录 |
| 通知 | 复用既有 `cn.song.mybatisplus.visualizer.updates` 通知组（不新增 EP、不动 plugin.xml），INFORMATION，一次变化一条 |
| 可关 | `UpstreamVersionMonitor.NOTIFY_ENABLED` 常量关（设置三件套本件冻结，不接 UI） |
| 接线 | `StartupUpdateCheck.execute` 开头一次 `runCatching { UpstreamVersionMonitor.checkOnce(project) }`，放在 `autoCheckUpdate` 开关判定**之前**（上游版本与插件自更新是两件事） |

**已知边界（如实登记）**：探测走插件类加载器。IDE 运行时项目依赖的 mybatis jar 通常不在插件类加载器视野内，此时返回空列表并静默——不误报、不造噪音。要覆盖项目依赖面需接 `ProjectFileIndex`/`Library` 扫描，属后续项。

## 六、零行为变更声明

本件**不改动任何宿主能力判断路径**：§二列出的 71 处 `Class.forName` 调用一行未改，`ExecuteSqlSupport`、`DataSourceSelectorConsole`、`DialectPreMapping` 等行为与基点逐字一致。新增的只有一次只读版本探测 + 一次项目级属性写入 + 条件性的通知。
