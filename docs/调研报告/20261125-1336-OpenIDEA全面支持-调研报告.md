# OpenIDEA 全面支持调研报告

- 日期：2026-11-25
- 对象：OpenIDEA（`l0ng-ai/openidea`，main @ `a7b67347c`；本机安装版 0.1.51，随附插件 API 1.15）
- 被移植方：MyBatis-Plus SQL Visualizer（IntelliJ 平台 Kotlin 插件，613 个 Kotlin 文件 / 17 万行 / 201 条功能）
- 分册：`docs/调研报告/20261125-openidea-support/`（00 基线 + 01~10 共 10 份）

## 第 1 章 结论

### 1.1 一句话

OpenIDEA **能承接**这个插件「SQL 渲染、静态校验、日志还原、生成与转换、MCP 工具」这条主干的大部分能力，**但不能承接**「基于 Java 类型推断的精确渲染与导航」——因为 1.x 的插件 API 明确没有 PSI、没有类型/成员查询，且禁止插件向语言服务器发 `textDocument/*`。**1:1 全功能复刻在当前 API 下不成立**，目标应改为「主干 1:1、类型推断降级、平台独占项不迁」。

### 1.2 五个一级约束（每条都有源码级证据）

| # | 约束 | 证据 | 影响面 |
| --- | --- | --- | --- |
| 1 | 没有 PSI / 跨语言语义模型 | `docs/zh/contribute/architecture/code-intelligence.mdx`；`plugins/README.md`「Type resolution and member queries remain deferred to the asynchronous API 2.0 model.」 | Wrapper 链判型、实体字段推导、JPA 继承、JdbcTemplate 变量追踪 |
| 2 | 插件拿不到 LSP 的语义答案 | `wit/host.wit` 的 `language-servers`：只放行服务器自有方法，`textDocument`/`workspace`/`typeHierarchy` 等首段一律 `invalid` | 同上；「借 JDT LS 解类型」这条路被堵死 |
| 3 | `database` 接口不能执行 SQL | `wit/database.wit` 只有 upsert/remove/sources/set-credential/connect；IDE 自己的 `ide-db` 有能力但未暴露给 WIT | EXPLAIN、预览执行、schema 元数据、影响行数试算 |
| 4 | 插件读不到运行控制台输出 | PR `#5361`（console commands）仍 open；`set-console-rules` 只让插件着色、不让读文本 | 控制台日志链（F114 及其下游）整体失效，捕获只剩 `java.agent` |
| 5 | API 处于 preview，组件预算很紧 | 已发布 1.15；命令/事件 5 s、`tasks` 后 60 s、provider 50 ms 软 / 500 ms 硬、内存 256 MiB、无长驻线程 | 重解析必须自建缓存；全项目扫描只能进 task 并周期续期 |

### 1.3 四档总账

统计口径：08 分册的 201 条功能（F01–F201）。判档标准见 `00-README.md` 末节。

| 档位 | 条数 | 占比 | 代表条目 |
| --- | ---: | ---: | --- |
| 现成可做（接口已具备，仅需按新形态重写实现） | 待汇总 | — | XML/注解/iBatis 渲染、方言与格式化、日志解析与还原、生成与转换、MCP 纯逻辑工具、设置/通知/图标/双语 |
| 变通可做（无直接接口，可组合达成或有精度损失） | 待汇总 | — | Wrapper 渲染、Mapper 导航、inlay、预览工作台、EXPLAIN（外挂）、javaAgent 捕获 |

### 1.4 推荐路线（三轨并行）

| 轨 | 内容 | 理由 |
| --- | --- | --- |
| A 主干重写（Rust wasm） | XML/注解/iBatis 动态 SQL 渲染、方言体系、日志解析、生成/反向/回滚、性能规则、设置与双语、MCP 工具 | 这批 08 分册判定为「核心引擎 16 包 26,168 行」里平台无渗透的部分，逻辑可逐条翻译，收益/风险比最高 |
| B 外挂 sidecar | Wrapper 链 → 中间模型、EXPLAIN、schema 元数据、可选 attach | 用 `process:java` 走既有范式（`izzyjere.jpa-powertools` 已验证）；渲染引擎可先以 JSON 契约复用现有 Kotlin 逻辑，逐步 Rust 化 |
| C 上游提案 | `database.execute`/`explain`、只读的类型/成员查询、控制台输出订阅 | 1.x 只加不改，通用能力（非 MyBatis 领域）比领域能力更可能被接受；PR `#1300`（MyBatis 能力进宿主）closed 是领域路线的反证 |

## 第 2 章 平台事实

### 2.1 它是什么

不是 IntelliJ 平台的分支，而是 **Tauri 2 桌面壳（Rust）+ React/CodeMirror 6 前端 + wasmtime 插件引擎**。Rust 侧 `ide-host` 是不依赖 UI 工具包的 IDE 后端，47 个功能 crate 分领域实现；同一份后端在远程开发时以 `openidea-server` 形式跑在项目所在机器。Java 智能来自 JDT LS（另有 0.1.49 起的可选 `java-analyzer`），Kotlin 仅由 `kotlin-bridge` 桥接编译产物（明确不含精确源码导航与重构）。

版本要分三层看：

| 层 | 值 | 证据 |
| --- | --- | --- |
| main 开发版 | 1.16.0 | `wit/plugin.wit:11` |
| 已发布快照 | 1.15.0 | `sdk/rust/openidea-plugin/tests/api/released/plugin.wit:1` |
| 本机 0.1.51 随附 | 1.15.0 | `git show v0.1.51:wit/plugin.wit` |

线上文档站（`openidea.sh/zh/plugins/api`）仍写 1.7.0 / 已发布 1.6.0，仓库内 `plugin-host.mdx` 也还写 1.7.0——**文档滞后于 tag，一切以 `wit/` 与 tag 为准**。新仓 `engines.openidea` 从 `^1.15` 起声明。

### 2.2 插件模型与沙箱

插件 = 带 `plugin.toml` 的目录；有代码时是一个 `wasm32-wasip2` 组件（component model + WASI preview 2）。每个插件一个 wasmtime `Store`、一个 actor 线程，**同一实例串行执行、从不并发**；无预打开目录、无环境变量、无继承 stdio、无直连网络，WASI 只给时钟与随机数。

| 限额 | 默认值 |
| --- | --- |
| 单次调用 fuel | 5·10⁹ wasm 指令 |
| 命令 / 事件 / 激活 / 停用 | 墙钟 5 秒 |
| 调用 `tasks.begin` 后 | 60 秒（每次 `report` 续期） |
| 编辑器 provider | 软 50 ms（超时结果丢弃）/ 硬 500 ms（中断） |
| 格式化 | 5 秒 |
| 线性内存 | 256 MiB |
| 常驻子进程 | 每插件最多 8 个，stdout/stderr 流式可到 128 MiB |
| 崩溃 | 连续 3 次标记 Failed；空闲 300 秒回收 |

证据：`docs/zh/contribute/architecture/plugin-host.mdx`（取值源 `crates/ide-plugin/src/types.rs`）。

### 2.3 语义来源四层

| 层 | crate | 提供 | 对插件可见性 |
| --- | --- | --- | --- |
| LSP | `ide-lsp` | 补全、跳转、用法、悬停、诊断、重命名、格式化、inlay、语义 token | **不可直接查询**（`textDocument/*` 被禁） |
| IDE 索引 | `ide-index` | 文件与符号（tree-sitter 标签，redb 持久化，nucleo 模糊匹配） | `Project::symbols(query, limit)`，只给 name/kind/container/location |
| tree-sitter 结构 | `ide-language`/`ide-syntax` | 大纲、折叠、语法错误、作用域、结构化范围 | 不直接暴露 |
| 插件 provider | `ide-host::plugins` | 补全/定义/行标记/悬停/inlay/语义 token/诊断/索引器 | 这是插件唯一的「主动贡献」面 |

### 2.4 IntelliJ 扩展点 → OpenIDEA 等价物

| IntelliJ 面（本插件用量） | OpenIDEA 对应 | 差异 |
| --- | --- | --- |

| `codeInsight.inlayProvider` | `inlay-hints-provider` | 只 text/parameter/other 三档，无自定义背景色 |
| `completion.contributor`（7 注册） | `providers.completion` | 结果后置追加到 LSP 结果之后 |

| `resource-bundle`（1,557 键 ×2） | 包内 `locales/<tag>.json` | 机制不同，需重建键表 |

### 2.5 竞品实证（决定「什么真的能做」）

| 事实 | 证据 | 含义 |
| --- | --- | --- |
| 上游拒绝把 MyBatis 能力放进宿主 | PR `#1300`「mapper navigation, generation, @Param support and SQL log conversion」**closed 未合并**；作者随后发布 `qtvbwfn.mybatis-duo` | 领域特性只能做插件；也说明导航已商品化 |

### 2.6 与宿主既有能力的重叠（决定「什么已不该算我方优势」）

| 宿主已有能力 | 证据 | 对我方功能的影响 |
| --- | --- | --- |
| MyBatis mapper XML 内的 SQL 智能 | PR `#3641`「SQL in MyBatis mapper XML」**已合并**：`<select>/<insert>/<update>/<delete>/<sql>` 获得按数据源方言的 SQL 着色、表列补全、`Unable to resolve` 检查、跳转到 Database 工具窗、Quick Documentation（依赖 #3638 的 SQL resolution scopes） | F190（注入语言）与 F189（XML 表列补全）的一部分已被宿主覆盖；**不能再当作差异化卖点**，我方价值必须落在「渲染出可执行 SQL」而不是「着色/补全」 |
| 插件可声明嵌入语言区间 | `wit/injections.wit`（API 1.4）+ `plugins/README.md:1741-1776`：插件实现 `Injections`，声明 `kinds=["injections"]`，宿主用嵌入语言的解析器着色，并把补全/悬停/诊断等路由给该语言的插件 provider | F190 的「着色 + provider 路由」变通可做；但 `typedHandler`（`#{}` 自动闭合并、成对退格）、自定义 `IElementType` 词法、拼写豁免仍无对应 |
| 内置 MCP Server 与 git/终端/运行等 | `crates/ide-mcp`、`ide-run`、`ide-terminal` | MCP 工具集走 `contributes.mcpTools` 即可被内置 Server 暴露，无需自建服务 |
| 符号索引里其实有字段与形参，但插件看不到 | `crates/ide-language/queries/java/outline.scm`：`field_declaration → @def.field`、`constant_declaration → @def.constant`、`method_declaration … parameters: (formal_parameters) @detail`；而 `workspace.wit` 的 `symbol-info` 只有 `name/kind/container/location` | **实体字段名可拿（按 container 限定查询 `symbols("User.")`，`crates/ide-index/src/matching.rs:520-535` 支持 `.`/`#`/`::` 分隔）**；字段类型与方法形参被 `detail` 捕获但未暴露——类型推断仍需文本解析或 sidecar。这是我方向上游要「暴露 detail」的最佳理由 |
| 宿主托管 WebSocket | `wit/io.wit` 的 `net.websocket-connect`（API 1.6 起，`v0.1.51` tag 内已含）：项目绑定、每插件最多 8 条、loopback `ws://` 允许、配 `on-event:websocket-ready` + `drain` | SQL 捕获的 agent→插件通道有正规解：**agent 侧改造成 loopback WebSocket 服务端**，插件消费；不必用裸 TCP，也不必用 `ipc`（Windows 命名管道 + Java 需 JNA，跨平台差） |

## 第 4 章 技术选型（依据分册 03）

### 4.1 三轨总览

| 轨 | 承担什么 | 延迟量级 | 权限代价 | 结论 |
| --- | --- | --- | --- | --- |
| A. wasm 内文本 + 宿主索引 | 即时路径：gutter 判定、XML/注解/iBatis 解析、方言/规则/生成、日志还原、设置与 MCP 纯逻辑 | 微秒–毫秒级，受 50 ms provider 预算约束 | 只需 `project.read`（低危） | **主干首选**，覆盖 98 条现成档 |
| B. JVM sidecar（`process:java`） | Wrapper 链 → 中间模型、SQL 渲染复用、EXPLAIN、schema 元数据、可选 attach | 首次启动 0.3–1.5 s（JVM 冷启），之后常驻调用毫秒级 | 高危：`process:java`，且程序哈希钉住 | **默认外挂方案**，覆盖 83 条变通档里最重的一批 |
| C. 纯 Rust 重写引擎 | 长期替代 B 的渲染与解析 | 微秒级 | 无额外权限 | 长期路线；`sqlparser-rs` 缺达梦/金仓方言，MyBatis 动态 SQL 无成熟 crate，短期不划算 |

### 4.2 即时路径（wasm）怎么做到 50 ms 内

宿主 provider 软预算 50 ms、硬 500 ms，且每次调用都传整份文档文本。可行设计：

1. 首次进入某文档：立即返回空结果（不阻塞编辑器），同时 `tasks.begin` 在后台解析全文档，结果进内存缓存（键＝`path` + `version`）。
2. 后续调用：`version` 未变则直接用缓存切片；变了则只重解析受影响行区间（按 XML 标签 / 方法体边界切块）。
3. 跨文件信息（实体注解、namespace）走 `Project::symbols` 的 container 限定查询（`symbols("User.")` 可列字段名）与 `read-file`（含未保存内容），结果带 TTL 缓存。
4. 解析器用 tree-sitter 的 Java/XML/SQL 语法（宿主已内置，插件可自带 wasm 编译版），避免自己写词法器。

### 4.3 sidecar 三方案对比

| 维度 | jar + 项目/系统 JDK（默认推荐） | GraalVM native-image | 纯 Rust 重写 |
| --- | --- | --- | --- |
| 复用现有引擎 | 高（26,168 行零改动，替换 `Project` 形参后上限 72–80%） | 同左，但需 native-image 兼容改造（反射/动态代理要配置） | 低（全部重写） |
| 分发 | 一个 jar，随包 | 3–4 个平台的可执行文件 | 无额外产物 |
| 启动 | JVM 冷启 0.3–1.5 s，可常驻 | 数十毫秒 | 无进程 |
| 授权体验 | `process:java` + 程序哈希钉住；**JDK 升级后需重新批准** | 同左（每次发版换哈希都要重批） | 无 |
| 许可 | JSqlParser 双许可，选 Apache-2.0 分支即可 | 同左 + 静态链接需确认 | `sqlparser-rs` Apache-2.0 |
| 风险 | JDK 不在 PATH、用户 JDK 过老（需 11+） | 构建链复杂、包体大 | 方言覆盖不足（无 DM/KingBase/H2）、动态 SQL 需自写 |

推荐：**以 jar + JDK 为默认**（复用率高、一套产物、许可简单），把「程序哈希钉住 → JDK 升级要重批」当作已知 UX 债，用两条缓解：① 声明 `process:java` 为 optional，缺失时自动降级为纯文本模式；② 在设置里允许用户指定 java 路径。GraalVM native 作为「愿意为启动速度付构建成本」时的升级项，纯 Rust 作为长期收敛目标。

### 4.4 中间模型契约

跨进程边界只传 JSON，契约沿用现有纯数据模型：

```
渲染请求  { kind: wrapper|xml|annotation|jpa|jdbcTemplate|log,
            source: {path, text, range}, entityTables: [...], dialect, params }
渲染响应  { sql, params[], confidence: exact|partial|unresolved,
            notes[], dialectWarnings[], perfIssues[] }
```

`model/`（17 文件 / 1,780 行）本来就是纯数据类，序列化成本低；`converter/` `sql/` `xml/` `reverse/` `generator/` 全在 P0/P1 复用清单里。**唯一必须重写的上游是「源码 → WrapperChain 中间模型」这一层**——现由 `psi/WrapperLocator.kt`（1,777 行，四种定位策略）+ 7 个 PSI 直连 converter 承担，约 1.97 万行。

### 4.5 复用率与重写清单

| 类别 | 规模 | 处置 |
| --- | --- | --- |
| 零改动复用（核心 16 包中的纯逻辑） | 26,168 / 41,583 行（63%） | 打成 `visualizer-core.jar`，加一层 JSON 入口 |
| 换 `Project` 形参后可复用 | 上限 72–80% | 用「路径 + 数据源连接串」自建等价上下文 |
| 必须重写 | ~1.97 万行（`psi/` 7,487 + `psi/jpa/` 6,755 + converter 直连部分） | Rust 或 Kotlin 重写「文本 → 中间模型」层 |
| 不移植 | 约 9 万行（`ui/` `execute/` `config/`） | 按 OpenIDEA 视图/设置模型重做，只搬文案与判定纯函数 |

### 4.6 「不猜」原则（防静默错 SQL）

无 PSI 时，文本启发会在复杂工程产生**结果看似正常但语义错误**的 SQL，这比报错更危险。硬性要求：

1. 每条渲染结果带 `confidence`：`exact`（注解/XML 直读、字面量确定）、`partial`（部分条件未解析，已标注占位）、`unresolved`（关键信息缺失，不给 SQL）。
2. UI 上对 `partial` 显著标注，对 `unresolved` 给「为什么解析不了 + 去哪补」的指引，不产出可执行 SQL。
3. MCP 工具同样返回 `confidence` 与 `notes`，禁止把 `partial` 当 `exact` 回给 agent。
4. Kotlin 侧明确声明边界：无精确源码语义，扩展函数/类型别名/跨语言重构不做。

### 4.7 上游提案优先级

| 优先级 | 提案 | 落点 | 理由 |
| --- | --- | --- | --- |
| P0 | `database.execute` / `database.explain`（只读 + 显式确认） | `wit/database.wit` → `crates/ide-db` → `crates/ide-plugin` 宿主端 → SDK → released 快照 | `ide-db` 已有查询能力，只是没暴露；能一次性解掉 EXPLAIN/预览执行/影响行数三条 |
| P1 | 暴露符号 `detail`（方法形参、字段类型） | `wit/workspace.wit` 的 `symbol-info` + `crates/ide-index` | `outline.scm` 已捕获 `@detail`，只差暴露；能显著提升实体字段类型精度 |
| P2 | 允许插件查询语言服务器的只读方法（hover/definition 白名单） | `wit/host.wit` 的 `language-servers` | 需改白名单策略，附带信任与预算问题，价值高但阻力大 |
| P3 | 插件声明式 JVM sidecar（免去 PATH/哈希钉住的摩擦） | `wit` 新增贡献点 + `ide-host` 装载 | 使 `process:java` 类方案产品化；阻力中等 |



## 第 5 章 体验降级与产品表达（依据分册 05/06）

### 5.1 预览工作台：弹窗消失，改「底部工具窗 + 包内网页」

宿主**不提供插件自定义模态框**，可选形态只有：底部工具窗口（声明式 tree/list/form/table/message/html）、包内 web 页、`open-content-tab` 只读编辑器页、diff 视图。因此：

| 现有面（IntelliJ） | OpenIDEA 落地 | 差异 |
| --- | --- | --- |
| 统一预览弹窗（21 处入口） | 底部工具窗 + web 页 | 从「浮层」变「停靠」，多屏操作习惯要改 |
| 参数区分组/预设/历史 | **必须**走 web 页（声明式 `form` 无分组、无逐字段提示） | 参数区是重前端，落在 web 视图里 |
| SQL 文本 / JSON 视图 | web 页或 `content-tab` | `content-tab` 只读、无富交互 |
| EXPLAIN 结果树 | `tree` 可做最小版；完整可视化需自绘 | HTML body 的 CSP 无 `wasm-unsafe-eval`、无 `blob:`，重前端只能走 web 视图 |
| JDK 侧交互（执行、Diff、分享） | web 页按钮 → 插件命令 → sidecar | 多一跳，需处理 loading/超时 |

### 5.2 gutter 与 inlay 的上限

| 项 | 事实 | 后果 |
| --- | --- | --- |
| 自定义图标 | `markerIcons` 允许包内 SVG，≤64 KiB，白名单消毒，14 px 绘制，支持 `iconDark` | 我方双色图标（`#F4EEFF` + `#4FB477`）合规，可做到「MPJ 同款」 |
| 同列拥挤 | line-marker(60) → gutter-action(65) → 索引 marker(70) 共用一条图标列 | 一行多图标会撑宽所有行；导航默认关也能减压 |
| 图标回落 | icon 名写错统一回落 `gutter-navigate` | 「两枚看起来一样」的真因是回落，不是配色 |
| inlay 样式 | 宿主统一画灰底圆角 chip，插件只给文本与浮层 | 不能做「带背景色的参数名」，只有 `type/parameter/other` 三档 |
| 刷新时机 | **无 provider 失效接口** | 设置改完不重开文件不生效（与 IntelliJ 版同一老问题），需在设置页写明 |

### 5.3 设置与快捷键

- 上限：≤200 字段、≤32 页（现有 118 字段 / 8 页，放得下）。
- `description` ≤4096 B、`example` ≤300 B 且示例**不参与翻译**。
- **不支持条件字段**（某开关打开才显示子项）与**自定义设置页**：现有设置树里依赖联动显隐的部分要摊平。
- 快捷键不能由插件录制：只能在 `keymaps` 静态声明，用户自行在 IDE 设置里改键。

### 5.4 双语

- 机制是「英文源文 → 译文」的扁平精确表，清单/视图/设置文本自动套用；**约八成可搬**。
- 带 `{n}` 占位的 318 条可用模板键；代码拼出的通知/错误文案需自建词表 + `host::locale()`。
- 插件名、描述、发行说明（marketplace 文本）**不走目录**，需单独维护中英两版。

### 5.5 捕获链的产品表达（分册 05）

| 场景 | 是否注入 agent | 产品口径 |
| --- | --- | --- |
| Application / Spring Boot / JAR Application | 是（`contributes.javaAgents`） | 默认开启，首次授权后生效 |
| 测试、Maven/Gradle 目标、Tomcat、远程 JVM | 否 | 明确不支持，引导用 Application 配置启动 |
| 控制台文本（任意运行配置） | 插件读不到 | 提供替代：运行配置勾选 “Save console output to file” + 插件 `read-file` 解析；或粘贴/选区还原 |

### 5.6 降级清单（按用户感知排序）

1. 从「gutter 一点就出浮层」变成「gutter 出图标 + 点击在底栏打开」。
2. 控制台实时日志链在非 Java Application 场景缺失，只能手动导出日志。
3. 参数区的分组/联动显隐被摊平。
4. 设置改动需重开文件才生效（gutter/inlay）。
5. 跨文件类型推断精度下降，部分结果只能给 `partial`。

## 第 6 章 发行与合规（依据分册 07）

### 6.1 从零到可装（摘要，完整 14 步见分册 07）

1. 用 **v0.1.51 的 `openidea-plugin`** 生成脚手架（`new` 只给 5 个文件：`plugin.toml`、`Cargo.toml`、`src/lib.rs`、`.gitignore`、`README.md`；**不给 CI、web、locales**），因为 SDK 依赖 tag 取工具自身版本，只有这个版本才落在 API 1.15。
2. 补 `web/`、`locales/`、`icons/`、CI、`rust-toolchain.toml`。
3. `build` → `check` → `link` 热更 → `keygen` → `pack` → `sha256` → Release → 注册表 PR（或自建索引）。
4. **`pack` 不校验组件新鲜度**，发布流水线必须「先 build 再 pack」。
5. 市场安装按 `engines.openidea` 选最新可加载版本，因此每次提升 API 需求都要新增一个 `[[versions]]`，旧版保留。

### 6.2 `check` 最易踩的五项

| 项 | 说明 |
| --- | --- |
| SDK 用 main 编 | 生成 1.16 依赖，0.1.51 用户加载不了 |
| 清单多写字段 | 未知顶层字段硬失败 |
| 能力没抬 `engines` | 例如用了 `net.http:` 却写 `^1.4`，安装即拒 |
| Vite 绝对路径 | web 页面资源路径必须相对 |
| 忘 build 直接 pack | 打进旧 wasm |

### 6.3 包体与限额

官方 MyBatis Navigator 整包 111 KB，市场最大 569 KB；硬约束为下载 256 MiB / 解包 512 MiB / 线性内存 256 MiB / 命令 5 秒。**瓶颈是内存与墙钟，不是体积**。

### 6.4 双通道发行

- 官方注册表：要求公开源码 + 开源许可 + 无混淆；审核由维护者做。
- **自建市场**：静态 `index.json` + `openidea-plugin index/merge --keep`，设置 › 插件 › 插件仓库… 填 URL；**没有开源要求**，可作闭源通道；IDE 只读一个索引，要保留官方插件就 `merge --keep` 并入。
- Gitee 重打包镜像仍可验签（digest 算解包内容），中国网络可行。

### 6.5 合规结论

| 项 | 结论 |
| --- | --- |
| 自有 Kotlin 代码迁移 | 可（自有版权，Apache-2.0 声明保留） |
| JSqlParser 5.3 | **LGPL-2.1 / Apache-2.0 双许可**，择一按 Apache-2.0；发行物附 NOTICE 并显式记录所选分支 |
| `sqlparser-rs` | Apache-2.0，与 JSqlParser 许可无冲突（若改 Rust） |
| GPL 竞品代码（`weigram.hotreload`） | GPL-2.0，不可抄 |
| 闭源 | 可，但不能上官方注册表；走自建索引 |
| MyBatis / MyBatis-Plus 商标 | 工具不打包 ORM 本体，描述里避免暗示官方关联 |

### 6.6 风险（摘要，11 条见分册 07）

1.15↔1.16 边界漂移、Gitee 作包源的可达性、审核 SLA 未知、包内 native 是否被允许执行未明确、web 视图资源懒加载缺失、`database.query` 缺口、商标检索未做、`license` 字段与实际一致性需人工核。

## 第 7 章 多仓协同与经验继承（依据分册 12，决策已定）

新仓与主仓同级并存时，采用「**新仓独立工作区 + 主仓按需加成附加目录**」；引擎以「**主仓 `engine-jar` 导出产物**」复用，不复制源码。

关键机制（均已实测）：

| 事项 | 结论 | 证据 |
| --- | --- | --- |
| 记忆隔离粒度 | 记忆目录名 = `<basename>-sha256(小写绝对路径，反斜杠分隔)[:16]`；`f:\code\java\gitee\songrenshuo\mybatis-plus-sql-visualizer` → `09474abd1ce62ee6` | 本机复算命中 |
| 附加目录是否继承记忆 | 是（不改变记忆根）；但附加目录的 `AGENTS.md` **不加载** | 分册 12 §2 |
| 全局记忆目录 | `~/.zcode/cli/memories/global/` **不会自动注入**；可靠通道是用户级 `AGENTS.md` | 分册 12 §3 |
| 继承前置 | 主仓 `MEMORY.md` 214 行 / 67,735 字符，超过注入上限（约 200 行 / 25,000 字符），当前已截断；**不瘦身则继承到残缺索引** | 本机实测 + 会话告警 |
| 技能共享 | 附加目录的技能按 basename 加命名空间；junction 是否被跟随未写入文档，标待验证 | 分册 12 §4 |

已在主仓发现的漂移证据（支持「单点 + 生成物 + CI 校验」，反对手工镜像）：`mpsv-sql-insight/AGENTS.md` 32 行 vs 主仓 98 行（缺 E1）；`LESSONS.md` L12/L13 撞号；`reviewed-through` 停在 10-27 而文件 11-25 仍在改；用户级 AGENTS 写「115 个文件」实际 129。
