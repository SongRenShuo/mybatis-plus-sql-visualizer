## 一、优势清单（带证据）

1. **运行时依赖极简**：生产依赖图只有 `com.github.jsqlparser:jsqlparser:5.3` 一项（`build.gradle.kts:130`），其余十余个 JDBC/驱动/Testcontainers 依赖全部限定在 `testImplementation`（同文件 libs.h2 / sqlite.jdbc / 各信创驱动段，注释均写明「仅测试 classpath，插件运行时零依赖不变」）。插件 jar 轻量、与用户工程类路径冲突面几乎为零，这是碾压同类插件的硬底座。
2. **可选依赖零成本降级**：五件 optional xml（`META-INF/database-optional.xml` / `diagram-optional.xml` / `kotlin-optional.xml` / `mcp-optional.xml` / `acp-transport-optional.xml`），全部「依赖在场才整文件加载」，Community 版/无 Database 插件环境自动降级（性能分析 §七已确认索引/stub EP 为 0，optional 注册面干净）。
3. **巨文件债已收口且有守卫**：dev 最大文件 `DataSourceSelectorResults.kt` 1977 行、`DataSourceSelector.kt` 1962 行，全部 <2000 行红线；`GiantFileBudgetTest`（`src/test/kotlin/cn/song/mybatisplus/visualizer/convention/GiantFileBudgetTest.kt`）对 10 个头部文件逐一定额，每条提额都在注释里写日期+理由+行数（「提额即承认现状，不是许可继续增长」）。预算文化与测试防回退意识远超一般插件项目。
4. **测试规模与守卫密度**：src/test 共 886 个文件、860 个测试类（按包分布：ui 221 / log 167 / execute 61 / sql 56 / psi 53 / mcp 41），其中 Guard/Budget 类守卫测试 58 个，含 `PluginXmlStructureGuardTest`（注册表结构守卫）、`SettingsRealityGuardTest`（设置项真实性守卫）、`ExecTempFileEdtGuardTest`、`EnhancedCaptureDefaultOnGuardTest` 等行为级守卫。测试不是装饰——UI-001、D202 等批次的修复语义均有无头钉（见 20261103 复盘 §五验证口径）。
5. **i18n 双语零缺键**：`messages/MpSqlVisualizerBundle.properties` 与 `_zh.properties` 各 1573 键，键集合 diff 完全为空；生产代码 87 处 `Bundle.message` 调用集中在设置面板，UI 文案不走硬编码字符串的主流面。错误归因文案质量在 UI-046/UI-048 五态分流后明显改善（`DataSourceSelectorResults.kt:514-586`：零源/判不出方言/未绑定/已绑定仍不可用/方言不匹配分开报，不再一律误导用户去改 Dialects）。
6. **首用即生效链完整在位**：onboarding 包四件——`OnboardingAnchorTip`（项目内首次打开含可预览 SQL 的文件弹一次性 Alt+Shift+Q 引导，零 PSI resolve、13 个 gutter 快速路径零改动，`OnboardingAnchorTip.kt:28-44`）、`OnboardingPrewarm`（fire-and-forget 方言映射预热）、`MapperProjectPrimerActivity`（nonBlocking+inSmartMode 探测）、`SqlPreviewStatusBarWidget`（常驻可见性）。P-7/P-8 批次的四个启动活动核实全部在 dev 现行代码中，首用链无需返工。
7. **发行说明质量高**：`update/preview.update.json`（2026.11.3）的 changeNotes 是用户可读的逐条修复归因（「执行 SQL 后预览面板下半区空白……结果不再只落在 Database 工具窗」），不是技术黑话流水账；`CHANGELOG.md` 更是到行号级的修复叙事（如 2026.11.2 节对 `FileDocumentManagerImpl:323-336` 写断言的根因描述），在 Marketplace 插件里属罕见水平。

## 二、劣势与风险分级清单

> P1 空：预览首开链 P1 已归 T-PerfSweep30 券01，不重复登记。

### P2-1 Gitee 更新通道结构性滞后 + 自动检查默认关闭，构成「用户到不了新版」的复合断点

- **现状证据**：`update/update.json` 停在 `2026.10.31-beta.2`（且稳定通道版本号带 `-beta.2` 后缀本身即是信号混乱），`update/preview.update.json` 已到 `2026.11.3`；`StartupUpdateCheck.kt:16-20` KDoc 明示「autoCheckUpdate 默认关——稳定版由 Marketplace 推送」，`PluginSettings.State.autoCheckUpdate = false`。
- **为什么是劣势**：从 Gitee zip 安装的用户（国内常见路径）默认收不到任何更新提示，且 Gitee 清单落后 dev 两个版本——2026.11.2/11.3 批次里正是用户报障驱动的预览执行面板五层修复与「每次省 1.7–2.0 秒」提速（CHANGELOG 2026.11.3 节），这些修复到不了 Gitee 通道用户手里。Marketplace 推送节奏是唯一替代，但 Marketplace 包（10.31）与 dev（11.3）之间同样存在窗口。`update/update.json` 属用户唯一动作（T-PerfSweep30 非目标已排除实施），本文只登记 UX 影响：**修复再快，分发链路是最后十公里**。
- **改进方向**：①update.json 收口时顺手评估稳定通道版本号去 `-beta` 后缀；②Gitee 通道用户引导开 autoCheckUpdate（首次从 zip 动态安装成功后弹一次性提示，复用 OnboardingAnchorTip 的一次性持久化形态）。

### P2-2 设置面复杂度：113 项 State + 10 个设置子页，超出普通用户认知预算

- **现状证据**：`PluginSettings.kt` State 含 113 个 `var`；`plugin.xml` 10 个 `applicationConfigurable`（1 个 tools 顶层 + 9 个子页）；`PluginSettingsPanelSections.kt` 一文件就组织 preview/tableMapping/codeGen/sqlLog(6 个 tab)/ui 等多 section。
- **为什么是劣势**：113 项默认值绝大多数合理（dialectAuto=true、replaceParams=true、formatSql=true 等出厂即好），问题不在默认值而在**发现成本**——重功能插件的设置页一旦超过一屏滚动，用户就放弃调优，等于把已实现的能力埋掉。有 searchable contributor 缓解（优势 8），但搜索只能救「知道自己要找什么」的用户。
- **改进方向**：不做减法（守卫测试已锁语义），做**场景化入口**——`SettingsScenarioGroups.kt` 已有场景分组雏形，把它从设置页内部前移到「预览面板更多菜单 → 场景预设」，用户从场景进设置而非从 113 项列表进。

### P2-3 双平台（243/262）兼容层是持续增长的维护税

- **现状证据**：`build.gradle.kts:31-77` 整段 mcpStub 桩源集（262 jar major 69 编译不了的变通）；`ChooseDataSourceTakeover.kt:76-86` 的 `displayTextInToolbar()` 平台行为反编译补洞；CHANGELOG 2026.11.2 节 `WriteIntentReadAction.compute` 重载选择（「按 243~262 两平台方法集交集选重载，避免 262 上 NoSuchMethodError」）。
- **为什么是劣势**：每个新功能都要过一遍「243 基线 + 262 前沿」双闸，反射桥、桩源集、平台行为注记在持续累积；T-Exec262ReadLock/T-PreviewDocPersistLock/T-Exec262ReadLock 三批 262 硬抛全是这一面。风险不是某单点 bug，而是**兼容面复杂度与团队测试矩阵（双 runIde 基准）的长期成本**。
- **改进方向**：维持现状可行（since-build 243 是用户面优势），但建议给兼容层立登记表（哪个文件哪个反射桥对应哪个平台差异），现在散在各文件注释里，新人接手成本高。归档性质，低紧迫。

### P3-1 测试基座的假绿形态已知但覆盖面有限

- **现状证据**：CHANGELOG 2026.11.2 自证「BasePlatformTestCase 整个测试体被 runWriteIntentReadAction 包住，写意图恒在，断言恒过」——写安全类断言在此基座上结构性偏松；性能分析 §五确认 src/test 对 IndexNotReady/DumbMode 点击链 grep 零命中（归券02 补）。
- **为什么是劣势**：860 个测试类的规模优势会被基座假绿侵蚀——「绿」不等于「对」，尤其 EDT/写安全/dumb 这三类平台时序面。
- **改进方向**：除券02 的 dumb 夹具外，值得为「写安全断言」立真机自动验收补位（ide-ui-acceptance 技能已在库），把无头测不到的三类面收敛成批次化走查清单。

### P3-2 Kotlin↔Java 互操作面已收敛，无实质劣势（正面确认）

`src/main/java` 仅 3 个 Java 文件（`SqlLogToolWindowFactory.java` / `ToolWindowVisibilityListener.java` / `MinSearchSession.java`），边界清晰，不构成互操作负担。登记为「已检查、无问题」，防后续轮次重复排查。

## 三、UX 痛点清单（带证据，区别于 §二 风险）

1. **功能发现率是最大 UX 短板（推断+证据混合）**：插件能力面极大（MCP 11 工具、留痕导出、回滚 SQL、JOIN 图、外部模板、信创体检、MCP/ACP 双通道——`plugin.xml` description 列了 10 个 `<li>` 能力块），但用户触达入口只有 gutter/右键/Alt+Shift+Q 三条（description 原文）+ 一条一次性 balloon（`OnboardingAnchorTip`）。VersionHighlightsActivity 能补版本级触达，但「老用户不知道新功能」的渐进式引导仍只有这一条一次性锚点提示。**推断**：以同类插件经验，重功能插件的多数功能长期使用率 <10%。
2. **状态栏 widget 的点击语义偏窄**：`SqlPreviewStatusBarWidget.getClickConsumer` 只开日志工具窗（`SqlPreviewStatusBarWidget.kt:120-125`）——widget 文本默认「预览就绪」，用户点击预期是「预览相关操作」，实际进的是捕获日志面板；widget 与预览功能之间没有菜单桥。
3. **快捷键策略自洽但无防撞登记**：Alt+Shift+Q/J 双 keymap 注册（plugin.xml keyboard-shortcut 段，注释自证 Ctrl+Alt+S 冲突已避），但未与其他常用插件（如 CodeGlance、Translation）的 Alt+Shift 系做冲突登记——低概率，登记即可。
4. **发行说明可读性好但发现路径窄**：changeNotes 质量高（优势 7），但 Marketplace 截图/演示动图是否与 11.x 的预览面板新形态（原生控制台嵌入、数据源下拉）同步未知（本轮未核查站点资产，标推断）——修复型发行说明触达的是已受影响用户，动图触达的是潜在用户。
5. **设置项默认值唯一可疑点是 autoCheckUpdate=false**（见 P2-1）：其余 113 项默认值抽查（前 40 项 + 空参填充三态 + 方言 auto）均符合「开箱即好」原则。

## 五、本轮新发现的盲区（区别于既有账本，均为此前轮次未提）

1. **插件卸载/禁用后的 agent 残留**：agent attach 到运行中应用 JVM 后，「禁用不卸载语义」是设计内行为（`AgentManager.kt:1623` 注释：CONFIG 下发停采集，禁用不卸载）——即插件被**禁用或卸载**时，已挂载 agent 的用户应用 JVM 内 agent 类与转换过的类不会被还原，agent jar（`AgentManager.kt:1239` `mps-sql-agent-$crc.jar` 落盘）也留在目标目录，直至应用重启。插件侧有卸载意识（`ChooseDataSourceTakeover` 注释明示「面板关闭或插件卸载时换回原动作」），但 agent 通道无对应钩子。**推断**：影响＝卸载插件后应用重启前仍产生 agent 日志输出/字节转换，量级小但属「插件走了、痕迹还在」的体验瑕疵。
2. **SQL 历史应用级共享的多项目混流**：`SqlHistoryManager` 是 application-level（`SqlHistoryManager.kt:26`），与 `PluginSettings` 同文件持久化——两个项目同时开发时，A 项目的捕获 SQL 混进 B 项目的最近执行记录弹框与历史面板，且历史无项目归属字段（State 仅 entries/favoriteEntries，:31-35）。多项目并发是真实使用形态（微服务团队常态），此前轮次从未评估。
3. **交互面无超大 SQL 护栏**：MCP 通道有 200k 字符上限（`McpSelectGuard.kt:24` MAX_SQL_LENGTH），留痕导出有 10KB 截断（`SqlShareManager.kt:24`），但**预览面板交互链**未见对超长 SQL（如 1MB 级动态拼接产物）的截断或懒渲染策略——性能账本覆盖到 50KB 逐键 <50ms，更大规模的形态未验证。**推断**：渲染进编辑器前无上限检查，极端拼接可能造成面板假死，需实测定性。
4. **项目级设置文件的 VCS 协作面**：`ProjectPluginSettings` 持久化到 `.idea/mp-sql-visualizer-project.xml`（`ProjectPluginSettings.kt:22-27`）——该文件会进版本库，团队成员方言覆盖/参数预设互相覆盖产生 diff 噪声；而 `PluginSettings`（roaming DISABLED）与禁用 API 规则（独立文件、KDoc 明示跨项目共享）无此问题。缺一个「哪些字段适合进 VCS」的分层建议（推断：方言、表名映射适合共享，参数预设是个人态）。
5. **非 Gradle 项目＝无盲区（正面确认）**：增强捕获双链均不依赖构建工具——attach 链按进程扫描判目标（`AgentAttachTarget.kt`，helper 名单含 Maven/Mvnd），premain 链走平台 RunConfigurationExtension（`PremainRunConfigurationExtension`），任何 Java 运行配置可用。此前轮次未正面确认过此点，登记销账。
6. **中文注释 SQL 的跨端形态未验证**：生产码有行注释处理痕迹（`SqlTypeClassifier.kt`/`JpaQueryEnhancer.kt` 等），但「中文注释 + 非默认编码工程（GBK）」「中文注释 SQL 提交 EXPLAIN」两形态无测试夹具也无真机读数。**推断**：编码场景（GBK 工程 vs IDE UTF-8 推断）可能出乱码预览，标未验证而非缺陷。

## 六、给第二十七轮报告与开发计划的落点建议

1. P2-1（更新通道）建议独立小任务立项，不并入 T-PerfSweep30（其非目标已显式排除 update.json）。
2. 盲区 1/2/3（agent 残留、历史混流、超大 SQL）建议进需求池按 P2 评估，各需一次小实测定性（分别：runIde 卸载走查、双项目并发走查、1MB SQL 渲染实测）。
3. 优势清单可原样作为竞品对比第三十六轮的「自身画像」素材——运行时零依赖、守卫测试密度、发行说明质量三项是可对外宣传的硬差异点。
