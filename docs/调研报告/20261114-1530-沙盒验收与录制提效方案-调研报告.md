# 沙盒验收与录制提效方案调研报告

> 日期：2026-11-14。前置：同日 agent-desktop 选型调研（UIA 路线对 IntelliJ 平台级不可用，已定案）。
> 问题：runIde 沙盒 UI 验收与演示动图录制两条作业线耗时长、效率低，找可落地的提效方案。
> 方法：内部耗时热点盘点（skill 坑表与经验总结实测读数）+ 外部方案核实（官方文档/论坛/博客，出处见文末）。

## 1. 耗时热点盘点

按两条作业线的实际流程拆段，时间大头不在「点 UI」，在「每轮重来」：

| 热点 | 现状读数（来源） | 每轮代价 |
|---|---|---|
| runIde 全量重启：prepareSandbox 重建 plugins + IDE 冷启动 | 本轮实测 gradle→主窗口 ≈5 分钟，尚不含 Trust 对话框卡死 8 分钟（本次调研实锤） | 5~15 分钟/轮 |
| 索引期 dumb 等待 | skill 坑表 44：动作前轮询 Analyzing，最多等 90s，索引期内动作静默无效 | 1~3 分钟/轮 |
| `build/` clean 后沙盒整个消失 | 坑表 48：idea.key 随 clean 丢失；系统索引/工程缓存同样归零 | 冷启动全价 |
| 前置清障：Trust/许可/气球/DFM | 坑表 20（气球点不动）、48（许可双证）、验收 skill §4（状态归一清单） | 2~5 分钟/轮 |
| robot 不可达层像素降级重试 | robot 对 JBPopup 不可达、设置页滚轮 0.3px/档、双次扫描一致才点击 | 不定，重试是重头 |
| 录制 take 重拍 | 坑表 26（凝视 take 被裁）、35（滚动段）等，一条 take 常录 2~3 遍 | 分钟级/条 |

结论：**最大的杠杆是「沙盒状态复用」——把每轮都付一遍的启动/索引/清障成本变成付一次**；第二杠杆是「少走像素层」。

## 2. 方案清单（按优先级）

### P0-1 录制/验收沙盒容器迁出 `build/`（改动最小、收益直接）

现状 `build.gradle.kts:233` 的 `sandboxContainer = layout.buildDirectory.dir("MPSV-GifFresh")` 在 `build/` 里，发版流程必 clean ⇒ 沙盒（含 idea.key、系统索引、工程索引、信任态、通知静音态）整目录消失，每次从零攒。

方案：录制态沙盒容器迁到 build 外的持久目录（如 `.sandboxes/MPSV-GifFresh`，补 gitignore），clean 不再伤沙盒。
收益：clean 后省掉「冷启动 + 全量索引 + 重新清障」全价，估每发版轮 10~20 分钟。
待验证前提：intellijPlatform 插件对 build 外容器无路径假设；T-GifRecordSwitch 的「录制态禁发布」闸门不受影响。

### P0-2 沙盒配置预置一键化（把清障从每轮操作变成一次性写文件）

清障项全部可以预置进沙盒 `config/`，而不是每轮 GUI 点掉：

- **信任对话框**：本轮实测 262.2 沙盒 `config/options/` 是空的、Trust 弹窗卡了启动 8 分钟。预置信任态（262 把信任设置落在 app-internal-state.db，落点与写法实施时先探一次——「待验证前提」），或预置后用「Trust all projects in folder」一次勾选落盘。
- **许可**：坑 48 已有配方（`config/idea.key` + `-Pmpvs.licenseAgent`），纳入预热脚本，clean 后自动补。
- **通知气球**：坑 20 的气球清障改为预置 `notifications.xml` 的 Don't-ask-again 条目（或启动参数静音已知分组）。
- **插件裁剪**：沙盒 `config/disabled_plugins.txt` 机制已实测存在（本轮在 262.2 沙盒里确认该文件），裁掉 AI Assistant/ml.llm/training 等与验收无关的重插件，压启动期与内存。注意 243 现文件里已有 `com.intellij.modules.ultimate` 这类粗粒度条目，裁剪须逐项验证插件能力不受影响（Database 工具等验收依赖要留）。

产出形态：`dev-support/`（或 `.local/`）一个 `prepare-sandbox-state.ps1`，启动前一键预置，两个 skill 各补一节引用。
收益：每轮 2~5 分钟清障 → 0；且消灭「Trust 卡 8 分钟」这类最阴的坑。

### P0-3 暖 IDE 热更新复用（消灭「改一版重启一轮」）

验收迭代的大头是「改一点代码 → 重启 runIde → 重新定位 → 继续」。本插件已交付**动态卸载/热更新能力**（动态卸载屏障文档、T-DynUpdate263：243/253/262 走免重启加载路径、`installFromLocal` 本地安装包更新链），完全可以反向自用：

- 批内只启动一次沙盒 IDE；每轮改动后 `buildPlugin` 出包 → 走插件自己的本地安装链热加载 → 继续验收。
- 例外条款：触达设置页/Configurable 的改动热更新后有 CNFE 坑（在册：热更新后设置页 apply 无反应），以及任何「重启才能复位的状态」——这类改动整轮重启，不做半吊子热更新。
- 待验证前提：验收批场景下 installFromLocal 触发方式（robot 点 UI / 直接调 Action / MCP）与耗时；热更新后 gutter/预览等编辑器层能力是否即时生效（动态卸载屏障文档说可卸载，须实测一轮）。

收益：迭代轮次从「5~15 分钟/轮」降到「buildPlugin+热载 ≈1~3 分钟/轮」，是清单里单项收益最大的。与 P0-1/P0-2 叠加后，一整个验收批只付一次启动价。

### P1-1 官方新 UI 测试框架（Starter + Driver）试点——robot-server 已被官方停更

关键外部情报（2026-11-14 核实）：JetBrains 员工在官方论坛明确「**对 intellij-ui-test-robot 没有任何后续计划，JetBrains 内部所有新 UI 测试都改用 Starter 和 Driver**」，其 Slack 支持频道已删。我们现行的 robot-server（8580）正是这套停止维护的库。

替代品已公开：官方 SDK 文档「Integration Tests: UI Testing」的 **Driver 框架**（2025 年 2 月起博客连载），Kotlin DSL 镜像 IDE 组件层级 + XPath 定位，Starter 负责 IDE 生命周期。**要求 IDE 2025.1+**：
- 262 录制/验收腿（2026.2.1）✅ 适用；
- 243 dev 验收腿（2024.3.7.1）❌ 不适用，该腿继续 robot-server + 像素。

试点价值：组件层级定位可直接吃掉像素降级层的大块重试（JBPopup 是否可达**待实测**——robot 时代的头号痛点，新框架未明确，列为试点第一验证项）。试点范围建议只开 262 一条腿、不并入门禁，跑 1~2 个真实验收项对比单项耗时后再决定扩面。
待验证前提：与我们高度定制的 build（gifRecord/toolchain 24/自管沙盒）能否装下 Starter 的 gradle 接法；JCEF 面板（若有）支持度。

### P1-2 robot/Driver 组件级截图 → 解锁「双路并行验收」

现行验收截图走全屏 `ImageGrab`，天然互斥（「同一时刻只允许一个 GUI 操作者」）。robot-server 与新 Driver 都支持**对单个组件截图**（不依赖 z 序与物理光标）。若验收项的操作与取证全部落在语义层（robot 点按 + 组件截图），两个 IDE 窗口可以同屏并行跑两路验收（两沙盒、两工作树、两登记条目）。
待验证前提：语义点按是否真的不动物理指针（robot-server 的 click 走组件分发，理论不动；实测确认）；JPEG/缩放差异对证据分级的影响。
收益：验收吞吐 ×2（配合 P0 系列前置）。风险：并行会话共用桌面，弹窗类场景仍互斥——并行粒度按「纯语义项」挑，不清一色。

### P1-3 扩大 IDE 内置 MCP 导航面（已有先例，边际成本低）

坑 53 已定案：MCP `open_file_in_editor` 一次到位零歧义，`record/mcpnav.py` 已封装。但只用于录制导航。扩展方向：`build_project`、`execute_run_configuration`（坑 79 已用它取证）、problems 读取——把验收清单里「打开某文件→触发→等结果」这类导航段全部 MCP 化，robot/像素只留「弹层与真实输入」。改动小，两个 skill 各加一节。

### P2（观察项，暂不做）

- **共享索引**：官方机制（省最多 75% 索引），但 demo 工程是我们自己的、索引只建一次，P0-1 的容器持久化已把索引成本摊掉，共享索引收益重叠。仅在「demo 语料大改版」时重评。
- **computer-use / VLM 截图点击类 agent**（含 agent-desktop）：上轮已定案 UIA 不可达；纯视觉 agent 对验收这种要确定性证据的场景更慢更不可靠。
- **Aqua**：JetBrains 测试自动化产品，面向 Web/移动 UI，不覆盖 IDE 插件面。
- **Windows Sandbox / VM 双机录制**：许可与 agent 链在 VM 里要整套重装，收益不抵成本。

## 3. 落地顺序建议

1. **第一批（纯配置/脚本，一天内）**：P0-1 沙盒迁出 build + P0-2 预置脚本 + P1-3 MCP 化扩展。零生产代码风险，先吃掉每轮 15 分钟级的固定成本。
2. **第二批（自用热更新链）**：P0-3，先拿一个高频验收项（如预览链）做 A/B 计时：全重启 vs 热更新，读数立住再铺开。
3. **第三批（试点新框架）**：P1-1 Driver 262 单腿试点 + P1-2 双路并行，按真实验收项计时对比，再决定是否替代 robot-server 成为 262 主链。
