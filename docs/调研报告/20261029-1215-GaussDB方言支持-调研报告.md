# GaussDB 方言支持 — 调研报告

> 触发：用户提出「插件需要支持 GaussDB」。
> 调研日期：2026-10-29。取证窗口：本机 IntelliJ 262 平台制品、DBX MCP 在册真库、华为云/openGauss 官方文档、MyBatis-Plus v3.5.18.1 源码与本地 3.5.17 jar 反编译。
> 结论一句话：**插件已经"能连"GaussDB，但"能生成正确 SQL"这件事目前有两类真实缺陷，且用户看不到 GaussDB 这个选项。** 需要拆出独立方言对象，并先修两类既有缺陷。

---

## 零、结论摘要

1. **现状不是「零支持」，是「藏在一个别名后面」**。`jdbc:gaussdb://` 在 2026-09-23 的 T-DialectXcFamily 里被并进 `OpenGaussDialect`（内部决策代号 D2=A「一 object 两前缀」）。设置页里根本没有 GaussDB 这一项，用户看到的永远是 `openGauss`；日志角标、MCP 方言名同样显示 `openGauss`。

2. **语义上并不需要分叉，需要分叉的是「身份」**。插件从 `Dialect` 接口真正消费的六项（分页 / 引号 / 大小写折叠 / upsert / EXPLAIN / 事务）在 GaussDB 与 openGauss 上**形态相同或相互兼容**，可以逐字节复用。真正的分叉点是**保留字集合**：官方关键字页机读结果 GaussDB 934 词、保留字 130 个，openGauss 862 词、保留字 122 个，其中 GaussDB 独有保留字 12 个、openGauss 独有 4 个。

3. **发现三处既有结论有误，其中两处是「假绿」**：
   - **`LIMIT 1, 2` 被判定"按 PG 语义静默错解"是假绿**。原探针用 `SELECT 1 LIMIT 1, 2`——单行源下「MySQL 语义（跳过 1 行取 2 行）」与「PG 语义（OFFSET 1 LIMIT 2）」**都返回 0 行**，两种假设给出同一读数，探针不可区分。本次用 5 行源重测：返回第 2、3 行，是**原生 MySQL 语义**，不存在错解。
   - **`supportsDeleteLimit = false` 的推理依据随之失效**，而实测 `DELETE ... LIMIT 1` 在 openGauss 上**语法通过**（只被权限拦下）。插件当前对 openGauss/GaussDB 静默丢弃 `last("LIMIT n")` 尾段，与 `DialectCapabilities` 声称的「能力如实披露」相悖。
   - **保留字基线用错了表**。`OpenGaussDialect.reservedWords = PG_RESERVED`（`sql/Dialect.kt:869`），而 PG 基线比 openGauss 实测保留字**少 17 个**（含 `rownum`/`minus`/`modify`/`procedure`/`is`）。`rownum` 已真机确认不能作别名——列名叫 `rownum` 的表在插件里的产物会直接语法报错。

4. **增强捕获链的缺口比方言链更硬**（第二轮补充，见 §七）：`DriverRegistry` 与 `WeaveSpecs` 都是**按驱动类名硬编码的白名单**。华为官方 GaussDB 驱动（`com.huawei.gaussdb.jdbc.Driver`）**三面全未登记**——attach 后 `matched=0`、零事件、零角标、无方言推断，且不会有任何报错。华为 openGauss 品牌驱动同理。仓内三处注释把 openGauss 驱动谱系写反了（实际 2.x/3.x 是 `org.opengauss.*`，5.x/7.x 才回到 `org.postgresql.*`），据此把「PG 家族已覆盖」当成结论并不成立。

5. **推荐路线**：S1 先修错（保留字 + DELETE LIMIT + 假绿订正，风险低、直接决定 SQL 能不能跑）→ S2 再拆 `GaussDbDialect`（复用 openGauss 形态、换 GaussDB 保留字表与身份链）→ S3 可选注册平台 `sql.dialect` 让 IDEA 方言链精确命中；**增强捕获的驱动登记独立成批**（见 §七），不阻塞方言主线。

## 三、真机取证（openGauss 5.0.0，`sql_compatibility = 'A'`）

### 3.1 先确认这台机器是什么

`SELECT version()` 原文：

```
(openGauss 5.0.0 build ) compiled at 2023-04-18 09:47:39 commit 0 last mr   on x86_64-unknown-linux-gnu, compiled by g++ (GCC) 7.3.0, 64-bit
```

`current_setting('server_version')` = `9.2.4`；`SHOW sql_compatibility` = `A`（Oracle 兼容模式）；`pgxc_node` / `pgxc_class` 均 0 行（单机非分布式）；`rolsuper = false`（非超级用户，DDL 不可验证）；`public` schema 零张用户表。

**结论：这是 openGauss 5.0.0 社区版，不是华为商用 GaussDB。** 唯一容易被误读的信号是错误文案后缀 `does not exist on gaussdb`——那是内核共享代码库留下的通用文案，不是发行版标识。**本轮所有真机读数只覆盖 openGauss，GaussDB 商用版一律无真机**（见 §八）。

`sql_compatibility` 是**库级**属性（`current_setting('dbcompatibility')` 报 `unrecognized configuration parameter`），不可会话切换。这意味着同一实例上不同库的函数可用性可能不同——这是插件做能力判断时必须按库取值、而不是按实例取值的直接依据。

### 3.2 与插件六项能力对应的读数

| 能力 | 探针 | 读数 | 判定 |
|---|---|---|---|
| 引号 | `` SELECT 1 AS `x` `` / `SELECT 1 AS [x]` | `syntax error at or near "\`"` / `"["` | 反引号、方括号均非法 |
| 引号 | `SELECT 1 AS "X"` | 成功 | 双引号唯一 |
| 折叠 | `SELECT COUNT(*) FROM INFORMATION_SCHEMA.TABLES` | 455 行 | 裸大写折小写命中 |
| 折叠 | `FROM information_schema."TABLES"` | `relation "information_schema.TABLES" does not exist on gaussdb` | 引号保留大小写 → **LOWER 族成立** |
| 分页 | `SELECT 1 LIMIT 1 OFFSET 0` | 1 行 | 支持 |
| 分页 | `SELECT * FROM generate_series(1,5) LIMIT 1, 2` | **2, 3（2 行）** | **MySQL 语义**（见 §四.1） |
| 分页 | `OFFSET 1 ROWS FETCH NEXT 2 ROWS ONLY` | 2, 3 | 支持（Oracle 形态也通） |
| EXPLAIN | `EXPLAIN (FORMAT JSON) SELECT 1` | 单列 `QUERY PLAN`，`[{"Plan":{"Node Type":"Result",…}}]` | **与 PG 同形，现有登记正确** |
| EXPLAIN | `EXPLAIN FORMAT=JSON SELECT 1` | `syntax error at or near "FORMAT"` | MySQL 写法非法 |
| EXPLAIN | `EXPLAIN (FORMAT YAML|XML)` / `EXPLAIN PERFORMANCE` / `(ANALYZE, FORMAT JSON)` | 全部成功 | 扩展面存在（本插件未用） |
| upsert | `EXPLAIN INSERT … ON DUPLICATE KEY UPDATE parent_id = VALUES(parent_id)` | `permission denied for relation` | **语法+计划通过** |
| upsert | `EXPLAIN INSERT … ON DUPLICATE KEY UPDATE id = VALUES(id)` | `don't allow update on primary key or unique key` | 仅语义拒绝 |
| upsert | `EXPLAIN INSERT … ON CONFLICT (id) DO UPDATE …` / `ON CONFLICT DO NOTHING` | `syntax error at or near "CONFLICT"` | **不支持** |
| upsert | `EXPLAIN MERGE INTO …` | 仅权限拒绝 | 支持 |
| 事务 | 文档级：`BEGIN` / `BEGIN WORK` / `START TRANSACTION` 均合法 | — | 现有登记 `BEGIN` 可保留 |
| 保留字 | `SELECT * FROM pg_get_keywords()` | 653 词；`R`=93 / `T`=27 / `C`=63 / `U`=470 | **权威可用**（见 §四.3） |
| 保留字 | `SELECT 1 AS rownum, 2 AS minus, 3 AS modify` | `ROWNUM cannot be used as an alias` | `rownum` 确为保留字 |
| 保留字 | `SELECT 1 AS binary, 2 AS notnull, 3 AS ilike` | 全部成功 | `T` 类词可作别名 → 过度引用但安全 |

### 3.3 函数面（决定插件若生成函数名会不会炸）

`GROUP_CONCAT`（含 `SEPARATOR`）、`NVL`、`now()`、`sysdate`、`||`、`CAST(x AS CHAR)`、`CAST` 可用；
`IFNULL`、`DATE_FORMAT`、`MySQL 形态 CONVERT(x, type)`、`LAST_INSERT_ID()` 报错，其中 `LAST_INSERT_ID` 的错误原文直接点名根因：

```
ERROR: last_insert_id is supported only in B-format database
```

即 **A 兼容模式下 B 模式专属函数不可用**。插件当前不生成这些函数，故无即时缺陷，但这是「同一 GaussDB 实例不同库行为不同」的实证，须进计划的前提清单。

## 四、三处既有结论的证伪与订正

### 4.1 `LIMIT 1, 2` 的「PG 语义静默错解」是假绿（探针不可区分）

仓内 `src/test/kotlin/.../sql/DialectXcFamilyTest.kt:24-25` 写着：

> `SELECT 1 LIMIT 1 OFFSET 0` → 1 行；`SELECT 1 LIMIT 1, 2` → **0 行**（按 PG 语义解析为 OFFSET 1 LIMIT 2——MySQL 形态 LIMIT 会被静默错解）

单行源上，「MySQL 语义：跳过 1 行取 2 行」与「PG 语义：OFFSET 1 LIMIT 2」**都返回 0 行**。两种假设给出同一读数，这个探针没有区分力，结论属于「假绿断言」。

本次用 5 行源重测（主控独立执行两次，结果一致）：

```sql
SELECT * FROM generate_series(1,5) AS g LIMIT 1, 2;
-- 返回 2, 3（2 行）
SELECT table_name FROM information_schema.tables LIMIT 1, 2;
-- 返回第 2、3 行（真实 455 行源复现）
```

**判定：openGauss 的 `LIMIT a, b` 是原生 MySQL 语义（offset,count），不存在静默错解。** 官方文档同向：GaussDB 与 openGauss 的 SELECT 语法图都是 `LIMIT { [offset,] count | ALL }`。

原结论「必须渲染 PG 形态」**仍然安全**（PG 形态无歧义且两边都支持），但**理由要改**：不是「防错解」，而是「PG 形态在两种解释下同义，避免歧义」。对应测试 KDoc 与 `supportsDeleteLimit` 的推理依据都要订正。

### 4.2 `supportsDeleteLimit = false` 失去依据，且 `DELETE ... LIMIT` 语法通过

`src/main/kotlin/.../sql/Dialect.kt` 的 `OpenGaussDialect` 未覆写 `supportsDeleteLimit`（基类 false），测试里的理由写作「PG 族无 DELETE LIMIT 尾段（真机佐证：LIMIT 1,2 按 PG 语义解析）」。前提 4.1 已被推翻，这条理由不成立。

主控新探针（同一实例）：

```sql
EXPLAIN DELETE FROM db4ai.snapshot WHERE id = 1;          -- permission denied for relation snapshot
EXPLAIN DELETE FROM db4ai.snapshot WHERE id = 1 LIMIT 1;  -- permission denied for relation snapshot
```

两条**报同一个权限错误**，说明语句已经过了语法与语义分析阶段。对照组证明本通道能可靠区分语法错误：同库 `EXPLAIN INSERT … ON CONFLICT (id) …` 直接返回 `syntax error at or near "CONFLICT ("`，不是权限错误。

**判定：openGauss 的 `DELETE ... LIMIT n` 语法合法（语义是否真的限行未验证——需可写表）。** 当前插件对 openGauss/GaussDB 静默丢弃 `last("LIMIT n")` 尾段：用户看到的是「没有 LIMIT 的 DELETE」，而 `DialectCapabilities` 的设计初衷正是防止这种静默降级。这是**潜在的真实缺陷**，须在计划里按「先写表真机验证，再决定翻转或保留 + 改文案」处理。

### 4.3 保留字基线用错表：PG 基线比 openGauss 实测少 17 词

`sql/Dialect.kt:869` 把 `OpenGaussDialect.reservedWords` 指向 `PG_RESERVED`；`SqlKeywords.kt:107-122` 的 `PG_RESERVED` 只有 84 词。与真机 `pg_get_keywords()` 的 `R` 类（93 词）比对：

| 方向 | 词数 | 词表 |
|---|---|---|
| **openGauss 保留但插件缺（应补）** | 17 | `authid, buckets, excluded, groupparent, is, less, maxvalue, minus, modify, nocycle, performance, procedure, reject, rownum, shrink, sysdate, verify` |
| 插件有但 openGauss 非 R（多包，安全） | 8 | `authorization, binary, concurrently, freeze, isnull, lateral, notnull, similar` |

其中两条**连 PostgreSQL 自身都错**（不是信创专属问题）：

- `is`：PG 官方关键字附录为 reserved，插件 `PG_RESERVED` 里只有 `isnull` 没有 `is`。列名/别名 `is` 在插件产物里不会被引用 → 语法错误。
- `procedure`：PG 11+ 起 reserved，插件缺失。

`rownum` 已真机确认「cannot be used as an alias」——一张列名叫 `rownum` 的表，插件生成的 INSERT/UPDATE 会直接语法报错。

**另一处口径分歧要显式登记**：真机 `pg_get_keywords()` 的 `R` 类只有 93 词，而 openGauss 官方关键字页的「保留」列有 122 个（GaussDB 130 个）。两个来源对「保留」的定义不同（前者是词法层 `catcode`，后者含语法位置限制）。按 `Dialect` KDoc 既有的「宁可多包、不漏包」口径，建议取**并集**（真机 `R∪T∪C` 共 183 词 ∪ 官方页保留列），并在 KDoc 里写清两边来源与并集理由，避免下一个人拿另一个来源「订正」回去。

## 五、GaussDB vs openGauss：拆「身份」不拆「形态」

### 5.1 差异矩阵（只列插件真正消费的面）

| 维度 | GaussDB | openGauss | 插件是否必须分叉 |
|---|---|---|---|
| 分页 | `LIMIT {[offset,] count \| ALL}`；`OFFSET … FETCH NEXT … ONLY` | 同形；`FETCH` 另有 `PERCENT` / `WITH TIES` | **否**——`LIMIT count OFFSET offset` 两边同义，现有渲染逐字节可用 |
| 引号 | `"x"` 通用；**B 模式反引号合法** | `"x"`；反引号非核心语法 | **否**——插件只用双引号 |
| 大小写折叠 | 未加引号折小写 | 真机 LOWER 实锤 | **否**——同族 |
| upsert | `ON DUPLICATE KEY UPDATE`（全模式）；`ON CONFLICT` **仅 PG 兼容** | 两者都支持 | **否**——插件已选 `ON DUPLICATE KEY UPDATE`，两边通吃 |
| EXPLAIN | `EXPLAIN (FORMAT JSON)` 单列 `QUERY PLAN` | 真机同形 | **否**——登记项可直接复用 |
| 事务 | `BEGIN` / `START TRANSACTION` | 同 | **否** |
| identity | `GENERATED ALWAYS` 不能显式插值；`OVERRIDING` 文档未列（推断） | 明确 `OVERRIDING SYSTEM VALUE` | 暂否（插件不生成 identity 包装给本族） |
| **保留字** | 934 词 / 保留 130 | 862 词 / 保留 122 | **是**——GaussDB 独有保留字 12 个（`crossbucket dbTimezone fenced force match maxvalue offline online priorer regexp rlike sessiontimezone`），openGauss 独有 4 个（`groupparent imcstored self unimcstored`） |
| 兼容模式取值 | 集中式 `A/B/C/PG/M`，分布式 `ORA/MYSQL/TD/PG/M` | `A/B/C/PG/D` | 是（能力判断维度，非渲染分叉） |
| DDL（`DISTRIBUTE BY` / 默认 USTORE） | 有 | 无 | 否——**插件不生成 DDL**（已核实：`sql/SqlGenerator.kt`、`generator/`、`reverse/` 无 `CREATE TABLE`） |
| MyBatis-Plus 分页映射 | `GAUSS_DB` → `GaussDBDialect`（`LIMIT ?,?`）；旧 `GAUSS` → Oracle 分页（已 `@Deprecated`） | `OPENGAUSS` → `PostgreDialect`（`LIMIT ? OFFSET ?`） | 否（两种形态两边都合法）；但**命名要跟 MP 走** |

### 5.2 判定

**形态层面：不需要分叉。** 六项能力在 GaussDB 上全部可用且与 openGauss 同形，硬拆会造成两份逐字节相同的实现——这正是本仓库反复踩过的「按族推定」反例的同构错误（只是方向反过来）。

**身份层面：必须分叉。** 三条理由：

1. **保留字真的不同**（130 vs 122，各有独有词），而保留字直接决定生成的 SQL 是否语法正确——这是唯一有实质后果的分叉点。
2. **用户可见性**：GaussDB 用户在设置下拉、日志角标、MCP 方言名里看到的都是 `openGauss`，无法确认插件认对了库。
3. **生态已分**：MyBatis-Plus 自 3.5.13 起同时提供 `GAUSS_DB` 与 `OPENGAUSS` 两个 `DbType`，并把它们映射到不同分页实现。插件反着合并，会让用户按 MP 文档配置却对不上号。

因此推荐：**新建 `GaussDbDialect`，形态全量复用 openGauss 的实现，只替换保留字表与身份链。** 这不是「多一个方言」，是「把别名显式化 + 修正保留字」。

## 六、平台侧缺口：IDEA 262 没有 GaussDB 方言

- 平台制品实测：`.intellijPlatform/localPlatformArtifacts/IU-262.9437.185/` 下 `grep -ril gauss` **零命中**；`intellij.database.dialects.*` 模块清单里没有 gauss/opengauss 条目。也就是说 IDEA 自身的 SQL 方言注册表不含 GaussDB。
- 后果：`IdeaSqlContextBridge.pluginDialectName`（`:219-226`）按名字精确匹配平台 language id，GaussDB 数据源永远命不中；`ExecDialectRouting` 只能靠候选链里的 `PostgreSQL` 兜底（`ExecDialectRouting.kt:62` 已包含 `PostgreSQL`，所以执行 Runner 能枚举到，但方言身份被记成 PostgreSQL）。
- **已有先例**：达梦走的就是这条路——平台无 DM，插件在 `META-INF/database-optional.xml:27-28` 用 `<sql.dialect dbms="UNKNOWN" order="last">` 注册自研 `DmSqlDialect`（`sql/dm/DmSqlDialect.kt`，模板照抄平台 `GenericDialect`，委托 Sql92 词法、不开错误高亮）。GaussDB 可完全照抄这个模板。

## 七、增强捕获链的 GaussDB 适配

增强捕获（字节码 agent）与渲染方言是两条独立的链。这条链对 GaussDB 的结论比方言链更硬：**方言链是「名字不对」，增强捕获是「一条都采不到」**。

### 7.1 唯一耦合点就是驱动类名白名单

架构文档自己点出了这一点（`docs/架构设计/01-项目架构总览.md:389`）：

> 采集面是 JDBC 接口级、对全部方言一视同仁（含 DM 达梦），**唯一耦合点是 `DriverRegistry` 驱动类名单**。

「对全部方言一视同仁」这个表述容易读成「驱动无关」，实际是**按驱动类名硬编码的白名单**，落在三张表：

| 面 | 表 | 作用 |
|---|---|---|
| connect 面 | `DriverRegistry.DRIVER_CLASSES`（`DriverRegistry.java:24-53`） | 织 `Driver.connect(String,Properties)` 出口，记 URL |
| 语句面 / prepare 面 | `WeaveSpecs.SPECS`（`WeaveSpecs.java:43-105`） | 织 `execute*`/`addBatch`/`clearBatch`/`setXxx`/`prepareStatement` |
| 测试侧镜像 | `StatementWeaverVendorCoverageTest` 的两个数组 | 谓词层 + 字节层（真实 jar 织入 + JVM 链接期校验） |

未命中时的降级是**静默的**：transformer 返回原字节，`AgentMain` 打印 `attach retransform: matched=0 wove=0`，宿主侧无异常、面板零条目。这正是「看着支持、实际不出」的形态。

### 7.2 实测驱动矩阵（Maven Central 真 jar 反编译）

| 驱动制品 | Driver 类 | 语句/连接类包 | connect | 语句+prepare | 实际结果 |
|---|---|---|---|---|---|
| `com.huaweicloud.gaussdb:gaussdbjdbc:506.0.0.b058`（华为 GaussDB 官方） | `com.huawei.gaussdb.jdbc.Driver` | `com.huawei.gaussdb.jdbc.jdbc.Pg*` | ❌ | ❌ | **零采集** |
| `com.huaweicloud.gaussdb:opengaussjdbc:506.0.T35`（华为 openGauss） | `com.huawei.opengauss.jdbc.Driver` | `com.huawei.opengauss.jdbc.jdbc.Pg*` | ❌ | ❌ | **零采集** |
| `org.opengauss:opengauss-jdbc:2.0.1 / 3.0.0` | `org.opengauss.Driver` | `org.opengauss.jdbc.Pg*` | ✅ | ❌ | **只有 URL，无 SQL** |
| `org.opengauss:opengauss-jdbc:5.0.0 / 7.0.0` | `org.postgresql.Driver` | `org.postgresql.jdbc.Pg*` | ✅ | ✅ | 名义已覆盖（未字节级实证） |
| `gsjdbc4.jar`（华为，PG 协议） | `org.postgresql.Driver` | `org.postgresql.jdbc.Pg*` | ✅ | ✅ | 名义已覆盖 |

实测要点（`unzip -l` + `javap`）：

- `gaussdbjdbc-506.0.0.b058-jdk7.jar` 与 `opengaussjdbc-506.0.T35.jar` 里 **`org/postgresql` 条目数为 0**，即完全重定位，**不继承** PG 驱动的任何类。`PgStatement implements GsStatement`，与 `org.postgresql.jdbc.PgStatement` 无继承关系。
- 好消息：方法形态与 pgjdbc 一致——`execute(String)/executeQuery(String)/executeUpdate(String)/executeBatch()/executeLargeBatch()/addBatch(String)/clearBatch()`、`PgPreparedStatement` 的 `execute()/executeQuery()/executeUpdate()/executeBatch()` 与 `setString/setInt/setObject` 全在；`PgConnection.getURL()` 是 **public**，`UrlResolver` 的反射链可用。也就是说**织入形态可以直接复用现有 PG 那条 spec**。
- `PgCallableStatement extends PgPreparedStatement`，自有 execute 族很少，**可不单独登记**。
- `com.huawei.gauss200.jdbc.Driver`（`gsjdbc200.jar`）在 Maven Central **无任何制品**，未实测。

### 7.3 仓内三处注释把驱动谱系写反了

| 位置 | 现写法 | 实测 |
|---|---|---|
| `DriverRegistry.java:31`（注释） | 「openGauss 2.x 走 PG 驱动，3.x 起自带驱动」 | **反了**：2.x/3.x 是 `org.opengauss.*`，5.x/7.x 才回到 `org.postgresql.*` |
| `WeaveSpecs.java:63` | 「PostgreSQL / openGauss 兼容（openGauss 2.x 走 PG 驱动）」 | 同上 |
| `StatementWeaverVendorCoverageTest.java:145-146` `VENDOR_NOT_COVERED` | 「openGauss 2.x 走 PG 驱动（已由 `org.postgresql.` 覆盖）；3.x 自带驱动未实证」 | 同上；且**认领方向错**——真正零采集的是 2.x/3.x |

复核读数：`org.opengauss:opengauss-jdbc:3.0.0` 里是 `org/opengauss/Driver.class` + `org/opengauss/jdbc/PgStatement.class`，`org/postgresql` 计数 0；`7.0.0` 里是 `org/postgresql/Driver.class`（`META-INF/services/java.sql.Driver` 声明），`org/opengauss` 计数 0。

后果不只是注释错：`DriverRegistry.java:33` 登记了 `org.opengauss.Driver`（3.0.0 存在）但语句面没登记 → **3.x 用户「看着支持、一条不出」**；而 `VENDOR_NOT_COVERED` 已把该厂商显式认领为「已由 PG 覆盖」，守卫因此保持绿色——典型的「守卫看不见它要防的站点」。

### 7.4 宿主安全（红线）现状：是安全的，但别碰

- `SqlHookCallbacks.DEFAULT_WRAP_CONNECTION` 读系统属性 `sqlvis.agent.wrapConnection`，**缺省 `false`**（`SqlHookCallbacks.java:53-57`）；关闭时 connect 出口只记 URL、**原对象直返**（`:85-89`）。这是 T-ConnCastSafety（2026-10-28）对达梦 CCE 的收口。
- 语句面 / prepare 面只改方法体、**不替换任何对象身份**，结构上不可能引发 `$ProxyN cannot be cast to ...`。
- 但 GaussDB 的 `com.huawei.gaussdb.jdbc.jdbc.PgConnection` / `PgStatement` / `PgPreparedStatement` 实测均为 `public` 非 final，宿主写 `(PgConnection) conn` 完全可能。**一旦有人打开 `-Dsqlvis.agent.wrapConnection=true`，就会复现达梦那个 CCE**。默认值不得改，且应在该属性的 KDoc 里点名 GaussDB。

### 7.5 两个守卫的口径缺陷（会假绿）

1. **厂商前缀只取两段**：`vendorKey()`（`StatementWeaverVendorCoverageTest.java:180-187`）把 `com.huawei.gaussdb.jdbc.Driver` 与 `com.huawei.opengauss.jdbc.Driver` 都压成 `com.huawei.`。**只要登记了其中一族语句面，另一族的缺口就被判为「已覆盖」**。同理 `com.huawei.gauss200.*` 也被顺带「假绿」。
2. **名单漂移无反向断言**：测试里只有「测试数组 ⊆ SPECS」单向断言，**`WeaveSpecs` 新增类但没加进测试数组不会红**——新类因此拿不到字节层校验（而那正是 premain 红线的唯一防线）。

此外 `VENDOR_NOT_COVERED` 的键也是两段前缀，只能整段认领，无法表达「同厂商下 A 族覆盖、B 族不覆盖」。

### 7.6 次要缺口

- **帧跳过前缀表缺两族**：`StackLocator.java:88-90` 有 `org.postgresql.`/`dm.jdbc.`/`com.kingbase8.`/`com.gbasedbt.`，**没有** `com.huawei.` 与 `org.opengauss.`。同名副本共 4 份（`CallerSourceLocator.kt:77-80`、`SourceInterceptorTemplates.kt:281-284`、`StackDigestFrames.kt:149-151`、`StackLocator.java`），由 `LocatorSkipPrefixSyncTest` 锁「四份同集」，改必须四份一起改。后果是 fat jar 场景下源码位置可能跳进驱动内部（体验缺陷，非功能失效）。
- **多主机 URL 角标**：`jdbc:gaussdb://n1:8000,n2:8000/db` 在 `JdbcUrlDialects.parseAuthority` 里 host 判含冒号 → 取 null、port 取 `8000`，角标退化成 `db:8000`。方言推断不受影响（只取子协议）。
- **`SmartRouteConnection` 两个 `prepareStatement` 重载**（`(String,int,int,int)`、`(String,String[])`）是自有实现，普通 `(String)` 继承自 `PgConnection`；走这两个重载的 PS 无 SQL 登记，属盲区。
- **openGauss 5.x/7.x 的读写分离与 OR 族**（`org.postgresql.readwritesplitting.*`、`org.postgresql.jdbc.OR*`）**不继承** `PgConnection/PgStatement`，现有 PG 名单覆盖不到。

### 7.7 与在途改动的冲突面

`git status` 显示另一会话正在改 agent 模块的 `hook/StatementHandler.java`、`hook/WovenEvents.java`、`util/StackDigest.java`、`util/StackLocator.java`（T-StackBizFrame 收口）。实测 `git diff`：这四笔只动栈摘要/锚点与一行调用点，**未触及** `DriverRegistry`、`WeaveSpecs`、`StatementWeaverVendorCoverageTest`、`build.gradle.kts`，也未改织入形态与事件字段。**结论：与 GaussDB 驱动登记无冲突**，但同模块并行编译会互相打断，建议在其收口后单开一笔。

### 7.8 可自动化的验证上限

- GaussDB 商用版**无公开容器镜像**（见 §九），跑不了端到端。可自动化的最高档是：**真实驱动 jar 字节 → 织入 → 隔离 loader 定义 + 初始化（JVM 链接期校验）**。`StatementWeaverVendorCoverageTest` 现有机制已支持，只需 `testImplementation("com.huaweicloud.gaussdb:gaussdbjdbc:506.0.0.b058-jdk7")`（Java 8 字节码、jar 自包含），与既有 `DmJdbcDriver18`/`postgresql`/`mssql-jdbc`/`ojdbc11` 的 `testImplementation` 完全同款。
- openGauss 3.x 与 5.x/7.x 有官方镜像，可做端到端 attach 验证。
- 拿到用户侧 GaussDB 真机 attach 读数前，**不得**在文档或能力矩阵里写「GaussDB 增强捕获已验证」。

## 八、可选方案与推荐

### 8.1 方言链的选项

| 方案 | 内容 | 代价 | 风险 |
|---|---|---|---|
| **A 不拆** | 只改文档说明「GaussDB 用 openGauss 方言」，修保留字缺陷 | 最小 | 用户仍看不到 GaussDB；保留字仍只能二选一（GaussDB 独有 12 词永远漏） |
| **B 拆身份**（推荐） | 新增 `GaussDbDialect`，形态复用 openGauss，保留字用 GaussDB 集；`jdbc:gaussdb` 全链改指新对象 | 中：7 处主源码 + 9 处守卫 + 兄弟文档仓 4 张表 | 低：形态逐字节复用，无渲染行为变更 |
| **C 拆身份 + 平台方言** | B + 仿 `DmSqlDialect` 注册平台 `sql.dialect`，让 IDEA 方言链精确命中 | 中大 | 中：`database-optional.xml` 是 optional 依赖文件，需真机沙盒验证；平台方言实现要给 `Dbms.UNKNOWN` + 不开错误高亮，能力面有限 |

**推荐 B 为本次主线，C 作为可选券**（价值真实但不阻塞「GaussDB 能用且认得出」这个目标）。

并**强制前置**：无论走哪个方案，§四的三条（保留字补齐含 `is`/`procedure`、DELETE LIMIT 依据重取、LIMIT 假绿订正）都必须先做——它们与「拆不拆」正交，且直接决定生成的 SQL 在 GaussDB 上跑不跑得起来。

### 8.2 增强捕获链的选项（与方言链独立）

| 方案 | 内容 | 代价 | 风险 |
|---|---|---|---|
| **A 不登记** | 只在文档里说清「华为 GaussDB 驱动不支持增强捕获，请用控制台通道」 | 最小 | 用户侧零 SQL 采集；文档与「JDBC 接口级一视同仁」的既有表述冲突 |
| **B 只补语句面 + prepare 面**（推荐） | 登记 `com.huawei.gaussdb.jdbc.jdbc.PgStatement/PgPreparedStatement/PgConnection`，**不碰 connect 面**；URL 由 `UrlResolver` 反射 `PgConnection.getURL()` 拿 | 中：agent 子项目 2 个文件 + 测试依赖 | 低：与达梦同款路径，premain 红线不受影响 |
| **C B + connect 面** | 再加 `com.huawei.gaussdb.jdbc.Driver` 做 connect 出口织入 | 略高 | **需先过字节层**；达梦 `DmDriver` 就是在这里 VerifyError 被整类撤出的 |

**推荐 B**。理由：`PgConnection.getURL()` 已实测 public，URL 不依赖 connect 面；connect 面的唯一独有能力是「最近 connect URL 兜底」，而达梦已经证明这个兜底可以不要。C 只有在字节层明确绿灯、且确有多库/多数据源场景需要粗粒度兜底时才考虑。

**共同前置**：无论 A/B/C，都必须先跑 P-9 的字节层（真实 jar 织入 + JVM 链接期校验）——这是唯一能在没有 GaussDB 服务端的情况下证明「不会让宿主起不来」的手段。

## 十、证据边界与未验证项

1. **GaussDB 商用版零真机**。所有 GaussDB 侧结论为官方文档级；`OVERRIDING SYSTEM VALUE` 在 GaussDB 是否可用、`DELETE ... LIMIT` 在 GaussDB 是否合法，均未验证（openGauss 上前者有文档、后者有语法级实证）。
2. **`DELETE ... LIMIT` 只证到语法通过**，语义是否限行未证（实例非超管、无用户表）。
3. **保留字两个来源口径不一致**（真机 `catcode R`=93 vs 官方页保留列 122/130），本次取并集是工程决策，不是等号。
4. **官方文档抓取存在入口受限**：`support.huawei.com/enterprise`（SPA+反爬）、`doc.huaweicloud.com`（不通）、`doc.hcs.huawei.com`（418）均未取到，故 GaussDB 100/T 的产品线与内核来源标为「未查到」。文档页数（934/862 词、130/122 保留字）为 HTML 表格机读结果，未逐词人工复核。
5. **`sql_compatibility` 的库级差异未覆盖**：真机只有 A 模式库。B/M/PG 模式下 `LIMIT m,n`、`IFNULL`、`DATE_FORMAT`、反引号的行为**全部未验证**，计划里作为前提 P-4。
6. IDEA 平台侧「无 GaussDB 方言」结论来自 `.intellijPlatform` 制品目录 grep；未对运行时 `SqlDialectMappings.getAvailableValues()` 实测（需 runIde 沙盒）。
7. **增强捕获链全部结论为「代码 + 驱动 jar 字节」级，无一处真实 attach 读数**。GaussDB 商用版无服务端镜像，`matched>0 wove>0` 与真机事件是否到来均未验证；openGauss 侧本轮也没跑 attach（在册实例是服务端，不是宿主应用）。
8. **驱动谱系只实测到包名/类名/方法签名，未实测织入产物是否通过 JVM 校验**。华为两族驱动是 pgjdbc 的深度改写（`PgStatement implements GsStatement`），达梦那种出口 `chop_frame` 导致的 `VerifyError` 是否同样存在**未知**——这正是必须先在 `testImplementation` 里跑字节层的理由。
9. **`com.huawei.gauss200.jdbc.Driver`（`gsjdbc200.jar`）无 Maven Central 制品**，全链路未实测，只能标「未查到」。
10. `VENDOR_NOT_COVERED` 里 openGauss 的认领理由与实测相反（见 §7.3），本轮只登记不改——改它属于实施动作。
