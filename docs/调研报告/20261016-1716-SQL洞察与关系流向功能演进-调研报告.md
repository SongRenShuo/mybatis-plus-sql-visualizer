## 一、结论：从“看见 SQL”走向“理解、验证和诊断 SQL”

推荐把 SQL Visualizer 扩展为 IDE 内的 SQL 开发与诊断工具，而不是在插件里重建一个完整 APM 平台或企业数据治理平台。

产品主线可以表达为：**代码生成了什么 SQL，为什么这样生成，涉及什么数据，实际运行是否符合预期，改动有没有带来回归。** 这条主线连接现有编码期预览与运行期捕获，比单独增加一个漂亮的拓扑图更符合定位。

优先投入三组能力：

1. **SQL 解释与关系分析**：从当前预览直接看逻辑结构、读写对象、结果字段来源，点击节点回到 SQL 片段；不启动应用、不连数据库也能提供主要价值。
2. **预览场景与运行对照**：在现有参数预设、条件模拟、Diff 基础上，比较多个参数场景，解释条件为何进入 SQL，核对预览与真实执行的差异。
3. **可信的运行画像与请求诊断**：先保留独立执行事件，再做 SQL 热点、请求内重复查询、时间轴、基线对比。不能以当前去重后的日志列表充当执行账本。

列级血缘、跨文件影响分析、事务图、分布式关联作为后续阶段。分布式能力优先与既有观测系统互补，不要求用户为使用本插件额外搭建 OAP、存储集群或常驻服务。

本次需求由最初的“类似 XRebel、SkyWalking 的链路与数据流向”扩展为 SQL 全流程功能研究。下文同时覆盖预览、结构理解、数据来源、运行诊断、安全与回归，不将范围限制为两类图。

## 三、先分清不同的“关系”和“流向”

| 视图 | 回答的问题 | 必要证据 |
|---|---|---|
| SQL 逻辑结构图 | 这条 SQL 在筛选、连接、聚合和输出什么？ | SQL AST 与作用域；不是数据库真实执行顺序 |
| JOIN 关系图 | 哪些表按什么条件关联？ | FROM/JOIN/ON；不是数据库真实外键证明 |
| 表级读写访问图 | 读取了哪些对象，写入或删除哪个对象？ | 语句类型、读集合、写目标、作用域 |
| 结果来源与列级血缘 | 输出字段由哪些输入字段或表达式产生？ | 投影、赋值表达式、别名绑定和必要元数据 |
| 执行计划图 | 数据库规划器选了什么算子和访问路径？ | 对应数据库的 EXPLAIN；实际统计需另行执行 |
| SQL 执行时间轴 | 某次观测中各 SQL 何时开始、持续多久？ | 独立执行事件、时钟口径、完整性 |
| 请求调用链 | 一个请求经过哪些入口、子调用和数据库操作？ | 请求生命周期、span 身份与父子上下文 |
| 工作负载依赖图 | 哪些调用点经常访问哪些库表？ | 一段明确观测范围内的聚合事实；不表达单次因果 |

同一个图组件可以复用交互与布局，但这些图不能共用含义模糊的箭头。`CaptureProvenance` 是采集通道来源，也不是数据血缘。

### 3.1 一条 SELECT 应该如何解释

```sql
SELECT c.name, SUM(o.amount) AS total
FROM customer c
JOIN orders o ON o.customer_id = c.id
WHERE o.status = :status
GROUP BY c.name;
```

合理的展示为：

- `customer`、`orders` 是读取对象，流向查询及其结果集；没有写表。
- `name` 的值来源是 `customer.name`；`total` 的值来源是 `SUM(orders.amount)`。
- `orders.status` 是筛选依赖，连接键是匹配依赖；它们不能一律画成 `total` 的直接值来源。
- 分组与聚合属于逻辑解释，不宣称数据库真的按图从左到右执行。
- 不能画出 `customer → orders` 并标为“数据写入”，也不能凭 SQL 判断一对多基数或真实外键。

对于 `INSERT INTO summary (...) SELECT ... FROM orders`，才存在明确的目标表；但静态图仍只是声明的写入关系。运行时执行成功也不等于事务最终提交。`DELETE` 表达删除访问与筛选依赖，不伪造输出值血缘。

## 四、外部产品和标准：借鉴什么，不照搬什么

### 4.1 XRebel

官方 FAQ 将其定位为 `Real-time, request-based profiling`，明确列出 SQL/NoSQL I/O 及 N+1 检测，也明确说明不以生产环境为目标。[S01]

使用手册的 Calls 视图沿 Java 方法组织数据库调用，展示查询数量、累计耗时，查询作为叶子；支持请求基线比较。[S02] 分布式场景需要每个被跟踪应用运行并激活 agent，异步跟踪还有超时和集成边界。[S03]

适合借鉴：请求内 SQL 清单、调用点聚合、重复查询提示、基线对比、从 SQL 返回业务源码。不能据此宣称 XRebel 已提供 SQL 列级血缘；本轮没有获得这种官方证据。N+1 是官方能力声明，但算法、误报率与本机可用范围未实测。价格、每席位/JVM 计费和开销比例未核实，不作数字比较。

### 4.2 Apache SkyWalking

官方架构分 Probe、平台后端、存储和 UI；OAP 承担分析与聚合，UI 查询后端。[S04] 拓扑中的服务与端点依赖，不等同于所有 Java 方法的完整调用树，也不等同于表列血缘。

Virtual Database 根据应用 agent 的数据库访问 span 识别数据库节点，提供访问侧流量、延迟、成功率等视角。[S05] MySQL 服务端资源指标和慢日志属于另一条采集链，文档分别列出 exporter、OpenTelemetry Collector、Fluent Bit 等组件。[S06]

适合借鉴：入口—SQL—数据库的分层下钻、观测质量提示、按上下文过滤和慢操作证据。暂不照搬：OAP 服务、长期遥测存储、运维告警中心、全网络自动拓扑。JDBC 客户端耗时不等于数据库服务端纯执行时间，不能混标。

Java agent 固定版本配置页显示 SQL 参数采集默认关闭且有长度上限。[S07] 这支持本插件“默认不扩大敏感参数采集”的选择，但长度截断本身不是脱敏。

### 4.3 OpenTelemetry、W3C 与 OpenLineage

- OpenTelemetry 数据库 span 描述数据库客户端调用，提供数据库、操作、查询摘要和文本等语义。低基数摘要与完整 SQL 应分开，参数不应默认收集。[S08]
- W3C Trace Context 定义跨服务上下文，不会自动给 SQL 添上父子关系。必须在执行时取得并传播；采样标记不保证所有事件齐全。[S09]
- OpenLineage 区分 Job、Run、Dataset，列级 facet 描述输入字段如何产生输出字段。[S10] 它是可互操作的表达方式，不是接入后即可解析任意 SQL 的保证。官方 SQL 集成源码同样写明语法边界。[S11]

推荐先采用这些标准的语义原则和可映射字段，不在首期引入整套 SDK、Collector 或服务端。未来只读导入与外部系统关联，必须经过独立兼容性验证。

### 4.4 DataGrip 与 DBeaver

DataGrip 把 Explain Plan 与实际执行的 Explain Analyse 分开，并提供树形、原始结果和图形视角。[S12] DBeaver Query Manager 把执行时间、耗时、影响行数、错误和连接上下文放在一起。[S13]

对本插件更直接的启示是：**在当前 SQL 上给可解释、可追溯的分析，减少从代码跳到另一套工具的成本。** 不能将所有数据库的计划格式统一成一个假精确模型；成本单位不是毫秒。PostgreSQL 官方明确指出 ANALYZE 会实际执行语句及其副作用，回滚也不能被包装成“绝对无副作用”。[S14]

## 六、运行分析的三个基础缺口

### 6.1 展示条目不是执行事件

实际模型链为 `SqlEvent → AgentEvent → LogSqlEntry`。日志默认按还原 SQL 指纹在 60 秒窗口内去重，键不包含请求、调用点或数据库。源码与测试均表明同为 agent 的两次执行也可能折叠，20ms 与 50ms 两次只保留前一条 20ms。

证据：`K:log/SqlLogEntryBuffer.kt:250–327,395–397,600`；`src/test/kotlin/cn/song/mybatisplus/visualizer/log/SqlLogEntryBufferTest.kt:797–805`。

因此：

- `×N` 混合了重复观测和真实重复执行，不能反算准确次数。
- 字段融合可能把不同执行的时间、请求标签与错误拼成展示条目，不适合作为 span。
- 历史“全量保存”接的是成功入队条目，不是原始执行全量。
- 直接从列表计算累计耗时、P95、请求预算或热点排名会受去重、过滤、淘汰影响。

推荐在展示去重之前建立独立事件通道，并明确分析采集范围。不能简单关闭日志去重解决，也不能让新通道绕过全局停采、用户隐私限制和显式排除策略。

### 6.2 调用栈、入口方法和请求标签不是同一类身份

`StackLocator.entryKey` 是类名加方法名的定位键，不包含调用实例身份。`requestTag` 当前来自应用预置 `MDC["sqlvisRequestTag"]`；没有自动生成请求 ID、Servlet 生命周期及异步传播的完整机制。现有 ThreadLocal 互斥门用于防止代理/织入双报，不是 Trace Context。

证据：`A:util/StackLocator.java:204–245`、`A:util/MdcAccessor.java:12–32`、`K:log/LogSqlModels.kt:113–183`。

已有栈只能证明捕获时同步线程上的调用归因；摘要省略中段时，应画省略节点，不能补出直接调用边。相同标签可先用于“标签分组”，但标签复用、请求起止未知时不能给出严格请求时长。

### 6.3 捕获质量和耗时语义还需加强

agent 已有纳秒耗时、线程名、错误文本及 DML 行数，但适配为日志时耗时变为整数毫秒、线程名未保留。没有完整查询结果行数、取结果耗时、事务 commit/rollback 终态。`mapperStatement` 还可能承载 agent 的方法键，不能全当真实 Mapper statementId。

证据：`K:log/agent/AgentEventAdapter.kt:33–62`、`A:hook/StatementHandler.java:82–155`、`A:hook/EventBuilder.java:26–57`。

队列已有 2048 容量及非阻塞 offer；但发送出队后的编码/IO 失败无重投，心跳没有完整丢失统计；自动存档待写队列仍为无界结构。证据：`A:transport/EventBus.java:30–57`、`A:transport/SenderLoop.java:250–275`、`K:log/SqlLogAutoSaver.kt:69–87`。

另有两项源码推导风险，尚未运行复现：纯织入 `IRETURN` 装箱与 `execute()` 的 Boolean 行数判定可能不一致；仅在已有 RETURN/ATHROW 插出口不能证明所有向外传播异常均捕获。证据：`A:StatementWeaver.java:337–375`、`A:hook/EventBuilder.java:26–57`。它们应成为开工验证用例，不在本报告中直接写成已复现故障。

| SI-10 | 性能基线与 SQL 预算 | 比较改动前后数量、结构、耗时和错误 | P2，完整性必需 |
| SI-11 | 表字段使用反查与变更影响 | 改列前定位相关 Mapper、实体和 SQL | P2，有范围地索引 |
| SI-12 | Schema/映射差异检查 | 发现代码模型与选定数据库快照不一致 | P2，复用 dev R46 |
| SI-13 | 执行计划解读与前后对比 | 把算子、估算量和变化放回当前 SQL | P2，复用 R61/R90 |
| SI-14 | 写入影响解释与事务视图 | 看写目标、影响范围、提交/回滚证据 | P2，分开静态与实测 |
| SI-15 | 场景回归包与结果比较 | 把已确认的 SQL 行为变成可重复验收 | P2 离线，P3 真库 |
| SI-16 | 证据驱动的优化建议 | 给出可核验前提，而不是一键盲改 SQL | P2 规则解释，P3 改写 |
| SI-17 | 外部 Trace 关联与只读导入 | 从本地 SQL 定位现有观测平台证据 | P3，可选集成 |

### 7.1 预览侧最有差异化的细节

**SI-01/02/03：围绕正在看的 SQL，而非全库扫图。** 首期覆盖已渲染的 SELECT、常见 JOIN/非递归 CTE、显式目标列的 INSERT…SELECT 与单表 UPDATE/DELETE。结果字段面板首先支持限定列、别名、常见表达式；星号缺元数据、裸列歧义、递归 CTE、过程体等显示未知/部分支持。

**SI-04：解释生成过程。** 点击 SQL 的某一段，可看到“来自哪个源码片段、受什么条件控制、当前参数决定了什么”。必须建立渲染时的范围映射；不能事后通过字符串相似度制造精确溯源。源映射缺失时可退为语句级定位。

**SI-05：不只是再加一个预设下拉框。** 复用现有命名预设，一屏比较若干场景的 SQL 形状、参数数量、读写对象和条件状态；支持缺值、空集合、单元素/多元素、分页开关等。默认只渲染，不执行，不调用有副作用的用户方法，不穷举任意布尔组合。

### 7.2 运行侧先做“有质量标记的画像”

**SI-07：给开发者可行动的排序。** 区分次数、累计 JDBC 耗时、最大/分位耗时、错误状态、调用点、库标。JOIN 查询涉及多表时，表视图标“关联查询耗时”，不能把整条耗时分摊成数据库表实际耗时。

**SI-08/09：先做 SQL 视角的请求诊断。** 首期请求树是请求根节点下的 SQL 执行和栈归因，不对所有 Java 方法插桩，也不假装有 Service 方法耗时。疑似 N+1 给出请求范围、模板次数、调用点与样本；重复可能是重试、批量写或合理业务，用户可以降噪。无参数证据时不能声称已经证明“逐父对象循环”。

**SI-10：比较必须可比。** 固定入口、参数场景、数据集/库、代码版本、采样策略与暖机条件；SQL 数量预算优先于易波动的耗时预算。有丢失、截断、未覆盖驱动或请求边界不明时不能给“无回归”；观测下界已超预算可判失败，否则为不可判定。完整性还需要请求/会话终态计数或水位，不能靠序号连续和心跳推断尾部未丢失。同步 HTTP 请求也可能等待线程池内的 SQL；无上下文传播证据时只展示请求线程内观测，不对整个请求判预算通过。

**SI-06：匹配是一个产品功能，不是一个 SQL 文本 join。** 结合项目/模块、调用来源、语句身份、参数形状、数据库、会话和时间窗口给候选，让用户确认；重复 SQL、多请求同调用点、分页 COUNT 与主查询分别处理。相似指纹不能自动证明是同一次执行。

### 7.3 影响、安全与优化建议的限制

- SI-11 从当前文件/模块、已解析预览与显式选定范围起步，不在编辑或绘图热路径扫描整个工程/依赖库。动态未展开 SQL、外部 JAR、存储过程均说明覆盖缺口。
- SI-12 的“未连接/未内省”不是“表列不存在”。仅对确定的数据库身份与元数据版本做检查；跨库同名表不可混合。
- SI-13 不自动运行 EXPLAIN ANALYZE，不把成本单位标成 ms，也不把估算行数当实际行数。
- SI-14 的 COUNT 只是当时谓词匹配试算，不是保证未来写入行数。事务关联需要物理连接、逻辑租借、事务边界与保存点语义；线程 ID 不够。
- SI-15 首期回归包记录渲染产物、指纹、对象集合、场景和期望，不自动回放 DML。结果比较需要另证平台结果读取能力；SQL 无 ORDER BY 时不能按行位置直接判差异，集合/多重集、NULL、浮点误差和截断都需定义。
- SI-16 优先规则解释与定位。索引建议需要真实现有索引、选择性及计划证据；改写候选默认仅展示，样本结果相同不等于语义普遍等价。
- SI-17 默认不上传 SQL、不连接远端、不在宿主应用引入第二套自动遥测。协议适配不等于已支持所有后端版本。

## 八、技术可行性小实验

### 8.1 环境与方法

本地制品 `com.github.jsqlparser:jsqlparser:5.3`，Java `17.0.19`。jar SHA-256：`41bcb5b00488231db179cb5a375690830a59aba521dfa303daa94dcb9dcc8e88`。

先用 `javap` 核实 `parse(String, Consumer)`、`withSquareBracketQuotation(boolean)`、`withAllowComplexParsing(boolean)`、`withTimeOut(long)`、`TablesNamesFinder.getTables(Statement)` 的签名；随后在仓外 Java 源文件运行探针，不启动 Gradle、不连接数据库。

配置：方括号引用开启、复杂解析关闭、单条解析 1000ms 预算。与现有入口的语法开关相近，但这是库级实验，不是插件入口端到端测试。

| 样本 | parse 结果 | 表名集合 |
|---|---|---|
| SELECT + JOIN + GROUP BY | PlainSelect | customer、orders |
| INSERT…SELECT | Insert | order_summary、orders |
| UPDATE 含相关子查询 | Update | order_item、orders |
| DELETE…USING | Delete | order_item、orders |
| 非递归 CTE | PlainSelect | customer、orders |
| 递归 CTE | PlainSelect | category |
| MERGE | Merge | source、target |
| SELECT * + JOIN | PlainSelect | customer、orders |
| UPDATE…FROM | Update | source、target |
| 未展开 MyBatis XML 模板 | JSQLParserException | 无 |
| `THIS IS NOT SQL` 负对照 | JSQLParserException | 无 |

9 个合法样本可解析，2 个不适合直接解析的样本被拒绝。这个读数**只证明样本的 AST 入口可用**；不代表 9 类全部语法覆盖、列血缘正确或插件全量测试通过。

### 8.2 最重要的实验结论

`TablesNamesFinder` 返回集合，INSERT 源表与目标表都混在其中。sources jar 中 `TablesNamesFinder.java:1087–1096` 先访问目标表再访问 SELECT，`1035–1050` 的 UPDATE 同样遍历多类引用。因此不能把表名列表顺序解释为流向。

递归 CTE 与 MERGE 能 parse，不意味着应进首发语义范围；需要作用域、递归终止、分支写入和列绑定专项验证。`SELECT *` 能 parse，也不能在没有准确元数据时展开真实字段。

在线 JSqlParser 文档当前显示后续版本 5.4.162，与本仓 5.3 不同。[S16] 实施方法签名以本地同版本 jar/源码为准，禁止从滚动文档照搬新 API。

### 8.3 复现输入

下列语句必须逐条调用 `CCJSqlParserUtil.parse(sql, p -> p.withSquareBracketQuotation(true).withAllowComplexParsing(false).withTimeOut(1000))`，再对非空结果调用 `new TablesNamesFinder<Void>().getTables(statement)`；记录异常/null，不能忽略失败后宣称全部成功。API 已按本地 5.3 制品核实。本轮探针文件位于系统临时目录，不作为产品源码或持久验证资产；输入留在此处便于复跑。

```sql
-- 1. select_join
SELECT c.name, SUM(o.amount) AS total FROM customer c JOIN orders o ON o.customer_id=c.id WHERE o.status=? GROUP BY c.name;
-- 2. insert_select
INSERT INTO order_summary(customer_id,total) SELECT customer_id,SUM(amount) FROM orders GROUP BY customer_id;
-- 3. update_subquery
UPDATE orders SET amount=(SELECT SUM(price) FROM order_item WHERE order_item.order_id=orders.id) WHERE id=?;
-- 4. delete_using
DELETE FROM order_item USING orders WHERE order_item.order_id=orders.id AND orders.status='CANCELLED';
-- 5. cte_select
WITH x AS (SELECT customer_id,SUM(amount) AS total FROM orders GROUP BY customer_id) SELECT c.name,x.total FROM x JOIN customer c ON c.id=x.customer_id;
-- 6. recursive_cte
WITH RECURSIVE t(id,parent_id) AS (SELECT id,parent_id FROM category WHERE parent_id IS NULL UNION ALL SELECT c.id,c.parent_id FROM category c JOIN t ON c.parent_id=t.id) SELECT * FROM t;
-- 7. merge
MERGE INTO target t USING source s ON (t.id=s.id) WHEN MATCHED THEN UPDATE SET t.amount=s.amount WHEN NOT MATCHED THEN INSERT(id,amount) VALUES(s.id,s.amount);
-- 8. select_star
SELECT * FROM customer c JOIN orders o ON c.id=o.customer_id;
-- 9. update_from
UPDATE target SET amount=s.amount FROM source s WHERE target.id=s.id;
-- 10. template_unexpanded：故意直接传入未渲染模板
SELECT * FROM orders <where><if test="id != null">id = #{id}</if></where>;
-- 11. invalid_control
THIS IS NOT SQL;
```

这些是纯文本解析输入，不得拿去数据库执行。

## 九、架构建议与交互方向

### 9.1 两套事实模型，共享导航而不混淆语义

建议划分为：

- 静态分析：预览快照 → AST/作用域 → 对象读写、逻辑步骤、字段来源 → 解释/图。
- 运行分析：agent 事件 → 独立执行实例 → 请求/事务上下文与采集质量 → 画像/时间轴。
- 对照层：通过有证据的候选匹配把静态快照与运行事件联系起来；不直接共用一个“万能图模型”。

静态快照须包含方言、数据库上下文/元数据版本、参数场景、源码版本、是否编辑过预览。运行事件须有进程启动身份、事件身份、时间与质量标记。缓存必须绑定这些上下文，而不仅是 SQL 文本。

### 9.2 图形实现

首期推荐复用现有 Swing/平台可选图能力，保留树表后备。调用归因树、简单关系图和时间轴不需要浏览器引擎。只有后期大图交互确实不能满足时再评估 JCEF。

JetBrains 官方优先建议标准 Swing UI；JCEF 使用前要检查支持性并正确释放资源。[S15] 本仓又存在 243/253/262 平台与可选模块差异，不能为一张图提高最低 IDE 版本或让无 Database/Diagram 插件环境整类加载失败。

新入口从完整预览的“分析”文字动作进入，内容区按需显示“结构/关系/来源/场景”，不继续堆日志根页签。主视图应可在窄侧栏工作，复杂图提供放大编辑器。分析默认不执行 SQL；点击关系只能定位、过滤或解释，不隐式跑库。

### 9.3 图的可信状态

每个结果应说明属于：静态已解析、条件式/部分解析、运行已观测、启发式关联或未知。边以文字和线型区分，不能仅靠颜色。界面必须能回答“这条边凭什么存在”。

SQL 文本、表列名、路径等都是不可信显示数据，做 HTML/SVG/Markdown 导出时必须转义；离线包禁外部脚本与网络资源，分享前预览脱敏范围。未知不填零，缺失不画成成功。

| 阶段 | 主要交付 | 依赖与退出条件 |

## 十一、待验证前提与成功指标

开工前要验证：

1. 解析器能否给出稳定的源码区间与作用域绑定；不能则首期只做语句级定位。
2. 指定语法子集的表/列来源能否在歧义和缺元数据时正确保留未知。
3. 代理/纯织入通道能否共享执行身份并明确能力差异；新旧协议可否平滑共存。
4. 多请求同线程、线程复用、异常退出、异步交接后上下文是否清理可靠。
5. 独立事件采集在 JVM8/17/21、各目标驱动与共存 agent 下是否安全。
6. 无 Database/Diagram/JCEF 时是否仍能完成核心分析、导航与复制。
7. dev 资产最终是否获准回流、其接口是否适合复用；不能提前当作 master 依赖。

建议试用验证目标，而非已测成绩：

- 对选定黄金语料，精确边正确率必须 100%；不能证明的边全部标未知/部分，不用猜边提升覆盖率。
- 用户能在一个预览内完成“找到写目标、解释结果字段、定位筛选条件”三项任务；记录完成时间与错误理解。
- 已声明覆盖的请求测试中，执行数量与业务端独立计数一致；丢包场景显示不完整，预算不判通过。
- 运行画像默认关闭额外采集；开启后的额外内存、CPU、P95 延迟以对照实验出数，未测前不宣传“零开销”。

具体验收矩阵、阶段任务、估算和开工门见配套开发计划。
