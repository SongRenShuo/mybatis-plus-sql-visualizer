## 一、总体结论

**主体结论第八次维持：默认配置下本插件对 IDEA 无体感性能影响。** 且本期是系列开始以来增量质量最好的一期——55 笔生产码提交里**零新增周期任务、零新增 EP 注册、零新增 EDT 索引查询**；容器面有两处新增会话级 Set（`resolvedClassKeys`/`resolvedMapperClassKeys`），与第十期已登记的 `resolvedStatementKeys` 同款取舍，量级可忽略。

本期五项实质发现，按处置紧迫度排序：

**第一，L110 只修了九条兜底里的一条，另一条同型缺陷仍在（P2）。** `ConvertToSqlAction` 的预览回调在 EDT，里面用 `&&` 串起九条兜底分支。`c5685aee8` 把 `tryMapperXmlMethodFallback` 的索引查询前置到了 compute 块，但 `tryJpaFallback` 的第 5 步 `tryRepositoryDeclarationFallback`（`ConvertToSqlAction.kt:511-524`）仍**同步调用** `previewRepositoryDeclaration`（`SqlPreviewService.kt:230`，不走 `previewAsync`），一路下到 `HibernateNamingConfigProbe.scanProjectConfigs`——`FilenameIndex.getAllFilesByExt` + `readText`，索引查询与读盘，全在 EDT。与 L110 同链、同回调、同类操作，首击必触发，真机上会重报同类 SEVERE。这是本期唯一建议立刻动的。

**第二，第十期三张券全部兑现（销账核实通过）。** 券01 弹窗链池线程化（`b64e71e43` + 车道 A/B 对齐 `516acc09d`/`f20a79205`/`ed081cbdd`）、券02 `windowStamps` 双帽兜底（`7b318a5d1`，键数帽 1024 × 单键帽 64，落在写入路径上故「面板不开」也覆盖）、券03 EXPLAIN 前热 cacheOnly（`ca1a38a3b`）。三处逐行核对在位。

**第三，真机已经产生并已修复一条 SEVERE SlowOperations，其教训已进账本（L110）。** 2026-11-26 真机 runIde 在 `ConvertToSqlAction.tryMapperXmlMethodFallback` 链上连报两条 `SEVERE - #c.i.u.SlowOperations`（`Plugin to blame: MyBatis SQL Visualizer version: 2026.11.26-beta.2`），根因是 `previewAsync` 的 **EDT 回调**里查了自定义索引；修复提交 `c5685aee8`，配结构守卫。价值在于它暴露的形态是「`previewAsync` 回调设计上就在 EDT」这一系统性盲区——单测与门禁都看不出来。**也正因为是同一个盲区，第 1 条才漏了下来。**

**第四，本轮新增两个成本点，均为登记级但值得收窄（§4.2/§4.3）。** 一是 gutter 首渲染的「补全上下文预热」链**没有每项目额度**，每打开一个 mapper XML 就踢一次实体解析（该链冷态历史实测 13.3s，`XmlSqlGutterLineMarkerProvider.kt:146` 注释自带读数）；同批的装配预热有每项目 2 次额度，两条链预算口径不一致。二是让位开关变更会触发**全项目全量 `DaemonCodeAnalyzer.restart()`**（`PluginSettingsPanel.kt:1386`），单用户改一个 gutter 开关的代价是重新分析所有已打开项目——平台 API 支持按文件 restart（同仓 `SqlPreviewPanelExecution.kt:2460` 即 `restart(psi)` 形态）。

## 四、本期新发现

### 4.1 Repository 声明行兜底仍在 EDT 上查索引 + 读盘（P2，本期最高优先级）

L110 修掉了 `tryMapperXmlMethodFallback` 的 EDT 索引查询，但**同一条 `onResult` 短路链里的另一支没一起修**。

`ConvertToSqlAction.actionPerformed` → `previewAsync(...) { result -> ... }` 的**回调在 EDT**（`ConvertToSqlAction.kt:196-214`），里面用 `&&` 串起九条兜底：`tryMapperXmlMethodFallback`（已修，前置 `mapperXmlTagsFor` 到 compute 块）/ `tryMapperAnnotationMethodFallback` / `tryIbatisCallFallback` / `tryIbatisMethodFallback` / `tryHqlFallback` / `tryNamedQueryFallback` / `tryJdbcTemplateFallback` / `tryJpaFallback` / `tryMethodBodyStringSqlFallback`。

其中 `tryJpaFallback`（`:473`）的第 5 步 `tryRepositoryDeclarationFallback`（`:511-524`）**同步调用** `service.previewRepositoryDeclaration(method)`——注意这个函数签名里没有 `previewAsync`（`SqlPreviewService.kt:230`，普通同步函数），与同函数内其他分支（`:477`/`:484`/`:491` 都走 `previewAsync`）不同构。

调用链与成本：

```
previewRepositoryDeclaration (EDT)
  └ JpaCrudOperationConverter.convertRepositoryDeclaration
      └ JpaEntityResolver().resolve  → EmbeddedColumnNaming.resolveDetailed
          └ HibernateNamingConfigProbe.projectUsesComponentPath (EmbeddedColumnNaming.kt:67)
              └ scanProjectConfigs (HibernateNamingConfigProbe.kt:196)
                  ├ FilenameIndex.getAllFilesByExt(project, ext, projectScope)   ← 索引查询
                  └ readText(it)                                                 ← 读盘
```

**触发条件**：光标停在 Repository 接口**声明行**、方法名在 `REPOSITORY_METHODS` 名单内、且不是 `@Query`（走别的分支）。前八条兜底全部未命中才会走到这里。

**成本**：`FilenameIndex` 是索引查询，`readText` 是文件读——两者在 EDT 上都是平台明令禁止的慢操作（L110 的两条 SEVERE 就是这个判据）。有缓存兜着：`cached(project, scopeKey)`（`:163-171`）按 `PsiModificationTracker.modificationCount` 做戳，**命中时是 map 查表 O(1)**；但**首击**要付完整的一轮索引 + 读盘，估算数十至数百毫秒（代码级推算，取决于工程里配置文件数量）。

这不是理论风险：它与 L110 是同一条链、同一个回调、同一类操作，L110 已在真机报出 SEVERE。**首击必触发一次索引查询**，平台在真机上会重报同类 SlowOperations。

### 4.2 让位开关变更触发全项目全量重分析（建议收窄）

`PluginSettingsPanel.refreshGutterLineMarkers()`（`PluginSettingsPanel.kt:1380-1392`）：

```kotlin
ApplicationManager.getApplication().invokeLater({
    ProjectManager.getInstance().openProjects.forEach { proj ->
        if (!proj.isDisposed) {
            runCatching { DaemonCodeAnalyzer.getInstance(proj).restart() }
        }
    }
}, ModalityState.any())
```

三个成本特征：

1. **`restart()` 不带 PSI 参数 = 全项目全量重分析**，不是只重跑 line markers。gutter 图标是 `LineMarkerProvider` 的产物，重跑整个 daemon（含 inspection、annotator、高亮）远超必要成本。
2. **遍历 `openProjects` 全部项目**，不是当前项目。
3. 触发条件是用户在设置页切换「同类插件共存让位」——一个纯 gutter 显示开关。

同仓已有更精确的形态可对照：`SqlPreviewPanelExecution.kt:2460` 用 `DaemonCodeAnalyzer.getInstance(proj).restart(psi)` 做**按文件** restart。改成遍历打开的文件逐个 `restart(psi)`，或直接退化为只重画 gutter 区域，都比重启全项目 daemon 便宜一到两个量级。

单次触发（用户手动切开关不会连点），不影响日常使用；但它把「一个显示开关」的价格标成了「全项目重新分析」，属于该修的成本错配。

### 4.3 补全上下文预热缺每项目额度（建议补齐）

`XmlSqlGutterLineMarkerProvider.kickFileWarmers`（`:141-158`）在文件首次渲染 gutter 时踢三条预热：

| 链 | 去重粒度 | 每项目额度 | 冷态成本（历史读数） |
|---|---|---|---|
| `prefetchMbgExample` | 每语句 | 无限（但仅 MBG Example 形态命中） | — |
| `warmCompletionContextOnce` | **每文件一次，无项目额度** | **无** | **13.3s**（`:146` 注释自带：`pre-assembly:completion=13280ms`） |
| `PreviewAssemblyWarm.warmOnce` | 每文件一次 | **每项目 2 次**（`WARM_FILES_PER_PROJECT`） | 351ms 级 |

装配预热有明确的每项目额度（`PreviewAssemblyWarm.kt:55` `WARM_FILES_PER_PROJECT = 2`，超限即退并回滚去重标记），而更贵的补全上下文预热**没有任何项目级预算**——用户冷启动后连续打开 10 个 mapper，就会踢 10 次实体解析预热。

守卫：`GutterWarmScheduler` 已把「踢的时刻」后移 5s（`sqlvis.gutter.warmDelayMs`），缓解了冷窗口竞争（F2 的收益），但没有改变「踢多少次」的上界。两条链共用同一个信号却用两套预算口径，属于设计与实现的不一致。

### 4.4 gutter 逐 leaf 判定的顺序税（纯重排可收）

13 个 JAVA 语言的 `lineMarkerProvider` 对 Java 文件每个 leaf 都会回调 `getLineMarkerInfo`。标准形态（`JpaGutter` / `CriteriaQuery` / `CustomDaoHql` / `Hql` / `JdbcTemplate`）是**先类型早退、再取 settings**：

```kotlin
if (element !is PsiIdentifier) return null      // 一行解决绝大多数 leaf
val gutterState = runCatching { PluginSettings.getInstance().state }.getOrNull()
```

但有 4 个 provider 顺序相反：

| provider | settings 取值 | 类型早退 |
|---|---|---|
| `AnnotationSqlGutterLineMarkerProvider` | 第 5 行 | 第 9 行（`PsiJavaToken` + `AT`） |
| `JpqlGutterLineMarkerProvider` | 第 5 行 | 第 9 行（`PsiJavaToken` + `AT`） |
| `NamedQueryGutterLineMarkerProvider` | 第 5 行 | 第 9 行（`PsiJavaToken` + `AT`） |
| `StringSqlMethodGutterLineMarkerProvider` | 第 5 行 | 第 8 行 |

`PluginSettings.getInstance()`（`PluginSettings.kt:977-980`）每次做一次 `getService` 查找 + 一个可空探针调用，外面再包 `runCatching`。对一个典型 Java 文件，`AT` token 只占 leaf 的极小比例，绝大多数回调的完整路径就是「服务查找 + try/catch + 返回 null」。

量级推算：`getService` 是 map 查表量级（亚微秒），单次忽略不计；但这是**每次 daemon pass × 每 leaf × 4 个 provider** 的固定乘数。属「有界但可再收窄」形态，非体感问题。收法极简：把这 4 处的 settings 两行移到类型早退之后，语义逐值等价（组关时只是少省一点重活，而这三处的「重活」本来就只是一次 token 类型判断）。

顺带一句口径提醒：F36 那轮把「每元素 3 次 app 级查找收敛为 1 次」是有效优化，但收敛的是**次数**，没管**顺序**——两个维度都要看。

### 4.5 D256 链方法启发无缓存（登记，附带一条线程口径澄清）

D256（自研 Wrapper 子类识别）给 `isWrapperVariable` 加了第三条兜底：声明类型简单名不在基类型白名单、但以 `Wrapper`/`Join`/`Chain` 结尾时，走 `wrapperTypeFromChainMethods`（`WrapperLocator.kt:1914`）。该函数做一次 `ReferencesSearch.search(variable)` 收集分步调用名，必要时再跑第二次判消费者（`isReferencedByMpConsumer`，`:1939`）。

缓存状态是**不对称**的：父链识别有 `WeakHashMap<PsiClass, Optional<WrapperType>>` 类级缓存（连否定结果都缓存，`:1792`），链方法启发**一条都没有**。因此同一个「名字像 Wrapper 但父链接不到 MP」的变量，每次 daemon pass 都要重付 `ReferencesSearch`。

**线程口径澄清（推翻一条初判）**：`WrapperAnchorDetector.anchorElement` 是这条链唯一的 gutter 入口（`SqlGutterLineMarkerProvider.kt:50`，在 `getLineMarkerInfo` 里）。项目内 `PreviewReceiverResolver.kt:20` 明确记载 **`getLineMarkerInfo` 运行在后台 daemon 线程，无 EDT 风险**——所以这**不是** EDT 缺陷，是后台线程的重复计算。触发面也窄：需要「自研 `*Wrapper` 子类 + 父链完全接不到 MP/MPJ」两个条件同时成立，而 D256 的典型用户（复制改名库）恰好命中。

成本：`ReferencesSearch` 是索引检索，本仓既有实测读数在 1.6~2.4 秒级（`MbgExampleCallResolver.kt:101`/`:271` 注释），但那是大工程 + 冷缓存；daemon 再现时索引热、引用数少，实际是毫秒级。可接受但不优雅，收法是照父链那层补一个类级 `WeakHashMap` 缓存。

### 4.6 附带发现：缺失片段框「从文件选择」的回填必然丢失（功能缺陷，非性能）

调研过程中顺带确认的一处**功能性**缺陷，与性能无关但同属 `nonModal` 误用族，一并登记。

`MissingFragmentDialog` 是模态对话框（`DialogWrapper(project, true)`，`ui/standalone/MissingFragmentDialog.kt:29`），其「从文件选择」的回填写作：

```kotlin
app.executeOnPooledThread {
    val text = MapperFileLoader.loadText(file) ?: return@executeOnPooledThread
    app.invokeLater({
        if (isDisposed) return@invokeLater
        area.text = MissingSqlFragmentSupport.extractFragment(text, refid) ?: text
    }, ModalityState.nonModal())      // ← 问题在这
}
```

`ModalityState.nonModal()` 的语义是「**没有模态对话框时**才执行」。本框自身是模态的，所以这个 runnable 会一直排在队列里，直到对话框关闭、模态退栈才被泵到——届时 `isDisposed` 已为 true，被守卫直接丢弃。**整条链必然空转，回填永远不发生。**

同仓有正确先例：`CommunityDialog.startLoading`（`feedback/CommunityDialog.kt:86`）在完全相同的「池线程取结果 → 回填模态框内组件」场景用的是 `ModalityState.any()`。回填目标是 `JBTextArea.text`（纯 Swing，不改 Document/PSI），不需要 write-safe 资格，用 `any()` 安全。

影响面：只有「点『从文件选择』」这一条路径；手输与粘贴正常。所以用户感知是「选了文件没反应」。

## 七、结论与建议

1. **维持主体结论**：默认配置无体感影响，第八次维持，且本期增量是最干净的一期（四个「零新增」）。
2. **立刻收 Repository 声明行兜底**（§4.1，P2）：照 L110 同法，把 `previewRepositoryDeclaration` 的解析前置到 `previewAsync` 的 compute 块，回调只消费预解析结果。这是唯一一条「与已确认真机 SEVERE 同链同型」的，优先级高于其余全部。
3. **建议收窄让位重算**（§4.2）：改按文件 `restart(psi)` 或仅重画 gutter。唯一一条「成本与意图明显错配」的。
4. **建议补齐 ctx 预热额度**（§4.3）：与装配预热对齐每项目预算，两条链口径统一。
5. **顺手重排 4 个 provider 的判定顺序**（§4.4）：零语义变更的纯重排。
6. **可选补 D256 链方法启发缓存**（§4.5）：后台线程重复计算，非 EDT 问题，优先级最低。
7. **维持登记不立项**：`pasteReparseTimer` 待命轮询、EXPLAIN bind 轮询（有界自终止）、MCP 壳类一次性成本、`warmedContextFiles` 会话级不清理、F47 入口收敛。
8. **方法论沉淀**：L110 暴露的不是「某处漏改」，而是「`previewAsync` 的 `onResult` 回调在 EDT，但名字听起来像全链路异步」这一命名陷阱——本期第 1 条正是同一盲区的第二个受害者。新增预览入口时须把「这段代码在哪个线程」当第一等问题，且**同一回调里的 `&&` 短路链要整条一起审**，只修一条分支等于没修。
