## 三、核心数据链

### 3.1 自定义索引（`B.b`，整个设计的心脏）

`ScalarIndexExtension<String>`，要点（`B/b.java`）：

- `ID.create("MybatisCodeHelperIndexer6")`，`getVersion() = 7`
- `DefaultFileTypeSpecificInputFilter(XML)`，`dependsOnFileContent() = true`
- `DataIndexer.map(FileContent)`：对根标签为 `<mapper>` 的 XML 产出**键→Void** 的 map（键即值，只为查询）：
  - `MybatisMapperNameSpace@<namespace>` —— namespace 一个键
  - `MybatisFilePath@<文件路径>`
  - `MybatisResultMapId@<ns>.<id>`、`MybatisSqlId@<ns>.<id>`（注意：只对 `<sql>` 片段与 `<select>` 的 resultMap 引用建键；`insert/update/delete` 的语句 id **没有**建 SqlId 键——语句级定位走 §3.3 的文件内扫描）
  - `MybatisSelectReferenceResultMapId@...`
  - 哨兵键 `java.min$##.myMapperLocations.mapper_666` —— 「此文件是 mapper XML」，用于一次查询枚举全部 mapper 文件
- 索引期解析走 PSI（`FileContent.getPsiFile()`），平台按文件增量维护：只改一个 XML 就只重索引那一个，**不存在「全工程清单重建」这个概念**。

作者还内置了性能自检动作（Internal 菜单 `MybatisCheckFindMapperTimeUsage`，`view/j/a.java`），用 `Stopwatch` 实测三条索引查询的耗时——说明索引查询耗时是作者自己盯的指标（我们对应物是 `indexScanCount` 测试缝）。

### 3.2 namespace → XML 文件：一次索引查询即答案

`af/x.java#a(PsiElement, Project, String)`（namespace 找 mapper DOM）：

```java
if (state.getUseNewIndex()) {          // Profile.java L133 默认 true
    for (VirtualFile vf : FileBasedIndex.getInstance().getContainingFiles(
            B.b.a, "MybatisMapperNameSpace@" + qualifiedName,
            af.af.b(element) /* SearchScopeUtils */)) {
        Mapper m = toDomMapper(project, vf); ...
    }
} else { /* 旧路径：DomService.getFileElements(Mapper.class, ...) 全枚举后逐个比 namespace */ }
```

- O(1) 化程度：**一次索引键查询**（持久化倒排，平台增量失效），无 TTL、无单槽、无「pending→restart daemon」状态机。
- 范围收窄有开关（`af/af.java#b` = `SearchScopeUtils.getSearchScopeFromSettings`）：用户设置 PROJECT → `allScope`；否则 `moduleWithDependenciesAndLibrariesScope(element)` —— 多模块大工程可按模块收范围。
- 保留旧路径做开关回退（`useNewIndex`），索引出问题时用户可切回 DOM 枚举——**自家索引带逃生门**。

### 3.3 两个方向的 gutter 实际链路

五个 marker 全部继承平台 `RelatedItemLineMarkerProvider`。注意：经 `javap -c` 核对平台发行件（ideaIU-2024.3.7.1 `lib/app-client.jar`），该基类 **`getLineMarkerInfo` 直接 return null，`collectSlowLineMarkers` 才调 `collectNavigationMarkers`** ——即 MPJ 的全部 marker 解析都在**慢趟（后台）**完成，与我们的形状一致（此前以为它跑快趟，实测推翻）。

**Java→XML（`view.A`，UAST）**：
1. `UastUtils.getUParentForIdentifier` 拿 UClass/PsiMethod（Kotlin 免费）；
2. `checkMappingIsJavaInterface` 开关（默认）要求接口，`qualifiedName` 作 namespace；
3. `af.x#…` 索引查询拿 List\<XmlFile\>；方法行再对每个候选文件调 `af/E.java#a(XmlFile, String)`——在根标签直接子级里线性找 `id==方法名` 的 `XmlAttribute`（单文件 O(children)，与我们 `findStatementTag` 同形）；
4. 可选 `baseClassSearchXml`（`ClassInheritorsSearch`）：继承 BaseMapper 的子接口也能带出 XML（`view.f.e#getBaseClassSearchXml` 开关）。

**XML→Java（`view.J`）**：
1. XML_NAME token 且是 `namespace`/`id` 属性名首 token；
2. `isMybatisFile`：XmlFile + `.xml` 后缀 + rootTag.name=="mapper"（`af/E.java#a(PsiFile)`，纯属性判断）；
3. namespace 属性 → `af/W.java#a(PsiElement, namespace)`（`JavaPsiFacade.findClass`，StubIndex 支撑）找接口，产出「跳接口类」marker；
4. 语句 id 属性 → `af/E.java#a(XmlTag)`：**CachedValuesManager 按元素缓存** `Pair<PsiClass, PsiMethod>`，依赖 `PsiModificationTracker.MODIFICATION_COUNT`（`af/E.java` L1384 区域）；provider 内 namespace→findClass→`getAllMethods()` 按名比对。

### 3.4 W.d：全部 mapper 接口的 O(1) 名单（Java 图标用）

`W/d.java`（project service）——与我们被替换掉的「全 XML 清单 + TTL」神似但关键处不同：

- 构造期订阅 `VirtualFileManager.VFS_CHANGES`（BulkFileListener），事件过滤：`.xml` 的 create/delete/move/rename、xml 文件 content change 才触发（`#a(VFileEvent)`）；
- 触发后 `AtomicBoolean` CAS 去重 → `DumbService.smartInvokeLater` → 后台线程 → `runReadActionInSmartMode` → `FileBasedIndex.getAllKeys(MybatisCodeHelperIndexer6, project)` 剥前缀得 namespace 集合 → **volatile unmodifiable Set**；
- 启动即建（构造函数尾调 `a()`）；查询 `a(fqcn)` = HashSet contains，O(1)。

即：**底座仍是索引（失效语义交给平台），VFS 监听只做「有 xml 动静就重刷」的廉价触发**，不像我们曾经的「FileTypeIndex 全扫当唯一数据源」。无 TTL——因为数据源本身增量、不会过期。

### 3.5 失效设计总览

| 缓存 | 粒度 | 失效机制 | TTL |
|---|---|---|---|
| namespace→XML | 平台索引 | 平台增量（dependsOnFileContent） | 无 |
| 语句→方法（XML 侧） | 每 XmlTag 一个 CachedValue | `PsiModificationTracker.MODIFICATION_COUNT` | 无 |
| 方法→XML（Java 侧） | 无缓存（索引查询+文件内扫描本身够快） | — | 无 |
| mapper 接口名单 | 项目级 volatile Set | VFS 监听触发、smart 模式后台重建 | 无 |
| 自有 EP `modificationTracker` | — | `I.a`=Java 语言级 tracker（`PsiModificationTrackerImpl.forLanguage(Java)`）；`I.f`=设置变更 `SimpleModificationTracker`（`I/e.java`），作为 CachedValue 依赖注入 | 无 |

配合 `postStartupActivity l.c` **强开 Registry `psi.modification.tracker.per-language`**——Java 改动不再整体作废 XML 侧缓存（反之亦然）。这是细粒度失效的关键一环：平台默认全局 MODIFICATION_COUNT，per-language 开关让「改一个 Java 文件」不会作废全项目 XML 的 CachedValue。

### 3.6 dumb 窗与冷启动

- 五个 marker 均未声明 dumbAware（plugin.xml 无 dumbAware 属性），即**索引期不出图标**——MPJ 接受「索引没完成就不画」，而不是我们的 dumb 乐观产出（F1-b）。它敢这么做，是因为索引就绪后第一次查询就是秒级答案，不存在「慢趟饿死→图标长期缺席」的坑。
- 启动期开销集中在两处且都后台化：索引（平台通用调度）+ `W.d` 名单（构造时触发、smartInvokeLater 后台）。`l.c` 的激活检查放独立 Thread，不抢启动。
- `daemon.changeLocalityDetector view.I`：把「含 `@Table` 的 XML 注释」与「mapper 文件内的空白改动」判定为需要整文件重跑的 dirty scope——是**保正确性**（注释里有配置语义）而非提速项。

## 四、与我们现状的对照

我们侧基线：`MapperNavigationLineMarkerProviders.kt` + `MapperXmlLocator.kt`（T-GutterFirstOpenDelay 后形态：慢趟 + FileTypeIndex 全扫清单 + 头扫提 namespace + 30s TTL 单槽 + stale-while-revalidate + pending 期 missedWhilePending → daemon restart + 会话级正缓存 + dumb 乐观产出）。

| 维度 | 我们 | MPJ | 差距实质 |
|---|---|---|---|
| namespace→XML 数据源 | FileTypeIndex 全扫 XML + 头扫建清单（30s 代际） | 自定义 ScalarIndex 索引期建倒排 | 它把成本付在索引期增量；我们在运行期付全扫，且每次换代重付 |
| 查询复杂度 | 命中候选后仍要对清单做 namespace 过滤（清单内 O(n) 比对） | `getContainingFiles` 一次键查询 | 无本质差（我们清单过滤也是 O(n) 字符串比对，但清单本身 30s 全量重建一次） |
| 失效 | TTL + isValid 兜底 + 异步重建 + daemon restart | 平台索引增量，零自管 | 我们的 pending/restart 状态机本质是在补「数据源不是索引」的坑 |
| 负结果 | memo 负缓存（有槽才负缓存） | 无需负缓存（索引查询本身快） | 我们负缓存是给慢查询止损的 |
| dumb 窗 | 乐观产出 + 智能后自愈（F1-b） | 不出图标 | 各有取舍：索引就绪后它不需要乐观；我们因「查询可能落空」才需要 |
| Kotlin 支持 | Java-only | UAST 一口覆盖 Java+Kotlin | 顺带收益项 |
| 多模块收范围 | projectScope 全工程 | 可配置 moduleWithDependenciesAndLibrariesScope | 大多模块工程收益明显 |
| 正缓存 | 会话级 resolvedStatementKeys（无失效，宁多不缺） | 无（依赖精确失效） | 我们 F1-a 是防御性设计，若数据源换成索引可简化 |

## 五、可借鉴点 Top N

1. **注册自定义 `ScalarIndexExtension`（namespace 建键）**——最大借鉴点。把 `MapperXmlLocator.rebuildSlotSync` 的「FileTypeIndex 全扫 + 头扫 + TTL 单槽」整体替换为一个 `ScalarIndexExtension<String>`：`DataIndexer` 里读 FileContent 的 PSI，产 `MapperNamespace@<ns>` 等键（可完全照抄键面）。落点：新文件 `src/main/kotlin/.../index/MapperNamespaceIndexExtension.kt` + `MapperXmlLocator.locateUnderRead` 改为 `FileBasedIndex.getContainingFiles(MapperNamespaceIndex, "MapperNamespace@"+ns, scope)`；`FileListSlot`/TTL/pending/restart 全部可删。收益预估：4800 XML 下 Java→XML 首跳从「秒级全扫（头扫 2~3s）」降到毫秒级；冷启动图标随索引就绪自然出现，`missedWhilePending`/restart 逻辑消失。风险：索引 version 升级触发一次全量重索引；`dependsOnFileContent=true` 会让每次 XML 编辑多付一次该文件的 PSI 解析（单文件粒度，可接受）；dumb 期查询仍会等索引——F1-b 乐观产出语义可原样保留（数据源换了，判定层不用动）。这是平台提供的正规失效语义，比自管 TTL 稳。
2. **索引键面顺带带 resultMap/sql 引用与文件路径**（照抄 MPJ 键清单）——一次 indexer 改动服务多个调用方（我们后续的 resultMap/inspection 类功能可复用同一索引），边际成本趋零。
3. **查询范围可配置收窄到模块**（`SearchScopeUtils.getSearchScopeFromSettings` 形态）——多模块工程把 `GlobalSearchScope.projectScope` 换成 `moduleWithDependenciesAndLibrariesScope(element)`（默认仍 project，开关进 PluginSettings）。收益：大 monorepo 下跨模块误命中减少、查询更快。风险：同 namespace 跨模块多命中语义要跟现状对齐（我们现在取索引序第一个并留痕）。
4. **W.d 的「VFS 监听 + 索引 getAllKeys + smart 模式后台」名单形态**——我们暂无「全部 mapper 接口名单」需求；若未来做 Java 文件图标/inspection 全量比对，照这个抄（底座索引、监听只触发、CAS 去重、runReadActionInSmartMode）。不是当前痛点，登记备查。
5. **强开 `psi.modification.tracker.per-language`**——若我们后续引入按 `PsiModificationTracker` 作依赖的 CachedValue（比如替换会话级 `resolvedStatementKeys` 正缓存），postStartup 强开此 Registry 可让 Java/XML 侧失效互不牵连。风险：全局 Registry 改动影响面是整个 IDE 的 PSI 缓存策略，需评估；MPJ 敢开是因为它重度依赖 MODIFICATION_COUNT。
6. **性能自检动作**——MPJ 的 Internal 菜单 Stopwatch 动作（`view.j.a`）值得照抄一个 dev-only action：一键打印「namespace 索引查询耗时 / 候选数」，真机验收 gutter 性能时不用靠断点+测试缝。

不建议照抄的：dumb 窗不出图标（我们有用户可见的「冷窗图标缺席」痛点，F1-b 乐观产出是对的方向，保留）；`useNewIndex` 双路径开关（我们直接上索引，保留旧同步分支只服务单测即可）；DOM `dom.fileMetaData` 底座（我们的场景轻于它的 completion/inspection 面板需求，ScalarIndex 足够）。
