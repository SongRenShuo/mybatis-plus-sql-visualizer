## 2. 当前插件功能与定位（v2026.9.14-beta.2）

**插件**：SQL Visualizer（id `cn.song.mybatisplus.visualizer.mybatis-plus-sql-visualizer`，Marketplace 页 33633），master 最新发行 v2026.9.11，内测 v2026.9.14-beta.2（仅走 Gitee 抢先体验通道，正式版 2026.9.14 发行时并入）。免费开源，IDEA 2024.3+（sinceBuild 243，无 untilBuild），运行时仅依赖 JSqlParser。

**一句话定位**：IDEA 内多 ORM 的 SQL 调试五环闭环——写前静态预览、跑后日志还原、原地执行验证、真实计划诊断、资产生成。本轮增量集中在把五环的每一环做深，外加三条新线：自更新免重启热替换、SQL 列表可视化增强（颜色标记/三显示模式）、错误一键上报。

### 4.2 MyBatis SQL Analyzer 深挖结论（专项报告：`docs/调研报告/MyBatisSQLAnalyzer 对标调研（内部资料库）`）

初筛判定它是「基线后唯一功能正面撞车者」（gutter icon 点击预览动态标签解析后的 MyBatis SQL）。源码级调研推翻了表面的威胁感：所谓「解析」是正则注释标注器——`DynamicSqlParser` 用一个 DOTALL 正则把 `<if>/<foreach>/<where>` 等标签转成 `/* IF ... */` 式 SQL 注释夹注，条件不求值、无 OGNL、所有分支原样保留，产物多数不可执行；文件头注释自述「无法在 IDE 中获取运行时参数值」。触发面仅 3 类（注解四件套/XML 四标签/mapper 方法行），不解析 `<include>/<sql>`，兼容墙卡在 251.*（2025.2+ 全装不上），7-13 后停更，0 评论 0 star，仓库无 LICENSE。执行走自带 JDBC 独立配置栈，EXPLAIN 五库无国产方言。唯一独有点是 OpenAI 兼容的 AI 流式 SQL 分析（171 行客户端 + 设置页 + Markdown 面板）。

**威胁评级：低**。响应动作：无需功能响应；「同名标签嵌套正则截断」「`<where>` 多分支清理失效」两个场景进金样矩阵防御清单即可；吸收两点见 §8.3（`${}` 注入标注）与 §8.4（AI 可选集成印证）。

### 4.3 Mybatis Log Ultra 动向（N-10 跟踪收尾）

上轮列它为「最可能长出来的对手」，本轮下调：稳定渠道 3.5 个月未发版（4.0.20，2026-05-25），8 天仅 +23，增速停滞；评分升到 4.90 说明口碑好但盘子不再扩大。其 changeNotes 确认的演进方向（Arthas agent 增强包远程打印完整 SQL、代码行级导航、按请求过滤）与本插件执行期标记路线同向，其中「agent 增强捕获」正是 M56 已在分支交付的方向。N-10 的跟踪结论归档：高口碑、停更、增长停滞，威胁评级从「中」降为「低」，无需抢功能响应窗口。

**MCP 能力规划**（本轮最重要的新增建议，完整方案见专项报告 §5）：

DBX 的 MCP 分发模式（19 工具、read_only/allow_dangerous_sql 双 bool 三级权限、连接白名单、中央策略不可被客户端环境变量放大、fail-closed 校验链、stdio + Streamable HTTP 双传输）是它 4 个半月 19.3k star 的核心引擎之一，且用户本机已是重度使用者。DBX 还在产品内（桌面 AI 面板）与产品外（向 Claude Code/Codex 等 8 种外部 AI CLI 注入自身 MCP server）双向跑通了该模式，其「Ask 模式只读四件套工具 / Agent 模式才追加执行」的双模式工具面是 P1 收敛口径的直接参照。本插件 P1 建议只做三个纯只读工具：`sqlv_render_sql`（源码片段/路径+行号 → 渲染后可执行 SQL，13 类触发面的确定性渲染是竞品 MCP 给不了的）、`sqlv_schema_context`（IDE 数据源紧凑表列上下文，凭证不出 IDE）、`sqlv_explain`（SELECT 白名单 + 七方言计划）。架构选插件内嵌 stdio server（IntelliJ 本身是常驻 JVM，无需 DBX 式独立二进制），权限起步只读、工具白名单固定、零弹窗红线兼容（agent 触发一律不弹确认，拒绝走 MCP error）。P2 补日志还原/执行记录/资产生成工具，P3 写通道无限期搁置（若开必须继承 DBX 四原则）。

**同日补充调研：IDEA ACP 与平台原生 MCP（详见 `docs/调研报告/20260914-0317-IDEA-ACP与平台AI原生能力-调研报告.md`，本机 262.10315.125 解包/javap 实证）**。两个决定性发现直接改写上面的架构选择：

1. **IDEA 平台已内置 MCP Server 插件体系，N-12 主轨改为「注册进平台」**。262 内置 `com.intellij.mcpServer`（253 同 EP，243 可装 Marketplace 1.0.30），提供公开的 `mcpServer.mcpToolset` 扩展点 + `@McpTool/@McpDescription/@McpToolHints` 注解 DSL，官方 README 明文支持下游插件注册工具；且该插件不依赖 AI Assistant，干净 IDE 即可用。本插件三工具写成一个 `SqlVisualizerToolset : McpToolset`，即自动出现在 AI Assistant、Junie、经 `use_idea_mcp` 开启的 ACP agent、外部 Claude Code/Cursor 等所有 MCP client 面前——零 launcher、零端口、零弹窗，只读声明用平台原生 `@McpToolHints(readOnlyHint=TRUE)`，白名单由 `idea_mcp_allowed_tools` + `mcp.server.tools.filter` 承担。「插件内嵌 stdio server」降级为可选兜底，移出一期；将来写类工具吸收 ACP 四值权限（allow_always 记忆式白名单），交互确认 ride `elicitationProvider` 不自建弹窗。
2. **「ride 262 平台自带 LLM API」被证伪，N-14 回退 OpenAI 兼容单路径**。干净 262 平台全量搜证无任何 LLM/`core.ai` 模块、SDK 公开文档（llms.txt）无 LLM API 页、limited access 依旧，叠加 2026-06 Marketplace 15 个恶意插件窃取 AI key 事件，平台短中期不会对第三方开放。AI Assistant 的模型额度不构成第三方插件 API。N-14 以 OpenAI 兼容单路径 + PasswordSafe 存 key 为主路径不变。

用户「尽量复用 IDEA 原生能力」的产品哲学在 ACP/平台 MCP 这件事上得到一次实证回报：平台原生体系已经把最难的部分（承载、传输、client 自动配置、权限设置）做完了，插件只需要贡献工具面。

## 9. 风险

4. **AI 替代（延续，出现对冲手段）**。锚定 IDE 深度集成、执行期确定性、方言正确性背书的立场不变；N-12 的 MCP 化正是把「AI 替代」翻转为「AI 依赖」的对冲——让 agent 用本插件而不是绕过它。

## 10. 落地优先级建议

如果只做三件事：**合流清账**（r2 分支 63 提交回 master + 文案回补 + N-9 冲突决断，已花的成本兑现）、**N-12 MCP 一期立项**（三个只读工具，主轨已修订为注册平台 MCP Server 体系，成本较自建再降，占住 agent 生态位）、**N-13 预览交互吸收包**（四件套全部落在已有链路，用户可感知度最高）。

一句话总结本轮：上轮的问题是「这么强的功能，为什么没人知道」；本轮多了一个更扎心的——「已交付的成果还在分支上睡觉」；也多了一个机会——「让 AI agent 成为下一批用户」。
