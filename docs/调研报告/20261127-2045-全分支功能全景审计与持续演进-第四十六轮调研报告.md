### 0.1 一条硬接口事实：`searchPlugins` 的 `max` 上限是 **24**

`https://plugins.jetbrains.com/api/searchPlugins?search=<kw>&max=N` —— **N ≥ 25 一律 400 `{"statusCode":400,"message":"Invalid max value: N"}`**（实测 25/30/50/60/100/200 全拒，24 通过）。

后果与对策：
- r45 报告里的「157 / 250 / 63」是响应的 **`total` 字段**，不是 `max` 的返回值。想拿我方位次必须用 **`offset` 分页步长 24** 扫描。
- 只取前 24 名会把「位次 >24」全部误判为「未上榜」。本轮首次翻页后立刻发现：r45 记「`mybatis` 39/250」，实际**本轮是 63/249**，两者都在 24 名之外，说明 r45 那次一定做了分页——但方法未写进报告，下一轮若照抄 `max=200` 会直接 400 并把全部关键词判成「未命中」。

**「可见度已经解决，转化和信任还没解决；而分支里躺着一整套能直接补上这两块的成品——安全加固、国产方言翻倍、检查与体检、性能券——它们没进 master。」**

3. **分支里躺着的正是补这两块的弹药**，而且**成本比历史判断低得多**：
   - `t-branch-merge-route` 相对当前 master 的 **`src/main` 双改文件 = 0**（主控亲自 `comm -12` 复核确认），内容含 **24 项安全审计闭环 + 45 条隐藏 bug 修复 + 10 个国产方言**。把它合进来，等于一次性拿到「稳定性信任」与「信创差异」两块资产。

   - 但 insight 的相对成本最高（**双改 36 文件**），dev 居中（**双改 12**）。

**一句话的顺序判断**：先合 route（零冲突、纯收益），再合 PEV（低冲突、纯增强），dev 与 insight 需要一次明确裁决（冲突成本 12 vs 36，但 insight 的能力面更补短板）——而**「D220 二选一」这个提法本身应该被放弃**，改为「按冲突成本与能力缺口分批吸收」。

## 三、竞品动态：CHP 三天三版，且打向稳定性

**本轮最重要的市场事件：MyBatisCodeHelperPro 在 11-23 / 11-24 / 11-27 三天连发三版。** r45 只记到 3.7.1（11-24），**3.7.2 是今天刚发的**。

### 3.1 三版各自打什么（原文抓取）

**3.7.0（11-23）** —— 能力面扩张
- `[NEW]` Mapper 接口输入 `findById.sql` 按 Tab 生成接口方法 + 对应 SQL
- `[IMPROVE]` 默认启用 Mapper 方法调用补全
- `[IMPROVE]` **重做 Mapper XML 的 SQL 格式化**（整文件/选区/当前语句，保留动态标签、参数、字符串、注释，跳过可能改变语义的语句）
- `[NEW]` **从数据库同步已有 Java 实体和 Mapper XML**（从 XML 或表发起，选字段与 resultMap 映射，预览后应用）
- `[NEW]` OGNL 支持链式方法调用与属性访问补全/引用检查
- `[NEW]` XML 无关联接口方法时按 `parameterType` 补全与检查参数

**3.7.1（11-24）** —— 格式化修缺
- `[FIX]` 格式化把长字段/赋值/参数列表合并成一行
- `[IMPROVE]` 无动态标签的完整语句按 IDE 的 SQL 代码样式换行

**3.7.2（11-27，今天）** —— **转向稳定性与性能**
- `[FIX]` **修复 Gradle 同步或大量 XML 变更时，Mapper 命名空间缓存刷新阻塞写锁导致 IDE 卡死**，并跳过非 Mapper XML 的 PSI 解析以提升索引性能
- `[FIX]` 修 Mapper XML 中动态标签/动态排序导致 JOIN 缩进丢失
- `[FIX]` 格式化保留 `<sql>` 字段清单已有换行

### 3.2 判读：三条威胁面同时收紧，但重心修正了一处

1. **代码生成侧被正面入侵**：3.7.0 的「`findById.sql` + Tab 生成方法与 SQL」与我方 SQL→Java / CRUD 生成正面重叠，而且它的入口是**在编辑器里输入即生成**，比我方「选中 SQL 按快捷键」更前置。
2. **OGNL 补全被补齐**：CHP 现在有 OGNL 链式方法调用补全与引用检查。这与我方 `Ognl.kt` 自研求值器是同一战场（我方长处在求值，短处在补全）。
3. **稳定性战场被对方主动开打**：3.7.2 一天的更新全是「卡死 + 索引性能」。这条最有战略含义——**它意味着 CHP 也在被用户抱怨 IDE 卡死**，而「卡顿」正是车道 D 里我方第三卸载因（58 条）。这是**双方共同的用户痛点**，谁先解决谁拿信任。

### 3.2.1 重要修正：**CHP 当前投入重心不是 AI，是 Mapper XML 格式化**

r45 把 CHP 定性为「AI 三线并进（AI + Agent + MCP）」，本轮证据显示**这个描述对 3.6.x 成立，对 3.7.x 不成立**：

**并且它没修好——用户还在报**（车道 B 拿到的一手评论 + GitHub issue）：

> **#1130（2026-11-26，open）**「这是 3.6.9 的 xml 格式化… 这是 3.7.1 的 xml 格式化… **新版的 xml 变成不换行的了？**」
> **#1129（2026-11-24 建、11-25 关）**「格式化后，不清楚为什么能出现这么长一排。**之前都不会出现** … 还有这关键词能被格式化成一列？」

1. **紧迫性↑**：CHP 用「用户报什么就 1~2 天修一版」的节奏在打磨这个高频场景，我方零覆盖。

### 4.5 dev 与 insight：**D220 的「二选一」提法是错的**

#### 核心发现：两者是同源分叉，insight 是 dev 的超集方向

用 `git ls-tree -r <ref> -- src/main` 导出三棵树的 blob 哈希做集合运算（不是逐文件 diff，口径更硬）：

**dev 的 86.9% 文件在 insight 里逐字节相同。** 更关键的两条：

→ **dev 相对 master 的每一个独有文件，insight 都改过。dev 没有任何 insight 之外的独立产出。**

1. 两者**不是互斥方案**，是同源分叉，dev 的 150 个独有文件 100% 包含在 insight 改动面内。
2. insight 能力面**严格覆盖** dev：69 共享 + 61 独占；dev 没有任何 insight 没有的能力。

### 6.3 性能面：治理到 P0/P1 清零，但有一笔最大的「未兑券」

**已消除（有真机读数）**：100ms EDT 轮询→500ms 指数退避至 2000ms；表名反查 16,804 类逐查 3.8s→全表索引 O(1)，建索引 4,737ms→**187ms**；预览首开 3.7~4.0s→装配 351→104ms（预热后 55~75ms）；启动期反查索引重复建 7 次→1 次；SQL 列表刷新 102~232ms→**7~9ms**；投递 512 条 726ms→**31ms**。

**仍存风险（最重要一条）**：**hiddenbug 分支 9 项性能券未合流**——历史文件逐字符 `reader.read()` 仍在 master（`SqlLogFileReader.boundedLines:99-111`，分支实测 19MB/8708 条 15~16.6s→701ms）、50KB SQL 体检 O(n²）、12000 条判重 O(n²）。**用户手里的发行版至今带着这三项。**

治理投入：PerfSweep 编号 2→34（25 个不同编号）、性能分析 9 期、911 次提及散在 203 个文档。**当前点位：P0/P1 已清零，剩下 P2/P3 与分支欠账。**

**一处过期前提**：2026-09-20 的 A/B 实测（「进程启动→项目扫描」中位差 −16ms，p=0.94；结构上「无任何 index/stubIndex EP」）**已过期**——现在有 **3 个 `fileBasedIndex`（均 `dependsOnFileContent=true`）**，首启对存量用户会做一次性重建。结论「启动无体感开销」大体仍成立，但**需按新索引面重测一次**。

### 6.4 设置项与新手路径

**心智负担**：9 个设置页、**119 个 State 字段、94 个控件、403 条 `settings.*` 键（103 条 tooltip）**。对冲手段齐备（每页 desc 摘要 / 接入 IDE 设置搜索 / `SettingsRealityGuardTest` 文案与真实行为对账）但**对首周用户仍偏重**。

**onboarding 只有 3 个一次性气球，没有动线**：
- `OnboardingAnchorTip`：首次打开含 SQL 的文件 → 「按 Alt+Shift+Q」，每机一次
- `DialectGapTip`：方言推断真死路 → 说后果 + 去设置 + 本项目不再提示
- 日志首次捕获成功引导

**未覆盖的能力面**（恰恰是差异化最强的）：独立工作台（`Alt+Shift+P`）、回滚快照、SQL→Java、**MCP**、iBatis、JOIN 图。

### 6.5 用户支持链路：内部到眼睛做得好，用户到作者仍靠人肉

- **有**：SQL 日志面板常驻诊断行（增强通道五态 + 已扫描行数 + 重放丢弃数 + EP 短路数 + attach 命中/失败 + 未登记 JDBC 实现点名单）——全仓最强自助面。
- **有**：`ShareDialog` 单条 SQL 诊断报告（七环 Markdown/HTML 导出）。
- **缺**：**没有「一键导出插件级诊断包」**（`grep -rni "supportBundle|collectDiagnostic" src/main` 零命中）。用户报障仍需自己找 `idea.log`、贴版本号、复述操作序列。
- **缺**：`docs/支持/` 只有 1 篇（线程转储三步判定法），且**不进产品**。

### 6.6 测试与守卫覆盖

70 个 `*Guard*Test`（元守卫 82 条登记），按守的分组：线程/EDT（7 个）、平台契约（3）、设置真实性（3）、缓存键（2）、发行合规（4）、回归钉（3）。

**裸奔区**：
1. **onboarding**：2 类只有 4 个测试，一次性状态/让位优先级/开关组合几乎无覆盖
2. **GUI 目视契约**：两份验收册自述「所有 GUI 目视项均未执行」
3. **回滚快照 P1~P7**：代码在分支，master 侧零测试
4. **反馈网络层**：`FeedbackApi` 明确「单测不测本类」
5. **真机性能**：T0 四项读数未取，`heavy` 仅 8 个类
6. **agent 字节码织入**：56 个 Java 测试，厂商 jar 缺失时显式 skip（CI 上条件绿）

### 6.7 核心结论：用户最可能因为什么卸载

1. **不是崩，是「结果不可信」**（B 类 79 条）。复制出去执行报 `ORA-01843`/`&gt;` 语法错/iBatis 参数错位 → 「这插件不准」→ 卸载。**每版仍在出。**
2. **其次「它好像没工作」**（A 类 88 + D 类 45，合计最大面）。用户无法区分「没有可预览的 SQL」「环境不支持」「插件坏了」——**静默失败**。
3. **再次「它让我的 IDE 卡了」**（C 类 58）。判定法在 docs 里，不在用户手里。
4. **结构性风险：卡在第一公里**。功能深度过剩、引导深度不足，0 票 0 评论。

> **这个插件不会因为「不够强」被卸载，会因为「有一次不准 / 有一次没反应 / 有一次卡住」被卸载，而它的差异化能力（MCP、自研框架、回滚）大多还没被用户看见。**
