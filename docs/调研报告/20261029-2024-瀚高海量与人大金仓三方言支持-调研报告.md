## 零、结论摘要

1. **人大金仓已经在册，不是从零加**。`KingBaseDialect` 自 P-立项-05 起就在 11 方言里；本轮机读对账 + **真机实测**显示六项核心形态全部正确（分页 / 双引号 / LOWER 折叠 493/493 / PG 形态 upsert 计划含 `Conflict Resolution: UPDATE` / `EXPLAIN (FORMAT JSON)` 单列 JSON 文本 / `DELETE … LIMIT` 语法错误印证 `supportsDeleteLimit=false`）。金仓真正的缺口是三条：**保留字缺 1 词 `enckey`**（引擎标 R，列引用报 `syntax error at or near "enckey"`）、**增强捕获语句面从未登记**（看得到库名却一条 SQL 都采不到）、**PG 协议版驱动未登记**（`postgresql-for-kingbase` 走 `jdbc:postgresql:`，会被误判成 PostgreSQL）。

2. **瀚高与海量是零支持，但形态可整体复用 PG 族**。两者都基于 PostgreSQL 内核（瀚高 V9 官方写 `PostgreSQL 14`；海量 G100 基于 openGauss 6.0），分页、双引号、折叠方向（裸名折小写）、`ON CONFLICT`、`EXPLAIN (FORMAT JSON)`、`BEGIN` 都有官方文档支撑，与现有 `PostgreSQLDialect` 逐字节一致。

3. **真正必须单独取证的是三件事**：
   - **瀚高的保留字表与 PG 双向有差集**：瀚高附录 150 词里有 65 词不在 dev 的 `PG_RESERVED`(86) 中（`BIGINT`/`INT`/`VARCHAR`/`TIMESTAMP`/`COALESCE`/`TRIM`/`EXTRACT`… 全是类型名与函数名），而 `PG_RESERVED` 有 1 词（`procedure`）不在瀚高表里 → **必须取并集 151 词**，照抄任一单表都会漏包。
   - **Vastbase 的 upsert 不能族推定**：官方通用文法**同时**收 `ON CONFLICT` 与 `ON DUPLICATE KEY UPDATE`，而同内核的 openGauss 5.0.0 真机只认后者（`ON CONFLICT` 语法错误）。文档文法在这个家族里不等于引擎现实。
   - **瀚高默认实例模式是 Oracle**（`initdb --dbmode` 默认 `oracle`，IvorySQL 血统），两个默认参数会咬人：`ivorysql.identifier_case_switch=INTERCHANGE`（带引号标识符大小写互换）、`ivorysql.enable_emptystring_to_null=on`（`''` 存成 NULL）。

4. **三族驱动全是整体改名的独立实现**（`org/postgresql` 条目均为 0）：`com.kingbase8.jdbc.Kb*`、`cn.com.vastbase.jdbc.Pg*`、`com.highgo.jdbc.jdbc.Pg*`。因此增强捕获的语句面**不能靠 PG 名单覆盖**，必须三族分别登记——这条与方言渲染正交，可独立分批交付。

5. **证据档位三族不同**：**金仓有真机**（DBX 在册 `KingbaseES V8`，六项核心形态引擎级实测通过）；**瀚高与海量零真机**（DBX 在册 56 条连接无此两族，Docker Hub 只有第三方镜像、无厂商官方组织）→ 它们止于「官方文档 + 驱动字节码」。因此对外只能说瀚高/海量「已适配」，金仓可写「已验证」。**三族都不得写「真机端到端验证」（增强捕获 attach 一条都没跑）。**

6. **推荐路线**：S1 新增两个方言对象（形态复用 PG + 各自保留字表 + URL/EXPLAIN/方言链登记）→ S2 金仓缺口与三族增强捕获驱动登记 → S3 守卫与文档同步（11 处守卫 + 兄弟文档站 4 表）。**兼容模式感知本轮不做**（瀚高/海量零真机，做了等于把猜测固化成产品行为）。dev 已有的 `GaussDbDialect`（形态复用 openGauss + 身份独立）是现成模板，两新方言照它写即可。

7. **一个必须先解决的前置**：`sql/Dialect.kt` 在 dev 上已并入 T-GaussDbDialect（12 方言）。dev 的 `docs/架构设计/03` §218 明确记了一条跨仓对齐坑——`DialectDocTableGuardTest` 读磁盘上的兄弟文档站目录、所有工作树共用一份，所以「插件分支 A 有 14 方言、分支 B 有 11 方言」不可能同时绿（上一轮真实发生过两向红）。**实施顺序固定：先 dev 落插件 14 → 再改文档站**；改完后 master 工作树跑该守卫必红，属已知且可接受（master 不是实施基线）。

## 二、现状盘点：三方言在插件里到底是什么

### 2.1 一句话结论

| 方言 | 当前状态 | 本次要做的事 |
|---|---|---|
| **人大金仓 KingbaseES** | **已在册**：`object KingBaseDialect`（dev `sql/Dialect.kt:754-783`），设置页可选中、URL 可推断、EXPLAIN 已登记；DBX 真机实测六项核心形态全部正确 | 补三处缺口（保留字缺 `enckey`、**增强捕获语句面未登记**、PG 协议版驱动未登记），不是从零加方言 |
| **瀚高 HighGo DB** | **零支持**：全仓 grep `highgo` 仅命中「用户生产库清单」类文字，无 `Dialect` 对象、无 URL 子协议、无保留字表 | 新增 `HighGoDialect` + 全链登记 |
| **海量 Vastbase** | **零支持**：同上（`vastbase` 仅在竞品调研文档里作为 DBX 的驱动条目出现） | 新增 `VastbaseDialect` + 全链登记 |

MySQL / PostgreSQL / Oracle / SQL Server / H2 / SQLite / MariaDB / DM（达梦）/ KingBase（人大金仓）/ OceanBase / openGauss / **GaussDB**。

master（`3164d4f5`）仍是 11 方言；本任务在 dev 上实施即 **12 → 14**。

### 2.2 金仓当前实现（逐项现值，供缺口审计对照）

`object KingBaseDialect`（`Dialect.kt:754-783`）：

| 维度 | 现值 | 本轮判定（详见 §7） |
|---|---|---|
| 分页 | PG 形态 `LIMIT count OFFSET offset` | 一致（官方文法） |
| 引号 | 双引号 `"x"`，`identifierQuotes = {'"'}` | 一致 |
| 折叠族 | `IdentifierFolding.LOWER` | 一致（**真机 493/493**） |
| 保留字 | `KINGBASE_RESERVED` 117 词 | **缺 1 词 `enckey`**（官方文档 117 词与插件逐词相等，但引擎把 `enckey` 标 `R` 且列引用报错） |
| upsert | PG 形态 `ON CONFLICT (k) DO UPDATE SET c = EXCLUDED.c` | 一致（**真机计划含 `Conflict Resolution: UPDATE`**） |
| EXPLAIN | `EXPLAIN (FORMAT JSON) {sql}`，JSON 档 | 一致（**真机单列 JSON 文本**） |
| DELETE LIMIT | 未覆写 → `false` | 一致（**真机 `DELETE … LIMIT` 报语法错误**） |
| 事务开始 | `"BEGIN"` | 一致（文档级；DBX 拒事务语句，真机不可测） |
| identity 包装 | 未覆写 → 不需要 | 默认路径一致；`GENERATED ALWAYS` 列是缺项（需 DDL 造列，本轮不可验） |

> 这张表是「现值 vs 判定」的对照，**判定依据全部落在 §7.2 的真机读数与 §7.3 的对账表**；此前版本按「PG 兼容推定」标注的几项，本轮已升级为引擎级。

### 2.3 三方共同的「族推定」陷阱（本仓库已被打过两次脸）

1. **openGauss 先例**：同属 PG 系，原生 upsert 却是 MySQL 形态 `ON DUPLICATE KEY UPDATE`，PG 的 `ON CONFLICT` 直接语法错误（`Dialect.kt:826-880` KDoc 留证）。→ **不能因为「基于 PostgreSQL」就照抄 PG 的 upsert**。
2. **H2 先例**：折叠方向按「其余方言」继承默认 NONE，与引擎实测（折大写）相反，后经订正（`Dialect.kt:602-612`）。→ **折叠方向必须实测或查官方口径，不能默认**。
3. **DM 先例**：identity 包装按「推定不需要」出厂，真机报 `-2723` 才补（`Dialect.kt:719-738`）。→ **「显式写自增列」要单独取证**。

## 五、瀚高 HighGo DB

### 5.1 产品与内核

- **HighGo DB V9 = PostgreSQL 14 内核**的国产发行版（官方产品页明写 `PostgreSQL 14`）；V9 在线参考文档的章节结构、SQL 命令大纲、词法、EXPLAIN、IDENTITY、ON CONFLICT 条目均与 PostgreSQL 官方参考同形。
- V5 / V6 的内核版本**无官方出处**（第三方说法不一：V6 沿 PG 9.6 或兼容 PG 13）→ 不作结论。
- **V9 实例默认兼容模式是 Oracle**：`initdb --dbmode=pg|oracle|mysql`，默认 `oracle`。这是「瀚高 = PG 克隆」这一直觉最大的偏差。
- Oracle 兼容层是 **IvorySQL 血统**（GUC 前缀 `ivorysql.*`）。两个会咬人的默认值：
  - `ivorysql.identifier_case_switch = INTERCHANGE`（默认）：**带双引号的标识符大小写互换**（全大写引号名 → 小写，全小写引号名 → 大写，混合大小写不变）；
  - `ivorysql.enable_emptystring_to_null = on`（默认）：**空串存成 NULL**——SQL 预览里 `''` 字面量的语义与 PG 不同。
- MySQL 兼容语法子集（V9.0.4/9.0.5 起）：`AUTO_INCREMENT`、`REPLACE INTO`、`UPDATE … ORDER BY … LIMIT`、多表 DELETE/UPDATE、`SHOW`、`USE db`、`DUAL`、`sql_mode`。**没有** `LIMIT a,b`、**没有** `ON DUPLICATE KEY UPDATE`、**没有**反引号条目。

### 5.2 JDBC 驱动（字节码反编译级，主控独立复核）

| 制品 | Driver 类 | 接受的 URL 前缀 | 包结构 |
|---|---|---|---|
| `com.highgo:HgdbJdbc:6.2.5`（Maven Central） | `com.highgo.jdbc.Driver` | **`jdbc:highgo:`**（`Driver.class` 常量池仅此一个前缀） | **整体改名的 pgjdbc 分叉**：`com/highgo/jdbc/jdbc/PgStatement`、`PgPreparedStatement`、`PgConnection`、`PgCallableStatement`；`org/postgresql` 条目数 **0** |
| `com.highgo:hgdb-pgjdbc:42.5.0`（Maven Central，描述 "based on pgjdbc usage"） | `org.postgresql.Driver` | `jdbc:postgresql:` | 518 个 `org/postgresql` 类，原版 pgjdbc 42.5.0 直用 |

复核命令与读数：

```
unzip -p HgdbJdbc-6.2.5.jar com/highgo/jdbc/Driver.class | grep -a -o "jdbc:[a-zA-Z]*"   → jdbc:highgo
unzip -l HgdbJdbc-6.2.5.jar | grep -c "org/postgresql"                                   → 0
unzip -p hgdb-pgjdbc-42.5.0.jar META-INF/services/java.sql.Driver                          → org.postgresql.Driver
```

**两个后果**：①同一库可能有两种 URL（`jdbc:highgo://…` 与 `jdbc:postgresql://…`），前者要新增子协议键、后者会被认成 PostgreSQL；②增强捕获的语句面**不能靠 PG 名单覆盖**（重定位类与 `org.postgresql.jdbc.PgStatement` 无继承关系）。

默认端口 **5866**；官方连接形态 `jdbc:highgo://ip:端口号/数据库名`，示例 `jdbc:highgo://localhost:5866/highgo`。

### 5.3 方言形态（逐项）

| 维度 | 结论 | 档位 |
|---|---|---|

### 5.4 保留字：瀚高与 PG 双向有差集（本次最重要的差异）

主控用脚本机读对账（`tmp/dialect-research/probe_highgo_reserved.py`；瀚高侧取附录 2 表格区域内的大写词，实测恰好 150 词；PG 侧取 **dev 分支**的 `PG_RESERVED`，86 词）：

| 项 | 读数 |
|---|---|
| 瀚高附录 2 保留字 | **150 词**（表格区域精确计数，无导航噪音） |
| PG 侧 `PG_RESERVED` | **86 词**（master 是 84；dev 的 T-GaussDbDialect 补了 `is` 与 `procedure`） |
| 瀚高有 / PG 没有 | **65 词**——正是 PG 附录里 `reserved (can be function or type name)` 那一档加类型名/函数名：`between`、`bigint`、`bit`、`boolean`、`char`、`character`、`coalesce`、`collation`、`cross`、`current_schema`、`dec`、`decimal`、`exists`、`extract`、`float`、`full`、`greatest`、`grouping`、`ilike`、`inner`、`inout`、`int`、`integer`、`interval`、`join`、`least`、`left`、`like`、`national`、`natural`、`nchar`、`none`、`nullif`、`numeric`、`out`、`outer`、`overlaps`、`overlay`、`position`、`precision`、`real`、`right`、`row`、`setof`、`smallint`、`substring`、`tablesample`、`time`、`timestamp`、`treat`、`trim`、`values`、`varchar`、`verbose`、`xmlattributes`、`xmlconcat`、`xmlelement`、`xmlexists`、`xmlforest`、`xmlnamespaces`、`xmlparse`、`xmlpi`、`xmlroot`、`xmlserialize`、`xmltable` |

→ **两个方向都有差集，必须取并集（151 词）**。照抄 `PG_RESERVED` 会漏包 65 词（列名撞上 `bigint`/`int`/`varchar`/`timestamp`/`coalesce`/`trim` 就不加引号）；只取瀚高表又会漏 `procedure`（PG 11+ 保留）。

> 顺带一条对 PG 方言本身的观察：这 65 词在 PostgreSQL 上「不能做函数名/类型名」，插件的 `PG_RESERVED` 只收了同档里的 7 个（`AUTHORIZATION/BINARY/CONCURRENTLY/FREEZE/ISNULL/NOTNULL/SIMILAR`）。属 PG 侧既有口径，本任务不改（登记为观察项——改它会影响所有 PG 项目的产物）。

### 5.5 Oracle 模式下 `INTERCHANGE` 对引用规则的影响（分析，非缺陷）

`ivorysql.identifier_case_switch = INTERCHANGE` 让**带引号**的标识符大小写互换。逐形态推演（对 `quoteIfNeeded(CATALOG)` 的 LOWER 族规则）：

| 目录里的真实名字 | LOWER 族规则产出 | INTERCHANGE 后实际查找 | 命中？ |
|---|---|---|---|
| `issue_new`（全小写，裸写创建） | 不加引号 → 折小写 | `issue_new` | ✅ |
| `Issue_New`（混合，引号创建） | 加引号 → `"Issue_New"` | 混合大小写不变 | ✅ |
| `ISSUE_NEW`（全大写，引号创建） | 加引号 → `"ISSUE_NEW"` | 被换小写 `issue_new` | ❌（不加引号同样 ❌） |

→ **LOWER 族仍是正确选择，`INTERCHANGE` 不会让现有规则更糟**；唯一无法命中的是「以引号创建的全大写名」，在 PG 上反而可解。这条写进 KDoc 即可，不做代码分叉。

### 6.4 与 openGauss 的关键分歧（族推定陷阱）

- **也不能照抄 PG 的 `ON CONFLICT`**（A 模式下能否解析无真机证据）。

|---|---|---|---|
| 分页 | PG 形态 `LIMIT count OFFSET offset` | 官方文法 + 真机 | 一致 |
| 引号 / 折叠 | 双引号 + `LOWER` 族 | 真机 493/493 + `"TABLES"` 报告 | **一致（引擎级）** |
| upsert | PG 形态 `ON CONFLICT … DO UPDATE` | 真机 `Conflict Resolution: UPDATE`；MySQL 形态语法错误 | **一致（引擎级）** |
| EXPLAIN | `EXPLAIN (FORMAT JSON)`，JSON 档 | 真机单列 JSON 文本 | **一致（引擎级）** |
| DELETE LIMIT | `false`（静默省略尾段） | 真机 `syntax error at or near "LIMIT"` | **一致（引擎级）** |
| **保留字** | `KINGBASE_RESERVED` 117 词 | 官方 V9「保留」117 词（两向差集皆空）；**但引擎把 `enckey` 标 R 且列引用报错，插件缺这个词** | **偏差（缺 1 词）** |
| 事务开始 | `"BEGIN"` | 官方 `BEGIN [WORK\|TRANSACTION]`；真机不可测（DBX MCP 拒事务语句：`SQL_BLOCKED`） | 一致（文档级） |
| identity 包装 | `null` | `BY DEFAULT AS IDENTITY` 接受显式值（不需包装）；`GENERATED ALWAYS` 需 `OVERRIDING SYSTEM VALUE`（**语句内子句，位置在列清单后 / VALUES 前，不是前置语句**） | 默认路径一致；ALWAYS 列是缺项（需 DDL 造列，本轮不可验） |
| URL 子协议 | `kingbase8` / `kingbase` | 四份驱动（8.6.0 / 9.0.1 / `-mysql` / `-sqlserver`）常量池**只有 `jdbc:kingbase8:`** | 一致（`kingbase` 为宽进，无害） |
| PG 协议版驱动 | 无登记 | `cn.com.kingbase:postgresql-for-kingbase` 用 `org.postgresql.Driver` + `jdbc:postgresql:` | **缺项**：该类项目会被推断成 PostgreSQL，金仓保留字表不生效 |
| 平台方言 id | `KingBase` / `KingbaseES` / `PostgreSQL` | 262 平台无金仓方言 | 一致（恒落 PG 兜底） |
| **增强捕获语句面** | **未登记** | `com.kingbase8.jdbc.KbStatement` / `KbPreparedStatement` / `KbCallableStatement` / `KbConnection`（`org/postgresql` 条目 **0**） | **缺项（最大缺口）** |

### 7.4 驱动制品（字节码反编译级，主控独立复核）

| 制品 | Driver 类 | URL 前缀 | `org/postgresql` 条目 |
|---|---|---|---|
| `kingbase8-8.6.0.jar` | `com.kingbase8.Driver` | `jdbc:kingbase8:` | 0 |
| `kingbase8-9.0.1.jar` | `com.kingbase8.Driver` | `jdbc:kingbase8:` | 0 |
| `kingbase8-mysql-9.0.1.jar` | `com.kingbase8.Driver` | `jdbc:kingbase8:` | 0 |
| `kingbase8-sqlserver-9.0.0.jre7.jar` | `com.kingbase8.Driver` | `jdbc:kingbase8:` | 0 |
| `postgresql-for-kingbase-9.0.0.jre7.jar` | `org.postgresql.Driver` | `jdbc:postgresql:` | 646（原版 pgjdbc 直用） |

→ 与瀚高 / 海量同型：**默认驱动是整体改名的独立实现**，PG 名单覆盖不到；官方另提供 PG 兼容驱动，走 `jdbc:postgresql:` 时会被认成 PostgreSQL。

### 7.5 最大缺口：增强捕获「只有 URL、没有 SQL」

- `DriverRegistry.java:52` 已登记 `com.kingbase8.Driver`（connect 面）→ 日志面板角标能显示「KingBase（人大金仓）· 库名@host:port」。
- `WeaveSpecs.java` 的语句面/prepare 面**只有** `org.postgresql.jdbc.Pg*` 与 `dm.jdbc.driver.Dm*` → 金仓的 `KbStatement`/`KbPreparedStatement` 从未被织入。
- 后果：attach 后 URL 有、SQL 零条，宿主侧无任何报错。这正是 T-ConnCastSafety §七 S5 留下的「按 javap 补金仓/翰高/海量/GBASE 面条目」未做项。

### 7.6 结论

金仓**方言本体只需补 `enckey` 一词**；其余要动的是：①增强捕获语句面登记（与两新方言同批，三族形态相同）；②`postgresql-for-kingbase` 驱动标记；③identity ALWAYS 列若将来支持，形态与 DM/SQL Server 的 `SET IDENTITY_INSERT` 完全不同，不能套现有 wrapper 抽象。

## 八、MyBatis-Plus 侧对齐（生态事实）

MP 的 `DbType` 在 `mybatis-plus-annotation` 模块（**不在** core —— 按 core 的 sources jar 找会扑空）。三个枚举都在册：

| 枚举 | 值 | 家族判定 |
|---|---|---|
| `KINGBASE_ES("kingbasees", "人大金仓数据库")` | 在册 | `postgresqlSameType()` = true |
| `HIGH_GO("highgo", "瀚高数据库")` | 在册 | `postgresqlSameType()` = true |
| `VASTBASE("vastbase", "Vastbase数据库")` | 在册 | `postgresqlSameType()` = true |
| `OPENGAUSS("openGauss", "华为 opengauss 数据库")` | 在册 | `postgresqlSameType()` = true |
| `GAUSS_DB("gaussDB", "GaussDB 数据库")` | 在册 | 独立 `GaussDBDialect` |

分页实现字节码对照（`mybatis-plus-extension-3.5.17.jar`，`javap -c`）：

- `PostgreDialect.buildPaginationSql` → `" LIMIT ? OFFSET ?"`；
- `GaussDBDialect.buildPaginationSql` → `" LIMIT ?,?"`（MySQL 形态）。

→ **三方言在 MP 侧都映射到 `PostgreDialect`**，插件用 PG 形态分页与 MP 运行时行为一致；MP 侧没有 HighGo / Vastbase / KingBase 专有分页类（`dialects/` 目录逐项列举无此三族）。瀚高官方《MyBatis-Plus》集成页也明写 `paginationInterceptor.setDialectType("postgresql")`。

> 注：`DbType.HIGH_GO` 的 username 域 `highgo` 与瀚高驱动的 URL 子协议同名，`JdbcUtils` 用 `:highgo:` 识别连接串——与插件新增的 `highgo` 子协议键一致，无冲突。

## 九、方案选项与推荐

### 9.1 方言链

| 方案 | 内容 | 代价 | 风险 |
|---|---|---|---|
| **A 只加别名** | 把 `jdbc:highgo` / `jdbc:vastbase` 映射到 `PostgreSQL` 方言，不新增 object | 最小（三处 URL 表） | 用户看不到方言名；**瀚高少包 66 个保留字**；海量的 upsert 与模式差异完全无表达；能力矩阵/EXPLAIN 登记表仍只认 PostgreSQL |
| **B 新增两个方言对象**（推荐） | `HighGoDialect` / `VastbaseDialect`：形态全量复用 PG 族，各自保留字表；金仓补缺口；守卫与文档同步 | 中：生产 ~8 文件 + 守卫 11 处 + 兄弟文档仓 4 表 | 低：渲染形态逐字节复用 PG，唯一行为变化是「保留字多包」与「方言身份可见」 |
| **C B + 兼容模式感知** | 再加设置项（Vastbase A/B/PG/MSSQL、瀚高 pg/oracle/mysql）与形态分叉 | 大：新设置项要动 State/面板/双 bundle/项目级覆盖/4 个设置守卫/搜索索引，且每模式形态需真机 | 高：**瀚高/海量零真机**，等于把未验证的推断固化成产品行为 |

**推荐 B**。理由：三方言的渲染形态都有官方文档级证据支持「与 PG 逐字节一致」（金仓另有真机佐证），风险集中在保留字（有官方词表可落）与 upsert（有官方文法 + 同族真机先例可定保守口径）。C 在没有瀚高/海量实例的前提下做，等于给用户一堆猜出来的开关。

### 9.2 增强捕获链（与方言链独立）

| 方案 | 内容 | 代价 | 风险 |
|---|---|---|---|
| **A 不登记** | 只在文档说明「金仓/海量/瀚高的增强捕获目前只出 URL、不出 SQL」 | 最小 | 用户侧零 SQL 采集；与「JDBC 接口级一视同仁」的既有表述冲突 |
| **B 只补语句面 + prepare 面**（推荐） | `WeaveSpecs` 登记 `com.kingbase8.jdbc.Kb*`、`cn.com.vastbase.jdbc.Pg*`、`com.highgo.jdbc.jdbc.Pg*`；connect 面按达梦教训不碰 | 中：agent 2 文件 + 测试依赖 + 帧跳过前缀四份 | 低：语句面不改对象身份，结构上不可能引发 CCE；须先过字节层（JVM 链接期校验） |
| **C B + connect 面** | 再加三族 Driver 做 connect 出口织入 | 略高 | **需先过字节层**；达梦 `DmDriver` 就是在这里 VerifyError 被整类撤出；`wrapConnection` 默认值不得改 |

**推荐 B**。connect 面唯一独有能力是「最近 connect URL 兜底」，而 URL 已经能由语句面/反射拿到；红线不值得为兜底冒一次。

## 十、证据边界与未验证项

1. **金仓有真机，瀚高/海量零真机**。DBX MCP 在册 `KingbaseES V8`（`114.66.55.245:20097/dbx_test`，`V009R001C010`，`database_mode=pg`）→ §7.2 九条探针为引擎级；瀚高/海量在册 56 条连接里没有对应类型 → 凡「引擎实际行为」均为官方文档或字节码推断。因此金仓可写「已验证」，瀚高/海量只能写「已适配」；**三族都不得写「增强捕获真机端到端验证」**（attach 一条没跑）。
2. **金仓 `enckey` 的读数有分歧要如实记**：引擎 `pg_get_keywords()` 标 `catcode=R`，`SELECT enckey FROM …` 报语法错误；但 `SELECT 1 AS enckey` **通过**（子代理报告称别名位也拒绝，主控实测相反）。按「宁可多包、不漏包」仍应补入保留字表；补后 `SELECT 1 AS enckey` 这类形态会多一对引号，不影响正确性。
3. **瀚高保留字取自 V4.5 附录**（V9 在线文档无该附录页）。V4.5 → V9 的词表是否变化未取证；取超集口径可容忍新增词缺失，但不能容忍「V9 删了某词」——那种情况只会多包，不影响正确性。
4. **瀚高 `INTERCHANGE` 影响只在 Oracle 模式**；`dbmode=pg` 实例下行为与 PG 完全一致，本轮未分模式验证。
5. **Vastbase upsert 的模式归属未证**：官方通用文法两种都收，但同内核 openGauss 5.0.0 真机只认 MySQL 形态。默认取 MySQL 形态是保守选择，不是「已验证」。
6. **Vastbase 的 `LIMIT a,b` 语义未证**（文档写 MySQL 语义且未标模式限制）；插件渲染侧不产出逗号形态，故不受影响，但若将来做「分页拦截器模拟」需先证。
7. **金仓事务与 identity ALWAYS 仍只有文档级**：`BEGIN` 真机不可测（DBX MCP `SQL_BLOCKED: Transaction statements are not supported`）；`OVERRIDING SYSTEM VALUE` 两次探针均 30s 超时（通道问题，非语法结论），需直连或造 DDL 列才能验。
8. **平台 262 无三族方言**：已用本机 `IDEA 262.10968.63` 的 `intellij.database.dialects.*.jar` 逐包列举证实（不是 grep 关键字）；运行时 `SqlDialectMappings.getAvailableValues()` 未实测（需 runIde 沙盒）。
9. **增强捕获未过字节层**：三族驱动 jar 已下载，但「织入产物能否通过 JVM 链接期校验」未跑（`StatementWeaverVendorCoverageTest` 的机制现成，实施时先跑）。金仓侧还实测到 `KbStatement.execute(...)` / `KbConnection.setClientInfo` / `Driver.connect` 的 StackMapTable 含 **chop 帧**，达梦式 VerifyError 风险真实存在。
10. **三族驱动均为整体改名分叉**（`org/postgresql` 条目 0），与华为 GaussDB 同型；但类名前缀各不相同（`com.kingbase8.jdbc.Kb*` / `cn.com.vastbase.jdbc.Pg*` / `com.highgo.jdbc.jdbc.Pg*`），不能按「PG 名单」一次性覆盖。
