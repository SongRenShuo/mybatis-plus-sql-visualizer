### 热更新为什么在开发沙盒里失败（根因链）

1. `DynamicInstallSupport.doInstall()` 先过守卫、再调平台 `DynamicPlugins.unloadPlugin(currentDescriptor)`；
2. 262 平台里 runIde 沙盒的插件是**目录形态**开发安装（`plugins/mybatis-plus-sql-visualizer/` 下直接是 `lib/*.jar` + 描述文件），`codeSource.location` 返回 null（日志实证），平台动态卸载对这种「开发态加载的 descriptor」返回 false；
3. 卸载失败 → 回退 `installRestartScript`（DeleteCommand + UnzipCommand），但脚本只在 **IDE 自己重启**时执行；
4. 沙盒里点「重启 IDE」会触发 Restarter 丢沙盒参数（坑 30），不能走；正常关 IDE 不会执行脚本（实测 jar 未变）。
5. **「正常模式运行 IDE」能否救活？** 见下节——这是本轮用户提出的新思路。

## 2. 「正常模式运行 + 迭代内测版本号热更新」方案分析

> 用户思路：不跑 `runIde` 沙盒，用**正常安装的 IDE**（插件从 zip 装进常规 plugins 目录，非目录开发态），每次改版本地 `buildPlugin` 出一个仅用于本地快速测试的内测版本号（不对外发版），走插件自更新链热加载，避免重启。

### 判定：方向正确、可行，但有三个必须先解决的硬前置

**为什么方向正确**：本轮失败根因是「开发态目录加载 → 平台拒绝 unload」，与插件代码、版本号、包内容都无关。正常安装的 IDE 里插件是标准 zip 解包形态、descriptor 走常规加载路径，`codeSource.location` 不再是 null——这正是 `DynamicInstallSupport` 设计的目标场景（M28/T-DynUpdate263 的正式发行自更新链就是为它做的）。所以「正常模式 + 本地包热更新」在机制上**是本轮失败的唯一正确修法**。

**硬前置 1：不能拿日常 IDE 做这件事。** 日常 IDE 有用户自己的工程、设置、许可、数据源，热更新失败/插件半卸载会污染真实环境。可行形态是「**专用常驻实例**」：单独一份 `idea.config.path`/`idea.system.path`/`idea.plugins.path`（类似沙盒但用标准安装布局），配专用许可与 demo 工程，与日常 IDE 完全隔离。这本质上还是一个沙盒，只是**不用 runIde 的目录开发态安装**，改成 zip 装进 `plugins/`。

**硬前置 2：热加载不是 100% 可靠，要有回退。** 平台 `unloadPlugin` 还有别的否决面（源码注释实证）：本插件在 243 上因 `com.intellij.sql.dialect` EP 非 dynamic 必然拒绝卸载；262/263 才标 dynamic。以及 `ide.dynamicPluginVetoer`、依赖图、UI 层残留引用都可能让 unload 失败。所以这个方案的稳态应该是「**热更新优先，失败即重跑实例**」，而不是「保证免重启」。好在暖容器下重跑实例已压到 ~1 分钟级，失败代价可接受。

**硬前置 3：本地测试版本号不能污染发行链。** 用户特别提醒的点，核实结果：
- 版本号比较只看语义化字符串大小（`LocalPackageScanner` 取最高可用版本），本地 `-beta.N` 递增本身**不会触发发版**；
- 但有三处会把它带出去：① `buildPlugin` 产物若被 `gitee-release.py --from-github`/CI 发行流程捡走；② `CHANGELOG.md [Unreleased]` 按仓库规矩要随提交回填；③ `update/update.json`（用户手改项，助手禁动）与 `preview.update.json` 别碰。
- **建议口径**：本地测试版用**不进发行命名空间的私有后缀**，例如 `2026.11.14-beta.1+local.N`（semver build metadata，比较时仍可区分、但发行脚本按 `-Notes`/tag 匹配时不会撞）；或更简单——固定一个版本号，每次 buildPlugin 前改 jar 内 `MPV-Build` 时间戳（本来每次构建就唯一），靠「同版本不同构建」不行（扫描器会判已是最新）⇒ 还是得递增。折中：**本地测试号只写在 `gradle.properties` 的临时改动里，不提交、不写 CHANGELOG、不建 tag**，每轮结束 `git checkout -- gradle.properties` 还原；`hot-reload-plugin.py` 增加 `--local-version` 参数自动做这件事（bump → 打包 → 还原一条龙，工作树不残留版本号脏改动）。

### 收益估算

| 路径 | 单轮耗时（实测/估计） |
|---|---|
| 冷 runIde 全重启（旧） | 5~15 分钟 |
| 暖容器 + 外部重跑 runIde（本轮已验证） | ~1.5 分钟（prepareSandbox 增量 + IDE 启动 84s） |
| 本地 buildPlugin（增量，本轮实测） | 4~76 秒（取决于版本号是否变） |
| 热加载成功时的理想单轮 | ≈ buildPlugin + installFromLocal(0.4s) + 验证 ≈ 1~2 分钟；主要省掉 IDE 启动那 84 秒与重新定位/等索引 |
| 热加载失败回退 | ≈ 暖容器重跑 1.5 分钟，不比现在差 |

**诚实结论**：暖容器落地后，「重启」本身的成本已从 15 分钟压到 1.5 分钟，热更新的边际收益只剩「省 84 秒启动 + 免重新定位/等索引」；而它引入的前置（专用常驻实例、版本号卫生、失败回退）不轻。**优先级建议：先固化「暖容器 + 外部重跑」为正路；专用常驻实例 + 本地测试版本号热更新作为第二阶段试点，拿一个真实验收批做 A/B 计时（热更新成功轮 vs 重跑轮），读数立住再决定是否替换。**

### 实施草案（若拍板试点）

1. 归档仓 `scripts/` 增 `local-iteration.py`：`--bump`（临时改 gradle.properties 版本号为 `+local.N`）→ `buildPlugin -PgifRecord=false` → 落位 `sandbox-live/hot-repo/` → 还原 gradle.properties（try/finally）；全程不提交版本号、不碰 CHANGELOG/`update.json`。
2. 专用常驻实例启动脚本：复制常规 IDEA 安装到独立 `config/system/plugins`，首次用 zip 把插件装进 `plugins/`，之后用 `idea64.exe` 直启（**这条只用于该专用实例**，不违反「沙盒只许 gradle 起」的既有定例——它是正常安装模式，不是 runIde 沙盒）。
3. 触发热更新：设置页「检测本地包 → 下载并安装」（已实测可达，robot 语义点按钮可用），或 MCP/Action 触发。
4. 成功判据：idea.log `dynamic install succeeded — plugin hot-reloaded to <版本>` + UI 显示「立即生效，无需重启」；失败判据 `old version unloaded=false` → 自动重跑实例。
5. 硬例外不变：触设置页/Configurable 的改动整轮重启（CNFE 坑）；`installFromLocal` 的归属/兼容守卫要求 zip 是标准 buildPlugin 产物。

## 2b. 补充：官方开发态热加载（`autoReload`）——「一直没成功」的根因分析

> 用户补充线索：「正常插件开发应该支持热加载改动到沙盒，但一直没成功过」。核实后**属实、且本仓本来就开着**。

**证据链（全部本地实证，非推测）**：

1. `buildSrc/src/main/kotlin/mpv-runide.gradle.kts:50`：开发 `runIde { autoReload = true }` —— 官方 IntelliJ Platform Gradle Plugin 的开发态热重载开关，**早就开了**。
2. 反编译本机 Gradle 插件 jar（`instrumented-intellij-platform-gradle-plugin-2.20.1.jar`，`javap -c RunIdeTask`）实证：`autoReload` 的全部作用就是给 IDE 传系统属性 **`idea.auto.reload.plugins=true`**（字节码锚点 `ldc_w #468 String idea.auto.reload.plugins` + `systemPropertyDefault(...)`）。**Gradle 不会把 `build/classes` 的改动推给运行中的 IDE**；监听插件目录变化并触发动态卸载/装载的是 IDE 自己。
3. 所以「改了源码没反应」的根因几乎确定是：**沙盒 `plugins/<插件>/lib/*.jar` 没变**——只跑编译（产物在 `build/classes/`）或只跑 `buildPlugin`（产物在 `build/distributions/`），IDE 监视的目录里那份插件原封不动，自然没有重载事件。
4. 另一条干扰线：`ide-ui-acceptance` skill 第 24 行明确 **验收态 init 脚本 `autoReload.set(false)`**（防止后台修复构建改变在验版本）；`runIdeHotSwap` 任务也特意 `autoReload.set(false)`（防与自更新链的卸载/装载竞态）。若一直用的是验收沙盒配置，热重载从一开始就是关的。
5. 平台侧还有硬限制（源码 KDoc 实证）：243 上 `com.intellij.sql.dialect` EP 非 dynamic，平台**必然拒绝卸载本插件**；262/263 才标 dynamic——即在 243 开发沙盒里，即使目录变了也只能重启。

**可落地的修法（待本轮探针实测钉死）**：改源码 → 跑 `./gradlew prepareSandbox -PgifRecord=true`（它会把新编译产物重新装进沙盒 plugins/，**不重启 IDE**）→ IDE 的 `idea.auto.reload.plugins` 监听器发现 jar 变化 → 自动 unload/load。归档仓 `scripts/auto-reload-probe.py` 已写好 step1/2/3 三步探针（取 jar mtime 基线 → prepareSandbox → 复取 mtime + 扫 idea.log 的 unload/load 行）。

**探针实测（2026-11-14 15:16~15:18，IDE 运行中 `autoReload=true`）**：

| 步骤 | 结果 |
|---|---|
| 改 `MpSqlVisualizerBundle_zh.properties` 一处可见文案 → `./gradlew prepareSandbox -PgifRecord=true`（不重启 IDE） | ❌ BUILD FAILED：`Could not copy ... \plugins\ml-llm\lib\io.github.oshai.kotlin.logging.jvm.jar`（请求的操作无法在**使用用户映射区域打开的文件**上执行） |
| 退一步：只把新 composedJar 覆盖**主插件自己的 jar**（绕开 ml-llm） | ❌ `shutil.copy2` → `OSError [Errno 22] Invalid argument`（同样被内存映射锁死） |
| `auto-reload-probe.py step3` 复取 | jar mtime **未变**、idea.log 后 300 行**无任何 unload/load 记录** |

**完整根因链（三层，全部实测）**：
1. `autoReload=true` ⇒ IDE 只带 `-Didea.auto.reload.plugins=true`，靠**监听沙盒 plugins 目录文件变化**触发动态卸载/装载；Gradle 不会推送 `build/classes` 的改动。
2. 要让目录"变化"，必须重跑 `prepareSandbox` 或手工复制 jar；但**运行中的 IDE 把 plugins/ 下所有已加载 jar 内存映射锁住**（Windows 报错原文「用户映射区域打开的文件」/ `Errno 22`），Gradle 与手工复制都覆盖不了——ml-llm 先挡、主插件自己同样挡。
3. 于是监听器永远看不到变化，热重载事件永不触发。此外 243 平台上非 dynamic EP 还会让平台本来就拒绝卸载（源码 KDoc），验收态 init 脚本又主动 `autoReload.set(false)`（skill §2）——多重叠加导致「一直没成功」。

**结论：开发态 `autoReload` 在 Windows + 运行中的 IDE 上对已加载 jar 不可行**，这不是配置没开对，是文件锁的机制性死结。§2 的「正常模式 + 本地测试版本号」方案同样要面对这个锁：它靠 `DynamicPlugins.unloadPlugin` **先卸载再装**，理论上解锁后再覆盖可行（这正是自更新链的设计），但本轮在 runIde 目录开发态上 `unload` 返回 false（§1），所以两条路的成败都压在**「插件从标准 zip 安装、descriptor 非开发态」**这一个前提上。

**给用户的可落地建议（按优先级）**：
1. **当前最稳的正路**：暖容器 + 外部重跑 `runIde`（本轮实测 ~1.5 分钟一轮，含 84s 启动），不赌热重载。
2. **值得试一次的第二路**：按 §2 搭「专用常驻实例（zip 标准安装）」，改一版 → 本地 buildPlugin（4~76s）→ 走 installFromLocal 自更新链 → 若 `unload` 成功则免重启；失败自动回退第 1 路。这条能绕开开发态 descriptor 的 unload 否决，但**必须实测一轮**才能定，不能先假设成功。
3. **`autoReload` 路线暂不投入**：Windows 文件锁是死结，除非改在 Linux/macOS 沙盒里做开发态热载（那里覆盖已加载 jar 不受此限），或让 IDE 先卸载插件再让 Gradle 灌目录（等于退化为第 2 路）。

## 4. 最终建议汇总（三批合计）

1. **现行正路**：暖容器（sandbox-live 常驻）+ 外部重跑 runIde（~1.5 分钟/轮）；MCP 导航（open_file 1.8s）替代像素导航。
2. **262 验收腿**：Starter+Driver 第二步实测——打开真实 mpj 工程（录制主战场）→ IDE 拉起+工程打开+索引就绪 **82.2s**、全链 1m58s 全自动语义断言（`LocalProjectInfo` 打开本地工程，计时读数见 `TEST-pilot.DemoProjectPilotTest.xml`）。与暖容器 runIde 的 84s 启动相当且免 gradle 重建/bootstrap——**262 腿切主链条件已满足**，剩余待办仅「插件面板交互用例」（预览链等）迁移。243 腿维持 robot-server。
3. **免重启热更新**：**开发态与 autoReload 双死结实锤（不投入）；标准安装态（263 用户日常 IDE）已实证可行**——适用面=标准安装实例（日常 IDE/专用实例），开发沙盒维持重跑正路。卸载成本 ~20s/次，装载 ~6s。
4. **插件裁剪（disabled_plugins）**：实测收益≈0——裁 `training` 后 smart-mode 初始任务完成时点 9542ms，落在未裁剪历史波动区间（5035~12242ms）内；启动大头在平台+工程导入而非教学插件。**判定不做裁剪**，`disabled_plugins.txt` 维持空、seed 不预置。
5. **不做**：Windows UIA 路线（平台级不可达）、robot 语义点击并行验收（会动物理指针）、双路像素并行。
