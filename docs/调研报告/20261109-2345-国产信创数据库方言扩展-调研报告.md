# 国产 / 信创数据库方言扩展 — 调研报告

> 触发：用户提出「现在插件需要尽可能支持目前常用的国产数据库、信创数据库等」。
> 调研日期：2026-11-09。取证窗口：本仓源码（master @ `a2e8e8657`，15 方言）、MyBatis-Plus 3.0 分支源码（DbType.java / DialectFactory.java）、Druid master 源码（DbType.java）、各厂商官方文档与 Maven Central、JetBrains 官方文档与支持论坛、DBeaver 文档。
> 调研方式：三路并行——主控做插件代码侧接线面审计（GoldenDB 样板全枚举）；子代理 A 做国产/信创数据库全景；子代理 B 做业界多方言接入方案。
> 结论一句话：**插件已有成熟的 15 方言注册表体系（含达梦/金仓/瀚高/海量/openGauss/GaussDB/OceanBase/GoldenDB），本轮按既有「方言对象 + 全链登记」样板再扩 10 个新方言 + 4 个识别/角标位，即可把常用国产库覆盖面从 8 个推到 18 个；不引入 Druid、不打包驱动，沿既有架构演进。**

---

## 零、结论摘要

1. **插件底座已经为「支持更多国产库」做好了架构准备**。现役 15 方言走统一的 `Dialect` 接口（分页 / 引号 / 保留字 / 大小写折叠 / UPSERT / identity 包装 / EXPLAIN 表驱动）+ `DialectRegistry` 注册表 + URL 子协议/驱动类名双推断 + 能力矩阵 `DialectCapabilities`（`sql/Dialect.kt:23-420`、`sql/Dialect.kt:1257-1275`）。2026 年 10 月起连续三轮方言扩军（GaussDB 拆分、瀚高/海量、GoldenDB）已经把「新增一种方言」锤炼成固定流水线。

2. **单方言接入面已完整枚举**（以 GoldenDB 为样板，§二.4）：1 个方言对象 + 注册表 + 保留字表 + URL/驱动推断 + EXPLAIN 表 + IDEA 平台 SqlDialect/ParserDefinition 成对注册 + MCP 别名 + 采集角标 + 执行链路由 + 约 7 个测试文件。每个新方言的工作量是**已知的、线性的**。

3. **本轮扩展清单（按调研优先级）**：新增 **10 个方言对象**——TiDB（MySQL 族）、PolarDB-X（MySQL 族）、PolarDB Oracle 兼容版（Oracle 族）、GBase 8a（MySQL 族）、GBase 8c（PG 族）、神通 Oscar（Oracle 族）、优炫 UXDB（PG 族）、AntDB（PG 族）、虚谷 XuGu（混合自有）、崖山 YashanDB（Oracle 族）；另做 **4 个识别/角标位**——TDSQL（MySQL 版/PG 版）、星瑞格 SinoDB、行云 XCloud，及磐维独立展示名升级。完成后插件渲染方言 15 → **25**，采集角标覆盖面同步扩大。

4. **四个决策点全部按推荐项定案**（§四）：①不引入 Druid/不换解析引擎——插件的渲染面是「Wrapper 模型 → SQL 渲染」，不是 SQL 文本解析，Druid 的方言 Lexer/Parser 对本项目收益低且带 ~10MB shade 成本；②不打包任何国产库驱动——生产面维持现状（驱动仅 testImplementation 做引擎级验证），识别靠 URL 前缀 + 驱动类名；③长尾库走「族推定 + 文档级证据 + 如实标注证据档位」，不因缺真机而拒绝支持（沿用 GoldenDB「官方文档级」先例）；④方言集合对齐 MyBatis-Plus `DbType` 枚举（用户报库名的心智基线），但不复用其三大族分页判定（能力维度更多，保留自有接口）。

5. **证据纪律**：新增方言的每条形态结论都标证据档位（真机引擎级 / 字节码反编译级 / 官方文档级 / 族推定）。族推定项在方言 KDoc 与设置页如实标注「待真机校验」，不做假证据——沿用本仓 P-9「诚实不接入」与三档证据分级惯例（§二.5）。

## 二、现状盘点（插件代码侧，主控审计）

### 2.1 现役 15 方言

### 2.2 `Dialect` 接口能力面（新增方言要实现的契约）

`sql/Dialect.kt:23-420`：

| 能力 | 接口点 | 说明 |
|---|---|---|
| 分页 | `renderLimit(LimitClause)` | 渲染完整分页子句 |
| 标识符引用 | `quoteIdentifier` / `identifierQuotes` / `quoteIfKeyword` / `quoteIfNeeded` | 引号集合是引号方言判定的唯一事实源（MySQL 反引号 / PG 双引号 / SQLServer 方括号+双引号） |
| 大小写折叠族 | `identifierFolding`（NONE/UPPER/LOWER） | 目录来源引用判定按族分流 |
| 保留字 | `reservedWords`（小写集合） | `quoteIfKeyword` 按方言判定 |
| UPSERT | `renderUpsert`（后缀形态）/ `renderUpsertStatement`（整语句形态） | null = 无原生形态，降级纯 INSERT |
| identity 包装 | `renderInsertWrapper` | SQL Server / DM 的 `SET IDENTITY_INSERT` 类包装 |
| EXPLAIN | `renderExplain`（默认读 `ExplainSupport` 表，不再逐方言覆写） | 表驱动：`sql/ExplainSupport.kt:131-183` |
| DELETE LIMIT | `supportsDeleteLimit` | 基类 false，MySQL 族覆写 |

### 2.3 推断与呈现链

- **URL 子协议 → 渲染方言**：`sql/DialectInference.kt:13-57` `SUBPROTOCOL_TO_DIALECT`（`jdbc:<子协议>:` 提取）。已含 panwei→Oracle、goldendb→GoldenDB 等特判与证据注释。
- **URL 子协议 → 采集角标显示名**：`log/agent/JdbcUrlDialects.kt:16-51`（GBASE / Panwei（磐维）等已作角标在册，但**不是**渲染方言）。

- **能力矩阵**：`sql/DialectCapabilities.kt`（EXPLAIN / DELETE_LIMIT / UPSERT / IDENTITY_WRAP 四列，全部读接口真值，新方言缺登记如实显示 false）。

## 三、国产/信创数据库全景（子代理 A 调研，主控收编）

### 3.1 兼容阵营总图

国产库按兼容路线分四大阵营——**MySQL 阵营 / PostgreSQL 阵营 / Oracle 阵营 / 自有语法阵营**。MyBatis-Plus 3.0 分支 `DbType` 枚举（55 常量 + OTHER）就是这个阵营图的最权威用户心智基线，其 `DialectFactory` 同样按三大同族判定映射分页方言（`mysqlSameType()` / `oracleSameType()` / `postgresqlSameType()` + 少量特判）。

### 3.3 优先级定案依据

P0/P1/P2 排序三因子 = **用户量（信创份额）× 驱动可得性 × 形态证据强度**。TiDB/PolarDB-X 是云上国产化 MySQL 系最常见形态且零驱动成本；Oscar/UXDB/AntDB/GBase 是信创名录常客；虚谷/崖山/星瑞格/行云是长尾。注意金仓/瀚高/海量/达梦/openGauss/GaussDB/OceanBase/GoldenDB **已在册**，本轮不重复立项。

## 四、决策点定案（按推荐项执行）

| # | 决策点 | 选项 | 定案（推荐项） | 理由 |
|---|---|---|---|---|
| D1 | 是否引入 Druid 作为方言/解析引擎 | ①引入 Druid（shade relocate）②沿插件既有 Dialect 体系扩展 | **②** | 插件渲染面是「Wrapper/XML/日志模型 → SQL 渲染 + 参数还原」，不做通用 SQL 文本解析；Druid 的方言 Lexer/Parser 解决的是「解析任意方言 SQL 文本」，对本插件核心链路收益低；引 Druid 带来 ~10MB shade 包体、relocate 维护成本与平台撞包风险（S/L10 类平台契约风险）。既有 15 方言流水线已三次实战验证。 |
| D2 | 是否打包国产库驱动 | ①打进插件 ②用户自备驱动 + URL/驱动类名识别 | **②** | 生产面现状即不打包（驱动仅 testImplementation 做引擎级验证，`build.gradle.kts:85-113`）；GBase/虚谷/神通等 License 明确禁止或未授权再分发；IDEA 与 DBeaver 均为「不捆绑驱动」正路（JetBrains 官方文档 + DBeaver Driver Manager 双先例）。 |
| D3 | 长尾库（缺真机）是否支持 | ①拒绝支持直到有真机 ②族推定 + 文档级证据 + 如实标注 | **②** | GoldenDB 先例：官方文档级即可接入，EXPLAIN 无输出形态示例则诚实不接入（`ExplainSupport.kt:183`）；瀚高/海量先例：族推定接入但标注「已适配」非「已验证」。支持面扩大与证据诚实可兼得。 |
| D4 | 方言集合对齐基准 | ①自造清单 ②对齐 MyBatis-Plus DbType 枚举 | **②（对齐但不复用）** | 用户报库名的心智就是 MP 的 DbType 字符串；但 MP 的三大族判定只服务分页，插件能力维度（引号/折叠/UPSERT/EXPLAIN/identity）更多，保留自有 `Dialect` 接口，仅以 DbType 清单为覆盖面对账基线。 |

## 五、风险与边界

1. **跨仓守卫**：`DialectDocTableGuardTest` 读磁盘上兄弟文档站目录（`docs/架构设计/03` §218 记载），方言数变化会使文档站表格失配——实施时按先例「先落插件方言 → 同批改文档站归属表」，必要时在计划中登记该守卫的预期红/同步步骤。
2. **平台 EP 注册**：新方言的 `<sql.dialect>`/`<lang.parserDefinition>` 落 `database-optional.xml`（可选依赖描述文件）；243 平台该 EP 非动态（L16），属已知既有形态，不新增风险面。
3. **设置页是平台 UI 面**：下拉项由注册表顺序驱动，改布局类测试须按 L13 口径（平台 UI 测试全量未跑 = not run 待收口）。
4. **假证据风险**：族推定方言不得在文案里写「真机验证」；未实测端口不写死；EXPLAIN 无证据就 null（P-9）。
5. ** informix 系（SinoDB/8s）暂不做渲染方言**：MP 有 GBase8sDialect 但本插件无 Informix 族先例，本轮只做角标识别，避免为凑数引入无证据的方言——这是「诚实降级」，不是缺口。
