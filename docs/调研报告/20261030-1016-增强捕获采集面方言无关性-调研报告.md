# 增强捕获采集面的方言无关性 — 调研报告

> 触发：用户提出「SQL 日志与增强捕获应该可以不受插件支持的方言影响，正常情况所有 SQL 都应该能捕获；红线是不能因为插件导致用户服务受影响（如接口 500、项目无法启动）」。
> 调研日期：2026-10-30。基线：`dev` @ `209e32cd`。
> 范围：本仓两条采集链的方言依赖度审计、按接口匹配（catch-all）的可行性、红线清单与分档建议。
> 本文只含**本仓代码审计与可行性结论**；竞品逆向类材料不入公开仓（见 `docs/MEMORY.md`「私有目录」节）。

---

## 零、结论摘要

1. **采集能力本身不该与方言耦合，而且机制上可以做到。** 控制台日志链已经是纯文本解析、全程不读 `DialectRegistry`；增强链的方言耦合来自 `DriverRegistry` / `WeaveSpecs` 的**类名白名单实现方式**，不是 JDBC 机制的要求。方言注册表服务的是渲染/预览/执行，不是采集。
2. **未命中驱动时的静默是彻底的**：`SqlHookTransformer` 直接 `return null`，类按原字节装载、四计数不动、无 UI 提示；宿主侧唯一信号是 attach 那一行 `matched=0`。
3. **最伤用户的不是「少一条通道」，而是「两条都没有」**：agent 在线且应用侧 ACK 确认在采集时 `SqlCaptureGate.paused` 置真，控制台桥 `processConsoleLine` 随即短路。白名单漏一个驱动 = 双通道同时零产出（与 T-CaptureCoverage 现场一致）。**这一条不依赖 catch-all 就能先修**。
4. **catch-all 可行，但最优的第一步不是改 transformer，而是 attach 时用反射匹配**：`getAllLoadedClasses()` + `java.sql.Statement/Connection/Driver.isAssignableFrom` 零字节解析成本，覆盖「attach 到运行中应用」这一主场景的全部白名单缺口。
5. **不建议用接口匹配替换白名单**：白名单的真正价值是「已验证字节形态」（达梦 `chop_frame` 撤出、`ADD_BATCH` 不登记等），是 premain 安全的护栏。正确形态是**白名单优先 + 接口匹配兜底**，白名单语义从「唯一覆盖」降级为「已验证快速路」。
6. **接口匹配会命中连接池/日志包装类，必须加「嵌套只报最内层」门**（HikariCP 的 `HikariProxyPreparedStatement` 是 `final` 且 `implements java.sql.PreparedStatement`；MyBatis 的 `PreparedStatementLogger` 是 JDK 动态代理）——否则同一执行双报。
7. **红线里最重的一条是 premain 不得内联织入未知形态**：类定义失败 = 宿主 JVM 起不来，比采不到严重一个数量级。安全形态是「记录候选 + attach/周期 retransform 补挂」。
8. **实测还发现一个字节版本闸缺口**：ASM 9.4 读 `h2-2.3.232.jar` 里 `META-INF/versions/21/` 的类（major 65）抛 `Unsupported class file major version 65`——必须先读 `bytes[6..7]` 做 major 闸。

## 一、两条采集链的方言依赖度

### 1.1 控制台日志解析链：已经是方言无关的

| 组件 | 依赖 | 证据 |
|---|---|---|
| `log/MyBatisLogParser` | 只吃行文本 | `MyBatisLogParser.kt:27`、`:230` |
| `log/HibernateLogParser` | 只吃行文本 | `HibernateLogParser.kt:20`、`:433` |
| `log/JdbcTemplateLogParser` | 只吃行文本 | `JdbcTemplateLogParser.kt:33`、`:469` |
| `log/ShardingSphereLogParser` | 只吃行文本 | `ShardingSphereLogParser.kt:23` |
| `log/LogSqlRestorer` | 只吃行文本 | `LogSqlRestorer.kt:26`、`:44` |

全仓 `grep` 未见任何解析器读 `DialectRegistry`。方言注册表只服务两处：预览/执行的渲染（`LogToSqlPanel.kt:350`）与面板角标（`JdbcUrlDialects.kt:48`）。

**结论**：控制台链对「插件不支持的方言」没有依赖，它是当前唯一天然方言无关的采集面。

### 1.2 增强捕获链：耦合来自实现方式

| 组件 | 现状 | 位置 |
|---|---|---|
| `DriverRegistry` | connect 面 **17 个驱动类名**（`Set<String>` 哈希表） | `DriverRegistry.java:24-67` |
| `WeaveSpecs` | 语句面 24 类 / prepare 面 13 类 | `WeaveSpecs.java:43-188` |
| `SqlHookTransformer` | 匹配逻辑只有两条 `if`：类名在表里 → 织；否则 → `return null` | `SqlHookTransformer.java:72-84` |
| `AgentMain` | attach 后 retransform 已加载驱动，日志打 `matched=N wove=M` | `AgentMain.java:152-212`、`:203-211` |

未命中时：**类按原字节装载，四个计数（weavable/woven/noChange/failed）全部不动，宿主侧无异常、面板零条目**。这是「看着支持、一条不出」的机制来源。

### 1.3 交叉：两条通道会同时哑掉

`SqlCaptureGate.paused` 在「agent 在线且应用侧 ACK 确认在采集」时置真（`AgentManager.kt:1282`、`:1347`）；此时控制台桥的 `processConsoleLine` 直接短路、只做日志时间嗅探（`SqlLogConsoleBridge.kt:884`，EP 通道同函数 `SqlConsoleBridgeFilterProvider.kt:90`）。

**所以白名单漏一个驱动 ≠ 少一条通道，而是两条都没有。** 这解释了为什么「某方言一条 SQL 都看不到」会被用户感知为「插件坏了」。

### 1.4 第三条通道

`SqlSourceInterceptor` 注入（`ui/inject/` 系）走的是源码期注入，与运行期采集正交、不依赖驱动；`PreviewSideQuery` 只做只读旁路查询，也不参与 SQL 采集。两者都不构成采集兜底。

## 二、catch-all 可行性

### 2.1 首选：attach 时反射匹配（零字节解析）

`AgentMain.retransformLoadedDrivers` 现成结构（`:152-212`）：遍历 `inst.getAllLoadedClasses()`，用
`java.sql.Statement` / `java.sql.Connection` / `java.sql.Driver` 的 `isAssignableFrom(c)` 判定。

- **零 ASM 依赖、零字节解析**，与既有「`DriverRegistry` 零 ASM 依赖」契约一致；
- 覆盖「attach 到运行中应用」的全部白名单缺口（含未知驱动、含连接池包装）；
- 单类失败已被现有 `try` 吞掉（`:191-200`），风险约等于 0；
- 边界：只对**已加载**的类生效，premain 阶段类尚未加载 → 不解决 premain 冷启动场景（那要靠 2.2）。

### 2.2 兜底：transformer 侧两段式预筛（成本实测）

独立探针（JDK8 + ASM 9.8，真实 jar）实测：

| 阶段 | 单类成本 | 说明 |
|---|---|---|
| 裸字节子串预筛（`java/sql/`） | **2–5 µs/类** | 不做任何解析，命中率 11–15% |
| ASM header（`SKIP_CODE\|SKIP_DEBUG\|SKIP_FRAMES`） | **8–11 µs/类** | 只在预筛命中后跑，读 `interfaces` |
| 全树解析（现有织入基线） | 200–515 µs/类 | **只能落在确认命中的类上** |

2 万类应用合计约 **60–140 ms CPU**（5 秒启动约 1–3%）。若对全部类直接全树解析，2 万类要多花约 0.6 秒——**这是红线，不能走**。

### 2.3 必须并存，不替换

白名单保留为「已验证字节形态 + premain 安全集」：达梦 `DmDriver` 出口 `chop_frame` 撤出（`DriverRegistry.java:47-53`）、达梦 `ADD_BATCH`/`CLEAR_BATCH` 出口不登记等，都是「试过才知道会坏」的形态。接口匹配只做兜底，不碰 premain 内联。

### 2.4 接口匹配抓不到的

- `java.sql` 之外的自有 API（如某些驱动的 batch 专有接口）；
- 未加载且 premain 阶段无法安全内联的类（见 2.2/券 08）；
- 动态代理类在各 JDK 的 `isModifiableClass` 表现未全测（见 §五）。

### 2.5 双报风险（必须加门）

| 场景 | 实测 | 后果 |
|---|---|---|
| HikariCP 4.0.3 | 8 个类实现 `java.sql.*`（`HikariProxyStatement/PreparedStatement/CallableStatement/Connection`、`Proxy*`，`HikariProxyPreparedStatement` 是 `final`） | 池内/池外双报 |
| MyBatis `PreparedStatementLogger` | JDK 动态代理，同样实现 `java.sql.PreparedStatement` | 应用层/驱动层双报 |

不加门的表现：`EXEC_PARAM` 双报（IDE 60s 指纹去重只折叠成 `×2`，关掉去重就是两行）、`EXEC_CTX` 抬高 `unresolvedCount` 并打出误导性类名。

## 三、红线清单

> 用户红线原话：「不能因为增强捕获导致用户服务受影响，例如导致接口 500，例如导致项目无法启动」。

| # | 风险 | 现状 | 缓解 | 验证手段 |
|---|---|---|---|---|
| **R1** | **ClassCastException**（对象身份被替换） | `wrapConnection` 默认 false（`SqlHookCallbacks.java:62-66`）；语句面只织方法体 | catch-all 与 `wrapConnection` **彻底解耦**，默认值不得改；新路径加 `assertSame` 用例 | 真实 JVM 冒烟：带/不带 agent 强转同一连接 |
| **R2** | **VerifyError / 链接期失败**（达梦 `chop_frame` 先例） | 单类 retransform 失败可吞（`AgentMain.java:191-200`）；premain 失败不可恢复 | **premain 不内联未知形态**：记录候选 → attach/周期 retransform 补挂；字节层校验前置到实施期（真实 jar 织入 + 隔离 loader 定义） | `StatementWeaverVendorCoverageTest` 字节层 + 真实 JVM premain/attach 冒烟 |
| **R3** | **类文件版本不支持** | ASM 9.4 读 major 65 抛 `Unsupported class file major version 65`（h2 2.3.232 的 `META-INF/versions/21`） | 先读 `bytes[6..7]` 做 major 闸，超限即原字节返回；评估升 ASM | 构造 major>上限 的样本 + 真实 jar 多版本矩阵 |
| **R4** | **启动变慢 / 类加载风暴** | 当前**无任何类数上限与耗时预算** | 加类数上限、累计耗时预算、连续失败 kill switch | 2 万类应用启动 A/B（带/不带 agent） |
| **R5** | **内存膨胀** | `StatementRegistry` 弱键但**无上限**（`:55-72`）；catch-all 会让池包装 PS 也登记 | 加上限 + 淘汰策略 | 压测：长连接池 + 高频 PS 创建 |
| **R6** | **classloader 泄漏**（热部署） | `SqlHookCallbacks.GET_CONNECTION_METHODS:254`、`UrlResolver.GET_URL_METHODS:19` 是 `Class` 强引用 | 改 `ClassValue` / 弱键 | 热部署反复 reload 后看 old loader 是否可达 |
| **R7** | **回调异常穿透** | 回调已全 `catch (Throwable)`；`DriverRegistry` 零 ASM 依赖是既有契约 | 新 matcher 必须在 `transform` 的 try 内首次触达 | 注入抛异常的探针 matcher |
| **R8** | **脱敏漏口** | 新 face 必须复用 `WovenEvents.java:88` 唯一出口 | 守卫：新事件构造点必须经该出口 | 源码扫描守卫 |
| **R9** | **双报**（见 §2.5） | 无 | 「嵌套只报最内层」门 | Hikari + MyBatis 单执行恰好 1 条事件 |
| **R10** | **`SqlCaptureGate.paused` 假在线** | agent ACK 即暂停控制台桥 | 活性回落：agent 在线但 N 秒零事件且控制台仍有 SQL → 自动解封 | 造「agent 在线但零事件」场景 |

**总原则**：任何新增采集面都必须满足「失败即原样返回 + 异常全吞 + 不改返回值 + 不改对象身份 + 有预算上限」。违反任一条即不得进入 premain 内联面。

## 四、分档建议

### 立即可做（低风险，不碰 premain 内联）

1. **attach 反射式接口匹配**（§2.1）——覆盖主场景全部缺口；
2. **控制台桥活性回落**（R10）——救「agent 假在线」这类双哑；
3. **覆盖自检上报**——`matched/woven` 进心跳/诊断行，让「采不到」可被用户看见；
4. **`Class` 强引用缓存改弱**（R6）；
5. **major 版本闸 + ASM 升级评估**（R3）。

### 需真机验证后再上

6. transformer 兜底分派（§2.2 两段式）；
7. 「嵌套只报最内层」门（§2.5）；
8. premain 延迟补挂（R2）；
9. 预算熔断（R4）；
10. Hikari / MyBatis 单执行恰好 1 条事件。

### 明确不建议

- 用接口匹配**替换**白名单；
- catch-all 与连接包装同时开；
- 纯子串匹配直接织（不跑 header 确认）；
- 用类名黑名单消双报；
- premain 内联未知字节；
- 把方言注册表接入采集门控（采集与方言本应正交）。
