## 4. 部署过程中必须打的三处补丁（镜像本身在本宿主跑不通）

1. **CPU 预检过严**：`check_cpu_instructions` 要求 `lscpu` 同时有 `avx` 和 `rdtscp`，本宿主是 QEMU vCPU
   （`avx/avx2/rdtscp/sse4.x/popcnt` 全无）。绕过预检后 **initdb 与引擎启动正常、`gs_checkos` 通过**——
   说明是预检门槛而非真实指令依赖。
2. **cgroup v2 使 `checkDockerEnv()` 恒假**：它 grep `/proc/1/cgroup` 的 cgroup v1 形态，本宿主是
   `0::/init.scope`。这一个 False 让 9 处「容器内可容忍」分支全部失效，先后卡在
   `find /etc/sysconfig/network-scripts`（GAUSS-51400）与 `/sbin/ethtool -g eth0`（GAUSS-50612）。
3. **`listen_addresses` 绑死安装时的容器 IP**：容器重启换 IP 后 `could not create listen socket`。
   已把「按当前 IP 重写 listen_addresses」写进 `/root/run.sh` 的启动分支，实测重启后自愈且数据完好。

另有一处非阻塞项：`hostnamectl set-hostname pdb` 在容器内报 `Device or resource busy`（无害，主机名仍生效）。

## 5. 未做 / 不能做

- **未验证**：仓库内的 `panweidb-jdbc-1.0.0.jar`（V1 驱动）连 3.4.0 实例是否正常；方言渲染套件未在磐维上跑过。
- **未做**：内存受限（16 GB 宿主，11 个既有容器）时没有尝试更多实例；两实例已把
  `shared_buffers` 从默认 1 GB 降到 256 MB。`max_process_memory` 不能再降：引擎下限为
  `2GB + cstore_buffers(512MB) + shared_buffers(256MB) + preserved(2241MB) ≈ 5057MB`。
  两实例稳定后宿主 `available` 只剩约 **960 MB**（`Mem: 16003 total / 9068 used / 966 available`）——
  再上新实例前必须先腾内存，否则会挤压既有 11 个容器。
- **不能做**：单实例内建多兼容档——3.4.0 的 `CREATE DATABASE` **没有** `DBCOMPATIBILITY` 选项（`\h create database` 实证），
  兼容档是安装期决定的，所以 A/B 必须两个实例。
- **风险提示**：镜像来自个人命名空间且无版本来源证明；如需长期使用，建议向中国移动索取官方镜像或
  直接使用厂商 tarball（`no_mot` 版 + `om` 版）自行构建。

脚本本身：`set -euo pipefail`、逐步 echo 锚点、幂等、无凭据、纯 ASCII（只有两行注释里带中文文档路径）、
LF 无 BOM；每次改写都走「写临时文件 → `os.replace` 原子替换」，所以属主与权限保持（不是 `sed -i` 那种，
后者可能把 `omm:dbgrp 0700` 变成 `root:root`）；`*.orig` 只写一次、不覆盖已存在的。

### 7.4 边界一：`docker commit` 不抓挂载卷

上表 ①② 缺席不是没打上，是**落点决定的**：这两处在 `<soft>` 树里，而 `<soft>` 就是
`-v /www/panweidb-ora/data:/database` 那个卷——`docker commit` 只快照容器可写层，卷内容一概不进镜像。
所以两条落地方式的实际覆盖面是：

- **A（脚本）**：①②③②b 全覆盖，代价是每次重建都要在「已解包、未安装」窗口内跑一次，
  窗口本身是几十秒到几分钟的赛跑（§4 末尾记的就是这个「可行但脆」）。
- **B（pwfix）**：**只覆盖 ③ 与 ②b**。复用同一个 `/www/.../data` 卷时等价于全覆盖（①② 本来就在卷里）；
  一旦换了新卷，仍需在解包后跑一次脚本补 ①②——只是这时脚本已经在镜像里，省掉 `docker cp` 那一步。

这条必须写在前面，否则「有个定型镜像了」最容易被读成「以后什么都不用管」。

### 7.5 边界二：脚本只做「已解包、未安装」那一步

脚本对「解包完成了没有」只有准入判断（`<soft>/script` 不存在就带原因非零退出），**没有**「等解包」的能力——
轮询等待仍靠人手。想让 B 路线彻底免窗口，可选做法是在 `run.sh` 安装分支的
`Ha_unarchive_and_config_xml.yml` 之后、`Ha_install_database.yml` 之前插一行
`bash /root/patch-panweidb-image.sh`。本轮**没做**：那改的是安装器主流程，动它要单独一轮验收，不在本次授权范围。

另外脚本对锚点做了**唯一性断言**（`PreInstallUtility.py` 里 `raise Exception(cpu_mission)` 恰好 1 处、
`def checkDockerEnv():` 恰好 1 处、`su - omm -c "gs_ctl start"` 恰好 1 处），锚点找不到或有多处就非零退出，
**不会静默跳过**。将来上游镜像改版导致锚点变化，会以失败告终而不是打半个补丁。

### 7.6 本轮在服务器上动了什么（与恢复情况）

全部落在允许动作内：`docker exec`、`docker commit`、`docker image inspect`、一次 `docker run --rm` 起 shell。
没有起第三个数据库实例、没有 `docker pull`、没有 `docker system prune`、没有停或重启任何容器。

| 动作 | 说明 | 恢复 |
|---|---|---|
| `docker exec panweidb-ora` 读文件 / 跑探针 | 读 `/database`、`/proc/1/cgroup`，在容器内 `/tmp` 建临时树 | 容器内 `/tmp/pwfix-replay`、`/tmp/patch-panweidb-image.sh`、`/tmp/pwfix-helper-*.py` 已删净 |
| 写入容器 `/root/patch-panweidb-image.sh` | 为定型镜像带上 helper | **有意保留**（随镜像定型，不删） |
| `docker commit --pause=false panweidb-ora panweidb:3.4.0-pwfix` | **未用默认的 `--pause`**：默认会 SIGSTOP 容器再快照，而 `/database` 是卷、可写层里没有库状态，冻结没有收益；两容器全程 Up，Uptime 未归零 | — |
| `docker run --rm --entrypoint sh panweidb:3.4.0-pwfix -c '<检查>'` | 不起数据库、退出即删 | 跑完 `docker ps -a` 无残留容器 |

宿主 `available` 无恶化（开工前 777 MB，收工 944 MB），`docker ps -q` 计数 12，与开工前一致。

### 7.7 仍未做

- 定型镜像只覆盖 ③/②b（§7.4 的卷边界），**没有**做成「开箱即用、连 ①② 都在镜像里」的成品；
  真要那样得在无卷容器里预装一遍再 commit，或走 §7.5 的 run.sh 钩子，两者本轮都没做。
- ① 的**线上**反向探针没跑：线上 `PreInstallUtility.py` 没有 `.orig`（当初是直接改的），
  反向证据取自洁净重放里那个与 pristine **逐字节相同**的副本，不是取自线上文件。
- pwfix 镜像是「某台宿主上某次安装」的冻结快照，不是厂商产物、也没有版本来源背书（同 §2 的定级）；
  上游镜像升版（3.4.0 之外的 tag）必须重做一遍。
- 两实例仍未进 `.local/db-env-instances.tsv` 灾难重建清单（§5 原本记的另一半「仍缺」，本轮未碰）。
