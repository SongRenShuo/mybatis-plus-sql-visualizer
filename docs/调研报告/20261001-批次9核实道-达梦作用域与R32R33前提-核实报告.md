# 批次 9 核实道：达梦作用域与 R32/R33 前提核实报告

一行总结：三项核实全部闭合——达梦元数据作用域判「不适用」（我方零元数据 SQL，表结构全走 DBN 内存模型且消费端已表级＋库名限定）；V40 前提「url 全程在握、仅映射显示名即弃」属实（两原锚点逐字命中），但 dynamic-datasource 语义名在现织入点不可达，R32 按「弱形态 S／真语义名 M」双档立项；V41 前提「EXPLAIN 直送原生控制台」属实且截获输出不可行，自建执行链的数据链大半现成，R33 档 M~L 成立。

核实基线：工作树 `mpsv-b9-verify`（分支 t-b9verify，基 = dev e8b5ca0），只读核实；达梦真库实测经 dbx MCP（会话已关闭，全程只读 SELECT）。所有行号为该基线现值。

## 一、达梦元数据查询作用域（对照 DBX #162「改表级作用域避免全库扫」）

### 现状锚点

src/main 全树 grep 达梦相关产物只有三类，没有一类是元数据 SQL：

1. 方言识别：`src/main/kotlin/cn/song/mybatisplus/visualizer/log/agent/JdbcUrlDialects.kt:26`（`"dm" to "DM（达梦）"`）、`mcp/McpDialectDetector.kt:20` 与 `:42`（`jdbc:dm`）、`sql/DialectInference.kt:24`——都是 URL/文本 → 方言名的映射。
2. SQL 生成：`sql/Dialect.kt:618` 起 `DmDialect`（LIMIT 形态、双引号引用、DM_RESERVED 保留字、identity 包装 `:489-499`，2026-09-23 DM8 真机证据在案）。
3. 执行与 EXPLAIN 提交：走原生 Database 控制台或 `mcp/McpDbExecutor.kt:51-58` 的反射执行链——两条都只执行调用方给的语句（用户 SQL/EXPLAIN 包装产物），不自发任何元数据查询。

表列结构的取数路径唯一：IDE database 插件的 DBN 内省内存模型，不是 SQL 查系统表。

- `ui/highlight/DatabaseSchemaResolver.kt:19-22`（KDoc 遍历路径：DataSourceManager → DasDataSource.getModel → DasModel.traverser 迭代筛 DasTable）、`:657-731` `reflectTraversal`（全反射链，遍历的是 IDE 已内省完的内存树）、`:748-825` `collectFromDataSource`（内存扫描按表名匹配）。
- MCP schema 上下文同源：`mcp/McpSchemaContextService.kt:20-33`（P4 自建「表名 → 目标库那张表」索引，数据源一次遍历）、`:344-347`。
- JOIN 图外键：`ui/diagram/nativefw/db/JoinVirtualFkProvider.kt:143`、`:184`、`:199`——`DasUtil.getColumns(table)`，DBN 的**表级** API。

反向证据：`ALL_TAB_COLUMNS` / `SYSCOLUMNS` / `SYSOBJECTS` / `USER_TAB*` / JDBC `DatabaseMetaData.getColumns` 在 src/main 零命中；`information_schema` 只出现在 `sql/Dialect.kt:90-95`、`:262-265`、`:403-405`、`:673-674`、`:731-732` 的标识符折叠注释里——那些是 DBX MCP 真机验证探针的读数留档，不是生产查询。

消费端限定与缓存已多层在位：P7 库名维度限定（`DatabaseSchemaResolver.kt:780-784`，表祖先链须含数据源 URL 的库名才命中）、正缓存（`:217-218`）、负缓存 TTL 30s（`:284-290`）、跨调用索引 TTL＋容量＋DDL 失效（`McpSchemaContextService.kt:211-261`）。

### 实测证据（dbx MCP 达梦真库，2026-10-01）

连接：`达梦 DM8`（dbx-test-host:20096），`SELECT USER FROM DUAL` → `DBX_TEST`；`V$VERSION` → DM Database Server 64 V8（0x7000c）。

- 全库元数据规模：`ALL_TABLES` 96 行（7 个 OWNER：SYS 62、DBX_TEST 22、MPJ_DEMO 6、SYSDBA 2 等）；`ALL_TAB_COLUMNS` 全库 3594 行；DM 原生字典 `SYS.SYSCOLUMNS` 全库 3775 行——后者正是 JDBC 驱动 `getColumns` 类路径的实际命中面，#162 说的「全库扫」就是这个量级的拉取。
- 表级作用域对照：`ALL_TAB_COLUMNS WHERE OWNER='DBX_TEST' AND TABLE_NAME='TB_USER'` → 4 行 52ms。#162 的修法在 DM8 上就是这条 WHERE，代价 O(单表列数) 而非全库千行级。
- 大小写折叠（在册教训复核）：裸写小写 `SELECT COUNT(*) FROM tb_user` 直接命中（18ms）——DM8 标识符解析大小写不敏感，与 `Dialect.kt:94-95`、`:265` 在册口径「DM 折叠 = NONE（不敏感）」一致。Oracle 系「引号＋大写」的字典查询习惯在 DM 上照搬只会自找麻烦：字典**值**是大写存储（`WHERE TABLE_NAME='TB_USER'` 才命中），标识符**解析**却不分大小写，两头是两回事。

### 判定

**不适用（我方不走该路径，无全库扫缺口）。** #162 的教训对象是「自持 JDBC/SQL 元数据查询」的实现方；我方元数据全部经 IDE DBN 内省模型，消费端已表级＋库名限定并带缓存矩阵。DBN 内省在 DM 上的库端查询作用域是 IDE database 插件的领地，不归我方管。

### 建议

销账。两点留档：

1. 若用户侧 DM 数据源内省慢，处置在 IDE 数据源设置（内省范围/连接选项），不是插件代码；我方 UI 侧的「全扫」只是 DasModel 内存遍历（UI 代价，非 DB 负载），已有缓存矩阵兜着。
2. 若未来 R 线引入自持元数据链（远端库结构对比之类），照 #162 直接写 `WHERE OWNER=? AND TABLE_NAME=?`，DM8 真机参数本次已备（96 表/3594 列的对照规模 + 折叠口径）。

## 二、V40 核实（R32 立项前提）：agent url → 数据源语义名映射形态

### 现状锚点（两处原锚点均逐字命中，无漂移）

- url 捕获源头：`sub-projects/sql-visualizer-agent/src/main/java/cn/song/mybatisplus/sqlvis/agent/hook/ConnectionHandler.java:26-30`（connect 时存 url）、织入点 `agent/ConnectWeaver.java:18-19`（`connect(String, Properties)` 每个 ARETURN 前插 `onConnection(conn, url)`）、目标类白名单 `agent/DriverRegistry.java:17-44`（含 `dm.jdbc.driver.DmDriver` :36）。
- url 透传：`hook/StatementHandler.java:149` `event.url = url;`（原锚点 :149 逐字命中）——**url 全程在握属实**。
- 映射即弃：`log/agent/AgentEventAdapter.kt:41` `databaseName = JdbcUrlDialects.displayName(event.url)`（原锚点逐字命中）；`JdbcUrlDialects.kt:42-50` 只按子协议映射方言显示名（未知 → null）；`log/LogSqlModels.kt:126` `val databaseName: String? = null` 是 LogSqlEntry 里**唯一**数据源相关字段——原始 url 不入库。消费点：`log/SqlLogPanel.kt:2250`（角标）、`log/SqlLogAutoSaver.kt:364`、`mcp/HistorySearchService.kt:208`。

### 可达性推演

任务问句「拦截点上下文有没有 DataSource lookup 机会」的答案是**没有**：织入回调签名只有 `(Connection, url)` 两个量（`ConnectWeaver.java:99-110` 的注入序列），没有 DataSource 对象在握。

dynamic-datasource 语义名的生存位置与织入点时空分离：语义名（primary/slave_1 等）是 `DynamicRoutingDataSource.dataSourceMap` 的键，每请求由 `determineTargetDataSource()` 按 ThreadLocal 查找键解析——解析发生在请求线程、池之上层；而 JDBC connect 发生在**池内**（Hikari 补充连接线程，稳态下与任何请求无时空交集）。所以 connect 时既拿不到路由 DataSource 也拿不到语义名，connect 时点的调用栈通常是池内部帧，栈推断同样无效。

execute 时点的栈：业务线程执行栈确含 `DynamicRoutingDataSource#getConnection` 帧，但解析出的语义名是方法**返回值**不是栈帧——16 帧截断的 StackDigest 只能证明「在用 dynamic-datasource」，拿不到名字。

真可达路径 = 新增按类织入：`SqlHookTransformer.java:22` 的目标类筛选（现仅 `DriverRegistry.isWeavable`）扩第二张注册表；对 `DynamicRoutingDataSource#determineTargetDataSource` 做 ARETURN 返回值捕获（`ConnectWeaver` 同款零分支注入、只改方法体、retransform 合规），对 `addDataSource` 织入建 DataSource 身份 → 语义名映射；getConnection 时把解析名存 agent ThreadLocal，`StatementHandler.emitEvent` 同业务线程读取。方法体级织入有 ConnectWeaver 先例，形态可行。

### 判定

url 在握、映射显示名即弃：属实。语义名在现织入点不可达，需新织入才可达。

### 建议与成本

R32 拆两档：

- 弱形态（S）：SqlEvent/LogSqlEntry 保留原始 url 或经 `execute/JdbcUrlDatabase.kt:30-36`（现成解析器，计划已点名）解析的库名，角标从「方言名」升级为「库名」。局限：池 URL 不总含库名（Oracle SID 形态等），且语义名 ≠ url 库名——一个语义名集合可共用同一 URL。
- 真语义名形态（M）：上述按类织入 + ThreadLocal 桥 + 事件协议加字段 + 面板展示。项数不少：协议帧加字段会撞 `AgentProtocolSyncTest` 帧守卫、dynamic-datasource 版本面要真机采样、agentmain 晚挂载时类已加载（retransform 可改但须真机验证）。都在 M 档内。

计划的「S~M」成立，但要注明 S 档只有弱形态。事务身份（@DS 事务内切换）两头都不够：ThreadLocal 桥只覆盖 getConnection 时点的键，事务中途切换会错标——立项时登记为已知限制。

## 三、V41 核实（R33 立项前提）：面板 EXPLAIN 结构化渲染的执行链形态

### 现状锚点（原 SqlPreviewPanel.kt:1514 漂移，重锚如下）

- `ui/SqlPreviewPanel.kt:1488` `explainSql()`；`:1494` `ExplainGate.planExplainSubmit`（`sql/ExplainGate.kt:21`）按方言包装；`:1513` `is SubmitPlan.Submit -> plan.statement`；`:1525-1533` `SqlExecutor.execute(proj, explainSql, null, true, onConsole = { embedConsole(...) }, ...)`——**「直送原生 Database 控制台」现状属实**：结果由平台控制台渲染，插件只做组件换入（`embedConsole`），顶部静态规则标注与控制台结果同屏对照（`:1479` KDoc）。
- 执行链：`execute/SqlExecutor.kt:32-59` → `DataSourceSelector.selectAndExecute` → `executeOnConsole`（`execute/DataSourceSelector.kt:2649`）反射 `console.executeQueries`（`:2705-2710`）。插件对结果区只做页签激活/组件换入/错误文本启发（consoleHistoryLength 基线，`:2712` 附近）——**无行列级程序化读取面**。这与 `util/ExplainIndexAdvisor.kt:12-16` 在仓结论（T-EI-01 落点定案：网格数据由 DBN 托管，硬读需侵入平台内部网格模型，IDE 面建议条当时挂账）互证。
- 两格式与消费面：`util/ExplainIndexAdvisor.kt:64` `adviseMysql`（TABLE 格式：type=ALL/key=NULL/filesort/temporary 四规则）、`:156` `adviseJsonPlan`（JSON 格式，T-ECH-03 修复点，三段容错）、`:114` `advisePlanText`（TEXT 格式）。**唯一生产消费方** = `mcp/SqlVisualizerExplainTool.kt:53-54`（MCP sqlv_explain）——「两格式仅 MCP 消费」属实。
- 自持链已在仓：`mcp/McpExplainFormatter.kt:25-30` `RawResult`（headers/rows/truncated/notices）、`:66-78` `format`（原 66-77 锚漂 1 行）；`mcp/McpDbExecutor.kt:51-58` 反射执行链（DatabaseConnectionManager.build → createBlocking → RemoteStatement.executeQuery，同步无 UI）+ `:18` drainWarnings + ExecutionTimeoutGuard；`SqlVisualizerExplainTool.kt:148-152` `executeExplain` → RawResult 接线现成。

### 判定（可行路径与成本）

- **截获原生控制台输出：不可行。** 结果网格由 DBN 托管，插件侧无程序化读面（组件换入 + 文本级错误启发是全部现有交互）；硬读 = 侵入平台内部网格模型，版本脆弱，排除。
- **自建执行链：可行，且数据链大半现成。** ExplainGate 包装、McpDbExecutor 建连执行、RawResult 行列、ExplainIndexAdvisor 规则、notices/超时闸全部可复用（从 mcp/ 包挪出或泛化）。缺口两块：①面板侧执行入口——McpDbExecutor 现按 alias 找数据源（`findDataSource`），面板需要数据源选择 UX，而 DataSourceSelector 的选择 UI 绑死在控制台创建链上，需剥离或轻造；②结构化渲染 UI（计划树表格/建议条），从零画。
- 成本档：数据链面板化 S~M；结构化渲染 UI M~L；整体 **M~L**——计划档成立。

### 建议与成本

R33 可立项，路线定为「自建执行链」，两步走：第一步数据链面板化（复用面最大、可独立验证——EXPLAIN 文本列头＋建议条先上，等价 MCP 链的面板版）；第二步结构化渲染 UI。风险注记：密码弹窗/建连时序（createBlocking 同步建连已在 MCP 链真机验证过）、Community 无 database 插件时自建链同样不可用（`McpDbExecutor.isDatabaseAvailable` 降级面已有）。R23（Oracle/SQL Server EXPLAIN 模板接入）与本件同域，排程时合并考量。
