# 演示录制点击定位提效工具调研报告

**创建时间**：2026-10-13 21:30
**问题来源**：录制管线（`record/`，pyautogui + mss + PIL + numpy）反复出现「点不到位 / 点错控件」，根因是**按屏幕像素坐标点击**这一路线本身脆弱（控件随内容漂、悬停才渲染、CJK 双宽、模态/独立窗口互相遮挡、合成滚动 no-op）。要求调研「按元素 / 按图像锚点定位」的工具与方案，给出明确推荐与落地路径。
**调研方法**：官方文档（JetBrains Platform SDK、Oracle Java Accessibility Guide、Microsoft Learn、pyautogui/pyscreeze/pywinauto/Airtest/PaddleOCR 官方仓库）+ 本机实证（Python 包清单、JBR 自带件、Swing 探针 + UIA/MSAA 实测、Gradle 缓存内 IPGP 2.18.1 源码、JetBrains Maven 元数据）+ 本仓 `record/` 与 `build.gradle.kts` 逐处实读。

---

## 一、结论先行

1. **首选＝JetBrains 组件树定位，纯 Python 接入，已在 IDEA 2026.2.1 沙盒真机通过。** RemoteRobot 的 `robot-server` 是 IDE 内 HTTP/JSON 服务。`POST /xpath/components` 返回组件身份与 `x/y/width/height`，但 **x/y 是父组件内相对坐标，不是屏幕坐标**（jar 构造器直接调 `Component.getX/getY`，真机也复现）；客户端用 XPath 的 `ancestor::div` 父链逐级累加，才得到屏幕物理坐标。实测将「SQL 历史」页签定位到 `(1463,118)`，提权点击后页签真的切换。录制态通过 `localPlugin(...)` 与主插件、AI Assistant 共装；不得覆盖 `idea.plugins.path`。RemoteRobot 官方虽已弃用，但这一组合在当前 2026.2.1 沙盒实测可用。
2. **兜底方案＝OpenCV 图像锚点匹配，立即可用、零 IDE 侧改动。** 只需装 `opencv-python`。把关键点击点从「算坐标」改为「匹配一张小模板图」，天然免疫控件漂移、CJK 双宽、主题局部变化（灰度 + 多尺度）。这是**当前就能把「点空」率压下来**的一步。
3. **Windows UIA 路线否决。** 本机实测：UIA 能看见 Swing 应用的顶层窗口（`SunAwtFrame`），但**看不到窗口内部的任何控件（children=0）**，即使已用 `jabswitch -enable` 注册了 JAB、且进程内确认加载了 `JavaAccessBridge-64.dll`。作为对照，同一个 UIA 探针在文件资源管理器上枚举到 173 个后代控件——探针本身没问题。结论：`pywinauto(backend='uia')` / `uiautomation` **拿不到 IntelliJ 的 Swing 控件树**，不解决本项目痛点。
4. **OCR 定位只作补充**，不作主路线。IDE 小字号 + 中英混排下识别率与耗时都不理想，且它只给「文字出现的位置」，仍需二次判定是哪个控件。
5. **SikuliX / Airtest 无增益。** 两者在 Windows 上的定位机制本质都是 OpenCV 图像匹配（Airtest 的 Windows 后端实测源码就是 `pywinauto` + `mss` + `aircv`），换框架只是把现有 `record/` 的匹配逻辑重写一遍，还引入 Java/JVM 或大依赖。

**一句话**：短期上「图像锚点」（`opencv-python`），中期上「RemoteRobot HTTP 组件定位」（`robot-server` + 自研 ~50 行 Python 客户端）做精确锚定，两者可并存——组件定位拿精确矩形，图像锚点做兜底与「点后校验」。

## 二、背景与痛点（本仓既有教训，作为评估基准）

`record/locate.py` 与 `record/BASELINE.md` 已把「按坐标点」的失败模式记录得很清楚，本报告不再重复论证，只提炼作为**评估各方案的判据**：

- **弹窗/对话框高度随内容变**：预览弹窗按钮行目测偏低 48px，连点三次全落空（`locate.button_row_y` 注释）。
- **按钮相对 x 随窗口宽度变**：按「窗口相对 979」硬算＝把偏移算了两遍，点到空白（`locate.bright_band_x` 注释）。
- **对话框/浮窗不是进程主窗口**：`Get-Process.MainWindowHandle` 看不到，必须 `EnumWindows` 按 PID 取矩形（`locate.window_rect`）。
- **悬停才渲染**：新 UI 下工具窗标题栏动作悬停才出现，坐标得现量。
- **CJK 双宽**：按单宽估算的 x 落到相邻 token（实测把注释里的中文词当表名）。
- **模态/独立窗口 TOPMOST 互相遮挡**：`ensure_foreground` 需按 PID（而非句柄）判定前台。
- 现有「按证据算」的三件套（窗口矩形 / 底部偏移 / 像素剖面）已经是对「纯目测」的修正，但仍是**几何推断**，不是**元素身份**——控件一旦换布局就失效。

评估维度统一为：**定位依据（元素身份 / 图像 / 文字 / 几何）**、**是否给屏幕坐标**、**Python 可接入性**、**IDE 侧改动**、**稳定性**、**代价**。

## 三、逐方案评估

### 方案 A：JetBrains 官方「组件树」路线（重点）

这是能够**按 Swing 组件身份**定位的路线；RemoteRobot 返回的是父组件相对几何，须累加祖先链才能得到屏幕矩形。要区分老的 RemoteRobot（HTTP）和新的 Starter + Driver（JMX）。

#### A1. RemoteRobot / `intellij-ui-test-robot`（HTTP，官方已弃用但仍可用）——本方案的主选

**是什么**：由两部分组成——客户端库 `remote-robot`（发指令）+ IDE 侧插件 `robot-server`（收指令）。官方 README 原文：「It consists of a `remote-robot` client and a `robot-server` plugin」「The `remote-robot` library communicates with the `robot-server` plugin via an HTTP protocol. This connection means you can launch IDEA on remote machines or in Docker containers.」（出处：`github.com/JetBrains/intellij-ui-test-robot` README）。

**怎么用（官方口径）**：
- 插件侧：`runIdeForUiTests { systemProperty "robot-server.port", "8082" }` + `downloadRobotServerPlugin { version = ... }`；默认端口 8580。
- 客户端侧：`RemoteRobot remoteRobot = new RemoteRobot("http://127.0.0.1:8082")`，用 XPath 找组件：`byXpath("//div[@class='MainButton' and @text='Log in to GitHub...']")`，再 `.click()`。打开 `http://ROBOT-SERVER:PORT` 会显示 **IDE 组件树的 HTML 页面**，并带一个简易 XPath 生成器（README 原文，附 `docs/hierarchy.gif`）。
- 最新版本 `0.11.23`（JetBrains Maven 元数据实测：`packages.jetbrains.team/maven/p/ij/intellij-dependencies/com/intellij/remoterobot/robot-server-plugin/maven-metadata.xml` 的 `<latest>` 与 `<release>` 均为 0.11.23）。

**关键发现：协议是普通 HTTP + JSON（REST），Python 可直连。**
客户端 `RemoteRobot.kt` 用 `Retrofit` + `OkHttp` + `GsonConverterFactory`，接口定义在 `remote-robot/src/main/kotlin/com/intellij/remoterobot/client/IdeRobotApi.kt`（本机实测抓取的源码）。核心端点：

```
POST  /xpath/component                 body {"xpath": "..."}   → FindComponentsResponse
POST  /xpath/components                body {"xpath": "..."}   → FindComponentsResponse
POST  /xpath/{containerId}/component   （限定在某容器内查找）
POST  /{componentId}/data              → ComponentDataResponse
POST  /js/execute                      body {"script":"...","runInEdt":bool}  → 在 IDE 侧跑 Rhino JS
POST  /{componentId}/js/execute
POST  /js/retrieveAny                  → 取任意值（读组件属性/文本）
GET   /screenshot                      → JSON 的有符号整数 bytes 数组，解码后才是 PNG
GET   /{componentId}/screenshot        → 单组件 PNG（isPaintingMode 可选）
```

数据类（本机实测源码）：
```kotlin
class FindByXpathRequest(@SerializedName("xpath") val xpath: String)
class FindComponentsResponse(
    @SerializedName("elementList") val components: List<RemoteComponent>?, ...)
class RemoteComponent(
    val id: String, val className: String, val name: String? = null,
    val x: Int, val y: Int, val width: Int, val height: Int)
```
`RemoteComponent` 由 `Component` 直接构造（`component.getX/getY/getWidth/getHeight`），其中 **x/y 是相对父组件**；按 XPath 找到唯一目标后，再查它的 `ancestor::div`，把父链各层的 x/y 相加，最后加目标的半宽/半高，才可交给 `pyautogui`。服务端不会直接给屏幕矩形。

**对本项目是否可行：可行，且是首选，但需联调验证三件事。**
- 可行性依据：① 协议是 REST，Python 只需 `requests`（或 `urllib`）即可，无需 JVM；② 响应含屏幕几何；③ 官方迁移指南明确它仍能驱动 IDEA 2026.1，本仓沙盒是 2026.2.1，版本邻近。
- 代价/风险：
  - 需给沙盒装 `robot-server` 插件（本仓用 IPGP 2.18.1，见 A3）并开端口；
  - RemoteRobot 已弃用（README 顶部原文），属「能用但不建议新写测试」；
  - `ObjectContainer`（findByLambda）走的是**序列化 Java 函数字节码**的机制，Python 用不了；但 XPath 端点与 `js/execute` 端点够用，不必碰 lambda。
  - `js/execute` 用 Rhino 在 IDE 进程内跑 JS，能力极强（可读任意 Swing 组件属性），是「点后校验」的好抓手。

#### A2. Starter + Driver（官方新框架，JMX，非 HTTP）

**是什么**：官方文档「Introduction to Integration Tests」把新框架分成 `Starter`（管 IDE 生命周期/项目/产物）与 `Driver`（管 UI 交互与 JMX 调用）。RemoteRobot 的 README 顶部原文：「This library is deprecated. New UI tests should use Starter and Driver. They also ship far more ready-made code: about twenty fixtures here, all plain Swing widgets, against over a hundred component classes there, most of them IDE parts such as the frame, the toolbars, the tool windows and the Settings dialog.」——**一百多个现成组件类**（frame / toolbar / tool window / Settings 对话框），正好命中本项目痛点。

**用法（官方 UI Testing 文档实测抓取）**：
- 用 XPath 定位，优先属性：`accessiblename`（`xQuery { byAccessibleName() }`）、`visible_text`、`javaclass`（`byType()`）、`myicon`；
- 交互：`x(xQuery { byVisibleText("Current File") }).click()`，键盘走 `java.awt.Robot`；
- 调试：`runIdeWithDriver()` 里 `Thread.sleep(30.minutes)` 暂停 IDE，日志会给出 `http://localhost:63343/api/remote-driver/`，浏览器打开即 **Swing 组件树的 HTML 视图**，可用开发者工具看属性。

**底层协议是 JMX，不是 HTTP。** `Driver` 的 README（`intellij-community/platform/remote-driver`）原文：「Driver uses **JMX** as the underlying protocol to call IDE code. To connect to an IDE via `Driver` you need to start it with the following VM Options: `-Dcom.sun.management.jmxremote=true ... -Dcom.sun.management.jmxremote.port=7777 ...`」，并用 `@Remote` 注解的接口做远程代理调用（如 `@Remote("com.intellij.psi.PsiManager")`）。

**对本项目是否可行：不推荐直接接入。** 理由：① 客户端是 Kotlin/JVM（`com.jetbrains.intellij.driver:driver-client` 等），官方无 Python 客户端；② 主协议 JMX/RMI + 自定义远程代理，Python 复刻成本远高于 REST；③ 那「一百多个组件类」是 Kotlin DSL 糖，Python 用不上。文档还明确标注：「Driver and UI components are in the **experimental state** and subject to API changes」。**唯一值得借鉴的是它的定位属性口径（accessiblename / visible_text / javaclass），这在 A1 的 XPath 里同样可用。**

#### A3. 本仓现状核实（含对「已接 UI 测试框架」说法的更正）

本仓 `build.gradle.kts:130` 确有 `testFramework(TestFrameworkType.Platform)`（实测读取），且插件版本为 `org.jetbrains.intellij.platform` **2.18.1**（`settings.gradle.kts:36`）。**但这条不等于「已接 UI 测试框架」**，需要更正：

- 本机反编译/源码核实 IPGP 2.18.1（Gradle 缓存内 `intellij-platform-gradle-plugin-2.18.1-sources.jar`）：
  - `TestFrameworkType.Platform` = `com.jetbrains.intellij.platform:test-framework`，即**平台单元测试框架**（`BasePlatformTestCase` 之类），**不含** robot-server、不含 Driver。
  - UI 测试用的是另一个枚举值：`TestFrameworkType.Starter` = `ide-starter-*` + `com.jetbrains.intellij.driver:driver-*`。
  - IPGP 2.x 的 UI 测试任务入口是 `intellijPlatformTesting { testIdeUi { ... } }`（`TestIdeUiTask`），并配套 `robotServerPlugin(version)`（依赖坐标 `com.intellij.remoterobot:robot-server-plugin`）。
  - **`runIdeForUiTests` 任务在 IPGP 2.18.1 中不存在**——该字符串只在旧版 `gradle-intellij-plugin-1.10.1.jar`（`org.jetbrains.intellij.IntelliJPlugin`）里出现（本机缓存实测）。本仓用的是新版 IPGP，故没有这个任务。
- 结论：要上组件树定位，**本仓需要新增配置**（`robotServerPlugin` 依赖 / `TestFrameworkType.Starter`），不是「开箱即有」。这是对「已接测试框架、无需新增依赖」说法的更正，会显著影响落地成本判断。

**与现有 `-PgifRecord=true` 沙盒如何共存（待联调）**：本仓录制沙盒走 `./gradlew runIde -PgifRecord=true`（`record/sandbox_start.cmd` 注释确认这是 canonical 方式），沙盒名 `MPSV-GifFresh`，vmoptions 由 `build/MPSV-GifFresh/.../config/idea64.exe.vmoptions` 与 `record/sandbox.vmoptions` 合并。候选落点：
```kotlin
intellijPlatform {
    intellijIdeaUltimate(if (gifRecord) "2026.2.1" else "2024.3.7.1")
    testFramework(TestFrameworkType.Platform)
    if (gifRecord) {
        plugins { robotServerPlugin("0.11.23") }   // 声明式装进 gif 沙盒（prepareSandbox 会重建 plugins/，必须声明式）
    }
    ...
}
```
并在沙盒 vmoptions 加 `-Drobot-server.port=8580`。`plugins { robotServerPlugin(...) }` 来自 `IntelliJPlatformPluginsExtension`（IPGP 2.18.1 源码：`Constants.Extensions.PLUGINS = "plugins"`，`robotServerPlugin(version)` 定义于 `IntelliJPlatformPluginsExtension.kt:378`，默认 `LATEST_VERSION`）。**该 DSL 落点、0.11.23 与 2026.2.1 的兼容性、以及 robot-server 是否与 `-PgifRecord=true` 的 JCEF/独立沙盒冲突，均未实测，须联调确认。**

### 方案 B：Windows UI Automation（UIA）——否决

**是什么**：Windows 无障碍/自动化框架。Python 侧两条路：`pywinauto`（`backend="uia"`）与 `uiautomation`（`yinkaisheng/Python-UIAutomation-for-Windows`，PyPI 实测最新 2.0.29）。理论链路是：Java Accessibility API → **Java Access Bridge (JAB)** → MSAA（`IAccessible`）→ **MSAA-to-UIA Proxy** → UIA 客户端。

**官方文档（链路存在性）**：
- Oracle《Enabling and Testing Java Access Bridge on Microsoft Windows》：JAB「enables Java applications ... to be visible to assistive technologies on Microsoft Windows systems」，启用命令 `%JRE_HOME%\bin\jabswitch -enable`，测试工具 `jaccessinspector` / `jaccesswalker`（JDK 11+）。
- Microsoft《Accessing Microsoft Active Accessibility Servers》：UIA 通过 **MSAA to UI Automation Proxy** 与实现 `IAccessible` 的服务交互，提供 `IUIAutomationLegacyIAccessiblePattern`。即「UIA 能看见 MSAA 提供者」这条桥在框架层成立。

**本机实测（关键，决定可行性）**：
1. **JBR 自带 JAB**：沙盒 JBR（`idea-2026.2.1-win/jbr/bin/`）含 `jabswitch.exe`、`javaaccessbridge.dll`、`windowsaccessbridge-64.dll`、`jaccessinspector.exe`、`jaccesswalker.exe`（实测列目录）。
2. **JAB 可启用且免提权**：运行 `jabswitch -enable`（版本 25.0.3.0）返回「The Java Access Bridge has been enabled.」，并在注册表登记 `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Accessibility\ATs\Oracle_JavaAccessBridge`（实测 `reg query`）。
3. **Swing 探针实验**：自建 JDK8 Swing 程序（`JFrame` + `JButton("Execute SQL")` + `JLabel` 中文 + `JTextField`），以 `-Djavax.accessibility.assistive_technologies=com.sun.java.accessibility.AccessBridge` 启动。进程内确认加载了 `JavaAccessBridge-64.dll` 与 `JAWTAccessBridge-64.dll`（实测 `Get-Process ... .Modules`）。
4. **UIA 结果**：用 PowerShell `UIAutomationClient` 枚举——顶层能看到 `name='ZCodeSwingProbe' class='SunAwtFrame'`，但该窗口 `Children=0`、`Descendants=0`，仅支持 `WindowPattern`/`TransformPattern`。
5. **MSAA 结果**：直接 `oleacc!AccessibleObjectFromWindow(OBJID_CLIENT)` 返回 `hr=0`、`childCount=0`。
6. **对照实验（证明探针有效）**：同一 UIA 探针在文件资源管理器（`CabinetWClass`）上枚举到 **173 个后代**（含 `ControlType.RadioButton class='SelectorButton' name='详细信息'` 等）。即探针能力正常，是 Swing 侧不暴露。

**结论**：**在本机环境下，UIA（以及朴素 MSAA 查询）拿不到 Swing 应用的内部控件**，即便 JAB 已注册、DLL 已加载。对 `pywinauto(backend='uia')` / `uiautomation` 而言，IntelliJ 只会是「一个没有子元素的 `SunAwtFrame`」，无法按控件定位。**门槛与代价写清**：即便未来 JAB 树能出来，也需 `jabswitch -enable`（影响全局、需重启 Java 应用）+ 可能要在 IDE vmoptions 里配 `assistive_technologies`，且能拿到什么完全取决于 IntelliJ 平台对 `javax.accessibility` 的实现完整度——**不确定且不受本项目控制**。故不推荐。
（诚实边界：我的 JAB 客户端不是「标准 AT 客户端」——标准 JAB 客户端会先经 `WindowsAccessBridge` 初始化；因此「0 children」是**强信号但非数学证明**。但即便按最乐观假设成立，其收益也只是「能拿到部分控件」，仍不及 A1 能通过父组件位置链换算到屏幕坐标且已真机验证。）

### 方案 C：图像锚点匹配（OpenCV 模板匹配）——兜底，立即落地

**是什么**：把控件的一小块截图当模板，在全屏/区域内滑动匹配，返回最佳位置。`pyautogui.locateCenterOnScreen(path, confidence=0.9)` 底层走 `pyscreeze`。

**本机实测的硬约束**：`pyscreeze` 源码（本机抓取）里
```python
try:
    import cv2, numpy
    _useOpenCV = True
except ImportError:
    _useOpenCV = False
...
def _locateAll_opencv(...):
    result = cv2.matchTemplate(haystackImage, needleImage, cv2.TM_CCOEFF_NORMED)
    match_indices = numpy.arange(result.size)[(result > confidence).flatten()]
```
即 **`confidence=` 参数依赖 OpenCV**；无 `cv2` 时 `locate*` 退化为**逐像素精确匹配**（`_locateAll_pillow`），对主题/缩放/抗锯齿零容忍。本机 Python 3.10.1 已装 `pyautogui 0.9.54 / mss / PIL 12.3.0 / numpy 2.2.6`，**未装 `cv2`**（实测 `import cv2` → ModuleNotFoundError）。**所以现在 `locateCenterOnScreen(..., confidence=)` 根本用不了。**

**怎么用（实操建议）**：
- 模板来源：用现有 `mss` 抓一张小图（比如按钮、图标、树节点），存 `record/templates/`。**模板越小越稳**（图标 + 少量文字），但太小易误配；建议带一点上下文边框。
- 抗缩放/主题：① 统一录制构图（本仓 `BASELINE.md` 已固定 1370×984 @ 120% 缩放，天然满足）；② 用**灰度**匹配（`grayscale=True`）削弱主题色差；③ 多尺度匹配：对模板做 0.8/0.9/1.0/1.1/1.2 缩放各匹配一遍，取最高分（`pyautogui` 不内置多尺度，需自己写，或直接 `cv2.matchTemplate`）。
- 性能：`pyautogui.locateOnScreen` 全屏约百毫秒级（官方文档：`screenshot()` 在 1920×1080 约 100ms）；用 `region=` 限定到已算出的窗口矩形（`locate.window_rect`）可显著提速并降低误配。建议**先窗口矩形定位（已有）→ 再在窗口内做模板匹配**。
- 与现有件的关系：`locate.bright_band_y/x`（像素剖面）已经是「图像证据」的低配版；模板匹配是它的升级——从「找亮带」升级到「找指定图案」。
- `pyscreeze` 的 `_locateAll_opencv` 有个细节：未命中时会把 `confidence *= 0.95` 循环降阈重试（源码实测），所以 `confidence` 是上限而非硬门限。

**对本项目是否可行：可行，且是当前最快见效的一步。** 代价：装 `opencv-python`（约几十 MB）；模板需按构图维护（构图一改模板作废，与 `BASELINE.md` 的整表作废规则一致）。**局限**：悬停才渲染的控件要先制造悬停再截图；纯色/无纹理控件无模板可匹配。

### 方案 D：OCR 定位——补充手段

**是什么**：对屏幕截图做 OCR，按识别出的文字框反推控件位置。三条路：`pytesseract`（Google Tesseract 封装）、`PaddleOCR`（百度，中文强）、Windows 自带 `Windows.Media.Ocr`（经 `winsdk`/`pywinrt` 绑定，PyPI 实测 `winsdk 1.0.0b10`）。

**出处/事实**：
- `pytesseract` 是 Tesseract 的 Python 封装（官方 README），需另装 Tesseract 引擎与语言包；`chi_sim.traineddata` 可从 `tesseract-ocr/tessdata` 获取（实测 HTTP 206，文件存在）。
- `PaddleOCR` 官方 README：PP-OCRv6「supports 50 languages with a single unified model (Chinese, English, Japanese, and 46 Latin-script languages)」，中文识别是其强项。
- Windows OCR：`winsdk` 是社区维护的 WinRT 绑定（`winrt` 的替代），可访问 `Windows.Media.Ocr`；但依赖系统已安装对应 OCR 语言包。

**对本项目是否可行：只作补充，不作主路线。** 理由：① IDE 字号小（本仓 13pt）、暗色主题、中英混排、代码里有大量标点/下划线，OCR 误识率高且不稳定；② 慢（百毫秒到秒级，PaddleOCR 首次加载模型更慢）；③ 即使识别到文字，也只知道「这串字在哪」，仍需判断它是不是目标控件（可能同名多处）；④ 与 `BASELINE.md` 已记的教训同类——「把注释里的中文词当表名」正是文本层面的误判，OCR 只会把这种误判从「代码逻辑」搬到「图像识别」。**唯一合适的用法**：当某控件没有稳定图标、又不想维护模板时，用 OCR 找它旁边的**唯一文案**作为锚点，再按相对偏移点击。

### 方案 E：经典 GUI 自动化框架（SikuliX / Airtest）——无增益

- **SikuliX**：基于 OpenCV 的**图像识别**自动化（截图即代码）。官方文档站（`sikulix-2014.readthedocs.io`）实测：作者 RaiMan 已于 2025 年停止开发，项目由 Julien Mer 接手为 **Oculix**。定位机制＝图像模板匹配，对 Swing 组件**没有元素树能力**，与本项目自研图像匹配同源。
- **Airtest**：官方「cross-platform UI automation framework for games and apps」。其 Windows 后端源码（`airtest/core/win/win.py`，本机实测抓取）显示：`from pywinauto.application import Application` + `from pywinauto import mouse, keyboard` + `import mss` + `from airtest import aircv`。即 **Windows 上它就是「pywinauto 管窗口/输入 + OpenCV 做图像匹配」**，并没有独立的元素树定位（Poco 是给游戏/Unity/Android 用的 UI 层级，Windows 桌面 Swing 不适用）。
- **结论**：两者对本项目**没有新能力**——都是图像匹配，只是换了个外壳；还会引入 Java 运行时（SikuliX）或一套重框架（Airtest）。不值得为「更顺」而迁移。

### 方案 F：其它提效件

- **ZCode `computer-use` 插件（本机已装）**：官方 skill 原文是 **accessibility-first**：「Accessibility is the primary action path. It is semantic, precise, works on a background app and does not steal the user's focus」，坐标点击是「last fallback, for canvas, games and Electron content accessibility cannot see」。Windows 后端（`zcode-cua` 的 `dist/mcp/server.js` 实测含大量 `Windows`/`UIA`/`win32`/`accessibility` 标识）走的是 UIA。**因此它同样受方案 B 的限制：看不见 Swing 控件。** 对本项目价值有限（且该插件是「主智能体专用」，不适合嵌进 `record/` 批量管线）。
- **`Inspect.exe` / Accessibility Insights**：作为「标定工具」的价值**有限**——它们本身是 UIA/MSAA 客户端，看到的树与方案 B 相同（Swing 内部为空），无法用来标定 IntelliJ 控件。**但对非 Java 窗口（文件对话框、浏览器、微信等）有用**，可快速确认某窗口是否值得用 UIA 而非图像。
- **值得注意的旁证**：JetBrains 自己的 UI 测试之所以能按组件定位，是因为 **robot-server / driver 跑在 IDE 进程内**，直接访问 Swing 组件对象——不是通过 OS 无障碍层。这解释了为什么 OS 级 UIA 看不到、而进程内插件能看到。

### 8.3 更正本报告 §六 第 2 条：`robotServerPlugin` 的 DSL 落点（已实测钉死）

报告原先推断是 `intellijPlatform { plugins { robotServerPlugin(...) } }`。**实测两次编译均报
`Unresolved reference 'robotServerPlugin'`**，读 IPGP 2.18.1 源码后定案：

- `robotServerPlugin` 是 **`IntelliJPlatformPluginsExtension`** 的成员；
- 而 `plugins { }` 块**只挂在该类的注册点 `IntelliJPlatformTestingExtension` 上**
  （`IntelliJPlatformTestingExtension.kt:63 val plugins = IntelliJPlatformPluginsExtension.register(..., target = this)`），
  即 **`intellijPlatformTesting { plugins { robotServerPlugin("0.11.23") } }`**；
- `dependencies { intellijPlatform { } }`（`IntelliJPlatformDependenciesExtension`）**没有** `robotServerPlugin`，
  它的 `plugins { }` 也不存在（仓内 `plugins {` 只有 Gradle 自己那一个，在第 6 行）。

**结论（对录制工作流是关键的坏消息）**：官方 DSL 只覆盖**测试**沙盒，**不覆盖 `runIde -PgifRecord=true`
用的那个沙盒**。所以录制沙盒要走另一条装法（下条）。

### 8.4 录制沙盒装 robot-server 的真实路径（2026-10-15 在 t-sql-list-native-tail 验证）

旧提议的 `-Didea.plugins.path=<robot目录>` **错误且危险**：这会把沙盒完整插件目录替换成仅有 robot-server
的目录，使 SQL Visualizer/AI Assistant 消失。也不能把 `robotServerPlugin()` 写进根工程的
`dependencies { intellijPlatform { ... } }` 或普通 `intellijPlatform { plugins { ... } }`，两次配置期都报
`Unresolved reference`。真正可行的方案：

1. `python record/bootstrap-robot-server.py` 从 JetBrains Maven 下载 `robot-server-plugin:0.11.23@zip`，
   按已核对的 SHA-256 校验后解包到被忽略的 `record/robot-plugins/robot-server-plugin`；
2. 目标分支 `build.gradle.kts` 在 `gifRecord && gifRobotServer=true` 时调用已核实的
   `IntelliJPlatformDependenciesExtension.localPlugin(File)`；
3. 用**标准** `./gradlew runIde -PgifRecord=true -PgifRobotServer=true --args=<demo>` 启动，
   由 `prepareSandbox` 将 robot-server 与 SQL Visualizer、AI Assistant 一起安装，不触碰/覆写用户配置。

**真机读数**：`prepareSandbox` 成功，沙盒 plugins/ 三者都在；`idea.log` 的 `Loaded custom plugins`
同时列出这三者；`127.0.0.1:8580` 监听；`GET /` 为 200；`POST /xpath/components` 成功返回 206
个节点；IDE 主窗 `IdeFrameImpl` 是 `(260,20,1400,992)`；页签父链求和得到 `(1463,118)`，实际
点击后页签切换；PNG 截图接口也通过。**真正返回的是父组件相对 x/y**（`RemoteComponent` 调
`Component.getX/getY`），不是旧报告误写的屏幕绝对几何。当前新分支运行的许可横幅为
`Start Free Trial`，正式重录素材不能直接覆盖站点，应待合法授权后再出正式成片。
