# GUI 自动化工具选型 子报告 A：框架对比

**日期**：2026-10-26
**范围**：Windows 桌面 GUI 自动化 + 截图录制，用于 IntelliJ IDEA 插件演示 GIF 录制
**目标环境**：Windows 11 + IntelliJ IDEA 2026.2.1（自绘 Swing），IDE 进程内已装 robot-server（HTTP + XPath 组件树定位）
**数据口径**：star / 最近 push 时间 / 归档状态全部为 2026-10-26 通过 GitHub REST API 实测（`Authorization: Bearer <token>`，走 `-x http://127.0.0.1:7890`）。OpenCV 章节的数值为本机真实截图上的对照实验，实验条件写在正文里。

## 一、结论先行

**推荐：继续用现有 robot-server（组件树定位）作主路线，OpenCV 模板匹配只作兜底与「点后校验」。本报告调研的 13 个外部框架，没有一个比现状更好。**

三条硬理由：

1. **定位依据的代差无法靠换框架弥补。** 我们的 5 类失败模式里，第 1 类（布局变就点空）、第 3 类（弹窗动画期控件漂移）、第 4 类（菜单悬停时序）的共同根因是「拿不到控件身份，只能拿几何/像素近似」。robot-server 给的是 Swing 组件身份 + `x/y/width/height`，是目前唯一在本机真机验证过的身份级定位（`record/robot.py` 已用它切换过「SQL 历史」页签）。所有基于 UIA/MSAA 的框架（pywinauto、FlaUI、WinAppDriver、TestStack.White、uiautomation）在 Swing 上都是**零控件可见**，属于从根上不可用，不是调参问题。
2. **图像匹配派（Airtest、Poco、SikuliX、pyautogui.confidence）换框架等于重写现有 `anchor.py`。** 本机实测它们的匹配核心就是 OpenCV `TM_CCOEFF_NORMED`（Airtest `aircv/cal_confidence.py` 源码直读、pyscreeze 源码 `cv2.matchTemplate(...TM_CCOEFF_NORMED)`），还多带一层 JVM 或大依赖，对精度零增益。
3. **能真正给出 Swing 身份的框架（Squish、Marathon、AssertJ Swing、Robot Framework SwingLibrary）都要求改 IDE 启动方式或侵入 JVM**（`-javaagent:squishagent.jar`、Jemmy 在 JVM 内、JUnit 同进程），成本和风险都高于「IDE 内已装好的 robot-server」。

**必须在报告里写明的现状短板**（不是换框架能救的，是 robot-server 自身的边界）：独立 heavyweight popup（补全列表、气球通知）不在主窗组件树里，`/xpath/components` 返回 0；这一点本仓已有实测记录（`docs/开发计划/20261024-1026-文档站演示动图录制事故修复-开发计划.md:172`、`docs/经验总结/20260910-0100-IntelliJ演示GIF录制-经验总结.md:385`）。这层缺口只能用「图像兜底 + 录制前禁用对应插件/气泡」解决。

## 三、逐候选评估（能不能解决 5 类失败模式）

先把 5 类失败模式编号，后续统一引用：

- **F1** 坐标写死，布局一变（面板位置/页签数量/对话框形态）就点空
- **F2** 元素定位靠像素扫描（找下划线/亮行/聚簇），判据不稳
- **F3** 弹窗有动画，控件 1~2s 内漂移
- **F4** 菜单/子菜单悬停展开，时序敏感
- **F5** 录制中弹窗遮挡、焦点被别的窗口抢走

### 3.1 intellij-ui-test-robot / robot-server（现状）— 主选

JetBrains 官方项目，README 首行自标 deprecated，新项目建议迁 Starter and Driver，但**服务端 plugin（robot-server）与 HTTP 协议在 2026.2.1 上仍实测可用**，本仓 `record/robot.py` 已跑通。核心端点是 `POST /xpath/components`（源码 `remote-robot/.../client/IdeRobotApi.kt` 实证），返回 `className/name/x/y/width/height`，x/y 是父组件相对坐标，需沿 `ancestor::div` 累加。

- **F1 解决**：按 XPath/`accessiblename` 取身份，布局改了 XPath 不变就能找到；找不到时 `find_one` 直接返回 None 而不猜坐标，失败是显式的。
- **F2 解决**：完全不碰像素。
- **F3 部分解决**：能定位「已存在的组件」，但动画期间组件矩形在变，返回值是查询瞬间的快照，仍需 `require_component` 的重试等待。治标不治本但可用。
- **F4 部分解决**：菜单项若在主窗组件树里可按名点；但见下方短板——补全列表/气球这类独立 heavy popup 不在树内。
- **F5 不解决**：robot-server 不管焦点和遮挡，点击仍是 pyautogui 发到屏幕坐标。这块要么继续用 `bring_ide_front.py`/`force_front.py`，要么加前置自检（本仓已有七项自检清单）。

**短板（本仓实测）**：`docs/开发计划/20261024-1026-...md:172` 记录「补全列表在独立的 heavyweight popup 窗口里，`/xpath/components` 只遍历主窗组件树，连正向对照都返回 0」；`docs/经验总结/20260910-0100-...md:385` 记录气球通知同样「robot-server 点它无效」。

### 3.2 pywinauto — 否决

Python 生态最主流的 Windows GUI 库（6,230 star，2026-10-23 仍有提交）。但官方 `docs/getting_started.txt` 的支持列表只有两类：`backend="win32"`（MFC、VB6、VCL、simple WinForms、老式应用）与 `backend="uia"`（WinForms、WPF、Store apps、Qt5、browsers），**Java AWT/Swing 不在其中**。Swing 走 Java Accessibility API → JAB → MSAA → UIA proxy 这条路，UIA 看不到 Swing 内部控件是行业共识性事实，且本仓已有本机对照实测（`docs/调研报告/20261013-2130-演示录制点击定位提效工具调研-调研报告.md`：IDE 侧 `SunAwtFrame` children=0，同探针在文件资源管理器枚举到 173 个后代）。

- 5 类失败模式：**一类都解决不了**。win32 后端只能拿顶层窗口矩形（F1 里最粗的那一档）；uia 后端拿不到控件。
- 附带价值：`mouse`/`keyboard` 模块可用，但 pyautogui 已经覆盖。

### 3.3 FlaUI / WinAppDriver / Appium Windows Driver — 否决

三者是同一技术栈的不同封装：FlaUI 是 .NET 的 UIA2/UIA3 封装（README 明写「based on native UI Automation libraries from Microsoft」）；WinAppDriver 是微软的 UIA + WebDriver 服务，README 只承诺 UWP/WinForms/WPF/Win32；Appium Windows Driver 是 WinAppDriver 的 Appium 外壳。Swing 面前三者一律只能看到窗口壳。

- 额外成本：FlaUI 要 .NET 运行时 + C#；WinAppDriver 要装 exe + 开开发者模式 + 管理员权限；Appium 全家桶再叠一层 Node。
- 5 类失败模式：**一类都解决不了**，且把 Python 管线拆成跨语言。

### 3.4 Airtest / Poco — 否决

Airtest（9,618 star）Windows 后端源码直读：`airtest/core/win/win.py` 顶部 `from pywinauto.application import Application`，屏幕走 `mss`，找元素走 `airtest.aircv`。也就是说它 = pywinauto（只用来取顶层窗口）+ mss + OpenCV 模板匹配，**与我们现有 `record/` 的技术栈完全同构**，只是把匹配代码包了一层。`aircv/cal_confidence.py` 里就是 `cv2.TM_CCOEFF_NORMED`。

Poco（1,961 star）官方平台支持表写明 **Windows「Not yet」**（`docs/wiki/device/platforms.md`），它依赖向引擎注入 UI 树（Unity/Cocos/Android），对 Swing 无从注入。

- 5 类失败模式：F2 不变（还是像素匹配），F1/F3/F4/F5 全不解决。换它只增加约 200MB 依赖与 JVM/AirtestIDE 心智负担。

### 3.5 SikuliX — 否决

3,261 star，最近 push 2026-10-25，仓库已迁到 `oculix-org/SikuliX1`（`RaiMan/SikuliX1` 现 301 跳转）。它是纯图像匹配（OpenCV），Swing 概念为零。本仓 `record/anchor.py` 已经实现了等价能力（灰度 + `TM_CCOEFF_NORMED` + 多尺度 + 命中尺度细化），且更贴合我们的截图/合成管线（mss 直取 + ffmpeg 管道）。引入 SikuliX 意味着多一个 JVM + Jython/GraalVM 依赖。

- 5 类失败模式：只对 F2 的「判据不稳」有理论收益（SikuliX 的匹配策略与我们的等价），F1/F3/F4/F5 不解决。

### 3.6 TestStack.White — 否决（已废弃）

1,000 star，README 第一行 `DEPRECATED - no longer actively maintained`，最近 push 2023-07-09。技术上它是 UIA/MSAA 封装，与 FlaUI 同源，Swing 同样不可见。没有任何理由考虑。

### 3.7 Squish（Qt 商业）— 唯一能力对口，但不可接受

Squish for Java 官方明确支持「Java Swing/AWT、SWT/Eclipse RCP、JavaFX」并提供对象级识别（property-based，非像素）。这是本表里**除 robot-server 外唯一真正能给出 Swing 控件身份**的产品。

否决理由不是能力，是接入形态：
- 它靠替换 AUT 的 JVM 库或 `-javaagent:squishagent.jar` 挂钩（`kb.froglogic.com` / `qatools.knowledgebase.qt.io` 的 hooking 文档），意味着**录制沙盒必须按 Squish 要求启动**，与我们「用 `gradlew runIde` 起沙盒 + 注入许可 agent」的既有链路直接冲突（本仓已经有 qwdn 许可 agent 的冲突史，见 `docs/经验总结/20261023-1810-录制沙盒许可失效反复踩坑与根治-经验总结.md`）。
- 商业授权、闭源、单机 license，为一个内部文档站配图引入采购流程不成比例。
- 5 类失败模式：F1/F2/F3/F4 理论上都能解决（对象级 + 等待机制），F5 仍不解决（Squish 也会被抢焦点）。

### 3.8 AssertJ Swing / Robot Framework SwingLibrary / Marathon — 否决（都要进 JVM）

这三个是「Swing 原生测试库」这一族的代表，能力都真实存在：
- **AssertJ Swing**（121 star，2026-01-26）：README 明写「provides a reliable mechanism for GUI component lookup that ensures that changes in the GUI's layout or look-and-feel will not break your tests」。但它是 JUnit/TestNG 断言库，要求被测 UI 与测试代码跑在**同一个 JVM**。
- **Robot Framework SwingLibrary**（117 star，2024-08-20）：内部用 NetBeans 的 Jemmy 作驱动，要求 `SwingLibrary.jar` 在**被测应用的 classpath 上**（wiki 原文）。
- **Marathon V5**（27 star，2022-04-19）：Swing/JavaFX 录制回放，但近 4 年停滞，且需以它的 launcher 启应用。

对我们的意义：这三者都要求把测试框架塞进 IDE 进程或同 JVM。robot-server 已经是以**插件形式**待在 IDE 里、通过 HTTP 对外暴露，形态上更优（外部 Python 直连，不用改 IDE 启动参数，不占 classpath）。所以**没有换的理由**。

- 5 类失败模式：F1/F2 能解决（组件身份），F3/F4 有等待机制，F5 不解决。但接入成本把我们挡在门外。

### 3.9 pyjab — 备选观察项（未验证）

52 star，2026-10-12 仍活跃，「Python implementation for Java application UI automation with Java Access Bridge」。它**绕开 UIA 直接说 JAB 协议**，理论上能拿到 Swing 的 `Accessible` 树（`javax.accessibility` 层，比 UIA 代理更靠内）。

- 潜力：如果成立，能拿到 IDE 全量控件（不仅是主窗），可能补上 robot-server 的 heavy popup 短板。
- 现实约束：本仓 2026-10 的实测是「JAB 已 `jabswitch -enable`、DLL 已加载，但 UIA 与朴素 MSAA 查询均 0 children」，且当时明确记录「探针未走标准的 `WindowsAccessBridge` 初始化，这是强信号非证明」。pyjab 恰好走标准 JAB 初始化，**值得一次独立验证**，但本报告不下结论。
- 5 类失败模式：**若验证成功**，F1/F2/F3/F4 全解决且覆盖面优于 robot-server；F5 仍不解决。

### 3.10 Playwright / Puppeteer 桌面变体 — 不适用

Playwright（98,482 star）的桌面能力仅限 Electron / WebView2 这类带 CDP 的 Web 壳，官方 Electron 支持还是 experimental 且只驱动 renderer，**不碰原生控件**。Tauri 的 `tauri-driver` 只能驱动 Tauri 应用（Windows/Linux）。IntelliJ 是纯 Swing，无 Web 渲染层可供 CDP 接入。**不适用，不是「不好用」。**

### 3.11 TagUI 及其他 RPA（TagUI 6,339 star、pywinauto_recorder 200 star、BotCity 144 star）

以图像 + OCR + 浏览器为主的通用 RPA，Swing 支持为零。TagUI 的 Windows 通道本质还是图像/OCR 定位，与我们现有 `anchor.py` 同级。无理由引入。

## 四、图像模板匹配的实际精度（本机实测）

这一节回答「OpenCV matchTemplate 在暗色主题 IDE 上到底行不行、多尺度怎么处理、120% 缩放怎么办」。**以下数值全部在真实 IDE 截图上跑出，非文档引用。**

### 4.1 实验条件

- 屏幕样本：`record/shots/` 下 128 张全屏 IDE 截图（1922×1042 或 1920×1080，Islands Dark 主题）
- 模板样本：`record/templates/` 下 15 张已标定模板
- 环境：本机 OpenCV **5.0.0**、NumPy 2.2.6、mss 10.2.0
- 方法：`cv2.matchTemplate(TM_CCOEFF_NORMED)`，灰度，窗口限定为屏幕/窗口矩形

### 4.2 暗色主题下的可行性：高，但阈值必须按模板定

同一模板跨 128 张画面的得分分布：

| 模板 | 最高分 | 次高分 | 中位数 |
|---|---|---|---|
| `native_history_oct13` | 0.994 | 0.648 | 0.456 |
| `native_stack_controller` | 0.991 | 0.991 | 0.454 |
| `native_history_device` | 0.987 | 0.987 | 0.487 |
| `db_plus_btn` | 1.000 | 1.000 | 0.595 |

结论：**暗色主题不构成障碍**，命中分普遍 0.98~1.00，与非命中画面（中位数 0.45~0.60）之间有 0.35 以上的安全间隔。这与 `anchor.py` docstring 记录的「同尺度命中普遍 >0.95」一致。

但要注意：`db_plus_btn` / `svc_plus_btn` 这类工具条按钮在**多张不同画面的同一位置**都是 1.000，也就是「同一模板在多张图上的最高分并列」。这不是误匹配，而是该按钮本来就常驻——但意味着**单靠分数无法区分「找对了画面」**，必须配合 `find_all` 的去重或区域限定。

### 4.3 低方差模板会退化成「到处命中」（必须拦）

实测：纯色块（灰度标准差 0）作模板时 `TM_CCOEFF_NORMED` 返回 **1.000**，即在任意位置都满分。

```
flat std=0.0 -> max=1.000  (1.0 = 到处命中)
```

本仓 `anchor.py:save_template()` 已有防护（`sd < 8.0` 直接拒绝），这条实测印证该防护是必需的，不是过度设计。

### 4.4 多尺度：这是真正的痛点，且 5% 步长不够

受控实验（从真实截图裁 40×300 文字带作模板，把整屏按不同比例重采样，测同尺度下的得分）：

| 屏幕缩放 | 用原尺寸模板匹配 | 模板同步缩放后匹配 |
|---|---|---|
| 0.90 | 0.737 | **1.000** |
| 0.95 | 0.776 | **0.967** |
| 1.05 | 0.768 | **0.968** |
| 1.10 | 0.717 | **1.000** |
| 1.20 | 0.683 | **1.000** |
| 1.25 | 0.694 | 0.971 |
| 1.50 | 0.706 | **1.000** |
| 2.00 | 0.703 | **1.000** |

**关键读数**：只要屏幕缩放偏离 1.0，**不缩放模板就直接掉到 0.68~0.78** —— 低于 `anchor.py` 的 0.85 阈值，表现为「明明在屏幕上却找不到」。这不是阈值调低能救的，因为 0.70 附近已经和非命中画面（中位数 0.5~0.6）很接近。**多尺度（按比例缩放模板）是必需项，不是优化项。**

**5% 网格不够密的证据**（真实缩放 0.925 时，用网格上的 0.90 和 0.95 去匹配）：

| 真实缩放 | 网格 0.90 | 网格 0.95 | 网格 1.00 |
|---|---|---|---|
| 0.900 | **1.000** | 0.816 | 0.734 |
| 0.925 | 0.834 | 0.865 | 0.737 |
| 0.950 | 0.803 | **0.966** | 0.774 |
| 0.975 | 0.792 | 0.866 | 0.802 |

真实缩放落在网格中间（0.925、0.975）时，最好也只有 **0.834~0.866**，已经贴近 0.85 阈值——**随时会掉到阈值以下**。当前 `anchor.py` 用的正是 `[0.90, 0.95, 1.00, 1.05, 1.10]` 这组 5% 网格，这是它不稳定的一个可量化来源。

**代价**（1042×1922 全屏，300×40 模板）：

| 方案 | 全屏 | 窗口 1370×984 | 局部 400×200 |
|---|---|---|---|
| 5 档 5% 网格 | 0.313s | 0.216s | 0.012s |
| 71 档 1% 网格 | 4.026s | — | 0.123s |

结论：**1% 步长只在局部区域可行**（0.12s 可接受），全屏跑 1% 网格到 4s，不能放进每个点击动作里。正确姿势是「先粗后细」：5% 粗扫定位 → 在命中点附近 100px 内用 1% 细扫。`anchor.py` 的细化逻辑方向正确，但细化窗口只有 ±0.02，覆盖不了「真实缩放落在两个 5% 格点正中」的情况（需要 ±0.025，实际上应该按格距的一半取）。

### 4.5 DPI / 120% 缩放怎么办

分两层，不能混为一谈：

1. **Windows 系统 DPI 缩放（125%/150%）**：本仓所有脚本首行都调 `ctypes.windll.shcore.SetProcessDpiAwareness(2)`（`record/gifkit.py:18`、`record/win_enum.py:12`、`record/locate.py` 同），进程声明 Per-Monitor DPI Aware 后，mss 与 pyautogui 使用的都是**物理像素**，坐标口径统一。这一层已经解决，不需要改。
2. **IDE 自身的 UI Scale（本仓固定 120%）**：这不是 DPI，是 Swing 内部按 `ideScale` 放大字体与控件（`docs/经验总结/20260910-0100-...md:203` 记录 `ideScale=1.2` 从 `other.xml` 读入）。它让**屏幕上的实际控件尺寸**变成基准的 1.2 倍——完全等价于上表「屏幕缩放 1.20」那一行：**用原模板匹配得 0.683，模板同步缩放后得 1.000**。

所以 120% 的处置办法不是「调整阈值」，而是：**模板必须与当前 ideScale 同尺度标定，或匹配时按 ideScale 缩放模板**。由于本仓录制构图已固定（窗口 1370×984 @ (277,25)、IDE 缩放 120%、13pt，见 `docs/开发计划/20261024-1026-...md:105`），最省事的做法是**标定模板时就按 120% 截**，把 1.0 尺度当基准，多尺度只用来吸收窗口尺寸/字体渲染的微小差异（±3% 足够），而不是吸收 ideScale。

### 4.6 对 5 类失败模式的实际覆盖

| 失败模式 | 模板匹配能做到什么 | 做不到什么 |
|---|---|---|
| F1 布局变点空 | 控件外观不变就还能找到（免疫位置变化） | 控件外观变了（文案/图标/尺寸）就失效 |
| F2 像素扫描判据不稳 | 用整块模板替代「找亮行/找下划线」这类启发式，判据从多规则降为单分数 | 阈值仍需按模板标定，0.85 是通用妥协不是最优 |
| F3 动画漂移 | 命中点就是当前帧的真实位置，天然免疫漂移 | 动画中途命中可能点到过渡态控件 |
| F4 悬停菜单 | 可以在每次 `moveTo` 后重新 `find`，不必预判 | 菜单展开动画期间同样可能命中过渡位置 |
| F5 遮挡/抢焦点 | **完全不解决**，匹配的是屏幕像素，被遮住就是找不到 | — |

## 五、推荐与落地建议

### 5.1 推荐结论

**不换框架。** 现有组合（robot-server 为主 + `anchor.py` 兜底 + `locate.py` 窗口几何作最后一道）在能力上已经覆盖了本报告调研的全部开源选项，且是唯一「零 IDE 启动改造 + Python 直连 + 组件身份定位」的组合。

具体排位：

1. **robot-server**：F1/F2 满分，F3/F4 及格，F5 不合格。
2. **anchor.py（OpenCV）**：F1/F3/F4 及格（作为 robot-server 的补充而非替代），F5 不合格，F2 的判据比像素扫描稳但仍需标定。
3. **两者叠加**：robot 找组件 → 点 → anchor 复核（点后画面是否出现预期元素）。这是当前架构的正确方向，本仓 `BC_RUNBOOK.md:10` 已经写了这条优先级链。

### 5.2 三个低成本改进（按性价比排序）

1. **补上 anchor.py 的尺度细化窗口**：把细化范围从 ±0.02 改成 ±0.025（5% 格距的一半），并把 `scales` 默认值改成以当前 ideScale（1.2）为基准的窄带 `[1.15, 1.20, 1.25]` + 兜底宽扫。依据：4.4 节表格，真实缩放落在格点正中时得分掉到 0.83~0.87。
2. **模板标定固化到 120% 基准**：录制构图已固定，模板按 120% 截一次即可，避免每次录制重新标定。依据：4.5 节，ideScale 是确定量不是随机量。
3. **验证 pyjab 能否补 heavy popup 缺口**：robot-server 的短板就是独立 popup（补全列表、气球），而 pyjab 走标准 JAB 初始化，与 2026-10 那次「0 children」探针的失败前提不同。这是一次**有明确成功判据的独立实验**（能枚举到 IDE 主窗内 >100 个 Accessible 后代即为成功）。若成功，F1/F2/F3/F4 的覆盖面积会显著优于现状。**注意：这是待验证项，不是结论。**

### 5.3 明确不建议的三件事

- **不要为了「用上大厂框架」引入 Airtest/SikuliX**：它们的匹配核心就是 OpenCV，与我们现有实现同构，收益为零、依赖增加。
- **不要再试任何 UIA 路线**（pywinauto/FlaUI/WinAppDriver/White/uiautomation）：本仓已有本机对照实测证明 Swing 内部控件不可见，这是协议层的墙，不是配置问题。
- **不要考虑 Squish**：能力对口但要求改 IDE 启动方式，与现有许可 agent 链路冲突，且商业授权成本不成比例。
