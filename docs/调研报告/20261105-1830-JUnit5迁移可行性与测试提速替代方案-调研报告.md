# JUnit3 → JUnit5 迁移可行性调研（重点：能不能压缩测试时间）

- 调研时间：2026-11-05（只读，未跑 Gradle、未改任何文件）
- 数据快照：`build/test-results/testShard1..5 + testShardTail`（2026-11-05 00:49–01:11 全量轮，811 套件 / 8594 用例 / suite 合计 1141.0s）
- 平台：IntelliJ IDEA Ultimate 2024.3.7.1（243.28141.41），`lib/testFramework.jar`
- 相关：`docs/开发计划/20261105-1806-T-Junit4Migration-平台测试JUnit3语义清理与迁移-开发计划.md`

## 一句话结论

**不能实质压缩。** 平台 JUnit3 路径已经是「每 JVM 一个 Application、每 JVM 一个 light project、跨类复用」，JUnit5 的 `ExtensionContext.Store(GLOBAL)` 只是同语义复刻；本套件 77% 的时间在平台测试上，而平台测试整段跑在 EDT（`UsefulTestCase.runInDispatchUnitThread()==true`），JUnit5 的 `@Execution(CONCURRENT)` 被 EDT 串行化。

**保守收益 0~5%，乐观 5~10%；迁移成本 550~1100 人时（3.5~7 人月），高风险。** 不换框架的三条手段可拿到分片关键路径 15~20% 的收益，成本低两个数量级。

## 一、两条结构性事实（javap 实证，也是全篇推断的支点）

### 1.1 light project 是跨类复用的，不是每类重建

`com.intellij.testFramework.LightPlatformTestCase` 持有：

```
private static LightProjectDescriptor ourProjectDescriptor;
private static Project ourProject;
private static Module  ourModule;
public static Pair<Project, Module> doSetup(LightProjectDescriptor, LocalInspectionTool[], Disposable, Disposable, String);
```

`doSetup` 里 `ourProject != null && ourProjectDescriptor.equals(新 descriptor)` 成立就复用。仓内只有 5 个类覆盖 `getProjectDescriptor()`，且全是 DB 集成类（在 `testDb*` 任务，不在分片）。**分片轮里的 388 个平台类共享每 JVM 一个 light project。**

### 1.2 平台的「JUnit4 基类」是空壳

```
public abstract class LightPlatformCodeInsightFixture4TestCase extends BasePlatformTestCase {
  public LightPlatformCodeInsightFixture4TestCase();   // 只有构造器
}
```

243 与 253 都是这样。**它不是 JUnit4 适配器**——「先迁 JUnit4 再迁 JUnit5」没有中间落点。（本次已按用户定调改为「统一向 JUnit3 收口」，见 T-Junit4Migration。）

### 1.3 JUnit5 的共享模型等价于 JUnit3

`TestApplicationExtensionKt.testApplication(ctx)` = `ctx.getRoot().getStore(GLOBAL).getOrComputeIfAbsent("application", …)`：一个 JVM 一份 Application，且 `TestApplicationExtension` 是 `AfterEachCallback`（每个用例后 `cleanApplicationState`）。注解 `@TestApplication` **无成员**，没有 `shared=true` 之类开关。

对照 JUnit3：`TestApplicationManager` 本身就是 `private static final ourInstance` 单例。→ **应用复用上收益为 0。**

JUnit5 的 `projectFixture` 反而更差：`ProjectManagerEx.newProjectAsync(tempPath, …)` 建的是临时目录上的真实项目，static 字段只到「每类一份」，默认不跨类共享。

### 1.4 JUnit5 下 `myFixture` 没有等价物

243 的 `com.intellij.testFramework.junit5.*` 共 91 个类，fixture 只有 `tempPath/project/module/sourceRoot/psiFile/editor/extensionPoint/disposable` 八种，**没有 `CodeInsightTestFixture` 工厂**。而 `myFixture` 是本仓 **171 个文件 / 1569 处**引用的核心 API。

## 二、套件耗时结构（实测）

| 口径 | 类数 | 用例数 | suite 时间 | 占比 |
|---|---:|---:|---:|---:|
| 平台类（继承平台基类） | 388 | 3623 | 878.9s | **77.0%** |
| 纯逻辑（JUnit4，不继承平台基类） | 423 | 4971 | 262.1s | 23.0% |
| 合计（5 分片 + 尾道） | 811 | 8594 | 1141.0s | 100% |

平台用例平均 **0.243s/例**、纯逻辑 **0.053s/例**（平台贵 4.6 倍）。

分片实测：`225.4 / 199.8 / 208.0 / 206.8 / 270.6s`——**最重片比最轻片重 35.4%**。

头部集中度：Top 3 个纯逻辑类（`O147HistoryUpgradeTest` 98.04s、`JavaCodeGeneratorTest` 53.92s、`ReverseRoundTripGateTest` 33.51s）合计 **185.5s = 16.3%**；覆盖 50% 时间只需 41 个类（5.1%）。

## 三、换 JUnit5 的收益逐条评估

| 收益点 | 上限 | 判断 |
|---|---:|---|
| Application 复用 | 0 | JUnit3 已是每 JVM 一份 |
| light project 跨类复用 | 0 | JUnit3 已复用（§1.1）；JUnit5 默认反而每类建真实项目 |
| per-class fixture | 理论 257s（22.5%），实际 0~10% | 71ms/例是「setUp + 测试体」合计；JUnit5 每类新建项目很可能把收益吃掉 |
| JVM 内并行 `@Execution(CONCURRENT)` | 纯逻辑 262.1s 的一半 = 11.5% | 平台 77% 跑 EDT，并行度≈1；本地 5 片已占满 6C12T，本地收益≈0；CI 每片独占 2 核，或可拿到 0~10% |

**保守区间**：本地 `testShards` 0~3%；CI `test ×5` 3~5%（乐观 5~10%）；本地 `releaseGate` 端到端 **0**（关键路径是 `verifyMarketplace` 789s，测试段 544s 装在其窗口内）。

**迁移成本**：平台类 398 × 1~2h + 纯逻辑 449 × 0.2~0.5h + 基建/守卫 40~80h ≈ **550~1100 人时**；且需给每个平台类加 `@RunInEdt`，现有的 `Junit3SemanticsGuardTest` 整体失效需重写。

## 四、不换框架的三条替代（按性价比）

| # | 做法 | 建模收益 | 保守 | 成本 |
|---|---|---:|---:|---|
| 1 | **刷新分片权重画像 + LPT 重装箱**（`dev-support/weight-refresh.ps1`） | −15.7% | **−10~15%** | 一轮干净全量 + 提交 TSV，零代码风险 |
| 2 | **纯逻辑桶摘出分片，单独一条并行腿**（370 类 / 4386 例 / 231.7s = 20.3%） | −32.8% | **−15~20%** | CI 加一条 matrix job；需补「分片排除清单 ↔ testFast 清单」parity 守卫 |
| 3 | **热点类隔离或 CI 第 6 分片**（O147 单类 98s = 8.6%） | −22.9% / −29.7% | **−20%** | 改 include 清单（低风险）或加 1 台 runner |

不建议再做：`forkEvery`、多 fork、GC/线程参数、AppCDS——文档已逐项 A/B 销案。

### 4.1 方案 2 实施方案与实测（2026-11-05 晚，提交 006b9766）

落地形态：分片桶 = `discoveredTestClasses − fastBucketClasses`（446 类），快桶由 `testFast` 作为
独立腿承载，`testShards` 聚合 `dependsOn("testFast")`；配置期新增「每个测试类必须落在某个执行面」
的 `require` 断言；`testFast` 与分片同源尊重 `-PtestShardExcludeClasses`（O147RealAgentAcceptanceTest
属快桶，不尊重就会在无本机 JDK8 的 runner 上红）。

三条实测订正：

1. **口径**：本文的 370 类 / 4386 例 / 231.7s 是「是否继承平台基类」分类；构建自身口径是「测试源码
   是否含 `com.intellij` 字面引用」，本轮 374 类 / 4416 例 / 226.6s（第二轮 240.4s）。差的 4 类 =
   源码无平台引用但继承平台基类，落快桶，两边各自自洽，结论不变。
2. **本地 testShards 的 5 片从来不是并行的**：两轮每片 doLast 的 `laneAtEnd` 全 0，END 时刻逐片相接
   （改前 08:47 轮 external END → shard5 END 共 1234.6s，5 片 exec 合计 1111s）。`org.gradle.parallel`
   只跨项目并行，5 个 `testShardN` 同属 root project。→ 方案 2 在**本机**兑现的是「分片总量与失衡
   下降」（5 片 exec 合计 1111s → 735.8s，execSum 961.3 → 735.8，失衡 +20% → +6.6%），不是「两条腿
   并行」；并行那部分只在 CI（每腿独立 runner）或 `dev-support/test-shards-parallel.ps1`（已加 fast
   lane）兑现。本机整条测试腿墙钟 1234.6s → 1076.9s（−12.8%），因为快桶的 256s 串在分片前面而不是并排。
3. **方案 1 的真实收益是刻度校正，不是再平衡**：旧画像出自 961.9s 污染轮（`-Force` 放行），
   expected 176.0s/片 vs 实测 147.2s（高估 16%）；刷新后 expected 147.2s，实测均值 154.0s。
   relCrit 1.066 → 1.088，均远低于 1.10 告警线——片间失衡本来就不是本套件的痛点，
   方案 1 的价值在「expected 可信」（对照行与缺权告警不再被刻度差污染）。

## 五、未找到 / 未验证（不要当实测）

1. **没有任何 JUnit5 实跑对照**；仓内零 JUnit5 使用痕迹。本报告的收益全是由耗时结构与平台字节码推出的上界。
2. XML **拿不到 setUp/tearDown 分项**（suite 与 Σtestcase 只差 0.6s，setUp/tearDown 混在 testcase 内）。
3. JUnit5 `projectFixture` 的每类真实项目创建成本**未测**——这是收益判断里最大的不确定项，可能把 0~10% 打成负值。
4. `useJUnitPlatform()` + vintage 的 per-test 固定开销**未测**。
5. 13s bootstrap 是文档口径 + 首用例间接读数，未做「同片只跑 1 类 vs 150 类」对照。
6. 本轮 1141.0s 与权重画像轮 961.9s 差 +18.6% 未完全解释（窗口漂移/新增用例/顺序 vs 并发）；**相对占比比绝对值可信**。
7. 纯逻辑测试在 JVM 内并发是否安全**未审计**（已知平台侧有 27 类全局态泄漏史）。

## 六、结论

- **JUnit5 迁移：不做。** 收益上限 10%，成本 3.5~7 人月，且决定性收益点（应用/project 复用）已不存在。
- **压测试墙钟：做替代方案 1→2→3**，分片关键路径可拿 15~20%（保守），实施成本约 1~3 人天 + 1 台 CI runner，零测试语义改动。
  - 方案 2 与方案 1 已于 2026-11-05 晚落地（提交 006b9766 + 画像刷新轮），实测与订正见 §4.1；
    方案 3（热点类隔离 / 第 6 分片）未动。
- 本题并入 `T-Junit4Migration` 的结论段：该任务只做「语义正确性收口」（P0/P1/P2/P2.5），**不做框架迁移**。
