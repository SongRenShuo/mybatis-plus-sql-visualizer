# 国产库安装器 cgroup 探测普适性 - 调研报告

> 日期：2026-11-06
> 调研对象：`checkDockerEnv()` 一类「grep `/proc/1/cgroup` 的 cgroup v1 形态」的容器探测，在 cgroup v2 宿主上恒假的问题，是否会波及磐维以外的国产/商业数据库安装器。
> 结论先行：**命中面是「openGauss OM（gspylib）血统」的安装器，不是「所有国产库」。**
> 磐维之外，海量 Vastbase 的安装器里存在**逐字相同**的函数，并已在本宿主实测返回 `False`（但它的容器镜像安装路径不走 OM 预检，所以没有复现安装失败）；
> openGauss-OM 上游 master 至今仍是同款写法；瀚高 HighGo 6.0.1、GaussDB Kernel 503、openGauss 官方运行镜像里**没有这个函数**；
> 金仓/达梦/GBase 8c 本机无镜像也无安装包，公开渠道未取到安装器代码，**无证据**。

## 2. 磐维：判定原文、失效机制与读数出处

### 2.1 原文（未打补丁版本，容器内 `.orig` 备份）

文件：`/database/panweidb/soft/script/gspylib/common/Common.py.orig`（`checkDockerEnv` 定义在 `Common.py:2424`）

```python
def checkDockerEnv():
    cmd = "egrep  '^1:.+(docker|lxc|kubepods)' /proc/1/cgroup"
    (status, output) = subprocess.getstatusoutput(cmd)
    if output:
        return True
    else:
        return False
```

### 2.2 失效机制

该正则要求 `/proc/1/cgroup` 里存在以 `1:` 开头的行。cgroup v1 的形态是
`1:name=systemd:/docker/<id>`，能被命中；cgroup v2 的统一层级形态是 `0::/...`，**没有任何 `1:` 行**，
`output` 为空 ⇒ 恒返回 `False` ⇒ 所有包在 `if checkDockerEnv()` 后面的「容器内可容忍」分支全部走不到。

本宿主实测（Ubuntu 22.04，`docker info` 报 `Cgroup Version: 2`、`Cgroup Driver: systemd`）：

```
$ cat /proc/1/cgroup          # 宿主
0::/init.scope
$ docker exec panweidb-test cat /proc/1/cgroup   # 容器内
0::/init.scope
$ docker exec xc3-vastbase cat /proc/1/cgroup
0::/
```

### 2.3 「一个 False 让 9 处容器内可容忍分支失效」的出处与订正

出处：`docs/经验总结/20261106-1523-磐维PanWeiDB镜像搜索与容器部署-经验总结.md` §4.2（行 137-190），
以及 `.agents/skills/db-env-provisioning/SKILL.md:220` 与 `:378`。

本轮在容器内按行重新数了一遍调用点（`grep -rn "checkDockerEnv()"`，排除定义行与 `.orig` 备份），
**调用行共 10 行，按「guard 组」计为 9 组**，与文档的「9 处」对得上：

| # | 文件:行（相对 `script/`） | 备注 |
|---|---|---|
| 1 | `local/LocalCheckOS.py:828` | |
| 2 | `local/LocalCheckOS.py:927` | |
| 3 | `local/LocalCheck.py:245` | 容器内跳过 `docker_no_need_check` 里的内核参数检查 |
| 4 | `inspection/items/network/CheckMultiQueue.py:60` | |
| 5 | `inspection/items/os/CheckHyperThread.py:50` | |
| 6 | `inspection/common/SharedFuncs.py:69` | |
| 7 | `inspection/common/SharedFuncs.py:749` | 与 #8 是同一函数里嵌套两级判断，合为 1 组 |
| 8 | `inspection/common/SharedFuncs.py:753` | 同上 |
| 9 | `inspection/common/SharedFuncs.py:770` | `CheckNetWorkBonding` |

因此读数的准确表述是「**10 个调用行 / 9 组判定**」，文档写「9 处」不算错，但建议合并 skill 时补一句口径，
避免后续按 `grep | wc -l` 复核时对不上。

### 2.4 补丁后实测

磐维 `checkDockerEnv()` 开头插入 `/.dockerenv` 判定后，容器内直接调用：

```
$ docker exec panweidb-test sh -c 'cd /root/gauss_om/omm/script && python3 -c "... DefaultValue.checkDockerEnv()"'
checkDockerEnv()= True
```

镜像内同名文件共 4 份（`/root/gauss_om/omm/script/`、`/database/panweidb/soft/script/`、
`/database/panweidb/tool/script/`、`/database/panweidb/app_*/bin/script/`），安装期生效的是 `soft/script` 那份。
**换产品复用时必须确认改的是安装期加载的那一份**，否则补丁不生效且很难看出来。

## 3. 同源扩散：海量 Vastbase 有逐字相同的代码

### 3.1 代码

文件：`xc3-vastbase` 容器内 `/home/omm/vbdata/install/om/script/gspylib/common/Common.py:2427`

```python
def checkDockerEnv():
    cmd = "egrep  '^1:.+(docker|lxc|kubepods)' /proc/1/cgroup"
    (status, output) = subprocess.getstatusoutput(cmd)
    if output:
        return True
    else:
        return False
```

调用点与磐维**同一集合、同一行号段**（`LocalCheckOS.py:828/927`、`LocalCheck.py:245`、
`CheckMultiQueue.py:60`、`CheckHyperThread.py:50`、`SharedFuncs.py:69/749/753/770`、`Common.py:686`），
说明两者都是从 openGauss-OM 拉的同源代码分支。

### 3.2 判定实测为 False

用 Vastbase 自带解释器（`/home/omm/vbdata/install/vastbase/python/bin/python3.8`；
注意容器内 `/usr/bin/python3` 是 3.6.8，导入该文件的 f-string 会报语法错，不是代码问题）直接调用：

```
$ docker exec xc3-vastbase sh -c 'cd /home/omm/vbdata/install/om/script && ...python3.8 -c "... DefaultValue.checkDockerEnv()"'
checkDockerEnv()= False
```

同宿主、同 cgroup v2、同款代码 ⇒ 磐维的失效机制在 Vastbase 里客观成立。

### 3.3 为什么 Vastbase 没有复现安装失败

两条独立原因，都是「没走到那条路」，不是「这条路没问题」：

1. **容器安装不走 OM 预检**：`/opt/script/entrypoint.sh` 里只有
   `gs_initdb -D $dataPath -U $initUser ...`（第 273 行），全文没有 `gs_preinstall` / `gs_install` / LocalCheck。
   OM 脚本随包落地但不参与首装。
2. **它恰好不缺那个目录**：磐维的 GAUSS-51400 来自
   `find /etc/sysconfig/network-scripts -iname 'ifcfg-*-lo'` 失败；Vastbase 镜像内
   `/etc/sysconfig/network-scripts/ifcfg-lo` 本来就在，`find` 退出码 0，容忍分支根本没被调用。

⇒ 结论只能写「代码同款 + 判定实测 False」，不能写「Vastbase 安装会失败」。真正的复现条件是
「cgroup v2 宿主 + 用 OM 的 `gs_preinstall`/`gs_checkos` 路径 + 命中被跳过的那几项检查」。

## 4. 上游与「没有这个函数」的产品

### 4.1 openGauss-OM 上游 master（同款，缺陷仍在）

抓取 `https://gitee.com/opengauss/openGauss-OM/raw/master/script/gspylib/common/Common.py`（188385 字节）后 grep：

```
2375:    def checkDockerEnv():
2376-        cmd = "egrep  '^1:.+(docker|lxc|kubepods)' /proc/1/cgroup"
```

即上游从未修过这个问题，所有从 openGauss-OM 拉分支的商业发行版（含本轮的磐维、海量）都会继承。

### 4.2 GaussDB Kernel 503（华为商用内核）

`/opt/om/script/gspylib/common/Common.py`（405912 字节、8388 行）里：

```
$ grep -rn "DockerEnv\|/proc/1/cgroup\|dockerenv" /opt/om/    → 0 命中
$ grep -in "docker" .../Common.py
6116:        function: The /proc mounting in the Docker environment is unstable.
```

只有一句注释，配的是 `retryGetNetcard()` 的重试逻辑，**没有容器探测函数**。
也就是说 GaussDB 503 天然不受这个缺陷影响（它可能因别的原因在容器里挑剔，但那不是本报告的题目）。

### 4.3 瀚高 HighGo 6.0.1

`/opt/HighGo6.0.1-cluster` 全树 grep `checkDockerEnv` / `/proc/1/cgroup` / `/proc/self/cgroup` / `dockerenv`
= 0 命中。其容器是 PostgreSQL 直跑形态（`PGDATA=/opt/HighGo6.0.1-cluster/data`），没有 OM 式安装器。

### 4.4 openGauss 官方/社区运行镜像

`opengauss/opengauss:5.0.0` 容器内 `find / -maxdepth 5 -name gspylib` 无结果，`/usr/local/opengauss/bin`
下没有 `script/`；`enmotech/opengauss:5.0.0` 同理（只有 `bin etc include jre lib share simpleInstall`，
`simpleInstall` 里是 `install.sh` + 示例 SQL，无 cgroup 探测）。
⇒ 这两类镜像不暴露 OM，**不能拿「镜像里没有」推断「openGauss 没这个问题」**；上游源码才是权威。

### 4.5 无证据的三家

金仓、达梦、GBase 8c：本机 `find /` 只命中 `/opt/xc3-attach-smoke/kingbase8-9.0.1.jar`（JDBC 驱动，非安装器），
无镜像、无安装包；公开渠道本轮没取到安装器源码。按纪律记「无证据」，不套用 openGauss 的结论。

## 5. 判据（下次遇到 cgroup v2 宿主，先跑这一条）

在**准备安装的容器内**执行（不是宿主）：

```bash
sh -c 'head -1 /proc/self/cgroup; grep -rln "checkDockerEnv" / 2>/dev/null | head'
```

判读：

- 首行是 `0::/...` ⇒ cgroup v2；若同时 grep 命中 `checkDockerEnv`，**大概率会中同一枪**（磐维/海量即此形态）。
- 首行是 `1:name=...` ⇒ cgroup v1，原判定能正常工作，不用管。
- 命中 `checkDockerEnv` 后，再确认它是不是安装期加载的那份：
  `grep -rn "checkDockerEnv()" <安装根>/script | wc -l`（磐维/海量均为 10 个调用行）。

更快的一次性验证（有 Python 的安装器可直接问它自己）：

```bash
cd <安装根>/script && python3 -c "import sys;sys.path.insert(0,'.');from gspylib.common.Common import DefaultValue;print(DefaultValue.checkDockerEnv())"
```

返回 `False` 就是已中招（Vastbase 实测 `False`，磐维补丁后实测 `True`）。

## 6. 最小补丁思路

| 方案 | 做法 | 验证状态 |
|---|---|---|
| **改探测函数（首选）** | 在 `checkDockerEnv()` 开头加 `if os.path.exists("/.dockerenv") or os.path.exists("/run/.containerenv"): return True`，保留原正则做后备 | **磐维已实测**：补丁后 `checkDockerEnv()=True`，`gs_checkos` 通过、库正常起停 |
| 只补检查点输入（降级） | `mkdir -p /etc/sysconfig/network-scripts`（`find` 无匹配返回 0，空目录即可过） | **磐维已实测**仅能过 GAUSS-51400 一项；GAUSS-50612（`ethtool -g eth0`）仍要改函数。**不解决 10 个调用行** |
| 环境变量/安装参数开关 | 需要厂商安装器自带「跳过 OS 检查」入口 | **未验证**：openGauss-OM 的 `gs_preinstall` 是否有等价开关本轮未查证，不要写成可行 |
| 宿主回落 cgroup v1（`systemd.unified_cgroup_hierarchy=0`） | 整机重启生效，影响同机所有容器 | **未验证且不推荐**：Docker 24+ 默认 cgroup v2，且本宿主还有其他在跑实例；只作为最后手段 |

补丁落点提醒：同镜像内 `checkDockerEnv` 可能有多份拷贝（磐维 4 份），只改一份等于没改；
安装型镜像要在 **`gs_preinstall` 之前**改，装完再改只能救 `gs_checkos` 这类运行期检查。
