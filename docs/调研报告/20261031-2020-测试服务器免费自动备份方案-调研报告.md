# 测试服务器免费自动备份方案 调研报告

**创建时间**：2026-10-31 20:20
**调研对象**：DBX 在册 SSH 靶机「不大-北京-16G」（`103.36.220.245`，Ubuntu 22.04 / 16C15G / 194G 盘用 35G），跑 8 个数据库容器，用户自述「这台服务器很容易丢数据」。
**需求**：免费的、定时的、自动的数据备份；候选取向为阿里云 OSS / 腾讯云 COS / 七牛云等对象存储桶。
**执行形态**：三路子智能体后台并行（A 路免费额度、B 路工具链、C 路现成方案）+ 主控经 DBX MCP 亲自体检服务器与实测链路。所有服务器侧读数均为本会话只读命令实测，非推断。

---

## 0. 结论

**推荐方案**：`restic 0.19.1（已装并验证）` + `七牛云 Kodo 标准存储（10GB 长期免费额度）` + `systemd timer 每日定时` + `healthchecks.io 心跳告警`，备份内容为**七库逻辑导出 + 配置与镜像清单**，保留 7 日 / 4 周 / 6 月。

**成本**：按实测压缩比推算，去重压缩后的仓库极可能落在 2~5GB，**落在七牛 10GB 长期免费额度内，常态支出 0 元**；即使超到 20GB，也就 2.3~3.3 元/月。

**为什么不是其他家**：

| 候选 | 结论 | 关键理由 |
|---|---|---|
| 七牛 Kodo | **选它** | 唯一同时满足「无到期日的免费额度 + 境内速度 + 恢复便宜（0.26 元/GB）+ 个人实名可开 + S3 兼容」 |
| 腾讯 COS | 备选/过渡 | 50GB×180 天额度最大、防删能力最全（版本控制 + 对象锁），但第 181 天起按量计费，本质是限时 |
| 阿里云 OSS | 不推荐 | 免费期仅 3 个月、"20GB 装不下"、恢复 0.5 元/GB（35GB 一次 17.5 元）；WORM 最完备是需要合规留痕时才成立的理由 |
| Cloudflare R2 / Backblaze B2 | 不做主桶 | egress 免费、经济性最好，但跨境：首次 17G 上传播不完、恢复按 500KB/s 要按小时计，且数据出境要合规评估 |
| 火山 / 华为 / 京东 | 淘汰 | 免费政策不透明（多为未核实传闻），只在「服务器本就在该云」时才有内网免费优势 |

**两个推翻预期的事实**（决定了方案形态）：

1. **这台机器不在阿里云/腾讯云/华为云上**。四个云元数据端点全部无响应，DMI 是裸 `Red Hat KVM`，宿主还挂着服务商自己的 `gmssh` 与 `mofang-security`——它是中小 IDC 的 VPS。**「开云厂商自动快照」这条最省事的第一层在本机不存在**，控制台是否有自助快照需用户自己确认购买面板。所以「很容易丢数据」的最可能根因从「磁盘坏」变成**服务商生命周期**（停机 / 回收 / 跑路），这恰恰是必须做异地对象存储备份、而不是只做本机快照的理由。
2. **这台机器连不上 GitHub**（`github.com` 12 秒超时、经本地代理 `api.github.com` 也 403），apt 里的 restic 只有 2022 年的 0.12.1（无仓库压缩）。**装新版 restic 得走「本地代理下载 → bz2 → SFTP 上传 → 服务器解压」**，这条链本次已完整验证通过。

| 缺失 | rclone/restic/borg/pigz/sqlite3/宿主 pg_dump |

### 1.5 风险信号（与「容易丢数据」直接相关）

1. **SSH 暴力破解量极大**：近 7 天 `Failed password` **166,944 条**（约 17 万次）。root 口令一旦被撞开，攻击者与备份同机同权 → 备份会一起被删。
2. **服务商对宿主有 root 级接入**：`/usr/local/bin/mofang-security` 每 5 分钟心跳、每 20 分钟上报「未检测到违规项」，另有 `/usr/local/bin/gmssh`。本机配置一旦被判定违规可能直接处置，这也是「数据易丢」的候选成因。
3. **无 SMART、单 `/dev/vda`**：机器侧无法判断底层盘健康，冗余只能靠外部备份。
4. **当前没有任何自建备份**：crontab 里只有服务商心跳任务。
5. **mssql 数据在容器写层**（`docker inspect` 无 Mounts）——`docker rm` 或重建容器即丢，这是本机最像「莫名丢数据」的一处结构性风险。

### 2.1 裁决理由

选中七牛的三条硬理由：

1. **没有到期日**。这是给「挂着就不管」的 cron 用的系统。COS 的 50GB 半年后消失、OSS 的 20GB 三个月后消失，到期不会停机而是直接扣费——半年后一张莫名其妙的账单，比多花两块钱更糟。七牛的额度按官方《免费额度信息》页是「标准存储 0-10GB、GET 0-100 万次、PUT/DELETE 0-10 万次、CDN 回源 0-10GB」，超出进入标准阶梯计费、次月初扣费；**该页并未书面承诺"永久"**（价格页表述为长期免费，实际政策多年未变，但无合同级承诺）。所以准确说法是「没有到期日的长期免费额度」，不是「永久免费」。
2. **容量刚好够用**。实测数据压缩后在 2~5GB 区间，10GB 额度不但够，还留了历史版本空间。
3. **恢复便宜**。这是最容易被忽略的一项：备份的价值在「取得回」，35GB 全量恢复在阿里/腾讯是 17.5 元一次，七牛 6.5~10 元，R2/B2 是 0——但 R2/B2 输在跨境速度（见下）。

不选 R2/B2 做**主桶**的理由：经济性确实更好（B2 35GB 约 1.2 元/月、egress 全免），但首次 17G 上行要跑一整夜、恢复按大陆访问体感 500KB/s~5MB/s 计算，最坏情况是「备份存在但恢复要 20 小时」，而备份的可用性恰恰由最坏情况定义。另有一条非技术约束：若备份里含真实用户数据，境外存储要走出境合规评估。

不选阿里云 OSS 的理由：免费窗口只有 3 个月、20GB 装不下、恢复最贵。它唯一的优势是 WORM 最完备（Bucket 级合规保留 + 对象级 retention），属于「等保/审计留痕」需求，不是当前需求画像。

### 2.2 一个必须提前知道的冲突：WORM 与 restic 的 prune 互斥

restic 靠 `forget --prune` 删除过期快照，而对象锁（WORM）在保留期内**不允许任何删除**，两者天然打架。所以「开对象锁的桶」不能同时是「每日增量仓」。正确做法是拆两个角色：

- **每日仓**（可维护）：普通桶，AK 有读写删权限，靠 restic 保留策略控量；
- **不可变归档**（防入侵/防误删）：另一个桶开对象锁，AK **只给 PutObject**，只放月度全量归档，靠「密钥不全在手」防删。

七牛的 10GB 免费额度是账号级共享，两个桶共用这一份额度，规划时按总量算。

### 2.3 超过 10GB 怎么办

先算清账：七牛超出部分 0.115 元/GB/月（华东-浙江2，最便宜档）。15GB ≈ 0.58 元/月，20GB ≈ 1.15 元/月，30GB ≈ 2.3 元/月。**这不是需要设计规避的量级**，但要知道触发点在哪、以及怎么把增长压住。

按优先级可用的手段：

1. **先看真实读数**：`restic stats --mode raw-data` 给出仓库实际体积。注意 10GB 额度里要留 5~10% 给 restic 的 index/locks，可用约 9GB。
2. **收紧保留**：`--keep-daily 7 --keep-weekly 4 --keep-monthly 6` → 改成 `5/4/3`，历史快照数直接决定仓库体积上限。
3. **每周 prune 带封顶**：`--prune --max-repack-size 2G`，否则未引用的 pack 会一直占着。
4. **分层**：把「月度全量归档」放到 B2 或 R2 的免费 10GB（它们 egress 免费），七牛只放近 30 天的热仓。
5. **只备逻辑 dump、不备镜像**（本方案已如此）：镜像 8GB 是最大的一块，用 digest 清单代替，重建时从镜像源重拉。
6. **接受几块钱**：年成本几十元，对「数据不丢」这件事而言是划算的。

不建议：开多个账号分摊额度（触发风控/违反条款）、把备份仓转低频或归档（取回费 + 最短存储期会把恢复变贵变慢，且 restic 的 check/prune 直接不可用）。

监控方式：每月初看七牛控制台「免费额度/用量」页，配一条月度 `restic stats` 记进日志。额度是「次月初扣费」模式，当月超了不会有即时提醒，必须自己按月看。

### 2.4 收费陷阱（比价目表重要）

1. **恢复流量费是账单大头**，不是存储费。一次慌乱中的全量恢复 = 一年的存储费。
2. **「免费额度」普遍只覆盖存储**，不含下行流量与请求（COS 官方原文就写明资源包「仅可抵扣标准存储容量」）。
3. **限时额度到期自动转按量、不提醒**。
4. **备份仓别做生命周期降级**：转低频/归档会产生取回费，restic 的 `prune`/`check` 要大量读 pack 文件，转归档后 check 直接不可用。
5. **最低存储时长 + 提前删除补费**：用「每天全量上传新文件」的朴素脚本，等于每天都在为前一天补费。
6. **64KB 最小计量**：restic 的小 pack 文件在低频/归档类下会被放大计费。
7. **七牛的 10GB「CDN 回源」不等于「源站下行」免费**：走 S3 endpoint 恢复不计入那 10GB，按 0.26 元/GB 计。

### 2.5 七牛没有「超过 10GB 就停」的开关，闸门只能自己做

查过官方文档：Kodo 空间**没有容量硬配额**，容量可以一直涨，超出免费额度的部分直接按量计费。控制台能设的只有「余额/费用预警」这类通知，不是硬闸门。

**不能用欠费当闸门**：余额为 0 时超额仍会计费并累积欠费，欠费会冻结存储服务（上传下载失败），长期欠费还会清数据且不可恢复。拿它当「免费额度保险丝」，等于把备份仓押在一条会把数据删掉的电路上。

**更不能给 restic 仓库配生命周期删除规则**：七牛的生命周期按「上传时间 + N 天」删对象，不理解 restic 的引用关系，会删掉仍被快照引用的 pack，直接把仓库搞坏。restic 仓库前缀的生命周期最多只允许配「未完成分片清理」，不许配任何删除或转存储类规则。另外它只对规则创建后新上传的对象生效，天生做不到「保留最近 N 份」。

所以「只用免费额度 + 新备份顶掉最旧备份」这两个需求，全部落在备份脚本里，做成三道闸（见 §3.4）。

## 3. 工具链：为什么是 restic

| 工具 | 增量/去重 | 加密 | 单二进制 | 对象存储支持 | 校验 | 结论 |
|---|---|---|---|---|---|---|
| **restic** | 是（内容定义分块 + zstd 压缩） | 是（AES-256-CTR + Poly1305） | 是（静态链接） | 原生 S3/COS/七牛 | `check --read-data-subset` | **选它**，0.19.1 已装并验证 |
| borg/borgmatic | 是 | 是 | 否（依赖 Python + FUSE） | 需要 rclone 中转（rclone backend） | `check --verify-data` | 备选；对象存储上 prune 要全量下载，不划算 |
| kopia | 是 | 是 | 是 | 原生 S3 | 有 | 备选，生态比 restic 小 |
| duplicity | 增量链 | 是（GPG） | 否 | 是 | 较弱 | 增量链一断全废，淘汰 |
| rclone sync | 无（同步） | 传输时可选 | 是 | 极广 | `check` 只比哈希 | **只做辅助**（跨桶复制/恢复提速），不做版本 |
| tar + 日期命名 | 无 | 靠 gpg | 是 | 靠 rclone | 无 | 只适合「每月一份全量归档」 |

选 restic 的决定性理由是三条本机实测事实而不是纸面功能：GitHub 不通但已用 SFTP 装上 0.19.1；S3 兼容后端在七牛有官方 path-style 支持；单二进制、无运行时依赖，符合这台机器「不想为备份再装一堆包」的现状。

其他要点：

- **保留策略**：`--keep-last 7`（只留最近 7 份，新增一份就顶掉最旧一份），配 `--prune --max-repack-size 2G`。GFS 式 `--keep-daily/--keep-weekly/--keep-monthly` 更省空间但也更复杂，10GB 额度下先用 `--keep-last` 更直观；prune 会把部分使用的 pack 下载、重打包、再上传，官方原话是 "can be very time-consuming for remote repositories"，所以要封顶且不必每日跑。
- **限速**：`--limit-upload 3000`（KB/s，约 24Mbps）避免把出口打满影响数据库测试。
- **调度**：用 systemd timer 而非裸 crontab —— `systemctl status` 能看上次结果、可 `flock` 防重叠、失败可 `OnFailure=` 挂告警单元，且 `Persistent=true` 能在关机错过后补跑。
- **告警**：healthchecks.io 免费 20 个 check，脚本末尾 ping，**26 小时没 ping 就发邮件**。这是「备份静默失败」唯一的可靠解法——免费面板的失败告警基本都在付费侧。
- **加密口令**：restic 仓库密码**不能只存在被备份的这台机器上**，否则机器没了等于备份没了。要离线存一份（密码管理器 + 打印/另一台机器）。
- **锁**：restic 的锁是对象存储上的普通文件，进程每 5 分钟刷新；被 kill 后残留锁会让下次报 "repository is already locked"。定时任务里用 `--retry-lock 10m` 等锁，不要无脑 `restic unlock`（`--remove-all` 会连活锁一起删）。

### 3.1 关键实现细节：dump 格式要配合 restic 的去重

**不要把 dump 先 gzip 再交给 restic**。`mysqldump | gzip` 产出的已压缩字节流会让 restic 的跨天去重基本失效——每天一个全新的压缩流，块级指纹对不上，等于每天全量重传。正确做法：

- MySQL / MariaDB：输出**纯 SQL 文本，不压缩**，交给 restic 压；
- PostgreSQL 系：`pg_dump -Fc -Z0`（自定义格式但关闭内部压缩），这样未变动的表数据块能跨天命中；
- 代价：本地暂存目录会显著变大（文本 dump 可能到十几 G），`/` 还有 160G 可用，够放两代，但脚本必须限制本地保留份数。

### 3.2 后端对接参数（两处坑，不写对必然 403）

| 后端 | 仓库地址形态 | 必须追加的参数 |
|---|---|---|
| 腾讯 COS | `s3:https://cos.<region>.myqcloud.com/<bucket-appid>/restic` | `-o s3.bucket-lookup=dns`（2024-01-01 后新建桶**禁用 path-style**，报 `PathStyleDomainForbidden`）；`-o s3.region=<region>` |
| 七牛 Kodo | `s3:s3.<region>.qiniucs.com/<bucket>` | `-o s3.region=<region>`（官方 restic 对接文档即用 path-style，默认配置可用） |

七牛区域 ID：`cn-east-1`（华东-浙江）、`cn-east-2`（华东-浙江2）、`cn-north-1`（华北-河北）、`cn-south-1`（华南-广东）。

七牛 S3 兼容层只承诺「涉及的接口实现了兼容」，没有逐项列出 multipart / DeleteObjects / ListObjectsV2 的支持情况，因此**首次接入必须跑一轮真实验收**（造 1GB 测试数据 → 首次备份 → 追加增量 → 校验 → 恢复比对 → 删除快照并 prune → 中断续传），全部通过再上生产。

### 3.3 与 B 路结论的分歧（如实登记）

B 路（工具链专项）独立给出的推荐是 **restic + 腾讯 COS**，理由是「35GB 装不进七牛的 10GB」。这个分歧的根源是前提不同：B 路用的是调研任务里给的 35GB 账面容量，而主控实测真实数据只有 17~19G、压缩后 2~5GB，因此七牛 10GB 够用。两者对工具的判断完全一致（都是 restic 0.19.1 + systemd timer + 心跳告警），只在后端归位上分歧，裁决依据以实测数据为准。

B 路的第二名方案是 **kopia**（保留策略按 source 配更直观、`snapshot verify --verify-files-percent` 更贴近恢复演练），代价是多一个「维护所有者」概念、重建主机后要手动改 owner，运维心智高于 restic。

### 3.4 「只用免费额度 + 新备份顶掉最旧」怎么落

需求拆成两件事：**滚动删除**（restic 原生）与**容量闸门**（自建，七牛没有）。

滚动删除用 `restic forget --keep-last N` —— 语义就是「只留最近 N 份快照，更早的删掉」，配合 `--prune` 才真正释放空间（**只 forget 不 prune，空间不会减少**，因为 pack 文件还在）。

```bash
r forget --keep-last 7 --prune --max-repack-size 2G
```

容量闸门做成备份前置检查，三道闸逐级收紧：

| 闸 | 触发条件 | 动作 |
|---|---|---|
| 1 | 每次备份前 | 先跑 `forget --keep-last N --prune`，把过期快照回收掉 |
| 2 | 回收后仓库体积仍 > 预算 | 自动降一档（`N` 减半）再 prune 一次 |
| 3 | 仍超预算，或本次 dump 体积异常 | **中止本次备份**，保留现有快照，发告警；不做任何破坏性操作 |

预算按免费额度留余量：额度 10GB，restic 的 index/locks 约占 5~10%，且删除后计量不会立刻归零，所以把闸门定在 **9GB**。

判断体积用 `restic stats --mode raw-data --json` 的 `total_size`（字节），脚本里用 python3 解析即可，不必装 jq：

```bash
SIZE=$(r stats --mode raw-data --json | python3 -c 'import sys,json;print(json.load(sys.stdin)["total_size"])')
LIMIT=$((9*1024*1024*1024))
if [ "$SIZE" -gt "$LIMIT" ]; then
  echo "repo over budget: $SIZE > $LIMIT" >&2
  exit 1          # 由 systemd OnFailure 触发告警，本次不备份
fi
```

另外两条护栏：

- **单份体积也要设上限**：某天某个 dump 异常膨胀时，宁可这次不备也不要把额度一次吃掉。dump 完成后先比对本份与上一份的体积，超 2 倍就告警并跳过上传。
- **控制台仍要设「余额/费用预警」**：闸门防的是正常增长，预警防的是脚本被绕过或桶里混进别的对象。

## 5. 恢复怎么做（工具已逐个确认在位）

恢复分三档，从最常用到最极端。所有命令在**任意一台装了 restic 的机器**上都能跑，不要求原服务器还活着——这正是异地备份的意义。

### 5.1 准备（一次性，写进恢复手册）

```bash
export AWS_ACCESS_KEY_ID=<只读 AK>          # 恢复用只读凭据，平时不放在被备份的机器上
export AWS_SECRET_ACCESS_KEY=<只读 SK>
export RESTIC_REPOSITORY=s3:s3.cn-east-2.qiniucs.com/sv-backup
export RESTIC_PASSWORD_FILE=/root/.config/restic/pass   # 或交互输入 RESTIC_PASSWORD
alias r='restic -o s3.region=cn-east-2'
```

### 5.2 先看清有什么（不要盲恢复）

```bash
r snapshots                                  # 有哪几天、每份多大
r ls latest /var/backups/svbackup/dumps      # 最新一份里有哪些文件
r find --path '*highgo*'                     # 按名字找某个库的 dump
```

### 5.3 单文件直出（最常用，不落地整仓）

`restic dump` 把单个文件直接打到 stdout，恢复一个小库不需要先还原整个快照：

```bash
r dump latest /var/backups/svbackup/dumps/2026-10-31/mariadb-xc3_test.sql > /tmp/mariadb.sql
r dump latest /var/backups/svbackup/meta.tar.zst > /tmp/meta.tar.zst
```

需要整目录时用 `restic restore`：

```bash
r restore latest --target /tmp/restore --include /var/backups/svbackup/dumps/2026-10-31
```

### 5.4 逐库恢复命令（工具路径已实测存在）

| 库 | 恢复命令（容器内工具） | 注意 |
|---|---|---|
| MariaDB | `docker exec -i xc3-mariadb mysql -u<x> -p<y> xc3_test < mariadb.sql` | `mysql` 客户端在 `/usr/bin/mysql`（已确认） |
| HighGo | `docker exec -i xc3-highgo /opt/HighGo6.0.1-cluster/bin/pg_restore -U highgo -d xc3_test --clean --if-exists < highgo.dump` | `pg_restore` 已确认；需 `PGPASSWORD` |
| Vastbase | `docker exec -i xc3-vastbase /home/omm/vbdata/install/vastbase/bin/gs_restore -d xc3_test < vastbase.dump` | `gs_restore` 与 `pg_restore` 都在 |
| openGauss | `docker exec -i xc3-opengauss /usr/local/opengauss/bin/gs_restore -d xc3_test < og.dump` | 需以 DB 属主身份（`opengauss`）执行 |
| GaussDB | `docker exec -i xc3-gaussdb-kernel503 /opt/gaussdb/app/bin/gs_restore -d xc3_test < gdb.dump` | 需以 `omm` 身份 |
| SQL Server | `docker exec xc3-mssql /opt/mssql-tools18/bin/sqlcmd -C -Q "RESTORE DATABASE xc3_test FROM DISK='/var/opt/mssql/backup/x.bak' WITH REPLACE"` | 换库名恢复要加 `WITH MOVE`（逻辑文件名用 `RESTORE FILELISTONLY` 查） |
| OceanBase | `mysql -h127.0.0.1 -P25881 -u'xc3@test' -p<x> xc3_test < ob.sql` | 宿主 mysqldump 导出的，用宿主 mysql 客户端回灌 |

> 凭据见 `.local/test-databases.md`（不进仓）。上面用 `<x>/<y>` 占位，实际脚本从 `/etc/svbackup/credentials` 读，不写死在命令行（避免进 shell 历史）。

### 5.5 整机重建（服务商跑路 / 机器彻底没了）

这是本方案真正的验收场景，步骤固定为五步：

1. **新机器**：任意一台 Ubuntu，装 docker（`daemon.json` 里的国内镜像源在备份的 `meta.tar.zst` 里）。
2. **装 restic**：走「本地代理下载 → bz2 → SFTP → 解压」这条已验证的路（GitHub 在国内服务器普遍不通）。
3. **取回元数据**：`r dump latest /var/backups/svbackup/meta.tar.zst > meta.tar.zst && tar -xf meta.tar.zst`——里面有 `docker images --digests`、`docker inspect` 全量 JSON、各 `start.sh`、`daemon.json`、apt 源、crontab。
4. **按 digest 拉镜像、按 inspect 重建容器**（`start.sh` 可直接复跑，端口与挂载参数都在里面）。
5. **逐库 restore**，然后 `docker start` 验收连通性。

按 8 个库的体量，这套流程预期 30~60 分钟（大头是拉镜像，不是恢复数据）。

### 5.6 恢复演练（不做这一步，等于没备份）

- **每周自动**：`r check --read-data-subset=5%` + `r restore latest --target /tmp/verify --include /dumps`，比对文件数与大小。
- **每月人工**：抽一个小库（HighGo 或 MariaDB）真恢复到临时容器，`SELECT count(*)` 与生产比对。
- **每季度**：完整走一次 4.1.5 的整机重建，在另一台机器或本地 Docker 上做。

判据很直白：**演练没通过的那一天，你的备份就等于不存在**。

## 6. 「很容易丢数据」的根因排查（先定位再谈备份）

按本机画像的优先怀疑顺序：

| 顺位 | 根因 | 本机证据 | 检查方法 |
|---|---|---|---|
| 1 | **容器/卷生命周期** | mssql 无挂载（数据在写层）；其余多为 bind mount | `docker inspect -f '{{json .Mounts}}' $(docker ps -aq)`；`grep -Ei 'down -v\|volume rm\|rm -rf' ~/.bash_history` |
| 2 | **误操作** | 测试环境常态 | 同上 + 数据库日志里的 `DROP`/`corrupt` |
| 3 | ~~服务商生命周期~~ **已降级**（2026-10-31 用户确认：无快照能力、**永久使用**） | 非主流云、有厂商 root 级 agent；但**无到期/欠费回收层** | 只剩「服务商经营异常」这一类，本机侧看不出来 |
| 4 | 磁盘/宿主故障 | 无 SMART、单盘、`dmesg` 无 I/O error | `dmesg -T \| grep -Ei 'i/o error\|ext4-fs error\|remount-ro'`；`journalctl -k -p err` |
| 5 | 入侵 | **7 天 16.7 万次 SSH 失败** | `last`、`lastb`、`authorized_keys`、crontab、`ss -tlnp` |
| 6 | ~~快照回滚~~ **已排除**（用户确认该服务器没有任何快照能力） | 不存在快照则不可能被回滚 | — |

已排除的：本次 `dmesg` 只有一条正常的 ext4 挂载记录，无 I/O 错误；`last` 显示 19 天单次引导、无非计划重启；
**服务商侧无快照能力、账号为永久使用**（2026-10-31 用户确认）——因此「快照回滚」这一根因直接排除，
「到期/欠费回收」也不再成立，剩下的现实风险只有**容器/卷生命周期、误操作、入侵、宿主故障、服务商跑路**。

这个结论对方案有直接影响：**没有控制台快照，就没有「装坏了点一下回滚」这条退路**。所以本方案的逻辑导出
不是「多一层保险」，而是唯一可用的恢复手段——也正因如此，恢复演练（§5）从「建议做」变成「必须定期做」。

## 8. 与需求的一处口径修正

需求是「免费自动备份」。严格说，纯免费能覆盖的是**存储侧**：七牛 10GB 额度内 0 元。但下面几项成本是省不掉的，且都不是钱：

- **恢复流量**：只要真出一次事、把数据拉回来，就可能产生 6~10 元；
- **维护动作**：每周恢复演练、每季度确认额度与账号状态，这部分是人的时间；
- **服务商风险**：这台机器本身在小 IDC 上，「备份存在」不等于「服务能持续」，所以备份产物必须是**能迁到任意一家新服务器重建的形态**（逻辑 dump + digest + 配置，而不是整盘镜像）。

换句话说：**免费能做到「数据不丢」，但做不到「服务不中断」**。如果目标是后者，那是换云的事，不在备份方案范围内。
