# CI 从 Windows 换到 Linux 的提速空间与迁移成本调研

- 任务性质：只读调研（子代理执行），未修改任何代码
- 基线提交：`c48bcb90`（含 verifier-cli 随工件播种改造）
- 调研时间：2026-11-05
- 一句话结论：能换，但收益只有 **2~4 分钟（19.4 → 约 16~18 分钟，−10%~20%）**，不是数量级提升；代价是 **7 处硬阻塞**（其中 2 处会让整条腿必红）、约 12 个改动点、1~2 天迁移 + 2~3 轮验证，首轮缓存全冷（+5~10 分钟）。**混合方案因 GitHub 每仓库 10GB 缓存上限会与 Windows 缓存互踢，不划算。**

## 一、现状基线

### 1.1 Job 结构

| Job | 内容 |
|---|---|
| `build` | `:buildPlugin :verifyPlugin`（三目标离线验证）+ 导出 verifier-cli + 上传 build-outputs / plugin zip |
| `marketplace` | `:verifyMarketplace -PverifyOnly=true`（三目标在线、无豁免） |
| `verify`（matrix 3） | `:verifyGate -PverifyOnly=true -PverifyIdes=<243/253/262> -PgateStaggerMs=0` |
| `test`（matrix 5） | `:testShard<N>`，排除 `DataSourceJdbcSmokeTest` / `O147RealAgentAcceptanceTest` / `AttachPoolWarmGateTest` |
| `gate` | 聚合判定，`skipped` 判红 |
| `publish` | 发 Release，不跑 Gradle |

六个 job 全部 `runs-on: windows-latest`，所有 run 步骤 `shell: pwsh`。

### 1.3 CI 覆盖面（换 OS 前必须知道）

CI 的 `:testShard<N>` **不是**全量测试：

- `testShards` 聚合任务才依赖 `testExternal`（签名护栏）、`testShardTail`（性能计时类）和 `:sql-visualizer-agent:test`；CI 只跑 `:testShardN`，所以上述三类都不在 CI 内（CI 传的 `-PagentTestExclude` 实际是空转）。
- DB 集成 8 类、外部方言验证、`e2eFakeIde` 也都不在 CI。

这降低了 Linux 迁移的测试面风险，但也说明「CI 绿」不等于全量绿。

## 三、速度证据

### 3.1 有实测出处

| 事实 | 读数 | 出处 |
|---|---|---|
| 两边 runner 规格相同 | ubuntu-latest 2 vCPU / 8GB / 14GB SSD；windows-latest 同 | GitHub 官方 runner 文档 |
| Windows 侧缓存恢复 | 1m48~2m37（十 job 同起时 marketplace 曾 4m10） | run#10 / run#11 逐 step |
| 每片测试内部拆账 | 缓存 2 + 编译 2.75 + 测试 3.2 + 启动/配置 2（分钟） | 经验总结 §七.5 |
| 平台 bootstrap | 约 13s/JVM（6C12T Windows 本机） | `docs/变更记录/全量-2026-09-上半月.md:8` |
| Windows fork 开销被本仓实测点名 | 「大头是 Windows fork+classpath 而非解析」 | `O147HistoryUpgradeTest.kt:11,436` |
| 缓存 key 换新的保存代价 | Post 配置 Gradle 缓存 3.13 分钟（整份重存） | 经验总结 §七.4 |

**重要反证**：业界常引用的「Windows Defender 实时扫描拖慢构建」在 GitHub 托管 runner 上**不成立**——runner 镜像脚本已 `DisableRealtimeMonitoring = $true` 并把 `C:\`、`D:\` 全盘排除。不能把「Defender 税」算进本次收益。

### 3.2 公开 benchmark（仅作方向）

| 事实 | 数据 | 出处 |
|---|---|---|
| 大量小文件创建/遍历，Windows 比 Linux 慢约 4× | — | moby/moby#39954 |
| 进程创建 | Windows `CreateProcess` ~8ms vs Linux fork+exec ~0.28ms（2012 年旧机） | 博客，代差大 |
| Gradle 8.0 因 Windows/macOS 文件监听慢，改用自研 native watching | — | gradle.org/whats-new/gradle-8 |

这些说明方向（Linux 在元数据密集 IO 上更快），但**没有一个能直接换算成本仓库的分钟数**。

### 3.3 常识推断（非实测）

- Kotlin/Gradle 编译是 CPU + 小文件 IO 混合；2 vCPU 相同，CPU 项无收益，只能从 IO 拿 10~20%。
- 测试执行段（平台 bootstrap 要读上千个 jar）IO 占比高，估计 10~20%。
- verifyGate（离线字节码分析）几乎纯 CPU → 收益接近 0。
- marketplace（在线解析、下载插件元数据）几乎纯网络 → 收益接近 0。
- 缓存恢复是 zstd 解压 + 写盘，Linux 估计快 20~30%（约省 30~45 秒/job）。

### 3.4 为什么不能期待「快一倍」

关键路径的构成里，**在线门禁与缓存下载是网络/固定成本，OS 换不掉**。即使 IO 段全部快 30%，总墙钟也只能从 19.5 降到约 16.5。

**预期墙钟（模型估算，非实测）**：16~18 分钟（中位约 17），乐观 15，悲观 19~20（与现在持平）。首轮冷缓存 22~30 分钟。

## 四、缓存代价

### 4.1 换 OS 必然冷启动

`gradle/actions/setup-gradle@v5` 的缓存 key 包含 `RUNNER_OS`，换 `runs-on` 后现有约 9.6GB Windows 条目完全不可复用，首轮所有 job 都是 cache miss。

### 4.2 冷启动要重下多少

IDE 发行包是 OS 专属的（IPGP 默认 `useInstaller=true`，`ProductRelease.resolveDownload()` 按 `isWindows/isLinux` 选 `windowsZip` / `linux`）。从本机 `.intellijPlatform/productReleases/*.json` 解析出的三目标体积：

| IDE | Windows（现状缓存） | Linux（换后要下） |
|---|---|---|
| 2024.3.7.1（243，编译基准） | 1.61 GB | 1.59 GB |
| 2025.3.5（253） | 1.53 GB | 1.52 GB |
| 2026.2.4（262） | 1.64 GB | 1.63 GB |
| 合计 | 4.78 GB | 4.74 GB |

首轮「重下几次」：build ×1 约 6~7GB；test ×5 约 2.5GB × 5 ≈ 13GB；verify ×3 约 2.5GB × 3 ≈ 7.5GB；marketplace ×1 约 6GB —— **单轮总出口约 32~35GB，且 9 台 runner 同时拉**。按每台 20MB/s 估算，单 job 冷下载 2.5~6.5GB 约 2~5.5 分钟，叠加解包，首轮各腿 +3~7 分钟。

旁证：run#5 build 21.7 分钟（冷）vs run#10 8.1 分钟（暖）。

### 4.3 稳态是否等价

等价甚至略好：体积几乎相同（4.74 vs 4.78 GB），恢复时间取决于网络 + 解压 + 写盘，Linux 侧预计略快（省 30~45 秒/job）。唯一永久损失是 `-win` 目录名硬编码必须改，否则 verify/marketplace 直接红。

### 4.4 10GB 上限与两套 OS 缓存并存

官方口径：缓存默认每仓库 10GB；超额时按「最后访问时间」从最旧开始删；超过 7 天未访问的条目会被移除。

现状 Windows 侧已约 9.6GB。两套并存 ≈ 16~19GB > 10GB → 每次保存都触发淘汰，**谁最近没跑谁被踢**；两套 workflow 交替跑会形成互踢抖动，每轮都冷启动，收益全部吐回去。

结论：**缓存角度，全量迁移比混合迁移更干净。**

## 六、混合方案评估

结论：**不划算**，唯一值得留在 Windows 的是 `publish`（它不跑 Gradle、不碰缓存，留哪都一样）。

| 混合方案 | 缓存账 | 评价 |
|---|---|---|
| 只迁 test ×5 | Windows 仍需 3 IDE（~9.6GB），Linux 需编译基准（~6GB）→ 合计 >10GB → 互踢 | 缓存抖动吃掉全部收益 |
| 只迁 build + test | 仍双套 >10GB | 迁移面最小，但仍不推荐 |
| 只迁 verify/marketplace | 这两条腿恰是 `-win` + `powershell` 双硬阻塞所在，收益最低 | 最差组合 |
| **全量迁移** | 稳态单套 ~9.6GB，干净 | **推荐**（若一定要换） |
| 不迁（现状） | 无变化 | 若目标只是「再快几分钟」，不如继续压 test/marketplace 的固定成本 |

隐性成本：两套 workflow 的 job 名/矩阵/缓存 key 都要各自维护，后续改门禁要改两遍。
