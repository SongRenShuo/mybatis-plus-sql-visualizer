## 二、新缺陷 UI-049（P2）：绑定探针「失败」被当成「确定未绑定」

同一时刻的日志里还有这一行（照录）：

```
08:29:57,432 INFO - #…ExecFileBinding - [T-ConsoleBind] probe per-file mapping FAILED
(treat as unmapped): ClassNotFoundException:
com.intellij.database.dataSource.DataSourcePerFileMappingsImpl PluginClassLoader(…)
```

问题链：
1. `ExecFileBinding.probeExecBind` 内部 `runCatching{…}.onFailure{ LOG … }.getOrNull()`，反射失败时**返回 `ExecBindProbe(null, null)`**——与「真的没有 pin」**返回值完全相同**。
2. UI-048 的生产入口按 `probeExecBind(project, file).pinnedDsId != null` 判定，于是**探针失败 ≡ 未绑定**，`boundToDataSource` 拿到的是 `false` 而不是设计注释里说的 `null`（未知）。
3. 后果：在缺这个平台反射类的构建上，只要 `runners=0` 就一律落在「未绑定」档——**即使文件其实已绑定**。本轮这个状态下判断恰好正确（确实未绑定），但机制不成立：它又是一次「把没验证的推测当事实」，只是方向反过来了。

证据等级：**日志可判 + 静态面**（`ExecDialectRouting.kt:377-393` 的 `bound` 计算 + `ExecFileBinding.kt:192-210` 的 `getOrNull()`）。真机上「已绑定但被误报未绑定」这一形态本轮**未复现**（本环境造不出已绑定态），故按静态面登记，不外推。

修法（下轮实施）：
- 探针改为三态：`BOUND / UNBOUND / UNKNOWN`（或让 `ExecBindProbe` 带 `probeOk`），反射失败/类缺失一律 `UNKNOWN`；
- `classifyEmptyRunners` 的 `boundToDataSource` 只在 `BOUND/UNBOUND` 时取 true/false，`UNKNOWN` 传 `null` 退回既有口径；
- 用例要能区分这两条：`probeExecBind` 抛/降级 → UNKNOWN（不得落到未绑定档）；真 unbind → UNBOUND。反向验证两次读数。
