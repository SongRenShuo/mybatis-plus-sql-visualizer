## 二、回归的发现与修复（本轮的真正价值）

**第一版修复（`ba314f42`）引入了一个新断言**：异步回调用了 `invokeLater(onReady, ModalityState.any())`，而 `any()` 不是 write-safe 模态，续接链的 `consoleDoc.setText` + `commitDocument` + `saveDocument` 失去写资格 → 平台报 `TransactionGuard write-unsafe`，且频率随每次点执行计划线性增长。

**发现方式**：时间戳一一对应（`16:41:44.503 explainSql → 16:41:44.589 TxGuard`、`16:48:03.891 → 16:48:04.777`、`16:53:49.216 → 16:53:49.702`），并与历史基线（8 次 / 整份日志）对比判定为回归。

**修复（`86d70744`）**：改 `ModalityState.nonModal()`。依据是 243 平台字节码实证——`TransactionGuardImpl.<init>` 里 `put(ModalityState.nonModal(), TRUE)`，**只有 nonModal 在构造期被登记为 write-safe**；`wrapLaterInvocation` 产出的 `$1.run` 仅在 `isWriteSafeModality(模态)` 为真时才 `runWithWritingAllowed`。`submitTransaction` 系列在 243 已全部 `Deprecated`，故不走。

**附带修正**：非 EDT 防御分支原先由后台线程直接承接 `onReady`（弹窗越线程、文档写同样无资格），一并改为「慢段就地跑、回调经 write-safe 投递回 EDT」。

## 三、守卫（防再犯）

新增 `ExecTempFileEdtGuardTest` 规则五：`createTempPsiFileAsync` 内**每个** `onReady(` 调用点必须落在 `invokeLater(…, ModalityState.nonModal())` 或 `DocWriteContext.invokeLaterWriteSafe` / `submitTransaction` 之内，且函数体不得出现 `ModalityState.any()`；实参区按**括号配平**取（不用固定窗口，避免跨界假绿）。四态自证：`any()` 必红、省略模态必红、`nonModal` 放行、`invokeLaterWriteSafe` 放行。

行为断言（headless 下有判别力，非摆设）：回调内 `TransactionGuard.isWritingAllowed()` 必须为 true；`any()` 下实测为 false。

**既有守卫为什么没抓到**：`BannedApiScanRuleTest.anyModalityWriteOffenders` 只认**直接**写令牌（`setText(`/`commitDocument(`）出现在 any() 回调里，看不见 `invokeLater { callback(…) }` 这种**间接**形态——`onReady` 不在写令牌表内，所以上一版该守卫全绿而真机必报。
