## 一、D1 T-MapperMethodSqlPreview（Mapper 接口方法行 SQL 预览）

> 设计意图：Mapper 接口方法行此前只有「跳转 XML」一枚图标；本批在同一行补「预览该方法绑定的 SQL」图标，两枚并列（**预览在左、跳转在右**）。预览链路与 XML 语句行点击**逐字节一致**（同一个 `XmlSqlGutterLineMarkerProvider.previewStatementTag`）。

**推荐夹具**：`mybatis-plus-demo/src/main/java/cn/song/mybatisplusdemo/mapper/UserMapper.java:126` 的 `selectUserListByXml`，对应 `mybatis-plus-demo/src/main/resources/mapper/UserMapper.xml:25` 的同名 `<select>`（内含 `<include refid="Base_Column_List"/>` 与 `<if>` 动态条件）。

### A1 方法行两枚图标

**路径**：`UserMapper.java` 方法名 `selectUserListByXml` 的行号槽。
**步骤**：① 光标停在方法名上（不必选中）；② 分别悬停左右两枚图标看提示。
**期望**：行号槽出现**两枚**图标；左侧提示「SQL Visualizer：预览该方法绑定的 SQL」，右侧提示「跳转到 Mapper XML 语句」。
**判读**：只有一枚或零枚即不通过；顺序反了记缺陷（阅读顺序契约＝预览在左）。

### A2 点左图标出预览，且与 XML 语句行一致

**步骤**：① 点左侧预览图标，记下弹窗里的产物 SQL、参数表、`<include>` 展开结果；② 打开 `UserMapper.xml`，点第 25 行 `<select id="selectUserListByXml">` 的预览图标，比对两侧。
**期望**：两处产物**逐字节一致**——`<include>` 已展开成列清单、`<if>` 条件行可勾选、`${}` 段有模拟值提示；来源行号标注指向 XML 语句所在行。
**判读**：任意一处内容差异即不通过（设计上是同一条渲染链，不该有两个版本）。

### A3 同类插件共存「让位」只吃跳转、不吃预览

**路径**：同上方法行 + XML 语句行。
**步骤**：
1. 安装并启用任一同类插件（MyBatisX / MyBatisCodeHelperPro / MyBatisPlus）；

3. 看 `UserMapper.xml` 语句行；
4. 把该设置项**取消勾选**，再看两处。
**期望**：
- ② 方法行**只剩左侧预览图标**，右侧跳转消失（对方插件在同一位置画自己的箭头）；
- ③ XML 语句行**本插件零图标**（这行整体让位，属设计行为，不是缺陷——别登记成 bug）；
- ④ 两处图标全部回来。
**回退开关**：设置项「与同类 MyBatis 导航插件共存时让出 XML 与 Mapper 跳转图标」（`mapperNavYieldToCodeHelper`，默认开）。

## 二、D2 T-EpAttachBeforeCapture（先启动的那个控制台也要捕获）

> 缺陷机理（`SqlConsoleBridgeFilterProvider.kt:25-31` 的 KDoc 原文）：旧实现在 `getDefaultFilters` 里判「捕获服务未创建」就返回空数组 → **捕获开启前创建的旧控制台永远没有 EP**；而桥在捕获开启后会把 `SqlCaptureGate.epActive`（进程级）置位，旧控制台的桥随即被全局短路、又无 EP 兜底 → 旧控制台零产出。用户现象＝「两个应用单独都能捕获，并存只剩后启动的那个」。修复后 `getDefaultFilters` **恒返回 Filter**，Filter 内部惰性取 manager（`:44-51`、`:60`）。

### B1 双应用并存：两侧都收到

**路径**：右侧边栏 → SQL Visualizer → 「SQL 日志」页签 → 工具栏「**捕捉**」按钮（注意按钮文案是「捕捉」，不是「开始捕获」；无运行控制台时按钮下会显示「等待中...」）。
**步骤**（顺序不能颠倒，这是本项的全部意义）：
1. 只启动应用 A（`mybatis-plus-demo`，8081），确认控制台已有 SQL 日志输出；
2. 在 SQL 日志面板点「捕捉」；
3. 再启动应用 B（`mybatis-plus-join-demo`，8082）；
4. 两边各打一条会执行 SQL 的请求：A 打 `GET http://127.0.0.1:8081/pageSim/xmlPage`，B 打 `GET http://127.0.0.1:8082/mpj/queryWrapperString`（或任一已注册的 MPJ 端点）；
5. 回到 SQL 日志面板看列表。
**期望**：列表里**同时有 A 与 B 两侧的 SQL**（A 侧标签/连接名与 B 侧可区分）；列表条数随两侧请求增长。
**判读**：A（先启动那个）零条＝修复未生效，直接登记不通过。修复前症状就是这一侧全空。
**回退开关**：无独立开关（这是装配时序修复，不是特性开关）；临时回退＝停用「捕捉」。

### B2 捕获关闭时零副作用（负例）

**步骤**：不点「捕捉」（或点第二次停掉捕获），两个应用继续打请求。
**期望**：SQL 日志面板不新增条目；IDE 无报错，控制台输出本身不受影响（插件不吞控制台内容）。
**判读**：控制台出现插件异常栈或行丢失＝不通过（惰性 Filter 在未拿到 manager 时应当是零处理）。

### B3 单应用回归

**步骤**：只启动一个应用、点「捕捉」、打一条 SQL。
**期望**：照旧捕获（不能为了修双应用把单应用弄坏）。
**判读**：本条是回归哨兵，单独失败说明 Filter 惰性装配有副作用。

## 三、D3 T-ServiceJoinWrapperPreview 的 F14 缺口定谳

> 背景：现场自研 Wrapper 四层链 `CustomJoinWrapper → AbstractLambdaJoinBaseWrapper → AbstractJoinBaseWrapper → BaseWrapper → MPJLambdaWrapper`。计划册 F14（`docs/开发计划/20261123-1305-...-开发计划.md:48`）当时写「截图只显示 `AbstractJoinBaseWrapper extends BaseWrapper<T>`，`BaseWrapper<T>` 自身的 `extends/implements` 未给 → 待用户补一行类声明」。

### C1 F14 结论（已覆盖、可销）

**结论**：**已被四层同构语料覆盖，不再阻塞**；且覆盖路径**不是**「链方法启发兜底」，而是**父链 FQN 规则（最强证据）**直接命中。

**证据链**：

| # | 证据 | 位置 |
|---|---|---|
| 1 | demo 语料补齐了 F14 缺的那一行：`public abstract class BaseWrapper<T> extends MPJLambdaWrapper<T>` | `mybatis-plus-sql-visualizer-demo/custom-wrapper-demo/src/main/java/cn/song/customwrapperdemo/customwrapper/BaseWrapper.java:12` |
| 2 | 四层声明齐全且与现场同构（README 原文链） | 同目录 `AbstractJoinBaseWrapper.java`、`AbstractLambdaJoinBaseWrapper.java`、`CustomJoinWrapper.java`；`custom-wrapper-demo/README.md:11` |
| 3 | 判定顺序第一条即返回 `MPJ_LAMBDA`：任一祖先 canonicalText 以 `com.github.yulichang.` 开头 | `psi/WrapperLocator.kt:1866` 附近 `classifySuperChain` 首个 `if`；`MPJ_FQN_PREFIX` 常量定义在 `:1771` |
| 4 | 该形态有定向用例钉住（同一四层链 + 假 MPJ 基类 → 断言 `MPJ_LAMBDA`） | `src/test/kotlin/.../psi/WrapperTypeSuperChainTest.kt:78-105` `testUserFourLayerCustomChainResolvesToMpjLambda` |
| 5 | 「父链完全接不到 MP/MPJ」的兜底也有用例（链上有 `leftJoin` → 认作 MPJ wrapper） | 同文件 `:286-300` `testChainMethodHeuristicJoinMethodsResolveToMpjLambda` |

**为什么说「不阻塞」而不是「零风险」**：规则 4（链方法启发）是**变量级**判定，跑在 `WrapperLocator.isWrapperVariable`（`:329`），并已被 `WrapperAnchorDetector.anchorElement` 场景 B 复用（`:100-105`，变量声明行锚点）；所以即使现场 `BaseWrapper` 真身不接 MPJ，声明行的预览图标仍能靠规则 4 出来。唯一严格走类型级的是场景 A 的 `new` 关键字锚点（`WrapperAnchorDetector.kt:113`），但同一变量声明行已由场景 B 去重覆盖，用户可见面不受影响。

**保留一条现场核对（非阻塞）**：demo 语料是我们按现场形态复刻的等价物（README 自述「结构等价复刻，类名、方法名与业务语义均已脱敏」），其 `extends MPJLambdaWrapper` 属复刻假设而非用户原始截图证据。若用户侧真身不同（例如接到别的 ORM），类型级规则 1 不成立、只剩规则 4 的变量级兜底——功能可用但锚点覆盖面略窄。**一行真实声明即可彻底定谳，不建议再当阻塞项挂着。**
