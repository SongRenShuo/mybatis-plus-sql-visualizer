## 已实证的历史缺口与修复

buffer 融合分支更新内存后返回 false，没有触发 `onEntryStored`；manager 自动保存只订阅首次入队回调。真实事件复现：JDK17 console-first 内存 `MERGED / O147JdbcApp.java:51 / 7ms / H2`，历史却是 `CONSOLE_BRIDGE / null:0 / null / null`；agent-first 内存 MERGED，历史仍 AGENT。手动把融合快照交给 saver 的对照测试通过，说明缺口是生产回调接线，不是仅 codec 格式问题。

修复增加独立 `onEntryMerged(old, merged)`，保持首次入队回调、重复计数、序号、SQL 原文和参数不变。manager 将升级投递自动保存线程。历史不原位改写：只为有捕获来源的条目写随机 ID，融合追加 `-- pd: o147-revision:` 注释，Reader 按 ID + 原始/还原 SQL、参数、首次时间的 SHA-256 校验后补元数据。UNKNOWN/MCP 既有格式不扩大。

曾试原位原子替换，相关用例虽绿，但最终检查到 rename 之间仍有外部非协作写 TOCTOU，不能当 CAS。该实现已撤除，最终代码只追加、不覆盖原字节。旧 Reader 会把不认识的 pd 扩展保留为 SQL 注释，执行语义不变，但旧 UI 可能显示额外注释；不宣称回滚展示完全无变化。

安全边界：

- 写端最多追踪 2048 个实例，满额逐个淘汰最旧，不整批清空。融合回调可能先于首次存储回调到达：有界等待表按原实例串联修订，最多2048项/60秒，store到达才补修订；未知实例不制造文件，close/config清空等待。超出写索引或等待预算的条目保留原历史，可能缺部分后到元数据，不宣称无限规模保真。配置切换后、文件删除/替换后不补写。文件系统不给 fileKey 时以创建时间辅助核对；Windows 创建时间隧道已在专项中实证导致误认，故再查本实例 UUID 标记，不仅靠时间。
- 修订单条 Base64 ≤64KiB，单次读取最多 2048 条、总修订文本 ≤8MiB。文件读取遇超限修订逐字符丢弃余段，不先分配任意长度载荷；坏编码、未知 ID、摘要不符不制造条目。超过修订预算时保留原条目，部分元数据不回填；专项以2048条坏修订耗尽预算，确认后续有效修订被忽略且四入口仍只有一个原始条目。
- 修订只能补融合元数据；SQL 主体、参数、捕获时间、条目顺序来自原块。原文被外部改动后摘要不符，修订失效。

## 独立复核后补强：预算一致性与写侧内存上限

复核发现两处 blocker：超长修订在文件读取中折叠为裸前缀并计数，`parseContent` 的完整超长行却在计数前丢弃；以及 UUID 搜索仍用 `readLine`、修订序列化完整生成后才检查64KiB，内存上限形同虚设。

本次改为：

- 所有入口对超长修订统一收取一次计数和前缀长度成本，再丢弃载荷。用原块＋2048条超长修订＋合法修订，对照 String/Sequence/readFromFile/forEachEntry 和 count。

## CRLF 精确临界复核

再次复核发现：文件读取在剥尾 CR 之前判断修订行是否超过65686字符，而 String 的 lineSequence 已剥除 CRLF，导致逻辑长度恰65686的修订在文件端按超长前缀计费，在字符串端却按完整长度计费。2048条该类行后的小合法修订，可能因此在不同入口产生不同融合结果。

本次仅修该边界，补65686/65687字符×LF/CRLF四格，每格2048条无效修订后接一个有效修订，核对 String、Sequence、readFromFile、forEachEntry 与 count。同步保留主控对大夹具的 `old=entry().copy(executionTimeMs=0L)` 调整，使整份大文本保持ASCII，避免U+2014迫使Java String转UTF16；不缩小样本，不覆盖回原写法。

先红四格 **4/1/0/0**，仅65686+CRLF失败，String结果MERGED而文件结果CONSOLE_BRIDGE，日志 `call_tfOZRcZ5E8pqtgEMnqWSbYoz-stdout.log`。修复以剥单个尾CR后的逻辑长度判阈值：末尾CR暂宽限一个字符，若后续不是LF/EOF它会重新计费；普通SQL不走修订截断分支。修复后只跑这四格＋既有超长预算四入口、坏修订四入口、数量预算/未知ID、大SQL不截断，共 **8/0/0/0**（默认512MiB，1m38s），日志 `call_qvrIvXWwbnnKm9pil45F8k3C-stdout.log`。目标命令仍为 `run-o147.ps1 -Label crlf-boundary-fixed -Tests <8个具体方法>`，方法分别为 `exactRevisionLimitLfAgreesAcrossAllReaders`、`exactRevisionLimitCrLfAgreesAcrossAllReaders`、`overRevisionLimitLfAgreesAcrossAllReaders`、`overRevisionLimitCrLfAgreesAcrossAllReaders`、`oversizedRevisionBudgetAgreesAcrossAllReaders`、`allReaderEntrypointsAgreeAndMalformedRevisionsDoNotCreateRows`、`revisionCountLimitAndUnknownIdDoNotInventEntries`、`normalSaveDoesNotTruncateLargeSqlOrMetadata`（均位于 `cn.song.mybatisplus.visualizer.log.O147HistoryUpgradeTest`）。没有重跑其他类、真实JVM、全量或构建校验；此前216读数仅保留为当时版本证据。
