## 2. 构建与运行命令

| 命令 | 用途 |
|---|---|
| `./gradlew runIde` | 启动沙盒 IDE（日常验证 UI；注意：日常 IDE 加载的是已发布旧 jar，新改动须在沙盒验证） |

| `./gradlew testShards` | **全量测试推荐入口**：测试类按时长均衡自动分片，默认 5 片（`-PtestShardCount=N`，上限 6，`mpv-testing.gradle.kts:159` 的 `?: 5`；5 片定案依据见同文件顶部 T-TestPerf4/5/7 注释），各片使用独立沙盒（并行运行时互不踩 PersistentFS）；跑完自动打印各片与总数聚合报告（含「预期 vs 实测」对照与计划类并集 parity 校验）。含 testExternal 外部分离桶（6 类）与 `:sql-visualizer-agent:test`（178 例）；auto-handicap 缺省开（`?: true`，`-PtestShardAutoHandicap=false` 关闭退路）；头部巨类方法级跨片拆分**默认关**（`?: false`，`-PtestSplitHeavy=true` 显式开启——T-TestPerf10 S3 处置：执行侧 filter 间歇失效致片段重复执行、SHARD TOTAL 虚胖，收益仅临界片 −1~3s，判为负 EV，故转 opt-in）。**前置**：需要兄弟目录 `../mybatis-plus-sql-visualizer-demo`（5 个 `Demo*` 用例硬断言 demo 源码），先跑 `dev-support/test-demo/setup-test-env.ps1`（或 `.sh`）。**注意**：Gradle 不并行同一项目内的任务，5 个分片任务实测严格串行（测试段 826s）；要墙钟提速用下方并行运行器 |

| `powershell -File dev-support/test-demo/setup-test-env.ps1` / `bash dev-support/test-demo/setup-test-env.sh` | 准备全量测试前置：检出钉定版本的测试 demo（独立仓库 `mybatis-plus-sql-visualizer-demo`）、校验测试读取的文件、安装 `.idea/dataSources*.xml` 模板，并在 `mysql` 客户端可用时建库执行 SQL；`-CheckOnly` / `CHECK_ONLY=1` 只检查不改环境 |
| `./gradlew testShard1` … `testShard5` | 单跑某一片（一般无需单独跑；单跑会重写时长权重表，改变后续分片组成） |
| `./gradlew test --tests "cn.song.mybatisplus.visualizer.reverse.*"` | 定向测试（按包/类过滤）；**判据看 XML 类数**——过滤式匹配不上时 Gradle 会静默跳过仍 BUILD SUCCESSFUL |
| `./gradlew releaseGate` | **发版链路一命令（T-ReleasePerf / T-MarketCompatFix / T-AgentResiduals R7）：buildPlugin → verifyGate（三目标兼容门禁）→ verifyMarketplace（Marketplace 同口径在线判定）→ testShards（全量）→ e2eFakeIde（真机级端到端探针，需本机 MySQL + demo 工程）**；任一环失败即停，BUILD SUCCESSFUL 即全关通过 |
| `./gradlew verifyGate` | 权威兼容门禁（直驱 verifier-cli，离线 + 豁免清单；默认三目标 243+253+262，实测 3m06s；`-PverifyIdes=minimal`=243+262、`-PverifyOnly=true` 复用已存在 zip） |
| `./gradlew verifyMarketplace` | Marketplace 同口径在线判定（无豁免、按 verdict 文本判失败）：补上「离线 verifyGate 全绿但 Marketplace 判 Critical」的系统性缺口（2026-09-23 实测 7 目标 6 判 Critical 即由此而来） |
| `./gradlew e2eFakeIde` | 真机级端到端探针（假 IDE + `-javaagent` 注入真 Spring Boot/MPJ 应用）；前置＝本机 MySQL 127.0.0.1:3306（`mpj_demo`，脚本 `dev-support/test-demo/db/mpj_demo.sql`）+ demo 工程 + `~/.m2` 离线依赖，可用 `-Pe2eDemoDir=`/`-Pe2eMvn=` 覆盖路径 |
| `./gradlew verifySmoke` / `verifyFull` | 门禁快捷档：仅 243 / 三目标（均走 verifyGate） |
| `./gradlew verifyPlugin` | 兼容性**报告**生成器（IPGP 封装，判定缺陷字节码实证已降级；不再承担门禁）。注意它用的 verifier 版本（IPGP 自带依赖，1.410）与 verifyGate（caches 字典序取 1.409）不同；已配 `-Dplugin.verifier.home.dir` 与 verifyGate 共用 `build/verify-home`（T-VerifierHomeIso：1.410 在缺省 home `~/.pluginVerifier` 下提取插件 zip 恒败） |
| `./gradlew writeUpdateManifest` | 生成 `update/update.json`（Gitee 抢先体验检查源；`preview.update.json` 为草稿，发布时同步） |

### 2.1 runIde 沙盒版本切换（录制态 / 高版本调试）

**隔离性**：沙盒与日常 IDE 完全隔离——数据在项目目录 `.intellijPlatform/sandbox/mybatis-plus-sql-visualizer/IU-<版本>/`（自带 config/system），从不读取个人 IDE 的 `%APPDATA%\JetBrains\IntelliJIdea*`。沙盒里只有插件本体 + build.gradle.kts 声明的 bundled 插件依赖（java/kotlin/database/diagram）+ 全新默认设置，个人插件/设置不会出现，除非在沙盒内主动开启 Settings Sync；新版本首次启动须激活 Ultimate（登录 JetBrains 账号）。

**切成 2026.2 录制态**（2026-09-11 起改用内置开关，**不再手工改 `build.gradle.kts`**）：

```bash
./gradlew runIde -PgifRecord=true     # 跑前先查并行登记表，见第 6 节
```

`-PgifRecord` 是承接 T-GifFullscreen 录制需求内置的属性开关，**一条参数整体切换四处**，无需再手工改脚本、也无需用完 `git checkout` 还原：

| 开关项 | 不带参数 = 243 常规态（默认） | `-PgifRecord=true` = 262 录制态 |
|---|---|---|
| 构建平台 | `intellijIdeaUltimate("2024.3.7.1")` | `"2026.2.1"` |
| 捆绑插件 | 不声明 | `bundledPlugin("com.intellij.modules.jcef")` |
| Kotlin toolchain | `jvmToolchain(17)` | `jvmToolchain(24)` |
| runIde 沙盒 | `.intellijPlatform/sandbox/mybatis-plus-sql-visualizer/IU-2024.3.7.1` | `build/MPSV-GifFresh` |

四项**必须整体切换、不可拆**：JCEF 自 262 起才从平台核心拆为独立模块（243 distro 无此模块，单独声明会依赖解析失败）；`jvmToolchain(24)` 用于读 262 平台 v69 类文件（javac 17/21 报「错误的版本 69.0」）。开关默认值**不落实际属性**，不带参数即为 243 常规开发态。

> 两点提醒：①**录制态下 test 源码编译不过**（262 把 `com.intellij.diagram.*` 移入 Database 插件而测试 classpath 未含，且新版 Kotlin 将 `String.toLowerCase()` 升为硬错误）——该态只用于 runIde 录屏，不要在该态跑 `./gradlew test`，用完随手 `clean` 掉 262 产物；②`-PgifRecord=true` 与 `buildPlugin` / `publishPlugin` / `publish` 同用会被脚本内的闸门在配置期直接拒绝，防止 262 录制态流入发行产物。
>
> 相关：`-PplatformVersion` 仍未接线、不可用（要切平台请用 `-PgifRecord`；若想长期支持 `-PplatformVersion`，按 IPGP parametrize 写法把 `intellijIdeaUltimate(...)` 改读 `providers.gradleProperty("platformVersion")`）。

**注意事项**：

- 沙盒按版本分目录（`IU-2024.3.7.1` / `IU-2026.2.1` 等），切回互不影响；新版本首次启动下载发行版约 2GB（gradle.properties 已配代理），用完可删对应 `IU-*` 目录省空间；
- 兼容性已确认：插件 sinceBuild=243，且最新发行版（当前 2026.2.3，随本机 IDE 升级在 T-VerifyIde2623 追平）本就在 verifyPlugin 验证目标内（`pluginVerification { ides { ... } }` 里三个 `create(IntelliJPlatformType.IntellijIdeaUltimate, ...)`，见 build.gradle.kts）；
- 耦合点：`testDatabase` 任务 doFirst 写死从 `IU-2024.3.7.1` 沙盒复制 jdbc-drivers（该任务定义内多处引用固定 `IU-2024.3.7.1` 字符串，grep `IU-2024.3.7.1` 定位；这几处是**固定版本路径**、与构建平台无关），版本切走后路径缺失会静默跳过——跑 testDatabase 前先切回原版本。

## 3. 测试体系

### 3.1 三类测试风格（无自定义测试基类）

| 风格 | 继承/形式 | 适用场景 | 数量（文件口径，2026-10-27） |
|---|---|---|---|
| 纯 JUnit | `org.junit.Test` | 零 IDE fixture 的纯逻辑：模型、生成器、解析器、方言、OGNL、缓冲、分享格式化、MCP 工具纯函数核心、CRUD 生成、真实场景回环、原生图适配层、agent 事件适配与捕获门 | 395 |
| Light | `BasePlatformTestCase` | 单文件 PSI/编辑器/面板行为，fixture 全用三引号内联文本（无 testData 目录） | 360 |
| Heavy | `HeavyPlatformTestCase` | 需要真实项目模型/索引/多模块/全局状态的重型场景（反向实体候选、文件索引、端到端） | 21 |

> 三档互斥（21 + 360 + 395 = 776，与磁盘 `*Test.kt` 总数一致）；2 个文件同时出现 `HeavyPlatformTestCase` 与 `BasePlatformTestCase` 字样（一处是 KDoc 里提到基类名），已按实际继承归入 Heavy。

**fixture 约定**：

- **无 testData 目录**——所有 fixture 用 Kotlin 三引号字符串内联（`configureByText("Entity.java", """…""")`）。
- 测试模型表统一用 `car_device_info`（对齐 README 示例）。
- 纯逻辑测试在 KDoc 注明「纯 JUnit / 无 PSI / 零 IDE fixture」。
- Light 测试不可测 DataContext/performTypingAction（headless 限制）；内嵌编辑器补全（非项目文件）需 `UiCompatibleDataProvider` 包装（2025.3+ 平台陷阱）。
- **UI 交互测试**（F-44 系列沉淀）：headless 下 `JCheckBox.setSelected` 不触发 ActionEvent，须 `doClick()`；`invokeAndWait{空任务}` 泵不动 `invokeLater` 队列，须 `UIUtil.dispatchAllInvocationEvents()`；`BasePlatformTestCase` 同类方法共享临时项目目录且残留不清，每个测试 setUp 自清理。
- 生产代码为可测性暴露 `internal` 接缝（sealed class + resolve* 函数，如 `LogJumpTarget` / `HistoryJumpTarget` / `resolveEntryJump`），是本仓认可的「生产可测化重构」模式。
- **脆弱前置与假失败新形态**（2026-09-19 增补）：①平台 LazyInstanceHolder 服务毒化——服务创建异常被 catch(Throwable) 无过滤收进 CannotInitialize 缓存，该服务在该项目实例上永久重抛（旁证=catch 时 isDisposed=false 而消息是 disposed）；②light 测试项目同分片 JVM 共享 ProjectImpl，项目服务可变状态跨类串台——修法=`SqlLogManagerProjectState`（testutil/）capture/restore 复位缝 + `SqlLogManager.restoreCaptureStateForTest`；③分片读数必须读聚合报告——单独跑一片会重写时长权重表，改变后续分片组成；④ADE 排障用 `AlreadyDisposedDiagnostics`（testutil/）：补片号/触发点/服务/线程/项目态后同类型重抛。
- **测试基础设施**：`testutil/` 辅助类（FakeClipboard、AlreadyDisposedDiagnostics、SqlLogManagerProjectState）；`execute/` 夹具 DbIntegrationProjectSupport / DbIntegrationSeedSupport；`xml/fidelity/` 真引擎对照集 RealEngineFidelityTest + RealEngineDriver（34 场景真 MyBatis 3.5.19 语义对照、28 场景逐字节一致；mybatis 经 mp-core 传递已在测试 classpath，「零 mybatis 依赖」红线仅约束 implementation）+ 零真引擎依赖的自洽钉 RealEngineCardinalityTest（占位符计数 ↔ 参数映射条数的场景域对账，与真引擎侧两侧登记）。
- **约定守卫测试族**（T-TestGuard，2026-09-14）：把「编译通过、单测全绿、只有真机/特定发行版才炸」的历史坑固化为结构性断言，全部 headless 零平台依赖——
  - `i18n/BundleParityGuardTest`：中英 bundle key 全等（m41 缺键回退英文案）、占位符规范（`__X__` 自定义占位符永禁；含 `{n}` 的模板值禁混入非数字占位符）、源码/plugin.xml 字面量 key 存在性；
  - `config/PluginXmlStructureGuardTest`：META-INF 全部 xml 剥注释后负向断言——`<listener topic=`、action 缺 class、description 外链 img、projectConfigurable 套娃、completion.contributor 缺 language、notificationGroup displayName、toolWindow title、codeInsight.inlayProvider 缺 language/implementationClass 或实现类非预期（O-44b，243 sources 核实的 `@RequiredElement`：缺属性即插件加载报错）；
  - `convention/BannedApiSourceScanTest`：src/main 剥注释扫描——ActionToolbar 沙盒不可靠刷新 API、IPGP 裁剪平台类（JBIconButton 族/IconUtil）、BrowserUtil.browse 必须自带 isUnitTestMode 短路（新调用走 `util.SafeBrowser`）、createFileFromText 必须同文件含 ReadAction；豁免表按「文件+站点数+理由」登记（禁行号级白名单，会漂移）。后续新规则：catch(Throwable) 须含 `FatalErrors.isFatal` 调用或豁免登记；psiCapture 规则（豁免表 + `// psi-capture:` 标注）；初始化入口写项目服务级状态须复位（按 `getService(`/`projectService(` 绑定形态认承接名，复位判定跟绑定走）；

### 3.4 EDT 与 PSI 读取红线（T-M44 真机实证，2026-08-16）

**UI 回调（elementChosen / treeSelection / ListCellRenderer / mouseClicked 等）里的任何 PSI 属性读取
（`name` / `qualifiedName` / `getIcon` / `containingFile`）必须包 `ReadAction.compute`**（EDT 上同步执行、
语义不变）——这些属性不是纯字段读取，暗含 stub 树访问（`getStubTreeOrFileElement` / `ensureParsed`），
IDEA 2026.2 在 EDT 上硬抛 `RuntimeExceptionWithAttachments`（用户真机双实证：`createEditor` 的
`createFileFromText`、`ClassPickerField.elementChosen` 的 `getQualifiedName`）。

**headless 测试测不到这类问题**：unit test 模式关闭线程断言（`isUnitTestMode`）+ 测试缝（pickForTest 等）
绕过真实回调 + 无真实 AWT EDT 派发——验证只能 runIde 沙盒或用户真机。审计 UI 链路时把 PSI 属性读取
一律视为 stub 访问，不要判「轻量」；改动此类路径后跑沙盒实测（计划里的「沙盒兜底」要真的做）。

**跨线程 PSI 读取走 PsiSnapshot 两段式捕获协议**（VirtualFile + Document + offset + modificationStamp
三项校验）：`SqlGutterLineMarkerProvider` / `StringSqlMethodGutterLineMarkerProvider` 两个 gutter
provider 已接入，新增跨线程 PSI 读取点须照此办理；协议详见同目录《PSI跨线程读取协议.md》。

**EDT 上同样禁止做文件 I/O**（T-PreviewChainNoise，`9809a5b7` 实测）：`VirtualFile.inputStream` /
`document.setText` 这类调用在 EDT 上会触发平台慢操作断言，日志里表现为 `Plugin to blame: SQL Visualizer`
的 SEVERE。预览执行链曾有一处 EDT 读盘，改造后的读数从 9 条 SEVERE 降到 0。同批收口的另两类：
阻塞式 API（`createBlocking`）在裸池线程上缺进度上下文会打 SEVERE，须补 `EmptyProgressIndicator`；
注册在父 disposable 上的子监听不要在 `dispose()` 里手动二次摘除（ObjectTree 后序子先父后，二次摘会
抛「Can't remove document listener」）。三类共性是**只有 runIde 沙盒与真机才暴露**，headless 测试全绿

### 4.2.1 方言语义探针的区分力要求（必读，T-GaussDbDialect 券 03 教训）

**方言语义探针必须用多行源。单行源对 offset 类语义没有区分力，读数必然是同义的。**

2026-10-29 的实例：openGauss 的 `LIMIT a, b` 到底是什么语义，原探针是

```sql
SELECT 1 LIMIT 1, 2;   -- 返回 0 行
```

据此写成「openGauss 按 PG 语义（OFFSET a LIMIT b）解析，MySQL 形态会被静默错解」，并把它当成
真机实证写进了 `DialectXcFamilyTest` 的 KDoc 和 `supportsDeleteLimit` 的推理依据。换了 5 行源重测：

```sql
SELECT * FROM generate_series(1,5) LIMIT 1, 2;   -- 返回 2, 3，是 MySQL 语义（offset, count）
```

**为什么原探针无效**：单行源上「MySQL 语义：跳过 1 行取 2 行」与「PG 语义：OFFSET 1 LIMIT 2」
**给出同一个读数 0 行**。两种假设不可区分，读数不能证伪任何一方——这不是「测了但没测准」，
是探针本身没有判别力（同族坑见 `pitfall-fake-green-test-assertions` 的「假绿断言」清单）。

落地要求，写方言/分页/窗口类探针时逐条对照：

1. **行数要大于 `offset + count`**。探 `LIMIT a, b` 至少给 5 行源（`generate_series`、`VALUES`
   列表、或真实多行表），让两种语义给出**不同的行集**；
2. **断言具体返回行**，不要只断言行数。`2 行` 两种语义都可能满足；`返回 2 和 3` 只有 MySQL 语义
   能给出；
3. **先问「两种假设在这里给同一答案吗」**。给同一答案的读数不算证据，改夹具或换句式；
4. 反向验证时把**源改回单行**，新用例应当变红或退化为无区分力——变不红说明用例也没判别力。
   本轮的落点是 `DialectXcFamilyTest` 的「分页只产 PG 形态不产逗号形态」用例，以及
   「`DELETE ... LIMIT` 语法接受但语义未验证」的显式判无声明。

顺带一条同类口径：**「语法通过」不等于「语义生效」**。`EXPLAIN DELETE ... LIMIT 1` 只报
`permission denied`（说明过了语法与分析阶段），只能推出「该库接受这个语法」，推不出「真的限行」。
要断言语义必须有可写实例并观察影响行数。

### 4.9 增强捕获 agent 相关改动（M56）

1. 新增数据库驱动支持：在 `sub-projects/sql-visualizer-agent` 的 `DriverRegistry` 驱动类名单登记——采集面是 JDBC 接口级，对插件全部方言一视同仁，唯一耦合点就是这份名单（「在线但零捕获」先查名单/加载时序/loader 隐藏三类诱因）；
2. 事件字段改动必须双端联动：agent 侧 `model/SqlEvent`（Java）→ IDE 侧 `log/agent/AgentEvent` + `AgentEventAdapter` 映射——手写序列化两端各自绿、合流即断是本仓实证坑（`Jsons` 首成员逗号产出 `{,"sql":…}` 非法 JSON 曾被 IDE 全量静默丢弃），必须配格式守卫断言与往返用例，静默丢弃点必打日志；
3. agent 代码保持**纯 Java + 低版本字节码兼容**（用户应用 JVM 可能是 JDK8；`AgentLoadException: 0` 即 JDK8 二次 loadAgent 的良性表现，按幂等表容错）；agent 构建经 `embedAgentJar` 内嵌 `/agent/mps-sql-agent.jar` 随插件发行；
4. agent 侧对 JDK/驱动类的反射（`MdcAccessor` 等）自带「一次解析缓存 + 失败永久静默」降级；IDE 侧新增平台反射入口照旧登记 `PlatformSignatureCrossVersionTest` 跨版本签名护栏；
5. 接管语义改动要过「两通道并存」场景：agent 在线暂停控制台链（`SqlCaptureGate`）、降级三分支回落桥链路，`dedupeKey` 两通道同口径防双记——改动任一端还原/指纹逻辑必须对照另一端（`AgentEventAdapter` KDoc 为准）；
6. **premain 链路改动点**：注入入口 `PremainRunConfigurationExtension`（EP `runConfigurationExtension`）+ `PremainInjection` 注入决策表驱动（**三道闸门：增强开关 / agent jar 可用 / 端口协商**；注入确认闸门已随 T-EnhancedCaptureDefaultOn 删除）；agent jar 落盘 CRC32 定名、不 deleteOnExit（javaagent 打不开文件=目标 JVM 启动即终止）；端口前置协商（不复用 attach 实现）；premain 成功后跳 attach 窗口 30s；回连去重=同 pid 活动会话；premain 回连建会话点须带 clockMs 同源注入。
7. **暂停按钮（T-AgentPauseVisibility）**：增强捕获「暂停」动作在工具栏临时隐藏（动作对象保留在组内），不是开启入口；恢复 UI 需补 `AGENT_STATUS_TOPIC` 订阅，勿把它改回 `isEnhancedEnabled()` 判定。
8. **premain 里任何异常都不能外抛**（T-JRebelPremainCrash，`ee86f967`）：`AgentMain` 的 `install` 拆成兜底层与 `installOrThrow`，兜底层 `catch (Throwable)` 全吞——premain 抛异常对目标 JVM 是致命的（应用直接起不来）。降级时不写 `sqlvis.agent.active`、不置 installed，运行期 attach 仍可重试。驱动名单/织入形态登记上提为零 ASM 依赖的 `WeaveSpecs`，第三方 agent 干扰下判类不再要求 ASM 可解析。该坑真因是**类链接期就要全可见**：不调 `Opcodes` 也照炸（StackMapTable 帧引用它），删 `implements` 躲不掉；所以兜底必须用 `catch (Throwable)` 而不是 `catch (Exception)`。
9. **暂停/恢复要留兜底预算**（T-ReleasePerf8，`48049395`）：`resumePremainChannel` 用 accept 循环代际让位 + `PREMAIN_RESUME_JOIN_BUDGET_MS`（40s，盖过 30s 拍 + 5s HELLO 读）的有界 join，替掉原来的无界 join——pause→resume 竞态下旧循环会失去 `paused` 退出条件而无限 tick，发行门禁轮实测挂过 75 分钟。新增任何「等对端响应」的 join 都要给预算，并让旧循环能被代际号判退。

## 6. 🔴 并行开发铁律（多智能体协作）

本仓库常有多智能体并行开发，**任何 `./gradlew` 命令执行前必须先查共享登记表**：

```bash
python C:\Users\USER\.zcode\cli\parallel_tasks.py check    # 查活跃任务
python C:\Users\USER\.zcode\cli\parallel_tasks.py register # 有活跃任务时登记独立沙盒（分片 testShard1/2）
python C:\Users\USER\.zcode\cli\parallel_tasks.py done     # 跑完注销
```

- 有活跃任务 → **禁止直接跑默认沙盒全量**（共享沙盒互踩损坏 PersistentFS，实证 191 失败+卡死）；
- 绝不 kill 对方的 Gradle daemon / 进程；共享文件只动自己的行；
- 以 git 提交节奏判断对方活跃度；`--tests` 过滤避开对方测试领地；
- 被踩的症状：PersistentEnumerator corrupted、用户映射区域错误、断言计数中间态（如 4→5）、NoSuchMethodError（Kotlin 增量残留 → `--rerun-tasks`）。

## 7. 发布流程速查

1. 发版链路：`./gradlew releaseGate`（buildPlugin → verifyGate 三目标门禁 → verifyMarketplace 同口径在线判定 → testShards 全量 → e2eFakeIde 真机级探针；中间轮次可 `-PverifyIdes=minimal`，最终发版必须三目标；真机探针需本机 MySQL + demo 工程 + `~/.m2`，前置缺失会硬失败并给指引）；
2. `docs/变更记录.md` 追加任务记录 + `CHANGELOG.md` 新版本块（changeNotes 内容外置 `gradle/plugin-change-notes.html`，发版只编辑该数据文件，`patchPluginXml` 读取注入）；
3. `./gradlew writeUpdateManifest` 更新 `update/update.json`（Gitee 抢先体验检查源，Gitee raw 托管）；推送前可先用 `preview.update.json` 草稿 + `local-manifest-server.py` 本地清单沙盒验证通知效果；
4. 稳定版由 JetBrains Marketplace 推送；Gitee 通道为内测抢先体验（`autoCheckUpdate` 默认关，用户主动勾选开启；支持「忽略此版本」）；
5. 版本号 = `YYYY.M.D`（gradle.properties），一日一版；
6. 发布说明（docs/发行说明/）按规范编号；安装默认免重启动态生效（`update/DynamicInstallSupport`，平台动态装卸能力探测失败自动回退重启脚本；「performanceTesting 插件否决动态卸载」已被 262 反编译证伪）；跨版本反射入口签名由 `PlatformSignatureCrossVersionTest`（243/253/262）护栏保障，Gitee 推送前用 `runIdeHotSwap` 本地清单沙盒过一遍全链。
7. 双仓推送走 `dev-support/push-all.ps1`（读 `.local/*-token.json`）——**禁止裸 `git push github`**，那会退回 GCM GUI 凭据；脚本对 git stderr 视为非致命、网络间歇中断自动重试，`-DryRun` 会打印令牌故勿留日志。
8. GitHub Release 镜像用 `dev-support/mirror-releases-to-github.py`（幂等 + 自举：自动抓 Gitee 清单、按需下载 zip）：上传必须走 `uploads.github.com`（走 `api.github.com` 恒 404），只传插件 zip（主 jar 在 zip 的 `lib/` 内）。2026-10-26 已用它回填 32 个历史版本。
9. 同 tag 重发或换源发布：`dev-support/gitee-release.py --from-github` 把 GitHub Release 同步到 Gitee（需人工确认）；同 tag 重发用 `dev-support/gitee-release-update.py`（PATCH 正文 + 删旧附件再上传，**保留发行版创建时间**）。CI 发布只走 `--from-github` 这一路，CI 侧不再自动建 Gitee 发行版。
10. 云端 CI 目前跑不了本仓发版链路（GitHub Actions / Gitee Go 均不可用）：硬编码代理 7 处、`releaseGate` 依赖本机 MySQL 与 demo 工程、`Xmx4096m` 堆约束、Gitee Go 模板是 Maven 而本仓是 Gradle。发版在本机（或独立工作树）执行。
